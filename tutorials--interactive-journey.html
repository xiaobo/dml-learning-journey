Build a regional report with the interactive tutorial

We will build a February sales report with completed sales, a previous-month comparison, average customer sales, and regional share. Open A small journey through DML in a browser. Keep the page and its sibling files together for offline use.

Use the button beneath the introduction to start or resume at your next incomplete chapter.

The tutorial calculates invented rows in your browser. It does not compile arbitrary DML or connect to a database. Recorded companion queries include real compiler output. We will download a complete project at the end.

1. Identify each source row

Read the four sales in chapter 1. Find the two North rows. Choose [id] as the source dimension and check your answer.

The feedback explains why region is a grouping field rather than a unique source key. The progress indicator now shows one completed chapter.

2. Find an atomic measure

Read the model declaration in chapter 2. Select the measure that sums a source column and check the answer. We now have reusable definitions for sales and row count.

3. Reuse measures in a formula

Read DIVIDE({sales}, {cnt}) in chapter 3. For North, calculate 30 ÷ 2 = 15 and check your answer. The same formula gives 100 ÷ 4 = 25 for all four sales. A measure reference takes its value from the report's current grouping and filters.

Expand the complete declaration to see how a composite measure reuses atomic measures without a dataset: property.

4. Change the grouping

Select All sales, By region, and By sale in chapter 4. Watch the query, result table, and average calculation change together. All sales gives 100 and an average of 25. The regional view gives North 30 and South 70.

Click average_sale in the query to see its model declaration. Under References, open sales and then amount to trace the source column, or open cnt to see the row-count formula. Click a grouping field to inspect its column mapping. Close the definition with × or Escape.

Answer the question about the source dimension. It remains [id] throughout. At source-key grain the checked compiler reports an aggregation-simplification finding; that simplification relies on the declared key being unique.

5. Separate compilation from execution

Follow the model-and-query diagram in chapter 5. Choose what a successful compile produces and check the answer. Then trace the separate checks: inspect compiled SQL, validate reached source keys and SQL planning on a connection, and compare executed results with an independent answer.

6. Compare report filters and measure filters

Open the eight-row source table in chapter 6. Our original four sales now belong to February. Four January rows provide comparison history. Inspect the complete extended model.

Select North as the report region. The result shows sales = 30 and completed_sales = 10: one North sale is returned. Find +f in the completed_sales definition, then check the chapter exercise.

7. Choose a denominator

Keep North selected in chapter 7. With -d: region, the denominator is 30 and the share is 100%. Switch to -df: region. The denominator becomes 100 and the share becomes 30%.

Inspect the recorded compiler query and its strict findings. Check the exercise about retaining an all-region denominator. The report still selects North; the denominator reference has a different filter context.

8. Calculate at customer grain

Select AVG in chapter 8. Find South customer C's total of 70 in stage 1. Stage 2 averages that one customer total, giving 70. Average transaction amount is 35 because it averages two source transactions.

Switch the outer aggregate to SUM, then MAX. Observe both stages and the formula. Return to AVG and check the exercise.

9. Compare adjacent months

Read the two model definitions shown in chapter 9. previous_sales uses {sales: pp} for the previous month's value; sales_change uses {sales: pop} for growth. Select February 2025. North has sales of 30, previous sales of 20, and growth of 50%. South has sales of 70, previous sales of 50, and growth of 40%.

Select January 2025. Previous sales and growth are NULL because the example has no December facts. Check which period pp requests. Inspect the recorded companion query before treating its expected strict findings as resolved.

10. Break and repair a lookup key

In chapter 10, enable Add an invalid second North directory row. Four facts become six joined rows. North's amounts now sum to 60.

Disable the duplicate. Four facts again produce four joined rows and North totals 30. Check the exercise about source uniqueness. The compiler snapshot does not inspect these physical records.

To check the keys on a database connection, expand Catch the duplicate key with dmlc in chapter 10. Save its manager lookup query as lookup.sql beside the downloaded model. The query must reach regions for its dimension to be checked. Replace default with the connection containing your sample tables, then run:

dmlc.exe --validate-only lookup.sql --model=model.dml --connection=default --output-format=json

If that connection's DIM_REGION contains both North entries, expect DIMENSION_NOT_UNIQUE for regions. Correct the dataset dimension declaration or source data, then rerun validation. MCP clients use run_query with validateOnly: true. The browser toggle changes only this page's invented data. Validation reads the connected data, checks reached dataset dimensions, and probes the main query with EXPLAIN without executing its result rows.

11. Make missing-value behavior explicit

In chapter 11, switch from Keep NULL to Use a literal zero fallback. The same January result groups remain. Only the prior-period value changes from NULL to 0.

Read the filled measure formula and check what changes in January. The fallback supplies a value where that measure is used. It does not generate new calendar rows or decide the business meaning of missing history.

12. Build and download the final report

Chapter 12's Try it exercise asks you to build February's report for both regions. Select February, group by region, and include all regions. Select completed sales, previous sales, average customer sales, and all-region share. Sales is already selected.

Compare Model notebook · model.dml with Your question · query.sql below the controls. The notebook excerpt shows your selected measures and their dependencies. Expand the complete notebook or download model.dml to inspect the source dataset declarations. The result table follows both panes.

Choose Check chapter 12 beside the report controls. If a setting is missing, follow the feedback and try again, or choose Show explanation for guidance. Completing this exercise marks the twelfth stop complete. The completed configuration shows these expected example values:

region sales completed_sales previous_sales average_customer_sales all_region_share
North 30 10 20 15 0.3
South 70 70 50 70 0.7

The browser formats shares as percentages. The model and downloaded expected-result CSV contain decimal shares.

Choose Download the checked project. Extract the project archive to a writable directory. Open its START-HERE.txt. The archive contains the complete model, final query, source CSVs, expected result, recorded compiler output, and optional SQL Server setup with a calendar table.

To save a different report configuration, choose Download my query.sql. Only the recorded companion queries have the included compiler evidence. Other builder combinations still need compilation and SQL inspection.

Compile the downloaded project

With dmlc.exe available, open a terminal in the extracted directory and run these commands:

dmlc.exe --lint model.dml --output-format=json
dmlc.exe --compile --strict query.sql --model=model.dml --output-format=json --output-dir=gen

Inspect the diagnostics and generated SQL. The recorded capstone query has a key-union join warning, status: findings, and exit 1. This is an expected observation, not a passed strict check. Check result membership, unmatched comparison keys, customer-grain aggregation, and the final projection before using the SQL.

For optional database practice, use a new empty SQL Server database and review setup-mssql.sql. It creates the source tables and the calendar required by the time-comparison SQL. Validate the keys, execute the generated SQL, and compare every result value with expected.csv. This live database exercise has not been run as part of the documentation checks.

For connection and validation commands, follow Compile and validate a query. The language reference covers more advanced windows, classifiers, materializations, and model composition after this beginner project.

Resume or restart

Use the globe and language selector in the fixed header to switch between English, 中文, 日本語, and Deutsch. Each language keeps its own name, so you can find it without reading the current page language. The twelve lessons, questions, explanations, navigation, and feedback change together. Your answers, report settings, and completed chapters stay in place. The browser remembers your language separately from your progress. Code, field names, source values, and the downloadable project retain their original identifiers.

The fixed header shows your current chapter. Use its arrows to move between lessons, or open the chapter title to see all twelve chapters and your completed count. A check mark identifies completed chapters. At the final chapter, the return arrow opens the introduction.

Correct exercise answers save progress in this browser when local storage is available. Choose Resume learning in the chapter menu to find the next incomplete chapter. Progress stays on this device; the page sends no learner data to a server.

Choose Reset progress at the bottom of the chapter menu to clear completed exercises. If browser storage is unavailable, the lessons still work for the current page session.
