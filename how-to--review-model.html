Review a DML model

Run this technical review after the applicable checks in Forward analysis, Phase 5 pass. Review model reuse, query structure, evaluation grain, and validation evidence.

Prepare an independent review

Give a reviewer a focused bundle. Include the final artifacts and contract rather than the full conversation.

The bundle contains the following material.

  • The model and its includes, with changed definitions identified.
  • The consumer queries and original report contract.
  • The executable path, version, build timestamp, fingerprint, and dialect.
  • Compile, live validation, and result-comparison evidence.
  • The required semantic checks and their assumptions.
  • Known findings and missing prerequisites.

For a large change, assign model reuse, consumer queries, and result checks to separate reviewers. Keep each responsibility explicit. The author applies accepted fixes and makes the final delivery decision.

6.1 Reconcile the report contract

Compare each consumer query with the Phase 2 draft.

  1. Check the result grain and population.
  2. Check that all required measures resolve to the intended definitions.
  3. Check the time range, comparison period, and report slices.
  4. Check output columns, aliases, types, and effective order.
  5. Remove debug columns that the delivered report does not need.

6.2 Review model definitions

Check whether another report can reuse each new measure.

  • Merge duplicate formulas only when population, grain, filters, and NULL behavior match.
  • Move report-specific slices to the query unless the slice defines the business metric.
  • Keep intermediate measures that encode a required evaluation dimension.
  • Retain a named derivative when it is a reusable business metric or a materialization dependency.
  • Check that names, descriptions, and formulas agree.
  • Inspect warnings about similar measures before deciding that two definitions are redundant.

Lint changed models and strict-compile affected consumer queries after a merge or rename.

6.3 Review consumer queries

Check that grouping and measure modifiers express the requested report.

  • Keep a distinct explicit alias for modified measure references.
  • Remove redundant aliases on plain AGG(measure) when consumers do not need them.
  • Keep ORDER BY and LIMIT when result meaning or a consumer contract depends on them.
  • Check resolved time context and macro prerequisites.
  • Inspect join equality, source membership, fill behavior, and projected columns.
  • Keep SQL readable in saved files. Encode it as a string when a tool requires that format.

6.4 Check results against explicit assumptions

Re-run affected result checks after model or query edits.

  1. For subset counts, confirm that both counts use comparable populations.
  2. For subset amounts, account for negative values before applying an inequality.
  3. For ratios, check the declared zero-denominator and missing-input behavior.
  4. For time comparisons, check prior-period coverage and the declared NULL or fill rule.
  5. Compare representative rows with an independent result when one exists.

Do not impose a generic rule that missing prior-year data yields zero. Inspect the formula and emitted SQL. Record absent live evidence as not run.

6.5 Recheck affected artifacts

After a fix, lint changed models and strict-compile changed consumers. Re-run applicable live validation and result checks when the fix changes their inputs. Inspect SQL as well as totals, especially after a grain change or measure merge.

If a strict warning remains, report the finding. An emitted SQL artifact does not constitute a passed strict check.

6.6 Deliver the artifacts and review evidence

Return the model, consumer queries, review findings, accepted changes, and check results. Distinguish passed checks, reproduced defects, and checks that were not run.

For exports and dashboards, keep measures numeric and check output names against the consumer.

6.7 Resolve findings

Recheck accepted fixes in the updated model and affected queries. Record unresolved findings and their effect on the results.

Return to Phase 4 when a proposed optimization changes a business definition. Record that change explicitly.

6.8 Check analytical claims separately

Check business assumptions during modeling and after execution. Technical review alone does not establish that a business conclusion follows from the data.
