Model Query SQL

This page owns SQL query syntax, model discovery, aliases, grouping, and output rules. YAML query declarations describes type: query. Compile a first query provides a complete tutorial.

Two query surfaces

Syntax Format When to use
Model Query SQL .sql file or inline string SQL-literate users, MCP, CLI, dashboards
DML format type: query in .dml YAML YAML-native environments, dmlc --to-dml output

Query types

Aggregation queries

Use FROM … with at least one measure via AGG().

The name after FROM is the model file without .dml (case-insensitive). Most tutorials use the conventional pair FROM MODEL ↔ model.dml.

Model file Write in SQL
model.dml FROM MODEL
acme.dml FROM acme
渠道表现模型.dml FROM 渠道表现模型

How --model= interacts with that name (query / compile / validate-only):

You pass What happens
--model=some/dir dmlc looks for <FROM>.dml inside that directory (FROM MODEL → dir/model.dml, FROM acme → dir/acme.dml)
--model=acme.dml that file is the model; SQL must say FROM acme (not FROM MODEL)
omitted same discovery beside the SQL file (or on the model search path)

Do not put .dml in the FROM clause. Nested queries/ layouts: put the .dml beside the SQL, or pass --model= as the directory that contains it.

explain_change (dmlc -e) and setup (dmlc -s) take a .dml file, not a directory.

-- model.dml
SELECT product, dt_month, AGG(sales)
FROM MODEL
WHERE dt_month = date(current_date, 'start of month', '-1 month')
GROUP BY product, dt_month

-- acme.dml  (dmlc --model=acme.dml …  or  --model=<dir containing acme.dml>)
SELECT product, dt_month, AGG(sales)
FROM acme
GROUP BY product, dt_month

In the IDE, a pinned Model may still let navigation treat FROM MODEL as that pin. On the CLI, keep FROM aligned with the file you use (or with the .dml discovered under --model=<dir>).

Detail queries

Use FROM <model>.<dataset> for dataset rows. Direct GROUP BY is rejected: define reusable measures and query the model for grouped metrics. Use AGG() on the model aggregation surface.

-- model.dml
SELECT dt_date, transaction_id, raw_amount
FROM MODEL.transactions
WHERE dt_month = date(current_date, 'start of month')

-- acme.dml
SELECT ClaimNumber, ClaimOpenDate
FROM acme.Claim

Detail queries expose dataset rows. They also accept the checked ungrouped aggregate and window expressions. A direct GROUP BY is rejected. Aggregation queries expose reusable model measures at the requested grouping.

Model Query SQL specification

Fundamental constraints

Prohibited Why Alternative
Subqueries Not supported DML measures with modifiers or HAVING
UNION / UNION ALL Not supported Separate queries or measures with different filters
JOIN Not supported pk(...) in .dml
{...} on bare columns Braces are for .dml only — silently stripped Use bare names: SELECT product, AGG(sales)

Window functions (OVER()) are allowed in Model Query SQL — the compiler passes them through to generated SQL. For common patterns, prefer fn-macros from system_macros.dml (rank, rank_asc, pot, grand) — see Function modifiers. Where OVER belongs in a .dml model (window placement): Window placement.

SELECT rules

  • Aggregation: Use AGG(measure) for every measure. Use bare names for dimensions.
  • Detail: Use bare names for all columns. Add DISTINCT when listing unique values.
-- Aggregation
SELECT product, dt_month, AGG(sales), AGG({sales: yoy}) AS sales_yoy FROM MODEL GROUP BY product, dt_month

-- Detail
SELECT DISTINCT product FROM MODEL.transactions

Alias rules

Pattern Alias needed?
AGG(sales) No — auto-aliases to sales
AGG(sales) AS sales accepted but redundant(pass-through)
AGG({sales: yoy}) Yes — AS sales_yoy
AGG(sales, 'pop') AS sales Wrong — circular reference; use AS sales_mom
AGG({sales: yoy}) AS sales Wrong — circular reference; use AS sales_yoy

A prior select-list alias is a SQL result column, not a measure. When a later expression uses that name, such as AGG(current_value) after AGG(sales) AS current_value, the name refers to the prior result column. It does not fall back to an unrelated same-named DML measure.

Aliasing a measure reference with a modifier back to the measure's own name (e.g. AGG(sales, 'pop') AS sales) causes a circular reference because the compiler treats the alias as a redefinition of the measure. Use a distinct alias (e.g. AS sales_mom). Without a modifier, AGG(sales) AS sales is accepted as a redundant pass-through.

For semantic tooling, only AGG argument 0 is a measure-reference position. It accepts an identifier (AGG(sales)) or a modifier expression (AGG({sales: yoy})). A curly token outside that modifier position is not a measure reference. SQL keywords, function names, relation aliases, and cast types are syntax, not column references.

WHERE rules

  • Use bare names for columns: WHERE customer = 'John Doe'
  • Predicate order is not a syntax requirement.
  • Use first-day format for time filters: dt_month = '2024-01-01'
  • Prefer = over BETWEEN for single periods
  • Don't add redundant null filters unless explicitly requested

GROUP BY rules

  • Every non-aggregated SELECT field must appear in GROUP BY
  • Keep GROUP BY order aligned with SELECT when output order matters. The checked compiler accepts a different order and may reorder visible columns; inspect artifacts.sql and effectiveOutputOrder
  • Time modifiers need a resolved time context: a grouped time field or a time filter can supply it. Prefer explicit time grouping for multi-period reports; a single-period filter can supply a hidden time context
-- Correct: time modifier + matching time field in GROUP BY
SELECT dt_month, AGG(sales), AGG({sales: yoy}) AS sales_yoy
FROM MODEL
GROUP BY dt_month

-- Wrong: yoy with neither a grouped time field nor a time filter
SELECT product, AGG(sales), AGG({sales: yoy}) FROM MODEL GROUP BY product

ORDER BY / LIMIT

  • Always specify ASC/DESC
  • Only add if semantically necessary (Top N, extreme values)
  • Don't add "nice to have" sorting

Measure reference rules

  • In queries: AGG(measure) — always wrap in AGG()
  • Modifier form: AGG({measure: modifier}) or AGG(measure, 'modifier')
  • Never use {...} on bare columns in Model Query SQL (except modifier form inside AGG) — braces on bare columns are silently stripped to the bare name; use bare names directly
  • If the compiler says use existing measure "X", use AGG(X) — don't re-express the formula

Time handling

Field naming: dt_date, dt_week, dt_month, dt_quarter, dt_year — all first-day format.

System derivation: when the model explicitly declares a finer standard time field such as dt_date, supported coarser fields such as dt_month are available automatically in that dataset. Use the derived name directly; do not add duplicate physical columns only to satisfy a query, filter, or editor diagnostic. Go-to-definition on the derived name resolves to the explicit source time column.

Filtering: WHERE dt_month = '2024-01-01' (first day, = not BETWEEN for single periods).

The date function reference describes SQLite-style expression forms. The compiler lowers supported forms to the selected dialect.

Multiple time fields are accepted as input, but acceptance does not guarantee that every requested field survives in the result. On the 2026-10-16 build, the two_times probe requests dt_year and dt_month but emits only dt_month and the measure. This is a known output defect. See release evidence.

HAVING

-- Customers with outstanding balance
SELECT customer, AGG(outstanding)
FROM MODEL
GROUP BY customer
HAVING AGG(outstanding) > 0

-- Products selling less than last month
SELECT product, AGG(sales) as this_month, AGG(sales, 'pp') as last_month
FROM MODEL
WHERE dt_month = date(current_date, 'start of month')
GROUP BY product
HAVING AGG(sales) < AGG(sales, 'pp')

Measure-as-dimension note: a predicate on the classifier label (and/or sibling measures at label grain) is a label-pass filter. Model Query text may show HAVING, but the semantic contract is “after the label exists.” Compiled SQL often applies it as WHERE on the post-label CTE. Do not treat a doc-surface HAVING as permission to filter before classification. See classifier-label filters.

Aggregation lookup table

Model Query SQL (FROM MODEL) requires all aggregations to go through measures defined in model.dml or inline /** dml ... **/ blocks (inline measures). Raw-column aggregations are rejected.

What you want Wrong (will fail) Right
Total rows COUNT(*) Define 笔数: COUNT({ID}) in model.dml or inline, then AGG(笔数)
Sum of raw column SUM(出厂价金额) Define 销售额: SUM({出厂价金额}) in model.dml or inline, then AGG(销售额)
Average of raw column AVG(销售数量) Define 均价: DIVIDE(SUM({出厂价金额}), NULLIF(SUM({销售数量}),0)) in model.dml or inline, then AGG(均价)
Scalar MIN/MAX of dimension SELECT MIN(dt_month) FROM MODEL Use detail dataset: SELECT MIN(dt_month) FROM MODEL.<dataset>
Filter groups by row count HAVING COUNT(*) > 100 Define 行数: COUNT({ID}) in model.dml or inline, then HAVING AGG(行数) > 100

The only exception is scalar aggregation on detail datasets (FROM MODEL.<dataset>) for metadata exploration — not for business-metric dashboards.

Inline measures (/** dml ... **/)

Define temporary measures directly in Model Query SQL without editing .dml files. The compiler loads the .dml named by FROM (FROM MODEL → model.dml; FROM acme → acme.dml), merges inline definitions, then compiles the query.

/** dml
temp_sales:
    type: measure
    dataset: transactions
    formula: SUM({amount})
**/
SELECT product, AGG(temp_sales) FROM MODEL GROUP BY product

Use cases:

  • Ad-hoc aggregation without modifying .dml (solves the measure requirement)
  • Multi-level aggregation with +d and dimensions — define intermediate measures inline
  • RFM analysis — define customer-grain measures inline, query with rank fn-macros

Rules:

  • Must use multi-line YAML format (one property per line)
  • Inline measures can reference existing .dml measures and datasets
  • Inline measures can reference each other (defined earlier in the block)
  • Same syntax as .dml measure definitions (type, formula, dataset, dimensions)
