Reproduction

The reference probe guide describes the runner and its output. From the dml-dmx directory, the current command is:

node scripts/verify-reference.cjs scripts/dmlc-mcp/dmlc.exe

The current manifest contains build identity and expected SQL, diagnostics, and exits. The September manifest preserves the old expectations. Fixture counts are derived rather than maintained as prose:

node -e "console.log(require('./references/verification/manifest.json').cases.length)"

The runner copies inputs to an OS temporary directory. Each case retains stdout, stderr, emitted artifacts, and command arguments. report.json records expected observations and unexpected changes. Matching an expected warning or defect does not make that feature pass.

The reviewed run against this fingerprint reports no unexpected changes. The tutorial model also passes lint before strict compilation. Expected strict findings and known compiler gaps remain recorded in the manifest.

Validation limits

A strict success does not prove dataset-key uniqueness or SQL correctness. The two_times case demonstrates an output defect despite a zero exit. DATASET_GRAIN_UNVERIFIED notes state that compilation has not checked source keys against live data.

The classifier probes establish the checked stages and aliases on this build. Their result values still require database validation. Broader temporal classifiers, materialize classifiers, arbitrary window frames, and other dialects need separate evidence.

The language contract requires rejection of conflicting dimension modifiers. The two conflict probes show that the current executable does not enforce that requirement. Their accepted SQL is recorded as a compiler gap, not a supported authoring pattern. Report-filter population rules need their own evidence. A plan or source test name alone does not establish executable behavior.

Publication boundary

Examples outside the fixture directory can be partial patterns with model dependencies. Only the recorded probes have the evidence described here. Compiler observations, live validation, and result parity remain distinct.

The improvement plan records proposed compiler work. Reference schema edits do not change the distributed executable. An upgrade needs a new fingerprint and review of changed diagnostics, SQL, and applicable database results.
