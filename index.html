01 / The rows

First, know what
one row means.

The traveler counted four sales.
Each sale needed its own name.

A dataset maps a source table into the model. Its dimension: [id] declares the complete source-row key: here, one sale identified by id.

Two sales can share a region. That makes region useful for grouping, but insufficient as the source key.

02 / DML

Keep the definitions
in one notebook.

"What shall we call the total?"
The traveler wrote: sales.

DML defines the model in YAML. FACT_SALES names our dataset; TABLE_SALES is its physical source table. Measures name reusable business calculations.

Atomic measures bind to one dataset and aggregate its rows or column expressions without referencing other measures. Here, sales sums amounts; cnt counts rows.

Read the model names

Bare names in model formulas refer to physical SQL objects.

Keep a reusable calculation in the model. Choose report grouping and filters in the query. See DML, DMX, and Model Query.

model.dml · the reusable model

FACT_SALES:
  type: dataset
  table: TABLE_SALES
  dimension: [id]
  columns:
    id:
    region:
    amount:
  measures:
    sales: SUM({amount})
    cnt: COUNT(1)

{amount} references the model column amount. An empty column entry maps to the physical column with the same name.

03 / DMX

A calculation can
reuse what is known.

The traveler wanted an average sale. The model already had the total and the count.

DMX is the expression syntax inside a formula. {sales} references a measure definition, not a fixed total. Its value depends on the report's grouping and filters.

average_sale is a composite measure because it reuses measures. For a zero denominator, DIVIDE returns NULL, meaning no value is available.

For North, the same formula gives 30 ÷ 2 = 15. For all four sales, it gives 100 ÷ 4 = 25.

The formula, in DMX
DIVIDE({sales}, {cnt})

salesSum the amounts.

cntCount the source rows.

See the complete measure declaration
average_sale:
  type: measure
  formula: 'DIVIDE({sales}, {cnt})'

This composite measure omits dataset:. Its atomic dependencies select the source dataset. DMX also appears in query expressions.

04 / Model Query

The same measures.
A different view.

The traveler turned the telescope toward the regions.

A query chooses what one result row represents. AGG(sales) requests the named measure; SUM({amount}) stays in the model. The grouping changes; the model definitions stay the same.

If you know PivotTables, GROUP BY region is like putting region in Rows. AGG is specific to Model Query; it is not a standard SQL function.

Choose the report grouping

Try All sales, then By sale. Expect one total row, then four individual rows. Return to By region.

query.sql · Model Query

SELECT region, AGG(sales), AGG(average_sale)
FROM MODEL
GROUP BY region

FROM MODEL selects model.dml, which contains the dataset and all three measures above.

model.dml · a reusable measure

completed_sales:
  type: measure
  formula: '{sales: {+f: {status: completed}}}'

{sales: ...} reuses sales with a modified context. Here, +f adds the status filter to this measure reference.

Report WHERE selects the report's rows. +f restricts the inputs to completed_sales. The other measure still includes returned sales.

09 / Compare periods

Look back one month.

The traveler kept January's pages beside February's.

model.dml · comparison measures

previous_sales:
  type: measure
  formula: '{sales: pp}'
sales_change:
  type: measure
  formula: '{sales: pop}'

pp requests the previous period's value. pop calculates its growth rate. This example uses the standard dt_month field with dates at month start. See time context.

In February, North has 30 in sales and 20 in previous sales. Its growth is 30 ÷ 20 − 1 = 50%. Switch to January. Expect NULL comparisons because the example has no December history. Return to February before checking your answer.

10 / Attach an attribute

A lookup needs
one matching destination.

The regional directory names Ada for North and Lin for South. The model looks up the manager through the directory's complete key, [region]. Add an invalid duplicate North entry and inspect the joined rows.

regions:
  type: dataset
  table: DIM_REGION
  dimension: [region]
  columns:
    region:
    manager:

# Inside FACT_SALES.columns:
manager: 'pk(region).{regions}.manager'

Regional directory

February rows after lookup

The duplicate toggle deliberately violates the declared key. Ordinary compilation does not read source rows. With a database connection, dmlc --validate-only checks the complete dataset dimensions reached by the query and reports DIMENSION_NOT_UNIQUE when the declared key is not unique.

Catch the duplicate key with dmlc

For database practice, save this query as lookup.sql beside the downloaded project's model.dml. Selecting manager makes the query reach the regions dataset.

SELECT manager, AGG(sales)
FROM MODEL
WHERE dt_month = '2025-02-01'
GROUP BY manager

Run validation on the connection containing your sample tables. Replace default with that connection's ID.

dmlc.exe --validate-only lookup.sql --model=model.dml --connection=default --output-format=json

If that connection's DIM_REGION contains both North entries, expect DIMENSION_NOT_UNIQUE for regions. Correct the dataset dimension declaration or source data, then rerun validation. The MCP equivalent is run_query with validateOnly: true.

Validation checks observed keys and probes the main query with EXPLAIN; it does not execute the report's result rows. This browser toggle changes only the invented data on this page, not your database.
