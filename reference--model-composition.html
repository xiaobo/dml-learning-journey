Model composition and name resolution

This reference defines same-file visibility, include scope, and logical versus physical names in dataset SQL.

Same file #

The checked build resolves same-file forward references. A measure can precede its dataset or another measure. A calculated column can precede its dependency, and a pk() target dataset can appear later. Dependency-first order helps readers but is not a compilation requirement for these cases. Missing names and cycles remain errors.

Includes #

Each included file resolves from its own definitions and includes. A child cannot borrow a dataset defined only in its parent. A failed include invalidates the containing model. Include paths resolve relative to the including file first. Environment model paths are deployment inputs and do not declare dependencies.

Session history does not extend a module's declared visibility. A reusable base model can own shared datasets and measures, with each report including that model.

Logical versus physical SQL #

In dataset sql:, FROM {Customers} references the logical dataset. FROM Customers names a physical relation. Within column formulas, {net_amount} expands the model column, while bare net_amount is physical SQL. Reverse-generated SQL can deliberately retain physical references.

Direct query files #

For direct DML compilation, the query key must match the file stem: report.dml contains report: {type: query, ...}. A reusable model without a query is consumed by Model Query SQL; its FROM name follows the model filename (query discovery).

Check includes, names and generated SQL with your installed compiler before running a report.
