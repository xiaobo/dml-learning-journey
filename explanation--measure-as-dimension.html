Measure-as-dimension

Measure-as-dimension calculates a label per entity, then groups metrics by that label. The label has a query-dimension role. It does not identify source rows.

Entity keys and evaluation stages

Classification needs a complete entity key because a label belongs to an entity at a particular grain. Let Q be the ordinary report fields and K the entity key. With +d: K, the classifier is evaluated at Q ∪ K. The compiler attaches the label by the complete key, then aggregates ordinary metrics at Q plus the label.

Given atomic sales: SUM({amount}), this query fragment groups customers by their sales value.

report:
  type: query
  columns:
    dimension:
      - sales_bucket: '{sales: {+d: customer}}'
    total_sales: 'SUM({sales: {+d: customer}})'

The explicit outer SUM adds the sales of customers with the same label. This example uses the sales value itself as the label. A business bucket requires its own classifier definition and verification.

The classification use site requires an explicit key. A bare {measure} is rejected. A finer stage inside the measure definition or a sibling metric does not supply the missing key.

The 2026-10-16 build compiles the checked +d: customer and dimension: [customer] count classifiers to customer aggregation followed by label grouping. These probes establish the checked forms only.

Population and reaggregation

Classification scope, entity membership, and report scope are separate decisions. -d retains time filters, so removing time grouping does not imply lifetime classification. A NULL label can be a valid bucket. It does not prove that an entity is absent, and classification does not create inactive entities.

Multiple labels need compatible complete entity keys and independent definitions. Additive amounts can be summed from entity grain. Ratios, averages, and distinct counts need components that preserve their definitions across reaggregation.

Label-channel filters

A filter over a classifier label or sibling measures at label grain belongs after classification. DML queries can express such a predicate under filters:, for example "{首购月} is not null OR {销售额} > 0":.

Model Query can represent a measure predicate as HAVING. The semantic stage matters more than that keyword: compiled SQL commonly uses WHERE on the relation produced by classification. Moving the predicate before classification changes the population used to calculate the label.

Build evidence and limitations

The 2026-10-16 build of 0.3.16 emits two-stage SQL for the checked sales-value and COUNT(1) classifiers. Both explicit-key forms pass strict compilation.

The 2026-09-24 build emitted invalid GROUP BY COUNT(1) for the count classifier with +d and failed its replacement-dimension form. Those defects do not reproduce in the current probes.

The checks inspect compilation and SQL shape. They do not establish database execution or result parity. Release evidence records complete inputs and build identities.

This feature covers query columns.dimension. It does not establish support for classifiers in materialize.dimension_columns. That capability remains deferred in the improvement plan. Temporal classifier combinations and SQL round trips need separate evidence.
