Extend DML with custom modifiers and database functions

On this page

  • Calling a function defined in your database
  • Validate the function on the intended connection

DML is extensible at two distinct layers: define reusable measure/time transformations in DML, or call scalar functions installed in the target database. Custom modifiers compose with measure references; database functions provide calculations whose implementation belongs to that database.

Use a custom macro to reuse a time transformation or a formula over a caller-selected measure. Read the modifier reference for invocation and composition rules.

Custom macro definitions (dt-macro and fn-macro) #

Users can define their own macros in .dml — both dt-macro (time-range shifts) and fn-macro (formula wrappers). Define once, reference by name in any measure or query, just like built-in modifiers.

Two macro types:

Type Purpose Key property {measure} placeholder
dt-macro Shift/expand the time window value: (single-point shift) or range: [start, end] No — operates on time context
fn-macro Wrap the measure in a derived formula formula: using {measure} Yes — replaced by the caller's measure

Use value: for a time-point shift and range: [start, end] for a time window. A fn-macro uses {measure} for the caller's measure; a dt-macro uses {dim_dt} for the resolved time field. An optional prerequisite: restricts valid evaluation grains.

Choose the extension point #

You want to… Use What you maintain
Apply one calculation to several metrics fn-macro A DML formula over {measure}
Reuse a time shift or window dt-macro A DML time transformation
Reuse an existing database calculation A database scalar-function call The database function, its permissions and deployment

Custom modifiers keep analytical intent in the model and use the same invocation syntax as built-in modifiers. Database functions reuse logic close to the data, but introduce a dependency on that database's function implementation. Neither removes the need to choose the correct evaluation grain.

A verified composition example #

Custom modifiers use the same reference form as built-in modifiers. They do not require editing the compiler.

Start in an isolated DuckDB practice database with two sales:

CREATE TABLE sales(id INTEGER, dt_month DATE, amount DECIMAL(12,2));
INSERT INTO sales VALUES
  (1, DATE '2025-01-01', 20),
  (2, DATE '2025-02-01', 30);

Save this complete model as model.dml:

dialect: duckdb
S:
  type: dataset
  table: sales
  dimension: [id]
  columns:
    id:
    dt_month:
    amount:
  measures:
    sales: SUM({amount})
double_value:
  type: fn-macro
  formula: '{measure} * 2'
prior_month:
  type: dt-macro
  value: date({dim_dt}, '-1 month')

With January sales of 20 and February sales of 30:

SELECT AGG({sales: double_value}) AS doubled,
       AGG({sales: prior_month}) AS previous,
       AGG({sales: {double_value, prior_month}}) AS previous_doubled
FROM MODEL
WHERE dt_month = '2025-02-01'

Save the query as query.sql. With the practice database configured as default, run:

dmlc --compile --strict query.sql --model=model.dml --output-format=json
dmlc --validate-only query.sql --model=model.dml --connection=default --output-format=json
dmlc query.sql --model=model.dml --connection=default

The executed values were 60, 20, 40. Strict compilation, validate-only and execution all passed on the checked DuckDB connection. The model declared dialect: duckdb, a unique source id, dt_month, and sales: SUM({amount}).

This is reusable language-level composition: the macro receives the caller's measure and its evaluation context. It is not an arbitrary compiler plugin API. Grain rules, time prerequisites and modifier ordering still apply. A custom name does not bypass those rules.

Calling a function defined in your database #

DML can retain scalar function calls in generated SQL; the database supplies the implementation. For example, install this function in the DuckDB practice database before running DML:

CREATE FUNCTION business_net(x) AS x * 0.8;

DuckDB implements this form as a persistent SQL scalar macro. It verifies database-defined scalar-function invocation, not Python UDF registration, aggregate UDFs or table-valued functions.

Add the following entry beside sales under S.measures to call the function on source values before aggregation:

# Under the sales dataset's measures:
net_sales: SUM(business_net({amount}))

Then compare that measure with a call on the aggregated result:

SELECT AGG(net_sales), business_net(AGG(sales)) AS net_total
FROM MODEL
WHERE dt_month = '2025-02-01'

Both returned 24 for February sales of 30. Generated SQL retained SUM(business_net(amount)) and business_net(SUM(amount)). These are different evaluation stages: their equality here follows from the linear function. Rounding, thresholds or other nonlinear functions can give different results; choose the stage deliberately.

Validate the function on the intended connection #

DML does not install the function or translate its implementation between databases. The function must be visible to the executing connection, accept the generated argument types, and be permitted for that database user. Function naming, schema qualification, deployment and portability remain database-specific.

An intentionally missing function passed strict compilation, then failed validate-only during EXPLAIN (exit 65); direct execution failed (exit 70). Therefore compile success alone does not establish that a UDF exists or is callable. Use compile and validate, then compare actual results.

What was verified #

The examples above ran with dmlc 0.3.16, executable SHA-256 c019a84c3208aee31cb5fa068232fa24d3258e9cdc83dfc2a91584a86a5ba091, and DuckDB 1.5.5. They verify custom fn-macro, custom dt-macro, their composition, source-level and aggregate-result scalar calls, and missing-function diagnosis. Other engines, schema-qualified names, procedural/native UDFs, aggregate UDFs and table functions were not tested here.
