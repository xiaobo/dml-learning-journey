YAML query declarations

This page owns type: query, columns, filters, materialization selection, and after:. The query consumes the same model measures as Model Query SQL.

Filename constraint: When compiling a .dml file with dmlc -c, the type: query block name must match the filename (without .dml). For example, a file named my_report.dml must contain my_report: type: query, not some_other_name: type: query. The compiler rejects mismatches with: query name should be <filename> (the same as filename) instead of <block_name>.

Basic structure

my_report:
    type: query
    allows: ALL              # optional: consider compatible materializations

    columns:
        dimension:
            - dt_month
            - product
        sales:               # measure reference (no AGG needed)
        sales_yoy:
            formula: '{sales: yoy}'

columns: is required. Its non-dimension keys name output columns; their values are formulas or direct measure references. An optional dataset: selects the dataset-query form and cannot be combined with columns.dimension.

Query filters have these forms. Each key names a filter that measure-reference modifiers can address.

Value form Meaning
<column>: <value> Equality on the column with the same name
<column>: [a, b] Membership in the listed values
<name>: {column: <column>, value: <value>} Named equality filter on an explicit column
<name>: {column: <column>, range: [lo, hi]} Named inclusive range on an explicit column
<name>: {visibility: hidden, default: on} Hidden filter with its default enabled

The filter placement rules define which stage receives each predicate.

Detail vs aggregation

Mode How to specify Constraints
Aggregation No dataset: key Measures allowed; compiler aggregates
Detail dataset: DATASET_NAME No measures; raw columns only 
# Detail query
product_list:
    type: query
    dataset: DATASET_PRODUCTS
    columns:
        dimension:
            - product

Auto-join of multi-dataset measures

When an aggregate query references measures from different datasets, they compose through FULL OUTER JOIN semantics on the shared dimension fields: rows that exist in only one dataset still appear, with NULL for the other dataset's measures.

The emitted join type follows the proven population contract. The compiler starts from FULL OUTER JOIN and reduces each join to the strongest type proven by query filters: "{primary_measure} is not null": in filters: both prunes secondary-only rows and lowers the emitted join to LEFT JOIN; presence guards on both sides yield INNER JOIN. The guard matches a golden SQL LEFT JOIN only when valid primary groups cannot have a NULL primary measure. Prove that NULL/empty-group contract and inspect generated join types and output; otherwise the filter also deletes valid groups. Keep the guard out of after: so it remains visible to lineage, review, and reuse.

The formula-as-key shape is required: "{expr}": with an empty value. name: {condition: …} is schema-invalid.

Column references in DML format

Column type Syntax Example
Dimension field from same dataset bare name product:
Dimension field from another dataset "{DATASET}.column" prod_id: "{DATASET_PRODUCTS}.prod_id"
Measure bare name sales:
Measure with modifier formula: sales_yoy: {sales: yoy}

Pitfall: A bare column name in an aggregate query without dataset: will fail if the column lives on a specific dataset. Use "{DATASET}.column" form.

Auto-aliasing and direct reference

A query column with no formula can resolve to a measure or dataset column by name match — this is auto-aliasing. Three levels exist:

Level Mechanism Example Result
column (direct reference) Dataset columns: entry with no formula; DML name = table column name prod_amount: SUM(prod_amount) — name passed through as-is, no aliasing
Query column → measure (auto-aliasing) Query column with no formula; column name = measure name revenue: (measure revenue exists) Compiler substitutes the measure's formula: expression
Query column → dataset column (auto-aliasing) Query column with no formula; column name = dataset column name, derivable from the query dimension prod_name: (dataset column via pk({prod_id}) chain) Compiler resolves from dataset definition

Key behaviors:

  • dmlc -c does not validate dataset column existence against the table schema — a mismatched name compiles but produces runtime SQL errors. Use validateOnly (requires database connection) to catch mismatched names.
  • When a query column name matches neither a measure nor a derivable dataset column, it errors as not defined, add formula?.
  • When the query column name differs from the measure name, add an explicit formula (display_name: '{measure_name}') or rename the measure with abbr: (semantic review checks).
  • A dataset column that is not derivable from the query dimension (e.g., a raw fact column with no dimension-field dependency) errors with cannot be derived from dimension [store_id].
  • A pass-through column (no formula:) may carry metadata properties (description:, visibility:) in object form without requiring formula:. Example: revenue: { description: 'Total revenue' } auto-aliases to measure revenue while attaching the description.

visibility: hidden

Hides a column from the final query output while keeping it available in intermediate temp tables.

Aspect Behavior
Final SELECT Hidden columns are normally absent, but a hidden column referenced by a filter/HAVING may be carried into final output; inspect generated SQL before claiming exact output
Intermediate temp tables Hidden columns remain available for JOIN conditions and filters:
filters: referencing hidden dimension fields Compiles, but can strengthen optional joins and can force helper materialization; verify generated SQL
after: SQL referencing hidden dimension fields by name Breaks — query columns refer to nonexistence source column
PK chain Intact — no PK warning fires from visibility: hidden alone

Guidance: Remove visibility: hidden if after: references the dimension field by name. Keep it if after: only uses measure columns. For contracted outputs, compile and confirm that no hidden helper reaches the final result; extra columns are acceptable only when the output contract explicitly allows them.

YAML forms that work: - dim: {visibility: hidden} or a nested map whose keys sit under the dim entry. Sibling visibility: at the same indent as the dim key (under-indent) is a schema lint error — write the inline or nested form instead. Always inspect compiled SELECT when using dmlc -c alone (schema lint runs in the editor / dmlc --lint).

Query dimension format

columns:
    dimension:
        - dt_month
        - product
        # Correct: list dimension field names only

Wrong: Don't put cross-dataset column mappings among the query dimension fields. Define those formulas as separate query columns:

# Wrong
columns:
    dimension:
        - f_tag_id: {DATASET_PT}.id

# Correct
columns:
    dimension:
        - f_tag_id
    f_tag_id: "{DATASET_PT}.id"

Exception — measure-as-dimension: a query-dimension entry may bind a measure (usually with +d) so the query grain groups by that measure value:

columns:
    dimension:
        - first_purchase_month: '{first_purchase_month: {+d: store_id}}'
    sales:

Declare the classification entity key explicitly with +d (preferred) or dimension:. Multiple independent fields are allowed when their complete keys match; ordinary output measures must safely roll up from Q ∪ K. Label-channel filters (formula filters: / Model Query HAVING) apply after the label exists — see Measure-as-dimension. Do not use this exception for physical/{DATASET}.col mappings.

Filter placement hierarchy

Filter placement is a semantic decision, not a syntax preference:

Layer Where What goes here
Query filters: Query block Report-specific slices (channel, brand, date range)
Intermediate column / measure .dml dataset or top-level measure Metric-specific eligibility when rejected rows may remain in groups with NULL measures
Dataset sql: Dataset definition Permanent source-population invariants or constructs DML cannot express declaratively

Moving a source WHERE condition into a measure gate changes row existence unless rejected-only groups are impossible or contractually equivalent to present groups with NULL measures. Prove this explicitly; when it is false or unknown, keep a row-removing representation.

Structured range semantics: range: [start, end] in query filters: includes both endpoints at the declared dt_<grain>. For 2025 daily data use ['2025-01-01', '2025-12-31']; for monthly data use ['2025-01-01', '2025-12-01']. A dialect may implement this with an exclusive physical bound such as < dateadd(day, 1, end), but the DML input end remains the last included value.

List vs range — a common footgun: A bare list value dim: ['a', 'b'] compiles to WHERE dim IN ('a', 'b') (exact match of those two values), not an inclusive range. For date dimensions this is a silent data-loss trap: dt_date: ['2024-01-01', '2025-12-31'] returns only rows on those two days, not the full 2-year span. Always use range: [start, end] when you mean an inclusive interval:

# Wrong — only 2 days of data
filters:
    dt_date: ['2024-01-01', '2025-12-31']

# Right — full inclusive range
filters:
    dt_date:
        range: ['2024-01-01', '2025-12-31']

Common filter pitfalls:

Symptom Fix
[dataset …] [filters]: not supported Move to query filters:, measure formula, or sql: WHERE
referred column {DATASET}.col is undefined in query filter Use string form: "{DATASET}.col = value":
Two-element list on a date dimension returns only 2 days Use range: [start, end] instead of bare list — dim: [a, b] compiles to IN (a, b), not BETWEEN
Complex EXISTS / PK chain in query filters: Use measure-input gating only for metric-specific eligibility. If the condition removes source population and migration still requires dataset sql:, record the minimal escape under the sql-to-dml-v2 native-first contract.

pk chaining

# Single PK lookup
formula: 'pk(customer_id).{DATASET_CUSTOMERS}.tier'

# Composite PK — all columns required
formula: 'pk(brand_id, tag_id).{DATASET_PRODUCTS}.state'

Arity rule: the number of keys inside pk(...) must match the number of dimension fields in the target dataset's dimension:. A mismatch produces expect N expr(s) to query dataset X using pk, but got M (see Troubleshooting index P65).

Nested chains: a column derived from one pk() chain may serve as the key in another pk() chain. The compiler traces the derive chain and emits the corresponding nested LEFT JOINs. This is the native way to model "lookup an attribute, then use that attribute to look up another attribute" without sql: or after:.

# fact dataset
columns:
    store_id:
    # First hop: store_id → Dim Customer → hq_id
    hq_id: pk({store_id}).{Dim Customer}.hq_id
    # Second hop: hq_id (itself a pk chain result) → Dim Customer → store_code
    hq_code: pk({hq_id}).{Dim Customer}.store_code
    # Third hop: hq_id → Dim Customer → org_id, then org_id → Dim Org → emp_name
    hq_org_id: pk({hq_id}).{Dim Customer}.org_id
    hq_emp_name: pk({hq_org_id}).{Dim Org}.emp_name

Same-file forward references are supported in the checked build, including column dependencies and pk() targets. Keep dependency-first order for readability. Includes have a separate visibility boundary; see model composition.

after: clause

after: is optional. Without it, the compiler orders ascending by the compiler-resolved visible output columns that represent the query dimension fields, in resolved dimension-field order. A hidden dimension field may therefore be ordered through a visible query-column alias rather than its authored field name. With no effective output dimension, no row order is promised. An omitted NULL-order modifier uses the target dialect's default.

Any after: block takes ownership of the final result order. In particular, select * from {QUERY} without its own ORDER BY removes the compiler's default order. Use after: only when a business-significant custom direction, NULL ordering, tie-break, measure/expression order, or TOP/LIMIT differs from the default. Don't re-aggregate:

my_report:
    type: query
    columns:
        dimension: [product]
        sales:
    after: 'select * from {QUERY} ORDER BY sales DESC LIMIT 10'

When after: is present, {QUERY} is mandatory: it names the compiled query result consumed by the post-query statement. “Ordering only” means no business logic beyond this wrapper plus ORDER BY/TOP/LIMIT. Structured compile output exposes the final decision as effectiveOutputOrder; semantic manifests expose the same object under each queryContracts[] entry. The upstream compiler emits a redundant ORDER BY warning when an authored order matches the query's default output order. Follow its contextual hint: remove only the redundant ORDER BY clause when other important after: processing remains; remove the entire block only when nothing else remains.

The machine contract uses status: known with source: default_dimension_order | explicit_after | none and ordered items containing expression, direction: asc | desc, and nullOrdering: dialect_default | first | last. A manifest query that cannot compile uses status: unavailable (with a reason) and does not guess items. explicit_after is retained even when the post-query SQL has no ORDER BY, making the absence of a final order an explicit result of the authored block. For the .sql Model Query compile surface, the same explicit_after protocol bucket denotes an authored top-level ORDER BY; otherwise a compiled final order is classified as default_dimension_order.

Wrong: Re-aggregating with group by in after: on a standard measure query. Let the query block aggregate measures.

allows: ALL

To permit the compiler to consider all compatible materializations:

my_report:
    type: query
    allows: ALL
    columns:
        dimension:
            - dt_date
        sales:

allows: controls eligible materializations. ALL permits candidates; NONE disables their use; explicit names constrain candidates. Eligibility still depends on grain and filter compatibility. It does not relax measure dimensions: or grant arbitrary query grain. See materialization declarations.

YAML syntax pitfalls

  • Quote formulas containing :, {, or -: formula: 'SUMIF(...)'
  • Dimension field under measures:: Wrong — declare under dimension: only
  • dataset: on composite measures: Wrong — omit dataset: when formula references other measures
  • Mismatched dimension field names across datasets: Align to one name (e.g. tag_id) and map in columns:
