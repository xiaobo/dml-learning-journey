Fine-grain aggregation examples

These patterns evaluate a measure at an intermediate grain, then aggregate or filter those values. The fragments name their additional model dependencies. Measure modifiers defines the payload syntax.

Multi-level aggregation with +d

+d enables two-step aggregation: define a measure at an intermediate grain, then roll up to the query grain. The compiler generates a CTE (WITH ... AS (SELECT ... GROUP BY ...) SELECT ...).

Pattern: dimension-constrained measure → rollup measure → query

# Step 1: require customer_id during evaluation
customer_sales:
    type: measure
    dataset: transactions
    formula: SUM({amount})
    dimensions:
        - [customer_id, ...]  # customer required; additional query fields allowed

# Step 2: evaluate with dimension [customer_id], then roll up to the query dimension
total_customer_sales:
    type: measure
    formula: SUM({customer_sales: {+d: customer_id}})

-- Step 3: use any compatible query dimension ([brand], [region], total, etc.)
SELECT brand, AGG(total_customer_sales) FROM MODEL GROUP BY brand

RFM analysis — full example using +d + fn-macros:

# .dml: customer-grain measures for RFM
last_purchase_month:
    type: measure
    formula: 'MAXIF({dt_month}, {sales: {+d: dt_month}} > 0)'
    dimensions:
        - [customer_id]

purchase_months:
    type: measure
    dataset: transactions
    formula: 'COUNT(DISTINCT CASE WHEN {amount} > 0 THEN {dt_month} ELSE NULL END)'
    dimensions:
        - [customer_id]

-- Model Query SQL: RFM with ranks
SELECT AGG(sales) AS M, AGG(sales, 'rank') AS M_rank,
       AGG(purchase_months) AS F, AGG(purchase_months, 'rank') AS F_rank,
       AGG(last_purchase_month) AS R, AGG(last_purchase_month, 'rank_asc') AS R_rank
FROM MODEL GROUP BY customer_id

Inline measures — define temporary measures directly in Model Query SQL via /** dml ... **/ comment blocks, without modifying .dml. Full syntax and rules: Inline measures (/** dml ... **/).

/** dml
temp_customer_sales:
    type: measure
    dataset: transactions
    formula: SUM({amount})
    dimensions:
        - [customer_id, ...]

temp_avg_customer_sales:
    type: measure
    formula: 'AVG({temp_customer_sales: {+d: customer_id}})'
**/
SELECT brand, AGG(temp_avg_customer_sales) AS avg_customer_sales
FROM MODEL GROUP BY brand

Fine-grain filter, then +d roll-up

SQL often does: aggregate at a fine grain → WHERE on that grain → SUM to a coarser report grain.

WITH sales AS (
  SELECT product, region, SUM(amount) AS total, COUNT(*) AS cnt
  FROM fact GROUP BY product, region
)
SELECT product, SUM(total) AS grand_total
FROM sales
WHERE cnt > 3                -- filter fine-grain rows
GROUP BY product
HAVING SUM(total) > 500      -- report-level HAVING

Preferred DML — put the fine-grain predicate inside the roll-up formula; keep query filters: for report scope / HAVING only:

DATASET_SALES:
    type: dataset
    table: FACT
    columns:
        product:
        region:
    measures:
        total: SUM(amount)
        cnt: COUNT(1)

grand_total:
    type: measure
    formula: |-
        SUMIF({total: {+d: region}}, {cnt: {+d: region}} > 3)
    # No qualifying fine rows -> NULL. Use an explicit fill only if required.

report:
    type: query
    filters:
        "{grand_total} > 500":
    columns:
        dimension:
            - product
        grand_total:

How to read it: both {cnt: {+d: region}} and {total: {+d: region}} evaluate at the same fine grain (product, region); iif / SUMIF decides which fine rows enter the outer SUM; the query dimension stays product.

Avoid Why
Query filters: "cnt > 3" with only product in columns.dimension cnt left its defining grain; compile/fusion can rewrite to product-level HAVING COUNT(1) > 3 (wrong)
filters: "{cnt: {+d: region}} > 3" Compiles sometimes, but inverts the mental model (drill-down buried in a report filter)
SUM({total: {+d: region, +f: '{cnt} > 3'}}) The predicate references an aggregate measure; +f expects input-row filtering

Fallback when you want SQL-literal steps: keep a fine-grain query (dimension: [product, region], filters: "cnt > 3") and re-aggregate in presentation after: — prefer the measure form above for curation.

Also see measure design, and pitfalls P69.

Limitations of +d:

  • Full N×N co-occurrence matrix (same dimension as both rows and columns) not supported — requires dimension aliasing/self-join. Use multiple 1×N queries or export detail data.

When +d appears on a query dimension binding (columns.dimension: - name: '{m: {+d: K}}'), that is measure-as-dimension, not the roll-up pattern above — see Measure-as-dimension.

Co-occurrence analysis (1×N pattern) — count customers who bought both a target brand and each other brand, using +d + -d + +f:

/** dml
target_brand_customers:
    type: measure
    formula: 'MAXIF(1, {sales: {+d: customer_id, -d: brand, +f: {brand: ''BrandA''}}} > 0)'
    dimensions:
        - [..., customer_id]

current_brand_customers:
    type: measure
    formula: 'MAXIF(1, {sales: {+d: [brand, customer_id]}} > 0)'
    dimensions:
        - [brand, customer_id]

co_occurrence:
    type: measure
    formula: 'SUM({current_brand_customers: {+d: [brand, customer_id]}} * {target_brand_customers: {+d: customer_id}})'
**/
SELECT brand, AGG(co_occurrence) AS overlap_with_brandA
FROM MODEL GROUP BY brand ORDER BY AGG(co_occurrence) DESC

Key: -d: brand drops dimension field brand from the target measure's evaluation dimension ([customer] only), +f filters to the target brand, and the product of the two flags counts co-occurring customers.

Measure dimensions: is always array-of-arrays: each inner list is one allowed dimension and the outer list contains alternatives:

month_active_flag:
    type: measure
    formula: 'ISNULL(MAXIF(1, {month_qty: {+d: [prod_id, dt_month]}} > 0), 0)'
    dimensions:
      - [store_id, dt_month, ...]

Within an allowed dimension, ... (ellipsis) permits additional dimension fields beyond the listed ones, but the listed fields remain required in the measure reference's evaluation dimension.
