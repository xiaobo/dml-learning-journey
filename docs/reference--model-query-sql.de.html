Diese Seite beschreibt die Syntax von SQL-Abfragen, die Modellsuche sowie die Regeln für Aliasse, Gruppierung und Ausgabe. Unter Abfragedeklarationen in YAML finden Sie die Beschreibung von type: query. Eine erste Abfrage kompilieren führt Sie durch alle Schritte.

Zwei Möglichkeiten, Abfragen zu schreiben #

Syntax Format Einsatzbereiche

Abfragetypen #

Aggregationsabfragen #

Verwenden Sie FROM … und binden Sie mindestens eine Kennzahl über AGG() ein.

Der Name nach FROM entspricht dem Namen der Modelldatei ohne die Endung .dml. Groß- und Kleinschreibung spielen dabei keine Rolle. In den meisten Tutorials wird das übliche Paar FROM MODEL ↔ model.dml verwendet.

Modelldatei Schreibweise in SQL
model.dml FROM MODEL
acme.dml FROM acme
渠道表现模型.dml FROM 渠道表现模型

So wirkt sich --model= bei Abfragen, beim Kompilieren und bei reiner Validierung auf die Auflösung dieses Namens aus.

Übergebener Wert Verhalten
--model=some/dir dmlc sucht in diesem Verzeichnis nach <FROM>.dml (FROM MODEL → dir/model.dml, FROM acme → dir/acme.dml).
--model=acme.dml Diese Datei ist das Modell. In SQL muss FROM acme stehen (nicht FROM MODEL).
Nicht angegeben Dieselbe Suche erfolgt im Verzeichnis der SQL-Datei oder im Modellsuchpfad.

Geben Sie die Endung .dml in der FROM-Klausel nicht an. Legen Sie bei verschachtelten queries/-Verzeichnissen die .dml-Datei neben die SQL-Datei oder geben Sie mit --model= das Verzeichnis an, in dem die Modelldatei liegt.

setup (dmlc -s) erwartet eine .dml-Datei. Ein Verzeichnis ist unzulässig.

-- Query SQL using model.dml
SELECT product, dt_month, AGG(sales)
FROM MODEL
WHERE dt_month = date(current_date, 'start of month', '-1 month')
GROUP BY product, dt_month

-- Query SQL using acme.dml (dmlc --model=acme.dml …  or  --model=<dir containing acme.dml>)
SELECT product, dt_month, AGG(sales)
FROM acme
GROUP BY product, dt_month

Wenn in der IDE ein Modell angeheftet ist, kann die Navigation FROM MODEL weiterhin als Verweis auf dieses Modell auflösen. Stimmen Sie in der CLI den Namen nach FROM auf die verwendete Datei ab oder auf die .dml-Datei, die unter --model=<dir> gefunden wird.

Detailabfragen #

Rufen Sie Datensatzzeilen mit FROM <model>.<dataset> ab. Ein direktes GROUP BY ist unzulässig. Definieren Sie für gruppierte Kennzahlen wiederverwendbare Kennzahlen und fragen Sie das Modell ab. Verwenden Sie in Aggregationsabfragen auf dem Modell AGG().

-- Query SQL using model.dml
SELECT dt_date, transaction_id, raw_amount
FROM MODEL.transactions
WHERE dt_month = date(current_date, 'start of month')

-- Query SQL using acme.dml
SELECT ClaimNumber, ClaimOpenDate
FROM acme.Claim

Detailabfragen geben Zeilen eines Datensatzes aus. Sie unterstützen auch die geprüften Aggregatausdrücke ohne Gruppierung sowie die geprüften Fensterausdrücke. Ein direktes GROUP BY ist unzulässig. Aggregationsabfragen geben wiederverwendbare Modellkennzahlen auf der angeforderten Gruppierungsebene aus.

Grundlegende Einschränkungen #

Unzulässig Begründung Alternative
Unterabfragen In Modellabfragen mit SQL nicht unterstützt Bilden Sie die Berechnung mit Kennzahlen ab oder bereiten Sie die Relation im Datensatzfeld sql: vor.
UNION / UNION ALL In Modellabfragen mit SQL nicht unterstützt Bereiten Sie die durch UNION gebildete Relation im Datensatzfeld sql: oder in einer Datenbank-View vor.
JOIN In Modellabfragen mit SQL nicht unterstützt Modellieren Sie Attributabfragen mit pk(...) oder bereiten Sie eine Relation im Datensatzfeld sql: vor.
{...} um bloße Spaltennamen Geschweifte Klammern sind ausschließlich für .dml vorgesehen. Hier werden sie ohne Meldung entfernt. Geben Sie die Namen direkt an, etwa in SELECT product, AGG(sales).

Diese Einschränkungen für Abfragen auf dem Modell schließen den Einsatz von SQL in anderen Teilen von DML nicht aus. Im Datensatzfeld sql: können Sie unterstützte Joins, Vereinigungen und Unterabfragen vorbereiten. Referenzieren Sie deklarierte Datensätze als {DATASET} und beachten Sie die Zuständigkeit für physische Tabellen. Die Relation muss einen explizit definierten, korrekten Schlüssel haben. Die Datensatzreferenz beschreibt, wie die abgeleiteten Relationen validiert werden, die der Prüfung unterliegen. In den SQL-Code eingebaute Filter bestimmen weiterhin mit, welche Zeilen zum Datensatz gehören. Wenn Sie SQL in das Modell verlagern, passen sich die Regeln dadurch nicht automatisch alle an den jeweiligen Abfragekontext an. Siehe Datensatzdefinitionen.

Fensterfunktionen (OVER()) sind in Modellabfragen mit SQL zulässig. Der Compiler übernimmt sie unverändert in den generierten SQL-Code. Verwenden Sie für häufige Anwendungsfälle vorzugsweise die Funktionsmakros aus system_macros.dml (rank, rank_asc, pot, grand). Siehe Funktionsmodifikatoren. Wo OVER in einem .dml-Modell steht (Platzierung von Fensterfunktionen), ist unter Platzierung von Fensterfunktionen beschrieben.

Regeln für SELECT #

  • Aggregation. Verwenden Sie für jede Kennzahl AGG(measure). Geben Sie Dimensionen direkt mit ihrem Namen an.
  • Detailabfrage. Geben Sie alle Spalten direkt mit ihrem Namen an. Fügen Sie DISTINCT hinzu, wenn Sie Werte ohne Duplikate auflisten möchten.
-- Aggregation
SELECT product, dt_month, AGG(sales), AGG({sales: yoy}) AS sales_yoy FROM MODEL GROUP BY product, dt_month

-- Detail
SELECT DISTINCT product FROM MODEL.transactions

Aliasregeln #

Muster Alias erforderlich?
AGG(sales) Nein. Der Alias sales wird automatisch vergeben.
AGG(sales) AS sales Zulässig, aber redundant (unveränderte Durchleitung)
AGG({sales: yoy}) Ja, mit AS sales_yoy.
AGG(sales, 'pop') AS sales Falsch. Es entsteht ein Zirkelbezug. Verwenden Sie AS sales_mom.
AGG({sales: yoy}) AS sales Falsch. Es entsteht ein Zirkelbezug. Verwenden Sie AS sales_yoy.

Ein zuvor in der Auswahlliste vergebener Alias bezeichnet eine SQL-Ergebnisspalte, keine Kennzahl. Wenn ein späterer Ausdruck diesen Namen verwendet, etwa AGG(current_value) nach AGG(sales) AS current_value, verweist der Name auf die zuvor definierte Ergebnisspalte. Der Name wird nicht ersatzweise als Verweis auf eine andere, gleichnamige DML-Kennzahl aufgelöst.

Wenn Sie einer Kennzahlreferenz mit Modifikator den Namen der Kennzahl selbst als Alias geben, etwa mit AGG(sales, 'pop') AS sales, entsteht ein Zirkelbezug. Der Compiler behandelt den Alias als Neudefinition der Kennzahl. Verwenden Sie einen anderen Alias, etwa AS sales_mom. Ohne Modifikator ist AGG(sales) AS sales als redundante Durchleitung zulässig.

Das erste Argument von AGG gibt den Namen der Kennzahl an. Verwenden Sie AGG(sales) für den unveränderten Wert oder AGG({sales: yoy}), um diese Referenz zu modifizieren. Geben Sie an anderen Stellen einer Modellabfrage in SQL die Spaltennamen direkt an.

Regeln für WHERE #

  • Geben Sie Spaltennamen direkt an, etwa in WHERE customer = 'John Doe'.
  • Die Syntax schreibt keine Reihenfolge für Prädikate vor.
  • Geben Sie in Zeitfiltern den ersten Tag des Zeitraums an, etwa in dt_month = '2024-01-01'.
  • Verwenden Sie für einzelne Zeiträume vorzugsweise = statt BETWEEN.
  • Fügen Sie redundante NULL-Filter nur hinzu, wenn sie ausdrücklich verlangt werden.

Regeln für GROUP BY #

  • Jedes nicht aggregierte Feld aus SELECT muss in GROUP BY stehen.
  • Wenn die Ausgabereihenfolge wichtig ist, führen Sie die Felder in GROUP BY in derselben Reihenfolge wie in SELECT auf. Der geprüfte Compiler akzeptiert eine abweichende Reihenfolge und kann die sichtbaren Spalten neu anordnen. Prüfen Sie artifacts.sql und effectiveOutputOrder.
  • Für Zeitmodifikatoren muss der Zeitkontext aufgelöst sein. Ein Zeitfeld, nach dem gruppiert wird, oder ein Zeitfilter kann diesen Kontext liefern. Gruppieren Sie Berichte über mehrere Zeiträume vorzugsweise explizit nach einem Zeitfeld. Ein Filter für einen einzelnen Zeitraum kann einen verborgenen Zeitkontext liefern.
-- Correct: time modifier + matching time field in GROUP BY
SELECT dt_month, AGG(sales), AGG({sales: yoy}) AS sales_yoy
FROM MODEL
GROUP BY dt_month

-- Wrong: yoy with neither a grouped time field nor a time filter
SELECT product, AGG(sales), AGG({sales: yoy}) FROM MODEL GROUP BY product

ORDER BY / LIMIT #

  • Immer ASC/DESC angeben
  • Nur hinzufügen, wenn es für das Ergebnis erforderlich ist (Top N, Extremwerte)
  • Keine Sortierung hinzufügen, die lediglich wünschenswert ist.

Regeln für Kennzahlreferenzen #

  • In Abfragen: AGG(measure). Kennzahlreferenzen immer in AGG() einschließen.
  • Syntax mit Modifikator: AGG({measure: modifier}) oder AGG(measure, 'modifier')
  • Spaltennamen in Model Query SQL nie in {...} einschließen, außer bei der Syntax mit Modifikator innerhalb von AGG. Geschweifte Klammern um einfache Spaltennamen werden ohne Meldung entfernt. Die Spaltennamen direkt verwenden.
  • Wenn der Compiler use existing measure "X" meldet, AGG(X) verwenden. Die Formel nicht erneut ausdrücken.

Umgang mit Zeitfeldern #

Feldnamen: dt_date, dt_week, dt_month, dt_quarter, dt_year. Alle geben den ersten Tag des jeweiligen Zeitraums an.

Automatische Ableitung: Wenn das Modell ein Standardzeitfeld auf einer feineren Zeitebene wie dt_date ausdrücklich deklariert, stehen unterstützte Felder auf gröberen Zeitebenen wie dt_month automatisch im selben Datensatz zur Verfügung. Den abgeleiteten Namen direkt verwenden. Keine zusätzlichen physischen Spalten anlegen, nur um eine Abfrage, einen Filter oder eine Diagnosemeldung im Editor zufriedenzustellen. Die Funktion zum Springen zur Definition führt beim abgeleiteten Namen zur ausdrücklich deklarierten Zeitspalte.

Filtern: WHERE dt_month = '2024-01-01' (erster Tag des Zeitraums, bei einzelnen Zeiträumen = statt BETWEEN).

Die Referenz zu Datumsfunktionen beschreibt Ausdrucksformen in der Syntax von SQLite. Der Compiler übersetzt unterstützte Formen in den ausgewählten Dialekt.

Der Compiler lehnt die geprüfte Abfrage mit dt_year und dt_month ab, weil dt_year in der generierten Ausgabe fehlt. Diese Kombination nicht als funktionsfähigen Bericht mit zwei Feldern behandeln. Wenn das Jahr nur als Anzeigebeschriftung benötigt wird, auf der erforderlichen Monatsebene abfragen und die Beschriftung anschließend aus dem Monatsschlüssel ableiten. Separat prüfen, auf welcher Ebene die Ergebniszeilen definiert sind. Daraus folgt nicht, dass alle Abfragen mit mehreren Zeitfeldern nicht unterstützt werden.

HAVING #

-- Customers with outstanding balance
SELECT customer, AGG(outstanding)
FROM MODEL
GROUP BY customer
HAVING AGG(outstanding) > 0

-- Products selling less than last month
SELECT product, AGG(sales) as this_month, AGG(sales, 'pp') as last_month
FROM MODEL
WHERE dt_month = date(current_date, 'start of month')
GROUP BY product
HAVING AGG(sales) < AGG(sales, 'pp')

Hinweis zur Verwendung einer Kennzahl als Dimension: Eine Bedingung für das Klassifizierungslabel, für andere Kennzahlen auf der Ebene des Labels oder für beides ist ein Filter für die Phase nach der Labelbildung. Im Text der Model Query kann HAVING stehen. Semantisch greift der Filter erst, sobald das Label vorliegt. Im kompilierten SQL wird der Filter häufig als WHERE auf die CTE nach der Labelbildung angewendet. Ein in der Dokumentation gezeigtes HAVING erlaubt keine Filterung vor der Klassifizierung. Siehe Filter für Klassifizierungslabels.

Die Syntax für Zeitvergleiche kann im geprüften Build strenge Diagnosemeldungen zu Joins auslösen, die auf der Vereinigung der Schlüssel beruhen. Die Beispiele zeigen mögliche Abfrageformen. Vor der Ausführung die Diagnosemeldungen lesen und die generierten Joins prüfen.

Übersicht der Aggregationssyntax #

In Model Query SQL (FROM MODEL) müssen alle Aggregationen über Kennzahlen erfolgen, die in model.dml oder in Inline-Blöcken der Form /** dml ... **/ definiert sind (Inline-Kennzahlen). Aggregationen direkt auf Rohspalten werden abgelehnt.

Gewünschtes Ergebnis Falsch (schlägt fehl) Richtig
Gesamtzahl der Zeilen COUNT(*) 笔数: COUNT({ID}) in model.dml oder inline definieren, dann AGG(笔数) verwenden
Summe einer Rohspalte SUM(出厂价金额) 销售额: SUM({出厂价金额}) in model.dml oder inline definieren, dann AGG(销售额) verwenden
Durchschnitt einer Rohspalte AVG(销售数量) 均价: DIVIDE(SUM({出厂价金额}), NULLIF(SUM({销售数量}),0)) in model.dml oder inline definieren, dann AGG(均价) verwenden
Skalares MIN/MAX einer Dimension SELECT MIN(dt_month) FROM MODEL Detaildatensatz verwenden: SELECT MIN(dt_month) FROM MODEL.<dataset>
Gruppen nach Zeilenanzahl filtern HAVING COUNT(*) > 100 行数: COUNT({ID}) in model.dml oder inline definieren, dann HAVING AGG(行数) > 100 verwenden

Die einzige Ausnahme ist die skalare Aggregation auf Detaildatensätzen (FROM MODEL.<dataset>) zur Untersuchung von Metadaten. Die Ausnahme gilt nicht für Dashboards mit Geschäftskennzahlen.

Inline-Kennzahlen (/** dml ... **/) #

Temporäre Kennzahlen direkt in Model Query SQL definieren, ohne .dml-Dateien zu ändern. Der Compiler lädt die mit FROM angegebene .dml-Datei (FROM MODEL → model.dml, FROM acme → acme.dml), führt die Inline-Definitionen mit dem Modell zusammen und kompiliert dann die Abfrage.

/** dml
temp_sales:
    type: measure
    dataset: transactions
    formula: SUM({amount})
**/
SELECT product, AGG(temp_sales) FROM MODEL GROUP BY product

Sobald die explorative Berechnung eine gemeinsame fachliche Bedeutung hat, dieselbe Formel unter einem festen Namen in das .dml-Modell übernehmen. Anwender können die Kennzahl weiterhin über ihren Namen referenzieren, ohne die Formel zu wiederholen. Eine Marge aus mehreren Komponenten lässt sich inline oder im Modell als DIVIDE({net_revenue} - {sales_cost}, {net_revenue}) definieren. Wird ytd auf diese Kennzahl angewendet, werden ihre Komponenten über den kumulierten Zeitraum neu berechnet. Die angezeigten Monatsquoten werden dabei nicht gemittelt.

Anwendungsfälle:

  • Ad-hoc-Aggregation ohne Änderung an .dml (erfüllt die Anforderung, eine Kennzahl zu verwenden)
  • Aggregation über mehrere Ebenen mit +d und dimensions. Zwischenkennzahlen inline definieren.
  • RFM-Analyse: Kennzahlen auf Kundenebene inline definieren und mit rank-Funktionsmakros abfragen.

Regeln:

  • Mehrzeiliges YAML-Format verwenden (eine Eigenschaft pro Zeile)
  • Inline-Kennzahlen können vorhandene Kennzahlen und Datensätze aus .dml referenzieren
  • Inline-Kennzahlen können andere Kennzahlen referenzieren, die weiter oben im selben Block definiert sind
  • Dieselbe Syntax wie bei Kennzahldefinitionen in .dml (type, formula, dataset, dimensions)

JDBC-Parameter und Abfragetyp #

Die geprüfte JDBC-Distribution bindet Positionsparameter ? in physischem SQL und in Model Query. In den Testdaten der Aufgabe ergab die Bindung von 2 an einen Filter bzw. an einen Kennzahlausdruck bei beiden Abfragetypen 20 bzw. 60. Das Beispielprojekt zur Aufgabe enthält die Schritte zur Reproduktion.

Parameter für die Materialisierung und die interne Parametrisierung von Literalen sind getrennte Mechanismen. Binden Sie Anwendungseingaben beim Aufruf als Parameter. Fügen Sie nicht vertrauenswürdige Werte nicht durch Zeichenkettenverkettung in SQL ein.

Ein Zeitfilter schränkt auch andere Kennzahlen derselben Abfrage ein #

Ein Monatsfilter auf Abfrageebene kann den zeitlichen Bezugspunkt für eine YTD-Kennzahl liefern. Er schränkt zugleich die regulären Kennzahlen derselben Abfrage ein. Im Beispiel mit einem einzelnen KPI fließen Januar und Februar in die YTD-Marge für Februar ein, während der reguläre Umsatz nur den Februar umfasst. Eine Abfrage ohne zeitlichen Bezugspunkt schlägt fehl. Nach Kalenderzeiträumen gruppierte Abfragen können Monate mit einem kumulierten Wert, aber ohne Umsatz in der jeweiligen Periode ausgeben. Welche Zeilen ausgegeben werden und welche Daten in eine Kennzahl einfließen, sind getrennte Fragen. Verwenden Sie weder das heutige Datum noch das jüngste Datum in den Faktendaten stillschweigend als Bezugspunkt.

Kurzreferenz zu Model Query SQL #

FROM MODEL bindet model.dml ein. Mit AGG(sales) referenzieren Sie eine Kennzahl, und mit GROUP BY region legen Sie eine Zeile pro Region fest. Mit WHERE grenzen Sie den Abfragebereich ein, und mit HAVING AGG(sales) > 0 filtern Sie die Gruppen nach der Aggregation. Den Namen einer Ausgabespalte legen Sie mit AS fest.
