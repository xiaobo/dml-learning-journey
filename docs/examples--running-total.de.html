Eine Kennzahl für den in festgelegter Reihenfolge kumulierten Umsatz wiederverwenden

Definieren Sie die Kumulation in festgelegter Reihenfolge als benannte Kennzahl und geben Sie an, auf welcher Ebene sie verwendet werden darf. In diesem Beispiel werden Umsätze kumuliert, keine Bruttomargen oder monatlichen Anzahlen unterschiedlicher Kunden.

Definition und Ergebnis prüfen #

Der Monatsumsatz beträgt im Januar 40 und im Februar 20. LaufenderUmsatz liefert für Januar 40 und für Februar 60.

LaufenderUmsatz:
  type: measure
  formula: 'SUM({Umsatz}) OVER (ORDER BY {dt_month} ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)'
  dimensions:
    - [dt_month]

ORDER BY dt_month ordnet die Monate chronologisch. ROWS summiert die Zeilen bis zum aktuellen Monat. Ohne Partitionierung werden die Regionen zuerst zu Monatsumsätzen zusammengefasst. dimensions: [[dt_month]] legt die monatliche Gruppierung fest. Die Tabelle speichert den Monat als Datum.

Vollständige Datei: fixed/model.dml 
dialect: duckdb
Verkäufe:
  type: dataset
  table: FACT
  dimension: [Kennung]
  columns:
    Kennung:
      abbr: id
    Region:
    dt_month:
      abbr: month
    Bestellwert:
      abbr: amount
  measures:
    Umsatz: SUM({Bestellwert})
RegionsumsatzAuswahl:
  type: measure
  formula: '{Umsatz: {-d: dt_month}}'
RegionsumsatzAlleMonate:
  type: measure
  formula: '{Umsatz: {-df: dt_month}}'
LaufenderUmsatz:
  type: measure
  formula: 'SUM({Umsatz}) OVER (ORDER BY {dt_month} ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)'
  dimensions:
    - [dt_month]
Vollständige Datei: fixed/running.sql 
SELECT dt_month, AGG(Umsatz), AGG(LaufenderUmsatz) FROM MODEL GROUP BY dt_month ORDER BY dt_month

Andere Abfragen können dieselbe Kennzahl LaufenderUmsatz referenzieren. Wenn Sie die Umsätze je Region separat kumulieren möchten, definieren Sie die Partitionierung und die zulässige Aggregationsebene. Prüfen Sie anschließend die Ergebnisse. Wenn Sie einer Abfrage lediglich die Region hinzufügen, werden die Umsätze dadurch noch nicht je Region separat kumuliert.

Filtern vor der Fensterberechnung verschiebt den Startpunkt der Kumulation #

Vollständige Datei: fixed/running_february.sql 
SELECT dt_month, AGG(Umsatz), AGG(LaufenderUmsatz) FROM MODEL WHERE dt_month='2024-02-01' GROUP BY dt_month ORDER BY dt_month

Wenn nur der Februar ausgewählt ist, betragen sowohl der Umsatz als auch der kumulierte Umsatz 20. Der Januarwert von 40 wird nicht automatisch übernommen. Die Kumulation erfolgt über die ausgewählten Ergebniszeilen. Für die Kumulation vom Jahresbeginn bis einschließlich Februar geben Sie den Zeitraum ausdrücklich mit YTD an und prüfen die einbezogenen Eingabedaten. Siehe kumulierte KPI.

Ein kumulativer Rang, der nach dem Kennzahlwert sortiert ist, ist kein chronologisch kumulierter Gesamtwert. Die Sortierreihenfolge ist Teil der Definition. Eine leere Auswertungsebene wie {Umsatz: {dimension: []}} fordert einen Gesamtwert an, keine Kumulation in festgelegter Reihenfolge.

Prüfung ausführen und Ergebnis lesen #

Laden Sie das vollständige Projekt herunter und führen Sie verify.ps1 wie in der Datei README beschrieben in PowerShell aus. dmlc muss über den Suchpfad erreichbar sein. Das Skript legt die Übungsdatenbank im neuen Ausgabeordner an und speichert dort die Ergebnisse und Diagnosemeldungen.

Dieses Beispiel wurde auf DuckDB mit dmlc 0.3.16 (Build 2026-11-27) geprüft. Den Fingerabdruck der ausführbaren Datei und den Status der einzelnen Prüffälle finden Sie in der Datei verification-summary.json im Download. Die Datenbankvalidierung und die anschließende Ausführung sind voneinander unabhängige Vorgänge. Es ist daher nicht gewährleistet, dass beide denselben Datenbank-Snapshot verwenden. Prüfen Sie das Beispiel für andere Datenbank-Engines separat.
