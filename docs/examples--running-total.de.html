Eine Kennzahl für den in festgelegter Reihenfolge kumulierten Umsatz wiederverwenden

Definieren Sie die Kumulation in festgelegter Reihenfolge als benannte Kennzahl und geben Sie an, auf welcher Ebene sie verwendet werden darf. In diesem Beispiel werden Umsätze kumuliert, keine Bruttomargen oder monatlichen Anzahlen unterschiedlicher Kunden.

Definition und Ergebnis prüfen #

Der Monatsumsatz beträgt im Januar 40 und im Februar 20. running_sales liefert für Januar 40 und für Februar 60.

running_sales:
  type: measure
  formula: 'SUM({sales}) OVER (ORDER BY {month} ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)'
  dimensions:
    - [month]

ORDER BY month legt die zeitliche Reihenfolge fest. ROWS kumuliert die Werte von der ersten bis einschließlich der aktuellen Zeile. Da es keine Partitionierung gibt, werden die Umsätze aller Regionen zunächst zu Monatsumsätzen zusammengefasst. dimensions: [[month]] erlaubt die Verwendung der Kennzahl nur auf Monatsebene. Die Sortierung der Monatsangaben im ISO-Format ergibt die chronologische Reihenfolge.

Vollständige Datei: fixed/model.dml 
dialect: duckdb
F:
  type: dataset
  table: FACT
  dimension: [id]
  columns:
    id:
    region:
    month:
    amount:
  measures:
    sales: SUM({amount})
region_selected:
  type: measure
  formula: '{sales: {-d: month}}'
region_all_months:
  type: measure
  formula: '{sales: {-df: month}}'
running_sales:
  type: measure
  formula: 'SUM({sales}) OVER (ORDER BY {month} ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)'
  dimensions:
    - [month]
Vollständige Datei: fixed/running.sql 
SELECT month, AGG(sales), AGG(running_sales) FROM MODEL GROUP BY month ORDER BY month

Andere Abfragen können dieselbe Kennzahl running_sales referenzieren. Wenn Sie die Umsätze je Region separat kumulieren möchten, definieren Sie die Partitionierung und die zulässige Aggregationsebene. Prüfen Sie anschließend die Ergebnisse. Wenn Sie einer Abfrage lediglich die Region hinzufügen, werden die Umsätze dadurch noch nicht je Region separat kumuliert.

Filtern vor der Fensterberechnung verschiebt den Startpunkt der Kumulation #

Vollständige Datei: fixed/running_february.sql 
SELECT month, AGG(sales), AGG(running_sales) FROM MODEL WHERE month='2024-02-01' GROUP BY month ORDER BY month

Wenn nur der Februar ausgewählt ist, betragen sowohl der Umsatz als auch der kumulierte Umsatz 20. Der Januarwert von 40 wird nicht automatisch übernommen. Die Kumulation erfolgt über die ausgewählten Ergebniszeilen. Für die Kumulation vom Jahresbeginn bis einschließlich Februar geben Sie den Zeitraum ausdrücklich mit YTD an und prüfen die einbezogenen Eingabedaten. Siehe kumulierte KPI.

Ein kumulativer Rang, der nach dem Kennzahlwert sortiert ist, ist kein chronologisch kumulierter Gesamtwert. Die Sortierreihenfolge ist Teil der Definition. Eine leere Auswertungsebene wie {sales: {dimension: []}} fordert einen Gesamtwert an, keine Kumulation in festgelegter Reihenfolge.

Prüfung ausführen und Ergebnis lesen #

Laden Sie das vollständige Projekt herunter und führen Sie verify.py wie in der Datei README beschrieben aus. Sie benötigen dmlc, Python und DuckDB. Das Skript legt die Übungsdatenbank im neuen Ausgabeordner Ihrer Wahl an. Dort speichert es auch die Ergebnisse und die Diagnosemeldungen.

Dieses Beispiel wurde auf DuckDB mit dmlc 0.3.16 (Build 2026-11-13) geprüft. Den Fingerabdruck der ausführbaren Datei und den Status der einzelnen Prüffälle finden Sie in der Datei verification-summary.json im Download. Die Datenbankvalidierung und die anschließende Ausführung sind voneinander unabhängige Vorgänge. Es ist daher nicht gewährleistet, dass beide denselben Datenbank-Snapshot verwenden. Prüfen Sie das Beispiel für andere Datenbank-Engines separat.
