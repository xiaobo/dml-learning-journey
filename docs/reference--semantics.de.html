Diese Seite definiert den Auswertungskontext, die Kompatibilität von Granularitätsebenen und die Kompositionsregeln. Die Deklarationssyntax finden Sie unter Modellstruktur, Kennzahlen, Abfragen und Materialisierung.

Geltungsbereich und Einordnung #

Was diese Spezifikation abdeckt #

Dieses Dokument legt den Auswertungskontext, die Kompatibilität von Granularitätsebenen und die Einschränkungen für Modifikatoren in DML fest. Die folgenden Regeln definieren das verbindliche Verhalten der Sprache. Unter Fehlercodes finden Sie die Bedeutung der Diagnosemeldungen und Vorschläge zur Behebung.

Was diese Spezifikation nicht abdeckt #

  • Eine Abfrage kompilieren und validieren beschreibt die Befehle der CLI und das Erfassen von Nachweisen.
  • Eine Analyse erstellen beschreibt die Schritte für fachliche Analysen.
  • Grundkonzepte erläutert die Modell-, Abfrage- und Ausdrucksebene.

Dreischichtige Architektur #

Ebene Sprache Was Sie schreiben Datei
Modellierung DML Datensätze, Kennzahlen, Spaltenmakros, materialize, dt/fn-Makros .dml (YAML)
Abfragen Modellabfrage (Format SQL oder DML) AGG(measure), GROUP BY, Modifikatoren .sql oder .dml mit type: query
Ausdrücke DMX (Dato Measure eXpression) Formeln, Referenzen, Modifikatoren, pk() In beiden Schichten

DMX ist die gemeinsame Ausdruckssprache. Beispiele in .dml-Formeln sind {column}, {measure: modifier} und pk(...). Beispiele in Modellabfragen im Format SQL sind AGG(measure) und AGG({measure: modifier}).

Grundbausteine #

Ein Datensatz ist eine Tabelle mit einer deklarierten Dimension und Spalten. Seine deklarierte Datensatzgranularität ergibt sich aus der deklarierten Liste dimension:.

Eine Kennzahl ist eine benannte fachliche Kennzahl. Es gibt zwei Typen.

  • Eine atomare Kennzahl ist über das Feld dataset: an einen Datensatz gebunden und aggregiert Spalten mit SQL.
  • Eine zusammengesetzte Kennzahl referenziert andere Kennzahlen und hat kein Feld dataset:.

Ein Dimensionsfeld ist ein einzelnes benanntes Feld in DML.

Eine Dimension ist eine Liste mit einem oder mehreren Dimensionsfeldern. Die Angabe dimension: eines Datensatzes legt fest, wodurch eine Quellzeile identifiziert wird. Eine Abfragedimension legt die Gruppierung fest, eine Auswertungsdimension steuert die Auswertung einer Kennzahlreferenz, und eine Materialisierungsdimension deklariert einen Ausgabeschlüssel. Jede innere Liste in dimensions: einer Kennzahl entspricht einer zulässigen Dimension. Ein Feld vom Typ Kennzahl als Dimension ist ein Feld einer Abfragedimension, dessen Wert durch die Auswertung einer Kennzahl entsteht (siehe Kennzahl als Dimension).

Die Modifikatorform {dimension: []} entfernt die Auswertungsdimension, um einen Kontext für die Gesamtsumme anzufordern. Die leere Liste gibt eine Operation an und definiert keine Dimension ohne Felder.

Ein Spaltenmakro ist eine in .dml definierte abgeleitete Spalte oder ein datensatzübergreifender Zugriff. Damit lassen sich Felder aus anderen Datensätzen ohne JOIN in Kennzahlformeln verwenden.

Entwurfsprinzipien #

  1. Semantik muss ausführbar sein. Kennzahlen dienen nicht nur der Dokumentation. Sie werden in SQL für das Data Warehouse kompiliert.
  2. Semantik wie Code verwalten. Dazu gehören Git, PR, LSP und die Validierung mit dml_schema.yaml.
  3. Kennzahlen sind nicht an eine feste Ergebnisgranularität gebunden. Für jede Kennzahl ergibt sich aus ihrer Definition ein gültiger beziehungsweise nativer Kennzahlkontext, der zusätzlich eingeschränkt werden kann. Abfrage und Modifikatoren bestimmen die effektive Granularität der Auswertung. Der Compiler stellt die Kompatibilität sicher.
  4. Komplexe Ableitungen gehören ins Modell. Zeitvergleiche, Verhältnisse und mehrstufige Aggregationen bleiben in .dml. Sie werden nicht auf berechnete Felder in BI-Tools oder Ad-hoc-Abfragen in SQL verteilt.

Modell des Auswertungskontexts #

Definition #

Der Auswertungskontext umfasst alle Informationen, mit denen der Compiler eine Kennzahlreferenz auflöst und daraus ausführbares SQL erzeugt.

Die standardisierte Kurzschreibweise im Produkt lautet Context = {grain, filters, time}. Im folgenden Sprachmodell übernimmt das aufgelöste Feld dim_dt die Rolle von time.

Context = {
    grain: [dim₁, dim₂, ...],   // active grouping dimension fields
    filters: [predicate₁, ...],  // active filter predicates
    dim_dt: TimeDim | null       // resolved time dimension
}

Standardbegriffe für Granularität und Kennzahlkontext #

Rolle Quelle Beschreibung
Deklarierte Datensatzgranularität dimension: im Dataset Was eine einzelne Zeile des Datensatzes darstellt
Gültiger beziehungsweise nativer Kennzahlkontext Quelldatensatz, referenzierte Kennzahlen, Formel und Modifikatoren sowie die optionale Einschränkung dimensions: der Kennzahl Kontexte, in denen die Kennzahldefinition gültig ist. Sie legen keine feste Ausgabegranularität fest.
Effektive Auswertungsgranularität Abfragegranularität nach Anwendung von +d, -d, dimension und weiteren zugehörigen Modifikatoren Granularitätsebene, auf der eine bestimmte Kennzahlreferenz ausgewertet wird
Granularität des Abfrageergebnisses GROUP BY oder columns.dimension in der Abfrage Was eine einzelne Ausgabezeile darstellt. Neben physischen oder zugeordneten Dimensionsfeldern können auch Kennzahlen als Dimensionsfelder einfließen (siehe Kennzahl als Dimension).

Der umfassendere Abfragekontext verbindet die Granularität des Abfrageergebnisses mit WHERE beziehungsweise filters: und den aufgelösten Zeitinformationen. Die älteren Bezeichnungen „native Kennzahlgranularität“ und „Zielgranularität“ stehen für den gültigen beziehungsweise nativen Kennzahlkontext bzw. die effektive Auswertungsgranularität. Neue normative Texte sollten die oben aufgeführten Standardbegriffe verwenden.

Änderung des Auswertungskontexts #

Modifikatoren ändern den Auswertungskontext. Der Compiler wendet sie an, um einen neuen Kontext für die Kennzahlauswertung abzuleiten.

apply_modifier(Context, Modifier) -> Context'
Modifikator Auswirkung auf die Granularität Auswirkung auf Filter
+d: dim dim ans Ende der Liste der Felder anhängen, die die Granularität bestimmen (Drilldown) Keine Änderung
-d: dim dim aus der Granularität entfernen (Rollup) Keine Änderung. Filter auf dim werden weiterhin in die WHERE-Klausel des Datensatzes verschoben.
-df: dim dim aus der Granularität entfernen Filter auf dim und daraus abgeleiteten Spalten bei der Kennzahlauswertung entfernen
dimension: [dims] Die gesamte Granularität durch dims ersetzen Keine Änderung
+f: condition Keine Änderung condition zu den Filtern hinzufügen
-f: dim Keine Änderung Filter entfernen, die dim referenzieren
dt-Makro (z. B. ya, pp, ytd) Keine Änderung Zeitraum in dim_dt ersetzen
fn-macro (z. B. yoy, rank) Kann die Granularität ändern (z. B. grand → dimension: []) Hängt von der Makroformel ab

dim_dt – die Zeitdimension #

dim_dt ist die Systemvariable für die Zeitdimension der aktuellen Abfrage.

Auflösungsreihenfolge: dimension der Abfrage → filter der Abfrage → null.

Eigenschaften:

  • {dim_dt} – wird zum aktuellen Zeitfeld der Abfrage aufgelöst (z. B. dt_month, dt_quarter)
  • {dim_dt.datetype} – Zeichenfolge für den Typ: 'day', 'week', 'month', 'quarter', 'year'
  • {dim_dt.periods_per_year} – Perioden pro Jahr: 52 bei Wochen, 12 bei Monaten, 4 bei Quartalen
  • {dim_dt.datepart} – Zeichenfolge für den Datumsbestandteil in SQL

Entwurfsziel: Verwenden Sie in Maßformeln dim_dt anstelle der konkreten Felder dt_date, dt_month oder dt_quarter. So lässt sich ein Maß ohne Änderung der Formel auf jeder Zeitebene auswerten.

Umstellung der Periode: Mit dim_dt as quarter arbeitet pp auf Quartalsebene, auch wenn die Abfrage nach Jahr und Quartal gruppiert:

SELECT dt_year, dt_quarter,
       AGG({sales: {dim_dt as quarter: pp}}) as last_quarter
FROM MODEL GROUP BY dt_year, dt_quarter

Standardfelder der Zeitdimension #

Feld Granularität Beispielwert
dt_date Tag 2024-03-15
dt_week Woche (beginnt am Montag) 2024-03-11
dt_month Monat 2024-03-01
dt_quarter Quartal 2024-01-01

Alle Zeitfelder verwenden das Format mit dem ersten Tag: Der Wert ist der erste Tag der Periode.

Automatische Ableitung gröberer Zeitebenen

Wenn ein Dataset ein Standardzeitfeld explizit deklariert, stellt es über den Systemkalender auch die unterstützten Felder der Reihe dt_<grain> auf gröberen Zeitebenen bereit. Ist beispielsweise die Spalte dt_date explizit deklariert, sind dt_week, dt_month, dt_quarter und dt_year gültige Spaltenreferenzen innerhalb des Datasets. Wer ein Modell erstellt, muss diese Namen nicht eigens unter columns: aufführen, um auf einer gröberen Zeitebene abzufragen oder zu filtern. Die erzeugten Werte folgen den oben beschriebenen Kalenderregeln und verwenden jeweils den ersten Tag der Periode.

Ein automatisch abgeleitetes Zeitfeld hat eine virtuelle Spaltenidentität und ist keine zweite explizite Quellendefinition. Sprachwerkzeuge müssen daher:

  • unterstützte abgeleitete Felder bei der Namensauflösung und Autovervollständigung innerhalb des Datasets berücksichtigen,
  • sie überall zulassen, wo die entsprechende Dataset-Spalte zulässig ist, etwa als Dimensionsfelder in Abfragen oder in Filtern, Formeln und Argumenten von Modifikatoren,
  • beim Navigieren von einer abgeleiteten Referenz zur expliziten Zeitspalte springen, aus der das Feld abgeleitet ist (bei dt_month, abgeleitet aus dt_date, führt die Navigation zu dt_date),
  • den virtuellen Feldnamen bei Umbenennungen als schreibgeschützt behandeln, sofern keine explizite Definition mit diesem Namen existiert.

Wenn sich dasselbe abgeleitete Feld aus mehreren expliziten Zeitquellen ableiten lässt und keine Quelle eindeutig bestimmt werden kann, müssen die Werkzeuge die Auflösung abbrechen, statt eine Definition willkürlich auszuwählen.

Kalender-Dataset #

Das System stellt das Dataset Dim Calendar für das Nachschlagen von Zeitwerten über verschiedene Zeitebenen hinweg bereit:

Dim Calendar:
    type: dataset
    table: DML_CALENDAR
    dimension: [dt_date]
    columns:
        dt_date:
        dt_week:
        dt_month:
            source: pk({dt_date}).DML_CALENDAR(dt_date).dt_month
        dt_quarter:
            source: pk({dt_month}).DML_CALENDAR(dt_date).dt_quarter
        dt_year:
            source: pk({dt_quarter}).DML_CALENDAR(dt_date).dt_year

Filterkontext und Filter-Pushdown #

Wo ein Filter gesetzt wird, hängt von seinem semantischen Geltungsbereich ab:

Ebene Ort Was hier angegeben wird
filters: / WHERE der Abfrage Abfrageblock Berichtsspezifische Datenausschnitte (Kanal, Marke, Datumsbereich)
Maßformel Maß in .dml Kennzahlspezifische Kriterien dafür, welche Zeilen in die Berechnung eingehen, wenn ausgeschlossene Zeilen in den Ergebnisgruppen verbleiben dürfen
sql: im Dataset Dataset-Definition Dauerhafte Einschränkungen der Quelldatenmenge, die sich mit dem derzeitigen deklarativen DML nicht ausdrücken lassen

Ein WHERE auf den Quelldaten und eine Bedingung im Maß, die NULL liefert, sind im Allgemeinen nicht austauschbar. Im ersten Fall verschwinden Gruppen, die ausschließlich ausgeschlossene Zeilen enthalten. Im zweiten Fall können solche Gruppen bestehen bleiben. Prüfen Sie vor einem Wechsel zwischen diesen Ebenen, welche Gruppen bestehen bleiben, wie sich die Änderung auf andere Kennzahlen derselben Abfrage, auf die Deduplizierung, auf Joins und Fensterfunktionen sowie auf die Semantik von NULL auswirkt.

Pushdown-Regel: Die unter filters: angegebenen Abfragefilter werden vor der Aggregation an die WHERE-Klausel des Datasets weitergegeben. Erstellt -d eine temporäre Tabelle mit gröberer Granularität, wird der Filter weiterhin angewendet. Dadurch können die Nenner von Verhältniskennzahlen kleiner werden. Mit -df verhindern Sie den Filter-Pushdown für ein bestimmtes Dimensionsfeld.

Verfolgung von Abhängigkeiten: Der Compiler verfolgt die Ableitungskette einer Spalte. Ein Filter auf store_name (pk({store_id}).MDM_STORE(store_id).store_name) wird nicht weitergegeben, wenn für store_id die Option -df gesetzt ist, da die Spalte ausschließlich aus store_id abgeleitet ist.

Granularitätsregeln #

Die Dimension eines Auswertungskontexts bestimmt dessen Granularität und Kompatibilität mit anderen Kontexten. Welche Rolle die einzelnen Dimensionsdeklarationen in DML haben, fasst Dimensionsrollen zusammen.

Drei Arten von Granularität #

Art der Granularität Deklariert durch Bedeutung
Granularität des Datasets dimension: im Dataset Eine Zeile der zugrunde liegenden Tabelle steht für eine Wertekombination der Felder dieser Dimension
Granularität des Maßes Formel + Modifikatoren + optionale Einschränkung über dimensions: Die Ebene, auf der die Formel des Maßes gültig ist
Granularität der Abfrage GROUP BY / columns.dimension: der Abfrage Eine Zeile im Abfrageergebnis steht für eine Wertekombination der Felder dieser Dimension

Regel zur Kompatibilität der Granularität #

Die Granularität der Abfrage muss mit der Granularität jedes Maßes kompatibel sein.

Für ein atomares Maß ohne Einschränkung über dimensions: gilt:

  • Das Maß lässt sich für jede kompatible Dimension auswerten, die aus den Dimensionsfeldern seines Datasets besteht.
  • Der Compiler wählt die Aggregation anhand der deklarierten Granularität und des angeforderten Kontexts. Auf der deklarierten Granularität, die jede Zeile eindeutig bestimmt, kann er die Rohwerte direkt projizieren.

Für ein atomares Maß mit der Einschränkung dimensions: [[dims]] gilt:

  • Das Maß kann nur auf der angegebenen Ebene ausgewertet werden.
  • Andere Formeln, die dieses Maß verwenden, müssen mit {measure: {+d: dim}} ausdrücklich auf diese Ebene wechseln.
  • Der Compiler weist inkompatible Granularitäten mit der Meldung cannot set dimension [...] since only [...] are allowed zurück.

Bei einem Dataset oder einer Materialisierung enthält dimension: genau eine Dimension. Bei einem Maß enthält dimensions: die alternativ zulässigen Dimensionen. Jede innere Liste steht für eine Dimension. Diese Angabe schränkt die zulässigen Dimensionen ein. Sie deklariert weder die Identität des Datasets noch die Gruppierung der Abfrage. Die Regeln dazu finden Sie unter Dimensionsrollen.

Für eine zusammengesetzte Kennzahl gilt:

  • Die Granularität ergibt sich aus der Vereinigung der Dimensionsfelder der referenzierten Kennzahlen, nachdem die Modifikatoren aufgelöst wurden.
  • Die Granularitäten aller referenzierten Kennzahlen müssen untereinander kompatibel sein.

Mehrstufige Aggregation mit +d #

+d richtet eine Auswertungsstufe auf feinerer Granularität ein. Der Modifikator allein aggregiert den Wert nicht zurück auf die Granularität der Abfrage.

Schreibweise Bedeutung
{m: {+d: x}} Auf der Granularität der Abfrage ∪ {x} auswerten und dort aufhören
SUM / AVG / MAX / …({m: {+d: x}}) Den Wert auf feinerer Granularität auswerten und dann mit einer expliziten äußeren Aggregation auf die aktuelle Granularität der Abfrage zurückführen
Bindung einer Abfragedimension - lab: '{m: {+d: K}}' Kennzahl als Dimension (Kennzahl als Dimension): Das Ergebnis ist ein Gruppierungsschlüssel, keine gewöhnliche Spalte mit einer aggregierten Kennzahl.

Die äußere Aggregationsfunktion (SUM, AVG, MAX usw.) legt der Autor fest. Der Compiler ergänzt sie nicht selbst. Bei einer äußeren Aggregation erzeugt der Compiler in der Regel eine CTE (WITH ... AS (SELECT ... GROUP BY ...) SELECT ...).

Muster: atomare Kennzahl → mit +d in einer zusammengesetzten Kennzahl, die die äußere Aggregation vorgibt, auf eine feinere Granularität wechseln → Abfrage auf beliebiger Granularität

# Atomic measure (dataset grain: dt_date × store_id × prod_id)
销售量:
    type: measure
    dataset: o2o_pos
    formula: SUM(count_qty)

# Distribution SKU count: how many products have sales > 0?
# {销售量: {+d: prod_id}} drills down to per-product grain,
# then DISTINCTCOUNTIF counts products with positive sales.
分销SKU数:
    type: measure
    formula: |-
        DISTINCTCOUNTIF({prod_id}, {销售量: {+d: prod_id}} > 0)

# Distribution store count: how many stores have sales > 0?
分销客户数:
    type: measure
    formula: |-
        DISTINCTCOUNTIF({store_id}, {销售量: {+d: store_id}} > 0)

# Average sales per store (selling power)
卖力:
    type: measure
    formula: |-
        divide({销售额}, {分销客户数})

-- Query at brand × quarter grain — the +d inside each measure
-- generates intermediate CTEs at prod_id / store_id grain, then rolls up.
SELECT dt_quarter, brand,
       AGG(销售额),
       AGG(分销SKU数),
       AGG(分销客户数),
       AGG(卖力)
FROM MODEL
GROUP BY dt_quarter, brand

Steht +d in der Bindung einer Abfragedimension statt in einer Kennzahlenformel mit expliziter äußerer Aggregation, handelt es sich um eine Kennzahl als Dimension (Kennzahl als Dimension) und nicht um das oben beschriebene zweistufige Muster.

Automatische Joins über Datensätze hinweg #

Unabhängige Kennzahlendatensätze werden normalerweise getrennt aggregiert. Anschließend werden alle ihre Gruppierungsschlüssel vereinigt (Schlüsselvereinigung). Der NULL-sichere Gleichheitsvergleich berücksichtigt den vollständigen Schlüssel. Dadurch passen Schlüssel mit NULL an denselben Positionen zusammen, wenn auch die übrigen Dimensionen übereinstimmen. Auch bei ausdrücklich zeilenerhaltenden Verknüpfungen über LEFT JOIN und nullpk kommt ein NULL-sicherer Gleichheitsvergleich zum Einsatz. Explizite SQL-Prädikate behalten ihre definierte Semantik. Ein Beispiel finden Sie unter Gleichheitsvergleich mit NULL in Joins.

Erzeugter Join-Typ. Der Compiler kann FULL OUTER JOIN verwenden oder mit UNION eine Menge eindeutiger Schlüssel bilden und die Kennzahlen per LEFT JOIN hinzufügen. Beide Varianten gleichen die Schlüssel NULL-sicher ab. Bei nativen vollständigen äußeren Joins kann der Compiler den erzeugten Join auf LEFT JOIN reduzieren, wenn ein Filter wie {primary_presence_measure} is not null nachweist, dass die Primärquelle erforderlich ist. Filter, die beide Quellen voraussetzen, können ihn auf INNER JOIN reduzieren. Die Filter bestimmen, welche Gruppen erhalten bleiben. Der Vergleich der Gruppierungsschlüssel bleibt gleich.

Für eine LEFT-Ergebnismenge filtern Sie auf eine eigene Kennzahl, die das Vorhandensein einer Gruppe in der Primärquelle anzeigt. Für jede vorhandene Gruppe muss sie einen Wert liefern (auch 0 ist ein Wert), für fehlende Gruppen dagegen NULL. Für eine INNER-Ergebnismenge muss die Gruppe auf beiden Seiten vorhanden sein. Verwenden Sie Zählwerte aus der Quelle ohne nachträgliche Auffüllung oder ein anderes verlässliches Anwesenheitsmerkmal. Kann eine fachliche Kennzahl bei vorhandener Gruppe NULL sein, würde der Filter gültige Gruppen ausschließen. Wird ein fehlender Wert durch 0 ersetzt, können dagegen Gruppen ohne Eintrag in der Primärquelle erhalten bleiben.

Prüfen Sie getrennt, ob gemeinsam verwendete Schlüssel dieselbe Bedeutung haben, ob vollständige Schlüssel eindeutig sind, wie Gruppierungsschlüssel, die NULL enthalten, abgeglichen werden und wie Zeilen ohne Gegenstück sowie die Auffüllung fehlender Zeilen behandelt werden. Eine getrennte Voraggregation behebt weder doppelte Nachschlageschlüssel noch fehlerhafte Zuordnungsregeln. Durch die Prüfung des erzeugten SQL lässt sich die Abfragestruktur feststellen. Die Validierung in der Datenbank und der Ergebnisvergleich erfordern eigene Prüfungen.

Prüfung der Granularität (bestehendes Compilerverhalten) #

Der Compiler prüft die Granularität beim Kompilieren:

  1. Verstoß gegen die Dimensionsbeschränkung einer Kennzahl: Wird eine Kennzahl mit der zulässigen Dimension dimensions: [[customer_id]] auf einer Abfragedimension referenziert, die auch dt_date enthält, lehnt der Compiler die Abfrage mit folgender Meldung ab:

    cannot set dimension [dt_date, customer_id]+d: customer_id since only [[customer_id]] are allowed

    Der Compiler gibt jetzt einen Hinweis (Hint) aus. Er erklärt, dass ... zusätzliche Dimensionsfelder zulässt und die aufgeführten Felder weiterhin erforderlich sind. Zum Ergänzen fehlender Pflichtfelder empfiehlt er +d. Verwenden Sie ..., um zusätzliche Dimensionsfelder zuzulassen. Die aufgeführten Felder bleiben erforderlich.

  2. Das Aggregieren einer Kennzahl erfordert +d: SUM({measure}) schlägt mit der Meldung „cannot aggregate a measure w/o +d modifier“ fehl. Ein Hinweis (Hint) des Compilers erklärt, dass die Kennzahl ohne +d bereits auf ihrer Zielgranularität ausgewertet wird und keine feineren Werte zum Aggregieren vorliegen. Das gilt für jede Kennzahlenreferenz innerhalb einer Aggregationsfunktion, unabhängig von dimensions:-Deklarationen. Die Zielgranularität für die Auswertung ergibt sich aus dem GROUP BY der Abfrage und der Beschränkung auf die zulässigen Dimensionen der Kennzahl. +d: dim fügt ein Dimensionsfeld hinzu und wertet die Kennzahl auf der dadurch feineren Granularität aus. Die äußere Aggregation per SUM/AVG/… führt das Ergebnis auf die Zielgranularität zurück. Verwenden Sie für diese zweistufige Auswertung SUM({measure: {+d: dim}}). Die bloße Referenz {measure: {+d: dim}} eignet sich dafür nicht als aggregierte Spalte.

  3. Fehlender Zeitkontext: Zeitmodifikatoren erfordern ein auflösbares dim_dt und setzen voraus, dass die Anforderungen ihrer Makros erfüllt sind. Ein Zeitfeld in der Gruppierung oder ein Zeitfilter kann den Kontext liefern.

  4. Inkompatible Granularitäten über Datensätze hinweg: Wenn zwei Kennzahlen aus verschiedenen Datensätzen nicht genügend gemeinsame Dimensionen für die Granularität der Abfrage haben, meldet der Compiler einen Fehler.

  5. Regeln für Kennzahlen als Dimensionen: Siehe Kennzahl als Dimension und die Einschränkungen in den Versionshinweisen. Der Compiler lehnt Abfragen mit fehlenden Entitätsschlüsseln ab. Die statischen Prüfungen erkennen jedoch nicht jede ungültige Übersetzung in die Zielform.

Aussagekraft der Kompilierung: Eine erfolgreiche Kompilierung allein belegt weder, dass das erzeugte SQL gültig ist, noch, dass die berechneten Werte stimmen. Prüfen Sie die Klassifizierungs- und Aggregationsstufen, validieren Sie die Schlüssel in den tatsächlichen Daten und vergleichen Sie die Ergebnisse separat.

Regeln für die zeitliche Granularität #

  • Geben Sie für eine eindeutige Berichtsdefinition möglichst eine einzige zeitliche Granularität explizit an. Im geprüften Build kann dt_year, dt_month gemeinsam verwendet werden. Daraus lässt sich nicht ableiten, dass jede Kombination mehrerer Zeitmodifikatoren funktioniert.
  • Verwenden Sie für Zeitfelder mit gröberer Granularität den Beginn des jeweiligen Zeitraums als Wert. Ein Gleichheitsvergleich wählt einen Zeitraum aus. Die strukturierte Angabe range: [start, end] schließt auf dieser Ebene beide Grenzen ein.
  • Die Reihenfolge der Prädikate in WHERE ist eine Schreibkonvention und keine Einschränkung der Grammatik.
  • Verwenden Sie die tatsächlichen Voraussetzungen des Makros und den aufgelösten Wert für dim_dt. Ein Zeitfilter kann den Kontext auch ohne sichtbares Zeitfeld zur Gruppierung bereitstellen.

Kennzahl als Dimension #

Ein Feld vom Typ Kennzahl als Dimension gehört zur Abfragedimension. Sein Wert stammt aus der Auswertung einer Kennzahl oder eines skalaren Ausdrucks über eine solche Kennzahl, nicht aus einer physischen Spalte des Datensatzes. Das Feld behält seine Rolle als Abfragedimension (Dimensionsrollen) und bestimmt damit die Granularität des Abfrageergebnisses mit. Es legt die Identität des Datensatzes nicht fest.

Erläuterung zu Kennzahlen als Dimensionen. Dieser Abschnitt beschreibt die vorgesehenen Regeln für die Verarbeitung in mehreren Durchläufen. Die Erläuterung nennt die geprüften Formen und die zu überprüfenden Klassifizierungsphasen. Der Compiler modelliert diese Abfragespalten getrennt von physischen Dimensionsspalten und gewöhnlichen Ausgabekennzahlen und verwendet dabei die reguläre Kennzahlberechnung.

Syntax in columns.dimension

Schreibweisen und Grenzen der Unterstützung (Abfrage im DML-Format):

Form Beispiel Bedeutung
Benannte Kennzahl mit explizitem +d - first_purchase_month: '{first_purchase_month: {+d: store_id}}' Ergänzen Sie die Auswertungsdimension der Kennzahl um store_id, werten Sie die Kennzahl aus und verwenden Sie das Ergebnis als Feld der Abfragedimension.
Kennzahlname ohne weitere Angaben - first_purchase_month Für eine aus einer Kennzahl abgeleitete Dimension ist diese Form ungültig. An der Verwendungsstelle muss ein vollständiger +d-Schlüssel explizit angegeben werden.
{m: {+d: dim}} in einem skalaren Ausdruck - payment_day: 'cast({authorization_ts: {+d: payment_id}} as date)' Werten Sie den skalaren Ausdruck einmal pro vollständigem Schlüssel aus und verwenden Sie das Ergebnis als Feld der Abfragedimension.
Benannte skalare Kennzahl mit +d in der Abfrage Kennzahl mit formula: 'cast({authorization_ts} as date)', danach - payment_day: '{dt_payment_day: {+d: payment_id}}' Gleichwertige und bevorzugte Schreibweise, wenn der skalare Ausdruck wiederverwendbar ist
Label mit dimension: / rank (ohne +d) - brand_bucket: 'iif({sales: {dimension: [brand], rank}} < 5, {brand}, ''others'')' Formel der Abfragedimension, die die Auswertungsdimension mit dimension: ersetzt bzw. rank verwendet. Sie verwendet nicht das Muster zur Verknüpfung in mehreren Durchläufen mit +d.

Verwenden Sie zum Schreiben und Validieren dieser Bindungen vorzugsweise type: query. Die Angabe SQL im Kopf generierter Test-Fixtures belegt nicht, dass der entsprechende Roundtrip zwischen Model Query und SQL unterstützt wird.

Auswertungssemantik bei mehreren Durchläufen

Sei M der Ausdruck für die Kennzahl als Dimension, K die Menge der darin explizit angegebenen +d-Felder und Q die Menge der gewöhnlichen Felder der Abfragedimension. Die Granularität für Auswertung und Verknüpfung ist G = Q ∪ K. Aus Kennzahlen abgeleitete Labels sind davon ausgeschlossen. Interne Aggregationsphasen definieren K nicht neu.

  1. Auswertung auf feiner Granularität. Werten Sie jede als Dimension verwendete Kennzahl auf Ebene G aus. Werten Sie auch gewöhnliche Ausgabekennzahlen auf Ebene G aus. Behalten Sie dabei die Zustände oder Teilkennzahlen bei, die für die spätere Aggregation auf gröberer Ebene erforderlich sind.
  2. Über den vollständigen Klassifizierungsschlüssel G verknüpfen. Die Klassifizierungsrelation muss pro vollständigem Schlüssel genau einen skalaren Wert enthalten. Wenn sie getrennt von den Kennzahlen vorliegt, die sie verwenden, muss sie vor der Gruppierung dieser Kennzahlen nach dem Klassifizierungswert verknüpft werden. Bei der Klassifizierung nach Filiale und Monat muss der Join sowohl die Filiale als auch den Monat einbeziehen. +d: store_id allein reicht nicht aus. Für eine Verknüpfung auf gröberer Ebene muss der vollständige Schlüssel in der verarbeitenden Relation verfügbar oder nachweislich daraus ableitbar sein. Eine Verknüpfung auf feinerer Ebene erfordert einen expliziten Drilldown und eine anschließende Aggregation auf gröberer Ebene. Die Semantik für NULL-Schlüssel und für die Menge der von der Abfrage erfassten Datensätze muss erhalten bleiben.
  3. Auf die Granularität des Abfrageergebnisses aggregieren. Aggregieren Sie gewöhnliche Kennzahlen auf Ebene { measure-as-dimension fields } ∪ Q. Felder aus K entfallen, sofern sie nicht auch in Q enthalten sind. Lässt sich eine gewöhnliche Kennzahl nicht sicher so umschreiben, dass sie zunächst auf Ebene G ausgewertet und dann wie beschrieben aggregiert wird, schlägt die Kompilierung fehl.

Das Verfahren beruht auf demselben Ausführungsprinzip wie die Aggregation über mehrere Ebenen mit +d (Mehrstufige Aggregation). In diesem Fall wird das auf der feineren Ebene berechnete Kennzahlergebnis zu einem Feld der Abfragedimension und dient nicht nur als Zwischeneingabe für eine zusammengesetzte Formel.

source
  → evaluate measure-as-dimension + other measures at finer evaluation dimension (+d)
  → attach on the complete classification key
  → roll up to query result grain (GROUP BY measure-as-dimension field[, ordinary query-dimension fields])

Kompatibilität von +d

Geben Sie Entitätsschlüssel sowohl für die Klassifizierung als auch für die beteiligten Drilldown-Referenzen auf derselben Ebene explizit an. Die Kompatibilität richtet sich nach den aufgelösten Auswertungsdimensionen und ihrem Geltungsbereich und hängt nicht allein davon ab, wie die Argumente von +d geschrieben sind.

Gemeinsames +d. Jede als Dimension verwendete Kennzahl erfordert einen expliziten vollständigen Schlüssel. Mehrere unabhängige Labels sind nur zulässig, wenn ihre Schlüssel dieselben Felder enthalten. Die Reihenfolge der Felder in der Schlüsseldeklaration spielt dabei keine Rolle.

Referenzen ohne Schlüsselangabe. Leiten Sie die Entitätsgranularität nicht aus anderen Kennzahlen auf derselben Ebene ab. Geben Sie einen Entitätsschlüssel explizit mit +d oder dimension: an. Eine Kennzahlbindung ohne Schlüssel wird abgelehnt. Beide Formen lassen sich für die geprüfte Klassifizierung nach Kundenanzahl kompilieren. Das ist kein Nachweis für alle Klassifizierungsformen. Das Hinzufügen oder Entfernen einer Ausgabekennzahl darf die Zuordnung zu den Klassen nicht ändern.

Unterschiedliche Schlüssel. Unabhängige Labels mit unterschiedlichen Schlüsseln werden abgelehnt. Ein Label darf nicht von einem anderen Label derselben Abfrage abhängen. Die allgemeine Verknüpfung verschiedener Entitätsgranularitäten erfordert eine separat modellierte Relation.

Einschränkungen

  1. Die Klassifizierung erfordert explizite Entitätsschlüssel (vorzugsweise +d, auch dimension: wird erkannt). Die Kompatibilität mehrerer Labels und die sichere Aggregation auf gröberer Ebene sind Anforderungen der Spezifikation und keine pauschalen Garantien für eine veröffentlichte Version. Validieren Sie die konkrete Abfrage.

  2. Kombinationen von Zeitraummodifikatoren sind nicht allgemein verifiziert. test_82d testet eine Klassifizierung mit einem gleitenden Jahreszeitraum über mat. Das belegt nicht die Korrektheit von yoy oder pop. Verwenden Sie nur Kombinationen, bei denen die Zeitbereiche für Klassifizierung und Bericht explizit angegeben sind und die Ergebnisse überprüft wurden.

  3. Skalare Transformationen können direkt angegeben oder benannt werden. Sie müssen pro vollständigem Klassifizierungsschlüssel genau einen eindeutig bestimmten Wert liefern.

  4. Die Positivlisten unter dimensions: für Kennzahlen und die Regeln zur sicheren Granularität (Sicherheit der Granularität) gelten für jeden Kennzahlverweis im Ausdruck, der eine Kennzahl als Dimension verwendet, jeweils auf der Granularität, auf der der Verweis tatsächlich ausgewertet wird.

  5. Der automatische Join über mehrere Datensätze hinweg (Kombination mehrerer Datensätze) aggregiert die Kennzahlen jedes Datensatzes weiterhin auf eine gemeinsame Abfragegranularität. Ein Feld, das eine Kennzahl als Dimension verwendet, gehört nach dem Anfügen und der Aggregation auf eine gröbere Ebene zu dieser Abfragegranularität.

  6. Gruppieren Sie nach demselben endgültigen Klassifizierungswert, der angezeigt wird. Für jeden vollständigen Abfrageschlüssel ist genau eine Zeile erforderlich, auch für Schlüssel mit NULL. Eine Klassifizierung erlaubt weder das Summieren nicht additiver Kennzahlen noch das Erfinden inaktiver Entitäten. Bei Verhältniszahlen bleibt die Semantik ihrer Bestandteile erhalten. Ob die Werte pro Entität explizit in einer äußeren Aggregation zusammengefasst werden, entscheidet der Autor der Abfrage.

  7. Filter der Datenquelle werden nach den bestehenden Modifikatorregeln angewendet. -d ändert die Granularität, ohne Filter zu entfernen. Mit -f und -df lässt sich der Geltungsbereich wie bisher steuern. Ein Prädikat auf dem Klassifizierungslabel wird nach der Klassifizierung angewendet, ein Schwellenwert für einen aggregierten Berichtswert nach der Aggregation. Keines von beiden darf die Eingabedaten der zugehörigen Klassifizierung verändern. Klassifizierungen anhand der Historie bis zu einem Stichtag, eines rollierenden Zeitfensters oder der aktuellen Auswahl sind fachlich unterschiedlich definiert.

Beispiel

first_purchase_month bezeichnet im folgenden Beispiel den ersten Monat im Auswertungsbereich mit positivem monatlichem Nettoumsatz. purchase_span wertet beide Endpunkte ausdrücklich auf Entitätsebene aus und wendet die abschließende Aggregation auf das Ergebnis dieser feineren Ebene an.

first_purchase_month:
    type: measure
    formula: 'MINIF({dt_month}, {sales: {+d: dt_month}} > 0)'

report:
    type: query
    allows: ALL
    columns:
        dimension:
            - first_purchase_month: '{first_purchase_month: {+d: store_id}}'
        sales:
        purchase_span: 'SUM(datediff(day, {first_buy: {+d: store_id}}, {last_buy: {+d: store_id}}))'
  • Granularität des Abfrageergebnisses: [first_purchase_month].
  • Die Auswertung auf der feineren Granularität erfolgt, indem {+d: store_id} sowohl auf die als Dimension verwendete Kennzahl als auch auf purchase_span angewendet wird.
  • Das abschließende GROUP BY gruppiert nach first_purchase_month und lässt store_id weg.

Schemaeinschränkungen für Modifikatoren #

Gemäß dmx_variable_schema.yaml gelten für das Modifikatorobjekt folgende strukturelle Einschränkungen:

  • Varianten von dim_dt dürfen pro Modifikatorobjekt höchstens einmal vorkommen. Das gilt für dim_dt, dim_dt as date, dim_dt as month und weitere Varianten zusammen.
  • +d und dimension schließen sich gegenseitig aus. Pro Modifikatorobjekt ist höchstens eines von beiden zulässig.
  • -d und dimension schließen sich gegenseitig aus. Pro Modifikatorobjekt ist höchstens eines von beiden zulässig.
  • +d und -d / -df dürfen nur gemeinsam vorkommen, wenn ihre Mengen von Dimensionsnamen keine gemeinsamen Elemente haben. So kann ein Feld zur Verfeinerung der Granularität hinzugefügt und ein anderes entfernt werden. Übereinstimmende Dimensionsnamen sind unzulässig. Siehe Kombinieren von Modifikatoren.
  • Mehrere Modifikatoren dürfen im selben Modifikatorobjekt vorkommen, sofern die oben genannte Regel für sich überschneidende Dimensionsnamen eingehalten wird. Beispiele finden Sie unter Modifikatoren kombinieren.

Kombinieren von Modifikatoren #

Behalten Sie die angegebene Reihenfolge der Modifikatoren bei. Mehrere Makros können Zwischenkennzahlen erzeugen. Bei Funktionen mit mehreren Auswertungspfaden können Zeitmakros stattdessen an jeden Zweig weitergegeben werden. Siehe Semantik aufeinanderfolgender Modifikatoren und die dort beschriebenen Release-Prüfungen.

Verwenden Sie pro Modifikator genau einen YAML-Schlüssel. Schreiben Sie {+f: {a: 1, b: 2}} und vermeiden Sie wiederholte +f-Schlüssel. -df entfernt sowohl Dimensionen als auch Filter.

Modifikatorkonflikte bei derselben Dimension

Die Sprachspezifikation verlangt einen Kompilierungsfehler, wenn sich in einem Modifikatorobjekt die Feldmenge von +d mit der Feldmenge von -d oder -df überschneidet. Der aktuelle Build setzt diese Anforderung in den geprüften Fällen nicht durch. Vereinfachen Sie den Ausdruck algebraisch nicht zu bloßem {m}. Schreiben Sie keinesfalls {+d: x, -df: x} stillschweigend in {-f: x} um. Wenn die Ausgabegranularität bereits x enthält, unterscheiden sich -df und -f.

Unzulässig Begründung
{销量: {+d: 门店, -d: 门店}} Das Hinzufügen und Entfernen desselben Feldes lässt keine eindeutige implizite Auslegung zu. Eine Vereinfachung zu {销量} verdeckt Tippfehler und weicht von AVG({销量: {+d: 门店}}) ab, das jede Filiale gleich gewichtet.
{销量: {+d: 门店, -df: 门店}} Darf nicht in {-f: 门店} umgewandelt werden. Eine Änderung der Granularität hat eine andere Bedeutung als eine reine Filteränderung.

Für eine eindeutige Auslegung müssen Autoren eine der folgenden Formen schreiben: {销量} / SUM({销量: {+d: 门店}}) / {销量: {-d:…\|-df:…\|-f:…}}.
Unterschiedliche Dimensionen dürfen weiterhin gemeinsam vorkommen, zum Beispiel in SUM({销量: {+d: 门店, -d: 品牌}}).

Der aktuell geprüfte Build akzeptiert die untersuchten Dimensionskonflikte für dasselbe Feld und wiederholt die regionalen Summen auf Kundenebene, bevor er sie addiert. Das ist eine bekannte Lücke in der Implementierung und keine zulässige Schreibweise. Geben Sie eine Auswertungsstufe explizit an und prüfen Sie das zugehörige SQL.
