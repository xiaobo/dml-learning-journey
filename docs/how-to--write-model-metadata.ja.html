モデルのメタデータを書く

このページの内容
  • 各データセットを説明する
  • 判断に影響する列を説明する
  • 指標名を数式と一致させる
  • 元のテーブルの列名を指定する
  • 派生ラベルと推定値を文書化する
  • モデルを使ってメタデータを検証する

モデルにクエリを実行する前に、読者が適切なデータセット、対象集団、指標を選べるように説明を記述します。

各データセットを説明する #

ソースの1行が何を表し、どのフィールドで識別できるかを明記します。主要な合計値が業務上何を意味するか、対象範囲を絞るために必要なフィルター、既知の期間や地域の制約を説明します。

description: |-
  各行は流通経路の取引明細で、取引番号で識別します。
  SUM(出荷金額) は振替・本部倉庫間移動を含む流通純売上高です。店頭POS売上は含みません。
  公式ULレポートでは UL集計対象 = '是' を使います。
  経路は購入者側の販売経路を表します。

2つのデータセットが同じソースを売り手と買い手の視点でそれぞれ提供する場合は、取引先番号 のマッピングの違いを説明します。ソースの行が定義されるレベルが実際には同じ場合に、データセット間で異なると受け取られる記述は避けます。

判断に影響する列を説明する #

列名からその列の意味が分からない場合は、オブジェクト形式を使用します。

columns:
  仕入経路:
    description: 購入者側の販売経路です。モデルでは販売経路と呼びます。
  UL集計対象:
    description: 公式UL集計の対象を示します。レポートと要因分析では同じ条件を使います。
  前年同期出荷金額:
    description: 明細行の前年同期額です。前年比の計算前に対象期間と欠損値を確認します。

対象集団、グループ化、結合、比較に影響する列を優先します。既知の制約は、ソースに関する事実として記載します。1つのサンプルで得た結果を、列に恒常的に当てはまる特性として記載しないでください。

指標名を数式と一致させる #

指標のキーには業務用語を使用します。解釈に影響する場合は、対象集団、評価に必要なディメンション、NULL またはゼロの場合の動作を説明に記載します。

従来の名前が数式の内容を正しく表していない場合は、正規の指標名を変更します。既存の利用側で互換性が必要な場合に限り、エイリアスを残します。アトミックな定義は、引き続き元のデータセットに属するようにします。

# Fragment under a dataset's measures mapping.
流通純売上高:
  description: 振替・本部倉庫間移動を含む流通純売上高です。店頭POS売上は含みません。
  formula: SUM({出荷金額})

購入者数:
  description: 記録がある購入者を重複なく数えます。すべての購入者区分を含みます。
  formula: DISTINCTCOUNT({購入者コード})

購入薬局数:
  description: 記録があり、区分がDrugstoreの購入者を重複なく数えます。
  formula: 'DISTINCTCOUNTIF({購入者コード}, {購入者区分} = ''Drugstore'')'

誤解を招く正規名をコメントで補わないでください。恒常的な制約は description: に記載し、メタデータを読み取るツールで表示できるようにします。

元のテーブルの列名を指定する #

データセットが 1 つのテーブルを参照する場合は、table: に元のテーブル名、abbr: に元の列名を指定します。クエリでは業務上の名前を使います。次の例のように、指標にも内部で使う略称を指定できます。

税抜仕入額:
  abbr: SaleAmountNoTax
  type: measure
  dataset: 取引明細
  description: 税抜きの有効仕入額です。
  formula: SUM({有効売上高})

指標名を変更する前に、数式内の参照、クエリ、マテリアライズされた結果の利用側を確認します。abbr を指定するだけで、その指標に依存するすべての箇所で安全に名前を変更できるとは限りません。

派生ラベルと推定値を文書化する #

列マクロの意味を説明する必要がある場合は、description: と formula: を指定します。

# Fragment under a dataset's column-macros mapping.
購入者側仕入経路:
  description: Businesschannelから取得した購入者側の販売経路です。
  formula: '{仕入経路}'

ラベルがハードコードされたルールから生成される場合は、そのルールと適用範囲の限界を明記します。モデルで定義したカレンダー上のラベルと、正式な業務カレンダーを区別します。指標が処理フロー内の取引から最終段階の活動を推定する場合は、どの取引種別を含むかを明記します。

モデルを使ってメタデータを検証する #

  1. 名前、説明、数式がそれぞれ同じ指標を表していることを確認します。
  2. データセットの説明を、宣言されたソースキーと現在の対象範囲に照らして確認します。
  3. 互換性のためのエイリアスと、その利用側を確認します。
  4. 変更したモデルに対してリンターを実行します。
  5. 変更した計算ごとに、その計算を使用するクエリを厳格モードでコンパイルします。
  6. 生成されたエイリアスと出力列を確認します。
  7. CLI ガイドに従って、該当するライブチェックを実行します。

指標の構文と評価ディメンションについては、指標を参照してください。モデルの作成からクエリまでの一連の手順については、順方向分析に従ってください。
