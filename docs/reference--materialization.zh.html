本页介绍 type: materialize、其分组键和属性，以及如何选择指标。有关设计决策，请参阅选择物化粒度。物化示例提供了声明片段。

物化定义（type: materialize） #

<name>:
    type: materialize
    parameters:                         # stored-procedure parameters
        <param>: <column_name>
    filters:                            # materialize-level filters
        <column>: <value>

    allows: [<materialize_name>]        # allowed materialize tables

    dataset: <dataset_name>      # optional, for direct dataset materialize
    dimension: [col1, col2]      # materialization grain — grain keys only
    dimension_columns:           # functionally dependent attribute columns
        <col>: <formula>          # (1:1 with grain keys, not grain themselves)

    measures: [<measure1>, <measure2>]  # measures to materialize

dimension:与dimension_columns:的区别。dimension:包含物化维度。维度字段是确定行粒度的键，能够唯一标识每一行，编译器将这些字段用作 GROUP BY 的键。dimension_columns:列出可从这些键推导出的属性列。例如，store_name依赖于store_id，region_code依赖于store_id。编译器在 GROUP BY 处理后保留 dimension_columns: 中的列，但这些列不参与确定粒度。将可推导的属性放入 dimension: 会导致编译错误（“can be derived from [...], should it be moved to dimension_columns instead?”）。

未指定公式时的继承。dimension_columns:中的条目如果未指定 formula:，就会从源数据集继承该列。该列必须存在于源数据集的 columns: 中，否则会报错“not found from relate dataset(s)”。如果物化粒度比源数据集维度的粒度更粗，编译器会检查该列能否推导出来。如果列值在源数据集较细的粒度上有变化，则会报错“definition from dataset [...] cannot be derived from dimension [...], please advise”。如果物化粒度与源数据集的维度一致，则允许使用源数据集中的任意列（行按 1:1 映射）。

公式的引用范围。当 dimension_columns: 中的条目指定了 formula: 时，公式只能引用 pk() 链式查找和物化维度自身的字段。引用源数据集的列或指标会报错“not defined, did you mean …?”。

约束。必须使用以下任一形式：

  • dimension + measures（指定指标列表的形式），或者
  • dataset + dimension + dimension_columns（限定在指定数据集内的形式），或者
  • 仅指定 dataset（继承数据集的粒度）。

物化示例提供了常见的声明写法。指标级别没有 materialize: true 标志，编译器会拒绝该标志（undefined modifier 'materialize'，请参阅故障排查索引中的 P64）。声明形式见本节，数据集级别的 materialize: <name> 见模型结构。

适用条件、选择和性能测量 #

allows:控制哪些物化结果可以使用。仅凭声明无法确定查询会选择哪个已存储的聚合结果。请检查生成的 SQL 或执行计划，确认目标数据库引擎实际使用的对象。

按完整的键比较优化前后的结果，包括没有匹配项的分组、NULL 和比率。更改源数据后，检查刷新情况及刷新后的结果。完成这些检查后，再测量代表性工作负载的性能。SQL 更短或编译更快，都不足以判断数据库查询性能。刷新权限和调度由部署环境负责。

请按照物化工作流程进行设置、验证查询是否命中物化结果、执行刷新并检查结果。

SQL Server 运行时 #

SQL Server 运行时通过共享过程 DML_PREPARE_MAZ 和 DML_REFRESH_MAZ 注册需求，然后同步调用唯一的执行器 DML_RUN_MAZ。执行器忙时，注册调用可能在所请求的数据就绪之前返回。

setup_sql安装运行时和 Maz 写入组件。生成的 prepare_sql 执行准备工作并检查数据是否就绪。它会重试常规准备流程，直到数据就绪或达到以协作方式遵守的五秒重试期限。成功时返回 data_ready=1，随后调用方执行业务 sql。发生错误时，查询停止。等待期间仍可使用 prepare_status_sql 查看状态。状态查询观察 Query 选定的分区及其参数绑定。它不会将任务加入队列，也不保证准备过程和 SELECT 使用同一个快照。

共享视图 dbo.DML_MAZ_PROGRESS 报告全局待处理分区、完成速率和到达速率，以及清空积压预计需要的秒数。它采用 60 秒的滚动窗口，同一个物理分区即使多次完成处理，也只计一次。全局进度无法确定某个 Query 的数据是否就绪。

SELECT pending_partitions, runner_running, estimated_seconds
FROM dbo.DML_MAZ_PROGRESS;

有关精确匹配和 LIKE 匹配、force_update、invalidate_only、连接要求以及调用中断后的恢复，请参阅准备、刷新和恢复约定。

常规准备会在参数绑定相同的情况下复用有效的整表结果和按日期生成的结果。invalidate_only=1 提交失效标记，不调用执行器。不带参数调用 DML_REFRESH_MAZ 会继续处理已登记的待办任务。@_source 不能与其他选择参数同时使用。它接受按 schema.table 格式指定的已注册本地源表，并选中直接使用该源表的所有 Maz。无法确认日期映射时，会将已有日期范围全部纳入处理范围。
