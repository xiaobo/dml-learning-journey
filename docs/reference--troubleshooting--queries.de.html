Diese Einträge behandeln SQL- und YAML-Abfragen. Die unterstützte Syntax ist unter Modellabfrage in SQL und YAML-Abfragen beschrieben.

P8. Fehlendes AGG() in Aggregatabfragen #

Falsch: SELECT Produkt, Umsatz FROM MODEL GROUP BY Produkt Korrektur: SELECT Produkt, AGG(Umsatz) FROM MODEL GROUP BY Produkt

P9. Überflüssiger Alias für AGG() #

Falsch: SELECT AGG(Umsatz) as Umsatz Korrektur: SELECT AGG(Umsatz) erhält automatisch den Alias Umsatz.

P10. Verwendung von Unterabfragen #

Falsch: SELECT * FROM MODEL WHERE Umsatz > (SELECT AVG(Umsatz) FROM MODEL) Korrektur: Verwenden Sie HAVING mit einer Kennzahl, wie in HAVING AGG(Umsatz) > AGG(avg_sales).

P11. Verwendung von JOINs #

Falsch: SELECT a.*, b.* FROM MODEL a JOIN MODEL b ON a.VerkaufspositionID = b.VerkaufspositionID Korrektur: Verwenden Sie datasetübergreifende Spaltenmakros oder Lookups mit pk(...) in der .dml-Datei.

P12. Fehlender Zeitkontext für Zeitmodifikatoren #

Falsch: SELECT Produkt, AGG({Umsatz: yoy}) FROM MODEL GROUP BY Produkt (weder ein Zeitfeld als Gruppierung noch ein Zeitfilter)

Regel: Legen Sie den Zeitkontext fest und erfüllen Sie die Voraussetzungen der Makros. Am klarsten ist es, ausdrücklich nach einem Zeitfeld zu gruppieren. Auch ein Zeitfilter kann den Kontext liefern. Verwenden Sie für eine bessere Lesbarkeit möglichst nur eine Zeitebene für Zeilen oder Aggregate.

Referenz zum Zeitkontext: Zeitmodifikatoren.

Korrekt (Vorjahresvergleich auf Monatsebene):

SELECT dt_month, AGG(Umsatz), AGG({Umsatz: yoy}) FROM MODEL GROUP BY dt_month

Korrekt (YTD auf Tagesebene):

SELECT dt_date, AGG(Umsatz, 'ytd') FROM MODEL WHERE dt_date = date(current_date) GROUP BY dt_date

P13. Verwendung mehrerer Zeitebenen #

Empfehlung: Verwenden Sie möglichst nur eine Zeitebene. Der geprüfte Build akzeptiert dt_year, dt_month gemeinsam. Dass der Build mehrere Felder akzeptiert, garantiert nicht, dass jede Makrokombination den beabsichtigten Zeitkontext erhält. Prüfen Sie, welche Zeitebene ermittelt wurde.

P14. Unnötige Filter auf Nullwerte #

Falsch: WHERE Kunde is not null ohne ausdrückliche Anforderung. Korrektur: Schließen Sie Nullwerte nur aus, wenn die Fragestellung dies ausdrücklich verlangt.

P15. Verwendung von BETWEEN für einzelne Zeiträume #

Empfehlung: dt_month = '2024-01-01' wählt eindeutig den Januar aus. Ein Datumsintervall ist gültig, wenn genau dieser Zeitraum gemeint ist. Geben Sie die Grenzen ausdrücklich an und prüfen Sie, wie Zeitstempel und der letzte Tag des Intervalls behandelt werden.

P16. Die Reihenfolge der Zeitfilter ist eine Stilkonvention #

Beide Reihenfolgen der Prädikate lassen sich kompilieren. Die Engine schreibt keine Reihenfolge vor. Wählen Sie die Reihenfolge danach, wie gut sich die Abfrage lesen lässt.

P17. Unnötige Verwendung von ORDER BY #

Falsch: ORDER BY zu jeder Abfrage hinzufügen. Korrektur: Verwenden Sie ORDER BY nur für Top N oder wenn die Fragestellung ausdrücklich eine Rangfolge verlangt.

P18. Manuelle Berechnung der Wachstumsrate #

Falsch: DIVIDE(AGG(Umsatz), AGG(Umsatz, 'ya')) - 1 Korrektur: Verwenden Sie AGG(Umsatz, 'yoy') mit dem integrierten Modifikator.

P20. Existenzprüfung allein mit DISTINCT #

Falsch: SELECT DISTINCT Kunde FROM MODEL.Transaktionen für die Frage „Haben wir überhaupt Kunden?“ Korrektur: Geben Sie mit SELECT Kunde, dt_date, TransaktionsID FROM MODEL.Transaktionen LIMIT 1 einen konkreten Datensatz zurück.

Kategorie: DML-Modellierung #

P45. Kennzahl in einer Detailabfrage #

Falsch: dataset: DATASET_PRODUCTS in einer Abfrage, die die Kennzahl total_cost: auswählt. Korrektur: Entfernen Sie dataset:, um in den Aggregatmodus zu wechseln, oder entfernen Sie die Kennzahl aus der Detailabfrage.

P46. Spaltenname ohne Dataset-Angabe in einer Aggregatabfrage #

Falsch: Artikelnummer: ohne dataset:, wenn die Spalte zu DATASET_PRODUCTS gehört. Korrektur: Artikelnummer: "{DATASET_PRODUCTS}.Artikelnummer".

P47. Uneinheitliche Dimensionsfeldnamen in verschiedenen Datasets #

Falsch: DATASET_PT verwendet die Dimension VerkaufspositionID, DATASET_MC die Dimension tag_id. Korrektur: Verwenden Sie einen einheitlichen Namen (z. B. tag_id) und ordnen Sie die Spalten des Data Warehouse in columns: zu (tag_id: VerkaufspositionID).

P48. Zuordnung als Dimensionsfeld in dimension: #

Falsch: - f_tag_id: {DATASET_PT}.VerkaufspositionID unter columns: dimension:. Korrektur: Führen Sie nur - f_tag_id auf. Definieren Sie die Formel f_tag_id: |- … separat.

P49. Dimensionsfeld unter measures: #

Falsch: tag_id: mit einer Formel unter measures: im Dataset. Korrektur: Geben Sie unter dimension: im Dataset an, auf welcher Ebene die Zeilen definiert sind. Verwenden Sie Kennzahlen nur für Aggregationen.

P50. Komplexer Filter unter filters: in der Abfrage #

Falsch: Eine EXISTS-Unterabfrage oder eine PK-Verkettung über mehrere Felder unter filters: in der Abfrage. Korrektur: Verschieben Sie das Prädikat in die WHERE-Klausel unter sql: im Fakten-Dataset.

P51. Falsche Anzahl von Parametern bei einer PK-Verkettung #

Falsch: pk(1, tag_id).{DATASET_PRODUCTS}.state, wenn DATASET_PRODUCTS den zusammengesetzten PK (brand_id, tag_id) hat. Korrektur: Verwenden Sie pk(brand_id, tag_id).{DATASET_PRODUCTS}.state mit allen PK-Spalten.

P52. Manuelles GROUP BY in after: #

Falsch: In einer Standardabfrage für Kennzahlen unter after: mit group by erneut aggregieren. Korrektur: Lassen Sie den Abfrageblock die Kennzahlen aggregieren. Lassen Sie after: weg, damit die Dimensionen automatisch sortiert werden. Wenn eine benutzerdefinierte Sortierung oder Begrenzung den Block erfordert, verweisen Sie auf {QUERY} und beschränken Sie den Block auf die Darstellung der Ergebnisse (select * from {QUERY} plus ORDER BY/TOP/LIMIT), sofern keine unvermeidbare benutzerdefinierte Nachbearbeitung mit SQL ausdrücklich dokumentiert ist.

Befehle und Hinweise zur Ergebnisprüfung finden Sie unter Abfrage kompilieren und validieren.

P60. Unterabfrage für das Datum mit MAX in einer Aggregationsabfrage #

Falsch: WHERE dt_month = (SELECT MAX(dt_month) FROM MODEL ...) Lösung: Den Monat für die Prüfung fest vorgeben oder die Detailabfrage SELECT MAX(dt_month) FROM MODEL.<dataset> verwenden.

P61. Direkt auf dem Datensatz mit GROUP BY aggregieren #

Falsch: SELECT Käufernummer, 品牌, SUM(Abgabepreisbetrag) FROM MODEL.DATASET_X GROUP BY Käufernummer, 品牌 Symptom: cannot aggregate directly on dataset MODEL.DATASET_X using GROUP BY Lösung: Entweder (a) Kennzahlen in model.dml definieren und FROM MODEL mit AGG() verwenden oder (b) für Ad-hoc-Abfragen Inline-Kennzahlen in Kommentarblöcken der Form /** dml ... **/ verwenden, ohne .dml zu bearbeiten (siehe Inline-Kennzahlen (/** dml ... **/)).

Fehlerbehebung bei Abfragen #

Prüfen Sie zunächst das Modell und die Joins mit einer Abfrage, die nur eine Kennzahl enthält. Fügen Sie dann Dimensionen, Filter und Kennzahlen einzeln wieder hinzu. Wenn die Abfrage zu viele Zeilen liefert, prüfen Sie, ob Schlüssel im Datensatz mehrfach vorkommen, wie viele Zeilen nach dem Join vorliegen und welche Schlüssel nur im Vergleichszeitraum vorkommen. Wenn Werte abweichen, führen Sie eine separate Abfrage in SQL mit demselben Zeitraum und demselben Datenstand aus und vergleichen Sie für jede Gruppe die Schlüssel, NULL und die Kennzahlenwerte.
