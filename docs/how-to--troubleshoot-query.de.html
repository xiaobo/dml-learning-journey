Fehler in einer Abfrage beheben

Inhalt dieser Seite
  • Ablauf der Fehlersuche (Model Query SQL)
  • Kompilierungsfehler lesen

Gehen Sie wie folgt vor, wenn die Kompilierung fehlschlägt, eine Warnung im Strict-Modus erscheint oder das ausgegebene SQL von der beabsichtigten Abfragelogik abweicht. Klären Sie ungewisses Verhalten mit der ausgewählten dmlc.exe.

Ablauf der Fehlersuche (Model Query SQL) #

Verwenden Sie diesen Ablauf, wenn die Kompilierung COMPILE_ERROR meldet oder die Meldungen UNION, JOIN, subquery, aggregation is not possible, ref {...} not defined, measure cannot be redefined oder use existing measure enthalten.

  1. Lesen Sie die vollständige Fehlermeldung einschließlich des generierten -- dialect: … SQL in den Meldungsdaten.
  2. Bestimmen Sie den Abfragetyp: Detailabfrage (Existenzprüfung, Liste oder einzelner Datensatz) oder Aggregation. Verwenden Sie für Aggregationen FROM MODEL + AGG(). Verwenden Sie FROM <name> als Quelle, wenn die Modelldatei <name>.dml heißt.
  3. Wählen Sie die passende FROM-Klausel. Für Aggregationen verwenden Sie FROM MODEL oder, wenn die Datei <name>.dml heißt, FROM <name>. Für Detailabfragen verwenden Sie FROM MODEL.<dataset> oder FROM <name>.<dataset>, jeweils ohne AGG und ohne GROUP BY. Stimmen Sie den Namen auf die .dml-Datei ab (model.dml ↔ FROM MODEL).
  4. Entfernen Sie nicht unterstütztes SQL. Unterabfragen sowie UNION und JOIN sind nicht zulässig. Verwenden Sie für portable Fensteroperationen fn-Makros aus system_macros.dml (rank, pot, grand), für mehrstufige Aggregationen +d-Kennzahlen und für komplexe Logik .dml-Definitionen (Kennzahlen entwerfen, Modifikatoren kombinieren). Zur Platzierung von Fensteroperationen im Dataset bei manuell geschriebenem OVER siehe Platzierung von Fensteroperationen. In Model Query ist direkt geschriebenes OVER() zulässig, wenn kein fn-Makro das benötigte Muster abdeckt.
  5. Unterscheiden Sie Kennzahlen und Spalten. Verwenden Sie in Abfragen AGG(measure) und in .dml-Dateien {column} oder '{measure: modifier}'. Wenden Sie in Model Query SQL die Schreibweise {...} nicht auf direkt referenzierte Spalten an. Die Ausnahme ist AGG({measure: modifier}).
  6. Grenzen Sie den Fehler schrittweise ein. Validieren Sie zuerst SELECT AGG(one_measure) FROM MODEL und fügen Sie danach GROUP BY und Filter hinzu. Verwenden Sie dazu dmlc --validate <query.sql> --model=<model> --connection=<id> --json.

Kompilierungsfehler lesen #

Lesen Sie die Compilermeldung zusammen mit dem generierten SQL. Wenn die Ursache unklar ist, reduzieren Sie die Abfrage auf eine Kennzahl und fügen Sie anschließend Spalten und Filter einzeln hinzu.

Checkliste zur Fehlervermeidung #

Prüfen Sie vor dem Einreichen von DML oder Model Query SQL die folgenden Punkte:

  1. Kennzahlen haben fachliche und keine technischen Namen.
  2. Kennzahlenformeln in .dml-Dateien enthalten kein AGG().
  3. Einfache AGG(measure)-Ausdrücke haben keine überflüssigen Aliase.
  4. Für Zeitmodifikatoren ist der zeitliche Kontext eindeutig bestimmt, und die Voraussetzungen der Makros sind erfüllt.
  5. Zeitfilter verwenden das Datumsformat mit dem ersten Tag des jeweiligen Zeitraums.
  6. Zur besseren Lesbarkeit können Zeitfilter am Ende stehen. Die Syntax schreibt keine Reihenfolge der Prädikate vor.
  7. Die Abfrage enthält keine Unterabfragen, JOINs oder UNIONs.
  8. Speichern Sie gut lesbares Model Query SQL in einer .sql-Datei.
  9. Der Abfragetyp entspricht dem Ziel der Abfrage (Detailabfrage oder Aggregation).
  10. Die Prüfung mit --validate ist für die vorgesehene Datenbankverbindung erfolgreich.
  11. Aggregieren Sie MODEL.DATASET_* nicht direkt mit GROUP BY. Verwenden Sie FROM MODEL + AGG() oder exportieren Sie die Detaildaten.
  12. Bei zusammengesetzten Kennzahlen mit lückenhaften Daten oder FOJ aktivieren Sie für die referenzierten Eingaben das Auffüllen mit einem Standardwert. Dazu muss isnull, ifnull oder coalesce(公式, 字面量) die äußerste Funktion sein (P28b). Auch beim Einbetten einer Abhängigkeit mit aktiviertem Auffüllen wird die Auffülllogik expandiert.
  13. Kennzahlen als Dimensionen: Jede aus einer Kennzahl abgeleitete Dimension hat einen vollständigen, expliziten Entitätsschlüssel (vorzugsweise +d). Bei mehreren Labels hat jedes einen eigenen, mit den anderen übereinstimmenden Schlüssel. Jede ausgegebene Kennzahl lässt sich von der durch Q ∪ K definierten Ebene aus korrekt auf eine gröbere Ebene aggregieren. Labelfilter greifen erst, wenn das Label vorhanden ist (P66–P68).
  14. Wenn auf feiner Granularität zuerst in einer CTE mit WHERE gefiltert und anschließend außen mit SUM summiert werden soll, verwenden Sie SUMIF oder SUM(iif) mit passendem {+d: …}. Setzen Sie keine direkten Kennzahlenfilter in der Abfrage auf gröberer Ebene ein (P69).
  15. Platzierung von Fensteroperationen: Auf Detailebene steht OVER unter columns:, gefolgt von der atomaren Aggregation. Nach GROUP-BY gehört die Fensteroperation in eine zusammengesetzte Kennzahl oder zu {-d:} oder {-df:}. Verwenden Sie OVER niemals auf atomaren Kennzahlen (P70–P71).
  16. Wenn zwei Felder, die die Granularität bestimmen, Aliase derselben physischen Spalte sind, prüfen Sie jede generierte ON-Klausel für die Rollup-Aggregation auf den richtigen Schlüssel (P72). Wenn Sie einen expliziten Schlüssel benötigen, übernehmen Sie die Daten mit pk() in ein sql:-Dataset mit deklarierter Dimension (P77).
  17. Dataset-übergreifende zusammengesetzte -df-Rollups verwenden FULL OUTER. Filtern Sie Zeilen, die nur auf der Partnerseite vorkommen, mit '{primary_measure} is not null': heraus (P73). Temporäre Ergebnisse der Partnerseite können mit max() aufgefüllte Schlüssel enthalten. Dadurch können „zusätzliche Zeilen“ wie gültige Paare einer Zeile mit sich selbst aussehen.
  18. Verwenden Sie für dasselbe Objekt niemals {+d:x,-d:x} oder {+d:x,-df:x}. Solche Kombinationen müssen einen klaren Fehler auslösen. Schreiben Sie den Ausdruck explizit um (P79).
  19. -f entfernt keine Filter, die die Grundgesamtheit der Abfrage bestimmen. Blockierte Filter, die sich nicht auf die Granularität beziehen, benötigen EXISTS (P80).
  20. Wenn Sie die Zeitdimension mit dimension: über Granularitätsebenen hinweg ersetzen, benötigen Sie eine Kalendertabelle als Brücke und müssen die Werte auf die Zielzeilen übertragen (P81).
  21. {m:{+d:x}} allein liefert nur Ergebnisse auf der feineren Granularitätsebene. Für die Rückaggregation auf die ursprüngliche Ebene ist eine äußere Aggregation mit SUM, AVG usw. erforderlich. Eine Ausnahme sind MAD-Labelbindungen.
