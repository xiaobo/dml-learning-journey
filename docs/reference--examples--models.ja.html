以下のコード断片では、クエリのディメンション、補完、マテリアライズ、複数のデータセットにまたがる粒度を扱います。各例で名前を挙げたモデルオブジェクトが必要です。

ディメンション修飾子 #

分析の問い：各製品が属するカテゴリ内で、その製品の割合はどのくらいですか？

カテゴリ内の製品別割合 #

SELECT category, product,
       AGG(sales) as product_sales,
       AGG({sales: {dimension: [category]}}) as category_total
FROM MODEL
GROUP BY category, product

ここでは {sales: {dimension: [category]}} が product と region を除外するため、sales はカテゴリだけを粒度として評価されます。

pot の使用（総計に対する割合） #

pot はすべてのディメンションを除外し、各行の値が総計に占める割合を求めます。

SELECT category, product,
       AGG(sales) as product_sales,
       AGG({sales: pot}) as share_of_grand_total
FROM MODEL
GROUP BY category, product

親ディメンション内での割合（たとえば、製品の値をカテゴリの合計で割った値）を求める場合は、代わりに dimension 修飾子を使用します。

-- Share of category (product / category total)
SELECT category, product,
       AGG(sales) as product_sales,
       DIVIDE(AGG(sales), AGG({sales: {dimension: [category]}})) as category_share
FROM MODEL
GROUP BY category, product

非表示のディメンションフィールド #

データセットには、内部計算に必要でも、エンドユーザーには表示すべきでないディメンションが含まれることがあります。

transactions:
    type: dataset
    dimension:
        - dt_date
        - product
        - region
    columns:
        dt_date:
        product:
        region:
        transaction_id:          # internal dimension, not for analysis
        amount:

transaction_id は引き続き +d 修飾子で使えます。MODEL テーブルには表示されません。

移動年間合計（MAT） #

SELECT dt_month, AGG(sales), AGG({sales: mat})
FROM MODEL
WHERE dt_month BETWEEN date(current_date, 'start of month', '-12 months')
                   AND date(current_date, 'start of month', '-1 month')
GROUP BY dt_month

mat は、各 dt_month を最終月とする直近 12 か月の合計を計算します。

要点：+d はドリルダウンを行います。評価ディメンションにディメンションフィールドを追加し、より細かい粒度で集計してから、元の粒度に戻します。-d はディメンションフィールドを除外します（ロールアップ）。dimension: [list] は評価ディメンション全体を置き換えます。これらを使うと、構成比や親子レベル間の比率を求めたり、粒度を変えて比較したりできます。

組み合わせ列 #

分析の問い：製品ごとに、支払い済みの請求書に記載された数量の最小値を表示するにはどうすればよいですか？

条件付き集計 #

min_paid_qty:
    type: measure
    dataset: transactions
    formula: MINIF({quantity}, {is_paid} = 1)

SELECT product, AGG(min_paid_qty)
FROM MODEL
GROUP BY product

日付の補完と既定値による補完の違い #

日付を補完する（すべての日付を表示）：カレンダーまたは連続した日付系列で必要な粒度が使えるようにします。たとえば、Dim Calendar でフラグを設定し、その粒度でクエリを実行します。

Dim Calendar:
    type: dataset
    table: DML_CALENDAR
    dimension:
        - dt_date
    columns:
        dt_date:
        has_data:
            source: '1'

行が欠落している場合に既定値で補完する（結合 / FOJ 後の NULL の伝播を防ぐ）：最外層に isnull / ifnull / coalesce(公式, 字面量) を指定して有効にします。補完が適用されるのは、その指標の使用箇所だけです。詳細は欠落行の補完を参照してください。

daily_sales:
    type: measure
    formula: 'isnull(SUM({sales: {+d: dt_date}}), 0)'   # activate

後続の複合計算で結合後の欠落行を補う場合は、SUM(isnull({sales: {+d: dt_date}}, 0)) だけに頼らないでください。参照する指標か、複合計算の結果に対して補完を有効にします。

要点：条件に基づいて単一の値に集計するには、MINIF / MAXIF / AVGIF を使用します。日付に欠落がある場合は日付を補完し、結合後の指標の行に欠落がある場合は使用箇所で既定値を使って補完します（P28b）。

マテリアライズ候補の選択に使う allows: ALL #

構文と例については、allows: ALLを参照してください。allows: ALL を指定すると、互換性のあるマテリアライズを候補にできます。指標の粒度に関する制約は引き続き適用されます。

マテリアライズ #

分析の問い：あるダッシュボードは、過去 24 か月の月次売上、前年同月比の伸び率、MAT を毎時クエリします。元のデータセットは非常に大きくなっています。

解決策：マテリアライズする #

指標を定義し、続いて、それらの指標を固定の粒度で事前集計するマテリアライズオブジェクトを定義します。

sales:
    type: measure
    dataset: transactions
    formula: SUM({amount})

sales_yoy:
    type: measure
    formula: '{sales: yoy}'

sales_mat:
    type: measure
    formula: '{sales: mat}'

DWS_SALES_DATE_PRODUCT:
    type: materialize
    parameters:
        dt_date: date
    dimension:
        - dt_date
        - product
    measures:
        - sales
        - sales_yoy
        - sales_mat

データセットは、自身の定義内でマテリアライズを宣言することもできます（データセットに materialize: <name> を指定）。データセット定義（type: dataset）を参照してください。独立したオブジェクトとして定義する形式については、マテリアライズの宣言を参照してください。

⚠️ 指標レベルには materialize: true フラグはありません。コンパイラはこの指定を拒否し、undefined modifier 'materialize' を返します（dmlc -c で確認済み）。マテリアライズは type: materialize またはデータセットレベルの materialize: <name> で宣言します。指標には宣言できません。

仕組み #

  1. コンパイラはマテリアライズを登録し、列挙された指標を dimension: で指定された粒度で事前集計します。
  2. 互換性のある粒度でこれらの指標を参照するクエリは、元データをスキャンする代わりに、マテリアライズ済みテーブルから結果を取得する候補になります（allows: の設定に従います。クエリ定義（type: query）を参照）。
  3. マテリアライズの更新は、対応するストアドプロシージャ（parameters:）で行います。リアルタイムでは更新されません。

マテリアライズされていないディメンションで絞り込むクエリ #

SELECT dt_month, product, region, AGG(sales)
FROM MODEL
WHERE region = 'North'
GROUP BY dt_month, product, region

マテリアライズの粒度が dt_date + product（region なし）の場合、このクエリにはそのマテリアライズを使用できません。必要に応じて、複数の粒度でのマテリアライズを検討してください。

マテリアライズが適した場面 #

ケース マテリアライズするか
指標のスキャン頻度が高く、元データが非常に大きい はい
厳格な SLA が適用されるダッシュボードで指標を使用する はい
指標をアドホックに、まれにクエリする いいえ（追加コストに見合わないため）
指標の粒度 = 元データの粒度 いいえ（集計によるメリットがないため）
指標に複雑なウィンドウ関数が含まれる はい

要点：マテリアライズは type: materialize オブジェクトで宣言します（粒度は dimension:、指標は measures: で指定）。指標自体には宣言できません。マテリアライズされた指標は、クエリで通常どおり参照します（AGG(sales)）。マテリアライズの定義（type: materialize）とマテリアライズの設計を参照してください。

ETL をマテリアライズで置き換える #

分析の問い：ストアドプロシージャがファクトテーブルを作成し（INSERT INTO RPT_X SELECT ... FROM raw LEFT JOIN dim1 LEFT JOIN dim2 ...）、レポートがその後 RPT_X を使用します。このストアドプロシージャを DML で置き換えられますか？

解決策：ETL パイプラインをマテリアライズオブジェクトとしてモデル化する #

RPT_X を外部で作成された table: データセットとして扱う代わりに、パイプライン全体をモデル化します。元データを table: データセットとして定義し、pk() を連鎖させてデータを補強し、RPT_X を補強済みのデータソースから事前集計する type: materialize として定義します。

# 1. Dimension datasets (the stored procedure's #temp tables)
Dim Customer:
    type: dataset
    table: MDM_STORE
    dimension: [store_id]
    columns:
        store_id:
        store_name:
        hq_id:

Dim Org:
    type: dataset
    table: MDM_ORG
    dimension: [org_id]
    columns:
        org_id:
        emp_name:

# 2. Source fact dataset with pk() chain enrichment
#    (replaces the stored procedure's SELECT ... LEFT JOIN ...)
raw_sales:
    type: dataset
    table: RAW_SALES
    dimension: [dt_month, store_id, prod_id]
    columns:
        dt_month:
        store_id:
        prod_id:
        amt:
        # pk() chain enrichment replaces LEFT JOINs
        store_name: pk({store_id}).{Dim Customer}.store_name
        hq_id: pk({store_id}).{Dim Customer}.hq_id
        # nested pk() chain: hq_id → Dim Customer → ... (hq_id is itself a pk result)
        hq_name: pk({hq_id}).{Dim Customer}.store_name
        # three-hop chain: store → hq_id → org_id → emp_name
        hq_org_id: pk({hq_id}).{Dim Customer}.org_id
        hq_emp: pk({hq_org_id}).{Dim Org}.emp_name
    measures:
        sales: SUM({amt})

# 3. Materialize replaces INSERT INTO RPT_X
#    Grain keys (dt_month, store_id, prod_id) go in dimension:.
#    Functionally dependent attributes (store_name, hq_name, hq_emp) go in
#    dimension_columns: — the compiler rejects derivable attributes in dimension:.
RPT_X:
    type: materialize
    parameters:
        dt_month: range
    dimension:
        - dt_month
        - store_id
        - prod_id
    dimension_columns:
        store_name:
        hq_name:
        hq_emp:
    measures:
        - sales

# 4. Report query consumes the materialize
report:
    type: query
    allows:
        - RPT_X
    filters:
        dt_month: { range: ['2024-01-01', '2024-03-01'] }
    columns:
        dimension: [dt_month, store_name]
        sales: '{sales}'

このパターンを使う場面：

  • 基準となる SQL の実装は、INSERT INTO ... SELECT ... FROM raw JOIN dims を含むストアドプロシージャです。
  • ストアドプロシージャの一時テーブルは、pk() チェーンで参照先を検索するディメンションデータセットとして素直に表現できます。
  • ストアドプロシージャで INNER JOIN によって対象行を絞り込む条件は、指標の集計対象を制限する条件になります。元の対象行を維持し、生成された述語を確認してください。

注意点：

  • @month（最終残高月）を使って過去の全月のマスターデータを更新するストアドプロシージャは、pk() チェーンで archive_month（月ごとのマスターデータ）を結合キーにする方法では厳密に再現できません。同じソースデータのスナップショットで結果を比較する必要がある既知の制約として記録してください。
  • CROSS APPLY を使うテーブル値関数と、CASE WHEN を使うキーの再マッピングには、ディメンションデータセットで sql: によるエスケープが必要です。変換後のキーを宣言し、一意性を検証してください。

ディメンションが異なる場合 #

分析したいこと：地域別の売上と倉庫別の在庫を比較します。dt_date と product は共通ですが、region と warehouse は共通ではありません。

比較の課題 #

ディメンションがまったく異なるデータセットの指標は、ディメンションをそろえない限り直接比較できません。

sales:
    type: dataset
    table: fact_sales
    dimension:
        - dt_date
        - product
        - region
        - customer
    columns:
        dt_date:
        product:
        region:
        customer:
        amount:

inventory:
    type: dataset
    table: fact_inventory
    dimension:
        - dt_date
        - product
        - warehouse
    columns:
        dt_date:
        product:
        warehouse:
        units:

total_sales:
    type: measure
    dataset: sales
    formula: SUM({amount})

total_inventory:
    type: measure
    dataset: inventory
    formula: SUM({units})

共通の粒度：商品と日付単位 #

SELECT dt_date, product, AGG(total_sales), AGG(total_inventory)
FROM MODEL
WHERE dt_date = date(current_date)
GROUP BY dt_date, product

両方の指標に dt_date と product が共通しているため、この比較が可能です。モデルは欠けているディメンションを暗黙的に処理します。

同じクエリに地域と倉庫が必要な場合 #

通常、region と warehouse の両方でグループ化することは できません。total_inventory には region がなく、total_sales には warehouse がないためです。

方法 1：2 つのクエリに分ける

-- Sales by region
SELECT dt_date, region, AGG(total_sales) FROM MODEL GROUP BY dt_date, region

-- Inventory by warehouse
SELECT dt_date, warehouse, AGG(total_inventory) FROM MODEL GROUP BY dt_date, warehouse

方法 2：修飾子で互換性のないディメンションを除外する

SELECT dt_date, region,
       AGG(total_sales) as sales,
       AGG({total_inventory: {-d: warehouse}}) as inventory_dropped_warehouse
FROM MODEL
GROUP BY dt_date, region

{-d: warehouse} は、在庫の粒度を定めるディメンションから warehouse を除外します。これにより、在庫は dt_date + product の粒度で計算され、dt_date + region + product の粒度の売上と結合できます。ただし、通常はこの結合が業務上の意味に合うか疑問が残るため、慎重に扱ってください。

選択した期間と全履歴の合計 #

-d はグループ化を解除します。月のフィルターが残っている場合、全履歴が対象になるわけではありません。これらのモデル断片では、対象範囲を明示したクエリを個別に使用します。

-- Selected month
SELECT product, region, AGG(total_sales) AS period_sales
FROM MODEL
WHERE dt_month = date(current_date, 'start of month')
GROUP BY product, region

-- All history
SELECT product, region, AGG(total_sales) AS all_time_sales
FROM MODEL
GROUP BY product, region

このページで必要となるモデル定義を使って、各ステートメントを個別に実行してください。1 つのレポート内で比較を最後まで実行した例は、固定軸の分母を参照してください。その例で通常のグループ化に使うフィールド month は、時間コンテキスト dim_dt とは別です。

要点：共通するディメンションが十分にあれば、異なるデータセットの指標を同じクエリで取得できます。ディメンションがそろわない場合は、クエリを分けるか、-d 修飾子を慎重に適用してください。互換性を持たせるためにディメンションを除外すると、結果が誤解を招くことがあります。除外の意図を記録してください。
