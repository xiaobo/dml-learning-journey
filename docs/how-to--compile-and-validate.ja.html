このガイドでは、モデルクエリのコンパイル、診断情報と生成されたSQLの確認、ソースデータのキーの検証、結果の比較を行います。インストール済みの実行ファイルで使用できるオプションは、--helpと--advanced-helpで確認できます。

モデル、読み込まれる定義、関連する設定をクエリと一緒に保管してください。いずれかを変更すると、生成されるSQLが変わることがあります。

1. 実行ファイルとモデルを特定する #

ドキュメントに記載されたビルドと動作を比較する前に、実行ファイルのパス、バージョン、ビルドのタイムスタンプ、SHA-256ハッシュを記録します。

$dmlc = (Get-Command dmlc.exe).Source
& $dmlc --version
Get-FileHash -LiteralPath $dmlc -Algorithm SHA256
& $dmlc --advanced-help

dmlc.exeをインストールし、そのディレクトリをPATHに追加します。以下のコマンドは、モデルとクエリが入っているディレクトリで実行します。

モデルのファイル名とSQLのFROM句で指定する名前を対応させます。model.dmlにはFROM MODELを、acme.dmlにはFROM acmeを使用します。ファイルを指定するには--model=model.dmlを渡します。ファイル名に基づいて自動検出するには、そのファイルが入っているディレクトリを渡します。詳しくはクエリに対応するファイルの検出を参照してください。

2. lint チェックと厳格モードでのコンパイルを行う #

モデルの lint チェックを行ってから、そのモデルを使うクエリを厳格モードでコンパイルします。

& $dmlc --lint model.dml --json
& $dmlc --compile --strict query.sql --model=model.dml --json --artifacts=gen

各コマンドの実行後に、プロセスの終了コードを確認します。JSON出力のステータス、診断情報、補足情報、出力されたSQL、出力順序を確認します。生成されたクエリのグループ化、結合、述語、別名、選択列が、クエリの仕様に合っていることを確認します。

厳格モードでのコンパイルで指摘が出た場合は、警告と出力されたSQLを保存します。クエリを変更する前に、対象となるデータの範囲とNULLの扱いを明確にします。--strictを外しても、厳格モードのチェックに合格したことにはなりません。

--artifactsを使うと、コンパイルで生成されたSQLと関連ファイルをディレクトリに保存できます。コマンドの結果をファイルに保存するには、--outputを使います。

3. 文字エンコーディングを変えずにJSONを保存する #

--output でクエリの結果行をファイルに保存します。次の例では --replace を指定しているため、既存の result.json を上書きできます。--with-validation を付けると、実行前に、クエリが使うデータセットのキーを対象の接続先で検証します。

& $dmlc --query query.sql --model=model.dml --connection=default --with-validation --output=result.json --replace

lint チェックやコンパイルの記録を取るときは、stdout と stderr を別々に取得します。Node.js で引数を配列として渡すと、シェル用の引用符処理を避けられ、デコードにUTF-8を明示的に指定できます。このスクリプトを、モデルとクエリと同じディレクトリにcompile.cjsとして保存します。

const fs = require('node:fs');
const { spawnSync } = require('node:child_process');
const result = spawnSync(process.argv[2], [
	'--compile', '--strict', 'query.sql', '--model=model.dml',
	'--json', '--artifacts=gen'
], { encoding: 'utf8', cwd: __dirname });
if (result.error) throw result.error;
fs.writeFileSync('compile.stdout.json', result.stdout);
fs.writeFileSync('compile.stderr.txt', result.stderr);
const report = JSON.parse(result.stdout);
console.log(JSON.stringify({ processExit: result.status, report }, null, 2));
process.exitCode = result.status ?? 1;

選択した実行ファイルを指定して、スクリプトを実行します。

node compile.cjs $dmlc

JSONの解析に失敗した場合は、加工していない出力ストリームとプロセスの終了コードを保存します。クエリ言語のエラーと判断する前に、解析に失敗した原因を調べます。

Windows PowerShell 5.1では、ネイティブコマンドの出力をパイプでOut-Fileに渡したり、テキストとして取得したりすると、ASCII以外の文字が通知なしに破損することがあります。stdout を取得する前に、コンソールのデコード設定をUTF-8にします。

[Console]::OutputEncoding = [System.Text.Encoding]::UTF8

stdout をバイト列のまま保存するには、モデルのディレクトリでコマンド プロンプト（cmd.exe）を開き、次のコマンドを実行します。

dmlc.exe --compile --strict query.sql --model=model.dml --json --artifacts=gen > compile.stdout.json 2> compile.stderr.txt

Windows PowerShell 5.1は&&に対応していないため、コマンドは個別に実行します。JSONを出力する stdout に stderr を混ぜないでください。対話操作で stderr を抑制する必要がある場合は、PowerShellで2>$nullを使います。

4. ソースデータのキーとデータベースでの計画可否を検証する #

レポートが必要な場合は、--validateを使います。結果が必要で、検証記録がないか、既存の記録が古い場合は、検証付きのクエリ実行を使います。

& $dmlc --validate query.sql --model=model.dml --connection=default --json

default を対象の接続名に置き換えます。終了コード、検証ステータス、検証したデータセット、報告された問題を確認します。CLI の JSON レポートでは、検証の詳細は data にあります。

検証では、クエリが使用する宣言済みのデータセットキーごとに、同じキー値に対応するソース行が最大1行であることを確認します。また、EXPLAINを使って、データベースがクエリの実行計画を作成できるかを確認します。業務上の集計値は、独立したSQLクエリの結果で確認します。

たとえば、異なる2件の仕訳が同じキー(勘定科目, 請求書, party)を持ち、金額がそれぞれ10と20だとします。この組み合わせがデータセットのdimension:として宣言されている場合、検証ではそのキーと、一致した2行が報告されます。--with-validationを指定すると、クエリは実行前に停止します。仕訳のIDをデータセットキーとして宣言し、クエリで account、invoice、party ごとにグループ化すると、合計は30になります。2行が意図しない重複である場合は、ソースデータか、重複を生じさせた結合を修正します。

モデル、クエリの仕様、接続、関連するソースデータのいずれかが変わった場合は、検証をやり直します。前提条件が満たされていない場合は、チェックの結果をnot runとして記録し、不足している前提条件を明記します。

5. クエリを実行して結果を比較する #

--with-validationを指定し、対象の接続先でクエリを実行します。このオプションを付けずに実行すると、接続先のデータを使ったデータセットキーの検証と、データベースで実行計画を作成できるかどうかの確認が省略されます。

& $dmlc --query query.sql --model=model.dml --connection=default --with-validation --json

クエリと指定したエクスポートは、検証に合格した後にのみ実行されます。検証に失敗した場合や検証を完了できない場合は、レポートを確認し、問題を解消してから再実行します。検証と実行では、データベースを別々に読み取ります。その間に、別の処理がデータを変更することがあります。

キー、各行の出現回数、NULL、すべての指標を確認します。独立して得られた結果がある場合は、同じソースデータのスナップショットと同じ対象範囲で、両方のクエリの結果を比較します。

DuckDBのキャッシュがロックされている場合は、ロックを保持しているプロセスと接続を特定します。設定済みの別の接続を使うのは、その接続が目的のデータソースを指している場合に限ります。ロックを回避するためだけにソースデータを変更しないでください。

個別のエラーについては、トラブルシューティングの索引とエラーコードを参照してください。

モデル全体を検証する #

dmlc --validate model.dml --connection=default --jsonを実行すると、モデルを使うクエリを指定せずに、宣言済みのキーと範囲制約を検証できます。検証対象のデータセットはcheckedDatasetsで確認します。特定のクエリの実行計画を確認するには、代わりにそのクエリを指定します。

モデルとデータの不整合の修正を練習する #

複合キーと有効範囲の例を実行します。通常の検証、意図的に作った重複や範囲の重なりによる検証エラー、修正後の検証と、それに続く結果の比較を確認します。これにより、参照結果を使う前に、宣言されたキーと実際のデータの不整合を見つけられます。検証とクエリの実行は別々の処理です。検証に合格しても、両方の処理が同じスナップショットを使うことや、今後もキーの一意性が保たれることは保証されません。

変化を調べる、または既存のクエリを復元する #

--explain-change では、指標名と対象期間を指定し、どの期間と比較するかを決めます。次の例では前の期間と比較します。必要な引数は dmlc --advanced-help で確認できます。純売上高、dt_month、地域 を含むモデルで確認したコマンドは次のとおりです。

空の DuckDB データベースに、次の 4 件の売上を登録します。金額はすべて返金を差し引いた後の値です。文を monthly-sales.sql に保存し、DuckDB の接続を使って dmlc -q monthly-sales.sql を実行します。

CREATE TABLE monthly_sales (id INTEGER, dt_month DATE, region VARCHAR, net_amount INTEGER);
INSERT INTO monthly_sales VALUES
  (1, DATE '2025-01-01', 'North', 100),
  (2, DATE '2025-01-01', 'South', 200),
  (3, DATE '2025-02-01', 'North', 300),
  (4, DATE '2025-02-01', 'South', 100);

次のモデルを例のディレクトリに model.dml として保存し、2 月と 1 月を比較します。

dialect: duckdb
取引明細:
    type: dataset
    table: monthly_sales
    dimension: [売上明細番号]
    columns:
        売上明細番号:
            abbr: id
        dt_month:
            abbr: dt_month
        地域:
            abbr: region
        純額:
            abbr: net_amount
    measures:
        純売上高: SUM({純額})

dmlc --explain-change --measure=純売上高 --dim_dt=dt_month --current=2025-02-01 --baseline-modifier=pp --dimensions=地域 --model=model.dml

比較用のテストデータでは、基準値は 300、現在値は 400、地域別の寄与は +200 と -100 です。これらはこのテストデータの値であり、このサイトのすべての例に共通する値ではありません。ディメンションの順位を解釈する前に、基準値と現在値を確認してください。寄与と意外性スコアは、何を調べるかを決める手がかりになります。原因の特定や交絡要因の除外はできません。

既存の SQL クエリから、--to-dml でモデルとクエリのドラフトを生成できます。

dmlc --to-dml raw.sql --output=recovered.dml

新しい出力パスを使い、生成されたドラフトに関する警告は残してください。これらのコマンドは dmlc 0.3.16 で確認済みです。利用できるオプションは操作によって異なるため、コンパイル専用のオプションを復元コマンドに付けないでください。推定されたキー、数式、母集団と、出力された警告を確認します。その後、復元したクエリをコンパイルして検証し、同じソースデータのスナップショットを使って元のクエリと結果を比較してください。ドラフトの生成は、セマンティックモデルが本番環境で使用できることを保証するものではありません。

これらのツールを組み込む際は、データベースとアプリケーションの責務を明確にしてください。アクセスはデータベースの権限とアプリケーションの認可で制御します。モデルのフィルターだけではアクセス制御を保証できません。生成された SQL には複数の文や一時リレーションが含まれることがあり、カレンダーに依存する場合もあります。性能について述べる前に、対象のエンジンで実行を確認し、代表的なワークロードで性能を測定してください。コンパイラはダッシュボードや実行スケジュールの機能を提供しません。

コンパイルと検証の手順 #

作業ディレクトリで、まず dmlc --lint model.dml --json を実行し、次に dmlc --compile --strict query.sql --model=model.dml --json --artifacts=gen を実行します。終了コード、診断メッセージ、生成された SQL を確認してください。検証レポートだけが必要な場合は --validate を使います。クエリ結果が必要な場合は --query と --with-validation を使い、--connection=default で接続先を指定します。--with-validation を付けずに実行すると、接続先のデータベースでのキー検査がスキップされます。
