Beispiele für Aggregation auf feiner Ebene

Inhalt dieser Seite
  • Mehrstufige Aggregation mit +d
  • Auf feiner Ebene filtern, dann mit +d zusammenfassen

In diesen Mustern wird eine Kennzahl auf einer Zwischenebene ausgewertet. Anschließend werden die Werte aggregiert oder gefiltert. Die Ausschnitte nennen die zusätzlichen Modellbestandteile, von denen sie abhängen. Die Syntax der übergebenen Werte ist unter Kennzahlmodifikatoren beschrieben.

Mehrstufige Aggregation mit +d #

Mit +d ist eine zweistufige Aggregation möglich. Definieren Sie eine Kennzahl auf einer Zwischenebene und aggregieren Sie sie dann auf die Ebene der Abfrage. Der Compiler erzeugt eine CTE (WITH ... AS (SELECT ... GROUP BY ...) SELECT ...).

Muster: Kennzahl mit eingeschränkter Dimension → Kennzahl für die Zusammenfassung → Abfrage

# Step 1: require customer_id during evaluation
customer_sales:
    type: measure
    dataset: transactions
    formula: SUM({amount})
    dimensions:
        - [customer_id, ...]  # customer required; additional query fields allowed

# Step 2: evaluate with dimension [customer_id], then roll up to the query dimension
total_customer_sales:
    type: measure
    formula: SUM({customer_sales: {+d: customer_id}})

-- Step 3: use any compatible query dimension ([brand], [region], total, etc.)
SELECT brand, AGG(total_customer_sales) FROM MODEL GROUP BY brand

RFM-Analyse – vollständiges Beispiel mit +d und fn-Makros:

# .dml: customer-grain measures for RFM
last_purchase_month:
    type: measure
    formula: 'MAXIF({dt_month}, {sales: {+d: dt_month}} > 0)'
    dimensions:
        - [customer_id]

purchase_months:
    type: measure
    dataset: transactions
    formula: 'COUNT(DISTINCT CASE WHEN {amount} > 0 THEN {dt_month} ELSE NULL END)'
    dimensions:
        - [customer_id]

-- Model Query SQL: RFM with ranks
SELECT AGG(sales) AS M, AGG(sales, 'rank') AS M_rank,
       AGG(purchase_months) AS F, AGG(purchase_months, 'rank') AS F_rank,
       AGG(last_purchase_month) AS R, AGG(last_purchase_month, 'rank_asc') AS R_rank
FROM MODEL GROUP BY customer_id

Inline-Kennzahlen – Definieren Sie temporäre Kennzahlen direkt im SQL der Modellabfrage, indem Sie /** dml ... **/-Kommentarblöcke verwenden. Dazu müssen Sie .dml nicht ändern. Die vollständige Syntax und alle Regeln finden Sie unter Inline-Kennzahlen (/** dml ... **/).

/** dml
temp_customer_sales:
    type: measure
    dataset: transactions
    formula: SUM({amount})
    dimensions:
        - [customer_id, ...]

temp_avg_customer_sales:
    type: measure
    formula: 'AVG({temp_customer_sales: {+d: customer_id}})'
**/
SELECT brand, AGG(temp_avg_customer_sales) AS avg_customer_sales
FROM MODEL GROUP BY brand

Auf feiner Ebene filtern, dann mit +d zusammenfassen #

Mit SQL geht man häufig so vor: auf feiner Ebene aggregieren → auf dieser Ebene mit WHERE filtern → mit SUM auf eine gröbere Berichtsebene zusammenfassen.

WITH sales AS (
  SELECT product, region, SUM(amount) AS total, COUNT(*) AS cnt
  FROM fact GROUP BY product, region
)
SELECT product, SUM(total) AS grand_total
FROM sales
WHERE cnt > 3                -- filter fine-grain rows
GROUP BY product
HAVING SUM(total) > 500      -- report-level HAVING

Empfohlene Vorgehensweise in DML – Setzen Sie die Filterbedingung für die feine Ebene in die Formel für die Zusammenfassung. Verwenden Sie filters: in der Abfrage nur für den Datenumfang des Berichts oder für HAVING:

DATASET_SALES:
    type: dataset
    table: FACT
    columns:
        product:
        region:
    measures:
        total: SUM(amount)
        cnt: COUNT(1)

grand_total:
    type: measure
    formula: |-
        SUMIF({total: {+d: region}}, {cnt: {+d: region}} > 3)
    # No qualifying fine rows -> NULL. Use an explicit fill only if required.

report:
    type: query
    filters:
        "{grand_total} > 500":
    columns:
        dimension:
            - product
        grand_total:

So funktioniert das Beispiel: {cnt: {+d: region}} und {total: {+d: region}} werden auf derselben feinen Ebene (product, region) ausgewertet. iif bzw. SUMIF bestimmt, welche Zeilen dieser Ebene in das äußere SUM eingehen. Die Abfragedimension bleibt product.

Zu vermeiden Begründung
Eine Abfrage mit filters: "cnt > 3" ausführen und in columns.dimension nur product angeben cnt wird außerhalb der Ebene verwendet, auf der die Kennzahl definiert ist. Beim Kompilieren oder Zusammenführen kann daraus fälschlicherweise HAVING COUNT(1) > 3 auf Produktebene werden.
filters: "{cnt: {+d: region}} > 3" Das lässt sich manchmal kompilieren, kehrt aber die erwartete Logik um. Der Wechsel auf die feinere Ebene steckt im Berichtsfilter.
SUM({total: {+d: region, +f: '{cnt} > 3'}}) Die Bedingung verweist auf eine aggregierte Kennzahl. +f erwartet eine Filterbedingung für Eingabezeilen.

Wenn Sie die Schritte genau wie in SQL abbilden möchten, können Sie als Ausweichlösung die Abfrage auf feiner Ebene beibehalten (dimension: [product, region], filters: "cnt > 3") und in der Darstellung unter after: erneut aggregieren. Für die Modellpflege ist die oben gezeigte Kennzahl vorzuziehen.

Siehe auch Kennzahlen entwerfen und den Fallstrick P69.

Einschränkungen von +d:

  • +d allein führt keine zwei unabhängigen Aliasse für dieselbe Dimension ein. Für eine vollständige N×N-Matrix des gemeinsamen Auftretens können Sie stattdessen einen Datensatz mit sql: verwenden. Verknüpfen Sie eine deklarierte Quelle über den Kunden mit sich selbst, wählen Sie die eindeutigen Kombinationen (customer, brand_from, brand_to) aus, deklarieren Sie diese Feldkombination als vollständigen Schlüssel und zählen Sie dann die Kunden gruppiert nach den beiden Markenfeldern. Der geprüfte Testdatensatz mit zwei Marken lässt sich kompilieren und validieren und liefert A–A: 2, A–B: 1, B–A: 1, B–B: 1. Dazu ist eine explizite Relation für Markenpaare erforderlich. +d führt diese Transformation nicht automatisch aus.

Steht +d in einer Dimensionsbindung der Abfrage (columns.dimension: - name: '{m: {+d: K}}'), handelt es sich um eine Kennzahl als Dimension und nicht um das obige Muster zur Zusammenfassung. Siehe Kennzahl als Dimension.

Analyse gemeinsam gekaufter Marken (1×N-Muster) – Zählen Sie für jede andere Marke die Kunden, die sowohl die Zielmarke als auch diese Marke gekauft haben. Verwenden Sie dazu +d, -d und +f:

/** dml
target_brand_customers:
    type: measure
    formula: 'MAXIF(1, {sales: {+d: customer_id, -d: brand, +f: {brand: ''BrandA''}}} > 0)'
    dimensions:
        - [..., customer_id]

current_brand_customers:
    type: measure
    formula: 'MAXIF(1, {sales: {+d: [brand, customer_id]}} > 0)'
    dimensions:
        - [brand, customer_id]

co_occurrence:
    type: measure
    formula: 'SUM({current_brand_customers: {+d: [brand, customer_id]}} * {target_brand_customers: {+d: customer_id}})'
**/
SELECT brand, AGG(co_occurrence) AS overlap_with_brandA
FROM MODEL GROUP BY brand ORDER BY AGG(co_occurrence) DESC

Entscheidend ist, dass -d: brand das Dimensionsfeld brand aus der Auswertungsdimension der Zielkennzahl entfernt. Es bleibt nur [customer]. +f filtert auf die Zielmarke, und das Produkt der beiden Indikatorwerte zählt die Kunden, die beide Marken gekauft haben.

dimensions: ist bei einer Kennzahl immer ein Array aus Arrays. Jede innere Liste definiert eine zulässige Dimension. Die äußere Liste enthält die Alternativen:

month_active_flag:
    type: measure
    formula: 'ISNULL(MAXIF(1, {month_qty: {+d: [prod_id, dt_month]}} > 0), 0)'
    dimensions:
      - [store_id, dt_month, ...]

... (Auslassungspunkte) lässt innerhalb einer zulässigen Dimension weitere Dimensionsfelder zu. Die aufgeführten Felder bleiben in der Auswertungsdimension der Kennzahlreferenz erforderlich.
