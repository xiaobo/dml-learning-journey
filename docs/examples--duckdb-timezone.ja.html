DuckDB で固定のタイムゾーンを使って営業日を定義する

このページの内容
  • 入力値が何を表すかを確認する
  • 現地時刻の午前0時を2つ使って1日の範囲を定める
  • 現地時刻で同じ時間帯が繰り返される場合に異なる時点を区別する
  • 例を再実行して調整する

日付や日の境界を求める前に、時点を業務で使用するタイムゾーンに変換します。この例では America/New_York を使用し、DuckDB の物理 SQL を検証します。この例は、DML がユーザーごとのタイムゾーンやデータベースをまたぐタイムゾーン処理に自動で対応することを示すものではありません。

入力値が何を表すかを確認する #

入力値は、UTC オフセットが明示された TIMESTAMPTZ 型の時点です。接続のセッションタイムゾーンは UTC、業務で使用するタイムゾーンは America/New_York です。オフセットのないタイムスタンプが自動的に UTC として扱われるわけではありません。まず、データソースでの記録方法を確認します。

SET TimeZone = 'UTC';
SELECT timezone('America/New_York', TIMESTAMPTZ '2024-01-01 02:00:00+00');

現地時刻は 2023-12-31 21:00:00 なので、営業日の日付は前日になります。グループ化に使う日付を取り出す前に、時点を業務で使用するタイムゾーンに変換します。

現地時刻の午前0時を2つ使って1日の範囲を定める #

SELECT count(*)
FROM (VALUES
  (TIMESTAMPTZ '2024-03-10 04:59:59+00'),
  (TIMESTAMPTZ '2024-03-10 05:00:00+00'),
  (TIMESTAMPTZ '2024-03-11 03:59:59+00'),
  (TIMESTAMPTZ '2024-03-11 04:00:00+00')
) events(ts)
WHERE ts >= timezone('America/New_York', TIMESTAMP '2024-03-10 00:00:00')
  AND ts < timezone('America/New_York', TIMESTAMP '2024-03-11 00:00:00');

結果は 2 です。範囲には開始時点を含め、終了時点は含めません。終了時点が常に開始時点の 24 時間後になるわけではありません。検証プログラムは、春の時刻切り替えで 23 時間になる日と、秋の時刻切り替えで 25 時間になる日を検証します。

現地時刻で同じ時間帯が繰り返される場合に異なる時点を区別する #

2024-11-03 05:30 UTC と 06:30 UTC は、どちらも現地時刻の 01:30 に対応します。この2つは異なる時点です。現地時刻のタイムスタンプだけで重複を除外せず、イベントキーと元の時点を保持します。

例を再実行して調整する #

プロジェクトをダウンロードし、README に記載されている JDBC の手順に従って jdbc/VerifyJdbc.java を実行します。既存の JDK とインストール済みの対応する JAR ファイルを使い、展開したプロジェクトのディレクトリから次のコマンドを実行します。

java -cp "C:/path/to/dmlc-assembly.jar;C:/path/to/duckdb-jdbc.jar" jdbc/VerifyJdbc.java "$PWD/jdbc" C:/path/to/driver-directory

パスを置き換えます。他のシステムでは、クラスパスの区切りにセミコロンではなくコロンを使います。プログラムは、物理クエリとセマンティッククエリのパラメータバインドも検証します。最後に表示される成功メッセージと、プロセスの終了コードを確認します。プログラムがサードパーティのランタイムをダウンロードすることはありません。

検証プログラムは、午前0時、繰り返される時間帯、23 時間および 25 時間の日、半開区間による絞り込みを検証します。検証に失敗すると、プログラムはゼロ以外のコードで終了します。

検証対象の JDBC ディストリビューションでは、DuckDB 1.5.4 のドライバーを使用します。DML で営業日の日付を再利用するには、データベースビューで先にタイムスタンプを正規化し、営業日の日付をモデルの列として公開できます。使用するモデルと接続で、この連携が機能することを確認してください。この物理 SQL の例は、タイムゾーンを扱う任意のモデルへの対応を示すものではありません。
