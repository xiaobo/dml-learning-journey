Abfragen mit der dmlc-CLI prüfen und ausführen

In dieser Anleitung kompilieren Sie eine Modellabfrage, prüfen Diagnosemeldungen und das erzeugte SQL, validieren Schlüssel in den Quelldaten und vergleichen Ergebnisse. Mit --help und --advanced-help zeigen Sie die verfügbaren Optionen Ihres installierten Programms an.

Bewahren Sie das Modell, die eingebundenen Definitionen und die relevante Konfiguration zusammen mit der Abfrage auf. Änderungen daran können das erzeugte SQL verändern.

1. Programmdatei und Modell bestimmen #

Halten Sie den Pfad zur Programmdatei, die Version, den Build-Zeitstempel und die SHA-256-Prüfsumme fest, bevor Sie das Verhalten mit dem eines dokumentierten Builds vergleichen.

$dmlc = (Get-Command dmlc.exe).Source
& $dmlc --version
Get-FileHash -LiteralPath $dmlc -Algorithm SHA256
& $dmlc --advanced-help

Installieren Sie dmlc.exe und fügen Sie das Verzeichnis der Programmdatei zu PATH hinzu. Führen Sie die folgenden Befehle in dem Verzeichnis aus, das Ihr Modell und Ihre Abfrage enthält.

Stimmen Sie den Dateinamen des Modells mit dem Namen in der SQL-Klausel FROM ab. Verwenden Sie für model.dml die Angabe FROM MODEL und für acme.dml die Angabe FROM acme. Wählen Sie eine Datei mit --model=model.dml aus. Für die automatische Ermittlung anhand des Dateinamens geben Sie stattdessen das Verzeichnis an, das die Datei enthält. Siehe Dateiermittlung für Abfragen.

2. Lint-Prüfung durchführen und strikt kompilieren #

Führen Sie die Lint-Prüfung für das Modell durch und kompilieren Sie anschließend die Abfrage, die das Modell verwendet, im strikten Modus.

& $dmlc --lint model.dml --json
& $dmlc --compile --strict query.sql --model=model.dml --json --artifacts=gen

Prüfen Sie nach jedem Befehl den Exitcode des Prozesses. Sehen Sie sich den Status in der JSON-Ausgabe, die Diagnosemeldungen und Hinweise, das ausgegebene SQL und die Ausgabereihenfolge an. Prüfen Sie, ob Gruppierung, Joins, Prädikate, Aliase und ausgewählte Spalten der erzeugten Abfrage den Anforderungen an die Abfrage entsprechen.

Wenn die Kompilierung im strikten Modus Auffälligkeiten meldet, bewahren Sie die Warnung und das ausgegebene SQL auf. Klären Sie vor einer Änderung der Abfrage, welche Datensätze einbezogen werden sollen und wie NULL behandelt werden soll. Durch Entfernen von --strict wird die strikte Prüfung nicht bestanden.

Speichern Sie mit --artifacts das bei der Kompilierung erzeugte SQL und die zugehörigen Dateien in einem Verzeichnis. Speichern Sie mit --output das Ergebnis eines Befehls in einer Datei.

3. JSON ohne Änderung der Zeichenkodierung erfassen #

Mit --output schreiben Sie die Ergebniszeilen der Abfrage in eine Datei. Im folgenden Beispiel erlaubt --replace, eine vorhandene result.json zu überschreiben. Mit --with-validation prüft dmlc vor der Ausführung über die Zielverbindung die Schlüssel der von der Abfrage verwendeten Datensätze.

& $dmlc --query query.sql --model=model.dml --connection=default --with-validation --output=result.json --replace

Wenn Sie die Lint-Prüfung oder die Kompilierung dokumentieren, erfassen Sie stdout und stderr getrennt. Ein Argumentarray in Node.js erspart die Maskierung für die Shell und ermöglicht eine explizite Dekodierung als UTF-8. Speichern Sie das Skript als compile.cjs im selben Verzeichnis wie das Modell und die Abfrage.

const fs = require('node:fs');
const { spawnSync } = require('node:child_process');
const result = spawnSync(process.argv[2], [
	'--compile', '--strict', 'query.sql', '--model=model.dml',
	'--json', '--artifacts=gen'
], { encoding: 'utf8', cwd: __dirname });
if (result.error) throw result.error;
fs.writeFileSync('compile.stdout.json', result.stdout);
fs.writeFileSync('compile.stderr.txt', result.stderr);
const report = JSON.parse(result.stdout);
console.log(JSON.stringify({ processExit: result.status, report }, null, 2));
process.exitCode = result.status ?? 1;

Führen Sie das Skript mit der ausgewählten Programmdatei aus.

node compile.cjs $dmlc

Wenn das Parsen von JSON fehlschlägt, sichern Sie die unveränderten Ausgabeströme und den Exitcode des Prozesses. Untersuchen Sie die Ursache, bevor Sie den Fehler als Fehler in der Abfragesprache einordnen.

Windows PowerShell 5.1 kann Ausgaben mit Zeichen außerhalb von ASCII unbemerkt verfälschen, wenn Sie die Ausgabe eines nativen Befehls per Pipe an Out-File übergeben oder als Text erfassen. Stellen Sie die Dekodierung der Konsole auf UTF-8 ein, bevor Sie stdout erfassen.

[Console]::OutputEncoding = [System.Text.Encoding]::UTF8

Um die Bytes von stdout direkt zu speichern, öffnen Sie die Eingabeaufforderung (cmd.exe) im Modellverzeichnis und führen Sie den folgenden Befehl aus:

dmlc.exe --compile --strict query.sql --model=model.dml --json --artifacts=gen > compile.stdout.json 2> compile.stderr.txt

Führen Sie Befehle in Windows PowerShell 5.1 einzeln aus, da && nicht unterstützt wird. Leiten Sie stderr nicht in den stdout-Strom mit der JSON-Ausgabe um. Wenn Sie stderr bei der interaktiven Arbeit unterdrücken müssen, verwenden Sie 2>$null in PowerShell.

4. Quellschlüssel und Planbarkeit durch die Datenbank prüfen #

Verwenden Sie --validate, wenn Sie einen Prüfbericht benötigen. Nutzen Sie die Abfrageausführung mit Validierung, wenn Sie Ergebnisse benötigen und kein aktueller Prüfnachweis vorliegt.

& $dmlc --validate query.sql --model=model.dml --connection=default --json

Ersetzen Sie default durch die vorgesehene Verbindung. Prüfen Sie den Exitcode, den Validierungsstatus, die geprüften Datensätze und die gemeldeten Probleme. Im JSON-Bericht der CLI finden Sie die Validierungsdetails unter data.

Die Validierung prüft für jeden deklarierten Datensatzschlüssel, den die Abfrage verwendet, ob pro Schlüsselwert höchstens eine Quellzeile vorhanden ist. Sie prüft außerdem mit EXPLAIN, ob die Datenbank einen Ausführungsplan für die Abfrage erstellen kann. Prüfen Sie die fachlichen Summen anhand eines unabhängig ermittelten SQL-Ergebnisses.

Angenommen, zwei verschiedene Buchungseinträge haben denselben Schlüssel (Konto, Rechnung, party) und die Beträge 10 und 20. Wenn diese Kombination im Datensatz als dimension: deklariert ist, meldet die Validierung den Schlüssel und die beiden zugehörigen Zeilen. Mit --with-validation wird die Abfrage vor der Ausführung abgebrochen. Deklarieren Sie die ID des Buchungseintrags als Datensatzschlüssel und gruppieren Sie die Abfrage dann nach account, invoice und party, um die Summe 30 zu erhalten. Wenn die beiden Zeilen eine unbeabsichtigte Dublette bilden, korrigieren Sie die Quelldaten oder den Join, der die Dublette erzeugt hat.

Wiederholen Sie die Validierung, wenn sich das Modell, die Anforderungen an die Abfrage, die Verbindung oder relevante Quelldaten ändern. Fehlt eine Voraussetzung, erfassen Sie die Prüfung als not run und geben Sie an, welche Voraussetzung fehlt.

5. Abfrage ausführen und Ergebnisse vergleichen #

Führen Sie die Abfrage mit --with-validation über die Zielverbindung aus. Ohne diese Option prüft das Programm bei der Ausführung weder die Datensatzschlüssel anhand der aktuellen Daten noch, ob die Datenbank einen Ausführungsplan erstellen kann.

& $dmlc --query query.sql --model=model.dml --connection=default --with-validation --json

Die Abfrage und alle angeforderten Exporte werden erst ausgeführt, wenn die Validierung erfolgreich war. Wenn die Validierung fehlschlägt oder nicht abgeschlossen werden kann, prüfen Sie den Bericht und beheben Sie das Problem vor dem nächsten Versuch. Prüfung und Ausführung lesen die Datenbank getrennt. Dazwischen können andere Vorgänge die Daten ändern.

Prüfen Sie die Schlüssel, die Anzahl der Vorkommen jeder Zeile, die NULL-Werte und alle Kennzahlen. Wenn ein unabhängig ermitteltes Ergebnis vorliegt, vergleichen Sie beide Abfragen mit demselben Stand der Quelldaten und demselben fachlichen Umfang.

Wenn ein DuckDB-Cache gesperrt ist, ermitteln Sie den Prozess und die Verbindung, die die Sperre halten. Verwenden Sie eine andere konfigurierte Verbindung nur, wenn sie auf die vorgesehene Datenquelle verweist. Ändern Sie die Quelldaten nicht allein zur Umgehung einer Sperre.

Bei konkreten Fehlern helfen Ihnen der Index zur Fehlerbehebung und die Fehlercodes weiter.

Ein ganzes Modell validieren #

Führen Sie dmlc --validate model.dml --connection=default --json aus, um deklarierte Schlüssel und Bereichsbedingungen ohne eine Abfrage zu prüfen, die das Modell verwendet. Unter checkedDatasets sehen Sie, welche Datasets geprüft wurden. Um den Ausführungsplan einer bestimmten Abfrage zu prüfen, geben Sie stattdessen diese Abfrage an.

Die Korrektur von Abweichungen zwischen Modell und Daten üben #

Führen Sie die Beispiele zum zusammengesetzten Schlüssel und zum Gültigkeitsbereich aus. Verfolgen Sie die reguläre Validierung, einen absichtlich herbeigeführten Fehler durch eine Dublette oder Überlappung und die Validierung nach der Korrektur mit anschließendem Ergebnisvergleich. So erkennen Sie Abweichungen zwischen dem deklarierten Schlüssel und den tatsächlichen Daten, bevor Sie sich auf ein Nachschlageergebnis verlassen. Validierung und Abfrageausführung sind getrennte Vorgänge. Eine erfolgreiche Prüfung garantiert weder, dass beide denselben Datenstand verwenden, noch, dass die Schlüsselwerte künftig eindeutig bleiben.

Eine Änderung untersuchen oder eine bestehende Abfrage wiederherstellen #

Geben Sie bei --explain-change die Kennzahl, den Vergleichszeitraum und den aktuellen Zeitraum an. Im folgenden Beispiel dient die Vorperiode als Vergleich. Die erforderlichen Angaben finden Sie unter dmlc --advanced-help. Für ein Modell mit Nettoumsatz, dt_month und Region wurde folgender Aufruf geprüft:

Legen Sie in einer leeren DuckDB-Datenbank die folgenden vier Verkäufe an. Bei jedem Betrag sind Erstattungen bereits abgezogen. Speichern Sie die Anweisungen unter monthly-sales.sql und führen Sie dmlc -q monthly-sales.sql über die DuckDB-Verbindung aus.

CREATE TABLE monthly_sales (id INTEGER, dt_month DATE, region VARCHAR, net_amount INTEGER);
INSERT INTO monthly_sales VALUES
  (1, DATE '2025-01-01', 'North', 100),
  (2, DATE '2025-01-01', 'South', 200),
  (3, DATE '2025-02-01', 'North', 300),
  (4, DATE '2025-02-01', 'South', 100);

Speichern Sie das folgende Modell im Beispielverzeichnis als model.dml. Vergleichen Sie anschließend Februar mit Januar.

dialect: duckdb
Transaktionen:
    type: dataset
    table: monthly_sales
    dimension: [VerkaufspositionID]
    columns:
        VerkaufspositionID:
            abbr: id
        dt_month:
        Region:
        Nettobetrag:
            abbr: net_amount
    measures:
        Nettoumsatz: SUM({Nettobetrag})

dmlc --explain-change --measure=Nettoumsatz --dim_dt=dt_month --current=2025-02-01 --baseline-modifier=pp --dimensions=Region --model=model.dml

Die Testdaten für den Vergleich enthalten den Referenzwert 300, den aktuellen Wert 400 und regionale Beiträge von +200 und -100. Diese Werte gelten für diesen Testfall und können in anderen Beispielen auf dieser Website abweichen. Prüfen Sie den Referenzwert und den aktuellen Wert, bevor Sie die Rangfolge der Dimensionen interpretieren. Beiträge und Überraschungswerte helfen bei der Auswahl eines Untersuchungsansatzes. Sie belegen keine Ursachen und schließen keine Störfaktoren aus.

Aus einer bestehenden SQL-Abfrage kann --to-dml einen Entwurf für ein Modell und eine Abfrage erzeugen.

dmlc --to-dml raw.sql --output=recovered.dml

Verwenden Sie einen neuen Ausgabepfad und behalten Sie den erzeugten Warnhinweis zum Entwurfsstatus bei. Die Befehle wurden mit dmlc 0.3.16 geprüft. Die verfügbaren Optionen hängen vom Vorgang ab. Übernehmen Sie daher keine Optionen, die nur für die Kompilierung gelten, in Befehle zur Wiederherstellung. Prüfen Sie die abgeleiteten Schlüssel, Formeln und Grundgesamtheiten sowie die Warnungen. Kompilieren und validieren Sie anschließend die wiederhergestellte Abfrage und vergleichen Sie ihre Ergebnisse mit denen der ursprünglichen Abfrage auf demselben Stand der Quelldaten. Die Entwurfserstellung bestätigt keine Produktionstauglichkeit des semantischen Modells.

Legen Sie bei der Integration dieser Werkzeuge klar fest, wofür die Datenbank und wofür die Anwendung zuständig ist. Datenbankberechtigungen und die Autorisierung in der Anwendung regeln den Zugriff. Ein Modellfilter allein gewährleistet keine Zugriffskontrolle. Der generierte SQL-Code kann mehrere Anweisungen und temporäre Relationen enthalten und von Kalendern abhängen. Prüfen Sie die Ausführung auf Ihrer Zieldatenbank-Engine und messen Sie die Leistung unter repräsentativen Lasten, bevor Sie Leistungsangaben machen. Der Compiler stellt weder Dashboards noch eine Zeitplanung für die Ausführung bereit.

Schritte zum Kompilieren und Validieren #

Führen Sie im Arbeitsverzeichnis zuerst dmlc --lint model.dml --json und dann dmlc --compile --strict query.sql --model=model.dml --json --artifacts=gen aus. Prüfen Sie den Exitcode, die Diagnosemeldungen und den generierten SQL-Code. Wenn Sie nur einen Validierungsbericht benötigen, verwenden Sie --validate. Wenn Sie Abfrageergebnisse benötigen, verwenden Sie --query und --with-validation und geben Sie die Zielverbindung mit --connection=default an. Bei einer Ausführung ohne --with-validation werden Schlüsselprüfungen auf der Datenbank übersprungen.
