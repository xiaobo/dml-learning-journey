Dieser Leitfaden hilft Ihnen, das Verhalten von Dimensionen beim Modellieren von Datensätzen, Schreiben von Kennzahlen, Kompilieren von Abfragen und Untersuchen von Zeilenvervielfachungen zu verstehen. Er erläutert das Sprachmodell. Maßgeblich bleibt die Referenz zur Auswertungssemantik von DML.

1. Das Objektmodell #

Ein Dimensionsfeld ist ein einzelnes benanntes Feld in DML.

Eine Dimension ist eine Liste mit einem oder mehreren Dimensionsfeldern.

Beispiele:

[order_id]
[order_id, line_id]
[product_id, dt_month]

Jede Zeile oben definiert eine Dimension. [product_id, dt_month] ist eine Dimension mit zwei Feldern.

Die Kennzahloption dimensions: hat eine zusätzliche Listenebene, weil sie mehrere zulässige Dimensionen zur Auswahl enthalten kann:

dimensions:
  - [customer_id]
  - [account_id, dt_month]

Die äußere Liste enthält zwei zulässige Dimensionen. Jede innere Liste bildet eine Dimension.

Eine Gesamtsumme hat keine Dimension. In der Syntax für Kennzahlmodifikatoren hebt {dimension: []} die Auswertungsdimension auf, um diesen Kontext anzufordern. Die leere Liste steht für eine Operation, nicht für eine Dimension ohne Felder.

2. Die fünf Rollen von Dimensionen #

Die Listenstruktur ist immer dieselbe. Das Verhalten hängt davon ab, an welcher Stelle in DML die Liste steht:

Position in DML Rolle Verhalten
dimension: im Dataset Datensatzdimension Deklariert die Dimensionsfelder, deren vollständige Wertekombination eine einzelne Quellzeile identifiziert.
Formel mit Dimensionsmodifikatoren Auswertungsdimension Bestimmt, mit welcher Dimension eine einzelne Kennzahlreferenz ausgewertet wird.
GROUP BY oder columns.dimension in der Abfrage Abfragedimension Gruppiert die zurückgegebenen Zeilen und bestimmt, wofür eine einzelne Ergebniszeile steht.
dimension: in der Materialisierung Materialisierungsdimension Definiert die Gruppierung und den Schlüssel der materialisierten Relation.
dimensions: in der Kennzahl Zulässige Dimensionen Beschränkt die Auswahl an Dimensionen, mit denen die Kennzahl ausgewertet werden darf. Legt weder die Identität der Quellzeilen noch die Gruppierung der Abfrage fest.

Diese Rollen sind nicht austauschbar. Wenn Sie etwa [region] unter dimensions: einer Kennzahl hinzufügen, erscheint region dadurch nicht im Abfrageergebnis. Die Abfrage benötigt weiterhin GROUP BY region oder columns.dimension: [region].

3. Die Granularität ergibt sich aus der Dimension #

Die Granularität beschreibt, wofür eine einzelne Zeile steht, nachdem eine Dimension in einem bestimmten Kontext angewendet wurde.

Kontext Dimension Abgeleitete Granularität
Datensatz mit Bestellpositionen [order_id, line_id] Eine Quellzeile pro Bestellposition
Monatliche Abfrage nach Produkt [product_id, dt_month] Eine Ergebniszeile pro Produkt und Monat
Auswertung nach Kunde [customer_id] Ein Zwischenwert pro Kunde
Monatliche Materialisierung nach Konto [account_id, dt_month] Eine materialisierte Zeile pro Konto und Monat

Die Dimension ist die verbindliche Angabe in der Sprache. Die Granularität beschreibt, wofür eine Zeile gemäß dieser Angabe steht. Anhand der Granularität können Sie die Bedeutung von Zeilen vergleichen, Zeilenvervielfachungen nachvollziehen und erklären, warum zwei Dimensionen nicht kompatibel sind. Verwenden Sie die gewünschte Berichtsgranularität nicht als Ersatz für die Identität der Quellzeilen.

Wenn Sie ein Dimensionsfeld hinzufügen, wird die Granularität in der Regel feiner. Wenn Sie eines entfernen, wird sie in der Regel gröber. Diese Faustregel reicht nicht aus, um Kompatibilität nachzuweisen. Auch die Herleitung der Felder, zeitliche Beziehungen, Kennzahlbeschränkungen und Datensatzgrenzen spielen eine Rolle. Lassen Sie den Compiler die deklarierte Beziehung prüfen.

4. Datensatzdimension und Identität der Quellzeilen #

Die Datensatzdimension enthält die Felder, die eine einzelne physische Quellzeile identifizieren:

Order Line:
    type: dataset
    table: tabOrderLine
    dimension: [order_id, line_id]
    columns:
        order_id:
        line_id:
        product_id:
        net_amount:

Die vollständige Wertekombination von [order_id, line_id] muss eindeutig sein. order_id kann sich über mehrere Bestellpositionen hinweg wiederholen und line_id über mehrere Bestellungen hinweg. Die vollständige Datensatzdimension bleibt dabei eindeutig.

Ersetzen Sie die physische Zeilenidentität nicht durch eine fachliche Gruppierung, deren Werte sich wiederholen können. Enthält die Quelle mehrere Buchungseinträge mit derselben Wertekombination für [account_id, invoice_id], ist diese Liste keine gültige Datensatzdimension, auch wenn Berichte häufig danach gruppieren. Verwenden Sie den physischen Schlüssel des Buchungseintrags als Datensatzdimension und [account_id, invoice_id] als Abfrage- oder Materialisierungsdimension.

pk(...) stützt sich auf die Datensatzdimension des Zieldatensatzes:

  • Die Nachschlageargumente entsprechen den Dimensionsfeldern des Zieldatensatzes.
  • Anzahl und Bedeutung der Argumente müssen zu dieser Dimension passen.
  • Ein Nachschlagevorgang darf höchstens eine Zeile im Zieldatensatz finden.

Der Compiler setzt voraus, dass diese Anforderungen erfüllt sind, und kann einen Nachschlagevorgang in einen LEFT JOIN übersetzen. Doppelte Zielschlüssel können daher Zeilen vervielfachen und Kennzahlwerte mehrfach in die Berechnung einfließen lassen. Wenn Sie dem kompilierten SQL ein DISTINCT oder GROUP BY hinzufügen, behebt das den Verstoß gegen die Modellanforderungen nicht.

5. Abfragedimension und Gruppierung der Ergebnisse #

In Model Query SQL:

SELECT dt_month, product_id, AGG(net_sales)
FROM MODEL
GROUP BY dt_month, product_id

Die Abfragedimension ist [dt_month, product_id]. Jede Ergebniszeile steht für eine Kombination aus Monats- und Produktwert.

Bei einer Abfrage im DML-Format ist diese Rolle explizit angegeben:

Monthly Product Sales:
    type: query
    columns:
        dimension: [dt_month, product_id]
        net_sales: "{net_sales}"

Eine Abfrage ohne Gruppierung hat keine Abfragedimension. Wenn ihre Kennzahlen es zulassen, liefert sie ein Ergebnis im Gesamtsummenkontext.

Wenn kompatible Kennzahlen aus unterschiedlichen Datensätzen stammen, aggregiert der Compiler jede Kennzahl separat auf die Granularität der Abfrage und führt die Ergebnisse anschließend anhand gemeinsamer Dimensionsfelder zusammen. So vermeidet er die typische Vervielfachung von Beiträgen zu Aggregaten, die entsteht, wenn Detailzeilen zuerst verknüpft werden. Gültige Datensatzdimensionen und eindeutige Nachschlagevorgänge mit pk(...) sind weiterhin erforderlich.

Ein Feld der Abfragedimension kann auch eine Kennzahl als Dimension sein. Dabei dient das Ergebnis einer Kennzahl als Feld der Abfragedimension und wird häufig mit {name: {+d: dim}} gebunden. Das Feld behält die Rolle einer Abfragedimension und legt die Identität der Quellzeilen über dimension: nicht fest. Die Regeln für die Definition finden Sie unter Kennzahl als Dimension.

6. Auswertungsdimension einer einzelnen Kennzahlreferenz #

Die Abfragedimension liefert den Ausgangskontext für eine Kennzahlreferenz. Die Formelstruktur, die zulässigen Dimensionen und die Modifikatoren bestimmen ihre effektive Auswertungsdimension.

Für die Abfragedimension [dt_month, region, brand] gilt:

Kennzahlreferenz Dimensionsoperation Resultierende Auswertungsdimension
{sales} Kein Dimensionsmodifikator Ermittelte Zieldimension
{sales: {+d: customer_id}} Dimensionsfeld customer_id hinzufügen [dt_month, region, brand, customer_id]
{sales: {-d: brand}} Dimensionsfeld brand entfernen [dt_month, region]
{sales: {dimension: [region]}} Die gesamte Dimension ersetzen [region]
{sales: {dimension: []}} Die Dimension aufheben Gesamtsummenkontext

Diese Operationen wirken sich nur auf die jeweilige Kennzahlreferenz aus. Das GROUP BY der Abfrage bleibt unverändert.

-d entfernt ein Dimensionsfeld, behält aber einen Abfragefilter auf diesem Feld bei, wenn der Compiler die Filter an den Datensatz weitergibt. -df entfernt das Feld und unterbindet für diese Referenz die Weitergabe des zugehörigen Filters. Verwenden Sie den zweiten Modifikator, wenn ein Nenner auch Werte berücksichtigen muss, die der Abfragefilter ausschließt. Syntax und Filterverhalten sind unter Kennzahlmodifikatoren beschrieben.

7. Zulässige Dimensionen für die Auswertung von Kennzahlen #

Mit dimensions: in der Kennzahldeklaration lassen sich die zulässigen Auswertungsdimensionen einschränken, wenn die fachliche Definition dies erfordert:

Revenue per Customer:
    type: measure
    formula: DIVIDE({net_sales}, {active_customers})
    dimensions:
      - [customer_id]

[customer_id] ist eine zulässige Dimension mit einer abgeschlossenen Feldliste. Sie schränkt die Auswertung ein, identifiziert aber weder Datensatzzeilen noch gruppiert sie das Abfrageergebnis.

Auslassungspunkte lassen zusätzliche Dimensionsfelder zu, während die aufgeführten Felder Pflicht bleiben:

dimensions:
  - [customer_id, ...]

Damit sind kompatible Auswertungsdimensionen zulässig, die customer_id enthalten. Fehlt dimensions: in der Kennzahldeklaration, ist jede Dimension zulässig, die mit der Kennzahl und ihren Datensatzabhängigkeiten kompatibel ist.

Benötigt eine Formel ein Pflichtfeld der Dimension, das die Abfrage nicht bereitstellt, ergänzen Sie es mit +d in der betreffenden Kennzahlreferenz und führen Sie die erforderliche äußere Aggregation durch. Fügen Sie der Abfrage keine Gruppierung hinzu, nur um eine Zwischenberechnung zu ermöglichen.

8. Materialisierungsdimension und Identität gespeicherter Ergebniszeilen #

Eine Materialisierungsdimension legt die Gruppierung und den Schlüssel der gespeicherten Ergebnisse fest:

Monthly Account Balance:
    type: materialize
    dimension: [account_id, dt_month]
    measures: [closing_balance]

dimension_columns: enthält Attribute, die funktional von diesen Schlüsseln abhängen und mit ihnen gespeichert werden. Diese Attribute sind keine zusätzlichen Felder der Materialisierungsdimension. Lässt sich ein Attribut aus der Materialisierungsdimension ableiten, belassen Sie es in dimension_columns:, ohne die Identität der gespeicherten Zeilen zu ändern.

9. Kompatibilität und Validierung #

Bei der Kompilierung werden die deklarierten Modellvorgaben geprüft:

  • Dimensionsfelder lassen sich über die relevanten Datensätze und Spaltenmakros auflösen.
  • Die Auswertungsdimensionen erfüllen die unter dimensions: deklarierten Einschränkungen der Kennzahl.
  • Die Modifikatoren können eine gültige Auswertungsdimension erzeugen.
  • Kennzahlen aus verschiedenen Datensätzen unterstützen die Abfragedimension.
  • Für Zeitmodifikatoren ist das erforderliche aktive Zeitfeld vorhanden.

Bei der Kompilierung wird keine Verbindung zu den aktuellen Daten hergestellt. Daher lässt sich dabei nicht nachweisen, dass die Datensatzdimension eindeutige Werte hat.

Führen Sie validateOnly aus, wenn kein aktueller Validierungsnachweis vorliegt oder der vorhandene veraltet ist. Für die kompilierte Abfrage führt die Option die generierten Prüfungen der Datensatzschlüssel über die ausgewählte Verbindung aus. Mit EXPLAIN prüft sie, ob die Datenbank die Hauptabfrage akzeptiert und einen Ausführungsplan dafür erstellt. Die Hauptabfrage wird dabei nicht zur Ermittlung ihrer Ergebniszeilen ausgeführt.

Der Validierungsnachweis gilt für die Modell- und Abfragevorgaben, die Verbindung und den Zustand der Quelle zum Zeitpunkt der Validierung. Eine relevante Modelländerung, eine Aktualisierung der Quelle oder eine Änderung der Schlüsselregeln oder der Verbindung macht den Nachweis ungültig.

Wenn die Validierung VALIDATION_ERROR meldet, korrigieren Sie den Schlüssel der Quelle, die Datensatzdimension, die sich überschneidenden Bereiche oder die Quelldaten. Kann eine Validierungsabfrage nicht ausgeführt werden oder liefert sie ein fehlerhaft aufgebautes Ergebnis, behandeln Sie EXECUTION_ERROR separat. Diese Meldung weist keine doppelten Schlüssel nach.

Die Validierung weist weder die fachliche Korrektheit noch die Übereinstimmung mit einem vertrauenswürdigen Bericht nach. Wenn Sie eine bestehende Abfrage migrieren, vergleichen Sie beide Ergebnisse mit denselben Filtern, demselben Zeitfenster und derselben Abfragedimension.

10. Ablauf beim Erstellen und Bearbeiten #

Der Ablauf für die Vorwärtsanalyse wendet diese Rollen auf Änderungen an Modellen und Abfragen an. Die dmlc CLI verwenden beschreibt die Kompilierung und die Validierung anhand aktueller Daten.
