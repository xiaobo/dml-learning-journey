本页定义求值上下文、粒度兼容性和组合规则。有关声明语法，请参阅模型结构、指标、查询和物化。

适用范围与定位 #

本规范涵盖的内容 #

本文规定 DML 的求值上下文、粒度兼容性和修饰符约束。下文的规则定义了语言必须遵循的行为。诊断信息的含义和建议的修复方法见错误代码。

本规范不涵盖的内容 #

  • 编译和验证查询介绍 CLI 命令及如何收集验证依据。
  • 创建分析介绍业务分析的操作步骤。
  • 核心概念介绍模型层、查询层和表达式层。

三层架构 #

层 语言 编写内容 文件
建模 DML 数据集、指标、列宏、materialize、dt/fn 宏 .dml (YAML)
查询 模型查询（SQL 或 DML 格式） AGG(measure)、GROUP BY、修饰符 .sql 或指定了 type: query 的 .dml
表达式 DMX（Dato Measure eXpression） 公式、引用、修饰符、pk() 在两层中使用

DMX 是两层共用的表达式语言。.dml 公式中的示例有 {column}、{measure: modifier} 和 pk(...)。模型查询的 SQL 中的示例有 AGG(measure) 和 AGG({measure: modifier})。

基本组成部分 #

数据集是包含已声明维度和列的表。其数据集声明粒度由声明的 dimension: 列表决定。

指标是有名称的业务度量。指标分为两类。

  • 原子指标通过 dataset: 字段绑定到一个数据集，并使用 SQL 对列进行聚合。
  • 复合指标引用其他指标，没有 dataset: 字段。

维度字段是单个有名称的 DML 字段。

维度是由一个或多个维度字段组成的列表。数据集的 dimension: 声明如何标识源行，查询维度声明如何分组，求值维度控制指标引用的求值方式，物化维度声明输出键。指标的 dimensions: 中，每个内部列表表示一个允许使用的维度。用作维度的指标是查询维度中的一种字段，其值通过对指标求值得到（参见将指标用作维度）。

修饰符形式 {dimension: []} 清除求值维度，以请求总计上下文。空列表表示一项操作，并不表示不含字段的维度。

列宏是在 .dml 中定义的派生列或跨数据集查找。借助列宏，指标公式无需使用 JOIN 即可引用其他数据集中的字段。

设计原则 #

  1. 语义必须可执行。 指标不仅用于文档记录，还会编译为可在数据仓库中执行的 SQL。
  2. 像管理代码一样管理语义。 使用 Git、PR、LSP，并通过 dml_schema.yaml 进行验证。
  3. 指标不绑定到固定的结果粒度。 指标具有从定义推导出的指标有效上下文（原生上下文），可按需加以约束。求值使用由查询和修饰符决定的实际粒度，编译器强制检查兼容性。
  4. 复杂的派生逻辑应放在模型中。 将时间对比、比率和多级聚合统一定义在 .dml 中，避免分散到 BI 计算字段或临时 SQL 中。

求值上下文模型 #

定义 #

求值上下文是编译器将指标引用解析为可执行 SQL 时所用的全部信息。

产品采用的标准简写为 Context = {grain, filters, time}。在下文的语言模型中，time 由解析后的 dim_dt 字段表示。

Context = {
    grain: [dim₁, dim₂, ...],   // active grouping dimension fields
    filters: [predicate₁, ...],  // active filter predicates
    dim_dt: TimeDim | null       // resolved time dimension
}

粒度与指标上下文的标准术语 #

作用 来源 说明
数据集声明粒度 数据集中的 dimension: 数据集中的一行代表什么
指标有效上下文（原生上下文） 源数据集、引用的指标、公式和修饰符，以及指标的可选 dimensions: 约束 指标定义适用的上下文，并非固定的输出粒度。
实际求值粒度 应用 +d、-d、dimension 及相关修饰符后的查询粒度 对特定指标引用进行求值时采用的粒度
查询结果粒度 GROUP BY 或查询中的 columns.dimension 描述输出中的一行代表什么。除了物理维度字段或映射后的维度字段外，还可以包含用作维度的指标字段（参见将指标用作维度）。

范围更广的查询上下文包括查询结果粒度、WHERE 或 filters:，以及解析后的时间信息。旧版资料中的“指标原生粒度”和“目标粒度”分别是指标有效上下文（原生上下文）和实际求值粒度的别称。新的规范性文本应使用上文列出的标准术语。

上下文转换 #

修饰符会转换求值上下文。编译器通过应用修饰符，推导出新的指标求值上下文。

apply_modifier(Context, Modifier) -> Context'
修饰符 对粒度的影响 对筛选条件的影响
+d: dim 将 dim 追加到定义粒度的字段列表末尾（下钻） 无变化
-d: dim 从定义粒度的字段中移除 dim（上卷） 无变化。针对 dim 的筛选条件仍会下推到数据集的 WHERE 子句。
-df: dim 从定义粒度的字段中移除 dim 在指标求值时移除针对 dim 及其派生列的筛选条件
dimension: [dims] 用 dims 替换定义粒度的全部字段 无变化
+f: condition 无变化 将 condition 添加到筛选条件中
-f: dim 无变化 移除引用 dim 的筛选条件
dt 宏（如 ya、pp、ytd） 无变化 替换 dim_dt 中的时间范围
fn-macro（例如 yoy、rank） 可能改变粒度（例如 grand → dimension: []） 取决于宏的公式

dim_dt — 时间维度 #

dim_dt 是表示当前查询的时间维度的系统变量。

解析优先级：查询的 dimension → 查询的 filter → null。

属性：

  • {dim_dt} — 解析为查询当前使用的时间字段（例如 dt_month、dt_quarter）
  • {dim_dt.datetype} — 表示类型的字符串：'day'、'week'、'month'、'quarter'、'year'
  • {dim_dt.periods_per_year} — 每年的周期数：按周为 52，按月为 12，按季度为 4
  • {dim_dt.datepart} — 表示 SQL 日期部分的字符串

设计目标：在度量公式中使用 dim_dt 代替具体字段 dt_date、dt_month 或 dt_quarter，使度量无需改写公式即可用于任意时间粒度。

周期转换：使用 dim_dt as quarter 后，即使查询按年份和季度分组，pp 也会按季度粒度运行：

SELECT dt_year, dt_quarter,
       AGG({sales: {dim_dt as quarter: pp}}) as last_quarter
FROM MODEL GROUP BY dt_year, dt_quarter

标准时间维度字段 #

字段 粒度 示例值
dt_date 日 2024-03-15
dt_week 周（从星期一开始） 2024-03-11
dt_month 月 2024-03-01
dt_quarter 季度 2024-01-01
dt_year 年 2024-01-01

所有时间字段均采用首日格式，即以周期的第一天作为字段值。

自动派生更粗粒度的时间字段

如果数据集显式声明了标准时间字段，它也会通过系统日历提供 dt_<grain> 系列中受支持的更粗粒度字段。例如，显式声明 dt_date 列后，dt_week、dt_month、dt_quarter 和 dt_year 都可在该数据集的作用域内作为有效的列引用。若只是要按更粗的时间粒度查询或筛选，模型作者无需在 columns: 下重复列出这些名称。生成的值遵循上述日历和首日规则。

自动派生的时间字段具有虚拟列标识，而不是第二个显式的源定义。因此，语言工具必须：

  • 在数据集作用域内进行名称解析和自动补全时，纳入受支持的派生字段；
  • 凡是允许使用相应数据集列的地方，都允许使用这些派生字段，包括查询的维度字段、筛选条件、公式和修饰符的参数；
  • 从派生字段的引用跳转到提供该字段的显式源时间列（dt_month 由 dt_date 派生时，跳转到 dt_date）；
  • 除非存在同名的显式定义，否则将虚拟字段名视为只读，不允许重命名。

如果同一个派生字段可以从多个显式时间来源导出，且无法唯一确定来源，工具必须拒绝解析，不得任意选择一个定义。

日历数据集 #

系统提供 Dim Calendar 数据集，用于跨时间粒度查找时间值：

Dim Calendar:
    type: dataset
    table: DML_CALENDAR
    dimension: [dt_date]
    columns:
        dt_date:
        dt_week:
        dt_month:
            source: pk({dt_date}).DML_CALENDAR(dt_date).dt_month
        dt_quarter:
            source: pk({dt_month}).DML_CALENDAR(dt_date).dt_quarter
        dt_year:
            source: pk({dt_quarter}).DML_CALENDAR(dt_date).dt_year

筛选上下文和筛选下推 #

筛选条件放在哪里取决于其语义作用域：

层 位置 此处填写的内容
查询的 filters: / WHERE 查询块 特定于报表的数据切片（渠道、品牌、日期范围）
度量公式 .dml 度量 当不符合条件的行可以保留在输出分组中时，用于确定哪些行参与计算的指标专属条件
数据集中的 sql: 数据集定义 当前的声明式 DML 无法表达的、对源数据范围的永久限制

源数据上的 WHERE 与不满足条件时返回 NULL 的度量条件通常不能互换。前者会让仅包含不符合条件的行的分组消失，后者则可能保留这些分组。在这些层之间移动条件之前，请验证分组是否存在、同一查询中其他指标的结果、去重、联接和窗口操作的行为，以及 NULL 的语义。

下推规则：查询中通过 filters: 指定的筛选条件会在聚合前下推到数据集的 WHERE 子句。当 -d 生成粒度更粗的临时表时，筛选条件仍会生效，因此比率的分母可能变小。使用 -df 可阻止特定维度字段的筛选条件下推。

依赖关系追踪：编译器会追踪列的派生链。对 store_id 指定 -df 后，store_name（pk({store_id}).MDM_STORE(store_id).store_name）上的筛选条件不会下推，因为该列仅由 store_id 派生。

粒度体系 #

每个求值上下文中的维度决定其粒度，以及它与其他上下文是否兼容。各维度声明在 DML 中的作用见维度的作用。

三种粒度 #

粒度类型 声明方式 含义
数据集粒度 数据集中的 dimension: 底层表中的一行表示该维度中各维度字段的一组取值
度量粒度 公式 + 修饰符 + 可选的 dimensions: 约束 度量公式适用的粒度
查询粒度 查询的 GROUP BY / columns.dimension: 查询结果中的一行表示该维度中各维度字段的一组取值

粒度兼容性规则 #

查询粒度必须与每个度量的粒度兼容。

对于没有 dimensions: 约束的原子度量：

  • 只要维度兼容，且由该度量所属数据集的维度字段组成，就可以在该维度上计算此度量。
  • 编译器根据声明的粒度和请求的上下文选择聚合方式。在声明的、能够唯一确定每一行的粒度上，编译器可以直接投影原始值。

对于具有 dimensions: [[dims]] 约束的原子度量：

  • 该度量只能在指定粒度上计算。
  • 其他公式若要使用此度量，必须显式使用 {measure: {+d: dim}} 下钻到该粒度。
  • 编译器会拒绝不兼容的粒度，并返回 cannot set dimension [...] since only [...] are allowed。

数据集或物化定义中的 dimension: 包含一个维度，而度量中的 dimensions: 包含可供选择的允许维度，每个内层列表代表一个维度。后者是一项约束，不用于声明数据集的标识或查询的分组方式。有关维度声明的规则，请参阅维度的作用。

对于复合指标，适用以下规则：

  • 粒度由解析修饰符后各引用指标用于定义粒度的维度字段的并集决定。
  • 所有引用指标的粒度必须彼此兼容。

使用 +d 进行多级聚合 #

+d 建立一个粒度更细的求值阶段。仅使用此修饰符不会将值重新聚合到查询粒度。

写法 含义
{m: {+d: x}} 在查询粒度 ∪ {x} 上求值，到此为止
SUM / AVG / MAX / …({m: {+d: x}}) 先在更细粒度上求值，再通过显式的外层聚合回到当前查询粒度
查询维度绑定 - lab: '{m: {+d: K}}' 将指标用作维度（将指标用作维度）时，结果是分组键，而不是普通的汇总指标列。

外层聚合函数（SUM、AVG、MAX 等）由编写者选择。编译器不会自行添加该函数。使用外层聚合时，编译器通常会生成 CTE（WITH ... AS (SELECT ... GROUP BY ...) SELECT ...）。

模式：原子指标 → 在提供外层聚合的复合指标内使用 +d 下钻到更细粒度 → 按任意粒度查询

# Atomic measure (dataset grain: dt_date × store_id × prod_id)
销售量:
    type: measure
    dataset: o2o_pos
    formula: SUM(count_qty)

# Distribution SKU count: how many products have sales > 0?
# {销售量: {+d: prod_id}} drills down to per-product grain,
# then DISTINCTCOUNTIF counts products with positive sales.
分销SKU数:
    type: measure
    formula: |-
        DISTINCTCOUNTIF({prod_id}, {销售量: {+d: prod_id}} > 0)

# Distribution store count: how many stores have sales > 0?
分销客户数:
    type: measure
    formula: |-
        DISTINCTCOUNTIF({store_id}, {销售量: {+d: store_id}} > 0)

# Average sales per store (selling power)
卖力:
    type: measure
    formula: |-
        divide({销售额}, {分销客户数})

-- Query at brand × quarter grain — the +d inside each measure
-- generates intermediate CTEs at prod_id / store_id grain, then rolls up.
SELECT dt_quarter, brand,
       AGG(销售额),
       AGG(分销SKU数),
       AGG(分销客户数),
       AGG(卖力)
FROM MODEL
GROUP BY dt_quarter, brand

如果 +d 出现在查询维度的绑定中，而不是出现在带有显式外层聚合的指标公式中，这属于将指标用作维度（将指标用作维度），而不是上述两步模式。

跨数据集自动联接 #

独立的指标数据集通常先分别聚合，再合并所有分组键（键的并集）。NULL 安全的相等比较会比较完整的键，因此，当其他维度也匹配时，相同位置上的 NULL 会相互匹配。指定为保留行的 LEFT JOIN 和 nullpk 关联也使用 NULL 安全的相等比较。显式 SQL 谓词保留其原有语义。有关示例，请参阅联接中的 NULL 相等比较。

生成的联接类型。 编译器可以使用 FULL OUTER JOIN，也可以用 UNION 构建去重后的键集合，再用 LEFT JOIN 联接指标。两种形式都采用 NULL 安全的键匹配。使用原生全外联接时，如果 {primary_presence_measure} is not null 等筛选条件能证明必须存在主数据源中的对应分组，编译器可以将生成的联接简化为 LEFT JOIN。如果筛选条件要求两个数据源中都存在对应分组，则可以简化为 INNER JOIN。筛选条件决定保留哪些分组。分组键的比较方式保持不变。

对于 LEFT 结果集，请使用专门用于判断主数据源中分组是否存在的指标进行筛选。该指标在每个有效的主数据源分组中都必须为非空值，在不存在的分组中则必须为 NULL。对于 INNER 结果集，要求两侧都存在对应分组。请使用未经填补的源数据计数，或其他经验证能判断分组是否存在的信号。使用可为空的业务值可能会丢弃有效分组，而填补缺失行可能会保留原本不存在的分组。

请分别验证共享键的含义、完整键的唯一性、含 NULL 的分组键如何匹配、未匹配行如何处理，以及缺失行如何填补。独立预聚合无法消除查找键重复的问题，也无法纠正错误的匹配规则。检查生成的 SQL 可以确认查询结构。在数据库中验证和比较结果需要分别检查。

粒度安全检查（编译器现有行为） #

编译器在编译时检查粒度是否安全：

  1. 违反指标的维度约束：如果指标允许的维度为 dimensions: [[customer_id]]，而引用该指标的查询维度还包含 dt_date，编译器会拒绝该查询并给出以下消息：

    cannot set dimension [dt_date, customer_id]+d: customer_id since only [[customer_id]] are allowed

    编译器现在会给出提示（Hint），说明 ... 允许额外的维度字段，但列出的字段仍为必需字段，并建议使用 +d 添加缺少的必需字段。使用 ... 可允许额外的维度字段，列出的字段仍为必需字段。

  2. 聚合指标需要 +d：SUM({measure}) 会失败，并返回“cannot aggregate a measure w/o +d modifier”。编译器会给出提示（Hint），说明缺少 +d 时，指标已在目标求值维度上求值，没有更细粒度的值可供聚合。无论如何声明 dimensions:，此规则适用于聚合函数中的任何指标引用。目标求值维度由查询的 GROUP BY 和指标的允许维度约束共同决定。+d: dim 会添加一个维度字段，并在由此得到的更细粒度上求值。外层的 SUM/AVG/… 再将结果聚合回目标维度。如果需要这两步处理，请使用 SUM({measure: {+d: dim}})，不要将单独的 {measure: {+d: dim}} 用作汇总列。

  3. 缺少时间上下文：时间修饰符要求 dim_dt 可解析，并且满足对应宏的前置条件。用于分组的时间字段或时间筛选条件都可以提供上下文。

  4. 跨数据集的粒度不兼容：如果来自不同数据集的两个指标没有足够的共享维度来满足查询粒度，编译器会报错。

  5. 将指标用作维度的规则：请参阅将指标用作维度和版本注意事项。编译器会拒绝缺少实体键的查询，但静态检查无法发现所有无效的底层转换。

编译能验证的范围： 编译成功本身无法证明生成的 SQL 有效，也无法证明计算出的数值正确。请检查分类和聚合阶段，验证实际数据中的键，并单独比较结果。

时间粒度规则 #

  • 为明确报表的汇总级别，建议只显式指定一种时间粒度。已验证的构建版本接受同时使用 dt_year, dt_month。这无法证明所有包含多个时间修饰符的组合都受支持。
  • 对于粒度较粗的时间字段，请使用各时间段的起始值。等值比较选中一个时间段，结构化的 range: [start, end] 在该粒度下包含两个端点。
  • WHERE 中谓词的顺序是编写约定，不是语法限制。
  • 请使用宏的实际前置条件和解析后的 dim_dt。即使没有可见的时间分组字段，时间筛选条件也能提供上下文。

将度量用作维度 #

用作维度的指标字段属于查询维度。它的值来自对指标或基于该指标的标量表达式的求值，而不是数据集中的物理列。该字段仍承担查询维度的角色（参见维度角色），参与确定查询结果的粒度。它不声明数据集的标识。

说明：将指标用作维度。本节说明多轮处理应遵循的约定。说明列出了已验证的写法和需要检查的分类阶段。编译器对此类查询列单独建模，将其与物理维度列和常规输出指标区分开来，同时复用常规的指标计算逻辑。

columns.dimension 中的语法

编写形式及支持范围（DML 格式的查询）：

形式 示例 含义
命名指标加显式 +d - first_purchase_month: '{first_purchase_month: {+d: store_id}}' 将 store_id 加入指标的求值维度后对指标求值，并将结果用作查询维度字段。
仅使用指标名称 - first_purchase_month 此写法不适用于从指标派生的维度。必须在引用处显式声明完整的 +d 键。
对 {m: {+d: dim}} 应用标量表达式 - payment_day: 'cast({authorization_ts: {+d: payment_id}} as date)' 对每个完整键求值一次标量表达式，并将结果用作查询维度字段。
命名标量指标加查询中的 +d 先在指标中指定 formula: 'cast({authorization_ts} as date)'，再写 - payment_day: '{dt_payment_day: {+d: payment_id}}' 标量表达式可复用时，优先采用这种等价写法
dimension: / rank 标签（无 +d） - brand_bucket: 'iif({sales: {dimension: [brand], rank}} < 5, {brand}, ''others'')' 这种查询维度公式通过 dimension: 替换求值维度，或使用 rank，不属于使用 +d 的多轮处理关联模式。

编写和验证这些绑定时，优先使用 type: query。生成的测试夹具头部显示 SQL，并不能证明相应的 Model Query 与 SQL 之间支持往返转换。

求值语义（多轮处理）

设 M 为将指标用作维度的表达式，K 为其中显式指定的 +d 字段集合，Q 为常规查询维度字段集合。求值和关联的粒度为 G = Q ∪ K，其中不包含从指标派生的标签。内部聚合阶段不会重新定义 K。

  1. 按细粒度求值。 在 G 粒度下对每个用作维度的指标求值。常规输出指标也在 G 粒度下求值，并保留后续向上汇总所需的状态或组成指标。
  2. 按完整分类键 G 关联。 分类关系必须为每个完整键提供唯一一个标量值。如果分类关系和使用它的指标不在同一关系中，必须先进行关联，再按分类值对这些指标分组。按门店和月份分类时，连接条件必须同时包含门店和月份，仅使用 +d: store_id 不够。按更粗粒度关联时，使用方必须能取得完整键，或能证明可从已有字段推导出完整键。按更细粒度关联时，必须显式下钻并向上汇总。保留 NULL 键的处理语义以及查询数据范围的语义。
  3. 汇总到查询结果粒度。 将常规指标聚合到 { measure-as-dimension fields } ∪ Q 粒度。移除 K 中未同时出现在 Q 中的字段。如果某个常规指标无法安全地改写为先在 G 粒度下求值，再执行此汇总，则编译失败。

其执行原理与通过 +d 进行多级聚合相同（参见多级聚合）。在这一用法中，下钻后得到的指标结果成为查询维度字段，而不只是复合公式的中间输入。

source
  → evaluate measure-as-dimension + other measures at finer evaluation dimension (+d)
  → attach on the complete classification key
  → roll up to query result grain (GROUP BY measure-as-dimension field[, ordinary query-dimension fields])

+d 的兼容性

分类及参与分类的同级下钻引用都应使用显式实体键。兼容性取决于解析后的求值维度和作用范围，而不只取决于 +d 参数的写法。

共享 +d。 每个用作维度的指标都需要显式指定完整键。只有各键的字段集合相同时，才允许使用多个独立标签。键内字段的声明顺序不影响判断。

未指定键的引用。 不要根据同级指标推断实体粒度。请通过 +d 或 dimension: 显式指定实体键。只绑定指标而不指定键会被拒绝。对于已验证的客户数分类器，两种写法都能通过编译。这一结果无法证明所有分类形式都受支持。增加或删除输出指标不得改变各实体的分类归属。

不同的键。 键不相等的独立标签会被拒绝。标签不得依赖同一查询中的其他标签。若要在不同实体粒度之间建立通用映射，必须单独建模一个关系。

约束

  1. 分类需要显式实体键（优先使用 +d，也能识别 dimension:）。多标签兼容性和安全汇总是规范要求，并不意味着发布版本对所有情况都提供保证。请验证实际使用的查询。

  2. 时间段修饰符的组合尚未得到普遍验证。test_82d 测试了使用 mat 的滚动年度分类器，但这不能证明 yoy 或 pop 的正确性。仅使用明确指定了分类和报表各自的时间范围、且有证据支持其结果的组合。

  3. 标量转换可以内联编写，也可以命名定义。每个完整分类键必须得到一个确定的值。

  4. 度量指标的 dimensions: 允许列表和粒度安全规则（粒度安全性）适用于将指标用作维度的表达式中的每个指标引用，并按该引用实际求值的粒度应用。

  5. 跨数据集自动联接（跨数据集组合）仍会将每个数据集的指标聚合到共同的查询粒度。用作维度的指标字段在附加并向上汇总后，成为该查询粒度的一部分。

  6. 按显示的最终分类值分组。每个完整的查询键必须恰好对应一行，包括含有 NULL 的键。使用分类器并不意味着可以对不可加指标求和或凭空生成非活跃实体。比率各组成部分的语义保持不变。是否对实体级的值显式应用外层聚合，由编写者决定。

  7. 源数据筛选条件按现有修饰符规则应用。-d 会更改粒度，同时保留筛选条件。-f 和 -df 提供现有的范围控制。标签谓词应在分类之后应用，报表聚合值的阈值应在聚合之后应用。两者都不得改变各自对应的分类输入。基于截至截止点的历史数据、滚动窗口或当前选择范围的分类器，采用的是不同的业务定义。

示例

下文的 first_purchase_month 特指求值范围内首个月度净销售额为正的月份。purchase_span 显式在实体粒度上对两个端点求值，再对较细粒度的结果进行最终聚合。

first_purchase_month:
    type: measure
    formula: 'MINIF({dt_month}, {sales: {+d: dt_month}} > 0)'

report:
    type: query
    allows: ALL
    columns:
        dimension:
            - first_purchase_month: '{first_purchase_month: {+d: store_id}}'
        sales:
        purchase_span: 'SUM(datediff(day, {first_buy: {+d: store_id}}, {last_buy: {+d: store_id}}))'
  • 查询结果的粒度为 [first_purchase_month]。
  • 对用作维度的指标和 purchase_span 都应用 {+d: store_id}，以便在更细的粒度上求值。
  • 最终的 GROUP BY 按 first_purchase_month 分组，并移除 store_id。

修饰符的架构约束 #

根据 dmx_variable_schema.yaml，修饰符对象有以下结构约束：

  • dim_dt 的变体包括 dim_dt、dim_dt as date、dim_dt as month 等。每个修饰符对象最多只能包含其中一个。
  • +d 和 dimension 互斥，每个修饰符对象最多只能包含其中一个。
  • -d 和 dimension 互斥，每个修饰符对象最多只能包含其中一个。
  • +d 和 -d / -df 只有在维度名称集合互不相交时才可共存（按一个字段细化粒度，同时移除另一个字段）。两个集合包含同名维度时，该组合无效。请参阅修饰符组合。
  • 遵循上述集合相交规则时，同一个修饰符对象可以包含多个修饰符。组合示例请参阅组合修饰符。

修饰符组合 #

保留修饰符的书写顺序。多个宏可能生成中间指标。应用于多路径函数的时间宏则可能传播到每个分支。请参阅修饰符叠加语义及其中的发布验证用例。

每个修饰符只写一个 YAML 键。请写成 {+f: {a: 1, b: 2}}，不要重复写 +f 键。-df 同时移除维度和筛选条件。

同一维度上的修饰符冲突

语言规范要求，在同一个修饰符对象中，如果 +d 的字段集合与 -d 或 -df 的字段集合相交，编译时必须报错。当前构建在已检查的用例中没有执行这项要求。不要通过代数抵消将表达式化简为不带修饰符的 {m}，也不要将 {+d: x, -df: x} 静默改写为 {-f: x}。如果输出粒度已包含 x，则 -df 和 -f 的行为不同。

无效 原因
{销量: {+d: 门店, -d: 门店}} 同时添加和移除同一字段，无法得出唯一的隐式解释。抵消为 {销量} 会掩盖拼写错误，且语义有别于 AVG({销量: {+d: 门店}})（每家门店权重相同）。
{销量: {+d: 门店, -df: 门店}} 不得改写为 {-f: 门店}。更改粒度与仅更改筛选条件的语义不同。

为明确表达意图，编写者必须采用以下写法之一：{销量} / SUM({销量: {+d: 门店}}) / {销量: {-d:…\|-df:…\|-f:…}}。
不同维度仍可共存，例如 SUM({销量: {+d: 门店, -d: 品牌}})。

当前受检构建会接受已检查的同一字段维度冲突，并在客户粒度上重复区域总计，然后对这些值求和。这是已知的实现缺陷，属于不受支持的写法。请显式写出一个求值阶段，并检查对应的 SQL。
