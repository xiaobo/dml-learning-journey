For report developers, application developers, and data operations staff who know SQL.

This exercise uses two Mazes, monthly and quarterly sales. Install the runtime with the generated setup_sql. Run prepare_sql, and run the business query once it returns data_ready=1. While waiting, use prepare_status_sql to watch this request and DML_MAZ_PROGRESS for global progress.

A quarterly report from the tutorial's sales data #

In chapter 12 of the interactive journey, the FACT_SALES dataset reads TABLE_SALES, identifies one sale by id, records the month in dt_month, and computes sales as SUM({amount}). Keep using that model and its 8 source rows: January totals 70, February totals 100.

This extension adds two materialized results and one quarterly report.

TABLE_SALES (sales details) → SALES_MONTHLY (monthly sales) → SALES_QUARTERLY (quarterly sales) → quarterly_sales (report)

Query preparation first checks which months the upstream needs, then builds the downstream quarter. Each partition that needs rebuilding commits separately.

Prepare the first quarter #

  1. Run the interactive journey's setup script in an empty SQL Server practice database. If you already ran that exercise, keep using the same database.
  2. Run the calendar extension below. The tutorial's practice calendar has only date and month and ends in February 2025; this step adds quarters and fills the calendar through the end of June.
  3. Add dialect: mssql at the top of the tutorial's model.dml, then append the materialization and report definitions below.

For reference, see interactive journey chapter 12 and download the original model.dml and SQL Server setup script.

Show the SQL Server calendar extension 
ALTER TABLE dbo.DML_CALENDAR ADD dt_quarter date NULL;
GO
UPDATE dbo.DML_CALENDAR
SET dt_quarter = DATEFROMPARTS(YEAR(dt_date), 3 * (DATEPART(quarter, dt_date) - 1) + 1, 1);
ALTER TABLE dbo.DML_CALENDAR ALTER COLUMN dt_quarter date NOT NULL;

;WITH dates AS (
    SELECT CAST('20250301' AS date) AS dt_date
    UNION ALL
    SELECT DATEADD(day, 1, dt_date) FROM dates WHERE dt_date < '20250630'
)
INSERT dbo.DML_CALENDAR (dt_date, dt_month, dt_quarter)
SELECT dt_date, DATEFROMPARTS(YEAR(dt_date), MONTH(dt_date), 1),
       DATEFROMPARTS(YEAR(dt_date), 3 * (DATEPART(quarter, dt_date) - 1) + 1, 1)
FROM dates
OPTION (MAXRECURSION 0);
Show the materialization and report definitions 
SALES_MONTHLY:
  type: materialize
  parameters: {dt_month: range}
  dimension: [dt_month]
  measures: [sales]

SALES_QUARTERLY:
  type: materialize
  allows: [SALES_MONTHLY]
  parameters: {dt_quarter: range}
  dimension: [dt_quarter]
  measures: [sales]

quarterly_sales:
  type: query
  allows: [SALES_QUARTERLY]
  filters:
    dt_quarter:
      range: ['2025-01-01', '2025-01-01']
  columns:
    dimension: [dt_quarter]
    sales:

Compile the extended model and install the materializations and dependencies with the generated setup_sql. Then run quarterly_sales's prepare_sql on an autocommit connection; it completes preparation and the actual readiness check, returns data_ready=1, and you then run the same request's business sql. While waiting, another connection can observe status with prepare_status_sql. On error or wait timeout, do not query yet; remove the cause and retry ordinary preparation. The SQL Server session needs IMPLICIT_TRANSACTIONS OFF and @@TRANCOUNT = 0. The business query remains a SELECT or CTE.

The first quarter returns 170. Months 1, 2, and 3 all have monthly partition state; March's partition was empty at that point. The example uses uppercase materialization names to avoid a current limitation in SQL Server registration with mixed-case nested names.

How new months and historical corrections are handled #

Run the three data changes below in order in the practice database. Run refresh after the source transaction commits. The two inserts reuse regions and customers from the tutorial.

Source change Operation Report result
Insert March sales of 30 into TABLE_SALES; Q1 already published refresh SALES_MONTHLY for March; the default refreshes that month and the materialized Q1 Q1 170 → 200
Insert April sales of 40; Q2 and its monthly partitions not yet built Change both filter bounds of quarterly_sales to 2025-04-01. Run the new prepare_sql, then run sql for Q2 after it returns normally Q2 returns 40 for the first time
Correct February id = 2 sales from 20 to 25 refresh SALES_MONTHLY for February; the default refreshes that month and affected Q1 Q1 200 → 205, Q2 stays 40

The replay uses historical 2025 partitions. After the March backfill and the February correction, ordinary preparation alone still reuses old results. The first time you query Q2, ordinary preparation can read April's new data from the source, because Q2 and its upstream partitions are built for the first time. If upstream caches already exist — including months once built as empty — notify the affected months after committing to avoid missed refreshes.

Show the SQL for the three writes and notifications 
-- 1. March backfill. After the source write commits, register the
--    refresh demand and attempt to call the runner.
INSERT dbo.TABLE_SALES (id, region, customer, dt_month, status, amount)
VALUES (9, N'North', N'A', '20250301', N'completed', 30);

EXEC dbo.DML_REFRESH_MAZ
    @_materialize = N'SALES_MONTHLY',
    @_range_start = '20250301',
    @_range_end   = '20250331';

-- 2. April arrives for the first time. After the write commits,
--    prepare Q2 for the first time.
INSERT dbo.TABLE_SALES (id, region, customer, dt_month, status, amount)
VALUES (10, N'South', N'C', '20250401', N'completed', 40);

-- 3. Back to Q1. After the February correction commits, refresh
--    the month and the quarter.
UPDATE dbo.TABLE_SALES SET amount = 25 WHERE id = 2;

EXEC dbo.DML_REFRESH_MAZ
    @_materialize = N'SALES_MONTHLY',
    @_range_start = '20250201',
    @_range_end   = '20250228';

After each step, verify the result with the report range listed in the table before moving on. If your load script opens an explicit transaction, commit it first, then call refresh on an autocommit connection.

The default refresh first invalidates and registers the selected month plus affected quarters as a unit, then calls the runner; it may return "accepted" while busy. Run the query's prepare_sql before reading the report; it waits and checks this query's readiness. To defer rebuilding until a query needs it, add @_invalidate_only=1 explicitly; it submits marks and returns, starts no runner, and keeps existing pending work.

To audit the whole report, use DML_PREPARE_MAZ on SALES_QUARTERLY with the Q1 range and @_force_update = 1, forcing a rebuild of this request's required months and quarter. When you only know a month's source changed, call refresh from SALES_MONTHLY; refreshing the quarter alone will not discover unreported stale monthly caches.

@_match defaults to exact; like with SALES~_% matches the literal prefix SALES_ and with % matches every registered Maz. Dates include both bounds; refresh with both dates omitted handles existing ranges and does not prebuild the whole calendar. Moving across months must cover the old and the new month.

Continuing after an interruption #

Each partition commits independently. When a later partition fails, completed partitions are kept and the current one rolls back. Ordinary prepare can fill in known targets and ranges; re-running prepare with force_update=1 is a new forced refresh.

After a default refresh is interrupted, the registered remainder stays in STATE. Once the error is resolved, call parameterless DML_REFRESH_MAZ, or wake the runner through a later prepare or refresh. Sending a default refresh or force_update=1 again re-declares demand and may redo completed partitions. Parameterless refresh continues pending work only and does not re-invalidate completed partitions. After a cancellation or timeout, close the physical connection before continuing; ROLLBACK alone does not release the session-level runner lock. If a commit response was lost, re-check state first.

Common problems #

Symptom Checks and handling
Source corrected but the report still shows old values Check the source transaction committed, invalidation covered every entry point and date, and the report then ran prepare_sql. If you notified downstream only, check whether its upstream also needed invalidation.
Procedure, target, or @_match parameter not found Confirm you are connected to the target database and that deployment ran the model's generated setup_sql. Exact names use registered Maz names. LIKE with no matches succeeds but changes nothing; confirm the matched set first.
Asked for autocommit Use a JDBC connection with autoCommit=true and no explicit or implicit transaction. Send invalidation calls only after the source-write transaction commits.
Invalidation reports missing, reversed, or uncovered dates Pass both dates in order and confirm dbo.DML_CALENDAR covers every day in the interval. When you explicitly want every materialized range, omit both dates.
Writer permission denied Ask a database administrator to check the calling account's execute permission on the invalidation procedure and each affected Maz's writer. All affected targets are validated before invalidation; unauthorized requests are rejected.
Lock timeout or disconnection during a call After a client cancellation or timeout, close the physical connection where it happened; with a pool, discard it to release the session-level runner lock. Once the error is resolved, use parameterless DML_REFRESH_MAZ to continue registered work. If query preparation failed, re-run the whole prepare_sql and query only after data_ready=1.

With read permission on the state table, check partitions with:

SELECT materialize, dim_dt, state, COALESCE(last_end_time, created_end_time) AS build_finished_at
FROM dbo.DML_MATERIALIZE_STATE
WHERE materialize IN (N'SALES_QUARTERLY', N'SALES_MONTHLY')
ORDER BY materialize, dim_dt;

state = 0 means ordinary invalidation, state = 3 means invalid and pending active refresh, and state = 1 means a complete result has been published. The build time records when the Maz's writer finished. To judge whether a given correction is included, also check the invalidation notification and the preparation that followed.

Verify the exercise's final result with this source query: Q1 is 205, Q2 is 40.

WITH source_rows AS (
    SELECT DATEFROMPARTS(YEAR(dt_month), 3 * (DATEPART(quarter, dt_month) - 1) + 1, 1) AS dt_quarter,
           amount
    FROM dbo.TABLE_SALES
    WHERE dt_month >= '20250101' AND dt_month < '20250701'
)
SELECT dt_quarter, SUM(amount) AS sales
FROM source_rows
GROUP BY dt_quarter
ORDER BY dt_quarter;

Watch global runner progress #

Install the shared progress view with the generated setup_sql, then query:

SELECT pending_partitions, runner_running, estimated_seconds
FROM dbo.DML_MAZ_PROGRESS;

The view's statistics cover the last 60 seconds per query and report current pending work, distinct-partition completion and addition rates, and estimated seconds to drain. A partition completed several times within the window counts once. With no pending work the estimate is 0; it is NULL when the runner stopped with work remaining or cannot drain net-positive demand. Monitoring accounts need SELECT on the view.

This is global progress, not proof that this report is ready. Before reading the report, use that query's prepare_sql to wait for and confirm readiness. Full column descriptions, runtime object ownership, and recovery steps are in the prepare and refresh conventions.
