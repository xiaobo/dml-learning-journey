在建模数据集、编写指标、编译查询或排查行数成倍增加的问题时，可参考本指南了解维度的行为。本指南解释语言模型，规范仍以DML 求值语义为准。

1. 对象模型 #

维度字段是一个具名的 DML 字段。

维度是包含一个或多个维度字段的列表。

示例：

[order_id]
[order_id, line_id]
[product_id, dt_month]

上面的每一行都是一个维度。[商品编号, dt_month] 是一个包含两个字段的维度。

指标的 dimensions: 多嵌套一层列表，因为它可以包含多个可供选择的允许维度：

dimensions:
  - [客户编号]
  - [account_id, dt_month]

外层列表包含两个允许的维度。每个内层列表都是一个维度。

总计没有维度。在指标修饰符语法中，{dimension: []} 清除求值维度，以请求总计上下文。空列表表示一项操作，而不是包含零个字段的维度。

2. 维度的五种作用 #

列表结构相同，但它在 DML 中的位置决定其行为：

在 DML 中的位置 作用 行为
数据集中的 dimension: 数据集维度 声明一组维度字段，其完整值组合标识一条源数据行。
公式与维度修饰符 求值维度 决定单个指标引用按哪个维度求值。
查询中的 GROUP BY 或 columns.dimension 查询维度 对返回的行进行分组，并决定每个结果行代表什么。
物化中的 dimension: 物化维度 定义物化关系的分组方式和键。
指标中的 dimensions: 允许的维度 限定指标可按哪些维度求值。它不声明如何标识源数据行，也不声明查询如何分组。

这些作用不能互换。例如，将 [地区] 添加到指标的 dimensions: 中，并不会把 地区 添加到查询结果中。查询仍然需要 GROUP BY 地区 或 columns.dimension: [地区]。

3. 粒度由维度决定 #

粒度描述在特定上下文中应用维度后，每一行代表什么。

上下文 维度 派生粒度
订单明细数据集 [订单号, 行号] 每条订单明细对应一条源数据行
按产品分组的月度查询 [商品编号, dt_month] 每个产品与月份的组合对应一条结果行
按客户求值 [客户编号] 每位客户对应一个中间值
按账户分组的月度物化 [account_id, dt_month] 每个账户与月份的组合对应一条物化行

维度是语言层面的约定，粒度描述按该约定得出的行含义。可以借助粒度比较各行所代表的内容、分析行数为何成倍增加，或解释两个维度为何不兼容。不要用报表所需的粒度代替源数据行的标识。

添加维度字段通常会使粒度更细，移除维度字段通常会使粒度更粗。仅凭这一规律不足以证明兼容性，还需要考虑字段的派生方式、时间关系、指标约束和数据集边界。由编译器验证声明的关系。

4. 数据集维度与源数据行标识 #

数据集维度包含用于标识单条物理源数据行的字段：

订单明细:
    type: dataset
    table: tabOrderLine
    dimension: [订单号, 行号]
    columns:
        订单号:
            abbr: order_id
        行号:
            abbr: line_id
        商品编号:
            abbr: product_id
        净额:
            abbr: net_amount

唯一性要求适用于 [订单号, 行号] 的完整值组合。订单号 可以在不同订单明细中重复，行号 可以在不同订单中重复，而完整的数据集维度仍保持唯一。

不要用值可能重复的业务分组代替物理行标识。如果源数据中同一个 [account_id, invoice_id] 值组合对应多条账目记录，即使报表经常按该组合分组，这个列表也不是有效的数据集维度。应使用账目记录的物理键作为数据集维度，并使用 [account_id, invoice_id] 作为查询维度或物化维度。

pk(...) 依赖目标数据集的维度：

  • 查找参数与目标数据集的维度字段对应。
  • 参数的数量和含义必须与该维度匹配。
  • 一次查找最多只能匹配一条目标行。

编译器信赖这一约定，并且可能将查找转换为 LEFT JOIN。因此，目标键重复可能导致行数成倍增加，指标值也可能被重复计入。在编译生成的 SQL 中添加 DISTINCT 或 GROUP BY，无法修复模型对这一约定的违反。

5. 查询维度与结果分组 #

在 Model Query SQL 中：

SELECT dt_month, 商品编号, AGG(净销售额)
FROM MODEL
GROUP BY dt_month, 商品编号

查询维度为 [dt_month, 商品编号]。每个结果行代表一个月份值与产品值的组合。

在 DML 格式的查询中，同样的作用由显式声明指定：

商品月销售:
    type: query
    columns:
        dimension: [dt_month, 商品编号]
        净销售额: "{净销售额}"

没有分组的查询没有查询维度。如果指标允许，查询将在总计上下文中返回结果。

如果兼容的指标来自不同的数据集，编译器会先分别将每个指标聚合到查询粒度，再通过共有的维度字段合并结果。这样可以避免先连接明细行时常见的聚合重复计入问题。数据集维度仍须有效，pk(...) 查找仍须保证匹配的唯一性。

查询维度字段也可以使用充当维度的指标，即把指标结果用作查询维度字段，通常通过 {name: {+d: dim}} 绑定。它仍然承担查询维度的作用，不用于通过数据集的 dimension: 标识源数据行。编写规则请参阅充当维度的指标。

6. 单个指标引用的求值维度 #

查询维度为指标引用提供初始上下文。公式结构、允许的维度和修饰符决定其实际求值维度。

给定查询维度 [dt_month, 地区, 品牌]：

指标引用 维度操作 操作后的求值维度
{销售额} 无维度修饰符 解析得到的目标维度
{销售额: {+d: 客户编号}} 添加维度字段 客户编号 [dt_month, 地区, 品牌, 客户编号]
{销售额: {-d: 品牌}} 移除维度字段 品牌 [dt_month, 地区]
{销售额: {dimension: [地区]}} 替换整个维度 [地区]
{销售额: {dimension: []}} 清除维度 总计上下文

这些操作只影响该指标引用，不会改变查询的 GROUP BY。

-d 移除一个维度字段，但在编译器将筛选条件下推到数据集时，保留该字段上的查询筛选条件。-df 移除该字段，并阻止其相关筛选条件针对该引用传播。如果分母必须包含查询筛选条件排除的值，请使用后者。有关语法和筛选行为，请参阅指标修饰符。

7. 指标求值的允许维度 #

当业务定义有此要求时，可通过指标的 dimensions: 限制有效的求值维度：

每客户收入:
    type: measure
    formula: DIVIDE({净销售额}, {活跃客户数})
    dimensions:
      - [客户编号]

[客户编号] 是一个封闭的允许维度，仅包含列出的字段。它约束求值，既不标识数据集中的行，也不对查询输出分组。

省略号允许加入其他维度字段，同时仍要求包含列出的字段：

dimensions:
  - [客户编号, ...]

这样可接受包含 客户编号 的兼容求值维度。如果省略指标的 dimensions:，则允许使用与该指标及其依赖的数据集兼容的任何维度。

如果公式需要某个必需的维度字段，而查询未提供该字段，请使用 +d 将它添加到相应的指标引用中，并执行所需的外层聚合。不要仅为满足中间计算的需要而在查询中添加分组。

8. 物化维度与存储结果的标识 #

物化维度声明存储结果的分组方式和键：

月度账户余额:
    type: materialize
    dimension: [account_id, dt_month]
    measures: [closing_balance]

dimension_columns: 中的属性在函数上依赖于这些键，并与这些键一同存储。这些属性不是物化维度中的附加字段。如果可以从物化维度推导出某个属性，请将该属性保留在 dimension_columns: 中，避免改变存储行的标识。

9. 兼容性与验证 #

编译时会检查模型声明的约定：

  • 可通过相关数据集和列宏解析维度字段。
  • 求值维度满足指标的 dimensions: 约束。
  • 修饰符能够生成有效的求值维度。
  • 来自不同数据集的指标均支持查询维度。
  • 时间修饰符所需的当前启用的时间字段已存在。

编译不会连接实时数据，因此无法证明数据集维度的值具有唯一性。

如果缺少当前验证依据，或现有依据已过时，请运行 validateOnly。对于已编译的查询，该选项会通过所选连接运行生成的数据集键检查，并通过 EXPLAIN 检查数据库是否接受主查询并为其生成执行计划。它不会执行主查询来获取结果行。

验证依据涵盖验证时观察到的模型与查询约定、连接以及数据源状态。相关的模型变更、数据源刷新、键规则变更或连接变更都会使该依据失效。

如果验证报告 VALIDATION_ERROR，请修正数据源的键、数据集维度、重叠的范围或源数据。如果验证查询无法执行或返回了格式不正确的结果，请单独处理 EXECUTION_ERROR。此错误不能证明存在重复键。

验证既不能证明业务逻辑正确，也不能证明结果与可信报表一致。迁移现有查询时，请使用相同的筛选条件、时间窗口和查询维度比较两边的结果。
