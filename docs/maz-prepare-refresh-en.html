prepare readies the data a query needs; refresh handles source data changes. Run setup_sql at deployment time; the query's preparation unit checks readiness before querying, and DML_MAZ_PROGRESS shows global progress during operations.

Pick the entry point by task #

Task Operation How to confirm completion
Open a report, switch periods Run the query's ordinary prepare_sql After prepare_sql returns data_ready=1 normally, run the business sql
Audit a report, force recomputation prepare(force_update=1) The target and its required upstream are rebuilt forcibly; query after prepare returns normally
Update dependent results after a load refresh(invalidate_only=0, default) Requirements for the target and affected downstream are registered; use query prepare to wait for readiness when reading
Load now, recompute later refresh(invalidate_only=1) Invalidation marks are submitted; no runner call, no new active demand, no cancellation of pending work
Month-end warm-up Run the ordinary prepare for chosen queries in advance That query's prepare_sql returns normally
Resume registered work after an interruption Run DML_REFRESH_MAZ with no parameters Check global pending work and this query's readiness

prepare works upward through dependencies and accepts exact names only. refresh works downward from a change entry point and supports exact names and SQL LIKE. If a source change was not reported, old data may be reused; valid does not mean absolutely freshest against the source.

Delta refresh selects work by partition; it is not row-level CDC on the source. A full refresh means a forced rebuild of the range you named this time, not all history. Each partition commits its business data and success status together; a later partition's failure does not roll back committed partitions.

Prepare this query's data before reading #

Shared prepare and targeted refresh first submit a refresh demand, then call the shared procedure DML_RUN_MAZ synchronously. The invalidate-only branch returns immediately after submitting. The caller that obtains execution processes the global backlog; if a runner already exists, the call returns directly without waiting. An ordinary prepare may also keep running because of another call's global work.

At most one runner per database performs actual builds. The runner owns dependency order, writer invocation, and per-partition commits. The default implementation needs no Service Broker, SQL Server Agent, or background application service; it does not promise to keep working in the background after the call returns or the connection drops.

For the same request and its parameters, run this sequence:

  1. Run setup_sql at deployment time to install the shared runtime and each Maz's writer.
  2. At query time run the generated prepare_sql. It completes ordinary preparation, the actual readiness check, and any retries, returning one row with data_ready=1.
  3. After a normal return, run the business sql. Stop on preparation error or wait timeout, remove the cause, and retry.

The preparation unit retries ordinary preparation every 100 milliseconds and raises an error when the five-second retry deadline passes without readiness. The deadline does not interrupt an already-running synchronous writer or a target lock wait; client timeouts and connection cancellation are the integration's responsibility. Retries never escalate into a forced refresh.

While waiting, another connection can run the same request's prepare_status_sql to observe only this query's partitions, dates, and parameter bindings. It adds no demand and requires no hand-written polling from ordinary callers. The result column is data_ready. The readiness check and the following SELECT do not share a snapshot.

Calling the low-level shared prepare directly may still return 2, meaning registered but runner busy; 1 means this round completed. refresh results include accepted, runner_busy, and affected partitions. An accepted refresh or an empty global backlog does not replace the query's actual readiness check; the query's generated preparation unit performs that check.

prepare parameters #

Parameter Rule
@_materialize Required, exact Maz name; patterns are not supported
@_range_start / @_range_end Date-partitioned Mazes require both closed bounds; queries may derive them; every intersecting complete partition is included
@_force_update Default 0; 1 forcibly rebuilds this target and its required upstream; null is not accepted
@_parameters / @_user Typed parameter binding and audit purposes

A forced refresh first invalidates the required work and affected downstream; active demand is limited to this request's required-upstream closure, so other reports are not warmed as a side effect. A query's shared dependencies are reused by partition and parameter binding. Ordinary preparation reuses valid results for date partitions and whole tables when the parameter binding matches. Missing, invalid, expired, or re-bound results are rebuilt; to force recomputation, use force_update=1 explicitly. Source changes must still be reported reliably.

EXEC dbo.DML_PREPARE_MAZ
    @_materialize=N'SALES_QUARTERLY',
    @_range_start='20250101', @_range_end='20250331', @_force_update=1;

refresh parameters and matching #

Parameter Rule
@_materialize Exact name or pattern; mutually exclusive with @_source; if both are omitted, only existing pending work continues
@_source Exact schema.table of a registered local physical source table; same-database database.schema.table is also accepted; like is not supported
@_match Default exact; like matches per the collation of the registered column
@_range_start / @_range_end Give both or neither; omitting means the existing ranges, not the whole calendar
@_invalidate_only Default 0, registers active demand and calls the runner; 1 submits only invalidation marks, does not call the runner, and keeps existing pending work; null is not accepted
@_parameters / @_user Typed parameters and audit; parameters required by batch targets are validated before invalidation
Match Example
Single target exact + SALES_MONTHLY
Prefix like + SALES%
Literal underscore prefix like + SALES~_%
Every registered Maz in the current database like + %

SQL LIKE uses %, _, and bracket patterns; ~ is the escape character; * is not a wildcard. exact expands no wildcards. An unknown exact name raises an error; a pattern with zero matches returns zero targets. Exact names allow at most 128 UTF-16 code units and patterns at most 512; truncated names must not be executed.

-- After the source write commits, register February and its materialized
-- affected downstream, and call the runner.
EXEC dbo.DML_REFRESH_MAZ
    @_materialize=N'SALES_MONTHLY',
    @_range_start='20250201', @_range_end='20250228';

-- Invalidate every materialized range only; backfill later as queries need it.
EXEC dbo.DML_REFRESH_MAZ
    @_materialize=N'%', @_match=N'like', @_invalidate_only=1;

invalidate_only=1 does not run writers in this call. Runners already running on other connections may continue processing existing pending work.

Choose the change range from a Maz or a source table #

When you know the source table, you can select every direct entry point registered for it:

EXEC dbo.DML_REFRESH_MAZ
    @_source=N'dbo.TABLE_SALES',
    @_range_start='20250201', @_range_end='20250228';

A source identity mark proves date-and-partition equality and then the range is applied as given; without proof, existing downstream ranges are covered conservatively and cold date partitions are not guessed. Unknown or cross-database sources, missing schema, giving both source and materialize, and source combined with like all raise errors. Source selection does not auto-detect source changes.

When selecting by Maz, a source table with several independent direct entry points must report every entry point. Refreshing the quarter alone will not discover an unreported stale monthly summary; when you do not know at which layer the cache is stale, use the query's forced prepare.

Date bounds are closed intervals, expanded into intersecting complete partitions before downstream impact is computed; moving across periods covers both the old and new periods. For dimension tables and unclear impact, choose a range large enough. When exact reverse mapping cannot be proven, the system widens existing downstream ranges conservatively. One-sided dates, reversed dates, and incomplete calendar coverage are rejected, never silently clipped.

A dated default refresh may build an explicitly selected Maz for the first time; discovered cold downstream is propagated but not auto-prebuilt. An intermediate Maz without state does not block propagation to existing downstream. Undated refresh handles existing ranges only; a database-wide first warm-up needs explicit finite dates. A whole-table Maz is treated as one physical partition; passing dates widens it to the whole table.

Date partitions do not accept non-date value parameters; a whole table has a single current parameter binding.

Watch global runner progress #

After running the current build's generated setup_sql, query the shared view:

SELECT pending_partitions, runner_running, estimated_seconds
FROM dbo.DML_MAZ_PROGRESS;

This is progress for every Maz in the same database, unrelated to a specific query, and not added to query compilation results. The ordinary view reads current STATE on each query, keeps fixed statistics for the last 60 seconds, and stores no sampled history. A monitoring account needs SELECT on the view; deployment does not grant it automatically.

All statistics columns and their definitions

The full column set is available via SELECT * FROM dbo.DML_MAZ_PROGRESS;.

Column Meaning
pending_partitions Physical partitions currently pending, including those building but not yet published
runner_running Whether a runner currently holds the singleton execution right
completed_partitions / added_partitions Distinct physical partitions completed / newly registered within the last 60 seconds
completed_partitions_per_second / added_partitions_per_second Window counts divided by 60 seconds
net_partitions_per_second Completion rate minus addition rate
estimated_seconds Estimated seconds to drain at the current net rate
average_build_seconds Mean of each partition's latest successful build duration within the window
sample_start / sampled_at Start and sampling time of this statistics window

Physical partitions are deduplicated by Maz, partition type, and date; a whole table with several parameter bindings counts as one partition. A partition completed several times in the window still counts once, and a completion followed by another invalidation also counts in the window's completed count. Rates therefore measure partition coverage, not actual writer executions.

With no pending work the estimate is 0. It is NULL when additions meet or exceed completions, or when the runner has stopped while work remains. Partitions with different costs and the moving window both affect the estimate.

The progress view cannot decide whether a particular query is ready. It reads committed state, publication transactions can cause brief waits, and it provides no cross-partition snapshot. For other windows, the standalone Java helper MazRunner.progressSql("mssql", 300) can generate read-only SQL for the last five minutes; executing that SQL directly needs STATE read permission.

Interruption and retry #

Initial invalidation and demand registration commit or roll back in one metadata transaction; builds then commit partition by partition. STATE durably keeps partitions pending active refresh and their actual parameters. On interruption, committed partitions are kept, the current partition rolls back, and unfinished demand waits for the next call.

Situation Action
Runner build failure or dropped connection Remove the cause, then run ordinary prepare or parameterless DML_REFRESH_MAZ to continue the global backlog
Continue only the registered remainder Run the parameterless refresh below; do not re-declare a refresh range
Sending force_update=1 or a default refresh again Treated as a new refresh demand; completed partitions may be invalidated and rebuilt
Ordinary result invalid or new demand not yet registered Run the relevant query's ordinary prepare, then check readiness
Commit response lost The outcome is unknown; re-check state instead of assuming the commit did not happen 
-- Continue the current database's registered backlog without
-- re-invalidating completed partitions.
EXEC dbo.DML_REFRESH_MAZ;

Client cancellation or timeout can bypass SQL Server's CATCH and leave a session-level runner lock on the live connection. After a cancellation, close that physical connection and have the pool discard it; ROLLBACK alone is not enough. After disconnection, another call can advance the durable backlog. An ordinary SQL user can, after confirming the runner has stopped, roll back the open transaction on the original connection and then explicitly release the DML_MAZ_RUNNER session lock.

Parameterless refresh() continues pending work only; it does not mean a full-history rebuild, and it accepts no dates, like, invalidate-only, or parameter binding options. Selecting all Mazes still requires explicit % with like. Ordinary invalid state=0 takes no action by itself, state=3 means invalid and pending active refresh, state=1 means a complete published result; state=2 exists only inside the publication transaction. A window remains between source commit and notification; loaders must report reliably and retry.

Execution conditions and result boundaries #

Use an autocommit connection: IMPLICIT_TRANSACTIONS OFF and no active transaction. The entry point checks permissions on this request's targets and affected writers. The runner processes the global backlog as the caller, so the executing account also needs the writer permissions of everything pending; on insufficient permissions it returns the original error and keeps the demand.

Operations reference: runtime objects and permissions
Object Scope
Each Maz's result table and writer (PROC_M__...) Single Maz
prepare_sql, prepare_status_sql, business sql Current query and this request's parameters
DML_MATERIALIZE_DEFINITION, DML_MATERIALIZE_DEPENDENCY, DML_MATERIALIZE_STATE Shared runtime tables, records per Maz and partition
DML_PREPARE_MAZ, DML_REFRESH_MAZ, DML_RUN_MAZ Shared runtime procedures
DML_MAZ_IS_READY Shared readiness function
DML_MAZ_PROGRESS Shared global progress view

The calendar and its maintenance routines are installed by system setup. Before redeploying, stop new requests and confirm the runner has exited, then run the generated setup.
