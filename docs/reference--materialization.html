Materialize definition (type: materialize) #

<name>:
    type: materialize
    parameters:                         # stored-procedure parameters
        <param>: <column_name>
    filters:                            # materialize-level filters
        <column>: <value>

    allows: [<materialize_name>]        # allowed materialize tables

    dataset: <dataset_name>      # optional, for direct dataset materialize
    dimension: [col1, col2]      # materialization grain — grain keys only
    dimension_columns:           # functionally dependent attribute columns
        <col>: <formula>          # (1:1 with grain keys, not grain themselves)

    measures: [<measure1>, <measure2>]  # measures to materialize

dimension: vs dimension_columns: — dimension: contains the materialization dimension: its dimension fields are the grain keys that uniquely identify a row (the compiler's GROUP BY keys). dimension_columns: lists attribute columns derivable from those grain keys — e.g. store_name depends on store_id, region_code depends on store_id. The compiler carries dimension_columns: through the GROUP BY without treating them as grain. Placing a derivable attribute in dimension: causes a compile error ("can be derived from [...], should it be moved to dimension_columns instead?").

No-formula inheritance — a dimension_columns: entry without a formula: inherits the column from the source dataset. The column must exist in the source dataset's columns: (else "not found from relate dataset(s)"). When the materialize grain is coarser than the source dataset's dimension, the compiler checks derivability: a column that varies at the finer source grain fails with "definition from dataset [...] cannot be derived from dimension [...], please advise". When the materialize grain matches the source dataset's dimension, any source column is accepted (1:1 row mapping).

Formula scope — when a dimension_columns: entry has a formula:, the formula may only reference pk() chain lookups and the materialization dimension's own fields — not source dataset columns or measures (errors "not defined, did you mean …?").

Constraints — one of:

  • dimension + measures (measure-list form), or
  • dataset + dimension + dimension_columns (dataset-scoped form), or
  • dataset only (inherits grain from dataset).

Materialization examples contains declaration patterns. There is no measure-level materialize: true flag — the compiler rejects it (undefined modifier 'materialize', see Troubleshooting index P64). Declaration forms: this section, and dataset-level materialize: <name> in model structure.

Eligibility, selection and measured performance #

allows: controls eligible materializations. A declaration alone does not establish which stored aggregate a query selects. Inspect generated SQL or the execution plan for the actual object on the target engine.

Compare optimized and unoptimized results at complete keys, including unmatched groups, NULLs and ratios. After changing source data, check refresh and the new results. Measure representative workloads only after these checks; shorter SQL or faster compilation does not establish database query performance. Refresh permissions and scheduling belong to the deployment.

For setup, hit verification, refresh and result checks, follow the materialization workflow (中文).

SQL Server runtime #

The SQL Server runtime uses shared DML_PREPARE_MAZ and DML_REFRESH_MAZ procedures to register demands, then synchronously invokes the singleton DML_RUN_MAZ. A busy runner lets the registering call return before its data is ready.

setup_sql installs the runtime and Maz writers. The generated prepare_sql performs preparation and readiness checks, retrying ordinary preparation until ready or its cooperative five-second retry deadline. It returns data_ready=1 on success; the caller then runs the business sql. Errors stop the query. prepare_status_sql remains available for observation while waiting. The status query observes the Query's selected partitions and parameter bindings. It does not enqueue work or guarantee a snapshot across preparation and SELECT.

The shared view dbo.DML_MAZ_PROGRESS reports global pending partitions, completion and arrival rates, and estimated seconds to clear the backlog. It uses a rolling 60-second window and counts a physical partition once even if it completes repeatedly. Global progress does not establish readiness for a specific Query.

SELECT pending_partitions, runner_running, estimated_seconds
FROM dbo.DML_MAZ_PROGRESS;

See the prepare, refresh and recovery contract (中文) for exact and LIKE matching, force_update, invalidate_only, connection requirements, and interrupted-call recovery.

Ordinary preparation reuses valid whole-table and dated results with the same parameter binding. invalidate_only=1 commits invalidation without invoking the runner. A parameterless DML_REFRESH_MAZ resumes registered pending work. The mutually exclusive @_source selector accepts a registered local schema.table and includes every direct Maz consumer; unproven date mappings conservatively cover existing ranges.
