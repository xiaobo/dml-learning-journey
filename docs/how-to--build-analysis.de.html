Mit diesem Ablauf fügen Sie wiederverwendbare Berechnungen und eine Abfrage hinzu, die diese Berechnungen verwendet. Folgen Sie für die erste Kompilierung der Anleitung Ihre erste Modellabfrage kompilieren. Die Syntax finden Sie unter Modellabfrage.

Phase 1: Das benötigte Ergebnis festlegen #

Halten Sie die Berichtsanforderungen fest, bevor Sie SQL schreiben.

  1. Entscheiden Sie, ob das Ergebnis Quellzeilen oder nach Gruppen berechnete Werte benötigt.
  2. Listen Sie die Felder auf, die eine Ergebniszeile identifizieren.
  3. Geben Sie den Zeitraum, den Vergleichszeitraum und die Berichtsfilter an.
  4. Trennen Sie Berichtsfilter von den Bedingungen, die eine fachliche Berechnung definieren.
  5. Halten Sie die Grundgesamtheit der Quelldaten, den Umgang mit NULL und die erforderlichen Ausgabespalten fest.
  6. Listen Sie die Annahmen auf, die das Fazit ändern könnten.

Prüfen Sie die fachlichen Annahmen vor der Modellierung und nach der Ausführung. Berücksichtigen Sie dabei die Grundgesamtheit der Quelldaten, den Berichtszeitraum, fehlende Werte und den Nenner.

Phase 2: Die Abfrage entwerfen, die die Berechnungen verwendet #

Schreiben Sie die vorgesehenen Klauseln SELECT, WHERE und GROUP BY, bevor Sie Berechnungen hinzufügen. Verwenden Sie nach Möglichkeit bestehende fachliche Bezeichnungen.

SELECT
	dt_month,
	渠道,
	AGG(销售额),
	AGG({销售额: yoy}) AS 销售额_yoy,
	AGG(同店销售额)
FROM MODEL
WHERE dt_month = '2025-03-01'
GROUP BY dt_month, 渠道

Lassen Sie die Berichtsgruppierung, Zeitfenster und die Auswahl von Kanälen in der Abfrage. Hinterlegen Sie wiederverwendbare Definitionen im Modell, etwa die Kriterien für die Einbeziehung in den Vergleich derselben Filialen. Fügen Sie eine Sortierung oder eine Zeilenbegrenzung hinzu, wenn das gewünschte Ergebnis davon abhängt. Die Reihenfolge der Prädikate hat keinen Einfluss darauf, ob die Grammatik die Abfrage zulässt.

Verwenden Sie für jede Referenz auf eine Berechnung mit Modifikator einen eigenen Alias. Prüfen Sie die Spalten der erzeugten Ausgabe. Der Compiler kann ihre Reihenfolge ändern oder bei einer Abfragestruktur mit bekanntem Fehler ein angefordertes Zeitfeld weglassen.

Phase 3: Fehlende Berechnungsdefinitionen ermitteln #

Prüfen Sie für jedes AGG(...) im Entwurf das Zielmodell.

  1. Verwenden Sie eine vorhandene Berechnung wieder, wenn ihre Definition der benötigten Kennzahl entspricht.
  2. Wenn eine ähnliche Berechnung fachlich etwas anderes bedeutet, machen Sie den Unterschied in ihrem Namen und ihrer Beschreibung deutlich.
  3. Fügen Sie eine Berechnung hinzu, wenn der Abfrageentwurf eine wiederverwendbare fachliche Definition benötigt.
  4. Lassen Sie eine Auswahl, die nur für den Bericht gilt, in der Abfrage, sofern sie nicht die Kennzahl selbst definiert.

Verfolgen Sie die Abhängigkeiten bis zu den Basisberechnungen zurück. Bei einer Kennzahl für den Vergleich derselben Filialen können dazu ein Betrag je Kunde und Monat, eine Berechnung der Teilnahmeberechtigung je Kunde und Monat und eine äußere Aggregation gehören.

Phase 4: Das Modell erweitern #

Definieren Sie Abhängigkeiten vor den Elementen, die sie verwenden, wenn diese Reihenfolge das Lesen erleichtert. In den geprüften Fällen werden Vorwärtsreferenzen innerhalb derselben Datei unterstützt.

  1. Deklarieren Sie für jeden Datensatz alle Felder, die eine Quellzeile eindeutig identifizieren.
  2. Definieren Sie Basisberechnungen anhand der Spalten des Datensatzes.
  3. Ergänzen Sie in der Berechnungsdefinition dimensions:, wenn die fachliche Berechnung eine bestimmte Auswertungsdimension erfordert.
  4. Fügen Sie +d an der Referenz hinzu, die eine feinere Auswertungsdimension benötigt.
  5. Fassen Sie Zwischenwerte mit einer expliziten äußeren Aggregation zusammen.
  6. Definieren Sie zusammengesetzte Verhältniskennzahlen aus den benötigten Komponenten.
  7. Ergänzen Sie Beschreibungen, die die Grundgesamtheit, die Ebene, auf der Zeilen oder Summen definiert sind, und den Umgang mit NULL angeben.

Testen Sie Berechnungen mit eingeschränkten Auswertungsdimensionen anhand von Abfragen, die die erforderlichen Felder enthalten. Ein Filter auf dt_month allein erfüllt die Vorgabe der geschlossenen Auswertungsdimension [customer, dt_month] nicht.

Beispiele für Modellierungsmuster finden Sie unter Berechnungen. Folgen Sie für Beschreibungen und Namen der Anleitung Modellmetadaten schreiben.

Phase 5: Modell und Abfrage validieren #

Wenn das Verhalten unklar ist, ist die ausgewählte dmlc.exe maßgeblich. Halten Sie ihren Pfad, ihre Version, ihren Build-Zeitstempel und ihren Dialekt fest.

  1. Führen Sie den Linter für das geänderte Modell aus.
  2. Kompilieren Sie für jede neue Berechnung eine minimale Abfrage im strikten Modus.
  3. Kompilieren Sie die vollständige Abfrage, die die Berechnungen verwendet, im strikten Modus.
  4. Prüfen Sie Diagnosemeldungen, Hinweise, SQL, Gruppierungen, Joins, Filter, Aliasse und die Ausgabereihenfolge.
  5. Wenn eine geeignete Verbindung verfügbar ist, führen Sie vor der Ausführung, auf deren Ergebnisse Sie sich stützen, eine reine Validierung (validate-only) durch.
  6. Führen Sie die Abfrage für einen repräsentativen Ausschnitt aus und gleichen Sie die Ergebnisse mit den Berichtsanforderungen ab.
  7. Wenn eine unabhängige SQL-Abfrage oder ein unabhängiges Berichtsergebnis vorliegt, vergleichen Sie anhand desselben Quelldatenstands die Anzahl der Vorkommen jeder Zeile, die Schlüssel, die NULL-Werte und alle berechneten Werte.
dmlc --lint model.dml --json
dmlc --compile --strict query.sql --model=model.dml --json --artifacts=gen
dmlc --validate query.sql --model=model.dml --connection=default --json

Führen Sie den abschließenden Befehl nur aus, wenn default die vorgesehene konfigurierte Verbindung ist. Die Anleitung Die dmlc CLI verwenden erläutert, wie Sie Ausgaben erfassen und mit Validierungsfehlern umgehen.

Prüfen Sie jede fachliche Regel anhand der tatsächlichen Formel. Ein Zählwert für dieselben Filialen kann eine vergleichbare Gesamtzahl nicht überschreiten, wenn beide dieselbe Grundgesamtheit verwenden. Der Betrag einer Teilmenge kann den Gesamtbetrag überschreiten, wenn ausgeschlossene Zeilen negative Werte enthalten. Fehlende Vorjahresdaten können zu NULL, null oder einem anderen festgelegten Ersatzwert führen. Gehen Sie nicht davon aus, dass jede Kennzahl im Vorjahresvergleich null zurückgibt.

Wenn im strikten Modus eine Warnung bestehen bleibt, halten Sie den Befund und das zugehörige SQL fest. Eine ausgegebene Abfrage gilt nicht als bestandene Kompilierung im strikten Modus. Wenn Prüfungen mit einer aktiven Verbindung nicht möglich sind, dokumentieren Sie den Status not run und die fehlende Voraussetzung.

Führen Sie zu jeder zentralen Aussage der Analyse Abfragen aus, die diese Aussage widerlegen könnten. Bewahren Sie die Ergebnisse als Nachweise zusammen mit dem Bericht auf.

Phase 6: Die finalen Arbeitsergebnisse prüfen #

Wenn die relevanten Prüfungen aus Phase 5 bestanden sind, folgen Sie der Anleitung Technische Prüfung in Phase 6. Stellen Sie das Modell, die Abfrage, die die Berechnungen verwendet, die ursprünglichen Berichtsanforderungen, die Identifikationsdaten des Compilers und die Validierungsnachweise bereit.

Wiederholen Sie nach Korrekturen die betroffenen Prüfungen. Machen Sie Änderungen an fachlichen Definitionen sichtbar und kehren Sie zu Phase 4 zurück, wenn eine vorgeschlagene Optimierung die Kennzahl ändert.

Modell und Abfrage übergeben #

Speichern Sie das wiederverwendbare Modell, das SQL der Abfrage, die die Berechnungen verwendet, und die Validierungsnachweise zusammen. Dokumentieren Sie offene Befunde und nicht ausgeführte Prüfungen.
