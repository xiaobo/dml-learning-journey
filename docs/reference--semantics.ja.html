適用範囲と位置づけ #

この仕様で扱う内容 #

この文書では、DML の評価コンテキスト、粒度の互換性、修飾子の制約を規定します。以下の規則は、言語の仕様を定めるものです。診断メッセージの意味と推奨される修正方法については、エラーコードを参照してください。

この仕様で扱わない内容 #

  • クエリをコンパイルして検証するでは、CLI コマンドと検証結果を裏付ける情報の収集方法を説明します。
  • 分析を作成するでは、業務データを分析する手順を説明します。
  • 基本概念では、モデル層、クエリ層、式の層を説明します。

3 層アーキテクチャ #

レイヤー 言語 記述する内容 ファイル
モデリング DML データセット、指標、列マクロ、materialize、dt/fn マクロ .dml (YAML)
クエリの作成 モデルクエリ（SQL または DML 形式） AGG(measure)、GROUP BY、修飾子 .sql、または type: query を指定した .dml
式 DMX（Dato Measure eXpression） 数式、参照、修飾子、pk() 両方の層で使用

DMX は両方の層で使う式言語です。.dml の数式では {column}、{measure: modifier}、pk(...) などを使います。モデルクエリの SQL では AGG(measure)、AGG({measure: modifier}) などを使います。

基本要素 #

データセットは、宣言されたディメンションと列を持つテーブルです。データセットの宣言粒度は、宣言された dimension: のリストで決まります。

指標は、名前の付いた業務指標です。指標には 2 種類あります。

  • アトミック指標は、dataset: フィールドでデータセットに紐づけられ、SQL で列を集計します。
  • 複合指標は、ほかの指標を参照します。dataset: フィールドはありません。

ディメンションフィールドは、名前の付いた 1 つの DML フィールドです。

ディメンションは、1 つ以上のディメンションフィールドを含むリストです。データセットの dimension: はソース行を何で識別するかを宣言します。クエリディメンションはグループ化を宣言し、評価ディメンションは指標参照の評価を制御し、マテリアライズのディメンションは出力キーを宣言します。指標の dimensions: では、内側のリスト 1 つが許可されるディメンション 1 つに対応します。ディメンションとしての指標は、指標の評価によって値が決まるクエリディメンションのフィールドです（ディメンションとしての指標を参照）。

修飾子 {dimension: []} は、評価ディメンションをクリアして、総計のコンテキストを要求します。空のリストは操作を表し、フィールド数がゼロのディメンションを表すものではありません。

列マクロは、.dml で定義する派生列、またはデータセットをまたいで値を取得するための定義です。JOIN を使わずに、ほかのデータセットのフィールドを指標の数式で参照できます。

設計原則 #

  1. セマンティクスは実行可能でなければなりません。 指標はドキュメントに記載するだけのものではなく、データウェアハウス向けの SQL にコンパイルされます。
  2. セマンティクスをコードと同じように管理します。 Git、PR、LSP を活用し、dml_schema.yaml で検証します。
  3. 指標は固定の結果粒度に縛られません。 指標には、定義から導かれ、必要に応じて制約を課せる有効コンテキスト（ネイティブコンテキスト）があります。評価には、クエリと修飾子によって決まる実効粒度を使います。コンパイラが互換性を強制します。
  4. 複雑な計算はモデルで定義します。 期間比較、比率、多段階の集計は .dml にまとめ、BI の計算フィールドやアドホックな SQL に分散させません。

評価コンテキストのモデル #

定義 #

評価コンテキストとは、コンパイラが指標参照を解決して実行可能な SQL に変換するために使う情報のすべてです。

製品では、標準の略記として Context = {grain, filters, time} を使います。以下の言語モデルでは、time の役割を、解決済みの dim_dt フィールドが担います。

Context = {
    grain: [dim₁, dim₂, ...],   // active grouping dimension fields
    filters: [predicate₁, ...],  // active filter predicates
    dim_dt: TimeDim | null       // resolved time dimension
}

粒度と指標コンテキストの標準用語 #

役割 決定要因 説明
データセットの宣言粒度 データセットの dimension: データセットの 1 行が何を表すか
指標の有効コンテキスト（ネイティブコンテキスト） ソースデータセット、参照先の指標、数式と修飾子、および指標のオプションの dimensions: 制約 指標の定義が有効なコンテキストです。出力粒度を固定するものではありません。
実効評価粒度 +d、-d、dimension および関連する修飾子を適用した後のクエリの粒度 特定の指標参照を評価する粒度
クエリ結果の粒度 GROUP BY またはクエリの columns.dimension 出力の 1 行が何を表すかを示します。物理ディメンションフィールドやマッピングされたディメンションフィールドに加え、指標をディメンションとして使うフィールドも含めることができます（ディメンションとしての指標を参照）。

より広い概念であるクエリコンテキストには、クエリ結果の粒度に加えて、WHERE または filters: と、解決済みの時間情報が含まれます。以前の資料にある「指標のネイティブ粒度」と「対象粒度」は、それぞれ指標の有効コンテキスト（ネイティブコンテキスト）と実効評価粒度の別名です。新たに仕様を記述する際は、上記の標準用語を使用してください。

コンテキストの切り替え #

修飾子は評価コンテキストを変換します。コンパイラは修飾子を適用して、指標を評価するための新しいコンテキストを導出します。

apply_modifier(Context, Modifier) -> Context'
修飾子 粒度への影響 フィルターへの影響
+d: dim 粒度を定義するフィールドのリストの末尾に dim を追加する（ドリルダウン） 変更なし
-d: dim 粒度を定義する項目から dim を削除する（ロールアップ） 変更なし。dim に対するフィルターは引き続きデータセットの WHERE 句にプッシュダウンされます。
-df: dim 粒度を定義する項目から dim を削除する dim とその派生列に対するフィルターを指標の評価から除外する
dimension: [dims] 粒度を定義する項目をすべて dims で置き換える 変更なし
+f: condition 変更なし フィルターに condition を追加する
-f: dim 変更なし dim を参照するフィルターを削除する
dt マクロ（例 ya、pp、ytd） 変更なし dim_dtの時間範囲を置き換える
fn-macro（例: yoy、rank） 粒度が変わる場合がある（例: grand → dimension: []） マクロの式によって異なる

dim_dt — 時間ディメンション #

dim_dtは、現在のクエリの時間ディメンションを表すシステム変数です。

解決の優先順位: クエリのdimension → クエリのfilter → null。

プロパティ:

  • {dim_dt} — クエリの現在の時間フィールド（例: dt_month、dt_quarter）に解決される
  • {dim_dt.datetype} — 型を表す文字列: 'day'、'week'、'month'、'quarter'、'year'
  • {dim_dt.periods_per_year} — 1 年あたりの期間数: 週は52、月は12、四半期は4
  • {dim_dt.datepart} — SQLの日付部分を表す文字列

設計上の目的: メジャーの式では、具体的な時間フィールド（dt_date、dt_month、dt_quarter）の代わりにdim_dtを使います。これにより、式を書き換えずに任意の時間粒度でメジャーを評価できます。

期間の変換: dim_dt as quarterを使うと、クエリが年と四半期でグループ化されていても、ppは四半期単位で処理します。次の例を参照してください。

SELECT dt_year, dt_quarter,
       AGG({売上高: {dim_dt as quarter: pp}}) as 前四半期売上高
FROM MODEL GROUP BY dt_year, dt_quarter

標準の時間ディメンションフィールド #

フィールド 粒度 値の例
dt_date 日 2024-03-15
dt_week 週（月曜始まり） 2024-03-11
dt_month 月 2024-03-01
dt_quarter 四半期 2024-01-01
dt_year 年 2024-01-01

すべての時間フィールドは初日形式を使用し、期間の初日を値とします。

より粗い時間粒度の自動導出

標準の時間フィールドを明示的に宣言したデータセットでは、システムカレンダーを介して、dt_<grain>系列のうちサポートされる、より粗い粒度のフィールドも参照できます。たとえば、dt_date列を明示的に宣言すると、dt_week、dt_month、dt_quarter、dt_yearをデータセット内の列として参照できます。より粗い時間粒度でクエリやフィルタリングを行うだけなら、モデルの作成者がこれらの名前をcolumns:に再度記述する必要はありません。生成される値は、上記のカレンダーと初日の規則に従います。

自動導出された時間フィールドは仮想列として識別されるものであり、別の明示的なソース定義ではありません。そのため、言語ツールには次の対応が必要です。

  • データセット内の名前解決と補完の対象に、サポートされる派生フィールドを含める。
  • 対応するデータセットの列を使用できる場所ではすべて、派生フィールドも使用できるようにする。これには、クエリのディメンションフィールド、フィルター、式、修飾子に渡す値が含まれます。
  • 派生フィールドの参照から、その導出元である明示的な時間列に移動できるようにする（dt_dateから導出されたdt_monthの参照からはdt_dateに移動する）。
  • 同じ名前の明示的な定義が存在しない限り、仮想フィールド名を読み取り専用として扱い、名前を変更できないようにする。

同じ派生フィールドを複数の明示的な時間ソースから導出でき、ソースを一意に特定できない場合、ツールは任意の定義を選ばず、解決を失敗させる必要があります。

カレンダーデータセット #

システムは、異なる時間粒度の間で時間値を参照するために、次のデータセットを提供します。カレンダー

カレンダー:
    type: dataset
    table: DML_CALENDAR
    dimension: [dt_date]
    columns:
        dt_date:
            abbr: dt_date
        dt_week:
            abbr: dt_week
        dt_month:
            source: pk({dt_date}).DML_CALENDAR(dt_date).dt_month
        dt_quarter:
            source: pk({dt_month}).DML_CALENDAR(dt_date).dt_quarter
        dt_year:
            source: pk({dt_quarter}).DML_CALENDAR(dt_date).dt_year

フィルターのコンテキストとプッシュダウン #

フィルターを配置する場所は、適用対象によって決まります。

レイヤー 配置場所 ここで指定する内容
クエリのfilters: / WHERE クエリブロック レポートごとの絞り込み（チャネル、ブランド、日付範囲）
メジャーの式 .dmlのメジャー 対象外の行が結果グループに残ってもよい場合に、どの行を計算対象とするかを指標ごとに定める条件
データセットの sql: データセット定義 現在の宣言型DMLでは表現できない、ソースデータの対象範囲に対する恒久的な制限

ソース側のWHEREと、条件に合わない場合にNULLを返すメジャー内の条件は、一般には置き換えられません。前者では対象外の行だけで構成されるグループが消えますが、後者では残る場合があります。これらのレイヤー間で条件を移す前に、グループの有無、同じクエリ内の他の指標、重複除去・結合・ウィンドウ処理の挙動、およびNULLのセマンティクスを検証してください。

プッシュダウンの規則: クエリのfilters:で指定したフィルターは、集計前にデータセットのWHERE句にプッシュダウンされます。-dがより粗い粒度の一時テーブルを生成する場合も、フィルターは適用されるため、比率の分母が小さくなることがあります。特定のディメンションフィールドについてフィルターのプッシュダウンを無効にするには、-dfを使います。

依存関係の追跡: コンパイラは列の導出元をたどります。店舗名（pk({店舗番号}).MDM_STORE(店舗番号).店舗名）のフィルターは、店舗番号に-dfを指定するとプッシュダウンされません。この列が店舗番号だけから導出されるためです。

粒度の仕組み #

各評価コンテキストのディメンションによって、その粒度と他のコンテキストとの互換性が決まります。DMLでの各ディメンション宣言の役割については、ディメンションの役割を参照してください。

粒度の 3 つの種類 #

粒度の種類 宣言方法 意味
データセットの粒度 データセットの dimension: 基になるテーブルの 1 行は、このディメンションを構成するフィールドの値の組み合わせ 1 つを表す
メジャーの粒度 式 + 修飾子 + 省略可能なdimensions:制約 メジャーの式が有効な粒度
クエリの粒度 クエリのGROUP BY / columns.dimension: クエリ結果の 1 行は、このディメンションを構成するフィールドの値の組み合わせ 1 つを表す

粒度の互換性ルール #

クエリの粒度は、すべてのメジャーの粒度と互換性がなければなりません。

dimensions:制約のないアトミックメジャーの場合:

  • そのメジャーが属するデータセットのディメンションフィールドを組み合わせた互換性のあるディメンションであれば、どのディメンションでもメジャーを評価できます。
  • コンパイラは、宣言された粒度と要求されたコンテキストに基づいて集計方法を選びます。各行を一意に特定できると宣言された粒度では、元の値をそのまま射影する場合があります。

dimensions: [[dims]]制約のあるアトミックメジャーの場合:

  • メジャーは、指定された粒度でのみ評価できます。
  • このメジャーを使う他の式では、{measure: {+d: dim}}を明示的に指定して、その粒度にドリルダウンする必要があります。
  • コンパイラは互換性のない粒度を受け付けず、エラーメッセージ cannot set dimension [...] since only [...] are allowed を出します。

データセットまたはマテリアライズのdimension:にはディメンションが 1 つ入ります。メジャーのdimensions:には、許可されるディメンションを選択肢として指定し、内側のリスト 1 つがディメンション 1 つに対応します。後者は制約であり、データセットの識別やクエリのグループ化を宣言するものではありません。各ディメンション宣言の規則については、ディメンションの役割を参照してください。

複合指標には、次のルールが適用されます。

  • 粒度は、修飾子の解決後に参照先の各指標の粒度を定義するディメンションの和集合で決まります。
  • 参照先のすべての指標の粒度に互換性が必要です。

+d による多段階集計 #

+d は より細かい粒度での評価段階を設けます。この修飾子だけでは、値はクエリの粒度に再集計されません。

書き方 意味
{m: {+d: x}} クエリの粒度 ∪ {x} で評価し、そこで終了する
SUM / AVG / MAX / …({m: {+d: x}}) 細かい粒度で値を求め、明示的な外側の集計で現在のクエリの粒度に戻す
クエリディメンションのバインディング - lab: '{m: {+d: K}}' 指標をディメンションとして使用する場合（指標をディメンションとして使う）、結果はグループ化キーになり、通常の集計済み指標列にはなりません。

外側の集計関数（SUM、AVG、MAX など）は作成者が選びます。コンパイラが自動で選ぶことはありません。外側の集計がある場合、コンパイラは通常、CTE（WITH ... AS (SELECT ... GROUP BY ...) SELECT ...）を生成します。

パターン：アトミック指標 → 外側の集計を指定する複合指標の中で +d により細かい粒度に掘り下げる → 任意の粒度でクエリを実行する

# Atomic measure (dataset grain: dt_date × store_id × prod_id)
販売数量:
    type: measure
    dataset: o2o_pos
    formula: SUM(count_qty)

# Distribution SKU count: how many products have sales > 0?
# {销售量: {+d: prod_id}} drills down to per-product grain,
# then DISTINCTCOUNTIF counts products with positive sales.
取扱商品数:
    type: measure
    formula: |-
        DISTINCTCOUNTIF({商品番号}, {販売数量: {+d: 商品番号}} > 0)

# Distribution store count: how many stores have sales > 0?
取扱店舗数:
    type: measure
    formula: |-
        DISTINCTCOUNTIF({店舗番号}, {販売数量: {+d: 店舗番号}} > 0)

# Average sales per store (selling power)
取扱店舗当たり売上高:
    type: measure
    formula: |-
        divide({売上高}, {取扱店舗数})

-- Query at ブランド × quarter grain — the +d inside each measure
-- generates intermediate CTEs at 商品番号 / 店舗番号 grain, then rolls up.
SELECT dt_quarter, ブランド,
       AGG(売上高),
       AGG(取扱商品数),
       AGG(取扱店舗数),
       AGG(取扱店舗当たり売上高)
FROM MODEL
GROUP BY dt_quarter, ブランド

+d が、明示的な外側の集計を含む指標の式の中ではなく、クエリディメンションのバインディングに指定されている場合は、指標をディメンションとして使用する方法（指標をディメンションとして使う）に該当し、上記の 2 段階のパターンには該当しません。

データセット間の自動結合 #

独立した指標データセットは通常、個別に集計してから、すべてのグループ化キーの和集合を取ります（キーの和集合）。NULL セーフな等価比較はキー全体を比較します。そのため、他のディメンションも一致する場合、同じ位置に NULL があるキー同士が対応します。行を保持するよう指定された LEFT JOIN および nullpk による結合でも、NULL セーフな等価比較を使用します。明示的な SQL 述語は、記述どおりの意味を保ちます。例については、結合時の NULL の等価比較を参照してください。

生成される結合の種類。コンパイラは FULL OUTER JOIN を使用するか、UNION で重複のないキー集合を作り、LEFT JOIN で指標を結合できます。どちらの形式でも、キーの照合は NULL セーフです。完全外部結合をネイティブに使用できる場合、{primary_presence_measure} is not null などのフィルターによって主ソースの存在が必須と分かれば、コンパイラは生成する結合を LEFT JOIN に簡略化できます。両方のソースを必須とするフィルターでは、INNER JOIN に簡略化できます。どのグループが残るかはフィルターで決まります。グループ化キーの比較方法は同じです。

LEFT の結果集合を得るには、主ソースの有効なグループすべてで非 null になり、存在しないグループでは NULL になる専用の存在確認用指標で絞り込みます。INNER の結果集合では、両側でグループが存在することを条件にします。補完していないソースの件数か、グループの存在を確実に判定できる別の値を使います。null になり得る業務データの値を使うと、有効なグループが除外される可能性があります。欠落行を補完すると、存在しないグループが結果に残る可能性があります。

共有キーの意味、キー全体の一意性、NULL を含むグループ化キーの照合、対応する行がない場合の処理、欠落行の補完を個別に検証してください。独立した事前集計では、参照先のキーの重複や照合ルールの誤りは解消されません。SQL を確認すれば、生成されたクエリの構造が分かります。データベースでの検証と結果の比較は別途行う必要があります。

粒度の安全性チェック（既存のコンパイラの動作） #

コンパイラはコンパイル時に粒度の安全性をチェックします。

  1. 指標のディメンション制約違反：許可されているディメンションが dimensions: [[顧客番号]] の指標を、dt_date も含むクエリディメンションで参照すると、コンパイラは次のメッセージを出して拒否します。

    cannot set dimension [dt_date, customer_id]+d: customer_id since only [[customer_id]] are allowed

    コンパイラは、... で追加のディメンションフィールドを許可できる一方、列挙したフィールドは引き続き必須であることを示すヒント（Hint）を出すようになりました。また、不足している必須フィールドを +d で追加するよう案内します。追加のディメンションフィールドを許可するには ... を使います。列挙したフィールドは引き続き必須です。

  2. 指標の集計には +d が必要：SUM({measure}) は「cannot aggregate a measure w/o +d modifier」というエラーになります。コンパイラは、+d がなければ指標はすでに評価先のディメンションで評価されており、集計の対象となる、より細かい粒度の値がないことをヒント（Hint）で説明します。これは、dimensions: の宣言にかかわらず、集計関数で囲まれたすべての指標参照に適用されます。評価先のディメンションは、クエリの GROUP BY と指標に許可されたディメンションの制約で決まります。+d: dim はディメンションフィールドを追加し、その結果得られる細かい粒度で指標を評価します。外側の SUM/AVG/… で、評価先のディメンションに再集計します。この 2 段階の処理が必要な場合は、SUM({measure: {+d: dim}}) を使用してください。{measure: {+d: dim}} を単独で集計済みの列として使用しないでください。

  3. 時間コンテキストの不足：時間修飾子を使うには、dim_dt を解決でき、対応するマクロの前提条件を満たしている必要があります。グループ化に使用する時間フィールドや時間フィルターで、コンテキストを指定できます。

  4. データセット間で粒度に互換性がない：異なるデータセットに属する 2 つの指標に、クエリの粒度を満たすだけの共通ディメンションがない場合、コンパイラはエラーを報告します。

  5. 指標をディメンションとして使う場合のルール：指標をディメンションとして使うと、リリース時の注意事項を参照してください。エンティティキーが欠けている場合は拒否されますが、静的チェックですべての不正な変換を検出できるわけではありません。

コンパイルで確認できる範囲：コンパイルに成功しただけでは、生成された SQL が有効であることも、数値が正しいことも確認できません。分類と集計の各段階を確認し、実データのキーを検証し、結果は別途比較してください。

時間粒度のルール #

  • レポートの集計単位を明確にするため、時間粒度はできるだけ 1 つに絞り、明示してください。確認済みのビルドでは dt_year, dt_month を併用できます。この確認で、複数の時間修飾子のあらゆる組み合わせが使えると分かったわけではありません。
  • 粒度の粗い時間フィールドには、各期間の開始時点を値として使用します。等価比較では 1 つの期間が選択され、構造化された range: [start, end] では、その粒度で両端が含まれます。
  • WHERE 内の述語の順序は記述上の慣例であり、文法上の制約ではありません。
  • マクロの実際の前提条件と、解決済みの dim_dt を使用します。時間によるグループ化フィールドが表示されていなくても、時間フィルターでコンテキストを指定できます。

メジャーをディメンションとして使う #

指標をディメンションとして使うフィールドは、クエリディメンションの一部です。その値は、データセットの物理列ではなく、指標またはその指標を使ったスカラー式の評価結果です。このフィールドはクエリディメンションとしての役割（ディメンションの役割）を保ち、クエリ結果の粒度を決める一要素になります。データセットの同一性は定義しません。

解説：指標をディメンションとして使う。このセクションでは、複数パス処理で満たすべき仕様を示します。解説では、検証済みの記述形式と確認すべき分類処理の段階を示します。コンパイラは、これらのクエリ列を物理ディメンション列や通常の出力指標とは別にモデル化し、指標の計算には通常の処理を再利用します。

columns.dimension での構文

記述形式とサポート範囲（DML 形式のクエリ）：

形式 例 意味
名前付き指標と明示的な +d - 初回購入月: '{初回購入月: {+d: 店舗番号}}' 指標の評価ディメンションに 店舗番号 を追加して指標を評価し、その結果をクエリディメンションのフィールドとして使います。
指標名のみ - 初回購入月 指標から派生するディメンションには使えません。参照する箇所で完全な +d キーを明示する必要があります。
{m: {+d: dim}} を包むスカラー式 - payment_day: 'cast({承認日時: {+d: payment_id}} as date)' 完全なキーごとにスカラー式を 1 回評価し、その結果をクエリディメンションのフィールドとして使います。
名前付きスカラー指標とクエリ側の +d 指標に formula: 'cast({承認日時} as date)' を指定し、続いて - payment_day: '{dt_payment_day: {+d: payment_id}}' を記述 スカラー式を再利用できる場合に推奨される等価な記述形式
dimension: / rank のラベル（+d なし） - brand_bucket: 'iif({売上高: {dimension: [ブランド], rank}} < 5, {ブランド}, ''others'')' dimension: で評価ディメンションを置き換える、または rank を使うクエリディメンションの式です。+d による複数パスでの結合パターンには該当しません。

これらのバインディングの記述と検証には、type: query を推奨します。生成されたテストフィクスチャのヘッダーに SQL が表示されていても、対応する Model Query と SQL の往復変換がサポートされていることの証明にはなりません。

評価のセマンティクス（複数パス）

指標をディメンションとして使う式を M、その式で明示した +d フィールドの集合を K、通常のクエリディメンションのフィールドの集合を Q とします。評価と結合の粒度は G = Q ∪ K で、指標から派生したラベルは含みません。内部の集計段階で K が再定義されることはありません。

  1. 細かい粒度での評価。 ディメンションとして使う各指標を G の粒度で評価します。通常の出力指標も G の粒度で評価し、後で上位の粒度に集計するために必要な状態や構成指標を保持します。
  2. 完全な分類キー G で結合。 分類リレーションには、完全なキーごとにスカラー値が 1 つ必要です。分類リレーションが、それを使う指標と同じリレーションにない場合は、分類値で指標をグループ化する前に結合します。店舗と月の組み合わせで分類する場合、結合には店舗と月の両方が必要で、+d: 店舗番号 だけでは不十分です。粗い粒度で結合するには、結合先で完全なキーを利用できるか、結合先から導出できることを証明できなければなりません。細かい粒度で結合するには、明示的なドリルダウンと上位の粒度への集計が必要です。NULL キーとクエリの対象データ集合に関するセマンティクスを維持します。
  3. クエリ結果の粒度に集計。 通常の指標を { measure-as-dimension fields } ∪ Q の粒度に集計します。K のフィールドは、Q にも含まれるものを除いて取り除きます。通常の指標を G で評価してからこの集計を行う形に安全に書き換えられない場合、コンパイルは失敗します。

処理の仕組みは、+d を使う多段集計（多段集計）と同じです。この用途では、ドリルダウンした粒度で得た指標の値が、複合式の中間入力にとどまらず、クエリディメンションのフィールドになります。

source
  → evaluate measure-as-dimension + other measures at finer evaluation dimension (+d)
  → attach on the complete classification key
  → roll up to query result grain (GROUP BY measure-as-dimension field[, ordinary query-dimension fields])

+d の互換性

分類と、それに関与する同階層のドリルダウン参照には、明示的なエンティティキーを使います。互換性は、+d の引数の表記だけでなく、解決後の評価ディメンションとスコープによって決まります。

共通の +d。 ディメンションとして使う各指標には、完全なキーを明示する必要があります。複数の独立したラベルを使えるのは、それぞれのキーが集合として等しい場合に限ります。キー内のフィールドの宣言順序は問いません。

キーを省略した参照。 同階層の指標からエンティティの粒度を推論しないでください。+d または dimension: でエンティティキーを明示します。キーを指定せずに指標をバインドすると拒否されます。検証した顧客数による分類では、どちらの形式もコンパイルできます。この結果から、すべての分類形式が使えるとは判断できません。出力指標を追加または削除しても、分類先が変わってはなりません。

異なるキー。 キーが異なる独立したラベルは拒否されます。ラベルは、同じクエリ内の別のラベルに依存できません。異なるエンティティ粒度を一般的に対応付けるには、別途モデル化したリレーションが必要です。

制約

  1. 分類には明示的なエンティティキーが必要です（+d を推奨します。dimension: も認識されます）。複数ラベルの互換性と上位の粒度への安全な集計は仕様上の要件であり、リリースで一律に保証されるものではありません。実際に使用するクエリを検証してください。

  2. 期間修飾子の組み合わせ全般は未検証です。test_82d では、mat を使い、移動する 1 年間の時間範囲に基づいて分類する処理をテストしています。この結果は、yoy や pop の正しさを裏付けるものではありません。分類とレポートの時間範囲が明示され、結果を裏付ける証拠がある組み合わせだけを使ってください。

  3. スカラー変換は、インラインで記述することも、名前を付けて定義することもできます。完全な分類キーごとに、一意に定まる値を 1 つ返す必要があります。

  4. 指標の dimensions: の許可リストと、粒度の安全性に関する規則（粒度の安全性）は、指標をディメンションとして使う式内のすべての指標参照に、それぞれが実際に評価される粒度で適用されます。

  5. データセット間の自動結合（データセット間の組み合わせ）でも、各データセットの指標は共通のクエリ粒度に集計されます。指標をディメンションとして使うフィールドは、付加と上位粒度への集計の後、そのクエリ粒度の一部になります。

  6. 表示される最終的な分類値と同じ値でグループ化します。NULL を含むキーも含め、完全なクエリキーごとに行が 1 つ必要です。分類処理によって、非加算指標の合計や、実在しない非アクティブなエンティティの作成が許可されるわけではありません。比率を構成する各要素の意味は維持されます。エンティティごとの値に明示的な外側の集計を適用するかどうかは、作成者が決めます。

  7. ソースフィルターは既存の修飾子ルールに従って適用されます。-d はフィルターを削除せずに粒度を変更します。-f と -df では、既存の方法で適用範囲を制御できます。ラベルに対する述語は分類後に適用し、レポートの集計値に対するしきい値は集計後に適用します。どちらも、対応する分類の入力を変更してはいけません。基準時点までの履歴、移動期間、現在の選択範囲に基づく分類は、それぞれ異なる業務上の定義です。

例

以下の 初回購入月 は、評価範囲内で月間純売上高が正である最初の月を指します。購入期間 は両方の端点を明示的にエンティティ単位で評価し、その細かい粒度の結果に最終集計を適用します。

初回購入月:
    type: measure
    formula: 'MINIF({dt_month}, {売上高: {+d: dt_month}} > 0)'

report:
    type: query
    allows: ALL
    columns:
        dimension:
            - 初回購入月: '{初回購入月: {+d: 店舗番号}}'
        売上高:
        購入期間: 'SUM(datediff(day, {初回購入日: {+d: 店舗番号}}, {最終購入日: {+d: 店舗番号}}))'
  • クエリ結果の粒度は [初回購入月] です。
  • ディメンションとして使う指標と 購入期間 の両方に {+d: 店舗番号} を適用し、より細かい粒度で評価します。
  • 最終的な GROUP BY では 初回購入月 を使用し、店舗番号 を除外します。

修飾子のスキーマ制約 #

dmx_variable_schema.yaml では、修飾子オブジェクトに次の構造上の制約が定められています。

  • dim_dt のバリエーションは、修飾子オブジェクトごとに、dim_dt、dim_dt as date、dim_dt as month などのうち最大 1 つです。
  • +d と dimension は相互に排他的で、修飾子オブジェクトごとにどちらか一方のみ指定できます。
  • -d と dimension は相互に排他的で、修飾子オブジェクトごとにどちらか一方のみ指定できます。
  • +d と -d / -df は、ディメンション名の集合に重複がない場合に限り、併用できます（あるフィールドで粒度を細かくし、別のフィールドを削除する場合など）。同じ名前が両方の集合に含まれる指定は無効です。修飾子の組み合わせを参照してください。
  • 上記の重複に関する規則を満たす場合、1 つの修飾子オブジェクトに複数の修飾子を指定できます。例については、修飾子を組み合わせるを参照してください。

修飾子の組み合わせ #

修飾子は記述された順序のままにします。複数のマクロによって中間指標が生成されることがあります。複数の評価経路を持つ関数に適用した時間マクロは、代わりに各分岐へ伝播することがあります。修飾子を重ねて適用する場合のセマンティクスと、そこに記載されているリリース時の確認項目を参照してください。

修飾子ごとに YAML キーを 1 つ記述します。{+f: {a: 1, b: 2}} のように書き、+f キーを繰り返し指定しないでください。-df は、ディメンションとフィルターの両方を削除します。

同じディメンションでの修飾子の競合

言語仕様では、1 つの修飾子オブジェクト内で +d のフィールド集合が -d または -df のフィールド集合と重なる場合、コンパイルエラーが必要です。現行ビルドでは、確認したケースでこの要件が適用されていません。代数的に相殺して {m} だけにしてはいけません。また、{+d: x, -df: x} を暗黙に {-f: x} に書き換えてはいけません。出力粒度にすでに x が含まれている場合、-df と -f の動作は異なります。

無効 理由
{销量: {+d: 门店, -d: 门店}} 同じフィールドを追加して削除する指定には、暗黙に採用できる一意の解釈がありません。相殺して {销量} にすると、入力ミスが見えなくなり、各店舗を等しく重み付けする AVG({销量: {+d: 门店}}) とは異なる意味になります。
{销量: {+d: 门店, -df: 门店}} {-f: 门店} に変換してはいけません。粒度を変更する場合と、フィルターだけを変更する場合では意味が異なります。

意図を明確にするには、{销量} / SUM({销量: {+d: 门店}}) / {销量: {-d:…\|-df:…\|-f:…}} のいずれかを記述する必要があります。
異なるディメンションは、SUM({销量: {+d: 门店, -d: 品牌}}) のように引き続き併用できます。

今回確認したビルドは、検証対象となった同一フィールドのディメンション競合を受け入れ、地域別合計を顧客単位で繰り返してから合算します。これは既知の実装上の不備であり、許容される記述方法ではありません。評価段階を 1 つ明示し、対応する SQL を確認してください。
