このページでは、type: query、列、フィルター、マテリアライズ方式の選択、after:を扱います。このクエリでは、SQL でのモデルクエリと同じモデル指標を使用します。

ファイル名の制約：.dml ファイルを dmlc -c でコンパイルする場合、type: query ブロックの名前はファイル名から拡張子 .dml を除いた部分と一致する必要があります。たとえば、my_report.dml には my_report: type: query を記述する必要があり、some_other_name: type: query は使用できません。名前が一致しない場合、コンパイラは次のエラーを返します：query name should be <filename> (the same as filename) instead of <block_name>。

基本構造 #

my_report:
    type: query
    allows: ALL              # optional: consider compatible materializations

    columns:
        dimension:
            - dt_month
            - product
        sales:               # measure reference (no AGG needed)
        sales_yoy:
            formula: '{sales: yoy}'

columns: は必須です。ディメンションを指定するキー以外は出力列の名前を表し、その値には式または指標への直接参照を指定します。オプションの dataset: はデータセットクエリ形式を選択するもので、columns.dimension とは併用できません。

クエリフィルターには次の形式があります。各キーはフィルターの名前を表し、指標参照の修飾子からその名前で指定できます。

値の形式 意味
<column>: <value> 同名の列に対する等価条件
<column>: [a, b] 指定した値のリストに含まれるかどうかの判定
<name>: {column: <column>, value: <value>} 明示的に指定した列に対する名前付き等価フィルター
<name>: {column: <column>, range: [lo, hi]} 明示的に指定した列に対する名前付き範囲フィルター。両端の値を含む
<name>: {visibility: hidden, default: on} デフォルト値が有効な非表示フィルター

各述語を適用する処理段階は、フィルターの配置ルールで決まります。

明細と集計 #

モード 指定方法 制約
集計 dataset: キーなし 指標を使用できます。コンパイラが集計を行います。
明細 dataset: DATASET_NAME 指標は使用できず、元の列のみ使用できます。 
# Detail query
product_list:
    type: query
    dataset: DATASET_PRODUCTS
    columns:
        dimension:
            - product

複数のデータセットの指標の自動結合 #

集計クエリが異なるデータセットの指標を参照する場合、共通のディメンションフィールドを使い、FULL OUTER JOINの規則に従って結合します。一方のデータセットにしか存在しない行も結果に含まれ、もう一方のデータセットの指標は NULL になります。

生成される結合タイプは、結果に残ることが保証される行に応じて決まります。コンパイラは FULL OUTER JOIN を起点として、クエリフィルターから導ける最も制約の強い結合タイプを各結合に適用します。filters: に "{primary_measure} is not null": を指定すると、副側にしか存在しない行が除外され、生成される結合は LEFT JOIN になります。両側で値の存在を要求する条件がある場合は INNER JOIN になります。この条件を適用した結果が、基準となる SQL の LEFT JOIN の結果と一致するのは、有効な主側グループで主指標が NULL になり得ない場合に限ります。NULL と空グループに関するこの前提が成り立つことを確認し、生成された結合タイプと出力を検証してください。前提が成り立たない場合、フィルターは有効なグループも除外します。データリネージ、レビュー、再利用時にこの条件を確認できるよう、after: の外に記述してください。

式をキーにする形式が必須です。"{expr}": と記述し、値は空にします。name: {condition: …} はスキーマに適合しません。

DML 形式での列参照 #

列の種類 構文 例
同じデータセットのディメンションフィールド 名前のみ product:
別のデータセットのディメンションフィールド "{DATASET}.column" prod_id: "{DATASET_PRODUCTS}.prod_id"
指標 名前のみ sales:
修飾子付きの指標 formula: sales_yoy: {sales: yoy}

注意：dataset: を指定していない集計クエリで、特定のデータセットに属する列を単独の列名で参照するとエラーになります。"{DATASET}.column" の形式を使用してください。

自動エイリアスと直接参照 #

式のないクエリ列は、名前の一致によって指標またはデータセットの列に解決できる場合があります。この仕組みを自動エイリアスと呼びます。次の 3 つのレベルがあります。

レベル 仕組み 例 結果
column（直接参照） データセットの columns: に式のない項目を指定します。DML での名前はテーブルの列名と一致します。 prod_amount: SUM(prod_amount)。エイリアスを付けず、名前をそのまま使用します。
クエリ列 → 指標（自動エイリアス） 式のないクエリ列で、列名が指標名と一致します。 revenue:（指標 revenue が存在する場合） コンパイラが指標の formula: に指定された式を代入します。
クエリ列 → データセットの列（自動エイリアス） 式のないクエリ列で、列名がデータセットの列名と一致し、そのデータセットの列をクエリのディメンションから導出できる必要があります。 prod_name:（pk({prod_id}) の連鎖をたどって参照するデータセットの列） コンパイラがデータセットの定義から列を解決します。

主な動作：

  • dmlc -c は、データセットの列がテーブルスキーマに存在するかどうかを検証しません。列名が一致していなくてもコンパイルは成功しますが、実行時に SQL エラーが発生します。列名の不一致を検出するには validateOnly を使用してください。データベース接続が必要です。
  • クエリ列の名前が指標名にも導出可能なデータセットの列名にも一致しない場合、not defined, add formula? エラーが発生します。
  • クエリ列の名前が指標名と異なる場合は、式（display_name: '{measure_name}'）を明示的に指定するか、abbr: で指標名を変更してください。
  • クエリのディメンションから導出できないデータセットの列を参照すると、cannot be derived from dimension [store_id] エラーが発生します。たとえば、ディメンションフィールドに依存しない元のファクト列がこれに該当します。
  • そのまま渡す列（formula: なし）は、オブジェクト形式でメタデータプロパティ（description:、visibility:）を指定できます。この場合、formula: は不要です。たとえば、revenue: { description: 'Total revenue' } は自動エイリアスによって指標 revenue に対応付けられ、説明が追加されます。

visibility: hidden #

列を最終的なクエリ出力から非表示にし、中間の一時テーブルでは引き続き使用できるようにします。

項目 動作
最終 SELECT 非表示列は通常、出力に含まれません。ただし、フィルターまたは HAVING 句から参照される非表示列は、最終出力に含まれる場合があります。出力列を確定する前に、生成された SQL を確認してください。
中間の一時テーブル 非表示列は、JOIN 条件と filters: で引き続き使用できます。
非表示のディメンションフィールドを参照する filters: コンパイルは成功しますが、オプションの結合がより制約の強い結合に変わったり、補助結果のマテリアライズが強制されたりする場合があります。生成された SQL を確認してください。
非表示のディメンションフィールドを名前で参照する after: の SQL 失敗 — query columns refer to nonexistence source column
PK の連鎖 維持される — visibility: hidden だけでは PK の警告は発生しません。

指針: after: がディメンションフィールドを名前で参照する場合は、visibility: hidden を削除します。after: が指標列のみを使用する場合は、その設定を残します。出力契約がある場合は、コンパイルして、非表示の補助列が最終結果に含まれないことを確認します。追加の列が許可されるのは、出力契約で明示的に認められている場合に限ります。

有効な YAML の書き方: - dim: {visibility: hidden}、またはキーを dim エントリの配下に置いたネストされたマップを使用します。visibility: を dim キーと同じインデントで並べると、インデント不足でスキーマの lint エラーになります。インライン形式またはネスト形式で記述してください。dmlc -c だけを使う場合は、コンパイルで生成された SELECT を必ず確認します（スキーマの lint はエディターまたは dmlc --lint で実行されます）。

クエリディメンションの形式 #

columns:
    dimension:
        - dt_month
        - product
        # Correct: list dimension field names only

誤り: データセットをまたぐ列のマッピングをクエリのディメンションフィールドに含めないでください。これらの式は個別のクエリ列として定義します。

# Wrong
columns:
    dimension:
        - f_tag_id: {DATASET_PT}.id

# Correct
columns:
    dimension:
        - f_tag_id
    f_tag_id: "{DATASET_PT}.id"

例外：指標をディメンションとして使う場合、クエリディメンションのエントリに指標をバインドできます（通常は +d を使用します）。この場合、クエリはその指標値を単位として行をグループ化します。

columns:
    dimension:
        - first_purchase_month: '{first_purchase_month: {+d: store_id}}'
    sales:

分類対象のエンティティのキーは、+d（推奨）または dimension: で明示します。完全なキーが一致する場合は、複数の独立したフィールドを使用できます。通常の出力指標は、Q ∪ K のレベルから上位のレベルに正しく集計できる必要があります。ラベルに対するフィルター（式の filters: または Model Query の HAVING）は、ラベルが存在するようになった後に適用されます。指標をディメンションとして使うを参照してください。物理マッピングや {DATASET}.col マッピングにはこの例外を使用しないでください。

フィルターを配置する階層 #

フィルターの配置は処理の意味を決めるもので、構文上の好みで選ぶものではありません。

レイヤー 配置場所 ここで指定する内容
クエリの filters: クエリブロック レポートごとの絞り込み（チャネル、ブランド、日付範囲）
中間列または中間指標 .dml のデータセットまたはトップレベルの指標 除外された行が指標値が NULL のグループに残ってもよい場合の、指標固有の採用条件
データセットの sql: データセット定義 ソース行の集合に常に成り立つ不変条件、または DML で宣言的に表現できない構造

ソースの WHERE 条件を指標の入力条件に移すと、結果に行が存在するかどうかが変わります。ただし、除外された行だけで構成されるグループが生じ得ない場合、またはそのようなグループが、指標値が NULL で結果に存在するグループと契約上同等である場合は例外です。例外に該当することを明示的に証明してください。該当しない場合や判断できない場合は、行を除外する形式を維持します。

構造化範囲のセマンティクス: クエリの filters: に指定する range: [start, end] は、宣言された dt_<grain> の粒度で両端の値を含みます。2025 年の日次データには ['2025-01-01', '2025-12-31']、月次データには ['2025-01-01', '2025-12-01'] を使用します。SQL 方言によっては < dateadd(day, 1, end) のように上限を含まない条件で実装されますが、DML の入力で指定した終了値は、範囲に含まれる最後の値です。

リストと範囲でよくある間違い: 値を単にリストで dim: ['a', 'b'] と指定すると、WHERE dim IN ('a', 'b')（2 つの値のいずれかに完全一致）にコンパイルされ、両端を含む範囲にはなりません。日付ディメンションでは、これによりデータが気付かないうちに欠落します。dt_date: ['2024-01-01', '2025-12-31'] が返すのは指定した 2 日の行だけで、2 年間全体の行は返しません。両端を含む区間を指定するときは、必ず range: [start, end] を使用します。

# Wrong — only 2 days of data
filters:
    dt_date: ['2024-01-01', '2025-12-31']

# Right — full inclusive range
filters:
    dt_date:
        range: ['2024-01-01', '2025-12-31']

フィルターでよくある問題:

症状 対処方法
[dataset …] [filters]: not supported クエリの filters:、指標の式、または sql: の WHERE に移動する
クエリフィルターで referred column {DATASET}.col is undefined が発生する 文字列形式を使用する: "{DATASET}.col = value":
日付ディメンションに要素が 2 つのリストを指定すると、2 日分の行しか返らない 単なるリストではなく range: [start, end] を使用する。dim: [a, b] は IN (a, b) にコンパイルされ、BETWEEN にはならない。
クエリの filters: 内の複雑な EXISTS / PK の連鎖 指標の入力を絞り込むのは、指標固有の採用条件に限ります。条件がソース行を選択する場合は、ソース行を処理する段階に残します。条件を指標に移すと、レポートの対象となる行の集合が変わることがあります。生成された述語と結合を確認してください。

pk の連鎖 #

# Single PK lookup
formula: 'pk(customer_id).{DATASET_CUSTOMERS}.tier'

# Composite PK — all columns required
formula: 'pk(brand_id, tag_id).{DATASET_PRODUCTS}.state'

キーの個数に関するルール: pk(...) 内のキーの数は、対象データセットの dimension: にあるディメンションフィールドの数と一致する必要があります。一致しない場合は expect N expr(s) to query dataset X using pk, but got M が発生します（トラブルシューティング索引の P65 を参照）。

連鎖の入れ子: ある pk() の連鎖から導出した列を、別の pk() の連鎖のキーとして使用できます。コンパイラは導出の連鎖をたどり、対応する入れ子の LEFT JOIN を生成します。この方法を使うと、属性を検索し、その属性を使って別の属性を検索する処理を、sql: や after: を使わずに直接モデル化できます。

# fact dataset
columns:
    store_id:
    # First hop: store_id → Dim Customer → hq_id
    hq_id: pk({store_id}).{Dim Customer}.hq_id
    # Second hop: hq_id (itself a pk chain result) → Dim Customer → store_code
    hq_code: pk({hq_id}).{Dim Customer}.store_code
    # Third hop: hq_id → Dim Customer → org_id, then org_id → Dim Org → emp_name
    hq_org_id: pk({hq_id}).{Dim Customer}.org_id
    hq_emp_name: pk({hq_org_id}).{Dim Org}.emp_name

確認済みのビルドでは、列の依存関係や pk() の参照先を含め、同じファイル内の前方参照がサポートされます。読みやすくするため、依存先を先に記述します。インクルードには別の可視性境界があります。モデルの合成を参照してください。

after: 句 #

after: は省略できます。省略すると、コンパイラはクエリのディメンションフィールドに対応する可視の出力列を解決し、解決後のディメンションフィールドの順にその出力列をソートキーとして使い、結果の行を昇順に並べ替えます。そのため、非表示のディメンションフィールドについては、定義に記述されたフィールド名の代わりに、可視のクエリ列のエイリアスが並べ替えに使われることがあります。出力に有効なディメンションがなければ、行の順序は保証されません。NULL の並び順の指定を省略すると、対象の SQL 方言の既定値が使われます。

after: ブロックを指定すると、最終結果の並び順はそのブロックで決まります。特に、select * from {QUERY} に独自の ORDER BY がない場合、コンパイラの既定の並び順は解除されます。after: は、業務上意味のある指定が既定と異なる場合にのみ使用します。該当する指定は、並べ替えの方向、NULL の位置、同値の場合に順序を決める基準、指標や式による並べ替え、TOP または LIMIT です。再集計は行わないでください。

my_report:
    type: query
    columns:
        dimension: [product]
        sales:
    after: 'select * from {QUERY} ORDER BY sales DESC LIMIT 10'

after: を指定する場合は、{QUERY} が必須です。これは、クエリ後の文が参照する、コンパイル済みクエリの結果を表します。「並べ替えのみ」とは、このラッパーと ORDER BY/TOP/LIMIT 以外に業務ロジックがないことを意味します。明示した並べ替え順がクエリの既定の出力順と一致すると、前段のコンパイラが redundant ORDER BY 警告を出します。該当箇所のヒントに従ってください。after: にほかの重要な処理が残る場合は、冗長な ORDER BY 句だけを削除します。ブロック全体を削除するのは、ほかに処理が残らない場合だけです。

誤り：標準の指標クエリで、after: 内の group by を使って再集計する。指標の集計はクエリブロックで行います。

allows: ALL #

互換性のあるマテリアライゼーションをすべてコンパイラの検討対象にするには、次のように指定します。

my_report:
    type: query
    allows: ALL
    columns:
        dimension:
            - dt_date
        sales:

allows: は、使用候補となるマテリアライゼーションを指定します。ALL は候補の使用を許可し、NONE はマテリアライゼーションの使用を無効にします。名前を明示すると、その名前のものに候補が絞られます。候補を使用できるかどうかは、行や集計値を定義する粒度とフィルターが、それぞれクエリに適合するかどうかで決まります。この設定で指標の dimensions: の制約が緩和されたり、クエリの粒度を任意に指定できるようになったりすることはありません。マテリアライゼーションの宣言を参照してください。

YAML 構文でよくある間違い #

  • :、{、- のいずれかを含む数式は引用符で囲みます。例：formula: 'SUMIF(...)'
  • measures: 配下のディメンションフィールド：誤りです。宣言できるのは dimension: の配下だけです。
  • 複合指標での dataset: の指定：誤りです。数式がほかの指標を参照する場合は、dataset: を省略します。
  • データセット間でディメンションフィールド名が異なる場合：名前を 1 つ（例：tag_id）に統一し、columns: で対応付けます。

YAML クエリ早見表 #

type: query でクエリを定義します。dimension: で結果のグループ化を指定し、columns: で出力を指定します。フィルター条件を記述する位置によって、条件がソース行、個々の指標、集計後の結果のいずれに適用されるかが決まります。データセットを組み合わせる場合は、結合キー、値が NULL のキー、片側にだけ存在するグループを先に確認します。最終的な並べ替えなどのクエリ操作には after: を使用します。
