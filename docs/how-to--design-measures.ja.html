分析ワークフローで不足している業務上の計算が見つかったら、このガイドを使用します。式を選ぶ前に、計算の対象となる行と、中間値を求める単位を定義します。

中間列で指標の対象行を決める条件 #

条件によって、ある指標に算入する行だけが決まり、データセット全体の行集合にも意味がある場合は、中間列を使います。state や delete_time などの名前だけで条件を分類しないでください。同じように見える条件でも、ソースに含める行を恒常的に定義する場合があります。

columns:
    valid_amount:
        description: Row-level amount gated by validity checks
        formula: 'iif(state = 1 and delete_time is null, prod_amount, null)'
measures:
    total: SUM({valid_amount})

SUM は NULL を無視するため、条件を満たす行が 1 行以上あるグループでは、集計値がフィルター適用後の合計と一致します。この条件式は、ソースに適用する WHERE と一般には等価ではありません。条件を満たす行がないグループは WHERE では結果から消えますが、中間列で対象を制限すると、total = NULL の行として残ることがあります。同じクエリ内の他のカウント、結合、ウィンドウ計算、後続のフィルターも変わる可能性があります。

この書き換えは、条件を満たす行がないグループの挙動、同じクエリ内の他の指標で対象行を決める条件、重複排除・結合・ウィンドウ計算の対象行を検証し、行が存在しない場合と NULL を持つ行が存在する場合が等価であることを確認してから使います。それ以外の場合は、クエリまたはリレーションシップのスコープで行を除外する条件を維持するか、ソースで恒常的に成立する条件を、必要最小限の sql: を使ってデータセットに定義し、その内容を文書化します。

処理を段階に分ける例： tax_rate_effective（適用税率の決定）→ amount_excl_tax（税抜金額への換算）→ eligible_amount（指標の対象行の判定）→ SUM({eligible_amount})（メジャー）。コンパイラは中間式を生成先の式に直接展開します。生成された SQL を確認し、各式がどのように変換され、どの行が対象になるかを検証します。

派生メジャー #

レポート固有のモディファイアーは、メジャーを使う箇所で適用します。.dml で派生メジャーを定義するのは、変更後の値をすべての利用箇所で再利用する必要がある場合（type: materialize オブジェクトに列挙する場合など）、または名前付きの業務指標として定義する必要がある場合に限ります。メジャーの式では DMX 参照を使い、AGG() は決して使わないでください。

sales_last_month:
    type: measure
    formula: '{sales: pp}'

sales_yoy_growth:
    type: measure
    formula: '{sales: yoy}'

sales_by_product:
    type: measure
    formula: SUM({sales: {+d: product}})

これらのメジャーでは、メジャー名に対応する変換処理が維持されます。評価は引き続き、クエリのコンテキストとモディファイアーおよびフィルターのルールに従います。

CTE と複数ステップの処理 #

SQL で CTE を使用している場合は、次のいずれかの方法で置き換えます。

  1. モディファイアー付きのメジャー（推奨）：CTE がフィルターまたはディメンションフィールドを追加するだけの場合
  2. 列マクロ：CTE が派生列を計算する場合
  3. 個別のクエリ：CTE が実際に中間結果セットを生成する場合

例：CTE を使って完了済みの注文（"completed orders"）に絞り込む SQL

-- Original SQL
WITH completed AS (
    SELECT * FROM orders WHERE status = 'completed'
)
SELECT product, SUM(amount) FROM completed GROUP BY product

# DML approach
completed_sales:
    type: measure
    formula: SUM({amount: {+f: {status: 'completed'}}})

-- Model Query SQL: retain the row-removing population restriction
SELECT product, AGG(completed_sales) FROM MODEL
WHERE status = 'completed'
GROUP BY product

ディメンションを制約したメジャー #

⚠️ メジャーの dimensions: には、使用できるディメンションを指定します。 内側のリストはそれぞれ 1 つの許可されたディメンションを表し、外側のリストはその選択肢を列挙します。この設定では、データセットの行を識別する方法や、クエリでのグループ化は定義しません。行の識別はデータセットの dimension: で、グループ化はクエリの GROUP BY または columns.dimension: で定義します。ディメンションの役割を参照してください。

特定のディメンションで指標を評価する必要がある場合に限り、この制約を追加します。

# "Average order value per customer" — customer_id is required during evaluation
aov_per_customer:
    type: measure
    formula: DIVIDE({sales}, {number_of_transactions})
    dimensions:
        - [customer_id]    # ← the only allowed dimension

他の式でこのメジャーを使う場合は、{aov_per_customer: {+d: customer_id}} を明示的に指定して customer_id で評価し、その結果を上位の単位に集計する必要があります。この制約は評価単位を指定するのに役立ちますが、予想外の結果になることもあるため、制約の内容を明記してください。

SQL をメジャーに変換する #

指標の仕様や既存の SQL（CTE、JOIN）を、DML のメジャーとシンプルな Model Query SQL（FROM MODEL + AGG(...)）に変換するためのチェックリストです。

SQL の記述ではなく、ディメンションから検討する

  • 最終クエリのディメンションは何か？（例：[customer] または [customer, dt_month]）
  • 中間評価のディメンションは何か？（例：初回購入なら [customer]）
  • 評価方法に応じて実装を選びます。データセットのディメンションで直接評価する → アトミックメジャー、評価ディメンションを変更する → +d / dimension、使用できるディメンションを制限する → ディメンションを制約したメジャー。中間値を求める単位と結果を求める単位が両立することを確認します。処理に JOIN またはサブクエリが本当に必要で、DML で表現できない場合は、作業を止めて設計を見直してください。Model Query SQL のルールを回避しないでください。

ディメンションを制約したメジャー（CTE に相当する中間行を表現する）

  • 許可するディメンションを 1 つに限定したメジャーを定義します：dimensions: [[customer_id]]
  • SUM({that_measure: {+d: customer_id}})（または AVG など）で上位の単位に集計します。
  • dimensions: は、メジャーが有効となるディメンションを制限します。別の式でそのメジャーに +d を指定すると、メジャーの評価ディメンションに必要なディメンションフィールドが追加されます。
first_month:
    type: measure
    description: first month with sales > 0 (customer grain only)
    formula: 'MINIF({dt_month}, {sales: {+d: dt_month}} > 0)'
    dimensions:
        - [customer_id]

first_month_sales_by_customer:
    type: measure
    description: sales in customer's first month (customer grain only)
    formula: 'SUMIF({sales: {+d: dt_month}}, {dt_month} = {first_month})'
    dimensions:
        - [customer_id]

first_month_sales_total:
    type: measure
    formula: 'SUM({first_month_sales_by_customer: {+d: customer_id}})'

顧客ディメンションに制約されたメジャーでは、{sales: {+d: dt_month}} は対象の顧客の該当月の売上です。

first_month でレポートをグループ化し（クエリのディメンション = メジャーの結果）、同じクエリ内の他のメジャーを +d: customer_id でそろえる方法については、メジャーをディメンションとして使うを参照してください。

条件を一度でも満たしたかを判定する処理（継続や繰り返し行動の分析）

  • 顧客ごとのフラグ：ISNULL(MAXIF(1, <condition>), 0) に dimensions: [[customer_id]] を指定
  • フラグが立った顧客の合計数：SUM({flag: {+d: customer_id}})
  • 割合：DIVIDE(total_flag, total_customers)

CTE を 1 つ以上のメジャーに変換する

CTE のパターン DML での実装方法
顧客と月の組み合わせごとの集計 {sales: {+d: [customer, dt_month]}}
初回購入月 顧客単位での MINIF({dt_month}, …)
顧客ごとのフラグ 顧客単位での MAXIF
最終的な KPI SUM({customer_measure: {+d: customer_id}}) と比率

最終的なクエリの形式は SELECT AGG(kpi_1), AGG(kpi_2), ... FROM MODEL です。

DISTINCTCOUNTIF / SUMIF の条件で使う +d（集計とは異なる単位での絞り込み） #

ある単位でエンティティを数え、別の単位で絞り込む場合は、条件内の列ではなくメジャーに {+d: dimension_field} を指定します。

  • 誤り: DISTINCTCOUNTIF({entity: {+d: entity}}, …) は無効です。修飾子は指標にのみ指定できます。
  • 正しい例: DISTINCTCOUNTIF({entity}, {sales: {+d: entity}} > 0 AND …)

コホートの範囲: エンティティの粒度と、対象とする履歴の範囲または基準時点を明示して初回購入を定義し、その初回購入を観測期間と比較します。名前付きの分類式を再利用するのは、使用可能なディメンションと、その分類式を適用する粒度を検証した後に限ります。エラーになる式を直接埋め込んでも、その意味が正しいことの確認にはならず、粒度の不整合も回避できません。検証済みの式の形式とリリース版の不具合については、指標をディメンションとして使用するを参照してください。

過去の購入を振り返る再購入指標 #

まず、業務上の定義を文章にします（誰を対象とするか、観測月、対象期間）。顧客単位でフラグを作成し、SUM({flag: {+d: customer_id}}) または DISTINCTCOUNTIF(...) で集計します。定義の意味を変更する前に、業務責任者と確認してください。

レポートの粒度で重複を除いた件数を再計算する #

2 か月に登場する購入者は、それぞれの月で 1 人、四半期全体でも 1 人として数えます。ファクトデータセットで buyers: DISTINCTCOUNT({customer_id}) を定義します。四半期内の購入者を重複なく数えるには、月でグループ化せず、四半期全体に AGG(buyers) を適用します。複数の四半期を個別に表示するには、四半期でグループ化します。

SUM({buyers: {+d: dt_month}}) は月ごとの重複を除いた購入者数を合計します。試行では、購入者と月の組み合わせが 3,066 件、四半期全体で重複を除いた購入者数が 1,248 人でした。試行で検証したビルドは、この合計を受け付け、厳格な診断メッセージは出しませんでした。同じ期間に対して COUNT(DISTINCT customer_id) を直接適用した結果と比較してください。
