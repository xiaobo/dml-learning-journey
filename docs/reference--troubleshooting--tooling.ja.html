ここでは、検証、CLI の出力の取得、方言、モデルのファイル名を扱います。コマンドの実行手順は「コンパイルと検証」を参照してください。

P34. 信頼性が求められる用途で検証せずに使う #

誤り：データベースで検証できるにもかかわらず、クエリを書いてすぐに検証なしで実行する。対処：使用予定の接続で --with-validation を指定して実行するか、--validate でレポートを作成します。検証では、コンパイルエラーを検出し、クエリがアクセスするデータセットの完全なディメンションを実際のデータと照合し、EXPLAIN でメインクエリを確認します。結果の正しさや将来の一意性を証明するものではありません。前提条件：検証には、--validate に対応する実行ファイルと、設定済みの接続が必要です。--help と --advanced-help を確認してください。いずれかの前提条件が満たされていない場合は、データベース検証を未実施として記録します。「データベースでの検証」を参照してください。

P35. 列の説明を無視する #

誤り：説明に「内部使用専用。代わりに customer を使用してください」とあるのに、customer_name を使う。対処：列の説明を読み、その指示に従ってください。内部フィールドは対応する公開エイリアスに置き換えます。

P36. 方言の不一致 #

誤り：SQLite の日付式がすべて MSSQL でそのまま使えると想定する。対処：DML は、対応している SQLite 形式の日付式を対象の方言に変換します。生成された SQL を確認し、実際に使う式をそのままテストしてください。未対応の形式には、その方言に合った代替の式が必要です。「日付式」を参照してください。

カテゴリ：コンパイラ、YAML、名前の付け方 #

P53. PowerShell での && によるコマンドの連結 #

誤り：cd path && dmlc --model=model.dml query.sql 修正：cd path; dmlc --model=model.dml query.sql

P53b. FROM の名前 ≠ --model= のファイル名 #

誤り：SQL の SELECT AGG(x) FROM MODEL を dmlc q.sql --model=acme.dml で実行する。
→ model file "acme.dml" does not match FROM "MODEL" (expected "MODEL.dml")（終了コード 65）。
対処：FROM acme に変更するか、--model=model.dml を指定して FROM MODEL をそのまま使うか、正しい .dml ファイルが入っているディレクトリを指定します（--model=<dir> はその中の <FROM>.dml を見つけます）。
注記：dmlc -e はディレクトリを受け付けず、.dml ファイルが必要です。「モデルクエリ SQL」の「クエリの種類」を参照してください。

P63. Windows の CLI に直接渡すモデルクエリの SQL での / 演算子 #

症状：file not found: SELECT ...。a / b に含まれる / により、CLI が SQL 文字列をファイルパスとして扱います。対処：CLI にクエリを直接渡す場合は DIVIDE(a, b) を使います。または、コマンドライン引数の代わりに .sql ファイルでクエリを渡します。

P54. CJK 文字を含む JSON を PowerShell のパイプで渡す #

誤り：中国語のフィールド名を扱うときに dmlc ... | Out-File result.json を使うか、標準出力を取得する。対処：dmlc ... --output=result.json --replace を使うか、Node で execSync(..., { encoding: 'utf8' }) を使います。

ビルドごとの CLI オプション #

実行ファイルのビルド日時とヘルプを確認し、そのビルドでのコマンドの仕様を把握してください。

以前のオプション 確認済みのビルド
--output-format=json 構造化された CLI レポートを出力する --json
--output-dir=gen コンパイラの生成物を出力する --artifacts=gen
モデルクエリに対する --validate-only 単独で検証レポートを出力する --validate

Explain-change は、引き続き独自の事前チェックに --validate-only を使います。クエリの実行時は、--with-validation を指定すると、検証に失敗した場合に行を返す前に処理が停止します。

SQL の構文チェック #

2026-11-23 のビルドでは、たとえば QUALIFY を使ったときに、構文解析に失敗しても --check --json が成功と報告することがあります。必要な処理の終了ステータスと診断メッセージを確認してください。たとえば、モデルクエリなら厳密なコンパイル、変換なら --to-dml の結果を確認します。

検証中にカレンダーのセットアップが失敗する #

DML_CALENDAR の権限エラーが表示された場合は、選択したスキーマと接続に使用しているロールを確認してください。テーブルを作成し、行を挿入できるロールを使い、「システムカレンダーのセットアップ」の手順で初期化します。その後、実行時のロールで検証をやり直してください。
