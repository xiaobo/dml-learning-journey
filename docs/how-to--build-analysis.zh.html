按照此流程添加可复用的度量及使用这些度量的查询。首次编译时，请按照编译第一个模型查询中的步骤操作。查询语法请参阅模型查询。

第 1 阶段：明确所需结果 #

编写 SQL 之前，先记录报表要求。

  1. 确定结果需要源数据行还是分组计算的度量。
  2. 列出用于标识一条结果行的字段。
  3. 明确时间范围、对比期间和报表筛选条件。
  4. 区分报表筛选条件和定义业务度量的条件。
  5. 记录源数据的总体范围、NULL 的处理方式和必需的输出列。
  6. 列出可能改变结论的假设。

在建模前和执行后检查业务假设，包括源数据的总体范围、报告期、缺失值和分母。

第 2 阶段：起草使用度量的查询 #

添加度量前，先编写计划使用的 SELECT、WHERE 和 GROUP BY 子句。尽可能使用已有的业务名称。

SELECT
	dt_month,
	渠道,
	AGG(销售额),
	AGG({销售额: yoy}) AS 销售额_yoy,
	AGG(同店销售额)
FROM MODEL
WHERE dt_month = '2025-03-01'
GROUP BY dt_month, 渠道

将报表分组、时间窗口和按渠道筛选的条件保留在查询中。将同店纳入条件等可复用定义放在模型中。如果所需结果取决于排序或行数上限，请添加相应设置。谓词顺序不影响查询能否通过语法检查。

为每个带修饰符的度量引用使用不同的别名。检查编译器生成的输出列，因为编译器可能调整列顺序，也可能在采用已知有缺陷的查询结构时省略所请求的时间字段。

第 3 阶段：查找缺失的度量定义 #

针对查询草稿中的每个 AGG(...)，检查目标模型。

  1. 如果现有度量的定义与所需指标一致，请复用该度量。
  2. 如果相似度量的业务含义不同，请在其名称和描述中保留这一区别。
  3. 如果查询草稿需要可复用的业务定义，请添加度量。
  4. 仅用于报表的筛选条件应保留在查询中，除非该条件本身定义了指标。

沿依赖关系追溯到原子度量。同店指标的依赖项可能包括按客户和月份计算的金额、按客户和月份判断是否符合纳入条件的计算，以及外层汇总。

第 4 阶段：扩展模型 #

如果能提高可读性，请先定义依赖项，再定义使用它们的内容。在已检查的情形中，支持引用同一文件中稍后定义的内容。

  1. 在每个数据集中声明能唯一标识源数据行的所有字段。
  2. 使用数据集的列定义原子度量。
  3. 如果业务计算需要特定的求值维度，请在度量定义中添加 dimensions:。
  4. 在需要更细求值维度的引用处添加 +d。
  5. 使用显式的外层聚合来合并中间值。
  6. 使用所需的组成项定义复合比率。
  7. 在描述中写明总体范围、粒度（定义行或汇总值的层级）以及 NULL 的处理方式。

使用包含必需字段的查询测试受维度约束的度量。仅对 dt_month 应用筛选条件，无法满足封闭求值维度 [customer, dt_month] 的要求。

有关建模模式，请参阅度量。编写描述和命名时，请遵循编写模型元数据中的说明。

第 5 阶段：验证模型和查询 #

如果对行为有疑问，以所选 dmlc.exe 的实际行为为准。记录其路径、版本、构建时间戳和方言。

  1. 对修改后的模型运行 lint 检查。
  2. 针对每个新计算，在严格模式下编译一条最小查询。
  3. 在严格模式下编译使用度量的完整查询。
  4. 检查诊断信息、提示、SQL、分组、联接、筛选条件、别名和输出顺序。
  5. 如果有可用的相关连接，请先运行仅验证（validate-only），再进行用于获取可信结果的执行。
  6. 选取有代表性的数据子集执行查询，并将结果与报表要求对照。
  7. 如果有独立的 SQL 查询或报表结果，请基于同一份源数据快照比较每行的出现次数、键、NULL 值和所有度量。
dmlc --lint model.dml --json
dmlc --compile --strict query.sql --model=model.dml --json --artifacts=gen
dmlc --validate query.sql --model=model.dml --connection=default --json

仅当 default 是预期使用的已配置连接时，才运行最后一条命令。使用 dmlc CLI介绍如何捕获输出以及如何处理验证失败。

根据实际公式核对每条语义规则。如果同店计数和可比的总计数基于同一总体，同店计数就不能超过总计数。如果被排除的行含有负值，子集金额可能超过总金额。如果缺少上年输入数据，结果可能是 NULL、零或其他已声明的回退值。不要假设所有同比指标都返回零。

如果严格模式下仍有警告，请保留该问题及其对应的 SQL。生成了查询并不表示通过了严格编译。如果无法通过实际连接进行检查，请记录 not run 和缺少的前提条件。

针对每项主要分析结论，运行可能推翻该结论的查询。将相关证据与报表一同保存。

第 6 阶段：审查最终交付物 #

第 5 阶段的适用检查通过后，按照第 6 阶段的技术审查中的说明操作。提供模型、使用度量的查询、原始报表要求、用于标识编译器的信息和验证证据。

修复后重新运行受影响的检查。明确标注业务定义的变更。如果拟议的优化会改变指标，请返回第 4 阶段。

交付模型和查询 #

将可复用的模型、使用度量的 SQL 和验证证据一同保存。记录尚未解决的问题和未运行的检查。
