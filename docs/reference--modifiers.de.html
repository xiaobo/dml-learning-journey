Diese Seite beschreibt den Aufbau der Modifikatorwerte, die Wirkung von Filtern und die Kombination von Modifikatoren. Die Seite Ausdrücke und Funktionen behandelt Referenzen und integrierte Funktionen. Die Seite Beispiele für die Aggregation auf feinerer Ebene zeigt die vollständigen Verarbeitungsschritte.

Aufbau der Modifikatorwerte #

In {measure: {modifier_a: Wert, modifier_b: Wert}} hat das äußere Objekt genau einen Schlüssel für die Zielkennzahl. Die darin enthaltene Zuordnung von Modifikatoren kann mehrere Schlüssel enthalten, sofern die Modifikatorbeschränkungen eingehalten werden.

Schlüssel oder Form Modifikatorwert
dim_dt Formel als Zeichenfolge oder Objekt mit den Feldern Wert und range
dim_dt as date, dim_dt as week, dim_dt as month, dim_dt as quarter, dim_dt as year, dim_dt as hour Variante zur Periodenumrechnung. Pro Modifikatorobjekt ist höchstens eine Zeitvariante zulässig.
+f Filtername als Zeichenfolge, Liste von Filternamen oder Inline-Objekt wie {column: Wert}
-f Filter- oder Spaltenname als Zeichenfolge oder eine Liste solcher Namen
Modifikatorname allein Name eines dt-macro oder fn-macro

Zeitmodifikatoren #

Die Referenzkopie der Systemmakros enthält Definitionen für dt-macro zur Zeitverschiebung und für fn-macro, die eine Formel umschließen. Makros für Wachstumsraten geben die Raten als Dezimalzahlen zurück. Die in der ausgewählten ausführbaren Datei enthaltenen Ressourcen bestimmen die verfügbaren Makros und Formeln sowie die Beschränkungen für prerequisite.

Zwei Makrotypen

Typ Rückgabewert Beispiele
dt-macro Absoluter Wert pp, ya, ytd, mat, p3m, ...
fn-macro (Wachstum) Rate als Dezimalzahl pop, yoy, mom

Verkettung. Modifikatoren lassen sich verketten. AGG(Umsatz, 'ytd', 'ya') ergibt den Wert vom Beginn des Vorjahres bis zum entsprechenden Stichtag im Vorjahr. Die vollständigen Regeln stehen unter Verkettung von Modifikatoren.

Zeitkontext. Zeitmodifikatoren benötigen eine auflösbare Referenz auf dim_dt und müssen die Voraussetzungen ihrer Makros erfüllen. Eine Gruppierung nach einem Zeitfeld stellt den Kontext am deutlichsten her. Auch ein Zeitfilter kann den Kontext liefern. Siehe Zeitregeln für Model Query.

Periodenumrechnung mit dim_dt

SELECT dt_year, dt_quarter,
       AGG({Umsatz: {dim_dt as quarter: pp}}) as Vorquartalsumsatz
FROM MODEL GROUP BY dt_year, dt_quarter

Mit dim_dt as quarter arbeitet pp auf Quartalsebene, auch wenn die Abfrage nach Jahr und Quartal gruppiert.

Funktionsmodifikatoren #

Die Referenzkopie der Systemmakros definiert unter anderem die Makros rank, pot, grand, firstday und lastday. Die in der ausgewählten ausführbaren Datei enthaltenen Ressourcen bestimmen die verfügbaren Namen, Formeln und Voraussetzungen. Die Diagnosemeldung zu einem unbekannten Modifikator listet die in der geprüften Build-Version verfügbaren Namen auf.

Der Filtermodifikator +f ist ein Modifikator auf Schemaebene. Er ist kein Systemmakro.

Modifikator Syntax Rückgabewert Beschreibung
+f: condition {measure: {+f: {col: val}}} Gefilterter Wert Die Kennzahl bei der Aggregation filtern

+f filtert atomare Eingabezeilen und ist kein Prädikat, das nach der Aggregation ausgewertet wird.

Ziel / Prädikat Verhalten
Spalte innerhalb einer atomaren Aggregation Filtert die Eingabe dieser Aggregation
Atomare Kennzahl + Prädikat auf einer Quellspalte Unterstützt. Beispielsweise erzeugt {Umsatz: {+f: "Bestellstatus = 1"}} ein bedingtes SUM.
Einfache zusammengesetzte Kennzahl + Prädikat auf einer Quellspalte Der Filter wird an die atomaren Kennzahlen weitergegeben, von denen die zusammengesetzte Kennzahl abhängt. Das wurde für divide({Umsatz}, {Verkaufsanzahl}) geprüft. Nur verwenden, wenn der Filter auf alle diese atomaren Kennzahlen angewendet werden soll.
Atomare Kennzahl mit +d und +f auf einer Quellspalte Beim geprüften Rollup mit AVG unterstützt. Prüfen Sie, ob die Filterung vor der Aggregation auf feinerer Ebene erfolgt.
Prädikat, das eine aggregierte Kennzahl referenziert, beispielsweise "{Verkaufsanzahl} > 3" Wird mit cannot use +f modifier with measure(s) abgelehnt. Verwenden Sie die Beispiele für Filter auf feinerer Ebene.

Eine gefilterte Referenz auf eine atomare Kennzahl wird für sich genommen auf der aktuellen Abfrageebene ausgewertet. Geht es um Werte pro Entität, behalten Sie +d und eine explizite äußere Aggregation bei, insbesondere bei AVG, MIN, MAX und COUNT. Ein bedingtes SUM gibt NULL zurück, wenn keine Eingabezeile die Bedingung erfüllt. Ein explizites ELSE 0 hat eine andere Semantik. Beim Filtern der Eingabe können Gruppen erhalten bleiben, die nur ausgeschlossene Zeilen enthalten.

fn-Makros für Fensterfunktionen erzeugen rank() over (...) im kompilierten SQL. Verwenden Sie sie in Model Query SQL als AGG(measure, 'rank') oder AGG({measure: rank}). Die vollständige Liste und die Formeln finden Sie in system_macros.dml.

Filtermodifikator in .dml (Spalte als Ziel)

UmsatzAbgeschlossenerBestellungen:
    type: measure
    formula: "{Verkaufsbetrag: {+f: {Bestellstatus: 'completed'}}}"

Filtermodifikator in Model Query SQL

SELECT AGG(Umsatz, '+f', Region = 'North') FROM MODEL

Dimensionsmodifikatoren #

Modifikator Syntax Auswirkung
+d: dim {measure: {+d: dim}} Verfeinert die Auswertungsebene, indem das Dimensionsfeld dim an die Zieldimension für die Auswertung angehängt und die Kennzahl auf dieser Ebene ausgewertet wird. Das Ergebnis wird auf Abfrageebene nicht automatisch hochaggregiert. Dafür ist eine explizite äußere Aggregation erforderlich (SUM/AVG/…). Die Zieldimension ergibt sich aus GROUP BY der Abfrage und der Beschränkung dimensions: der Kennzahl. Pflichtfelder müssen enthalten sein. ... erlaubt zusätzliche Abfragefelder. Ohne Dimensionsmodifikator liegt eine Kennzahlreferenz bereits auf ihrer vorgesehenen Auswertungsebene. Wird sie in SUM() eingeschlossen, schlägt dies mit „cannot aggregate a measure w/o +d modifier“ fehl. +d ist für jedes Vorkommen von SUM({measure}) erforderlich, auch bei Kennzahlen ohne dimensions:-Deklaration.
-d: dim {measure: {-d: dim}} Entfernt das Dimensionsfeld dim aus der Auswertungsdimension der Kennzahl. Dadurch wird die Auswertungsebene gröber. Verwenden Sie die Listenform {-d: [dim1, dim2]}, um mehrere Felder zu entfernen. Die Form {-d: dim1, -d: dim2} führt in YAML zu Fehlern wegen doppelter Schlüssel. Wenn die Kennzahl eine abgeschlossene Menge zulässiger Dimensionen deklariert, muss eine davon die resultierende Auswertungs- beziehungsweise Abfragedimension zulassen. Ohne dimensions: an der Kennzahl ist jede kompatible Dimension zulässig. Abfragefilter unter filters: für das entfernte Feld werden weiterhin in die WHERE-Klausel des Datensatzes verschoben. Das kann die Nenner von Verhältniskennzahlen verfälschen (siehe unten unter Entfernen von Dimensionen und Filtern).
-df: dim {measure: {-df: dim}} Dieser Modifikator vereint die Wirkung von -d und -f. Er entfernt ein Dimensionsfeld aus der Auswertungsdimension (-d) und entfernt Filter auf diesem Feld aus der Kennzahlauswertung (-f). Abfragefilter unter filters:, die das entfernte Feld oder davon abhängige Spalten referenzieren, werden nicht in die WHERE-Klausel der Abfrage auf gröberer Ebene verschoben. Das gilt auch für Abhängigkeiten über pk()-Ketten. Verwenden Sie die Listenform {-df: [dim1, dim2]}. Der Modifikator entspricht DAX CALCULATE(expr, REMOVEFILTERS(dim)).
-f: name {measure: {-f: name}} Entfernt Filter mit Bezug auf name ausschließlich bei der Auswertung der Kennzahl. name kann ein Filtername (im Abfrageabschnitt filters: definiert) oder ein Spaltenname sein. Auch Abhängigkeiten über pk()-Ketten werden berücksichtigt. Verwenden Sie die Listenform {-f: [name1, name2]}. Die Gruppierung ändert sich nicht. Abfragefilter bestimmen weiterhin die Zeilenmenge des Berichts. Wenn die Spalte, auf die sich ein blockierter Filter bezieht, nicht zur Ausgabegranularität gehört, schränken Sie die Zeilenmenge ein (z. B. mit EXISTS), anstatt den Filter stillschweigend wegzulassen.
dimension: [dims] {measure: {dimension: [dim1, dim2]}} Ersetzt alle Auswertungsdimensionen durch die angegebenen Dimensionsfelder. Dataset-, Abfrage- und Materialisierungseigenschaften verwenden ebenfalls das Token dimension:. Hier ändert es jedoch eine einzelne Kennzahlreferenz, statt die Dataset-Identität, die Abfragegruppierung oder einen Materialisierungsschlüssel festzulegen. Die Semantik ähnelt -d, doch das erzeugte SQL verwendet einen separaten Aggregations-CTE statt eines Fensters mit OVER (PARTITION BY …). Siehe Stolperfallen P43. Verbinden Sie unterschiedliche Zeitebenen über den Kalender (z. B. {m:{dimension:[dt_quarter]}} in einer Abfrage auf Ebene dt_month) und übernehmen Sie die Summe der gröberen Ebene in jede zugehörige Zeile der feineren Ebene. Verwenden Sie dabei keinen einzelnen Gesamtsummenwert.

Kurzes Glossar zur eindeutigen Begriffswahl #

Schreibweise Bedeutung
{销量: {+d: 门店}} Auf der Ebene Abfragegranularität ∪ {门店} auswerten und auf dieser Ebene bleiben. Es erfolgt keine automatische Rückaggregation.
SUM({销量: {+d: 门店}}) (oder AVG/MAX/…) Zuerst entstehen Werte auf einer feineren Ebene. Danach führt die äußere Aggregation sie auf die aktuelle Abfrageebene zurück.
{销量: {-d: 门店}} Entfernt 门店 aus der Auswertungsebene. Filter auf 门店 können weiterhin in die zugrunde liegende Abfrage übernommen werden.
{销量: {-df: 门店}} Entfernt 门店 aus der Auswertungsebene und blockiert Filter mit Bezug auf 门店 für diese Kennzahl.
{销量: {-f: 门店}} Blockiert nur Filter mit Bezug auf 门店. Die Gruppierung bleibt unverändert.

Konflikte zwischen Modifikatoren für dasselbe Dimensionsfeld #

Die Sprachregeln verbieten, dass sich innerhalb desselben Modifikatorobjekts die Feldmengen von +d und -d oder von ersterem und -df überschneiden. Unterschiedliche Felder können gemeinsam angegeben werden, wie in SUM({销量: {+d: 门店, -d: 品牌}}). Seit der Korrektur vom 2026-11-15 weist der Compiler Konflikte für dasselbe Feld mit conflicting dimension modifiers +d and -d/-df for [fields] zurück. Dies wurde mit den Builds vom 2026-11-20 und 2026-11-23 geprüft. Siehe Kombination von Modifikatoren.

-df kombiniert -d und -f #

-df kombiniert die Wirkung zweier Modifikatoren:

  • -d (nicht danach gruppieren) entfernt ein Dimensionsfeld aus den Auswertungsdimensionen der Kennzahl. Dadurch wird auf einer gröberen Ebene aggregiert.
  • -f (Filter entfernen) entfernt Filter auf dieser Dimension aus der Kennzahlauswertung. Filter aus dem Abfrageabschnitt filters:, die auf die Dimension oder auf über pk()-Ketten davon abhängige Spalten verweisen, werden nicht in die WHERE-Klausel der Abfrage auf der gröberen Ebene übernommen.

-df ist die Kurzform von {-d: dim, -f: dim}. Beide Schreibweisen erzeugen beim Kompilieren identisches SQL. Verwenden Sie für die kürzere Schreibweise -df.

Verwenden Sie -df für Verhältniskennzahlen, wenn der Nenner sowohl die Gruppierung nach einer Dimension als auch die Filter darauf ignorieren muss.

Welches Problem wird gelöst? Ohne -df werden Filter aus dem Abfrageabschnitt filters: vor der Aggregation in die WHERE-Klausel des Datasets übernommen. Erzeugt -d eine temporäre Tabelle auf gröberer Ebene für den Nenner, beruht die Berechnung auf den gefilterten Ausgangsdaten. Dadurch fällt der Nenner kleiner aus. -df verhindert diese Filterweitergabe für die angegebene Dimension. Der Filter gilt nur für temporäre Tabellen, deren Granularität diese Dimension einschließt. In temporären Tabellen, aus deren Granularität die Dimension entfernt wurde, entfällt der Filter.

Wann eignet sich -df und wann -d?

Anwendungsfall Modifikator Begründung
Der Nenner muss alle Werte einer Dimension einbeziehen (z. B. Markenanteil = Umsatz der Marke / Gesamtumsatz aller Marken). -df Ein Filter auf brand_id würde den Nenner verkleinern, wenn er in die zugrunde liegende Abfrage übernommen würde.
Der Nenner soll die gefilterte Teilmenge widerspiegeln (z. B. der Anteil allein innerhalb der ausgewählten Marken). -d Der Filter auf brand_id soll sowohl für den Zähler als auch für den Nenner gelten.
Kein Filter auf dem entfernten Dimensionsfeld -d (oder das gleichwertige -df) Es gibt keinen Filter zu blockieren.

Beispiel: Markenanteil je Filiale. Der Zähler berücksichtigt die ausgewählten Marken, der Nenner alle Marken.

Markenumsatzanteil:
    type: measure
    formula: 'divide({Umsatz} * 100.0, {Umsatz: {-df: brand_id}})'

Auf der Abfrageebene [Filialnummer, brand_id] gilt ein Abfragefilter auf brand_id für den Zähler. Der Nenner lässt dieses Feld und seinen Filter weg und behält den Filialkontext bei.

Nachverfolgung von Abhängigkeiten. Der Compiler verfolgt Abhängigkeiten über pk()-Ketten. Ein Filter auf 客户标准名称 (pk({Filialnummer}).MDM_STORE(Filialnummer).Filialname) wird blockiert, wenn Filialnummer mit -df entfernt wird, weil die Spalte von Filialnummer abhängt.

       AGG({Umsatz: {dimension: [Kategorie]}}) as Kategoriesumme

{-d:} bei zusammengesetzten Kennzahlen mit FULL OUTER JOIN #

Unabhängige Kennzahl-Datasets werden üblicherweise auf aufeinander abgestimmten Auswertungsebenen zusammengeführt (Vereinigung der Schlüssel). Dazu wird der vollständige Gruppierungsschlüssel mit einem NULL-sicheren Gleichheitsvergleich abgeglichen. NULL-Werte an derselben Schlüsselposition werden einander zugeordnet, wenn die übrigen Dimensionen übereinstimmen. Auch dafür vorgesehene zeilenerhaltende Verknüpfungen mit LEFT JOIN und nullpk verwenden einen NULL-sicheren Gleichheitsvergleich. Welche Zeilen einbezogen werden, welche Schlüssel eindeutig sein müssen und wie fehlende Zeilen aufgefüllt werden, beschreiben Dataset-übergreifende Kombination und Gleichheitsvergleich mit NULL bei Joins.

Um die Zeilenmenge der Primärseite zu bestimmen, verwenden Sie eine Kennzahl ohne Auffüllung, die für jede tatsächlich vorhandene Gruppe der Primärseite garantiert einen Wert ungleich NULL und für fehlende Gruppen NULL liefert. Für die Zeilenmenge bei INNER muss die Gruppe auf beiden Seiten vorhanden sein. Eine beliebige fachliche Kennzahl kann für eine gültige Gruppe NULL liefern, und eine aufgefüllte Kennzahl kann für eine fehlende Gruppe einen Wert ungleich NULL liefern. Beide eignen sich daher nicht als zuverlässiger Nachweis, dass die Gruppe vorhanden ist. Arithmetik mit NULL allein entfernt keine Ausgabezeilen, die nur auf der Sekundärseite vorhanden sind.

Modifikatoren kombinieren #

In einer Referenz lassen sich mehrere Modifikatoren kombinieren. Dabei gelten die Regeln für Konflikte innerhalb derselben Dimension und die Einschränkungen für Modifikatoren:

# Filter + dimension (outer SUM rolls +d back to query grain)
formula: 'SUM({Umsatz: {+d: Kunde, +f: {Region: "North"}}})'

# Legal: +d and -d on DIFFERENT fields
formula: 'SUM({Umsatz: {+d: Kunde, -d: Marke}})'

# Rejected: the same field cannot appear in +d and -d or -df in one modifier object:
# formula: 'SUM({sales: {+d: store_id, -d: store_id}})'
# formula: '{sales: {+d: store_id, -df: store_id}}'

# Time + dimension
formula: '{Umsatz: {+d: Kunde}, yoy}'

# Dimension + rank
formula: '{Umsatz: {-d: dim_dt, rank}}'

# Dimension + filter removal (ratio with deferred filters)
formula: 'divide({Umsatz: {-df: brand_id}} * 100.0, {Umsatz: {-df: [Filialnummer, brand_id]}})'

# Filter + absolute grain (e.g., ratio numerator/denominator at different grains)
formula: 'DIVIDE({Umsatz: {+f: "Bestellstatus = 1", dimension: [Artikelnummer]}}, {Umsatz: {+f: "Bestellstatus = 1", dimension: [Artikelnummer, Filialnummer]}})'

In Model Query SQL:

SELECT Produkt,
       AGG({Umsatz: {-d: dt_date, rank}}) as RangÜberAlleJahre
FROM MODEL
WHERE dt_month = date(current_date, 'start of month')
GROUP BY Produkt

Modifikatoren verketten #

Mehrere Makros lassen sich in einem Ausdruck verketten. Der Compiler erstellt automatisch dieselben Zwischenkennzahlen, die Sie auch von Hand definieren würden.

Syntax: {measure: {macro1, macro2, macro3}} oder AGG(measure, 'macro1', 'macro2', 'macro3')

Bei einer gewöhnlichen Verkettung verändert das erste Makro die ursprüngliche Kennzahl. Das nächste Makro wird auf die so entstandene Zwischenkennzahl angewendet. Wenn Zeitmodifikatoren mit Funktionen kombiniert werden, die mehrere Zweige haben, wirken sie wie unten beschrieben auch auf deren Zweige. Das folgende Beispiel zeigt eine sequenzielle Verkettung.

# Stacking: yoy creates intermediate "sales_yoy", then rank applies to it
# Equivalent to:
#   sales_yoy:
#     type: measure
#     formula: '{sales: yoy}'
#   ...then: {sales_yoy: rank}
q_col: '{Umsatz: {yoy, rank}}'

Zeitmodifikatoren und Funktionen mit mehreren Berechnungspfaden: In der geprüften Version wendet der Compiler ytd sowohl im aktuellen Zweig als auch im Vergleichszweig von yoy an. Im protokollierten Test auf Monatsebene erzeugten {Umsatz: {yoy, ytd}} und {Umsatz: {ytd, yoy}} identisches SQL. Der YTD-Umsatz wird durch den YTD-Umsatz des Vorjahres geteilt. Anschließend wird eins abgezogen. Die monatlichen Wachstumsraten werden dabei nicht addiert. Sortieren Sie Modifikatoren nicht nach Kategorie und leiten Sie nicht allein aus den generierten Namen der Zwischenkennzahlen eine andere Bedeutung ab.

Makros wie firstday ändern die Ebene, auf der Zeilen oder Summen definiert sind. Für sie gelten bei mehreren Berechnungspfaden zusätzliche Einschränkungen. Kompilieren Sie genau die gewünschte Kombination und prüfen Sie das Ergebnis, bevor Sie sich darauf verlassen. Setzen Sie selbst geschriebene +f-Ausdrücke mit YAML-Indikatoren in Anführungszeichen, wie in {Umsatz: {+f: "Verkaufsbetrag > 5", yoy}}.

Zwischenkennzahlen wiederverwenden. Bevor der Compiler eine neue Zwischenkennzahl erstellt, sucht er unter den vorhandenen Kennzahlen nach derselben Formel. Dabei berücksichtigt er die ausgeschriebene Formel, die Kurzschreibweise und die Map-Form. Findet er eine passende benutzerdefinierte oder zuvor generierte Kennzahl, verwendet er sie erneut. So entstehen keine überflüssigen Zwischenkennzahlen, und Sie können deren Namen gezielt festlegen.

Namenskonflikte behandeln. Wenn der automatisch generierte Name einer Zwischenkennzahl (z. B. UmsatzZumVorjahr) mit dem Namen einer vorhandenen Kennzahl übereinstimmt, die eine andere Formel hat, hängt der Compiler ein numerisches Suffix an, etwa sales_yoy__2 oder sales_yoy__3.

Kompatibilität: Ob eine Verkettung gültig ist, hängt von den Voraussetzungen der Makros, dem Zeitkontext, den zulässigen Dimensionen, doppelten Schlüsseln und der erneuten Aggregation ab. Kompilieren Sie genau diese Verkettung mit der Zielversion. Zwei Bereichsmakros oder wiederholte Makroschlüssel lassen sich nicht als allgemeines Mittel zur Verkettung verwenden. Wenn nach der expliziten Angabe der einzelnen Schritte weiterhin ein Fehler auftritt, bewahren Sie die Diagnosemeldung und das reproduzierbare Beispiel auf. Eine manuell benannte Zwischenkennzahl belegt für sich allein keine Gleichwertigkeit.

Modifikatoren im Überblick #

Modifikatoren wirken sich nur auf die jeweilige Kennzahlreferenz aus. Mit {Umsatz: {+f: {Bestellstatus: completed}}} schränken Sie die Eingabedaten der Kennzahl ein. Mit +d fügen Sie der Berechnung eine Gruppierung hinzu. Eine äußere Aggregation führt das Ergebnis anschließend auf die Gruppierung des Berichts zurück. Mit -d entfernen Sie eine Gruppierungsdimension. Mit -df entfernen Sie zugleich die zugehörigen Filter auf dieser Dimension. Der Zeitmodifikator pp liefert den Wert der Vorperiode, pop berechnet die relative Veränderung gegenüber der Vorperiode und ytd berechnet den kumulierten Wert seit Jahresbeginn. Mehrere Modifikatoren werden in der angegebenen Reihenfolge angewendet.

Zeitmodifikatoren für zusammengesetzte Verhältniskennzahlen #

Ein Zeitmodifikator lässt sich direkt auf eine benannte zusammengesetzte Kennzahl anwenden. Definieren Sie beispielsweise BruttomargeSeitJahresbeginn mit formula: '{Bruttomarge: ytd}'. Dabei teilt Bruttomarge den Bruttogewinn durch den Umsatz. Im kumulierten Zeitkontext werden zuerst die zugrunde liegenden Kennzahlen und anschließend das Verhältnis neu berechnet. Die Monatsprozentsätze werden nicht addiert. Siehe das vollständige Beispiel zur Profitabilität. Dieses geprüfte Beispiel belegt nicht, dass sich beliebige nicht additive Formeln ohne Prüfung ihrer Semantik auf einer höheren Ebene aggregieren lassen.

Summen mit festen Achsen und Auswahl der Ausgabezeilen #

Das Beispiel mit fester Summe verwendet das Datumsfeld dt_month und eine Abfrage, die nach Region und Monat gruppiert. Wenn Januar ausgewählt ist, bleibt der Nenner mit -d: dt_month auf Januar beschränkt, während -df: dt_month beide Monate der Testdaten einbezieht. Beide Abfragen geben weiterhin ausschließlich Zeilen für Januar aus. Aus diesen Testdaten lassen sich keine Aussagen über dynamische Pivot-Achsen, Prädikate auf Zwischensummenebene oder das Entfernen von dim_dt in beliebigen Fällen ableiten.
