このページでは、SQLクエリの構文、モデルの検索、エイリアス、グループ化、出力のルールを説明します。YAMLでのクエリ宣言では、type: queryについて説明します。最初のクエリをコンパイルするでは、チュートリアルで一連の手順を説明します。

クエリを記述する2つの方法 #

構文 形式 利用場面
Model Query SQL .sql ファイルまたはインライン文字列 SQLに慣れたユーザー、CLI、ダッシュボード
DML形式 .dml の YAML 内の type: query YAMLを標準で使う環境、dmlc --to-dml の出力

クエリの種類 #

集計クエリ #

FROM … を使用し、AGG() で少なくとも1つの指標を指定します。

FROM の後に指定するのは、拡張子 .dml を除いたモデルファイル名です。大文字と小文字は区別されません。大半のチュートリアルでは、慣例に従い FROM MODEL ↔ model.dml の組み合わせを使います。

モデルファイル SQL での記述
model.dml FROM MODEL
acme.dml FROM acme
渠道表现模型.dml FROM 渠道表现模型

クエリ、コンパイル、検証のみの場合に、--model= がこの名前の解決にどう影響するかを示します。

渡す値 動作
--model=some/dir dmlc はそのディレクトリ内で <FROM>.dml を探します（FROM MODEL → dir/model.dml、FROM acme → dir/acme.dml）。
--model=acme.dml そのファイルがモデルになります。SQL には FROM acme と記述する必要があります（FROM MODEL は使えません）。
省略 SQL ファイルと同じディレクトリ、またはモデル検索パスで同じ方法で探します。

FROM 句には拡張子 .dml を付けないでください。queries/ 配下にディレクトリが入れ子になっている場合は、.dml ファイルを SQL ファイルと同じディレクトリに置くか、--model= でモデルファイルがあるディレクトリを指定します。

setup（dmlc -s）には.dml ファイルを渡します。ディレクトリは指定できません。

-- Query SQL using model.dml
SELECT product, dt_month, AGG(sales)
FROM MODEL
WHERE dt_month = date(current_date, 'start of month', '-1 month')
GROUP BY product, dt_month

-- Query SQL using acme.dml (dmlc --model=acme.dml …  or  --model=<dir containing acme.dml>)
SELECT product, dt_month, AGG(sales)
FROM acme
GROUP BY product, dt_month

IDE でモデルがピン留めされている場合、ナビゲーション機能が FROM MODEL をそのモデルへの参照として扱うことがあります。CLI では、FROM の後の名前を、使用するファイルまたは --model=<dir> 配下で見つかる .dml ファイルに合わせます。

明細クエリ #

データセットの行を取得するには FROM <model>.<dataset> を使います。GROUP BY を直接指定すると拒否されます。グループごとの指標を取得するには、再利用可能な指標を定義し、モデルにクエリを実行します。モデルの集計クエリでは AGG() を使います。

-- Query SQL using model.dml
SELECT dt_date, transaction_id, raw_amount
FROM MODEL.transactions
WHERE dt_month = date(current_date, 'start of month')

-- Query SQL using acme.dml
SELECT ClaimNumber, ClaimOpenDate
FROM acme.Claim

明細クエリはデータセットの行を返します。検査対象の式のうち、グループ化を伴わない集計式とウィンドウ式も使用できます。GROUP BY を直接指定すると拒否されます。集計クエリは、再利用可能なモデルの指標を指定されたグループ化の粒度で返します。

モデルクエリのSQL仕様 #

基本的な制約 #

使用不可 理由 代替方法
サブクエリ モデルクエリのSQLでは未対応 指標を使って計算をモデル化するか、データセットの sql: でリレーションを用意します。
UNION / UNION ALL モデルクエリのSQLでは未対応 データセットの sql: またはデータベースのビューで、UNION によるリレーションを用意します。
JOIN モデルクエリのSQLでは未対応 pk(...) を使って属性の参照をモデル化するか、データセットの sql: でリレーションを用意します。
列名に直接付ける {...} 波かっこは .dml 専用です。ここで使うと通知なしで取り除かれます。 SELECT product, AGG(sales) のように、名前をそのまま指定します。

利用側のクエリに適用されるこれらの制約は、DML 全体で SQL の使用を禁止するものではありません。データセットの sql: では、サポートされている結合、UNION、サブクエリを使ってリレーションを用意できます。宣言済みのデータセットは {DATASET} として参照し、物理テーブルの所有関係に従ってください。そのリレーションには正しいキーを明示する必要があります。データセットリファレンスでは、検査対象となる派生リレーションの検証方法を説明します。データセットの SQL に組み込んだフィルターは、引き続きデータセットに含まれる行を決める条件になります。SQL をモデルに移しても、すべてのルールが利用側のコンテキストに自動で対応するわけではありません。データセット定義を参照してください。

モデルクエリの SQL では、ウィンドウ関数（OVER()）を使用できます。コンパイラーはウィンドウ関数を変更せず、生成する SQL に含めます。よく使うパターンでは、system_macros.dml の関数マクロ（rank、rank_asc、pot、grand）を優先してください。詳しくは関数修飾子を参照してください。.dml モデルのどこに OVER を記述するか（ウィンドウ関数の配置）については、ウィンドウ関数の配置を参照してください。

SELECT のルール #

  • 集計では、すべての指標に AGG(measure) を使います。ディメンションは名前をそのまま指定します。
  • 明細では、すべての列を名前で直接指定します。重複のない値の一覧を取得するには DISTINCT を追加します。
-- Aggregation
SELECT product, dt_month, AGG(sales), AGG({sales: yoy}) AS sales_yoy FROM MODEL GROUP BY product, dt_month

-- Detail
SELECT DISTINCT product FROM MODEL.transactions

エイリアスのルール #

パターン エイリアスは必要か
AGG(sales) 不要です。自動で sales がエイリアスになります。
AGG(sales) AS sales 使用できますが冗長です（そのまま出力されます）。
AGG({sales: yoy}) 必要です。AS sales_yoy を使います。
AGG(sales, 'pop') AS sales 誤りです。循環参照になるため、AS sales_mom を使います。
AGG({sales: yoy}) AS sales 誤りです。循環参照になるため、AS sales_yoy を使います。

選択リストの前の項目で定義したエイリアスは、指標ではなくSQL の結果列を表します。AGG(sales) AS current_value の後に AGG(current_value) と記述する場合のように、後続の式でその名前を使うと、先に定義した結果列が参照されます。無関係な同名の DML 指標に解決されることはありません。

修飾子付きの指標参照に、その指標自体の名前をエイリアスとして付けると（例 AGG(sales, 'pop') AS sales）、コンパイラーがエイリアスを指標の再定義として扱うため、循環参照になります。AS sales_mom のように別の名前を使います。修飾子のない AGG(sales) AS sales は冗長ですが、値をそのまま返す指定として受け付けられます。

AGG の第1引数には指標名を指定します。通常の値を取得するには AGG(sales) を、この参照を修飾するには AGG({sales: yoy}) を使います。モデルクエリの SQL では、それ以外の箇所で列名をそのまま指定します。

WHERE のルール #

  • WHERE customer = 'John Doe' のように、列名をそのまま指定します。
  • 述語の順序に構文上の制約はありません。
  • 期間の初日を指定する形式で時間フィルターを記述します。例 dt_month = '2024-01-01'。
  • 単一期間の指定には、BETWEEN よりも = を優先します。
  • 明示的に求められた場合を除き、冗長な NULL フィルターは追加しないでください。

GROUP BY のルール #

  • SELECT の非集計フィールドは、すべて GROUP BY に含める必要があります。
  • 出力順序が重要な場合は、GROUP BY のフィールド順を SELECT に合わせます。確認済みのコンパイラーでは異なる順序も受け付けますが、表示される列の順序が変わることがあります。artifacts.sql と effectiveOutputOrder を確認してください。
  • 時間修飾子には、解決済みの時間コンテキストが必要です。グループ化に使う時間フィールド、または時間フィルターでそのコンテキストを指定できます。複数期間のレポートでは、時間で明示的にグループ化する方法を優先してください。単一期間に絞るフィルターで、出力に現れない時間コンテキストを指定することもできます。
-- Correct: time modifier + matching time field in GROUP BY
SELECT dt_month, AGG(sales), AGG({sales: yoy}) AS sales_yoy
FROM MODEL
GROUP BY dt_month

-- Wrong: yoy with neither a grouped time field nor a time filter
SELECT product, AGG(sales), AGG({sales: yoy}) FROM MODEL GROUP BY product

ORDER BY / LIMIT #

  • 必ず ASC/DESC を指定する
  • 結果の意味に関わる場合にのみ追加する（上位 N 件、極値）
  • あると便利というだけの理由で並べ替えを追加しない。

指標の参照ルール #

  • クエリでは AGG(measure) のように、指標を必ず AGG() で囲みます。
  • 修飾子を使う形式: AGG({measure: modifier}) または AGG(measure, 'modifier')
  • Model Query SQL では、AGG 内で修飾子を使う形式を除き、列名を {...} で囲まないでください。列名を囲む波括弧は通知なしに取り除かれ、列名だけが残ります。列名はそのまま指定してください。
  • コンパイラが use existing measure "X" と表示したら、AGG(X) を使ってください。式を書き直さないでください。

時刻・日付の扱い #

フィールド名: dt_date、dt_week、dt_month、dt_quarter、dt_year。いずれも該当する期間の初日を表します。

システムによる派生: モデルで dt_date などの細かい粒度の標準時間フィールドを明示的に宣言すると、dt_month など、サポート対象の粗い粒度のフィールドが同じデータセットで自動的に使えるようになります。派生フィールドの名前をそのまま使ってください。クエリやフィルターの要件を満たすためだけに、またはエディターの診断を解消するためだけに、重複する物理列を追加しないでください。派生フィールド名から定義に移動すると、明示的に宣言された派生元の時間列が開きます。

フィルタリング: WHERE dt_month = '2024-01-01'（期間の初日を指定し、単一期間には BETWEEN ではなく = を使います）。

日付関数リファレンスでは、SQLite 形式の式を説明しています。コンパイラは、サポート対象の式を選択した方言に変換します。

dt_year と dt_month の両方を指定した検証対象のクエリは、生成された出力に dt_year がないため、コンパイル時に拒否されます。この組み合わせで 2 フィールドのレポートが正常に作成できるとは見なさないでください。年が表示ラベルとしてのみ必要な場合は、必要な月単位でクエリを実行し、その後で月のキーからラベルを生成してください。結果の各行がどの単位で定義されているかは別途確認してください。この結果から、複数の時間フィールドを含むすべてのクエリがサポート対象外だとは判断できません。

HAVING #

-- Customers with outstanding balance
SELECT customer, AGG(outstanding)
FROM MODEL
GROUP BY customer
HAVING AGG(outstanding) > 0

-- Products selling less than last month
SELECT product, AGG(sales) as this_month, AGG(sales, 'pp') as last_month
FROM MODEL
WHERE dt_month = date(current_date, 'start of month')
GROUP BY product
HAVING AGG(sales) < AGG(sales, 'pp')

指標をディメンションとして使う場合の注意: 分類ラベル、またはラベルと同じ粒度の別の指標、あるいはその両方に対する述語は、ラベル生成後のフィルターです。Model Query の記述には HAVING が現れることがありますが、意味上、フィルターはラベルが生成された後に適用されます。コンパイルされた SQL では、多くの場合、ラベル生成後の CTE に対する WHERE として適用されます。ドキュメントに HAVING と記載されていても、分類前にフィルタリングできると解釈しないでください。分類ラベルのフィルターを参照してください。

集計の早見表 #

Model Query SQL（FROM MODEL）では、すべての集計を、model.dml またはインラインの /** dml ... **/ ブロック（インライン指標）で定義した指標を使って行う必要があります。元の列を直接集計するクエリは拒否されます。

目的 誤り（失敗する） 正しい書き方
総行数 COUNT(*) 笔数: COUNT({ID}) を model.dml またはインラインで定義してから、AGG(笔数) を使う
元の列の合計 SUM(出厂价金额) 销售额: SUM({出厂价金额}) を model.dml またはインラインで定義してから、AGG(销售额) を使う
元の列の平均 AVG(销售数量) 均价: DIVIDE(SUM({出厂价金额}), NULLIF(SUM({销售数量}),0)) を model.dml またはインラインで定義してから、AGG(均价) を使う
ディメンションのスカラー MIN/MAX SELECT MIN(dt_month) FROM MODEL 明細データセットを使う: SELECT MIN(dt_month) FROM MODEL.<dataset>
行数でグループを絞り込む HAVING COUNT(*) > 100 行数: COUNT({ID}) を model.dml またはインラインで定義してから、HAVING AGG(行数) > 100 を使う

唯一の例外は、明細データセット（FROM MODEL.<dataset>）に対して、メタデータを調べる目的で行うスカラー集計です。この例外は、ビジネス指標のダッシュボードには適用されません。

インライン指標（/** dml ... **/） #

.dml ファイルを編集せずに、Model Query SQL 内で一時的な指標を直接定義できます。コンパイラは、FROM で指定された .dml ファイル（FROM MODEL → model.dml、FROM acme → acme.dml）を読み込み、インライン定義を統合してからクエリをコンパイルします。

/** dml
temp_sales:
    type: measure
    dataset: transactions
    formula: SUM({amount})
**/
SELECT product, AGG(temp_sales) FROM MODEL GROUP BY product

試算の業務上の意味が関係者間で定まったら、同じ式を固定の名前で .dml モデルに移してください。利用者は式を繰り返し記述せずに、引き続きその指標を名前で参照できます。複数の要素から算出する利益率は、DIVIDE({net_revenue} - {sales_cost}, {net_revenue}) としてインラインまたはモデル内で定義できます。その指標に ytd を適用すると、累計対象の範囲で各要素が再計算されます。表示された月次比率の平均は取りません。

使用例:

  • .dml を変更せずにその場で集計する（指標を使う要件を満たす）
  • +d と dimensions を使った複数レベルの集計。中間指標はインラインで定義する。
  • RFM 分析: 顧客単位の指標をインラインで定義し、rank 関数マクロを使ってクエリを記述する。

ルール:

  • 複数行の YAML 形式を使うこと（1 行につき 1 プロパティ）
  • インライン指標からは、.dml の既存の指標やデータセットを参照できます
  • インライン指標からは、同じブロック内で先に定義した他のインライン指標を参照できます
  • .dml の指標定義と同じ構文（type、formula、dataset、dimensions）

クエリのフィルターと指標の意味 #

Model Query SQL の WHERE 句に記述する .dml の指標定義に記述する
クエリの行と同じ粒度で定義されたチャネル、地域、データ品質フラグ コホートの基準点、エンティティを対象に含める条件
クエリの行と同じ粒度での時間範囲（dt_period、dt_month） 顧客単位で定義する期間横断のフラグ

JDBC パラメーターとクエリの種類 #

検証対象の JDBC ディストリビューションでは、物理 SQL と Model Query の両方で位置パラメーター ? をバインドできます。タスクのテスト用データでは、フィルターと指標の式にそれぞれ 2 をバインドすると、どちらのクエリ形式でも、フィルターでは 20、指標の式では 60 が返りました。再現手順はタスクのサンプルプロジェクトに含まれています。

マテリアライズ用のパラメータと、内部でのリテラルのパラメータ化は別の仕組みです。アプリケーションからの入力は、呼び出し側でパラメータにバインドしてください。信頼できない値を文字列連結で SQL に組み込まないでください。

時間フィルターは同じクエリ内の他の指標にも適用される #

クエリレベルの月フィルターは、YTD 指標の基準時点を指定できます。このフィルターは、同じクエリ内の通常の指標にも適用されます。単一の KPI を使う例では、2 月の YTD マージンには 1 月と 2 月のデータが使われますが、通常の売上高には 2 月のデータだけが使われます。基準時点のないクエリは失敗します。カレンダー上の期間でグループ化したクエリでは、累計値はあるものの、その月の売上高がない月が結果に含まれることがあります。どの行を出力するかと、どのデータを指標の計算に使うかは別の問題です。今日の日付やファクトデータの最新日付を暗黙に基準時点として選択しないでください。

Model Query SQL クイックリファレンス #

FROM MODEL は model.dml をバインドします。AGG(sales) で指標を参照し、GROUP BY region で地域ごとに 1 行を出力するよう指定します。WHERE でクエリの対象範囲を限定し、HAVING AGG(sales) > 0 で集計後のグループを絞り込みます。出力列名は AS で指定します。
