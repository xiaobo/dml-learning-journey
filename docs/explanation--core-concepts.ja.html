レポートは、業務上の定義と、グループ化、フィルター、表示方法の指定を組み合わせます。DMLでは再利用できる定義をモデルに保持します。行や集計値を定義するレベル（粒度）が互いに適合していれば、複数のレポートで同じ指標を使用できます。

指標はほかの指標を参照できます。各参照の評価方法は分析コンテキストによって決まります。たとえば、同じ利益率の定義を地域別レポートと年初来のKPIで使用できます。時間変換では、月ごとの利益率を平均するのではなく、利益と売上高を再計算してから除算します。異なるデータセットの指標も、行や集計値の粒度に互換性があれば組み合わせられます。その際、出力キーと、片側にしかデータがないグループが、レポートの想定する対象範囲に合っている必要があります。収益性の例では、指標の組み合わせ、累積、比較を通じてこの仕組みを説明します。DMLモデル、DMX式、コンパイラは、分析用セマンティックレイヤーの計算の中核を担うことができます。業務上の定義は、引き続き関係者が合意して決めます。

図解付きのDML入門ガイドでは、4 件の売上例とグループ化を試せるツールを使って、これらの概念を紹介します。

実行可能な完全な例については、初めてのモデルクエリをコンパイルするを参照してください。言語の規則はDMLのコア仕様で定義されています。

1. モデル、クエリ、式の各レイヤー #

レイヤー 言語 内容 記述場所
モデル DML（Dato Measure Language） データセット、指標、列マクロ .dml YAML
クエリ Model Query 指標の選択、グループ化、レポートのフィルター .sql、または type: query を指定した DML
式 DMX（Dato Measure eXpression） 数式、参照、修飾子 モデルの数式とクエリの式

DMLは、モデルファイルを処理し、データベースが実行するSQLを生成する独立したセマンティックレイヤーのコンパイラです。アクセスはデータベースの権限とアプリケーションの認可で制御します。ダッシュボードとスケジュール管理は周辺システムが担います。モデルのフィルターだけでは、アクセス制御ポリシーにはなりません。

DMLは、宣言の構造と、粒度や時間コンテキストなどの分析上の互換性を検査します。SQL式の静的型チェックは完全には行いません。物理的な値の型はデータベースが扱い、検証に使うモデルスキーマは列の type: 宣言を受け付けません。そのため、型変換や関数の引数に誤りがあってもコンパイルを通過し、データベースでの実行時にエラーになることがあります。列のメタデータと値の型を参照してください。

データセットは、列を物理テーブルまたはSQLリレーションに結び付けます。dimension: には、ソース行の完全キーを宣言します。

取引明細:
  type: dataset
  table: fact_transactions
  dimension: [取引番号]
  columns:
    取引番号:
      abbr: transaction_id
    売上金額:
      abbr: amount
    割引額:
      abbr: discount
    純額: 売上金額 - 割引額
  measures:
    売上高: SUM({純額})
    取引件数: COUNT(1)

平均取引額:
  type: measure
  formula: 'DIVIDE({売上高}, {取引件数})'

売上高と取引件数はアトミック指標です。定義を含むデータセットを継承し、ほかの指標を参照せずに、そのデータセットの行または列式を直接集計します。どちらのアトミック指標も取引明細を使用していますが、平均取引額は数式でほかの指標を参照するため、複合指標です。複合指標には dataset: プロパティがありません。

モデルの数式では、波括弧のない売上金額は物理SQL列を指します。{純額}は、モデルの計算列の式に展開されます。論理名と物理名が一致する場合も、波括弧で両者を区別できます。

列マクロは、再利用できる列式や、別のデータセットを参照するルックアップを定義します。指標を使用するクエリごとに結合を書くことなく、指標から属性を利用できます。ルックアップの引数は、参照先データセットの完全キーで決まります。ソースリレーションとルックアップを参照してください。

Model Query では、AGG(...) を使って指標を参照します。モデルの数式では、SUM や COUNT などの集計関数を直接使用します。AGG はクエリから指標を参照するためのインターフェースであり、モデルの数式内の SUM を置き換えるものではありません。

一時的に使う指標は、まずクエリファイル内のインラインDMLブロックに定義できます。試す前に共有モデルを変更する必要はありません。有用な定義を共有指標に昇格させる前に、その内容を確認してください。

2. ソースリレーション、ルックアップ、指標の組み合わせ #

DMLは、処理のさまざまな段階でデータを組み合わせます。確認すべきキー、フィルター、対象行の範囲は、どの段階で組み合わせるかによって決まります。

目的 仕組み 結果の規則
完全キーを使って属性を再利用する モデルの数式内で pk(...) を使うルックアップ ルックアップキーごとに参照先の行は 1 件です。単一列のキーと複合キーを使用できます。
イベントの日付に有効な属性を取得する [売上明細番号, 'range(valid_from, valid_to)'] を対象とする pk(売上明細番号, dt_date) 検証対象の有限区間は [start,end) に従います。同じ id の区間どうしが重なってはいけません。
売上や予算など、独立したファクトを比較する ディメンションをそろえて評価する指標 キーの和集合を使う通常の組み合わせでは、少なくとも一方に存在するグループをすべて保持します。片側にしか存在しないグループでは、もう一方の値は欠損したままになります。
ブリッジ、結合、和集合、サブクエリのリレーションを用意する データセットの sql: またはデータベースビュー 用意したリレーションには、そのリレーション自体の完全キーが必要です。1 件のソース行が複数の行に一致し得る場合は、配分の重みを定義し、合計値を確認してください。

モデルを利用する Model Query の SQL では、JOIN、UNION、サブクエリを直接記述できません。この制約があっても、サポートされているリレーションはデータセットの SQL で準備できます。ソース SQL に組み込んだフィルターは、ソースリレーションの対象行を引き続き絞り込みます。利用側のコンテキストごとに動作が変わるルールには自動的にはなりません。

複合キーによるルックアップや、指定した日付に有効な値を取得するルックアップをサポートしていても、任意の経路を選べる汎用的な関係グラフや、多対多の自動配分までサポートしているとは限りません。指標を独立して集計しても、ルックアップキーの重複や誤った対応付けの規則は解消されません。複合キーによるルックアップと指定日に有効な値のルックアップの例では、完全なモデル、意図的に起こしたキーのエラー、その修正方法を確認できます。片側にしか存在しないグループと NULL キーの扱いについては、指標の組み合わせの規則を参照してください。ソースの所有関係と派生リレーションの検証については、データセットの SQLを参照してください。

3. ディメンションの役割と粒度 #

ディメンションフィールドは、名前付きの DML フィールド1つを指します。ディメンションはフィールドのリストです。ディメンションの役割は、宣言する場所によって決まります。

宣言 意味
データセットの dimension: ソース行を完全に識別する情報
数式のディメンション修飾子 1つの指標参照を評価するディメンション
クエリの GROUP BY または columns.dimension 結果のグループ化
マテリアライズの dimension: 保存時のグループ化の単位とキー
指標の dimensions: 評価ディメンションとして使用できる候補。各内側のリストが1つの候補を表します。

粒度は、あるコンテキストで1行が何を表すかを示します。たとえば、[取引番号] はトランザクションを識別し、[地域, dt_month] はレポートを地域と月でグループ化します。レポートの1つのグループには多数のソース行が含まれることがあるため、グループでソースキーを置き換えることはできません。

修飾子 dimension: [] は、総計を求めるために評価ディメンションを空にします。この修飾子は、データセットの行を識別するキーを宣言するものではありません。+d は中間計算用のフィールドを追加します。数式でより粗い粒度の結果が必要な場合は、外側に明示した集計で中間値をまとめます。

コンパイラは、宣言されたソースキーが正しいことを前提とします。pk(...) の参照先に同じキー値を持つ行が複数あると、コンパイルに成功しても行が増えることがあります。実データでの検証では、実際に存在するキー値が一意かどうかを確認します。結果の比較では、クエリが意図した答えを返すかどうかを確認します。

ディメンションの意味では、これらの役割とその影響を詳しく説明します。

4. 時間コンテキストと dim_dt #

dim_dt は、指標のクエリコンテキストで有効な時間フィールドを表します。数式では、dt_date、dt_month、dt_quarter を直接指定せずに、現在の時間粒度を参照できます。マクロが受け付ける粒度は、引き続きそのマクロの前提条件によって制限されます。

グループ化に使う時間フィールド、または時間フィルターがコンテキストを提供できます。厳格モードの診断メッセージと生成された結合は、構文が受理されるかどうかとは別に確認してください。期間比較やキーの和集合を使った結合があるだけで、厳格モードの警告が出るとは限りません。

dt_date のような細かい粒度の標準時間フィールドを宣言すると、システムカレンダーを通じて、サポートされるより粗い粒度の時間フィールドを使用できます。これらの仮想フィールドを物理フィールドとして重ねて宣言する必要はありません。派生した dt_month からエディターで定義に移動すると、明示的に宣言されたソースの時間列に移動します。

単一の KPI でも、集計対象期間の終了時点を明示する必要があります。実行可能な例では、2月で絞り込むと、1月と2月を対象とする YTD の利益率は 20% になります。一方、同じクエリ内の通常の売上高は2月分のみです。時間コンテキストがない場合、クエリは失敗します。カレンダーを使ってグループ化するクエリでは、累計値があり、当月の売上高が NULL の月も返ることがあります。出力する期間は目的に合わせて選んでください。クエリを実行する接続で、カレンダーが対象の日付をカバーしている必要があります。

時間コンテキストの仕様では、dim_dt と標準時間フィールドを定義しています。システムマクロでは、時間マクロと数式マクロの定義を参照できます。

5. 再利用と連携 #

カスタムの fn-macro 定義は呼び出し元の指標の数式を包み、dt-macro 定義はその数式の時間コンテキストを変更します。どちらも、コンパイラを変更せずに修飾子の構文で組み合わせられます。データベースのスカラー関数呼び出しでは、実行に使う接続にインストールされている関数を再利用します。拡張ガイドでは、実際に実行した例と、関数が存在しないために失敗する例を紹介します。これらの仕組みは、汎用のモジュールシステムや、あらゆる種類の UDF を環境間で利用できるようにする移植性を提供するものではありません。

モデルの SQL 方言を明示的に設定してください。方言が認識されても、そのデータベースエンジンですべての機能が正常に実行されたことの証明にはなりません。生成された SQL には、複数のステートメント、中間リレーション、カレンダーへの依存関係が含まれることがあるため、実行環境も確認してください。

動作を確認した JDBC ドライバーは、物理 SQL で位置パラメーターをバインドします。Model Query では、フィルターと指標式で位置パラメーターをバインドします。JDBC パラメーターの例を参照してください。マテリアライズ用パラメーターと、リテラルを内部でパラメーター化する処理は、それぞれ別の仕組みです。

コンパイル、検証、実行では、それぞれ確認できることが異なります。実データでキーを検証すると、ルックアップで行が増える前に重複を検出できる場合があります。ただし、検証とその後の実行で同じスナップショットが使われる保証はありません。データベースが EXPLAIN を受理しても、返される数値が正しいことの証明にはなりません。対象のデータ範囲について、各キーを構成するすべての値、各行の出現回数、NULL、丸め前の値を、独立に求めた結果と比較してください。

期間比較と結果に含まれる行 #

前の期間を処理するクエリ分岐では、カレンダーを使って、当月のファクトデータがない月にも前の期間のグループを含めることができます。そのグループがレポートに含まれるかどうかは、クエリの時間範囲と、現在の期間にデータがあるグループに絞り込むフィルターによって決まります。期間比較で追加される月を参照してください。
