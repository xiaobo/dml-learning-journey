分析を作成する

この手順では、再利用可能なメジャーと、それらを使用するクエリを追加します。初めてコンパイルする場合は、最初のモデルクエリをコンパイルするの手順に従ってください。構文はモデルクエリを参照してください。

フェーズ 1：必要な結果を定義する #

SQLを書く前に、レポートの要件を記録します。

  1. 結果に元データの行が必要か、グループごとに集計したメジャーが必要かを判断します。
  2. 結果の各行を識別するフィールドを列挙します。
  3. 対象期間、比較期間、レポートのフィルターを明記します。
  4. レポートのフィルターと、業務上のメジャーを定義する条件を区別します。
  5. 元データの対象範囲、NULLの扱い、必要な出力列を記録します。
  6. 結論を左右し得る前提を列挙します。

モデリングの前と実行の後に、業務上の前提を確認します。元データの対象範囲、レポートの対象期間、欠損値、分母を含めて確認してください。

フェーズ 2：メジャーを使用するクエリの下書きを作成する #

メジャーを追加する前に、予定している SELECT、WHERE、GROUP BY を記述します。可能な限り既存の業務用語を名前に使います。

SELECT
	dt_month,
	渠道,
	AGG(销售额),
	AGG({销售额: yoy}) AS 销售额_yoy,
	AGG(同店销售额)
FROM MODEL
WHERE dt_month = '2025-03-01'
GROUP BY dt_month, 渠道

レポートのグループ化、時間ウィンドウ、チャネルによる絞り込みはクエリに記述します。既存店比較の対象条件など、再利用可能な定義はモデルに記述します。必要な結果が並び順や行数の上限に依存する場合は、並べ替えや行数制限を追加します。述語の順序は、文法上受け付けられるかどうかに影響しません。

修飾子付きのメジャー参照ごとに、異なるエイリアスを使用します。生成された出力列を確認してください。コンパイラが列の順序を変更することがあります。また、既知の不具合があるクエリ形式では、指定した時間フィールドが省略されることがあります。

フェーズ 3：不足しているメジャー定義を見つける #

下書き内の AGG(...) ごとに、対象モデルを確認します。

  1. メジャーの定義が必要な指標と一致する場合は、そのメジャーを再利用します。
  2. 似たメジャーでも意味が異なる場合は、その違いが名前と説明から分かるようにします。
  3. 下書きのクエリに再利用可能な業務定義が必要な場合は、メジャーを追加します。
  4. レポート専用の絞り込みは、その絞り込み自体が指標を定義する場合を除き、クエリに記述します。

依存関係を基礎となるメジャーまでたどります。既存店比較の指標では、顧客・月ごとの金額、顧客・月ごとの対象可否の計算、外側の集計などが依存関係に含まれる場合があります。

フェーズ 4：モデルを拡張する #

読みやすくなる場合は、依存先を参照元より先に定義します。確認済みのケースでは、同じファイル内で後に定義される要素を参照できます。

  1. 各データセットで、元データの行を一意に識別するフィールドをすべて宣言します。
  2. データセットの列から基礎となるメジャーを定義します。
  3. 業務上の計算に特定の評価ディメンションが必要な場合は、メジャーに dimensions: を追加します。
  4. より細かい評価ディメンションが必要な参照に +d を追加します。
  5. 明示的な外側の集計を使って中間値をまとめます。
  6. 必要な構成要素を使って複合比率を定義します。
  7. 対象範囲、粒度（行や集計値を定義するレベル）、NULLの扱いを説明に記載します。

評価ディメンションに制約があるメジャーは、必須フィールドを含むクエリでテストします。dt_month にフィルターをかけるだけでは、閉じた評価ディメンション [customer, dt_month] の要件を満たしません。

モデルのパターンについてはメジャーを参照してください。説明と名前については、モデルのメタデータを記述するの手順に従ってください。

フェーズ 5：モデルとクエリを検証する #

挙動が不明な場合は、選択した dmlc.exe の挙動を判断基準にします。そのパス、バージョン、ビルド日時、方言を記録します。

  1. 変更したモデルに対してリンターを実行します。
  2. 新しい計算ごとに、最小限のクエリを厳格モードでコンパイルします。
  3. メジャーを使用するクエリ全体を厳格モードでコンパイルします。
  4. 診断メッセージ、注記、SQL、グループ化、結合、フィルター、エイリアス、出力順序を確認します。
  5. 該当する接続を利用できる場合は、結果を採用するための実行に先立ち、検証のみ（validate-only）を実行します。
  6. 代表的なデータ範囲でクエリを実行し、結果をレポートの要件と照合します。
  7. 独立した SQL クエリまたはレポート結果がある場合は、同じ元データのスナップショットを使って、各行の出現回数、キー、NULL、すべてのメジャーを比較します。
dmlc --lint model.dml --json
dmlc --compile --strict query.sql --model=model.dml --json --artifacts=gen
dmlc --validate query.sql --model=model.dml --connection=default --json

default が意図した設定済みの接続である場合に限り、最後のコマンドを実行します。dmlc CLI を使用するでは、出力の取得と検証エラーについて説明しています。

指標の結果の意味に関する各ルールを、実際の数式と照合します。既存店を対象とした件数と比較可能な総件数が同じ母集団に基づく場合、既存店を対象とした件数が総件数を超えることはありません。除外された行に負の値が含まれる場合、部分集合の金額が全体の金額を超えることがあります。前年の入力が欠けている場合は、NULL、ゼロ、または定義済みの別の代替値になることがあります。すべての前年比指標がゼロを返すと想定しないでください。

厳格モードの警告が残る場合は、指摘事項と対応する SQL を保存します。クエリが出力されても、厳格モードでのコンパイルに合格したことにはなりません。実際の接続を使った確認ができない場合は、not run と不足している前提条件を記録します。

分析の主な結論ごとに、その結論を反証し得るクエリを実行します。得られた証拠はレポートと一緒に保存します。

フェーズ 6：最終成果物をレビューする #

フェーズ 5 の該当するチェックに合格したら、フェーズ 6 の技術レビューの手順に従います。モデル、メジャーを使用するクエリ、当初のレポート要件、コンパイラを特定する情報、検証の証拠を提示します。

修正後は、影響を受けるチェックを再実行します。業務定義の変更が分かるようにし、提案された最適化によって指標が変わる場合はフェーズ 4 に戻ります。

モデルとクエリを引き渡す #

再利用可能なモデル、メジャーを使用する SQL、検証の証拠を一緒に保存します。残っている指摘事項と実行しなかったチェックを記録します。
