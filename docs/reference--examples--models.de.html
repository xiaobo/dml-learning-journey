Diese Ausschnitte zeigen Abfragedimensionen, das Auffüllen, Materialisierungen und die Granularität über mehrere Datensätze hinweg. Sie setzen die im jeweiligen Beispiel genannten Modellobjekte voraus.

Dimensionsmodifikatoren #

Fachliche Frage: Welchen Anteil hat jedes Produkt innerhalb seiner Kategorie?

Produktanteil innerhalb der Kategorie #

SELECT Kategorie, Produkt,
       AGG(Umsatz) as Artikelumsatz,
       AGG({Umsatz: {dimension: [Kategorie]}}) as Kategoriesumme
FROM MODEL
GROUP BY Kategorie, Produkt

Hier entfernt {Umsatz: {dimension: [Kategorie]}} die Dimensionen Produkt und Region. Dadurch wird Umsatz allein auf Kategorieebene ausgewertet.

pot verwenden (Prozentanteil an der Gesamtsumme) #

pot entfernt alle Dimensionen und liefert so für jede Zeile den Anteil an der Gesamtsumme:

SELECT Kategorie, Produkt,
       AGG(Umsatz) as Artikelumsatz,
       AGG({Umsatz: pot}) as AnteilAnGesamtsumme
FROM MODEL
GROUP BY Kategorie, Produkt

Für den Anteil innerhalb einer übergeordneten Dimension (z. B. Produktwert geteilt durch die Kategoriesumme) verwenden Sie stattdessen den Modifikator dimension:

-- Share of Kategorie (Produkt / Kategorie Summe)
SELECT Kategorie, Produkt,
       AGG(Umsatz) as Artikelumsatz,
       DIVIDE(AGG(Umsatz), AGG({Umsatz: {dimension: [Kategorie]}})) as Kategorieanteil
FROM MODEL
GROUP BY Kategorie, Produkt

Ausgeblendete Dimensionsfelder #

Ein Datensatz kann Dimensionen enthalten, die für interne Berechnungen erforderlich sind, aber für Endnutzer ausgeblendet werden sollen.

Transaktionen:
    type: dataset
    table: fact_transactions
    dimension:
        - dt_date
        - Produkt
        - Region
    columns:
        dt_date:
        Produkt:
            abbr: product
        Region:
        TransaktionsID:          # internal dimension, not for analysis
            abbr: transaction_id
        Verkaufsbetrag:
            abbr: amount

TransaktionsID lässt sich weiterhin in +d-Modifikatoren verwenden, ohne in der Tabelle MODEL angezeigt zu werden.

Gleitende Jahressumme (MAT) #

SELECT dt_month, AGG(Umsatz), AGG({Umsatz: mat})
FROM MODEL
WHERE dt_month BETWEEN date(current_date, 'start of month', '-12 months')
                   AND date(current_date, 'start of month', '-1 month')
GROUP BY dt_month

mat berechnet für jeden Wert von dt_month eine gleitende Summe über 12 Monate, einschließlich des jeweiligen Monats.

Das Wichtigste: +d führt einen Drilldown aus. Der Modifikator fügt der Auswertungsdimension ein Dimensionsfeld hinzu, aggregiert auf der feineren Ebene und führt das Ergebnis anschließend wieder auf die ursprüngliche Ebene zurück. -d entfernt Dimensionsfelder (Roll-up). dimension: [list] ersetzt die gesamte Auswertungsdimension. Verwenden Sie diese Modifikatoren, um Anteile und Verhältnisse zwischen über- und untergeordneten Ebenen zu berechnen oder Vergleiche auf einer anderen Granularitätsebene anzustellen.

Kombinierte Spalten #

Fachliche Frage: Welche kleinste in Rechnung gestellte Menge ergibt sich je Produkt, wenn nur bezahlte Rechnungen berücksichtigt werden?

Bedingte Aggregation #

KleinsteBezahlteMenge:
    type: measure
    dataset: Transaktionen
    formula: MINIF({Anzahl}, {Bezahlt} = 1)

SELECT Produkt, AGG(KleinsteBezahlteMenge)
FROM MODEL
GROUP BY Produkt

Kalenderdaten vervollständigen oder Standardwerte einsetzen #

Kalenderdaten vervollständigen (jedes Datum erscheint): Stellen Sie sicher, dass die gewünschte Zeitebene im Kalender oder in einer lückenlosen Datumsreihe vorhanden ist, etwa über ein Flag auf Kalender. Fragen Sie anschließend auf dieser Ebene ab.

Kalender:
    type: dataset
    table: DML_CALENDAR
    dimension:
        - dt_date
    columns:
        dt_date:
        DatenVorhanden:
            source: '1'

Fehlende Zeile mit einem Standardwert auffüllen (Weitergabe von NULL-Werten nach einem Join / FOJ verhindern): Aktivieren Sie das Auffüllen mit isnull / ifnull / coalesce(公式, 字面量) als äußerster Funktion. Das Auffüllen greift nur an den Verwendungsstellen dieser Kennzahl. Siehe Auffüllen fehlender Zeilen.

Tagesumsatz:
    type: measure
    formula: 'isnull(SUM({Umsatz: {+d: dt_date}}), 0)' # activate

Verlassen Sie sich bei späteren zusammengesetzten Berechnungen nicht allein auf SUM(isnull({Umsatz: {+d: dt_date}}, 0)), um nach dem Join fehlende Zeilen auszugleichen. Aktivieren Sie das Auffüllen für die Kennzahl, auf die Sie verweisen werden, oder für das Ergebnis der zusammengesetzten Berechnung.

Das Wichtigste: Verwenden Sie MINIF / MAXIF / AVGIF für bedingte Aggregationen, die einen einzelnen Wert liefern. Fehlende Datumswerte → Datumsreihe vervollständigen. Fehlende Kennzahlzeilen nach dem Join → Standardwerte an den Verwendungsstellen einsetzen (P28b).

allows: ALL zur Auswahl von Materialisierungen #

Syntax und Beispiel finden Sie unter allows: ALL. Mit allows: ALL kommen kompatible Materialisierungen infrage. Die Anforderungen an die Granularität der Kennzahlen gelten weiterhin.

Materialisieren #

Fachliche Frage: Ein Dashboard fragt stündlich die monatlichen Umsätze, das Wachstum gegenüber dem jeweiligen Vorjahresmonat und MAT für die vergangenen 24 Monate ab. Der zugrunde liegende Datensatz ist sehr groß.

Lösung: Materialisieren #

Definieren Sie zunächst die Kennzahlen und anschließend ein Materialisierungsobjekt, das diese auf einer festen Granularitätsebene voraggregiert:

Umsatz:
    type: measure
    dataset: Transaktionen
    formula: SUM({Verkaufsbetrag})

UmsatzZumVorjahr:
    type: measure
    formula: '{Umsatz: yoy}'

Umsatzübersicht:
    type: measure
    formula: '{Umsatz: mat}'

DWS_SALES_DATE_PRODUCT:
    type: materialize
    parameters:
        dt_date: date
    dimension:
        - dt_date
        - Produkt
    measures:
        - Umsatz
        - UmsatzZumVorjahr
        - Umsatzübersicht

Ein Datensatz kann seine Materialisierung auch direkt in seiner Definition deklarieren (mit materialize: <name> am Datensatz). Siehe Datensatzdefinition (type: dataset). Die Variante mit einem eigenständigen Objekt ist unter Materialisierungsdeklarationen beschrieben.

⚠️ Auf Kennzahlebene gibt es kein Flag materialize: true. Der Compiler lehnt es mit der Fehlermeldung undefined modifier 'materialize' ab (mit dmlc -c überprüft). Deklarieren Sie eine Materialisierung über type: materialize oder über materialize: <name> am Datensatz. Eine Deklaration direkt an einer Kennzahl ist nicht zulässig.

Funktionsweise #

  1. Der Compiler registriert die Materialisierung und aggregiert die aufgeführten Kennzahlen auf der mit dimension: angegebenen Granularitätsebene vor.
  2. Abfragen, die diese Kennzahlen auf einer kompatiblen Granularitätsebene referenzieren, können die materialisierte Tabelle nutzen, statt die Rohdaten zu lesen. Dies hängt von allows: ab. Siehe Abfragedefinition (type: query).
  3. Die Materialisierung wird über ihre gespeicherte Prozedur (parameters:) aktualisiert. Die Aktualisierung erfolgt nicht in Echtzeit.

Abfrage mit einem Filter auf einer nicht materialisierten Dimension #

SELECT dt_month, Produkt, Region, AGG(Umsatz)
FROM MODEL
WHERE Region = 'North'
GROUP BY dt_month, Produkt, Region

Wenn die Materialisierung auf der Ebene dt_date + Produkt definiert ist (ohne Region), kann sie diese Abfrage nicht bedienen. Ziehen Sie bei Bedarf Materialisierungen auf mehreren Granularitätsebenen in Betracht.

Wann sich eine Materialisierung lohnt #

Anwendungsfall Materialisieren?
Kennzahl wird häufig gelesen, Rohdatenmenge ist sehr groß Ja
Kennzahl wird in Dashboards mit strengen SLA-Vorgaben verwendet Ja
Kennzahl wird selten und nur bei Bedarf abgefragt Nein (der Zusatzaufwand lohnt sich nicht)
Granularität der Kennzahl = Granularität der Rohdaten Nein (kein Vorteil durch Aggregation)
Kennzahl verwendet komplexe Fensterfunktionen Ja

Das Wichtigste: Die Materialisierung wird mit einem Objekt vom Typ type: materialize deklariert (Granularität über dimension:, Kennzahlen über measures:). Eine Deklaration direkt an der Kennzahl ist nicht zulässig. Materialisierte Kennzahlen werden in Abfragen wie gewohnt referenziert (AGG(Umsatz)). Siehe Definition einer Materialisierung (type: materialize) und Materialisierungen entwerfen.

Materialisierung als Ersatz für ETL #

Fachliche Frage: Eine gespeicherte Prozedur erstellt eine Faktentabelle (INSERT INTO RPT_X SELECT ... FROM raw LEFT JOIN dim1 LEFT JOIN dim2 ...). Anschließend greift ein Bericht auf RPT_X zu. Lässt sich die gespeicherte Prozedur durch DML ersetzen?

Lösung: Die ETL-Pipeline als Materialisierungsobjekt modellieren #

Modellieren Sie RPT_X nicht als extern erstellten Datensatz mit table:, sondern bilden Sie die gesamte Pipeline ab: die Rohdatenquelle als Datensatz mit table:, die Datenanreicherung über Ketten von pk()-Aufrufen und RPT_X als Objekt vom Typ type: materialize, das die angereicherte Quelle voraggregiert.

# 1. Dimension datasets (the stored procedure's #temp tables)
Kundenverzeichnis:
    type: dataset
    table: MDM_STORE
    dimension: [Filialnummer]
    columns:
        Filialnummer:
            abbr: store_id
        Filialname:
            abbr: store_name
        ZentralenID:
            abbr: hq_id

Organisationsverzeichnis:
    type: dataset
    table: MDM_ORG
    dimension: [Organisationsnummer]
    columns:
        Organisationsnummer:
            abbr: org_id
        Mitarbeitername:
            abbr: emp_name

# 2. Source fact dataset with pk() chain enrichment
#    (replaces the stored procedure's SELECT ... LEFT JOIN ...)
Verkaufsrohdaten:
    type: dataset
    table: RAW_SALES
    dimension: [dt_month, Filialnummer, Artikelnummer]
    columns:
        dt_month:
        Filialnummer:
            abbr: store_id
        Artikelnummer:
            abbr: prod_id
        Betrag:
            abbr: amt
        # pk() chain enrichment replaces LEFT JOINs
        Filialname: pk({Filialnummer}).{Kundenverzeichnis}.Filialname
        ZentralenID: pk({Filialnummer}).{Kundenverzeichnis}.ZentralenID
        # nested pk() chain: hq_id → Dim Customer → ... (hq_id is itself a pk result)
        NameDerZentrale: pk({ZentralenID}).{Kundenverzeichnis}.Filialname
        # three-hop chain: store → hq_id → org_id → emp_name
        ZentralenOrganisation: pk({ZentralenID}).{Kundenverzeichnis}.Organisationsnummer
        MitarbeiterDerZentrale: pk({ZentralenOrganisation}).{Organisationsverzeichnis}.Mitarbeitername
    measures:
        Umsatz: SUM({Betrag})

# 3. Materialize replaces INSERT INTO RPT_X
#    Grain keys (dt_month, store_id, prod_id) go in dimension:.
#    Functionally dependent attributes (store_name, hq_name, hq_emp) go in
#    dimension_columns: — the compiler rejects derivable attributes in dimension:.
RPT_X:
    type: materialize
    parameters:
        dt_month: range
    dimension:
        - dt_month
        - Filialnummer
        - Artikelnummer
    dimension_columns:
        Filialname:
        NameDerZentrale:
        MitarbeiterDerZentrale:
    measures:
        - Umsatz

# 4. Report query consumes the materialize
report:
    type: query
    allows:
        - RPT_X
    filters:
        dt_month: { range: ['2024-01-01', '2024-03-01'] }
    columns:
        dimension: [dt_month, Filialname]
        Umsatz: '{Umsatz}'

Wann sich dieses Muster eignet:

  • Die maßgebliche SQL-Implementierung ist eine gespeicherte Prozedur mit INSERT INTO ... SELECT ... FROM raw JOIN dims.
  • Die temporären Tabellen der gespeicherten Prozedur lassen sich direkt als Dimensionsdatensätze mit Nachschlagevorgängen über pk()-Ketten abbilden.
  • Die Einschränkungen der berücksichtigten Zeilen durch INNER JOIN in der gespeicherten Prozedur werden zu Filterbedingungen für die Kennzahlen. Behalten Sie die ursprüngliche Zeilenmenge bei und prüfen Sie die generierten Prädikate.

Einschränkungen:

  • Gespeicherte Prozeduren, die mit @month (letzter Saldomonat) die Stammdaten aller historischen Monate aktualisieren, lassen sich mit pk()-Ketten, die über archive_month (monatsspezifische Stammdaten) verknüpfen, nicht exakt nachbilden. Dokumentieren Sie dies als bekannte Einschränkung, die einen Vergleich der Ergebnisse anhand desselben Snapshots der Quelldaten erfordert.
  • Tabellenwertfunktionen mit CROSS APPLY und die Neuzuordnung von Schlüsseln mit CASE WHEN erfordern in Dimensionsdatensätzen die Escape-Syntax sql:. Deklarieren Sie die resultierenden Schlüssel und prüfen Sie ihre Eindeutigkeit.

Unterschiedliche Dimensionen #

Fachliche Fragestellung: Vergleichen Sie die Verkäufe nach Region mit dem Bestand nach Lager. Beide haben dt_date und Produkt gemeinsam. Region und Lager sind keine gemeinsamen Dimensionen.

Herausforderung #

Kennzahlen aus Datensätzen mit völlig unterschiedlichen Dimensionen lassen sich nur dann direkt vergleichen, wenn Sie sie aufeinander abstimmen.

Umsatz:
    type: dataset
    table: fact_sales
    dimension:
        - dt_date
        - Produkt
        - Region
        - Kunde
    columns:
        dt_date:
        Produkt:
            abbr: product
        Region:
        Kunde:
            abbr: customer
        Verkaufsbetrag:
            abbr: amount

Bestand:
    type: dataset
    table: fact_inventory
    dimension:
        - dt_date
        - Produkt
        - Lager
    columns:
        dt_date:
        Produkt:
            abbr: product
        Lager:
            abbr: warehouse
        Stückzahl:
            abbr: units

Gesamtumsatz:
    type: measure
    dataset: Umsatz
    formula: SUM({Verkaufsbetrag})

Gesamtbestand:
    type: measure
    dataset: Bestand
    formula: SUM({Stückzahl})

Gemeinsame Granularität: nach Produkt und Datum #

SELECT dt_date, Produkt, AGG(Gesamtumsatz), AGG(Gesamtbestand)
FROM MODEL
WHERE dt_date = date(current_date)
GROUP BY dt_date, Produkt

Das funktioniert, weil beide Kennzahlen dt_date und Produkt gemeinsam haben. Das Modell berücksichtigt die fehlenden Dimensionen implizit.

Wenn Sie Region und Lager in derselben Abfrage benötigen #

In der Regel ist es nicht möglich, gleichzeitig nach Region und Lager zu gruppieren. Der Grund dafür ist, dass Gesamtbestand kein Region und Gesamtumsatz kein Lager hat.

Option 1: Zwei separate Abfragen

-- Sales by Region
SELECT dt_date, Region, AGG(Gesamtumsatz) FROM MODEL GROUP BY dt_date, Region

-- Inventory by Lager
SELECT dt_date, Lager, AGG(Gesamtbestand) FROM MODEL GROUP BY dt_date, Lager

Option 2: Inkompatible Dimensionen mit Modifikatoren entfernen

SELECT dt_date, Region,
       AGG(Gesamtumsatz) as Umsatz,
       AGG({Gesamtbestand: {-d: Lager}}) as BestandAllerLager
FROM MODEL
GROUP BY dt_date, Region

{-d: Lager} entfernt Lager aus der Granularität des Bestands. Dadurch wird der Bestand auf der Ebene dt_date + Produkt berechnet und lässt sich mit den Verkäufen auf der Ebene dt_date + Region + Produkt verknüpfen. Das ist fachlich meist fragwürdig. Gehen Sie dabei vorsichtig vor.

Summen für den ausgewählten Zeitraum und für die gesamte Historie #

-d hebt die Gruppierung auf. Bleibt ein Monatsfilter aktiv, bedeutet das Aufheben der Gruppierung allein noch keine Auswertung der gesamten Historie. Verwenden Sie für diese Modellausschnitte separate Abfragen mit jeweils explizit festgelegtem Geltungsbereich:

-- Selected month
SELECT Produkt, Region, AGG(Gesamtumsatz) AS Periodenumsatz
FROM MODEL
WHERE dt_month = date(current_date, 'start of month')
GROUP BY Produkt, Region

-- All history
SELECT Produkt, Region, AGG(Gesamtumsatz) AS UmsatzÜberAlleJahre
FROM MODEL
GROUP BY Produkt, Region

Führen Sie die Anweisungen einzeln mit den auf dieser Seite erforderlichen Modelldefinitionen aus. Einen vollständig ausgeführten Vergleich innerhalb eines einzigen Berichts finden Sie unter Nenner mit fester Achse. Das Beispiel gruppiert Datumswerte nach dt_month.

Wichtige Punkte: Kennzahlen aus verschiedenen Datensätzen lassen sich gemeinsam abfragen, wenn sie genügend Dimensionen gemeinsam haben. Wenn die Dimensionen nicht zusammenpassen, verwenden Sie separate Abfragen oder setzen Sie -d-Modifikatoren mit Bedacht ein. Wenn Sie Dimensionen entfernen, um Kompatibilität zu erzwingen, können die Ergebnisse irreführend sein. Dokumentieren Sie, was Sie damit erreichen wollen.
