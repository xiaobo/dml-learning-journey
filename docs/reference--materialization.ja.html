マテリアライズの宣言

このページの内容
  • マテリアライズの定義（type: materialize）
  • 利用条件、選択、性能測定
  • SQL Server のランタイム

このページでは、type: materializeと、そのグループ化キー、属性、指標の選択について説明します。設計上の判断については、マテリアライズの粒度を選ぶを参照してください。マテリアライズの例では、宣言の一部を例示します。

マテリアライズの定義（type: materialize） #

<name>:
    type: materialize
    parameters:                         # stored-procedure parameters
        <param>: <column_name>
    filters:                            # materialize-level filters
        <column>: <値>

    allows: [<materialize_name>]        # allowed materialize tables

    dataset: <dataset_name>      # optional, for direct dataset materialize
    dimension: [col1, col2]      # materialization grain — grain keys only
    dimension_columns:           # functionally dependent attribute columns
        <col>: <formula>          # (1:1 with grain keys, not grain themselves)

    measures: [<measure1>, <measure2>]  # measures to materialize

dimension:とdimension_columns:の違い。dimension:には、マテリアライズのディメンションを指定します。そのディメンションのフィールドが、行の粒度を定め、各行を一意に識別するキーになります。コンパイラはこれらをGROUP BYのキーとして使います。dimension_columns:には、これらのキーから導出できる属性列を指定します。たとえば、店舗名は店舗番号に依存し、region_codeは店舗番号に依存します。コンパイラはdimension_columns:に指定された列をGROUP BYの結果に引き継ぎますが、粒度を定めるキーには含めません。導出できる属性をdimension:に指定すると、コンパイルエラーになります（「can be derived from [...], should it be moved to dimension_columns instead?」）。

数式を指定しない場合の継承。dimension_columns:の項目にformula:を指定しない場合、ソースデータセットから列を継承します。その列はソースデータセットのcolumns:に存在する必要があります。存在しない場合は「not found from relate dataset(s)」と表示されます。マテリアライズの粒度がソースデータセットのディメンションより粗い場合、コンパイラは列を導出できるかどうかを確認します。ソースのより細かい粒度で値が変わる列は、「definition from dataset [...] cannot be derived from dimension [...], please advise」というエラーになります。マテリアライズの粒度がソースデータセットのディメンションと一致する場合は、ソースのどの列でも使用できます（行の対応は1:1）。

数式で参照できる範囲。dimension_columns:の項目にformula:を指定した場合、数式で参照できるのは、pk() を連ねたルックアップと、マテリアライズのディメンション自体のフィールドだけです。ソースデータセットの列や指標を参照すると、「not defined, did you mean …?」というエラーになります。

制約。次のいずれかの形式を指定します。

  • dimension + measures（指標リストを指定する形式）、または
  • dataset + dimension + dimension_columns（対象をデータセットに限定する形式）、または
  • datasetのみ（データセットの粒度を継承）。

マテリアライズの例には、宣言のパターンが記載されています。指標レベルにはmaterialize: trueフラグがなく、指定するとコンパイルエラーになります（undefined modifier 'materialize'。トラブルシューティング索引のP64を参照）。宣言形式はこのセクションで説明します。データセットレベルのmaterialize: <name>については、モデル構造を参照してください。

利用条件、選択、性能測定 #

allows:は、どのマテリアライズが利用候補になるかを制御します。宣言だけでは、クエリがどの保存済み集計を選ぶかは決まりません。生成されたSQLまたは実行計画を確認し、対象エンジンで実際に使用されるオブジェクトを特定してください。

完全なキーを使って、最適化ありとなしの結果を比較してください。対応するグループがないグループ、NULL、比率も比較に含めます。ソースデータを変更した後は、更新と更新後の結果を確認してください。代表的なワークロードの測定は、これらの確認を済ませてから行ってください。SQLが短くなることやコンパイルが速くなることだけでは、データベースでのクエリ性能は判断できません。更新の権限とスケジュールはデプロイ側で管理します。

設定、クエリがマテリアライズを利用したかどうかの確認、更新、結果の確認は、マテリアライズのワークフローに従って行います。

SQL Server のランタイム #

SQL Server のランタイムは、共有プロシージャDML_PREPARE_MAZとDML_REFRESH_MAZを使って要求を登録し、その後、単一インスタンスのDML_RUN_MAZを同期的に呼び出します。ランナーが処理中の場合、登録を行った呼び出しは、要求したデータの準備が整う前に戻ることがあります。

setup_sqlはランタイムと Maz の書き込みコンポーネントをインストールします。生成されたprepare_sqlは、準備処理とデータの準備状況の確認を行います。データの準備が整うか、再試行処理が協調的に守る 5 秒の期限に達するまで、通常の準備を繰り返します。成功するとdata_ready=1を返し、その後、呼び出し元は業務処理用のsqlを実行します。エラーが発生するとクエリは停止します。待機中もprepare_status_sqlで状況を確認できます。ステータスクエリは、Query で選択されたパーティションとパラメータのバインドを監視します。処理をキューに追加することも、準備処理とSELECTで共通のスナップショットを保証することもありません。

共有ビューdbo.DML_MAZ_PROGRESSは、システム全体の処理待ちパーティション、単位時間あたりの処理完了数と到着数、および処理待ちを解消するまでの推定秒数を表示します。直近60秒の移動ウィンドウを使用し、同じ物理パーティションの処理が複数回完了しても、1 回だけ数えます。全体の進捗から、特定の Query のデータが準備できているかどうかは判断できません。

SELECT pending_partitions, runner_running, estimated_seconds
FROM dbo.DML_MAZ_PROGRESS;

完全一致とLIKEによる照合、force_updateとinvalidate_only、接続要件、および呼び出し中断後の復旧については、準備、更新、復旧の仕様を参照してください。

通常の準備では、パラメータのバインドが同じであれば、テーブル全体と日付指定の有効な結果を再利用します。invalidate_only=1はランナーを呼び出さずに無効化をコミットします。DML_REFRESH_MAZをパラメータなしで呼び出すと、登録済みで処理待ちの作業を再開します。他の選択指定と併用できない@_sourceには、登録済みのローカルテーブルをschema.tableの形式で指定できます。この指定では、Maz を直接使用するすべての対象を含めます。日付の対応関係を確認できない場合は、安全側に倒して既存の範囲を対象に含めます。
