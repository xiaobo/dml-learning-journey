Ein Bericht verbindet fachliche Definitionen mit Festlegungen zu Gruppierung, Filtern und Darstellung. DML hält wiederverwendbare Definitionen in einem Modell vor. Berichte können so dieselben Kennzahlen verwenden, wenn die Ebenen, auf denen Zeilen oder Summen definiert sind, zueinander passen.

Kennzahlen können auf andere Kennzahlen verweisen. Der analytische Kontext bestimmt, wie jeder Verweis ausgewertet wird. So lässt sich dieselbe Margendefinition in einem regionalen Bericht und für einen KPI verwenden, der den Zeitraum vom Jahresbeginn bis zum Auswertungsstichtag abdeckt. Die Zeittransformation berechnet Gewinn und Umsatz vor der Division neu, statt den Durchschnitt der Monatsmargen zu bilden. Auch Kennzahlen aus verschiedenen Datensätzen lassen sich kombinieren, wenn die Ebenen, auf denen Zeilen oder Summen definiert sind, zueinander passen. Die Ausgabeschlüssel und die Gruppen, die auf einer Seite fehlen, müssen weiterhin zur vorgesehenen Grundgesamtheit des Berichts passen. Das Rentabilitätsbeispiel zeigt dies anhand von Kombination, Kumulation und Vergleich. DML-Modelle, DMX-Ausdrücke und der Compiler können den Berechnungskern einer analytischen semantischen Schicht bilden. Die fachlichen Definitionen müssen die Beteiligten weiterhin selbst abstimmen.

Der bebilderte kurze Rundgang durch DML führt anhand von vier Beispielverkäufen und einem Werkzeug zum Erkunden von Gruppierungen in diese Konzepte ein.

Ein vollständiges ausführbares Beispiel finden Sie unter Erste Modellabfrage kompilieren. Die DML-Kernspezifikation legt die verbindlichen Regeln der Sprache fest.

1. Die Ebenen für Modell, Abfrage und Ausdruck #

Ebene Sprache Inhalt Speicherort
Modell DML, Dato Measure Language Datensätze, Kennzahlen und Spaltenmakros .dml YAML
Abfrage Model Query Kennzahlauswahl, Gruppierung und Berichtsfilter .sql oder DML mit type: query
Ausdruck DMX, Dato Measure eXpression Formeln, Referenzen und Modifikatoren Modellformeln und Abfrageausdrücke

DML ist ein eigenständiger Compiler für eine semantische Schicht. Er verarbeitet Modelldateien und erzeugt SQL, das die Datenbank ausführt. Datenbankberechtigungen und die Autorisierung in der Anwendung regeln den Zugriff. Dashboards und die zeitgesteuerte Ausführung sind Aufgaben des umgebenden Systems. Ein Modellfilter allein ist keine Zugriffskontrollrichtlinie.

DML prüft die Struktur von Deklarationen und die analytische Kompatibilität, etwa im Hinblick auf die Ebene, auf der Zeilen oder Summen definiert sind, und auf den Zeitkontext. Der Compiler bietet keine vollständige statische Typprüfung für SQL-Ausdrücke. Die physischen Werttypen liegen in der Zuständigkeit der Datenbank, und das bei der Prüfung verwendete Modellschema weist type:-Deklarationen für Spalten zurück. Eine fehlerhafte Typkonvertierung oder ein ungültiges Funktionsargument kann daher die Kompilierung passieren und erst in der Datenbank zu einem Fehler führen. Siehe Spaltenmetadaten und Werttypen.

Ein Datensatz bindet Spalten an eine physische Tabelle oder eine SQL-Relation. Seine Deklaration dimension: legt den vollständigen Schlüssel der Quellzeilen fest.

Transaktionen:
  type: dataset
  table: fact_transactions
  dimension: [TransaktionsID]
  columns:
    TransaktionsID:
      abbr: transaction_id
    Verkaufsbetrag:
      abbr: amount
    Rabattbetrag:
      abbr: discount
    Nettobetrag: Verkaufsbetrag - Rabattbetrag
  measures:
    Umsatz: SUM({Nettobetrag})
    Transaktionsanzahl: COUNT(1)

DurchschnittlicherTransaktionswert:
  type: measure
  formula: 'DIVIDE({Umsatz}, {Transaktionsanzahl})'

Umsatz und Transaktionsanzahl sind atomare Kennzahlen. Sie übernehmen den Datensatz, in dem sie definiert sind, und aggregieren dessen Zeilen oder Spaltenausdrücke direkt, ohne auf andere Kennzahlen zu verweisen. DurchschnittlicherTransaktionswert ist eine zusammengesetzte Kennzahl, weil ihre Formel auf andere Kennzahlen verweist, obwohl beide atomaren Kennzahlen Transaktionen verwenden. Eine zusammengesetzte Kennzahl hat keine Eigenschaft dataset:.

In einer Modellformel bezeichnet Verkaufsbetrag ohne geschweifte Klammern eine physische SQL-Spalte. {Nettobetrag} wird durch den Ausdruck der berechneten Modellspalte ersetzt. Die geschweiften Klammern machen den Unterschied auch dann deutlich, wenn der logische und der physische Name übereinstimmen.

Spaltenmakros definieren wiederverwendbare Spaltenausdrücke oder Suchzugriffe auf andere Datensätze. So können sie Attribute für Kennzahlen bereitstellen, ohne dass jede Abfrage, die diese Kennzahlen verwendet, einen Join enthalten muss. Der vollständige Schlüssel des Zieldatensatzes bestimmt die Suchargumente. Siehe Quellrelationen und Suchzugriffe.

Model Query verweist über AGG(...) auf Kennzahlen. Modellformeln verwenden Aggregatfunktionen wie SUM und COUNT direkt. AGG ist die Abfrageschnittstelle für eine Kennzahl und ersetzt SUM innerhalb einer Modellformel nicht.

Eine einmalig benötigte Kennzahl kann zunächst in einem eingebetteten DML-Block in der Abfragedatei definiert werden. Zum Ausprobieren muss das gemeinsame Modell nicht zuerst geändert werden. Prüfen Sie brauchbare Definitionen, bevor Sie sie als gemeinsame Kennzahlen übernehmen.

2. Quellrelationen, Suchzugriffe und Kombination von Kennzahlen #

DML kombiniert Daten in verschiedenen Verarbeitungsschritten. Welchen Schritt Sie wählen, bestimmt, welche Schlüssel, Filter und Zeilenmengen Sie prüfen müssen.

Aufgabe Mechanismus Regeln für das Ergebnis
Ein Attribut über seinen vollständigen Schlüssel wiederverwenden Suchzugriff mit pk(...) in einer Modellformel Genau eine Zielzeile pro Suchschlüssel. Einfache und zusammengesetzte Schlüssel werden unterstützt.
Das am Ereignisdatum gültige Attribut ermitteln pk(VerkaufspositionID, dt_date) mit [VerkaufspositionID, 'range(valid_from, valid_to)'] als Zielschlüssel Die geprüften endlichen Intervalle entsprechen [start,end). Intervalle für dieselbe id dürfen sich nicht überschneiden.
Unabhängige Fakten wie Umsatz und Budget vergleichen Kennzahlen, die anhand aufeinander abgestimmter Dimensionen ausgewertet werden Bei der üblichen Kombination über die Vereinigung der Schlüssel bleiben alle Gruppen erhalten, die auf mindestens einer Seite vorkommen. Kommt eine Gruppe nur auf einer Seite vor, bleiben die Werte auf der anderen Seite fehlend.
Eine Relation als Brücke, Join, Union oder Unterabfrage vorbereiten sql: des Datensatzes oder eine Datenbanksicht Die vorbereitete Relation benötigt einen eigenen vollständigen Schlüssel. Legen Sie Verteilungsgewichte fest und prüfen Sie die Gesamtsummen, wenn eine Quellzeile mehreren Zeilen entsprechen kann.

Das SQL einer Model Query, die das Modell nutzt, unterstützt JOIN, UNION und Unterabfragen nicht direkt. Unterstützte Relationen lassen sich dennoch im SQL eines Datensatzes vorbereiten. Im Quell-SQL definierte Filter schränken weiterhin die Zeilenmenge der Quellrelation ein. Sie werden nicht automatisch zu Regeln, die auf jeden Kontext reagieren, in dem die Quellrelation verwendet wird.

Aus Suchzugriffen über zusammengesetzte Schlüssel oder anhand des am Ereignisdatum gültigen Intervalls lässt sich weder auf einen allgemeinen Beziehungsgraphen mit frei wählbaren Pfaden noch auf eine automatische Viele-zu-viele-Verteilung schließen. Auch die unabhängige Aggregation von Kennzahlen behebt weder doppelte Suchschlüssel noch fehlerhafte Vorgaben dafür, wie die Ergebnisse aufeinander abgestimmt werden. Die Beispiele zu zusammengesetzten Schlüsseln und zur Suche über Gültigkeitsintervalle zeigen vollständige Modelle, absichtlich herbeigeführte Schlüsselfehler und deren Behebung. Informationen zu Gruppen ohne Entsprechung und zu NULL-Schlüsseln finden Sie unter Semantik der Kennzahlenkombination. Wie Quellen zugeordnet und abgeleitete Relationen geprüft werden, erfahren Sie unter Datensatz-SQL.

3. Rollen von Dimensionen und Granularität #

Ein Dimensionsfeld ist ein einzelnes benanntes DML-Feld. Eine Dimension ist eine Liste von Feldern. Wo sie deklariert wird, bestimmt ihre Rolle.

Deklaration Bedeutung
dimension: im Dataset Vollständige Identifikation einer Quellzeile
Dimensionsmodifikatoren in Formeln Auswertungsdimension einer einzelnen Kennzahlreferenz
GROUP BY oder columns.dimension in der Abfrage Gruppierung des Ergebnisses
dimension: in der Materialisierung Gespeicherte Gruppierung und gespeicherter Schlüssel
dimensions: in der Kennzahl Zulässige Alternativen für die Auswertungsdimension, eine pro innerer Liste

Die Granularität beschreibt, wofür eine Zeile im jeweiligen Kontext steht. Beispielsweise identifiziert [TransaktionsID] eine Transaktion, während [Region, dt_month] einen Bericht nach Region und Monat gruppiert. Eine Berichtsgruppe kann viele Quellzeilen enthalten und daher den Quellschlüssel nicht ersetzen.

Der Modifikator dimension: [] leert die Auswertungsdimension, um einen Gesamtwert ohne Gruppierung zu berechnen. Er deklariert keinen Schlüssel zur Identifikation von Dataset-Zeilen. +d fügt Felder für eine Zwischenberechnung hinzu. Wenn eine Formel ein Ergebnis auf einer gröberen Ebene benötigt, fasst eine explizite äußere Aggregation diese Zwischenwerte zusammen.

Der Compiler verlässt sich auf den deklarierten Quellschlüssel. Gibt es im Ziel einer pk(...)-Referenz mehrere Zeilen mit demselben Schlüssel, können sich Zeilen auch bei erfolgreicher Kompilierung vervielfachen. Die Validierung anhand der tatsächlichen Daten prüft, ob die vorhandenen Schlüsselwerte eindeutig sind. Ergebnisvergleiche zeigen, ob die Abfrage das beabsichtigte Ergebnis liefert.

Semantik von Dimensionen erläutert diese Rollen und ihre Auswirkungen genauer.

4. Zeitkontext und dim_dt #

dim_dt steht für das aktive Zeitfeld im Abfragekontext einer Kennzahl. Damit kann eine Formel auf die aktuelle zeitliche Granularität Bezug nehmen, ohne dt_date, dt_month oder dt_quarter direkt zu nennen. Welche Granularitäten ein Makro akzeptiert, hängt weiterhin von seinen Voraussetzungen ab.

Ein Zeitfeld, nach dem gruppiert wird, oder ein Zeitfilter kann den Kontext liefern. Prüfen Sie die Diagnosemeldungen im strikten Modus und die generierten Joins getrennt davon, ob die Syntax akzeptiert wird. Ein Zeitvergleich oder ein Join über die Vereinigung von Schlüsseln führt für sich genommen nicht zwingend zu einer Warnung im strikten Modus.

Wenn Sie ein feingranulares Standardzeitfeld wie dt_date deklarieren, stellt der Systemkalender die unterstützten gröberen Zeitfelder bereit. Diese virtuellen Felder benötigen keine zusätzlichen physischen Deklarationen. Wenn Sie für ein abgeleitetes dt_month im Editor zur Definition springen, gelangen Sie zur explizit deklarierten Zeitspalte der Quelle.

Auch für einen einzelnen KPI muss das Ende des Auswertungszeitraums ausdrücklich festgelegt werden. Im ausführbaren Beispiel ergibt ein Filter auf Februar für Januar und Februar zusammen eine YTD-Marge von 20%. Die reguläre Umsatzkennzahl in derselben Abfrage berücksichtigt dagegen nur Februar. Ohne Zeitkontext schlägt die Abfrage fehl. Kalenderabfragen mit Gruppierung können auch Monate mit kumulierten Werten zurückgeben, deren Monatsumsatz NULL ist. Wählen Sie deshalb die Ausgabezeiträume gezielt aus. Der Kalender muss auf der Verbindung, über die die Abfrage ausgeführt wird, die vorgesehenen Datumswerte abdecken.

Die Spezifikation zum Zeitkontext definiert dim_dt und die Standardzeitfelder. Unter Systemmakros finden Sie die Definitionen der Zeit- und Formelmakros zum Nachschlagen.

5. Wiederverwendung und Integration #

Benutzerdefinierte fn-macro-Definitionen umschließen die Kennzahlformel des Aufrufers. dt-macro-Definitionen ändern den Zeitkontext der Formel. Beide lassen sich über die Modifikatorsyntax kombinieren, ohne den Compiler zu ändern. Aufrufe skalarer Datenbankfunktionen greifen auf Funktionen zurück, die auf der ausführenden Verbindung installiert sind. Der Leitfaden zu Erweiterungen zeigt Beispiele, die tatsächlich ausgeführt wurden, darunter einen Aufruf, der wegen einer fehlenden Funktion fehlschlägt. Diese Mechanismen stellen kein allgemeines Modulsystem bereit und bieten keine umgebungsübergreifende Unterstützung für alle Arten von UDF.

Legen Sie den SQL-Dialekt des Modells explizit fest. Wenn das System einen Dialekt erkennt, belegt das nicht, dass jede Funktion erfolgreich mit dieser Datenbank-Engine ausgeführt wurde. Generiertes SQL kann mehrere Anweisungen, Zwischenrelationen und Abhängigkeiten vom Kalender enthalten. Prüfen Sie daher auch die Ausführungsumgebung.

Der geprüfte JDBC-Treiber bindet Positionsparameter in physischem SQL sowie in Filtern und Kennzahlausdrücken von Model Query. Siehe Beispiele für JDBC-Parameter. Materialisierungsparameter und die interne Parametrisierung von Literalen sind eigenständige Mechanismen.

Kompilierung, Validierung und Ausführung weisen jeweils etwas anderes nach. Die Schlüsselvalidierung anhand der tatsächlichen Daten kann Duplikate erkennen, bevor ein Lookup Zeilen vervielfacht. Es ist jedoch nicht garantiert, dass die Validierung und die anschließende Ausführung denselben Daten-Snapshot verwenden. Wenn die Datenbank EXPLAIN akzeptiert, belegt das nicht, dass die zurückgegebenen Zahlen stimmen. Vergleichen Sie im vorgesehenen Datenbereich die vollständigen Schlüssel, die Anzahl der Vorkommen jeder Zeile, NULL-Werte und ungerundete Werte mit einem unabhängig ermittelten Ergebnis.

Zeitvergleiche und Auswahl der Ergebniszeilen #

Ein Abfragezweig für den vorherigen Zeitraum kann mithilfe des Kalenders eine Gruppe aus diesem Zeitraum in einen Monat übernehmen, für den keine Faktendaten vorliegen. Das Zeitfenster der Abfrage und der Filter auf vorhandene Daten im aktuellen Zeitraum bestimmen, ob die Gruppe im Bericht erscheint. Siehe zusätzliche Monate bei Vergleichen.
