Diese Seite beschreibt Referenzformen und integrierte Funktionen. Das Verhalten von Modifikatoren ist unter Kennzahlmodifikatoren beschrieben. Die Abfragegrammatik und die Aliasregeln stehen unter Model Query SQL. Die Beispiele zeigen Funktionen in der Ausdruckssyntax. Welches SQL erzeugt wird, hängt vom ausgewählten Dialekt ab.

Referenzsyntax #

In .dml-Formeln #

Referenztyp Syntax Beispiel
Spalte {column_name} SUM({Verkaufsbetrag})
Kennzahl {measure_name} DIVIDE({Umsatz}, {count})
Spalte aus einem anderen Dataset {DATASET}.column {products}.price
Kennzahl mit Modifikator {measure: modifier} {Umsatz: yoy}
Kennzahl mit verschachtelten Modifikatoren {measure: {modifier: sub}} {Umsatz: {+d: Kunde}}

In Model Query SQL #

Referenztyp Syntax Beispiel
Spalte (Dimension) Nur der Name SELECT Produkt, dt_month
Kennzahl AGG(measure_name) AGG(Umsatz)
Kennzahl mit Modifikator AGG({measure: modifier}) AGG({Umsatz: yoy})
Kennzahl mit Modifikator als Positionsargument AGG(measure, 'modifier') AGG(Umsatz, 'yoy')

Grundregel: Geschweifte Klammern {...} sind .dml vorbehalten. Verwenden Sie in Model Query SQL für Dimensionen den Namen allein und für Kennzahlen AGG(...). Die einzige Ausnahme ist die Schreibweise mit Modifikator: AGG({measure: modifier}).

Schlüssel-Lookups mit pk(...) #

Lookups unterstützen Einzelschlüssel, zusammengesetzte Schlüssel und Schlüssel mit Gültigkeitszeitraum. Geben Sie den vollständigen Schlüssel des Ziels an, nicht die Gruppierungsfelder der Abfrage, die den Lookup verwendet. Diese Attribut-Lookups unterscheiden sich vom Aufbereiten einer Relation im Dataset-SQL und vom Kombinieren unabhängig aggregierter Kennzahlen. Siehe Quellrelationen, Lookups und Kombination von Kennzahlen.

Spalten-Lookups über Dataset-Grenzen hinweg in .dml-Formeln:

# Single PK
formula: 'SUM({Verkaufsbetrag} * pk(Kundennummer).{Kundenanzahl}.tier_discount)'

# Composite PK
formula: 'SUM(pk(brand_id, tag_id).{DATASET_PRODUCTS}.state)'

Geben Sie für jedes Dimensionsfeld des Ziels genau einen Ausdruck in Deklarationsreihenfolge an. pk(1, tag_id) hat für [brand_id, tag_id] die richtige Anzahl von Argumenten und setzt brand_id absichtlich auf 1. Ob dieser Lookup korrekt ist, hängt vom vorgesehenen Schlüssel und seiner Eindeutigkeit in der Quelle ab.

Zusammengesetzte Schlüssel und Schlüssel mit Gültigkeitszeitraum #

Die Angabe dimension: des Ziels definiert dessen vollständigen Quellschlüssel, nicht die Gruppierung im Bericht. In beiden folgenden Lookup-Mustern stehen die Zielfelder in Deklarationsreihenfolge:

# Target with a compound key:
dimension: [VerkaufspositionID, Region]
# Column in the referring dataset:
Bezeichnung: 'pk({VerkaufspositionID}, {Region}).{D}.Bezeichnung'

# Target with an object key and validity interval:
dimension: [VerkaufspositionID, 'range(valid_from, valid_to)']
# Column in the referring dataset:
Bezeichnung: 'pk({VerkaufspositionID}, {dt_date}).{D}.Bezeichnung'

Lassen Sie 'range(valid_from, valid_to)' in Anführungszeichen, damit das Komma Teil desselben YAML-Listeneintrags bleibt. Das Ereignisdatum muss in [valid_from, valid_to) liegen. Der Beginn ist eingeschlossen, das Ende ausgeschlossen. Ein Ereignis am 1. Februar fällt daher in ein Intervall, das am 1. Februar beginnt, nicht in eines, das an diesem Tag endet. Diese Syntax ist von der Datenbankfunktion range() zu unterscheiden, die Arrays erzeugt.

Dieselbe ID darf in mehreren Regionen vorkommen, wenn der gesamte zusammengesetzte Schlüssel eindeutig ist. Gültigkeitsintervalle für dieselbe ID dürfen sich nicht überschneiden. Doppelte Zielzeilen oder überlappende Intervalle können nach erfolgreicher Kompilierung zusätzliche Abfragezeilen erzeugen. --validate prüft, ob die vorgefundenen Daten die Schlüsselanforderungen erfüllen. Dabei werden die Daten weder repariert noch wird garantiert, dass die anschließende Ausführung denselben Daten-Snapshot verwendet.

Die Übungen zu zusammengesetzten Schlüsseln und Schlüsseln mit Gültigkeitszeitraum enthalten vollständige Modelle, Datumswerte an den Intervallgrenzen, absichtlich herbeigeführte Validierungsfehler und Ergebnisse nach der Korrektur. Sie zeigen endliche, direkt aneinandergrenzende Intervalle. Offene Intervallgrenzen und allgemeine Regeln für n:m-Zuordnungen sind nicht Gegenstand der Übungen. Definieren Sie für eine Analyse mit Brückentabelle oder eine Verteilungsanalyse den vollständigen Schlüssel, die Gewichte und die erwarteten Summen separat. Aus einem Fehler bei der Anzahl der Lookup-Argumente lässt sich nicht ableiten, ob sich die Analyse ausdrücken lässt.

Funktionen #

Grundlegende Aggregatfunktionen #

Diese Funktionen sind in .dml und in Model Query SQL gültig. In .dml aggregieren sie Rohspalten (SUM({Verkaufsbetrag})) oder Kennzahlen auf einer feineren Detailebene (SUM({Umsatz: {+d: Produkt}})). In Model Query SQL aggregieren sie ausschließlich Kennzahlen auf einer feineren Detailebene. Beispielsweise summiert SUM(AGG({Umsatz: {+d: Produkt}})) die Umsätze je Produkt zu einem Gesamtumsatz. Verwenden Sie für eine einfache Kennzahlreferenz nur AGG(measure).

Funktion Syntax Beschreibung
SUM SUM({column}) Summe
COUNT COUNT({column}) Anzahl der Nicht-NULL-Werte
COUNT(DISTINCT ...) COUNT(DISTINCT {column}) Anzahl unterschiedlicher Werte
MAX MAX({column}) Maximum
MIN MIN({column}) Minimum
AVG AVG({column}) Mittelwert

DML-spezifische Funktionen #

Die Spalte „Kontext“ gibt an, wo eine Funktion in einem gültigen Kennzahlausdruck vorkommen kann. In Model Query SQL müssen Kennzahlen weiterhin über AGG(...) aggregiert werden. Diese Funktionen erlauben keine Aggregation von Rohspalten in SELECT.

Funktion Syntax Kontext Beschreibung
AGG() AGG(measure) Nur Model Query SQL Referenziert eine Kennzahl in Abfragen (keine Aggregatfunktion)
DIVIDE() DIVIDE({num}, {den}) Beide Sichere Division (liefert bei Division durch null NULL)
DISTINCTCOUNT() DISTINCTCOUNT({column}) Beide Zählt unterschiedliche Werte
SUMIF SUMIF({val}, {condition}) Beide Bedingte Summe
COUNTIF COUNTIF({condition}) / COUNTIF({val}, {condition}) Beide Zeilen, die die Bedingung erfüllen, bzw. Nicht-NULL-Werte, die die Bedingung erfüllen
AVGIF AVGIF({val}, {condition}) Beide Bedingter Mittelwert
MAXIF MAXIF({val}, {condition}) Beide Bedingtes Maximum
MINIF MINIF({val}, {condition}) Beide Bedingtes Minimum
DISTINCTCOUNTIF DISTINCTCOUNTIF({val}, {condition}) Beide Bedingte Zählung unterschiedlicher Werte

Beispiele für bedingte Aggregation:

# In .dml
UmsatzAbgeschlossenerBestellungen:
    type: measure
    formula: SUMIF({Verkaufsbetrag}, {Bestellstatus} = 'completed')

AnzahlWertvollerKunden:
    type: measure
    formula: 'DISTINCTCOUNTIF({Kundennummer}, {Umsatz: {+d: Kundennummer}} > 1000)'

-- In Model Query SQL (modifier form)
SELECT AGG(Umsatz, '+f', Region = 'North') FROM MODEL

Bedingungs- und Hilfsfunktionen #

Funktion Syntax Beschreibung
IIF IIF(condition, true_val, false_val) Inline-Bedingungsausdruck
ISNULL / IFNULL / COALESCE ISNULL({expr}, default) Ersten Nicht-NULL-Wert zurückgeben
NULLIF NULLIF({a}, {b}) Bei a = b den Wert NULL zurückgeben

Hilfsfunktionen verwenden die SQL-Ausdrucksebene. Sie sind in Formeln zulässig, zählen aber nicht zu den kanonischen intrinsischen Symbolen von DML. Im Funktionskatalog von DML ist diese Einstufung Funktionen vorbehalten, die DML selbst definiert, etwa AGG, DIVIDE und SUMIF.

Wenn die äußerste Operation einer Kennzahlformel eine NULL-Koaleszenz mit einem Literal als Ersatzwert ist, wird an den Verwendungsstellen dieser Kennzahl das Auffüllen fehlender Zeilen aktiviert.

Tagesumsatz:
    type: measure
    formula: SUM(ISNULL({Umsatz: {+d: dt_date}}, 0))

Datumsfunktionen (SQLite-Dialekt) #

Funktion Syntax Beschreibung
date() date(current_date) Aktuelles Datum
date(current_date, 'start of month') — Erster Tag des aktuellen Monats
date(current_date, 'start of month', '-1 month') — Erster Tag des vorherigen Monats
date(current_date, 'start of year') — Erster Tag des aktuellen Jahres
date(current_date, '-N days') — Vor N Tagen

Hinweis zum Dialekt: Stimmen Sie Ihre Datumsfunktionen auf den Zieldialekt ab. DML unterstützt eine Datumsausdruckssprache nach dem Vorbild von SQLite und übersetzt unterstützte Formen in den ausgewählten Dialekt. Prüfen Sie das erzeugte SQL. Die Zieldatenbank akzeptiert den ursprünglichen Ausdruckstext möglicherweise nicht direkt.

Modifikatorsyntax in Model Query SQL #

Zwei gleichwertige Schreibweisen in Model Query SQL:

Form Syntax Beispiel
Mit Positionsargument AGG(measure, 'mod1', 'mod2') AGG(Umsatz, 'yoy')
Mit geschweiften Klammern AGG({measure: mod}) AGG({Umsatz: yoy})

Aliasregeln: Die maßgebliche Tabelle steht unter Aliasregeln für Model Query. AGG(Umsatz) erhält automatisch einen Alias, bei AGG({Umsatz: yoy}) ist AS erforderlich.

Laufzeitvariablen #

Diese Variablen sind Platzhalter für den Auswertungskontext und keine vom Aufrufer übergebenen Abfrageparameter. Informationen zur Bindung durch die Anwendung finden Sie unter JDBC-Parameter und Abfrageart. Eine geprüfte Bindung auf physischer SQL-Ebene stellt keine semantische Bindung in Model Query her.

Variable Kontext Bedeutung
{dim_dt} Ausdrücke und Modifikatoren mit Zeitbezug Das für den aktuellen Auswertungskontext aufgelöste Standardzeitfeld
{measure} fn-macro-Formel Die aufrufende Kennzahl, die das Makro umschließt
{dt_date}, {dt_week}, {dt_month}, {dt_quarter}, {dt_year} Referenzen auf Standardzeitfelder Das namentlich angegebene Standardzeitfeld

Zeitkontext legt die Regeln für zeitliche Auflösung und Zeiträume fest. Makros definieren erläutert, wie Makros deklariert und Variablen verwendet werden.

In der Datenbank definierte Skalarfunktionen #

Aufrufe von Skalarfunktionen können im generierten SQL erhalten bleiben, auch innerhalb einer atomaren Kennzahl oder wenn sie auf das Ergebnis einer aggregierten Kennzahl angewendet werden. DML bestimmt den Kontext der Kennzahl. Die Zieldatenbank bestimmt, wie die Funktion implementiert ist und ob sie verfügbar ist. Unter Verifizierte benutzerdefinierte Modifikatoren und Datenbankfunktionen finden Sie ein funktionsfähiges Beispiel sowie Informationen zu den Unterschieden zwischen den Auswertungsphasen und zu den Validierungsanforderungen. Diese Aussage gilt nicht pauschal für aggregierende oder tabellenwertige UDFs.

Vollständige Lookup-Beispiele #

pk() erwartet die Argumente in der Reihenfolge der Dimensionen im Zieldatensatz und ist nicht auf einen einzelnen Schlüssel beschränkt. Das Beispiel mit zusammengesetztem Schlüssel deklariert [VerkaufspositionID, Region] und prüft mit validate-only, ob Schlüsselkombinationen im Zieldatensatz mehrfach vorkommen. Das Bereichsbeispiel verwendet [VerkaufspositionID, 'range(valid_from, valid_to)'] und prüft anhand seiner Testdaten, dass die Untergrenze eingeschlossen und die Obergrenze ausgeschlossen ist und dass überlappende Bereiche abgelehnt werden. Diese Beispiele belegen keine Unterstützung für beliebige Wertverteilungen über Viele-zu-viele-Beziehungen.
