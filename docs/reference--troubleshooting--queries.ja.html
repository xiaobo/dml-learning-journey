ここでは、SQL クエリと YAML クエリを扱います。サポートされている構文は、モデルクエリ（SQL）とYAML クエリに記載されています。

P8. 集計クエリでの AGG() の指定漏れ #

誤り：SELECT 商品, 売上高 FROM MODEL GROUP BY 商品 修正：SELECT 商品, AGG(売上高) FROM MODEL GROUP BY 商品

P9. AGG() に不要なエイリアスを付ける #

誤り：SELECT AGG(売上高) as 売上高 修正：SELECT AGG(売上高) には自動的に 売上高 というエイリアスが付きます。

P10. サブクエリを使用する #

誤り：SELECT * FROM MODEL WHERE 売上高 > (SELECT AVG(売上高) FROM MODEL) 修正：HAVING を指標と組み合わせて使用します。例：HAVING AGG(売上高) > AGG(avg_sales)

P11. JOIN を使用する #

誤り：SELECT a.*, b.* FROM MODEL a JOIN MODEL b ON a.売上明細番号 = b.売上明細番号 修正：.dml ファイルで、データセットをまたぐ列マクロまたは pk(...) による参照を使用します。

P12. 時間修飾子に必要な時間コンテキストがない #

誤り：SELECT 商品, AGG({売上高: yoy}) FROM MODEL GROUP BY 商品（グループ化に使う時間フィールドも時間フィルターもありません）

ルール：時間コンテキストを確定し、マクロの前提条件を満たしてください。グループ化に使う時間フィールドを明示する方法が最も明確です。時間フィルターでコンテキストを指定することもできます。読みやすさのため、行や集計値を定義する時間粒度はできるだけ 1 つにそろえてください。

時間コンテキストの参照先：時間修飾子。

正しい例（月単位の前年比）：

SELECT dt_month, AGG(売上高), AGG({売上高: yoy}) FROM MODEL GROUP BY dt_month

正しい例（日単位の YTD）：

SELECT dt_date, AGG(売上高, 'ytd') FROM MODEL WHERE dt_date = date(current_date) GROUP BY dt_date

P13. 異なる時間粒度を混在させる #

推奨：時間粒度はできるだけ 1 つにそろえてください。検証したビルドでは dt_year, dt_month を同時に指定できます。複数のフィールドを指定できても、すべてのマクロの組み合わせで意図した時間コンテキストが得られるとは限りません。確定した時間粒度を確認してください。

P14. 不要な NULL 除外フィルターを追加する #

誤り：明示的な指定がないのに WHERE 顧客 is not null を追加する。修正：質問で明示的に求められた場合にのみ、NULL 値を除外します。

P15. 単一の期間に BETWEEN を使用する #

推奨：dt_month = '2024-01-01' を使うと、1 月を選択することが明確になります。日付範囲は、その範囲を選択する意図がある場合に有効です。範囲の境界を明示し、タイムスタンプと終了日の扱いを確認してください。

P16. 時間フィルターの順序は記述上の慣例 #

条件はどちらの順序でもコンパイルできます。エンジンによる順序の制約はありません。読みやすい順序で条件を記述してください。

P17. 不要な ORDER BY を指定する #

誤り：すべてのクエリに ORDER BY を追加する。修正：ORDER BY は、上位 N 件を取得する場合、または質問で順位付けが明示的に求められた場合にのみ使用します。

P18. 増加率を手動で計算する #

誤り：DIVIDE(AGG(売上高), AGG(売上高, 'ya')) - 1 修正：組み込みの修飾子を使った AGG(売上高, 'yoy') を使用します。

P20. 存在確認に DISTINCT だけを使用する #

誤り：「顧客はいますか？」という質問に SELECT DISTINCT 顧客 FROM MODEL.取引明細 を使用する。修正：SELECT 顧客, dt_date, 取引番号 FROM MODEL.取引明細 LIMIT 1 を使って具体的なレコードを返します。

カテゴリ：DML モデル設計 #

P45. 詳細クエリに指標を指定する #

誤り：指標 total_cost: を選択するクエリに dataset: DATASET_PRODUCTS を指定する。修正：集計モードにするには dataset: を削除します。詳細クエリのままにする場合は、クエリから指標を削除します。

P46. 集計クエリでデータセットを指定せずに列名を使う #

誤り：列が DATASET_PRODUCTS にあるときに、dataset: を指定せずに 商品番号: を記述する。修正：商品番号: "{DATASET_PRODUCTS}.商品番号"。

P47. データセット間でディメンションフィールド名が一致しない #

誤り：DATASET_PT ではディメンション 売上明細番号 を使用し、DATASET_MC では tag_id を使用している。修正：名前を 1 つに統一し（例：tag_id）、columns: でデータウェアハウスの列を対応付けます（tag_id: 売上明細番号）。

P48. dimension: のディメンションフィールドにマッピングを記述する #

誤り：columns: dimension: の下に - f_tag_id: {DATASET_PT}.売上明細番号 を記述する。修正：- f_tag_id のみを列挙し、式 f_tag_id: |- … は別に定義します。

P49. measures: の下にディメンションフィールドを定義する #

誤り：データセットの measures: の下で tag_id: に式を指定する。修正：データセットの dimension: の下で、行を定義する粒度を宣言します。指標は集計にのみ使用します。

P50. クエリの filters: に複雑なフィルターを指定する #

誤り：クエリの filters: に EXISTS サブクエリや、複数のフィールドにわたる PK チェーンを指定する。修正：条件をファクトデータセットの sql: にある WHERE 句へ移動します。

P51. PK チェーンで引数の数が一致しない #

誤り：DATASET_PRODUCTS の複合 PK が (brand_id, tag_id) のときに pk(1, tag_id).{DATASET_PRODUCTS}.state を使用する。修正：pk(brand_id, tag_id).{DATASET_PRODUCTS}.state のように、PK を構成するすべての列を指定します。

P52. after: で GROUP BY を手動で指定する #

誤り：標準的な指標クエリの after: で group by を使って再集計する。修正：指標はクエリブロックで集計します。ディメンションを自動で並べ替えるには after: を省略します。独自の並べ替えや件数制限にこのブロックが必要な場合は、{QUERY} を参照し、ブロックの用途を結果の表示に限ります（select * from {QUERY} に ORDER BY／TOP／LIMIT を追加）。ただし、やむを得ず使用する独自の後処理用 SQL が文書に明記されている場合は例外です。

コマンドと結果の確認方法については、クエリのコンパイルと検証を参照してください。

P60. 集計クエリで MAX による日付の取得にサブクエリを使用する #

誤り：WHERE dt_month = (SELECT MAX(dt_month) FROM MODEL ...) 修正方法：確認に使う月を固定値で指定するか、明細クエリ SELECT MAX(dt_month) FROM MODEL.<dataset> を使用します。

P61. GROUP BY でデータセットを直接集計する #

誤り：SELECT 購入者コード, 品牌, SUM(出荷金額) FROM MODEL.DATASET_X GROUP BY 購入者コード, 品牌 症状：cannot aggregate directly on dataset MODEL.DATASET_X using GROUP BY 修正方法：次のいずれかの方法を使います。(a) model.dml で指標を定義し、FROM MODEL と AGG() を組み合わせて使う。(b) アドホッククエリでは /** dml ... **/ 形式のコメントブロックでインライン指標を定義し、.dml を編集せずに使う（インライン指標（/** dml ... **/）を参照）。

クエリのトラブルシューティング #

まず、指標を 1 つだけ含むクエリでモデルと結合を確認します。次に、ディメンション、フィルター、指標を 1 つずつ戻します。行数が多すぎる場合は、データセット内のキーの重複、結合後の行数、比較期間にのみ現れるキーを確認します。値が一致しない場合は、同じ期間とデータスナップショットを使って別の SQL クエリを実行し、グループごとにキー、NULL、指標の値を照合します。
