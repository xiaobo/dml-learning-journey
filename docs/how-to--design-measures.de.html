Verwenden Sie diesen Leitfaden, wenn der Analyseablauf zeigt, dass eine fachliche Berechnung fehlt. Legen Sie zuerst fest, welche Zeilen die Berechnung umfasst und auf welcher Ebene Zwischenwerte gebildet werden. Wählen Sie dann eine Formel.

Bedingungen in Zwischenspalten für die Auswahl der Zeilen einer Kennzahl #

Verwenden Sie eine Zwischenspalte, wenn eine Bedingung bestimmt, welche Zeilen zu einer einzelnen Kennzahl beitragen, und die Zeilenmenge des Datasets weiterhin fachlich sinnvoll ist. Ordnen Sie Bedingungen nicht anhand von Namen wie state oder delete_time ein. Eine gleich aussehende Bedingung kann auch dauerhaft festlegen, welche Zeilen zur Quelle gehören.

columns:
    GültigerBetrag:
        description: Row-level amount gated by validity checks
        formula: 'iif(state = 1 and delete_time is null, prod_amount, null)'
measures:
    Summe: SUM({GültigerBetrag})

SUM ignoriert NULL. Daher entspricht der aggregierte Wert in Gruppen mit mindestens einer berücksichtigten Zeile der gefilterten Summe. Die Bedingung in der Zwischenspalte ist im Allgemeinen nicht gleichwertig mit einem WHERE auf Quellenebene. Eine Gruppe mit ausschließlich ausgeschlossenen Zeilen entfällt bei WHERE, kann aber mit der Bedingung in der Zwischenspalte als Zeile mit Summe = NULL erhalten bleiben. Auch Zählungen für andere Kennzahlen, Joins, Fensterberechnungen und nachgelagerte Filter können sich ändern.

Verwenden Sie diese Umschreibung erst, wenn das Verhalten von Gruppen mit ausschließlich ausgeschlossenen Zeilen, die Bedingungen für andere Kennzahlen derselben Abfrage und die Zeilenmengen für Distinct-Operationen, Joins und Fensterberechnungen nachgewiesen sind. Weisen Sie auch nach, dass eine fehlende Zeile und eine vorhandene Zeile mit NULL gleichwertig sind. Andernfalls behalten Sie eine Bedingung bei, die Zeilen auf Abfrage- oder Beziehungsebene entfernt, oder verwenden für eine dauerhaft geltende Bedingung der Quelle eine minimale, dokumentierte Ausnahmelösung mit sql: im Dataset.

Beispiel für eine schrittweise Zerlegung: tax_rate_effective (geltenden Steuersatz bestimmen) → amount_excl_tax (Betrag ohne Steuer berechnen) → eligible_amount (Zeilen für die Kennzahl berücksichtigen) → SUM({eligible_amount}) (Measure). Der Compiler setzt diese Zwischenausdrücke direkt in die generierte Abfrage ein. Prüfen Sie das generierte SQL, um zu sehen, wie die Ausdrücke umgesetzt werden und welche Zeilen einfließen.

Abgeleitete Measures #

Wenden Sie berichtsspezifische Modifikatoren dort an, wo die Measure verwendet wird. Definieren Sie eine abgeleitete Measure in .dml nur, wenn der modifizierte Wert überall wiederverwendet werden muss, etwa weil er in einem Objekt vom Typ type: materialize aufgeführt wird, oder wenn er als benannte fachliche Kennzahl definiert werden soll. Verwenden Sie in Measure-Formeln DMX-Referenzen und niemals AGG():

Vormonatsumsatz:
    type: measure
    formula: '{Umsatz: pp}'

UmsatzwachstumZumVorjahr:
    type: measure
    formula: '{Umsatz: yoy}'

Produktumsatz:
    type: measure
    formula: SUM({Umsatz: {+d: Produkt}})

Diese Measures behalten die unter ihrem Namen definierte Transformation bei. Ihre Auswertung hängt weiterhin vom Abfragekontext und von den Regeln für Modifikatoren und Filter ab.

CTEs und mehrstufige Logik #

Wenn Ihr SQL CTEs verwendet, setzen Sie diese auf eine der folgenden Arten um:

  1. Measures mit Modifikatoren (bevorzugt), wenn der CTE nur einen Filter oder ein Dimensionsfeld hinzufügt
  2. Spaltenmakros, wenn der CTE eine abgeleitete Spalte berechnet
  3. Separate Abfragen, wenn der CTE tatsächlich eine Zwischenergebnismenge erzeugt

Beispiel: SQL mit einem CTE, der auf abgeschlossene Bestellungen ("completed orders") filtert

-- Original SQL
WITH completed AS (
    SELECT * FROM orders WHERE status = 'completed'
)
SELECT product, SUM(amount) FROM completed GROUP BY product

# DML approach
UmsatzAbgeschlossenerBestellungen:
    type: measure
    formula: SUM({Verkaufsbetrag: {+f: {Bestellstatus: 'completed'}}})

-- Model Query SQL: retain the row-removing population restriction
SELECT Produkt, AGG(UmsatzAbgeschlossenerBestellungen) FROM MODEL
WHERE Bestellstatus = 'completed'
GROUP BY Produkt

Measures mit Dimensionsbeschränkung #

⚠️ Für eine Measure enthält dimensions: die zulässigen Dimensionen. Jede innere Liste entspricht einer zulässigen Dimension. Die äußere Liste enthält die Alternativen. Diese Einstellung legt weder die Zeilenidentität im Dataset noch die Gruppierung der Abfrage fest. Die Zeilenidentität wird über dimension: im Dataset festgelegt, die Gruppierung über GROUP BY bzw. columns.dimension: in der Abfrage. Siehe Rollen von Dimensionen.

Fügen Sie diese Beschränkung nur hinzu, wenn die Kennzahl mit einer bestimmten Dimension ausgewertet werden muss:

# "Average order value per customer" — customer_id is required during evaluation
DurchschnittlicherBestellwertJeKunde:
    type: measure
    formula: DIVIDE({Umsatz}, {Transaktionsanzahl})
    dimensions:
        - [Kundennummer]    # ← the only allowed dimension

Andere Formeln, die diese Measure verwenden, müssen sie mit {DurchschnittlicherBestellwertJeKunde: {+d: Kundennummer}} explizit nach Kundennummer auswerten und das Ergebnis anschließend auf einer höheren Ebene aggregieren. Dokumentieren Sie die Beschränkung klar. Sie ermöglicht gezielte Berechnungen, kann aber zu unerwarteten Ergebnissen führen.

SQL in Measures umsetzen #

Mit dieser Checkliste setzen Sie eine Kennzahlspezifikation oder vorhandenes SQL (CTEs, JOINs) in DML-Measures und einfaches Model Query SQL (FROM MODEL + AGG(...)) um.

Beginnen Sie mit den Dimensionen, nicht mit dem SQL-Text:

  • Welche Dimension hat die endgültige Abfrage? (z. B. [Kunde] oder [Kunde, dt_month])
  • Welche Dimension gilt für die Zwischenauswertung? (z. B. [Kunde] für den Erstkauf)
  • Wählen Sie die Umsetzung nach Auswertungsdimension: direkt auf der Dataset-Dimension auswerten → atomare Measure, Auswertungsdimension ändern → +d / dimension, die zulässigen Dimensionen beschränken → Measure mit Dimensionsbeschränkung. Prüfen Sie, ob die Ebenen, auf denen Zwischenwerte und Ergebnisse gebildet werden, zueinander passen. Wenn die Logik tatsächlich einen JOIN oder eine Unterabfrage erfordert und sich nicht in DML ausdrücken lässt, halten Sie inne und prüfen Sie den Ansatz erneut. Umgehen Sie die Regeln von Model Query SQL nicht.

Measures mit Dimensionsbeschränkung (Zwischenzeilen wie bei einem CTE abbilden):

  • Definieren Sie eine Measure mit genau einer zulässigen Dimension: dimensions: [[Kundennummer]]
  • Aggregieren Sie mit SUM({that_measure: {+d: Kundennummer}}) (oder mit AVG usw.) auf einer höheren Ebene.
  • dimensions: beschränkt, bei welchen Auswertungsdimensionen die Measure gültig ist. Wird die Measure in einer anderen Formel mit +d referenziert, ergänzt der Modifikator ihre Auswertungsdimension um das erforderliche Dimensionsfeld.
ErsterKaufmonat:
    type: measure
    description: first month with sales > 0 (customer grain only)
    formula: 'MINIF({dt_month}, {Umsatz: {+d: dt_month}} > 0)'
    dimensions:
        - [Kundennummer]

ErstmonatsumsatzJeKunde:
    type: measure
    description: sales in customer's first month (customer grain only)
    formula: 'SUMIF({Umsatz: {+d: dt_month}}, {dt_month} = {ErsterKaufmonat})'
    dimensions:
        - [Kundennummer]

ErstmonatsumsatzGesamt:
    type: measure
    formula: 'SUM({ErstmonatsumsatzJeKunde: {+d: Kundennummer}})'

In einer auf die Kundendimension beschränkten Measure liefert {Umsatz: {+d: dt_month}} den Umsatz des jeweiligen Kunden im jeweiligen Monat.

Wenn Sie ErsterKaufmonat als Abfragedimension verwenden möchten, um einen Bericht danach zu gruppieren, und zugleich andere Measures derselben Abfrage mit +d: Kundennummer ausrichten möchten, ist das Measure-Ergebnis die Abfragedimension. Siehe Measure als Dimension.

Prüfen, ob eine Bedingung mindestens einmal erfüllt wurde (Bindung, Wiederholung):

  • Flag pro Kunde: ISNULL(MAXIF(1, <condition>), 0) mit dimensions: [[Kundennummer]]
  • Anzahl der Kunden mit gesetztem Flag: SUM({flag: {+d: Kundennummer}})
  • Anteil: DIVIDE(total_flag, total_customers)

CTEs in eine oder mehrere Measures umsetzen:

CTE-Muster Umsetzung in DML
Aggregation je Kunde und Monat {Umsatz: {+d: [Kunde, dt_month]}}
Monat des Erstkaufs MINIF({dt_month}, …) auf Kundenebene
Flags pro Kunde MAXIF auf Kundenebene
Endgültiger KPI SUM({customer_measure: {+d: Kundennummer}}) und Verhältniswerte

Zielform der Abfrage: SELECT AGG(kpi_1), AGG(kpi_2), ... FROM MODEL.

+d in Bedingungen von DISTINCTCOUNTIF / SUMIF (Filtern auf einer anderen Ebene als der Aggregation) #

Wenn Sie Entitäten auf einer Ebene zählen und auf einer anderen Ebene filtern, wenden Sie {+d: dimension_field} in der Bedingung auf die Measure an, nicht auf die Spalte.

  • Falsch: DISTINCTCOUNTIF({entity: {+d: entity}}, …) ist ungültig. Modifikatoren sind nur bei Kennzahlen zulässig.
  • Richtig: DISTINCTCOUNTIF({entity}, {Umsatz: {+d: entity}} > 0 AND …)

Kohortenabgrenzung: Definieren Sie den Erstkauf auf einer ausdrücklich festgelegten Entitätsebene und legen Sie den berücksichtigten Verlauf beziehungsweise den Stichtag fest. Vergleichen Sie den Erstkauf anschließend mit dem Beobachtungszeitraum. Verwenden Sie einen benannten Klassifikator erst wieder, nachdem seine zulässigen Dimensionen und die Ebene geprüft wurden, auf der er zugeordnet wird. Wenn Sie einen fehlschlagenden Ausdruck direkt einbetten, können Sie damit weder seine Semantik bestätigen noch eine inkompatible Granularität umgehen. Geprüfte Ausdrucksformen und Fehler in veröffentlichten Versionen finden Sie unter Kennzahl als Dimension.

Rückblickende Kennzahlen für Wiederkäufe #

Formulieren Sie zuerst die fachliche Definition (wer, Beobachtungsmonat, Zeitfenster). Erstellen Sie dann Flags auf Kundenebene und aggregieren Sie sie mit SUM({flag: {+d: Kundennummer}}) oder DISTINCTCOUNTIF(...). Stimmen Sie Änderungen an der Semantik vorher mit der fachlich verantwortlichen Person ab.

Eindeutige Werte auf Berichtsebene neu zählen #

Ein Käufer, der in zwei Monaten vorkommt, zählt in jedem dieser Monate einmal und im Quartal ebenfalls einmal. Definieren Sie buyers: DISTINCTCOUNT({Kundennummer}) im Faktendatensatz. Wenden Sie AGG(buyers) auf das gesamte Quartal an, ohne nach Monaten zu gruppieren, um jeden Käufer im Quartal genau einmal zu zählen. Gruppieren Sie nach Quartal, um mehrere Quartale getrennt auszuweisen.

SUM({buyers: {+d: dt_month}}) addiert die monatlichen Anzahlen eindeutiger Käufer. Im Testlauf ergab das 3,066 Käufer-Monate, während das Quartal 1,248 eindeutige Käufer umfasste. Der geprüfte Build akzeptierte die Summierung ohne strikte Diagnosemeldung. Vergleichen Sie das Ergebnis mit einer direkten Berechnung per COUNT(DISTINCT Kundennummer) über denselben Zeitraum.
