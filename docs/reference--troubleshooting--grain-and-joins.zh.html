筛选条件放置错误 #

症状：[filters]: not supported、cannot derive from dimension、referred column … is undefined

原因：使用 --to-dml 后，谓词仍留在错误的层级。例如，在数据集上指定 filters:（架构完全不允许数据集使用 filters:）、在事实数据的 sql: 中重复设置维度的范围限制，或对跨数据集属性使用查询筛选条件的简写。

解决方法：按语义作用域对每个谓词进行分类（见筛选条件的放置层级）。

症状 移至
[dataset …] [filters]: not supported 查询的 filters:、度量公式或 sql: 中的 WHERE（数据集完全不支持 filters:）
在每个事实分支中重复出现的生命周期或属性谓词 仅当谓词随报表变化时，才使用查询的 filters:。如果谓词用于定义固定的数据总体，则保留能够排除行的写法。
事实数据的 sql: 中 WHERE 子句里的数值谓词或关联谓词 只有在验证了仅含被排除行的分组、同级指标、连接和窗口的行为，以及值缺失与显式存在的 NULL 之间的语义差异后，才使用中间指标进行筛选。
查询过滤器中出现 referred column {DATASET}.col is undefined 字符串形式："{DATASET}.col = value":
包含两个元素的列表 dt_date: ['2024-01-01', '2025-12-31'] 只返回 2 天的数据 直接指定列表会编译为使用 IN (...) 的精确匹配，而非范围匹配。要指定包含两个端点的区间，请使用 dt_date: { range: ['2024-01-01', '2025-12-31'] }。
特定分支的日期窗口 在该数据集上声明 dt_date，并在查询中使用 filters: dt_date: range: [...]。

使用备选查找的资格规则可能使连接变得更严格 #

“匹配目标维度，或者在无法匹配目标维度时匹配间接维度”这类资格规则使用两个可选关系。如果将派生标志放在查询的 filters: 中，编译生成的 SQL 可能会使其中一个查找变为必需（INNER JOIN），也可能在转换 AND/OR 表达式时丢失回退语义。

建议采用以下结构。

target_state: pk({snapshot_month}, {customer_id}).{TARGET_CUSTOMER}.state
customer_is_eligible: |-
  iif({target_state} = 1, 1,
    iif(pk({customer_id}).{INDIRECT_CUSTOMER}.customer_id is not null, 1, 0))
included_amount: iif({customer_is_eligible} = 1, {amount}, null)

measures:
  amount: SUM({included_amount})

然后检查生成的 SQL。两个查找都必须保留为 LEFT JOIN，回退逻辑必须留在 CASE 内。如果需要对输出分组加以限制，应复用已选定的主要度量（HAVING AGG(amount) is not null），避免结果中带入额外的隐藏列。将键不唯一以及目标维度与间接维度重叠视为诊断线索。DML 关系不应悄然重现意外的行数膨胀。

P43. {dimension: [...]} 与 {-d: dim_dt} 的对比（SQL 结构不同） #

错误：在基准 SQL 已经使用独立的 GROUP BY CTE 在更粗粒度上聚合的情况下，仍使用 {-d: dim_dt}。解决方法：使结构与基准一致。{dimension: [cols]} 强制生成独立的聚合 CTE，而 {-d: dim_dt} 使用窗口表达式 OVER (PARTITION BY …)。参见 P44 和 P45。

P44. 窗口内占比与 {-d: dim} 的对比 #

错误：将 --to-dml 生成的草稿 divide({m}, {m_minus_dim_X}) 直接用作最终的业务 DML。解决方法：在查询的 columns: 或度量中使用 divide({m}*1.0, {m: {-d: dim}})。参见维度和筛选修饰符。

等同于 Model Query SQL。这里介绍 YAML 特有的常见陷阱。完整规则见YAML 查询声明。

P62. 将度量的 dimensions: 用于标识数据集行或对查询分组 #

症状：在度量上写入 dimensions: [[region]]，期望它像数据集的 dimension: 一样，让查询输出按 region 分组。实际编译查询时不会生成该分组，或者查询在使用其他维度时失败。错误理解：度量的 dimensions: 用于声明数据集如何标识行，或控制查询如何分组。正确理解：度量的 dimensions: 包含允许使用的维度。每个内层列表表示一个维度，外层列表列出可选项。数据集行的标识由数据集的 dimension: 定义，分组由查询的 GROUP BY 或 columns.dimension: 指定。解决方法：除非指标确实需要限定为这些允许使用的维度，否则请移除度量的 dimensions:。在查询中指定结果分组（GROUP BY / columns.dimension:）。

# Wrong: expecting dimensions: to produce GROUP BY region
sales:
    type: measure
    dataset: transactions
    formula: SUM({amount})
    dimensions:
        - [region]

# Right: no dimensions: lock; grouping lives in the query
sales:
    type: measure
    dataset: transactions
    formula: SUM({amount})
# SELECT region, AGG(sales) FROM MODEL GROUP BY region

维度角色的具体约定见维度角色。

P64. 在度量上设置 materialize: true #

症状：编译时出现 ERROR error during processing [ref null]: undefined modifier 'materialize'，该度量被静默丢弃（0 measure(s) processed）。错误：在度量定义中添加 materialize: true，期望编译器对该度量进行预聚合。度量级别没有物化标志（已在 dmlc 0.3.16 中使用 dmlc -c 验证）。解决方法：使用顶层 type: materialize 对象（parameters: + dimension: + measures:），或在数据集级别使用 materialize: <name> 来声明物化。切勿在度量上声明物化。参见物化定义（type: materialize）和物化示例。

# Wrong
sales:
    type: measure
    dataset: transactions
    formula: SUM({amount})
    materialize: true   # ← undefined modifier 'materialize'

# Right
DWS_SALES:
    type: materialize
    parameters:
        dt_date: date
    dimension: [dt_date, product]
    measures: [sales]

P66. 在未显式指定实体键的情况下将度量用作维度 #

症状：编译要求通过 +d 或 dimension: 显式指定实体键。优先使用 +d，并在使用替换维度的写法之前阅读版本限制。错误：使用未指定键的度量，期望另一个输出度量为它提供或隐式确定实体粒度。解决方法：在将度量用作维度的位置声明完整的实体键。如果作为输入的度量显式带有该键，就可以在外层使用内联标量函数。参见将度量用作维度。

# Wrong
dimension:
    - payment_day

# Right, inline scalar
dimension:
    - payment_day: 'cast({authorization_ts: {+d: payment_id}} as date)'

P67. 由指标派生的维度不兼容或存在依赖关系 #

现象：编译时报告分类键不兼容，或标签之间存在依赖关系。错误用法：一个标签使用 {+d: store_id}，另一个标签使用 {+d: customer_id}，或一个标签引用同一查询中声明的另一个标签。修正方法：让相互独立的标签使用相同的完整实体键。键字段的顺序可以不同。如果标签确实定义在不同粒度上，请单独建模为关系或可复用的业务指标。

P68. 无法将输出指标从分类粒度汇总到更粗粒度 #

现象：编译时报告缺少聚合，或无法重新聚合。错误用法：直接输出 {sales: {+d: store_id}}、对已计算出的去重计数求和，或在未定义所需权重的情况下对比率求平均值。修正方法：用所需的聚合函数包裹较细粒度的引用，例如 SUM({sales: {+d: store_id}})。对于比率，先汇总各组成部分，再重新计算比率。对于去重计数、中位数、百分位数及类似指标，请保留适用的输入或聚合状态，或单独定义一个受支持的指标。否则，只能接受编译错误。

P69. 将细粒度的 WHERE 放在粗粒度查询的 filters: 中 #

现象：CTE 先按粒度 (G)（例如商品×地区）聚合，再筛选（cnt > 3），最后用 SUM 汇总到粒度 (Q)（例如商品）。草稿或 --to-dml 生成的查询只包含查询维度 (Q)，并带有 filters: "cnt > 3" 和 SUM({total: {+d: region}})。编译或融合可能将其转换为商品级别的 HAVING COUNT(1) > 3，导致统计范围有误。

错误用法：

filters:
  "cnt > 3":                 # cnt is not defined at product-only grain
columns:
  dimension: [product]
  grand_total: 'SUM({total: {+d: region}})'

另一种错误用法：SUM({total: {+d: region, +f: '{cnt} > 3'}}) 在输入谓词中使用了聚合指标。诊断信息针对该谓词，并不表示禁止对指标引用应用 +f。请参阅功能支持表。

修正方法：在汇总过程中，按共同的细粒度进行筛选。

grand_total: |-
  SUMIF({total: {+d: region}}, {cnt: {+d: region}} > 3)
# No accepted fine rows -> NULL; ELSE 0 would change that result.

查询中的 filters: 仅用于报表或 HAVING 作用域。请参阅使用 +d 进行多级聚合a。

P70. 在原子指标中使用 OVER #

现象：出现 window functions are not allowed in atomic measures。旧版二进制文件则可能生成缺少分区列的无效 SUM(…) OVER (…) … GROUP BY，并以退出码 0 退出。

错误用法：

measures:
  净购进量: 'SUM({qty}) over (partition by {store_id}, {prod_id})'

修正方法：按窗口函数的放置规则，将明细行的 OVER 放在 columns: 下，然后执行原子聚合。

columns:
  net_qty: 'SUM({qty}) over (partition by {store_id}, {prod_id})'
measures:
  sum_net_qty: 'SUM({net_qty})'

GROUP-BY 之后计算的排名或占比仍采用复合指标，使用 {-d:} 或 {-df:}（不指定 dataset:）。相关规则请参阅窗口函数的放置规则。

P71. 在指标的 PARTITION BY 中直接使用 {col} #

现象：出现 … reference is not allowed in PARTITION BY，或出现有关 {dimension:} 或 {-d:} 的提示。

错误用法（用于指标）：SUM({total}) over (partition by {product})。修正方法：

  • 对于明细行的窗口函数，将其移到 columns:，并在其中继续直接引用 {product}。
  • 对于聚合后应用的窗口函数，在复合指标中使用 partition by {-d: region} 或 {dimension: product}。

对于明细行的窗口函数，请勿将 {-d:} 放在数据集的 columns: 下。该处使用直接列引用。

已在 dmlc 0.3.16 上验证（购物篮关联分析迁移，涉及两种商品角色）。这些情况可以顺利通过编译，却会在没有提示的情况下改变语义。请务必检查生成的 ON 子句。

P72. 定义粒度的两个字段指向同一列，导致跨数据集汇总使用错误的连接键 #

现象：严格模式下编译通过，诊断信息为空，但比率有误。例如，提升度的分母是 left_count * left_count，而不是 left_count * right_count。

错误用法：数据集公开了由同一物理列提供的两个字段（left_product_id: '{product_id}'、right_product_id: '{product_id}'），并预期第二种角色的汇总 {sold_baskets: {-df: [left_product_id]}}（或 {dimension: [month, store, right_product_id]}）按 right_product_id 连接。编译器会为汇总到更粗粒度的临时结果的键重新指定别名，并使用第一种角色的键进行连接（support.product = pair.left_product_id）。

修正方法：对每种角色，使用 pk() 在一个 sql: 数据集中查找。该数据集按 (shared dims, product_id) 粒度对源数据分组，并声明 dimension:（P77）。pk() 的键显式指定并按位置匹配，因此左右两侧的键不会合并。也可以仅在不会发生别名冲突的粒度使用 -df 汇总。请检查生成的 SQL，确认其中有两个独立的连接，即 … product_id = t.left_product_id 和 … product_id = t.right_product_id。

P73. 使用 -df 汇总的复合指标会输出仅存在于连接另一侧的行，并可能生成原本不存在的键值 #

现象：从另一个数据集汇总的指标会编译成使用 FULL OUTER JOIN 的复合指标。仅存在于连接伙伴汇总结果中的行也会出现在输出中。连接伙伴的临时结果可能用 max(<col>) 填充缺失的粒度字段，导致没有匹配项的 (month, store, product) 行显示为 left = right = product。这会凭空生成一个商品与自身的配对，而不仅仅是产生 NULL 值。

修正方法：在查询的选择列表中保留一个主指标，使其在仅存在于连接另一侧的行上取值为 NULL，并使用以公式为键的筛选条件约束查询。

filters:
    '{pair_basket_count} is not null':      # formula as key, empty value

编译后，回连处会生成条件 WHERE <primary> IS NOT NULL。确认主指标有值后，生成的 FULL OUTER JOIN 也会简化为 LEFT JOIN。请以生成的 SQL 为准判断最终的连接类型，而不是依据复合指标的模板。请先验证前提条件。任何有效的主分组中，主指标都不得为 NULL，且只有在仅存在于连接另一侧的行没有主指标值时，该筛选条件才有效。（这是对维度修饰符b 的补充。）

P74. 同一物理表上的两个 table: 数据集：合并行为与 -df 粒度的无提示丢失 #

症状：warn during processing [dataset B]: similar dataset(s) [A] exist, consolidate?。随后，如果两个数据集的列集合不同，就会出现 skip dimension column <f> for measure <m> which does not exist in dataset <A>，且汇总会在没有进一步提示的情况下按更粗的粒度聚合（例如用 pk(store_id) 代替 pk(store_id, left_id)）。

已验证（dmlc 0.3.16）：同一张表上的两个 table: 数据集本身不会导致崩溃。最小对称用例可以编译，第二个数据集用于不同角色时，甚至也能正确绑定 -df（right_id = t1.right_id）。两个数据集通过主键自连接合并为一个 #TEMP。但如果只给其中一侧添加列，合并就会使另一数据集的别名字段不再参与 -df 的名称解析。（此前的“重复 table: → NPE”报告误判了原因。崩溃是由 P75 的筛选器写法引起的。）

修复：优先为每张物理表使用一个带别名列的 table: 数据集。必须使用不同角色时，请保持列集合完全相同，并在生成的 SQL 中检查每个汇总临时表的 pk(...)。这里的警告表示语义错误，需要处理。

P75. 查询 filters: 中的指标保护筛选器：写法和失败方式 #

正确写法：'{measure} is not null':。将整个公式用作键，值留空。这样可以在查询粒度上剔除 FOJ 中没有匹配项的行。

错误写法：my_measure: {condition: '...'} → 架构错误（condition 不是筛选器属性）。my_measure: '<expr>' 会将键视为列名。如果该键解析为指标，Query.treat_filters 可能抛出 NPE，而不是输出诊断信息。

修复：直接将公式用作键，并确保引用的指标能在查询粒度上解析。无法解析的指标引用会引发 NPE，而不是返回易读的错误信息。

P76. -df / -d 的参数是已声明的粒度字段名，而非源列名 #

症状：通过绑定（columns.dimension: [..., new_name: '{col}']）重命名查询维度后，出现 column(s) [x] has been specified as -d/-df, but not in dimension [...]。

原因：绑定会生成一个内部字段（new_name__<query>）。修饰符按定义粒度的字段名移除字段，而底层列名已不在粒度定义中。

修复：向 -df / -d / dimension: 传入已声明的粒度字段名。如果仍需按名称移除某个字段，请以该名称将该字段保留在数据集中。

P77. 用 pk() 从聚合关系中查找值：以 sql: 为目标，并在外层指标上设置 dataset: #

症状：使用 MAX(pk(...).{Support}.col) 时出现 dataset must be specified when aggregate non-measure column, did you mean <SupportDataset>?。

规则：

  • pk() 的目标是数据集，也可以直接使用 TABLE(pk_cols) 形式。指标不能作为 pk() 的目标。因此，聚合后的查找值（例如更粗粒度上的 count(distinct …)）需要使用声明了 dimension: 的 sql: 数据集。该数据集会编译为带索引的临时表，可像其他维度一样参与连接。
  • 外层聚合指标遍历使用查找值的数据集中的行。请将 dataset: 设为这个数据集（dataset: BasketProductPair，而非辅助数据集）。
  • 基准查询中对保证匹配的辅助数据集使用的 INNER JOIN 会被编译为 LEFT JOIN。只有查找键来自同一数据总体时，才可接受这种转换。请在例外记录中注明理由。

P79. 对同一维度同时使用 +d 和 -d / -df #

错误行为：{销量: {+d: 门店, -d: 门店}} 或 {销量: {+d: 门店, -df: 门店}} 被接受，并分别改写为简化形式 {销量} 或 {-f: 门店}。

原因：不存在唯一的隐式解释。让修饰符相互抵消会掩盖拼写错误。对于 AVG，细粒度求值与直接引用所处的求值阶段不同。如果输出粒度已包含该字段，则 -df ≠ -f。

修复：明确指定一个预期的求值阶段。可以直接引用、显式指定细粒度引用并在外层聚合，或使用移除修饰符。作用于不同字段的修饰符仍可并用。本次检查的构建版本接受了所检查的冲突，未给出诊断信息，并在外层求和前重复输出各区域的总计。这违反了必须拒绝此类冲突的约定。请参阅修饰符组合。

P80. -f / -df 导致引用输出粒度之外字段的查询筛选器不再应用于报表行 #

错误行为：查询使用筛选器 {store_id}=1，某个指标使用 {-f: store_id}，且 store_id 不在输出粒度中 → 筛选器被无提示地省略 → 未筛选分支中的 FOJ 对应行出现在结果中。

修复：-f 仅从指标求值中移除筛选器。查询筛选器仍定义纳入查询的行集合。如果被屏蔽的筛选器无法引用输出列，请使用带 EXISTS 的相关子查询或半连接限制结果行。不要仅通过 -f 改变分组。

P81. 使用 dimension: 跨粒度替换时间维度，未通过日历映射分发结果 #

错误行为：在 dt_month 粒度的查询中使用 {销量: {dimension: [dt_quarter]}}，会附加单个标量值，或者无法从月粒度的 CTE 中解析 dt_quarter。

修复：通过日历将月份或日期映射到季度，按季度粒度求值，再将季度总计分发到该季度的每个月份行（采用 nullpk(pk(dt_month).CAL.dt_quarter) 模式）。可加性的 SUM 可以对月度值再次聚合。非可加指标需要基于事实数据按较粗粒度计算。

P78. sql: 转义块必须内置限定统计总体和时间窗口的谓词 #

现象：查询中的 dt_* 范围筛选条件不会被下推到 sql: 块的文本中，而是应用在编译生成的临时派生表的外层 WHERE 子句中。如果转义块内的自连接有一侧没有时间范围限制，统计总体就会在没有提示的情况下扩大（例如，右侧处于报表时间窗口之外的行也会参与配对）。

修复方法：在转义块的内部查询中写入始终生效的统计总体筛选谓词（line_status = 'SOLD'）和对称的时间窗口边界，使连接的每一侧和每个分支都使用相同的纳入条件。通过查询的 filters: 按外层键限定报表范围。当转义块读取由 table: 管理的物理表时，使用 from {Dataset}（P22b）进行引用，切勿直接使用物理表名。
