DML lässt sich auf zwei Ebenen erweitern: Sie können wiederverwendbare Transformationen für Kennzahlen und Zeitbezüge in DML definieren oder Skalarfunktionen aufrufen, die in der Zieldatenbank installiert sind. Benutzerdefinierte Modifikatoren lassen sich mit Kennzahlreferenzen kombinieren. Die Implementierung der Berechnungen von Datenbankfunktionen liegt in der jeweiligen Datenbank.

Verwenden Sie ein benutzerdefiniertes Makro, um eine Zeittransformation oder eine Formel für eine beim Aufruf gewählte Kennzahl wiederzuverwenden. Die Regeln für Aufruf und Kombination finden Sie in der Modifikatorreferenz.

Benutzerdefinierte Makros definieren (dt-macro und fn-macro) #

In .dml können Sie eigene Makros definieren, sowohl dt-macro (zum Verschieben von Zeitbereichen) als auch fn-macro (zum Einbetten von Kennzahlen in Formeln). Definieren Sie ein Makro einmal und referenzieren Sie es dann wie einen integrierten Modifikator in jeder Kennzahl oder Abfrage über seinen Namen.

Zwei Makrotypen

Typ Zweck Zentrale Eigenschaft Platzhalter {measure}
dt-macro Zeitfenster verschieben oder erweitern value: (Verschiebung um einen einzelnen Zeitversatz) oder range: [start, end] Nein, das Makro arbeitet mit dem Zeitkontext.
fn-macro Die Kennzahl in eine abgeleitete Formel einbetten formula: mit {measure} Ja, der Platzhalter wird durch die beim Aufruf angegebene Kennzahl ersetzt.

Verwenden Sie value: zum Verschieben eines Zeitpunkts und range: [start, end] für ein Zeitfenster. Ein fn-macro verwendet {measure} für die beim Aufruf angegebene Kennzahl. Ein dt-macro verwendet {dim_dt} für das ermittelte Zeitfeld. Mit der optionalen Eigenschaft prerequisite: können Sie einschränken, auf welchen Ebenen Zeilen oder Summen für die Auswertung definiert sein dürfen.

Erweiterungspunkt auswählen #

Ziel Geeignetes Mittel Was Sie pflegen
Dieselbe Berechnung auf mehrere Kennzahlen anwenden fn-macro Eine DML-Formel, die {measure} verwendet
Eine Zeitverschiebung oder ein Zeitfenster wiederverwenden dt-macro Eine DML-Zeittransformation
Eine vorhandene Berechnung in der Datenbank wiederverwenden Aufruf einer Skalarfunktion der Datenbank Die Datenbankfunktion, ihre Berechtigungen und ihre Bereitstellung

Mit benutzerdefinierten Modifikatoren legen Sie die fachliche Logik im Modell fest. Für den Aufruf gilt dieselbe Syntax wie bei integrierten Modifikatoren. Datenbankfunktionen greifen auf Logik direkt in der Datenbank zurück und hängen damit von deren Funktionsimplementierung ab. Bei beiden Varianten müssen Sie die passende Ebene wählen, auf der Zeilen oder Summen für die Auswertung definiert sind.

Geprüftes Beispiel für die Kombination von Modifikatoren #

Benutzerdefinierte Modifikatoren werden genauso referenziert wie integrierte Modifikatoren. Änderungen am Compiler sind dafür nicht erforderlich.

Beginnen Sie mit zwei Verkäufen in einer isolierten DuckDB-Übungsdatenbank:

CREATE TABLE sales(id INTEGER, dt_month DATE, amount DECIMAL(12,2));
INSERT INTO sales VALUES
  (1, DATE '2025-01-01', 20),
  (2, DATE '2025-02-01', 30);

Speichern Sie dieses vollständige Modell als model.dml:

dialect: duckdb
S:
  type: dataset
  table: sales
  dimension: [id]
  columns:
    id:
    dt_month:
    amount:
  measures:
    sales: SUM({amount})
double_value:
  type: fn-macro
  formula: '{measure} * 2'
prior_month:
  type: dt-macro
  value: date({dim_dt}, '-1 month')

Bei einem Umsatz von 20 im Januar und 30 im Februar gilt:

SELECT AGG({sales: double_value}) AS doubled,
       AGG({sales: prior_month}) AS previous,
       AGG({sales: {double_value, prior_month}}) AS previous_doubled
FROM MODEL
WHERE dt_month = '2025-02-01'

Speichern Sie die Abfrage als query.sql. Konfigurieren Sie die Übungsdatenbank als default und führen Sie Folgendes aus:

dmlc --compile --strict query.sql --model=model.dml --json
dmlc --validate query.sql --model=model.dml --connection=default --json
dmlc query.sql --model=model.dml --connection=default

Die Ausführung ergab die Werte 60, 20 und 40. Die strikte Kompilierung, der Modus validate-only und die Ausführung waren auf der geprüften DuckDB-Verbindung erfolgreich. Das Modell deklarierte dialect: duckdb, eine eindeutige Quell-ID id sowie dt_month und sales: SUM({amount}).

Diese Kombination ist auf Sprachebene wiederverwendbar. Das Makro erhält die beim Aufruf angegebene Kennzahl und ihren Auswertungskontext. Es handelt sich nicht um eine API für beliebige Compiler-Plug-ins. Die Regeln zur Auswertungsebene, zu den zeitbezogenen Voraussetzungen und zur Reihenfolge der Modifikatoren gelten weiterhin. Ein eigener Name umgeht diese Regeln nicht.

Eine in Ihrer Datenbank definierte Funktion aufrufen #

DML kann Aufrufe von Skalarfunktionen im generierten SQL beibehalten. Die Datenbank stellt die Implementierung bereit. Installieren Sie zum Beispiel die folgende Funktion in der DuckDB-Übungsdatenbank, bevor Sie DML ausführen:

CREATE FUNCTION business_net(x) AS x * 0.8;

DuckDB implementiert diese Form als persistentes SQL-Skalarmakro. Das Beispiel prüft den Aufruf einer in der Datenbank definierten Skalarfunktion. Die Registrierung einer Python-UDF, Aggregat-UDFs und tabellenwertige Funktionen werden dabei nicht geprüft.

Fügen Sie unter S.measures neben sales den folgenden Eintrag hinzu, um die Funktion vor der Aggregation auf die Quellwerte anzuwenden:

# Under the sales dataset's measures:
net_sales: SUM(business_net({amount}))

Vergleichen Sie diese Kennzahl anschließend mit einem Funktionsaufruf auf dem aggregierten Ergebnis:

SELECT AGG(net_sales), business_net(AGG(sales)) AS net_total
FROM MODEL
WHERE dt_month = '2025-02-01'

Bei einem Februarumsatz von 30 ergaben beide Varianten 24. Das generierte SQL behielt SUM(business_net(amount)) und business_net(SUM(amount)) bei. Die Funktionsaufrufe erfolgen in unterschiedlichen Auswertungsphasen. Hier führt die Linearität der Funktion zum gleichen Ergebnis. Rundungen, Schwellenwerte oder andere nichtlineare Funktionen können zu unterschiedlichen Ergebnissen führen. Wählen Sie daher gezielt, in welcher Phase die Funktion ausgewertet wird.

Die Funktion auf der vorgesehenen Verbindung validieren #

DML installiert die Funktion nicht und schreibt ihre Implementierung nicht für andere Datenbanken um. Die Funktion muss für die ausführende Verbindung sichtbar sein, die Typen der generierten Argumente akzeptieren und für den jeweiligen Datenbankbenutzer zur Ausführung freigegeben sein. Funktionsnamen, Schemaqualifizierung, Bereitstellung und Portabilität hängen von der jeweiligen Datenbank ab.

Der Aufruf einer absichtlich fehlenden Funktion bestand die strikte Kompilierung. Der anschließende Lauf im Modus validate-only schlug bei EXPLAIN fehl (Exitcode 65). Auch die direkte Ausführung schlug fehl (Exitcode 70). Eine erfolgreiche Kompilierung allein belegt daher nicht, dass eine UDF existiert oder aufgerufen werden kann. Verwenden Sie Kompilieren und Validieren und vergleichen Sie anschließend die tatsächlichen Ergebnisse.

Was geprüft wurde #

Die obigen Beispiele wurden mit dmlc 0.3.16 (SHA-256-Prüfsumme der ausführbaren Datei: c019a84c3208aee31cb5fa068232fa24d3258e9cdc83dfc2a91584a86a5ba091) und DuckDB 1.5.5 ausgeführt. Geprüft wurden benutzerdefinierte fn-macro und dt-macro, deren Kombination, Aufrufe von Skalarfunktionen auf Quellwerten und auf aggregierten Ergebnissen sowie die Diagnose fehlender Funktionen. Andere Datenbank-Engines, schemaqualifizierte Namen, prozedurale und native UDFs, Aggregat-UDFs und Tabellenfunktionen wurden hier nicht getestet.
