如果分析流程发现缺少某项业务计算，请使用本指南。选择公式之前，先确定计算涵盖哪些行，以及在哪个层级计算中间值。

在中间列中定义指标的纳入条件 #

如果某个条件只决定哪些行计入一项指标，而数据集的整体行范围仍具有业务意义，请使用中间列。不要根据 state 或 delete_time 等名称判断条件的用途。看起来相同的条件也可能用于长期界定数据源包含哪些行。

columns:
    有效金额:
        description: Row-level amount gated by validity checks
        formula: 'iif(state = 1 and delete_time is null, prod_amount, null)'
measures:
    合计: SUM({有效金额})

SUM 会忽略 NULL，因此，只要组内至少有一行满足条件，聚合值就与筛选后的求和结果相同。中间列中的条件通常不等价于在数据源上使用 WHERE。如果组内没有任何行满足条件，该组在 WHERE 下会消失，但使用中间列中的条件时，该组仍可能保留为一行（合计 = NULL）。同一查询中的其他计数、连接、窗口计算和下游筛选也可能发生变化。

只有在验证以下各项后，才能使用这种改写：组内没有满足条件的行时的行为、同一查询中其他指标的纳入条件、去重、连接和窗口计算各自涉及的行范围，以及行缺失与存在一行且值为 NULL 是否等价。否则，请保留查询或关系层级上会移除行的条件。如果是数据源必须始终满足的条件，也可以在数据集中使用最少量的 sql: 作为例外，并记录其用途。

分步计算示例： tax_rate_effective（确定适用税率）→ amount_excl_tax（换算为不含税金额）→ eligible_amount（判断哪些行计入指标）→ SUM({eligible_amount})（度量）。编译器会内联这些中间表达式。检查生成的 SQL，验证表达式的转换方式及其对纳入行范围的影响。

派生度量 #

报表专用的修饰符应在使用度量的地方应用。只有当修改后的值必须在所有使用处复用（例如列在 type: materialize 对象中），或者必须定义为具名业务指标时，才在 .dml 中定义派生度量。度量公式应使用 DMX 引用，绝不能使用 AGG()：

上月销售额:
    type: measure
    formula: '{销售额: pp}'

销售额同比增长率:
    type: measure
    formula: '{销售额: yoy}'

商品销售额:
    type: measure
    formula: SUM({销售额: {+d: 商品}})

这些度量会保留各自名称所对应的转换。求值仍取决于查询上下文以及修饰符和筛选规则。

CTE 与多步骤逻辑 #

如果 SQL 使用了 CTE，请采用以下方式之一改写：

  1. 带修饰符的度量（首选）：CTE 只添加筛选条件或维度字段时
  2. 列宏：CTE 计算派生列时
  3. 独立查询：CTE 确实生成中间结果集时

示例：使用 CTE 筛选已完成订单（"completed orders"）的 SQL

-- Original SQL
WITH completed AS (
    SELECT * FROM orders WHERE status = 'completed'
)
SELECT product, SUM(amount) FROM completed GROUP BY product

# DML approach
已完成订单销售额:
    type: measure
    formula: SUM({销售金额: {+f: {订单状态: 'completed'}}})

-- Model Query SQL: retain the row-removing population restriction
SELECT 商品, AGG(已完成订单销售额) FROM MODEL
WHERE 订单状态 = 'completed'
GROUP BY 商品

带维度约束的度量 #

⚠️ 度量的 dimensions: 列出允许使用的维度。 每个内层列表表示一个允许使用的维度，外层列表列出备选项。此设置不定义数据集中的行标识，也不定义查询分组。行标识由数据集中的 dimension: 定义，查询分组由查询中的 GROUP BY 或 columns.dimension: 定义。参见维度的作用。

只有当指标必须按特定维度求值时，才添加此约束：

# "Average order value per customer" — customer_id is required during evaluation
客户平均订单金额:
    type: measure
    formula: DIVIDE({销售额}, {交易笔数})
    dimensions:
        - [客户编号]    # ← the only allowed dimension

其他公式使用此度量时，必须显式写出 {客户平均订单金额: {+d: 客户编号}}，先按 客户编号 求值，再向上汇总。请明确记录此约束。它可以控制求值层级，但也可能产生意外结果。

将 SQL 转换为度量 #

使用此清单，将指标规格或现有 SQL（CTE、JOIN）转换为 DML 度量和简单的 Model Query SQL（FROM MODEL + AGG(...)）。

从维度入手，而不是从 SQL 文本入手：

  • 最终查询使用什么维度？（例如 [客户] 或 [客户, dt_month]）
  • 中间求值使用什么维度？（例如，计算首次购买时使用 [客户]）
  • 按求值维度选择实现方式：直接在数据集维度上求值 → 原子度量；修改求值维度 → +d / dimension；限制允许使用的维度 → 带维度约束的度量。确认中间值与最终结果的计算层级相容。如果逻辑确实需要 JOIN 或子查询，且无法用 DML 表达，请暂停并重新评估。不要绕过 Model Query SQL 的规则。

带维度约束的度量（表示类似 CTE 的中间行）：

  • 定义仅允许一个维度的度量：dimensions: [[客户编号]]
  • 使用 SUM({that_measure: {+d: 客户编号}})（或 AVG 等）向上汇总。
  • dimensions: 限制度量在哪些维度下有效。在另一个公式中对该度量使用 +d，会把所需的维度字段加入该度量的求值维度。
首次购买月份:
    type: measure
    description: first month with sales > 0 (customer grain only)
    formula: 'MINIF({dt_month}, {销售额: {+d: dt_month}} > 0)'
    dimensions:
        - [客户编号]

各客户首月销售额:
    type: measure
    description: sales in customer's first month (customer grain only)
    formula: 'SUMIF({销售额: {+d: dt_month}}, {dt_month} = {首次购买月份})'
    dimensions:
        - [客户编号]

首月销售额合计:
    type: measure
    formula: 'SUM({各客户首月销售额: {+d: 客户编号}})'

在受客户维度约束的度量中，{销售额: {+d: dt_month}} 表示该客户在该月的销售额。

要对报表分组，请使用 首次购买月份 作为分组依据（查询维度 = 度量结果）。有关如何这样分组并用 +d: 客户编号 对齐同一查询中的其他度量，请参见将度量用作维度。

判断是否至少满足过一次条件的逻辑（留存、重复行为）：

  • 客户级标记：使用 ISNULL(MAXIF(1, <condition>), 0)，并设置 dimensions: [[客户编号]]
  • 标记为 1 的客户总数：SUM({flag: {+d: 客户编号}})
  • 比例：DIVIDE(total_flag, total_customers)

将 CTE 转换为一个或多个度量：

CTE 模式 DML 实现方式
按客户和月份组合聚合 {销售额: {+d: [客户, dt_month]}}
首次购买月份 在客户层级计算 MINIF({dt_month}, …)
按客户设置的标记 在客户层级计算 MAXIF
最终 KPI SUM({customer_measure: {+d: 客户编号}}) 和比率

目标查询形式为 SELECT AGG(kpi_1), AGG(kpi_2), ... FROM MODEL。

在 DISTINCTCOUNTIF / SUMIF 的条件中使用 +d（在不同于聚合的层级上筛选） #

如果在一个层级统计实体、在另一个层级筛选，请将 {+d: dimension_field} 应用于条件中的度量，不要应用于列。

  • 错误：DISTINCTCOUNTIF({entity: {+d: entity}}, …) 无效。修饰符只能用于指标。
  • 正确：DISTINCTCOUNTIF({entity}, {销售额: {+d: entity}} > 0 AND …)

队列范围： 明确首次购买按哪一级实体定义，并指定所用历史数据的范围或截至时点，然后将首次购买与观察期进行比较。只有在验证了允许使用的维度和应用该分类器的粒度后，才能复用命名分类器。将失败的表达式直接内联，既不能证明其语义正确，也不能绕过粒度不兼容的问题。有关已验证的表达式形式和发布版本中的缺陷，请参阅将指标用作维度。

回溯性复购指标 #

先用一句话写清业务定义（统计对象、观察月份、时间窗口）。按客户设置标志，再用 SUM({flag: {+d: 客户编号}}) 或 DISTINCTCOUNTIF(...) 聚合。更改语义前，请与业务负责人共同审查。

按报表粒度重新计算去重计数 #

在两个月都出现的买家，在这两个月中各计一次，在整个季度也只计一次。在事实数据集上定义 buyers: DISTINCTCOUNT({客户编号})。要统计季度内的去重买家数，请对整个季度使用 AGG(buyers)，且不按月分组。要分别报告多个季度的结果，请按季度分组。

SUM({buyers: {+d: dt_month}}) 将各月的去重买家数相加。试验中，这得到了 3,066 个买家与月份的组合，而整个季度有 1,248 位不同的买家。试验中检查的构建版本接受了这一求和操作，未给出严格的诊断提示。请与直接对同一时段应用 COUNT(DISTINCT 客户编号) 得到的结果进行比较。
