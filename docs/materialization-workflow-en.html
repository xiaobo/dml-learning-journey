Materialization: from declaration to confirmed results

On this page
  • 1. Save the un-optimized result
  • 2. Declare and install
  • 3. Confirm hits and compare results
  • 4. Update and invalidate
  • 5. Keep the evidence

Check three things: correct results, query hits the materialization, and results stay correct after updates. Adding a declaration or seeing shorter SQL does not prove the optimization is done.

Prerequisites: you have the compiler and a target connection, and the un-materialized query has been verified. This is an operating procedure, not a compatibility claim verified on every database.

1. Save the un-optimized result #

Fix the data and filters, and save the original result, the generated SQL, and the full key set. Choose additive measures such as sales amount, cost, and transaction count; a margin must be recalculated, never accumulated as a ratio. Grain design explains how to keep the fields later queries need.

2. Declare and install #

Pick the grain, measures, and allowed materializations following the declaration reference. Check the current version's help, then run in an isolated practice database:

dmlc --advanced-help
dmlc --setup model.dml --connection=default

Setup installs the database materialization procedures and is a write operation. Check the complete diagnostics. Regular queries may install or refresh required procedures on demand; actual behavior depends on the current version and connection.

3. Confirm hits and compare results #

dmlc --validate query.sql --model=model.dml --connection=default --json
dmlc query.sql --model=model.dml --connection=default --output=optimized.json --replace

Check whether the generated SQL or execution plan reads the expected summary object. Compare against the un-optimized result key by key and column by column; independently check duplicate rows, missing groups, NULLs, and unformatted ratios. Vary dimensions and filters and check again — do not assume every question hits the same summary.

4. Update and invalidate #

Add a known record to the practice database, calculate first which results should change, then run the query. Check that the cache is refreshed and the output changes. If diagnostics ask for a new setup, run setup for the same model and connection, then retest. Do not hand-edit generated tables to hide problems.

SQL Server separates query preparation from change refreshes, and a synchronized singleton runner performs the builds. Execute the generated prepare_sql; it centralizes preparation, waiting, and the actual readiness check, and returns data_ready=1 normally before you run the business sql. Stop the query on error or wait timeout, remove the cause, and retry.

Use DML_MAZ_PROGRESS to see pending work, runner state, and the estimated time to drain; consult other statistics columns as needed. The global progress view does not replace the per-query readiness check. Run the generated setup_sql at deployment time. For parameters, invalidate-only, and recovery steps see prepare and refresh conventions; for a full exercise see monthly and quarterly summaries.

Record source changes, refresh actions, the objects hit, and the new results. Without this step you cannot claim "updates in real time". Verify each connection's refresh mechanism and permission requirements separately.

5. Keep the evidence #

Check Evidence
Correctness Results before and after optimization, and the differences
Hits The actual object in the SQL or execution plan
Refresh Change records, refresh actions, and the new results
Effect Plans on the same data and definitions; state cache state and repetition count when quoting timings

This page adds the operating procedure only and makes no new materialization claims. Declaration examples are not database compatibility reports.
