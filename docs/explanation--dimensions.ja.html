データセットのモデリング、指標の記述、クエリのコンパイル、行が増える原因の調査を行う際に、このガイドでディメンションの動作を確認できます。このガイドでは言語モデルを説明します。仕様の正式な参照先はDMLの評価セマンティクスです。

1. オブジェクトモデル #

ディメンションフィールドとは、名前を持つ 1 つの DML フィールドです。

ディメンションは、1 つ以上のディメンションフィールドを含むリストです。

例：

[order_id]
[order_id, line_id]
[product_id, dt_month]

上の各行は 1 つのディメンションです。[商品番号, dt_month] は、2 つのフィールドを含む 1 つのディメンションです。

指標の dimensions: では、評価に使えるディメンションの候補を複数指定できるため、リストが 1 段深くなります。

dimensions:
  - [顧客番号]
  - [account_id, dt_month]

外側のリストには、許可されるディメンションが 2 つ含まれています。内側の各リストが 1 つのディメンションです。

総計にはディメンションがありません。指標修飾子の構文では、{dimension: []} で評価ディメンションを解除し、総計のコンテキストを指定します。空のリストは操作を表すものであり、フィールドが 0 個のディメンションではありません。

2. ディメンションの 5 つの役割 #

リストの構造は同じですが、動作は DML 内での記述位置によって決まります。

DML 内での記述位置 役割 動作
データセットの dimension: データセットディメンション 値の組み合わせ全体で 1 つのソース行を識別するディメンションフィールドを宣言します。
式とディメンション修飾子 評価ディメンション 個々の指標参照をどのディメンションで評価するかを決めます。
クエリの GROUP BY または columns.dimension クエリディメンション 返される行をグループ化し、結果の 1 行が何を表すかを決めます。
マテリアライズの dimension: マテリアライズディメンション マテリアライズされたリレーションのグループ化とキーを定義します。
指標の dimensions: 許可されるディメンション 指標の評価に使えるディメンションの候補を制限します。ソース行の識別方法やクエリのグループ化は宣言しません。

これらの役割は互いに代用できません。たとえば、[地域] を指標の dimensions: に追加しても、クエリ結果に 地域 は追加されません。クエリには引き続き GROUP BY 地域 または columns.dimension: [地域] が必要です。

3. 粒度はディメンションから決まる #

粒度とは、あるコンテキストでディメンションを適用したときに、1 行が何を表すかを示すものです。

コンテキスト ディメンション ディメンションから決まる粒度
注文明細データセット [注文番号, 明細番号] 注文明細ごとにソース行が 1 行
製品別の月次クエリ [商品番号, dt_month] 製品と月の組み合わせごとに結果が 1 行
顧客単位の評価 [顧客番号] 顧客ごとに中間値が 1 つ
アカウント別の月次マテリアライズ [account_id, dt_month] アカウントと月の組み合わせごとにマテリアライズされた行が 1 行

ディメンションは言語上の取り決めであり、粒度はその取り決めによって各行が何を表すかを示します。粒度は、行が表す内容を比較したり、行が増える仕組みを考えたり、2 つのディメンションに互換性がない理由を説明したりするときに使います。レポートで求める粒度を、ソース行の識別に使うキーの代わりにしないでください。

ディメンションフィールドを追加すると通常は粒度が細かくなり、削除すると通常は粗くなります。この目安だけでは互換性を確認できません。フィールドの導出方法、時間の関係、指標の制約、データセットの境界も関係します。宣言した関係の妥当性はコンパイラで検証してください。

4. データセットディメンションによるソース行の識別 #

データセットディメンションには、物理的なソース行を 1 行ずつ識別するフィールドが含まれます。

注文明細:
    type: dataset
    table: tabOrderLine
    dimension: [注文番号, 明細番号]
    columns:
        注文番号:
            abbr: order_id
        明細番号:
            abbr: line_id
        商品番号:
            abbr: product_id
        純額:
            abbr: net_amount

一意性が求められるのは、[注文番号, 明細番号] の値の組み合わせ全体です。注文番号 は複数の明細で、明細番号 は複数の注文で重複してもかまいません。その場合でも、データセットディメンション全体では一意です。

物理行の識別に、同じ値が繰り返し現れ得る業務上のグループ化を使わないでください。ソースに同じ [account_id, invoice_id] の値を持つ仕訳が複数ある場合、レポートでその組み合わせを使ってグループ化することが多くても、そのリストは有効なデータセットディメンションではありません。物理的な仕訳キーをデータセットディメンションに使い、[account_id, invoice_id] をクエリディメンションまたはマテリアライズディメンションに使います。

pk(...) は、参照先のデータセットディメンションに依存します。

  • ルックアップの引数は、参照先のディメンションフィールドに対応します。
  • 引数の数と意味は、そのディメンションに一致している必要があります。
  • 1 回のルックアップに一致する参照先の行は、最大 1 行です。

コンパイラはこの取り決めが守られていることを前提とし、ルックアップを LEFT JOIN に変換することがあります。そのため、参照先のキーが重複すると、行が増え、指標値が重複して計算に使われる可能性があります。コンパイルされた SQL に DISTINCT や GROUP BY を追加しても、モデルの取り決めに対する違反は解消されません。

5. クエリディメンションによる結果のグループ化 #

Model Query SQL では次のように記述します。

SELECT dt_month, 商品番号, AGG(純売上高)
FROM MODEL
GROUP BY dt_month, 商品番号

クエリディメンションは [dt_month, 商品番号] です。結果の各行は、月と製品の値の組み合わせを 1 つ表します。

DML 形式のクエリでは、同じ役割を明示します。

商品別月間売上:
    type: query
    columns:
        dimension: [dt_month, 商品番号]
        純売上高: "{純売上高}"

グループ化しないクエリにはクエリディメンションがありません。指標が許容する場合は、総計のコンテキストで結果を返します。

互換性のある指標が異なるデータセットに由来する場合、コンパイラは各指標を個別にクエリの粒度まで集計し、その後、共通のディメンションフィールドを使って結果を結合します。これにより、明細行を先に結合した場合に起こりがちな、集計への重複計上を防ぎます。データセットディメンションは引き続き有効である必要があり、pk(...) の各ルックアップに一致する行は最大 1 行でなければなりません。

クエリディメンションのフィールドには、ディメンションとしての指標も使えます。これは、指標の結果をクエリディメンションのフィールドとして使うもので、多くの場合は {name: {+d: dim}} でバインドします。このフィールドの役割は引き続きクエリディメンションであり、データセットの dimension: によるソース行の識別には使いません。定義方法の規則については、ディメンションとしての指標を参照してください。

6. 個々の指標参照の評価ディメンション #

クエリディメンションが指標参照の初期コンテキストになります。式の構造、許可されるディメンション、修飾子によって、実際に使われる評価ディメンションが決まります。

クエリディメンションが [dt_month, 地域, ブランド] の場合：

指標参照 ディメンション操作 操作後の評価ディメンション
{売上高} ディメンション修飾子なし 確定した対象ディメンション
{売上高: {+d: 顧客番号}} ディメンションフィールド 顧客番号 を追加 [dt_month, 地域, ブランド, 顧客番号]
{売上高: {-d: ブランド}} ディメンションフィールド ブランド を削除 [dt_month, 地域]
{売上高: {dimension: [地域]}} ディメンション全体を置き換え [地域]
{売上高: {dimension: []}} ディメンションを解除 総計のコンテキスト

これらの操作は、その指標参照にのみ適用されます。クエリの GROUP BY は変更されません。

-d はディメンションフィールドを削除しますが、コンパイラがフィルターをデータセットにプッシュダウンする際、そのフィールドに対するクエリフィルターは保持します。-df はフィールドを削除し、その参照については関連するフィルターの伝播も抑止します。クエリフィルターで除外される値も分母に含める必要がある場合は、後者を使用します。構文とフィルターの動作については、指標の修飾子を参照してください。

7. 指標の評価に使用できるディメンション #

業務上の定義で必要な場合は、指標の dimensions: で有効な評価ディメンションを制限します。

顧客当たり収益:
    type: measure
    formula: DIVIDE({純売上高}, {アクティブ顧客数})
    dimensions:
      - [顧客番号]

[顧客番号] は、列挙されたフィールドだけを含む許可ディメンションの一つです。評価を制限しますが、データセットの行を識別することも、クエリ出力をグループ化することもありません。

省略記号を使うと、列挙されたフィールドを必須としたまま、追加のディメンションフィールドを許可できます。

dimensions:
  - [顧客番号, ...]

これにより、顧客番号 を含む互換性のある評価ディメンションが許可されます。指標の dimensions: を省略すると、その指標と依存先のデータセットに適合する任意のディメンションが許可されます。

数式に必要な必須ディメンションフィールドがクエリにない場合は、+d で該当する指標参照にそのフィールドを追加し、必要な外側の集計を行います。中間計算の要件を満たすためだけに、クエリにグループ化を追加しないでください。

8. マテリアライズのディメンションと保存される結果の識別 #

マテリアライズのディメンションは、保存される結果のグループ化とキーを宣言します。

月次口座残高:
    type: materialize
    dimension: [account_id, dt_month]
    measures: [closing_balance]

dimension_columns: に指定する属性は、これらのキーに関数従属し、キーとともに保存されます。これらの属性は、マテリアライズのディメンションに追加されるフィールドではありません。属性をマテリアライズのディメンションから導出できる場合は、保存される行の識別方法を変えず、その属性を dimension_columns: に残してください。

9. 互換性と検証 #

コンパイル時には、モデルで宣言された取り決めに照らして、次の点を確認します。

  • ディメンションフィールドを、関連するデータセットと列マクロを通じて解決できる。
  • 評価ディメンションが、指標の dimensions: の制約を満たしている。
  • 修飾子によって有効な評価ディメンションを構成できる。
  • 異なるデータセットの指標が、クエリのディメンションに対応している。
  • 時間修飾子に必要な有効な時間フィールドがある。

コンパイル時には実データに接続しないため、データセットのディメンションの値が一意であることは確認できません。

現在の状態を裏付ける検証結果がない場合や、既存の結果が古くなっている場合は、validateOnly を実行します。コンパイル済みクエリに対して生成されたデータセットキーのチェックを、選択した接続で実行します。また、EXPLAIN を使って、データベースがメインクエリを受け付け、実行計画を作成できるかどうかを確認します。結果行を取得するためにメインクエリを実行することはありません。

検証結果が有効なのは、検証時に確認したモデルとクエリの取り決め、接続、データソースの状態に対してです。関連するモデルの変更、データソースの更新、キーの規則の変更、接続の変更のいずれかがあると、その検証結果は現在の状態を裏付けるものではなくなります。

検証で VALIDATION_ERROR が報告された場合は、データソースのキー、データセットのディメンション、重複する範囲、またはソースデータを修正します。検証クエリを実行できない場合や、結果の形式が不正な場合は、EXECUTION_ERROR として別に対処します。このエラーはキーの重複を示すものではありません。

検証では、業務上の正しさも、信頼できるレポートとの一致も証明できません。既存のクエリを移行する際は、同じフィルター、時間範囲、クエリのディメンションを使って両方の結果を比較してください。
