コンパイルに失敗した場合、厳格モードの警告が表示された場合、または出力されたSQLがクエリの意図と一致しない場合は、この手順を使用します。動作が不明な場合は、選択したdmlc.exeで確認します。

デバッグ手順（Model Query SQL） #

コンパイル時にCOMPILE_ERRORが報告されるか、メッセージにUNION、JOIN、subquery、aggregation is not possible、ref {...} not defined、measure cannot be redefined、use existing measureのいずれかが含まれる場合に使用します。

  1. エラー全体を読む。ペイロード内にある、生成された-- dialect: … SQLも確認します。
  2. クエリの種類を判定する。明細クエリ（存在確認、一覧、単一レコード）か、集計クエリかを確認します。集計にはFROM MODEL + AGG()を使用します。モデルファイルが<name>.dmlの場合は、参照元にFROM <name>を使用します。
  3. 適切なFROM句を選ぶ。集計にはFROM MODELを使用します。ファイル名が<name>.dmlの場合はFROM <name>を使用します。明細にはFROM MODEL.<dataset>またはFROM <name>.<dataset>を使用し、AGGもGROUP BYも使用しません。名前は.dmlファイルと一致させます（model.dml ↔ FROM MODEL）。
  4. サポートされていないSQLを削除する。サブクエリ、UNION、JOINは使用できません。移植性のあるウィンドウ処理にはsystem_macros.dmlの fn マクロ（rank、pot、grand）、複数のレベルでの集計には+d指標、複雑なロジックには.dml定義を使用します（指標の設計、修飾子の組み合わせ）。OVERを手書きする場合のデータセット内でのウィンドウ処理の配置については、ウィンドウ処理の配置を参照してください。対象のパターンに対応する fn マクロがない場合は、Model Query にOVER()を直接記述できます。
  5. 指標と列を区別する。クエリではAGG(measure)を、.dmlファイルでは{column}または'{measure: modifier}'を使用します。Model Query SQLで列を直接参照する場合は、AGG({measure: modifier})を除き、{...}を使用しません。
  6. 段階的にデバッグする。まずSELECT AGG(one_measure) FROM MODELを検証し、その後でGROUP BYとフィルターを追加します。検証にはdmlc --validate <query.sql> --model=<model> --connection=<id> --jsonを使用します。

コンパイルエラーの読み方 #

コンパイラのメッセージと生成されたSQLを併せて確認します。原因が不明な場合は、クエリを指標1つに絞り、列とフィルターを1つずつ追加します。

エラー防止チェックリスト #

DMLまたは Model Query SQLを提出する前に、次の項目を確認します。

  1. 指標には技術名ではなく業務上の名称を使用している。
  2. .dmlの指標の式にAGG()が含まれていない。
  3. 単純なAGG(measure)に不要な別名が付いていない。
  4. 時間修飾子の時間コンテキストが確定しており、マクロの前提条件を満たしている。
  5. 時間フィルターでは、対象期間の初日を表す形式を使用している。
  6. 読みやすくするため、時間フィルターを最後に置くことができます。構文上、述語の順序に決まりはありません。
  7. サブクエリ、JOIN、UNION を使用していない。
  8. 読みやすく整形した Model Query SQLを.sqlファイルに保存する。
  9. クエリの種類（明細または集計）が目的に合っている。
  10. 使用予定のデータベース接続で--validateによる検証に合格する。
  11. MODEL.DATASET_*をGROUP BYで直接集計しません。FROM MODEL + AGG()を使用するか、明細データをエクスポートします。
  12. 疎なデータまたはFOJを扱う複合指標では、参照する入力で既定値による補完を有効にします（最外層にisnull、ifnull、coalesce(公式, 字面量)のいずれかを配置、P28b）。補完を有効にした依存先を埋め込んだ場合も、補完処理は展開されます。
  13. 指標をディメンションとして使う場合、指標から導出した各ディメンションに、完全なエンティティキーを明示します（+dを推奨）。ラベルが複数ある場合、各ラベルは独立した同一のキーを持ちます。出力するすべての指標は、Q ∪ Kで定義される粒度から正しくロールアップできる必要があります。ラベルのフィルターは、ラベルが生成された後に適用します（P66–P68）。
  14. 細かい粒度のCTEでWHEREを適用してから外側でSUMを行う場合は、対応する{+d: …}を指定してSUMIFまたはSUM(iif)を使用します。粗い粒度のクエリで指標を直接フィルターに指定しません（P69）。
  15. ウィンドウ処理の配置では、明細レベルのOVERをcolumns:の下に置き、その後にアトミック集計を行います。GROUP-BYの後は、ウィンドウ処理を複合指標、{-d:}、{-df:}のいずれかに配置します。アトミック指標にはOVERを使用しません（P70–P71）。
  16. 粒度を定義する2つのフィールドが同じ物理列を別名で参照する場合は、ロールアップ用に出力されたすべてのON句で、正しいキーが使われていることを確認します（P72）。明示的なキーを使う代替手段は、ディメンションを宣言したsql:データセットにpk()で取り込むことです（P77）。
  17. データセットをまたぐ-dfの複合ロールアップはFULL OUTERになります。相手側にしかない行は'{primary_measure} is not null':で除外します（P73）。相手側の一時データにmax()で補ったキーが含まれることがあるため、「余分な行」が、行を自分自身と組み合わせた有効なペアに見える場合があります。
  18. 同じオブジェクトに対して{+d:x,-d:x}や{+d:x,-df:x}を記述しません。この指定は明示的なエラーとし、式を明示的に書き換えます（P79）。
  19. -fはクエリの対象行集合を定めるフィルターを解除しません。粒度を定義する項目に対するフィルター以外で、適用がブロックされるフィルターにはEXISTSが必要です（P80）。
  20. 粒度をまたいで時間のdimension:を置き換えるには、カレンダーを使った橋渡しと、値を対象行に展開する処理が必要です（P81）。
  21. {m:{+d:x}}単体では、細かい粒度の結果だけが得られます。元の粒度に戻すには、外側でSUM、AVGなどによる集計が必要です。ただし、MADのラベルバインディングは例外です。
