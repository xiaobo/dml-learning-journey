Einen Geschäftstag in einer festen DuckDB-Zeitzone definieren

Inhalt dieser Seite
  • Bedeutung der Eingabewerte klären
  • Einen Tag durch zwei lokale Mitternachtszeitpunkte begrenzen
  • Unterschiedliche Zeitpunkte in einer wiederholten lokalen Stunde getrennt halten
  • Das Beispiel ausführen und anpassen

Rechnen Sie Zeitpunkte in die Geschäftszeitzone um, bevor Sie daraus ein Datum oder eine Tagesgrenze ableiten. Dieses Beispiel verwendet America/New_York und prüft physisches SQL in DuckDB. Es belegt keine automatische Unterstützung für benutzerspezifische oder datenbankübergreifende Zeitzonen in DML.

Bedeutung der Eingabewerte klären #

Die Eingabewerte sind Zeitpunkte vom Typ TIMESTAMPTZ mit expliziten UTC-Offsets. Die Sitzungszeitzone der Verbindung ist UTC, die Geschäftszeitzone ist America/New_York. Ein Zeitstempel ohne Offset ist nicht automatisch in UTC angegeben. Klären Sie zuerst, wie die Quelle den Zeitstempel erfasst.

SET TimeZone = 'UTC';
SELECT timezone('America/New_York', TIMESTAMPTZ '2024-01-01 02:00:00+00');

Die Ortszeit ist 2023-12-31 21:00:00. Das Geschäftsdatum ist daher der Vortag. Rechnen Sie den Zeitpunkt in die Geschäftszeitzone um, bevor Sie das Datum für die Gruppierung extrahieren.

Einen Tag durch zwei lokale Mitternachtszeitpunkte begrenzen #

SELECT count(*)
FROM (VALUES
  (TIMESTAMPTZ '2024-03-10 04:59:59+00'),
  (TIMESTAMPTZ '2024-03-10 05:00:00+00'),
  (TIMESTAMPTZ '2024-03-11 03:59:59+00'),
  (TIMESTAMPTZ '2024-03-11 04:00:00+00')
) events(ts)
WHERE ts >= timezone('America/New_York', TIMESTAMP '2024-03-10 00:00:00')
  AND ts < timezone('America/New_York', TIMESTAMP '2024-03-11 00:00:00');

Das Ergebnis ist 2. Schließen Sie den Beginn ein und das Ende aus. Das Ende liegt nicht immer 24 Stunden nach dem Beginn. Das Prüfprogramm prüft bei der Zeitumstellung im Frühjahr einen Tag mit 23 Stunden und bei der Zeitumstellung im Herbst einen Tag mit 25 Stunden.

Unterschiedliche Zeitpunkte in einer wiederholten lokalen Stunde getrennt halten #

2024-11-03 05:30 UTC und 06:30 UTC entsprechen beide der Ortszeit 01:30. Es handelt sich um unterschiedliche Zeitpunkte. Behalten Sie den Ereignisschlüssel und den ursprünglichen Zeitpunkt bei, statt Duplikate allein anhand des lokalen Zeitstempels zu entfernen.

Das Beispiel ausführen und anpassen #

Laden Sie das Projekt herunter und folgen Sie den Schritten zu JDBC in der Datei README, um jdbc/VerifyJdbc.java auszuführen. Führen Sie den folgenden Befehl mit dem vorhandenen JDK und den dazu passenden installierten JAR-Dateien im entpackten Projektverzeichnis aus:

java -cp "C:/path/to/dmlc-assembly.jar;C:/path/to/duckdb-jdbc.jar" jdbc/VerifyJdbc.java "$PWD/jdbc" C:/path/to/driver-directory

Passen Sie die Pfade an. Verwenden Sie auf anderen Systemen im Klassenpfad einen Doppelpunkt statt eines Semikolons. Das Programm prüft auch die Parameterbindung für physische und semantische Abfragen. Prüfen Sie die abschließenden Erfolgsmeldungen und den Exitcode des Prozesses. Das Programm lädt keine Laufzeitumgebungen von Drittanbietern herunter.

Das Prüfprogramm prüft Mitternacht, wiederholte Stunden, Tage mit 23 bzw. 25 Stunden und die Filterung mit halboffenen Intervallen. Schlägt eine Prüfung fehl, endet das Programm mit einem Exitcode ungleich null.

Die geprüfte JDBC-Distribution verwendet den Treiber DuckDB in Version 1.5.4. Um ein Geschäftsdatum in DML wiederzuverwenden, kann eine Datenbankansicht zuerst die Zeitstempel normalisieren und das Geschäftsdatum als Modellspalte bereitstellen. Prüfen Sie diese Integration mit Ihrem Modell und Ihrer Verbindung. Dieses Beispiel mit physischem SQL belegt keine Unterstützung für beliebige Modelle mit Zeitzonenlogik.
