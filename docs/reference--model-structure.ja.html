このページでは、モデルレベルのフィールド、データセット、列マクロ、共通メタデータについて説明します。インクルードの可視性と名前解決については、モデルの構成を参照してください。

モデルレベルのフィールド #

フィールド 種類 説明
includes string[] マージする他の.dmlファイルへのパス（各ファイルのシンボルの和集合を取ります）
dialect string 対象のSQL方言。明示的に設定してください。認識される名前、既定値、実行の対応範囲については、SQL方言を参照してください。
column-macros object 複数のデータセットで共有する列定義
<name> object | string データセット、指標、dt-macro、fn-macro、materialize、またはクエリ

オブジェクト名の規則: 予約キーワード（includes、column-macros、datasets、measures、columns、dimensions[dt]、dt-macros、fn-macros、materializes、queries、dialectsおよびそれらの単数形）を除く任意の文字列です。

指標定義の簡略形: 最上位のマッピングの値に文字列だけを指定すると、指標の式を表す省略記法として扱われます。

売上高: SUM({売上金額})
# equivalent to:
売上高:
    type: measure
    formula: SUM({売上金額})

SQL方言 #

確認に使用したコンパイラは、adb_mysql、duckdb、mssql、mysql、postgres、sqliteを認識します。現行のコンパイラでは、確認したモデルに方言の指定がないとコンパイルが拒否されます。対象の方言を明示的に指定してください。DuckDB接続を設定しても、モデルの対象方言は変わりません。DuckDBを対象とする場合は、dialect: duckdbを指定してください。

この確認では、BigQuery、Snowflake、Databricks、ClickHouse は対象として認識されませんでした。認識されないエンジンが必要な場合は、そのデプロイでdmlcを使用する前に、この要件を解決する必要があります。

方言の認識と、実行を確認した範囲は別です。実行可能な例では主にDuckDBの結果を検証しています。SQL Server 向けのコンパイルについては、概要に別途記載しています。これらの確認で、6 つすべてのエンジンが同じ機能を備えていることまで確認できるわけではありません。生成されたSQLを検証し、使用予定のデータベースで結果を比較してください。生成されたSQLでは、複数のステートメント、中間リレーション、カレンダーオブジェクトが必要になる場合があります。

データセットの定義（type: dataset） #

<name>:
    type: dataset
    table: <table_name>          # required (or sql:)
    # sql: <SELECT ...>          # alternative to table: — derived dataset
    dimension: [col1, col2]      # dataset grain dimensions
    materialize: <name>          # optional, declare a materialize table for this dataset
    # or:
    # materialize:
    #     name: <name>
    #     parameters:
    #         <param>: <value>
    columns:                     # required
        col1:                    # direct column (pass-through)
        col2: expr               # calculated column (inline expression)
        col3:                    # full column definition
            abbr: <source_column> # optional when the names match
            description: <text>
            formula: expr        # calculated column (block form)
            # source: expr       # alternative to formula: data-source verification formula
            prerequisite: <expr> # column-level grain constraint
    dimensions[dt]:              # optional explicit time metadata; coarser standard dt_* fields may be system-derived
        dt_date: date
        dt_month: month
    measures:                    # atomic measures (inherit enclosing dataset; no dataset:)
        <measure_name>: <formula or full definition>
            abbr: <short>
            description: <text>

制約:

  • table:とsql:のどちらか一方だけを指定します（両方は指定できません）。
  • table:によるテーブルの所有は排他的です。 table: policyは、データセットPolicyがその物理テーブルを所有することを意味します。他のデータセットでは、sql:内のFROMやJOINで物理テーブル名を指定してはいけません。from {Policy}またはjoin {Policy}と記述するか（コンパイラがデータセットのクエリ名に置き換えます）、pk(...).{Policy}.Colで属性を参照してその結合を省略してください。所有権を設定せずにテーブルを共有するには、table:の代わりにsql: select * from <table>を使用してください。
  • ファクトテーブルのパターン: ディメンションデータセット（Claim、Policy）ではtable:を使用します。これらの属性だけが必要なファクトデータセットでは、所有者のいないソーステーブルをそのまま使えます。所有者のいるテーブルとの結合をsql:に記述する代わりに、pk()で属性を参照できます。
  • 可視性: 確認したビルドでは、同じファイル内で後に定義されるデータセット、指標、列への参照がサポートされています。インクルードされたファイルは、自身の定義または自身のインクルードから名前を解決する必要があり、親ファイルからは解決できません。モデルの構成を参照してください。
  • ファイルを直接コンパイルする場合は、拡張子を除いたファイル名をクエリ名にします（report.dml → report）。
  • allows:は、使用できるマテリアライズの対象を指定します（ALL、NONE、または明示的に指定した名前）。指標のディメンションは上書きしません。
  • 例に示す形式の指標クエリでは、columns:が必須です。
  • dimensions[dt]に指定できる列挙値は、year、quarter、month、week、date、hourです。
  • materialize:には、名前をスカラー値として指定するか、必須のname:と任意のparameters:を持つオブジェクトを指定できます。どちらの形式も、データセット内で同じマテリアライズを識別します。

データセットのSQLでは、指標を評価する前に、サポートされている結合、和集合、サブクエリでデータを準備できます。UNION ALLは重複行も保持します。各入力内で行を一意に識別できるキーでも、入力をまとめた結果のすべての行を一意に識別できるとは限りません。各分岐の元のキーが一意のままであると仮定せず、入力をまとめたリレーションで行を識別するキーを定義してください。確認した例では、{DATASET}参照を通じて、列だけを定義したソースデータセットを使用します。現行の実行プログラムは、利用できない中間テーブルを必要とせずに、これらの派生リレーションを検証します。派生リレーションのキーを構成するすべての要素を確認してください。キーが一意なら検証に合格します。キーが重複している場合、検証レポートはdata.issues[].kind: duplicate_keyで違反を示します。不足しているキー要素を追加すると、検証に合格します。物理ソースが存在しない場合はEXECUTION_ERRORとなり、キーの重複としては報告されません。業務上の結果は、検証とは別に確認してください。

列定義の形式:

記述形式 YAML 意味
直接参照 売上金額:（null） 元のテーブルの列をそのまま使用
計算（インライン） net: 売上金額 - 割引額（文字列） 式から導出される列
計算（ブロック） net: { formula: 売上金額 - 割引額 } メタデータ付きの派生列
検証式付き net: { source: 売上金額 - 割引額 } データソースを検証する式を宣言します。コンパイルだけでは、ソースの値が等しいことは確認できません。

式における波かっこによる名前のバインド:

formula:での記述形式 バインド先 例
売上金額 単独 物理（ネイティブ）テーブル列。コンパイラは名前をそのままSQLに渡します。 両方の列が直接参照の場合のnet: 売上金額 - 割引額
{calc_amt} 計算列（または指標や列マクロ）。DMXが定義を展開します。 二倍値: '{calc_amt} * 2'

計算列の式に波かっこなしで名前を書くと、その識別子はネイティブのSQL列として扱われます。SELECT内のエイリアスの順序によっては動作しているように見えますが、計算列の定義は展開されません。式でその定義を再利用するには、名前を波かっこで囲みます。

依存先を先に定義するのは、読みやすさのための慣例です。確認したリリースでは、同じファイル内で後に定義される対象をpk()で参照しても、コンパイルに成功しました。名前を解決できない場合は、インクルードの不足、名前の誤記、インクルードの可視性ルールへの違反が考えられます。モデルの構成を参照してください。

列マクロ #

列マクロは、複数のデータセットで共通して使用する列を定義します。

column-macros:
    datasets: [tx, orders]       # scoped datasets
    columns:                     # shared column definitions
        地域: '{店舗数}.地域' # cross-dataset lookup
    dimensions[dt]:
        dt_month: month

    # OR per-dataset scope:
    <dataset_name>:
        <col>: <formula>

共通のメタデータフィールド #

サポートされるメタデータはオブジェクトの種類によって異なります。対応するスキーマ定義を参照してください。

フィールド 種類 説明
abbr string データセットのフィールド名と元のテーブルの列名が異なる場合に、元の列名を指定します。指標には内部で使う略称を指定できます。クエリ結果には業務上の名前か、AS で指定した別名が表示されます。
description string 人が読んで理解できる説明
tags string[] 自由に指定できるタグ
prerequisite string（数式） 行や集計値を定義できるレベル（粒度）の制約（メジャー、列、dt マクロ、fn マクロ）

列のメタデータは SQL の型宣言ではない #

列のプロパティは DML スキーマに従う必要があります。プロパティは対象の列の下に記述してください。columns: 内で対象の列と同じ階層に type: text を記述すると、type という名前の別の列が定義されます。そのモデルが受理されても、対象の列の型については何も判断できません。確認したビルドでは、列の下に記述した type: text と type: banana は、どちらも未対応のプロパティとして拒否されます。これはメタデータスキーマの検証であり、式の静的型チェックが完全に行われることを示すものではありません。物理列の型はデータベースで定義し、型変換が必要な場合は、サポートされている式やキャストを使用してください。最上位の type: dataset と type: measure は DML オブジェクトの種類を示します。SQL の値の型を宣言するものではありません。

システムカレンダー #

一部の接続では、データベースに接続する検証またはクエリの実行でその接続を初めて使用したときに、DML_CALENDAR が初期化されます。クエリに時間修飾子がない場合も同様です。試験に使用した DuckDB 接続では、2016 から 2036 までの両端を含む期間について、1 日 1 行のデータが初期化されました（7,671 行）。初期化に使うアカウントには、対象のスキーマでテーブルを作成し、データを格納する権限が必要です。以降のクエリには、そのテーブルの読み取り権限が必要です。

実行時アカウントでテーブルを作成できない場合は、そのアカウントで検証を実行する前に、データベース管理者に同じ dmlc ビルド、接続の SQL 方言、スキーマを使ってカレンダーを初期化してもらってください。カレンダーがレポート期間と比較期間をカバーしていることを確認してください。
