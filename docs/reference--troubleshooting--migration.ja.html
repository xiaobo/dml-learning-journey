再利用する定義はモデルに置き、表示方法はクエリ層またはレポート層で指定します。

P1. 表示ロジックをDMLに含める #

誤り：指標の式にFORMAT(...)、CONCAT(...)、CAST(... AS VARCHAR)を含める。修正：.dmlから書式設定を取り除き、ダッシュボードまたは描画層で行います。

P2. 特定のクエリでしか使わない派生列をDMLに含める #

誤り：特定のクエリでしか意味を持たない計算を指標として定義する。修正：クエリ固有の式は.dmlに記述せず、Model Query のSQLに記述します。

P5. コンパイルで生成されたSQLと基準となるSQLの結果が一致するか確認しない #

誤り：コンパイルが成功しただけで-cの出力は正しいと判断する。修正：元のSQLとコンパイルで生成されたSQLを両方実行し、結果セットを比較します。

P6. フィルターやクエリ内のディメンションの組み合わせごとに専用の指標を作る #

誤り：sales_north、sales_south、sales_eastを個別に作る。または、WHERE region = 'North'で十分な場合にsales_northを作る。修正：共通の指標salesを1つ定義し、クエリでWHERE region = 'North'を使用します。

P7. 同じ集計式を重複して定義する #

誤り：revenue: SUM({amount})とtotal_revenue: SUM({amount})を定義する。修正：最小単位の指標を1つだけ定義し、すべての箇所でその指標を参照します。

変換で下書きを生成できたSQL #

2026年11月の試行では、--to-dmlにより、標準的なCAST(... AS type)、CASEを含むGROUP BY、CTE内のROW_NUMBER()、LIMIT/OFFSET、EXTRACT、DATE_TRUNC、ILIKE、GENERATE_SERIES、NULLS LAST、EXCEPTの下書きが生成されました。下書きの生成後も、コンパイルと結果の比較が必要です。

試行で変換に失敗した入力 変換前の書き換え
sale_date::date AS d, DATE '2025-01-01' CAST(sale_date AS date) AS dまたはCAST('2025-01-01' AS date)を使用します。
SUM(amount) FILTER (WHERE paid) SUM(CASE WHEN paid THEN amount END)を使用します。
QUALIFY ROW_NUMBER() ... = 1またはDISTINCT ON 同じパーティション分けと並び順を使い、CTE内でROW_NUMBER()を計算します。外側のクエリでrn = 1を条件に絞り込みます。
$$hello$$ 文字列を単一引用符で囲み、文字列内の単一引用符は2つ重ねて記述します。
INTERVAL '1 day'、LATERAL、STRING_AGG(... ORDER BY ...)、またはJSONの->> 使用するパーサーと方言に合わせて式を正規化するか、ソースビューから列として取得します。変換前に、行の並び順、NULLの扱い、結果に含まれる行を確認します。

変換後の作業

  1. 下書きにdialect:の項目がなければ、対象データベースに合わせて追加します。
  2. 拡張子を除いたファイル名を、ファイル内に記述されたクエリ名と一致させます。2つの定義で同じ指標名を使っている場合は、定義を1つだけ残すか、クエリ内の計算の名前を変更し、その計算への参照を更新します。
  3. レポート対象期間の範囲はクエリで指定します。pp、pop、またはytdに必要な元データの履歴を指標から参照できるようにしておきます。

編集した下書きに対してリントと厳格モードでのコンパイルを実行し、同じデータで実行した場合の結果を元のSQLの実行結果と比較します。
