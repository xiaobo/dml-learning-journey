DMLは、2 つの異なるレイヤーで拡張できます。DMLで再利用可能な指標や時間の変換を定義するか、対象データベースにインストールされたスカラー関数を呼び出します。カスタム修飾子は指標の参照と組み合わせて使えます。データベース関数の計算処理は、そのデータベース側で実装します。

時間変換や、呼び出し元が選んだ指標に適用する数式を再利用するには、カスタムマクロを使用します。呼び出しと組み合わせのルールは、修飾子リファレンスを参照してください。

カスタムマクロの定義（dt-macro と fn-macro） #

.dmlでは、dt-macro（時間範囲をずらす）とfn-macro（指標を数式で包む）の両方を独自に定義できます。一度定義すれば、組み込みの修飾子と同じように、任意の指標やクエリから名前で参照できます。

2 種類のマクロ

種類 用途 主なプロパティ プレースホルダー {measure}
dt-macro 時間ウィンドウをずらす、または広げる 値:（単一の時点をずらす）または range: [start, end] いいえ。時間コンテキストに対して処理を行います。
fn-macro 指標を派生数式に組み込む {measure}を使うformula: はい。呼び出し元の指標に置き換わります。

時点をずらすには値:を、時間ウィンドウを指定するにはrange: [start, end]を使用します。fn-macroは呼び出し元の指標を参照するために{measure}を使い、dt-macroは解決された時間フィールドを参照するために{dim_dt}を使います。オプションのprerequisite:で、評価対象の行や集計値を定義できる粒度を制限できます。

拡張方法を選ぶ #

やりたいこと 使用するもの 管理するもの
同じ計算を複数の指標に適用する fn-macro {measure}を使うDMLの数式
時間のシフトや時間ウィンドウを再利用する dt-macro DMLの時間変換
データベースにある既存の計算を再利用する データベースのスカラー関数の呼び出し データベース関数と、その権限およびデプロイ

カスタム修飾子を使うと、分析の意図をモデルに記述できます。呼び出し構文は組み込みの修飾子と同じです。データベース関数を使うと、データがある場所でロジックを再利用できますが、そのデータベースでの関数の実装に依存します。どちらを使う場合も、評価対象の行や集計値を定義する粒度を適切に選ぶ必要があります。

検証済みの組み合わせ例 #

カスタム修飾子は組み込みの修飾子と同じ形式で参照します。コンパイラを変更する必要はありません。

独立した練習用のDuckDBデータベースに、次の 2 件の売上データを用意します。

CREATE TABLE sales(id INTEGER, dt_month DATE, amount DECIMAL(12,2));
INSERT INTO sales VALUES
  (1, DATE '2025-01-01', 20),
  (2, DATE '2025-02-01', 30);

このモデル全体をmodel.dmlとして保存します。

dialect: duckdb
S:
  type: dataset
  table: sales
  dimension: [売上明細番号]
  columns:
    売上明細番号:
      abbr: id
    dt_month:
    売上金額:
      abbr: amount
  measures:
    売上高: SUM({売上金額})
金額の二倍:
  type: fn-macro
  formula: '{measure} * 2'
前月:
  type: dt-macro
  値: date({dim_dt}, '-1 month')

1 月の売上が20、2 月の売上が30の場合：

SELECT AGG({売上高: 金額の二倍}) AS 二倍値,
       AGG({売上高: 前月}) AS previous,
       AGG({売上高: {金額の二倍, 前月}}) AS 前期二倍値
FROM MODEL
WHERE dt_month = '2025-02-01'

クエリをquery.sqlとして保存します。練習用データベースをdefaultとして設定した状態で、次を実行します。

dmlc --compile --strict query.sql --model=model.dml --json
dmlc --validate query.sql --model=model.dml --connection=default --json
dmlc query.sql --model=model.dml --connection=default

実行結果は60、20、40でした。確認に使用したDuckDB接続では、厳格モードでのコンパイル、validate-only、実行のすべてが成功しました。モデルには、dialect: duckdb、ソースで一意の売上明細番号、dt_month、売上高: SUM({売上金額})が宣言されていました。

これは、言語レベルで再利用できる組み合わせです。マクロは呼び出し元の指標とその評価コンテキストを受け取ります。任意のコンパイラプラグインを実装するためのAPIではありません。粒度のルール、時間に関する前提条件、修飾子の適用順序は引き続き適用されます。独自の名前を付けても、これらのルールは回避できません。

データベースで定義された関数を呼び出す #

DMLでは、生成されたSQLにスカラー関数の呼び出しを残すことができます。関数の実装はデータベースが提供します。たとえば、DMLを実行する前に、練習用のDuckDBデータベースに次の関数をインストールします。

CREATE FUNCTION business_net(x) AS x * 0.8;

DuckDBはこの形式を永続的なSQLスカラーマクロとして実装します。この例で検証するのは、データベースで定義されたスカラー関数の呼び出しです。Python UDFの登録、集約 UDF、テーブル値関数は検証の対象外です。

集計前に元データの値に対して関数を呼び出すには、S.measuresの下で売上高と同じ階層に次の項目を追加します。

# Under the sales dataset's measures:
純売上高: SUM(business_net({売上金額}))

次に、その指標を、集計結果に対して関数を呼び出した場合と比較します。

SELECT AGG(純売上高), business_net(AGG(売上高)) AS 純額合計
FROM MODEL
WHERE dt_month = '2025-02-01'

2 月の売上が30の場合、どちらも24を返しました。生成されたSQLには、SUM(business_net(売上金額))とbusiness_net(SUM(売上金額))がそのまま含まれていました。2 つの呼び出しは異なる段階で評価されます。ここで結果が等しいのは、関数が線形だからです。丸め、しきい値による処理、その他の非線形関数では結果が異なる場合があるため、どの段階で評価するかを意識して選んでください。

使用予定の接続で関数を検証する #

DMLは関数をインストールせず、別のデータベース向けに実装を変換することもありません。関数は実行に使用する接続から参照でき、生成された引数の型を受け付ける必要があります。また、そのデータベースユーザーに関数の実行権限が必要です。関数名、スキーマによる修飾、デプロイ、移植性はデータベースによって異なります。

意図的に用意しなかった関数の呼び出しは、厳格モードでのコンパイルに成功しましたが、その後の validate-only はEXPLAINの段階で失敗しました（終了コード 65）。直接実行しても失敗しました（終了コード 70）。したがって、コンパイルに成功しただけでは、UDFが存在することや呼び出せることは確認できません。コンパイルと検証を行い、その後で実際の結果を比較してください。

検証した内容 #

上記の例は、dmlc 0.3.16（実行ファイルの SHA-256 は c019a84c3208aee31cb5fa068232fa24d3258e9cdc83dfc2a91584a86a5ba091）と DuckDB 1.5.5 で実行しました。検証したのは、カスタムのfn-macroとdt-macro、それらの組み合わせ、元データの値と集計結果に対するスカラー関数の呼び出し、および関数が存在しない場合の診断です。他のデータベースエンジン、スキーマ修飾名、手続き型またはネイティブの UDF、集約 UDF、テーブル関数は、ここではテストしていません。
