ここでは、定義、名前、ルックアップ、メタデータを扱います。宣言の構文については、モデル構造と指標の宣言を参照してください。

P21. 指標の式での AGG() の使用 #

誤り: .dml に sales: AGG({amount}) を記述する。修正: sales: SUM({amount})。.dml では SQL の集約関数を使用します。

P22. ルックアップを使わないデータセット間の参照 #

誤り: データセットをまたいで profit: SUM({sales.amount} - {costs.amount}) を使用する。修正: {DATASET}.column または pk(...) によるルックアップを使った列マクロを使用します。

P22b. table: でデータセットに割り当てられた物理テーブルを、別のデータセットの sql: で結合する #

誤り: Policy に table: policy があり、別のデータセットの sql: で from policy または join policy を使用する。修正: 物理テーブルではなく、from {Policy} または join {Policy} でデータセットを参照します。SQL の結合を使わずに属性を参照するには、pk(...).{Policy}.Col を使用します。sql: 内の {Policy} はテーブルソースの置換に使われ、列式ではありません。コンパイラがこれをデータセットのクエリ名に置き換えます。データセット定義（type: dataset）を参照してください。

P23. アトミック指標での dataset: の指定漏れ #

誤り: sales: type: measure, formula: SUM({amount})。データセットが指定されていません。修正: sales: type: measure, dataset: transactions, formula: SUM({amount})

P24. 用途を絞りすぎた指標名 #

誤り: sales_q1_2024_north、sales_john_doe。修正: 汎用的な指標とクエリフィルターを組み合わせます。

P25. 例外的なケースを文書化していない #

誤り: 指標の説明に「返品を除外する」または「ゼロを含む」と明記していない。修正: 挙動が自明でない場合は、必ず description: を追加します。データセットのディメンション、各行の意味、適用範囲を示すフラグ、誤解を招く名前を文書化します。モデルのメタデータを記述するを参照してください。

P27. ディメンションに制約のある指標を互換性のないクエリで使用する #

誤り: クエリのディメンションが [dt_month] のクエリで、sales_by_product（許可されているディメンションは [product]）と total_sales を選択する。修正: すべての指標でクエリのディメンションが許可されていることと、各指標の行が定義される粒度に互換性があることを確認します。または、クエリを分けます。

P28. GROUP BY で十分な場合に +d を使用する #

誤り: sales_by_region: SUM({sales: {+d: region}}) を作成する。修正: sales: SUM({amount}) を定義し、クエリ SELECT region, AGG(sales) FROM MODEL GROUP BY region を使用します。

P28b. 結合する行がない場合の NULL の伝播 #

誤り: profit: '{revenue} - {costs}'。対象範囲の行がどちらか一方でも欠けている場合（FOJ または欠けのある dt）、その側の入力は NULL になり、差も NULL になります。

修正：行がない場合は既定値で補完する（欠落行の補完）:

  1. 補完を有効にするには、欠けのある入力の最外層で isnull、ifnull、または coalesce(公式, 字面量) を使用します。
revenue: 'isnull(SUM({amount}), 0)'   # or wrap the existing measure formula outermost
costs: 'isnull(SUM({cost}), 0)'
profit: '{revenue} - {costs}'         # use sites of revenue/costs → 0
  1. その粒度で対応する行がない場合でも、結果列自体を NULL にしてはいけないなら、結果に対して補完を有効にします。
profit: 'isnull({revenue} - {costs}, 0)'

不十分な指定、または補完が有効にならない指定: isnull({a}, {b})、coalesce(a, b, 0)、単独の {m: pp}、あるいは無関係な外側の複合指標が自動的に isnull で囲まれることを前提とする指定。補完がすでに有効な依存指標を複合指標に組み込むと、その依存指標が欠けのある FOJ で使われる箇所では、引き続き補完式が展開されます。measures.md 既定値で補完するを参照してください。

P28c. データセットをまたいで指標を組み合わせる場合の NULL のグループ化キー #

症状。 レポートに、地域が NULL で、複数のソースの指標を含む行が 1 行表示されます。この行は、複数のソースに共通するレポート上のグループを表します。複合キーの場合は、ほかのすべてのディメンションも一致する必要があります。

確認。 グループ化キーを全項目にわたって比較し、生成された述語を確認します。2026年11月19日の変更を含むビルドでは、この照合に NULL セーフな等価比較を使用します。以前のビルドでは、NULL のキーが一致しないことがあります。主ソースのグループだけを残すには、主ソースに行が存在することを示す、補完していない指標で絞り込みます。結合時の NULL の等価比較を参照してください。

カテゴリ：時間の扱い #

P37. 列に対する修飾子 #

誤り: 式の中で {customer_id: {+d: customer_id}} を使用する。修正: 評価対象の指標にドリルダウンを指定します。例: {sales: {+d: customer_id}}。入力用の +f など、ほかの修飾子には列に指定できる形式もあります。すべての列修飾子が禁止されているわけではありません。

P38. YAML の式を引用符で囲んでいない #

誤り: 値に :、{、または - が含まれているときに、formula: SUMIF({sales: {+d: dt_month}}, {dt_month} = {first_month}) の値を引用符で囲まない。修正: formula: 'SUMIF(...)'

P39. 複合指標での dataset: の指定 #

誤り: ほかの指標を参照する複合指標に dataset: が残っている。修正: 式がほかの指標を参照する場合は dataset: を省略します。dataset: はアトミック指標にのみ残します。

P40. 指標の再定義エラーまたは式の重複 #

誤り: sales または x がすでに指標として存在するときに、それぞれ SELECT AGG(sales) AS sales または AGG(x) AS x を使用する。修正: SELECT AGG(sales) を別名なしで使用するか、既存の指標名とは異なる別名（AS sales_value）を指定します。コンパイラが「use existing measure "X"」と表示した場合は、式を書き直さずに AGG(X) を使用します。

P41. モデルクエリの SQL での DML の {...} 構文 #

誤り: SELECT {dt_month}, AGG({sales}) FROM MODEL。波かっこは .dml の数式専用です。修正: SELECT dt_month, AGG(sales) FROM MODEL。クエリで AGG({sales: pop}) を使うのは、修飾子付きの形式に限ります。

P42. .dml の数式での、波かっこなしの列名と {col} の違い #

誤った解釈: formula: calc_amt * 2 を「波かっこの付け忘れ」や「コンパイラのチェック漏れ」と捉えることです。波かっこなしの calc_amt は、テーブルの物理列として解決されます（SQL にそのまま渡されます）。修正: 計算列の定義を参照する場合は、列名を波かっこで囲みます。例: formula: '{calc_amt} * 2'。物理列の名前には波かっこを付けません。例: net: amount - discount。データセットの定義（type: dataset）を参照してください。

モデルのトラブルシューティング #

まず、起点となるモデルの dialect: の設定と、includes: のパスや名前を確認します。データセットの dimension: でソースの各行を一意に識別できることを確認し、宣言順にキーの全要素を pk(...) に渡します。明確に報告された参照の欠落または競合のうち、最初のものを修正してから、lint を再実行します。
