SQL Server で Maz を使う

このページの内容
  • チュートリアルの売上データを使った四半期レポート
  • 第 1 四半期を準備する
  • 新しい月と過去データの訂正の扱い
  • 中断後の再開
  • よくある問題
  • ランナー全体の進捗を監視する

SQL を理解しているレポート開発者、アプリケーション開発者、データ運用担当者が対象です。

この演習では、月次売上と四半期売上の 2 つの Maz を使います。生成された setup_sql でランタイムをインストールします。prepare_sql を実行し、data_ready=1 が返ったら業務クエリを実行します。待機中は、prepare_status_sql でこのリクエストの状況を、DML_MAZ_PROGRESS で全体の進捗を確認できます。

最初に「prepare と refresh の選び方：パラメーターと復旧ルール」を読んでください。

チュートリアルの売上データを使った四半期レポート #

インタラクティブチュートリアルの第 12 章では、データセット FACT_SALES が TABLE_SALES を読み取り、id で個々の売上を識別し、dt_month に月を記録し、SUM({amount}) で売上を集計します。このモデルとその 8 行のソースデータを引き続き使います。1 月の合計は 70、2 月の合計は 100 です。

この拡張で、マテリアライズ済みの結果を 2 つ、四半期レポートを 1 つ追加します。

TABLE_SALES（売上明細）→ SALES_MONTHLY（月次売上）→ SALES_QUARTERLY（四半期売上）→ quarterly_sales（レポート）

クエリの準備では、まず上流で必要な月を確認し、次に下流の四半期パーティションを作成します。再構築が必要なパーティションは、それぞれ個別にコミットされます。

第 1 四半期を準備する #

  1. インタラクティブチュートリアルのセットアップスクリプトを、SQL Server の空の練習用データベースで実行します。その演習をすでに実行した場合は、同じデータベースを引き続き使います。
  2. 以下のカレンダー拡張を実行します。チュートリアルの練習用カレンダーには日付と月だけがあり、2025 年 2 月で終わります。この手順では四半期を追加し、6 月末までのデータを補います。
  3. チュートリアルの model.dml を quarterly_sales.dml という名前で保存します。元からある dialect: mssql の行を残し、以下のマテリアライズとレポートの定義をファイルの末尾に追加します。

参照用に、インタラクティブチュートリアルの第 12 章を確認し、元の model.dml と SQL Server 用のセットアップスクリプトをダウンロードしてください。

SQL Server 用のカレンダー拡張を表示 
ALTER TABLE dbo.DML_CALENDAR ADD dt_quarter date NULL;
GO
UPDATE dbo.DML_CALENDAR
SET dt_quarter = DATEFROMPARTS(YEAR(dt_date), 3 * (DATEPART(quarter, dt_date) - 1) + 1, 1);
ALTER TABLE dbo.DML_CALENDAR ALTER COLUMN dt_quarter date NOT NULL;

;WITH dates AS (
    SELECT CAST('20250301' AS date) AS dt_date
    UNION ALL
    SELECT DATEADD(day, 1, dt_date) FROM dates WHERE dt_date < '20250630'
)
INSERT dbo.DML_CALENDAR (dt_date, dt_month, dt_quarter)
SELECT dt_date, DATEFROMPARTS(YEAR(dt_date), MONTH(dt_date), 1),
       DATEFROMPARTS(YEAR(dt_date), 3 * (DATEPART(quarter, dt_date) - 1) + 1, 1)
FROM dates
OPTION (MAXRECURSION 0);
マテリアライズとレポートの定義を表示 
SALES_MONTHLY:
  type: materialize
  parameters: {dt_month: range}
  dimension: [dt_month]
  measures: [sales]

SALES_QUARTERLY:
  type: materialize
  allows: [SALES_MONTHLY]
  parameters: {dt_quarter: range}
  dimension: [dt_quarter]
  measures: [sales]

quarterly_sales:
  type: query
  allows: [SALES_QUARTERLY]
  filters:
    dt_quarter:
      range: ['2025-01-01', '2025-01-01']
  columns:
    dimension: [dt_quarter]
    sales:

$compiled = dmlc --compile --strict --json --artifacts=gen quarterly_sales.dml | ConvertFrom-Json
$compiled.data.setupSql    # setup_sql
$compiled.data.prepareSql  # prepare_sql
$compiled.data.sql         # sql

拡張したモデルをコンパイルし、生成された setup_sql でマテリアライズと依存関係をインストールします。次に、自動コミット接続で quarterly_sales の prepare_sql を実行します。準備と実際にデータが利用可能かどうかの確認が完了し、data_ready=1 が返ったら、同じリクエストの業務クエリ sql を実行します。待機中は、別の接続から prepare_status_sql で状況を確認できます。エラーが発生した場合や待機がタイムアウトした場合は、まだクエリを実行しないでください。原因を解消してから通常の準備をやり直します。SQL Server のセッションには IMPLICIT_TRANSACTIONS OFF と @@TRANCOUNT = 0 が必要です。業務クエリは引き続き SELECT または CTE です。

第 1 四半期の結果は 170 です。月 1、2、3 にはそれぞれ月次パーティションの状態が記録されています。この時点で 3 月のパーティションは空でした。SQL Server では、大文字と小文字が混在する入れ子の名前の登録に現時点で制約があるため、この例ではマテリアライズ名をすべて大文字にしています。

新しい月と過去データの訂正の扱い #

以下の 3 つのデータ変更を、練習用データベースで順番に実行します。ソースのトランザクションをコミットしてから refresh を実行します。2 件の挿入には、チュートリアルと同じ地域と顧客を使います。

ソースの変更 操作 レポート結果
3 月の売上 30 を TABLE_SALES に挿入する。Q1 は公開済み。 SALES_MONTHLY に対して 3 月の refresh を実行する。デフォルトでは、その月とマテリアライズ済みの Q1 が更新される。 Q1 170 → 200
4 月の売上 40 を挿入する。Q2 とその月次パーティションはまだ作成されていない。 第1四半期のコンパイル結果を保存しておきます。quarterly_sales.dml で dt_quarter の開始日と終了日をどちらも 2025-04-01 に変更し、上のコンパイルコマンドをもう一度実行します。新しい結果の prepareSql を実行し、data_ready=1 が返ったら、同じ結果の sql を実行します。2月分の修正を確認するときは、保存した第1四半期の結果を使うか、開始日と終了日を 2025-01-01 に戻して再コンパイルします。 Q2 の結果として初めて 40 が返る。
2 月の id = 2 の売上を 20 から 25 に訂正する。 SALES_MONTHLY に対して 2 月の refresh を実行する。デフォルトでは、その月と影響を受ける Q1 が更新される。 Q1 は 200 → 205、Q2 は 40 のまま。

この手順では、2025 年の過去のパーティションを使います。3 月分の追加と 2 月分の訂正の後も、通常の準備だけでは古い結果が再利用されます。初めて Q2 をクエリするときは、Q2 とその上流パーティションを初めて作成するため、通常の準備でソースから 4 月の新しいデータを読み取れます。作成時に空だった月も含め、上流キャッシュがすでに存在する場合は、更新漏れを防ぐためにコミット後に影響を受ける月を通知します。

3 件の書き込みと変更通知に使う SQL を表示 
-- 1. March backfill. After the source write commits, register the
--    refresh demand and attempt to call the runner.
INSERT dbo.TABLE_SALES (id, region, customer, dt_month, status, amount)
VALUES (9, N'North', N'A', '20250301', N'completed', 30);

EXEC dbo.DML_REFRESH_MAZ
    @_materialize = N'SALES_MONTHLY',
    @_range_start = '20250301',
    @_range_end   = '20250331';

-- 2. April arrives for the first time. After the write commits,
--    prepare Q2 for the first time.
INSERT dbo.TABLE_SALES (id, region, customer, dt_month, status, amount)
VALUES (10, N'South', N'C', '20250401', N'completed', 40);

-- 3. Back to Q1. After the February correction commits, refresh
--    the month and the quarter.
UPDATE dbo.TABLE_SALES SET amount = 25 WHERE id = 2;

EXEC dbo.DML_REFRESH_MAZ
    @_materialize = N'SALES_MONTHLY',
    @_range_start = '20250201',
    @_range_end   = '20250228';

各手順の後、次に進む前に、表に記載された期間でレポートの結果を確認します。ロードスクリプトが明示的なトランザクションを開始する場合は、先にコミットし、その後、自動コミット接続で refresh を呼び出します。

デフォルトの refresh は、まず指定した月と影響を受ける四半期をまとめて無効化して登録し、その後にランナーを呼び出します。処理中に "accepted" が返る場合があります。レポートを読み取る前に、クエリの prepare_sql を実行します。この処理は待機し、そのクエリでデータが利用可能かを確認します。クエリで必要になるまで再構築を延期するには、@_invalidate_only=1 を明示的に指定します。この場合は無効化マークを登録して戻ります。ランナーは起動せず、すでに保留中の処理は維持されます。

レポート全体を監査するには、SALES_QUARTERLY に対して、期間を Q1 に設定し、@_force_update = 1 を指定して DML_PREPARE_MAZ を実行します。これにより、このリクエストに必要な月と四半期が強制的に再構築されます。ある月のソースが変わったことだけが分かっている場合は、SALES_MONTHLY から refresh を呼び出します。四半期だけを更新しても、変更が通知されていない古い月次キャッシュは検出されません。

@_match のデフォルトは exact です。like モードで SALES~_% を指定すると、リテラルの接頭辞 SALES_ で始まる名前に一致します。同じモードで % を指定すると、登録済みのすべての Maz に一致します。日付の範囲には開始日と終了日の両方が含まれます。両方の日付を省略した refresh は既存の範囲を処理し、カレンダー全体を事前に構築することはありません。別の月に移動する場合は、移動元と移動先の両方の月を対象にする必要があります。

中断後の再開 #

コミットはパーティションごとに行われます。後続のパーティションの処理に失敗した場合、完了済みのパーティションは保持され、処理中のパーティションの変更はロールバックされます。通常の prepare では、既知のターゲットと範囲を補完できます。force_update=1 を指定して prepare を再実行すると、新たな強制更新が開始されます。

既定の更新が中断された場合、登録済みの残りの処理は STATE に保持されます。エラーを解消したら、DML_REFRESH_MAZ を引数なしで呼び出すか、その後の prepare または refresh の呼び出しでランナーを起動します。既定の更新や force_update=1 を指定した更新を再度要求すると、更新要求が再登録され、完了済みのパーティションが再処理されることがあります。引数なしの refresh は保留中の処理だけを再開し、完了済みのパーティションを再度無効化することはありません。キャンセルまたはタイムアウトが発生した場合は、再開する前に物理接続を閉じてください。ROLLBACK だけでは、ランナーのセッションレベルのロックは解放されません。コミットの応答が失われた場合は、先に状態を再確認してください。

よくある問題 #

症状 確認と対処
ソースデータを修正しても、レポートに古い値が表示される ソースのトランザクションがコミットされたこと、すべてのエントリーポイントと日付が無効化の対象になったこと、その後レポートで prepare_sql が実行されたことを確認してください。下流のオブジェクトにだけ通知した場合は、その上流のオブジェクトも無効化する必要があったか確認してください。
プロシージャ、ターゲット、またはパラメーター @_match が見つからない ターゲットデータベースに接続していることと、デプロイ時にモデル用に生成された setup_sql が実行されたことを確認してください。名前を完全一致で指定する場合は、登録済みの Maz 名を使用します。LIKE は一致する対象がなくても成功しますが、変更は行われません。どの対象が一致するかを事前に確認してください。
自動コミットを求められる autoCommit=true を設定した JDBC 接続を使用し、明示的なトランザクションも暗黙的なトランザクションも使用しないでください。無効化の呼び出しは、ソースへの書き込みトランザクションがコミットされた後に行ってください。
無効化時に、日付の不足、順序の逆転、または未カバーの日付が報告される 開始日と終了日をこの順に指定し、期間内のすべての日が dbo.DML_CALENDAR に含まれていることを確認してください。マテリアライズ済みの範囲すべてを対象にする場合は、両方の日付を省略してください。
ライターの実行権限がない 呼び出し元アカウントに、無効化プロシージャと影響を受ける各 Maz のライターを実行する権限があるか、データベース管理者に確認を依頼してください。無効化の前に、影響を受けるすべてのターゲットが検証されます。必要な権限がない要求は拒否されます。
呼び出し中にロック待ちがタイムアウトするか、接続が切断される クライアント側でキャンセルまたはタイムアウトが発生した場合は、そのとき使用していた物理接続を閉じてください。接続プールを使用している場合は、その接続を破棄して、ランナーのセッションレベルのロックを解放してください。エラーを解消したら、DML_REFRESH_MAZ を引数なしで呼び出して登録済みの処理を再開します。クエリの準備に失敗した場合は、prepare_sql 全体を再実行し、data_ready=1 になってからクエリを実行してください。

状態テーブルの読み取り権限がある場合は、次のクエリでパーティションを確認できます。

SELECT materialize, dim_dt, state, COALESCE(last_end_time, created_end_time) AS build_finished_at
FROM dbo.DML_MATERIALIZE_STATE
WHERE materialize IN (N'SALES_QUARTERLY', N'SALES_MONTHLY')
ORDER BY materialize, dim_dt;

state = 0 は通常の無効化、state = 3 は無効で能動的な更新を待っている状態、state = 1 は完全な結果が公開済みであることを示します。ビルド時刻は、Maz のライターが処理を完了した時刻です。特定の修正が反映されているかを判断するには、無効化の通知と、それに続く準備処理も確認してください。

次のソースクエリで演習の最終結果を確認してください。Q1 は 205、Q2 は 40 です。

WITH source_rows AS (
    SELECT DATEFROMPARTS(YEAR(dt_month), 3 * (DATEPART(quarter, dt_month) - 1) + 1, 1) AS dt_quarter,
           amount
    FROM dbo.TABLE_SALES
    WHERE dt_month >= '20250101' AND dt_month < '20250701'
)
SELECT dt_quarter, SUM(amount) AS sales
FROM source_rows
GROUP BY dt_quarter
ORDER BY dt_quarter;

prepare と refresh の規約を参照してください。

ランナー全体の進捗を監視する #

生成された setup_sql で共有の進捗ビューをインストールし、次のクエリを実行します。

SELECT pending_partitions, runner_running, estimated_seconds
FROM dbo.DML_MAZ_PROGRESS;

ビューには、クエリごとに直近 60 秒間の統計が表示されます。統計には、現在保留中の処理、完了したパーティションと追加されたパーティションのそれぞれの単位時間あたりの件数（重複を除く）、および保留中の処理がなくなるまでの推定秒数が含まれます。対象期間内に同じパーティションの処理が複数回完了しても、1 回として数えます。保留中の処理がなければ推定値は 0 です。処理を残したままランナーが停止した場合や、完了する処理より追加される処理のほうが多く、保留中の処理を解消できない場合は NULL です。監視用アカウントには、このビューに対する SELECT 権限が必要です。

このビューが示すのは全体の進捗であり、このレポートの準備が完了したかどうかは判断できません。レポートを参照する前に、対象クエリの prepare_sql を使って、データの準備が完了するまで待ち、完了を確認してください。各列の詳しい説明、実行時オブジェクトの所有者、復旧手順については、prepare と refresh の規約を参照してください。
