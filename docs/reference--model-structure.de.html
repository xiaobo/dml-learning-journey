Diese Seite beschreibt Felder auf Modellebene, Datensätze, Spaltenmakros und gemeinsame Metadaten. Die Sichtbarkeit eingebundener Dateien und die Namensauflösung sind unter Modellzusammensetzung beschrieben.

Felder auf Modellebene #

Feld Typ Beschreibung
includes string[] Pfade zu weiteren .dml-Dateien, die zusammengeführt werden sollen (die Symbole werden vereinigt)
dialect string Ziel-SQL-Dialekt. Geben Sie ihn explizit an. Die erkannten Namen, den Standardwert und den Ausführungsumfang finden Sie unter SQL-Dialekt.
column-macros object Gemeinsame Spaltendefinitionen für mehrere Datensätze
<name> object | string Ein Datensatz, eine Kennzahl, ein dt-macro, ein fn-macro, ein materialize-Objekt oder eine Abfrage

Zulässige Objektnamen: Jede Zeichenfolge außer reservierten Schlüsselwörtern (includes, column-macros, datasets, measures, columns, dimensions[dt], dt-macros, fn-macros, materializes, queries, dialects sowie deren Singularformen).

Kurzform für Kennzahldefinitionen: Ist der Wert eines Eintrags auf oberster Ebene eine einfache Zeichenfolge, wird er als Kurzform für eine Kennzahlformel behandelt:

Umsatz: SUM({Verkaufsbetrag})
# equivalent to:
Umsatz:
    type: measure
    formula: SUM({Verkaufsbetrag})

SQL-Dialekt #

Der geprüfte Compiler erkennt adb_mysql, duckdb, mssql, mysql, postgres und sqlite. Der aktuelle Compiler weist das geprüfte Modell zurück, wenn die Dialektangabe fehlt. Geben Sie den Zieldialekt explizit an. Eine konfigurierte DuckDB-Verbindung ändert den Zieldialekt des Modells nicht. Geben Sie für DuckDB als Ziel dialect: duckdb an.

BigQuery, Snowflake, Databricks und ClickHouse wurden bei dieser Prüfung nicht als Ziele erkannt. Wenn eine Bereitstellung eine nicht erkannte Datenbank-Engine voraussetzt, muss diese Anforderung geklärt werden, bevor dmlc für die Bereitstellung eingesetzt wird.

Die Erkennung eines Dialekts und der Umfang der geprüften Ausführung sind getrennt zu betrachten. Die ausführbaren Beispiele prüfen hauptsächlich Ergebnisse in DuckDB. Die Übersicht dokumentiert die Kompilierung für SQL Server gesondert. Diese Prüfungen belegen keinen identischen Funktionsumfang für alle sechs Datenbank-Engines. Validieren Sie das erzeugte SQL und vergleichen Sie die Ergebnisse in der vorgesehenen Datenbank. Erzeugtes SQL kann mehrere Anweisungen, Zwischenrelationen und Kalenderobjekte erfordern.

Datensatzdefinition (type: dataset) #

<name>:
    type: dataset
    table: <table_name>          # required (or sql:)
    # sql: <SELECT ...>          # alternative to table: — derived dataset
    dimension: [col1, col2]      # dataset grain dimensions
    materialize: <name>          # optional, declare a materialize table for this dataset
    # or:
    # materialize:
    #     name: <name>
    #     parameters:
    #         <param>: <value>
    columns:                     # required
        col1:                    # direct column (pass-through)
        col2: expr               # calculated column (inline expression)
        col3:                    # full column definition
            abbr: <source_column> # optional when the names match
            description: <text>
            formula: expr        # calculated column (block form)
            # source: expr       # alternative to formula: data-source verification formula
            prerequisite: <expr> # column-level grain constraint
    dimensions[dt]:              # optional explicit time metadata; coarser standard dt_* fields may be system-derived
        dt_date: date
        dt_month: month
    measures:                    # atomic measures (inherit enclosing dataset; no dataset:)
        <measure_name>: <formula or full definition>
            abbr: <short>
            description: <text>

Einschränkungen:

  • Geben Sie genau eines der beiden Felder table: oder sql: an (sie schließen sich gegenseitig aus).
  • table: legt eine exklusive Zuordnung fest. Mit table: policy gehört die physische Tabelle dem Datensatz Policy. Andere Datensätze dürfen den physischen Tabellennamen in sql: weder mit FROM noch mit JOIN referenzieren. Schreiben Sie from {Policy} bzw. join {Policy} (der Compiler setzt den Abfragenamen des Datensatzes ein), oder rufen Sie Attribute mit pk(...).{Policy}.Col ab und lassen Sie den Join weg. Um eine Tabelle ohne exklusive Zuordnung gemeinsam zu verwenden, geben Sie sql: select * from <table> anstelle von table: an.
  • Muster für Faktentabellen: Dimensionsdatensätze (Claim, Policy) verwenden table:. Ein Faktendatensatz, der nur die Attribute dieser Dimensionen benötigt, kann weiterhin eine Quelltabelle ohne exklusive Zuordnung verwenden und die Attribute mit pk() abrufen, statt in sql: einen Join mit der exklusiv zugeordneten Tabelle auszuführen.
  • Sichtbarkeit: Die geprüfte Version unterstützt innerhalb derselben Datei Verweise auf später definierte Datensätze, Kennzahlen und Spalten. Eingebundene Dateien müssen Namen über ihre eigenen Definitionen oder Einbindungen auflösen. Die übergeordnete Datei steht dafür nicht zur Verfügung. Siehe Modellzusammensetzung.
  • Wenn Sie eine Datei direkt kompilieren, benennen Sie die Abfrage wie die Datei ohne Dateiendung (report.dml → report).
  • allows: legt fest, welche Materialisierungen infrage kommen (ALL, NONE oder explizit angegebene Namen). Die Einstellung überschreibt keine Kennzahldimensionen.
  • Für die im Beispiel gezeigte Form einer Kennzahlabfrage ist columns: erforderlich.
  • dimensions[dt] hat die folgenden Aufzählungswerte: year, quarter, month, week, date und hour.
  • materialize: akzeptiert entweder einen Namen als Skalarwert oder ein Objekt mit dem Pflichtfeld name: und dem optionalen Feld parameters:. Beide Formen identifizieren dieselbe Materialisierung innerhalb des Datensatzes.

Mit dem SQL eines Datensatzes lassen sich unterstützte Joins, Vereinigungen und Unterabfragen vor der Auswertung der Kennzahlen ausführen. UNION ALL erhält die Zeilenmultiplizität: Ein Schlüssel, der die Zeilen in jeder Eingabe für sich eindeutig identifiziert, ist für die zusammengeführten Zeilen möglicherweise nicht eindeutig. Definieren Sie einen Schlüssel für die zusammengeführte Relation, statt anzunehmen, dass der ursprüngliche Schlüssel eines Zweigs eindeutig bleibt. Die geprüften Beispiele greifen über {DATASET}-Referenzen auf Quelldatensätze zu, die nur Spalten definieren. Das aktuelle Programm validiert diese abgeleiteten Relationen, ohne eine nicht verfügbare Zwischentabelle vorauszusetzen. Prüfen Sie den vollständigen Schlüssel der abgeleiteten Relation: Sind die Schlüssel eindeutig, ist die Validierung erfolgreich. Bei doppelten Schlüsseln meldet der Validierungsbericht einen Verstoß mit data.issues[].kind: duplicate_key. Ergänzen Sie die fehlende Schlüsselkomponente, damit die Validierung wieder erfolgreich ist. Eine fehlende physische Quelle führt zu EXECUTION_ERROR und wird nicht als doppelter Schlüssel gemeldet. Prüfen Sie die fachlichen Ergebnisse zusätzlich zur Validierung.

Formen der Spaltendefinition:

Form YAML Bedeutung
Direkt Verkaufsbetrag: (null) Übernimmt die Spalte der zugrunde liegenden Tabelle unverändert
Berechnet (inline) net: Verkaufsbetrag - Rabattbetrag (Zeichenfolge) Per Ausdruck abgeleitete Spalte
Berechnet (Block) net: { formula: Verkaufsbetrag - Rabattbetrag } Abgeleitete Spalte mit Metadaten
Mit Verifizierungsformel net: { source: Verkaufsbetrag - Rabattbetrag } Deklariert eine Formel zur Überprüfung der Datenquelle. Die Kompilierung allein weist nicht nach, dass die Quellwerte übereinstimmen.

Namensbindung mit geschweiften Klammern in Formeln:

Schreibweise in formula: Wird gebunden als Beispiel
Verkaufsbetrag allein Physische (native) Tabellenspalte. Der Compiler übernimmt den Namen unverändert in das SQL. net: Verkaufsbetrag - Rabattbetrag, wenn beide Spalten als direkt definiert sind
{calc_amt} Berechnete Spalte (oder Kennzahl bzw. Spaltenmakro). DMX expandiert die Definition. VerdoppelterWert: '{calc_amt} * 2'

Ein Name ohne geschweifte Klammern in der Formel einer berechneten Spalte wird als native SQL-Spalte behandelt. Die Reihenfolge der Aliase in SELECT kann den Eindruck erwecken, dass der Verweis funktioniert. Die Definition der berechneten Spalte wird jedoch nicht expandiert. Setzen Sie den Namen in geschweifte Klammern, wenn die Formel diese Definition wiederverwenden soll.

Abhängigkeiten zuerst zu definieren, ist eine Konvention für bessere Lesbarkeit. In der geprüften Version wurde ein pk()-Verweis auf ein später in derselben Datei definiertes Ziel erfolgreich kompiliert. Nicht auflösbare Namen können auf eine fehlende Einbindung, einen Tippfehler oder einen Verstoß gegen die Sichtbarkeitsregeln für Einbindungen hinweisen. Siehe Modellzusammensetzung.

Spaltenmakros #

Spaltenmakros definieren Spalten, die in mehreren Datasets verwendet werden:

column-macros:
    datasets: [tx, orders]       # scoped datasets
    columns:                     # shared column definitions
        Region: '{Filialanzahl}.Region' # cross-dataset lookup
    dimensions[dt]:
        dt_month: month

    # OR per-dataset scope:
    <dataset_name>:
        <col>: <formula>

Gemeinsame Metadatenfelder #

Welche Metadaten unterstützt werden, hängt vom Objekttyp ab. Maßgeblich ist die zugehörige Schemadefinition:

Feld Typ Beschreibung
abbr string Wenn ein Feld im Modell anders heißt als die Spalte in der Quelltabelle, geben Sie hier den Namen der Quellspalte an. Für eine Kennzahl können Sie einen kurzen internen Namen vergeben. Das Abfrageergebnis zeigt den fachlichen Namen oder den mit AS angegebenen Alias.
description string Für Menschen verständliche Beschreibung
tags string[] Frei wählbare Tags
prerequisite string (Formel) Einschränkung für die zulässige Ebene, auf der Zeilen oder Summen definiert sind (Kennzahlen, Spalten, dt-Makros, fn-Makros)

Spaltenmetadaten sind keine SQL-Typdeklaration #

Spalteneigenschaften müssen dem DML-Schema entsprechen. Geben Sie die Eigenschaften unter der jeweiligen Spalte an. Steht type: text innerhalb von columns: auf derselben Ebene wie diese Spalte, definiert der Eintrag eine andere Spalte namens type. Ob das Modell akzeptiert wird, sagt dann nichts über den Typ der ursprünglich gemeinten Spalte aus. In der geprüften Build-Version werden sowohl type: text als auch type: banana unter einer Spalte als nicht unterstützte Eigenschaft abgelehnt. Dabei wird das Metadatenschema validiert. Daraus lässt sich keine vollständige statische Typprüfung von Ausdrücken ableiten. Definieren Sie physische Spaltentypen in der Datenbank und verwenden Sie bei einer erforderlichen Konvertierung unterstützte Ausdrücke oder Casts. Die Angaben type: dataset und type: measure auf oberster Ebene kennzeichnen DML-Objektarten. Sie deklarieren keine SQL-Werttypen.

Systemkalender #

Bei manchen Verbindungen wird DML_CALENDAR initialisiert, sobald die Verbindung erstmals für eine Validierung mit Datenbankzugriff oder eine Ausführung verwendet wird. Das gilt auch, wenn die Abfrage keinen Zeitmodifikator enthält. Bei der getesteten DuckDB-Verbindung wurde für jeden Tag von 2016 bis einschließlich 2036 eine Zeile initialisiert (7,671 Zeilen). Das für die Initialisierung verwendete Konto benötigt die Berechtigung, die Tabelle im Zielschema anzulegen und zu befüllen. Für nachfolgende Abfragen ist Lesezugriff erforderlich.

Wenn das Laufzeitkonto keine Tabellen erstellen kann, lassen Sie den Kalender von einem Datenbankadministrator mit derselben dmlc-Build-Version, demselben Verbindungsdialekt und demselben Schema initialisieren, bevor Sie die Validierung mit dem Laufzeitkonto ausführen. Prüfen Sie, ob der Kalender den Berichtszeitraum und die Vergleichszeiträume abdeckt.
