Kennzahl als Dimension

Bei diesem Muster wird für jede Entität ein Label berechnet. Anschließend werden die Kennzahlen nach diesem Label gruppiert. Das Label dient in der Abfrage als Dimension. Es identifiziert keine Quellzeilen.

Entitätsschlüssel und Auswertungsstufen #

Die Klassifizierung benötigt einen vollständigen Entitätsschlüssel, weil ein Label zu einer Entität auf einer bestimmten Granularitätsebene gehört. Dabei bezeichnet Q die regulären Berichtsfelder und K den Entitätsschlüssel. Mit +d: K wird der Klassifikator auf der durch Q ∪ K definierten Ebene ausgewertet. Der Compiler ordnet das Label über den vollständigen Schlüssel zu und aggregiert anschließend die regulären Kennzahlen nach Q und dem Label.

Für die atomare Definition sales: SUM({amount}) gruppiert dieses Abfragefragment Kunden nach ihrem Umsatzwert.

report:
  type: query
  columns:
    dimension:
      - sales_bucket: '{sales: {+d: customer}}'
    total_sales: 'SUM({sales: {+d: customer}})'

Das explizite äußere SUM summiert die Umsätze der Kunden mit demselben Label. Dieses Beispiel verwendet den Umsatzwert selbst als Label. Eine fachlich definierte Kategorie benötigt eine eigene Klassifikatordefinition und muss eigens geprüft werden.

An der Stelle, an der die Klassifizierung verwendet wird, ist ein expliziter Schlüssel erforderlich. Die alleinstehende Referenz {measure} wird abgelehnt. Eine feiner granulare Auswertungsstufe innerhalb der Maßdefinition oder eine Kennzahl auf derselben Ebene liefert den fehlenden Schlüssel nicht.

Im aktuell geprüften Build werden die getesteten Klassifikatoren auf Basis einer Zählung mit +d: customer und dimension: [customer] so kompiliert, dass zuerst pro Kunde aggregiert und danach nach Label gruppiert wird. Die Prüfungen bestätigen ausschließlich die getesteten Schreibweisen.

Grundgesamtheit und erneute Aggregation #

Der Umfang der Klassifizierung, die Zugehörigkeit von Entitäten zur Grundgesamtheit und der Berichtsumfang werden unabhängig voneinander festgelegt. -d behält Zeitfilter bei. Wenn die Gruppierung nach Zeit entfällt, erstreckt sich die Klassifizierung daher nicht automatisch über die gesamte Lebensdauer. Ein Label mit dem Wert NULL kann eine gültige Kategorie bilden. Es belegt nicht, dass eine Entität fehlt, und die Klassifizierung erzeugt keine inaktiven Entitäten.

Mehrere Labels erfordern kompatible vollständige Entitätsschlüssel und voneinander unabhängige Definitionen. Additive Beträge lassen sich ausgehend von der Ebene einzelner Entitäten summieren. Verhältniszahlen, Mittelwerte und Anzahlen unterschiedlicher Werte benötigen Komponenten, mit denen ihre Definition bei der erneuten Aggregation erhalten bleibt.

Filter auf Klassifizierungslabels und Kennzahlen #

Ein Filter auf einem Klassifizierungslabel oder auf Kennzahlen derselben Ebene, die auf Label-Ebene ausgewertet werden, wird nach der Klassifizierung angewendet. In DML-Abfragen lässt sich eine solche Bedingung unter filters: angeben, etwa "{首购月} is not null OR {销售额} > 0":.

Model Query kann eine Bedingung für ein Maß als HAVING darstellen. Die semantische Auswertungsstufe ist wichtiger als dieses Schlüsselwort. Das bei der Kompilierung erzeugte SQL verwendet häufig WHERE auf der Relation, die durch die Klassifizierung entsteht. Wird die Bedingung vor die Klassifizierung verschoben, ändert sich die Grundgesamtheit, aus der das Label berechnet wird.

Einschränkungen #

Dieses Muster bezieht sich auf columns.dimension in Abfragen. In der geprüften Materialisierung lässt sich ein reguläres Attribut {region} kompilieren. Der Ausdruck {sales: {+d: id}} in materialize.dimension_columns wird dagegen abgelehnt, weil der Maßverweis dort nicht verfügbar ist. Übernehmen Sie einen Klassifikator aus einer Abfrage nicht unverändert in Materialisierungsattribute. Prüfen Sie die erzeugten Stufen für Klassifizierung und erneute Aggregation. Validieren Sie anschließend anhand Ihrer eigenen Daten die Schlüssel und vergleichen Sie die daraus ermittelten Ergebniswerte.
