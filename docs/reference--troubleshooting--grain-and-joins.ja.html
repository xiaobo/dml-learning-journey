フィルターの配置エラー #

症状：[filters]: not supported、cannot derive from dimension、referred column … is undefined

原因：--to-dml の後、述語が誤った階層に残っています。たとえば、データセットに filters: を指定している（スキーマではデータセットに filters: を一切指定できません）、ディメンションの範囲を絞る条件をファクトの sql: にも記述している、またはデータセットをまたぐ属性にクエリフィルターの短縮記法を使っている場合です。

対処：各述語を、意味上どこに適用されるかに基づいて分類します（フィルター配置の階層）。

症状 移動先
[dataset …] [filters]: not supported クエリの filters:、メジャーの式、または sql: の WHERE（データセットでは filters: を一切サポートしていません）
すべてのファクト分岐に繰り返し記述されるライフサイクルまたは属性の述語 レポートごとに述語が変わる場合に限り、クエリの filters: を使います。対象となる母集団を恒常的に定義する場合は、行を除外する形で保持します。
ファクトの sql: の WHERE にある数値またはリンクの述語 中間指標による絞り込みは、除外される行だけで構成されるグループ、同じ階層の他の指標、結合とウィンドウの挙動、および値が存在しない場合と NULL が明示されている場合の意味の違いを検証したうえで使います。
クエリフィルターで referred column {DATASET}.col is undefined が発生する 文字列形式："{DATASET}.col = 値":
2 要素のリスト dt_date: ['2024-01-01', '2025-12-31'] で返されるのは 2 日分だけ リストを直接指定すると、範囲ではなく IN (...) による完全一致にコンパイルされます。両端を含む区間には dt_date: { range: ['2024-01-01', '2025-12-31'] } を使います。
分岐ごとの日付ウィンドウ 対象のデータセットで dt_date を宣言し、クエリで filters: dt_date: range: [...] を指定します。

代替のルックアップを使う判定条件で結合が厳しくなることがある #

「対象ディメンションに一致する、または、一致しなければ間接ディメンションに一致する」という判定ルールでは、2 つのオプションのリレーションを使います。導出したフラグをクエリの filters: に置くと、コンパイルされた SQL で一方のルックアップが必須（INNER JOIN）になったり、AND/OR の式が変換され、代替先を使う条件が保たれなくなったりすることがあります。

次の構成を推奨します。

対象状態: pk({dt_month}, {顧客番号}).{TARGET_CUSTOMER}.state
対象顧客フラグ: |-
  iif({対象状態} = 1, 1,
    iif(pk({顧客番号}).{INDIRECT_CUSTOMER}.顧客番号 is not null, 1, 0))
対象金額: iif({対象顧客フラグ} = 1, {売上金額}, null)

measures:
  売上金額: SUM({対象金額})

次に、生成された SQL を確認します。両方のルックアップが LEFT JOIN のままであり、代替先を使うロジックが CASE の中に残っている必要があります。出力グループに条件を設ける場合は、結果に余分な非表示列が入り込まないように、選択済みの主メジャーを再利用します（HAVING AGG(売上金額) is not null）。一意でないキーや対象ディメンションと間接ディメンションの重複は、診断の手がかりとして扱います。DML のリレーションが意図しない行の増殖を暗黙のうちに再現することは避けてください。

P43. {dimension: [...]} と {-d: dim_dt} の比較（SQL の構造が異なる） #

誤り：参照 SQL がより粗い粒度で別の GROUP BY の CTE を使っているのに、{-d: dim_dt} を使うこと。対処：参照と構造をそろえます。{dimension: [cols]} は集計用の独立した CTE を生成します。{-d: dim_dt} はウィンドウ式 OVER (PARTITION BY …) を使います。P44とP45を参照してください。

P44. ウィンドウ内の構成比と {-d: dim} の比較 #

誤り：--to-dml が生成した下書きの divide({m}, {m_minus_dim_X}) を、業務で使う最終版の DML としてそのまま採用すること。対処：クエリの columns: またはメジャーで divide({m}*1.0, {m: {-d: dim}}) を使います。ディメンション修飾子とフィルター修飾子を参照してください。

Model Query SQL と同等です。ここでは YAML 固有の落とし穴を扱います。ルールの全体はYAML クエリ宣言を参照してください。

P62. メジャーの dimensions: をデータセットの行識別やクエリのグループ化に使う #

症状：データセットの dimension: と同じように、クエリの出力が 地域 でグループ化されると考えて、メジャーに dimensions: [[地域]] を記述します。実際には、そのグループ化なしでコンパイルされるか、別のクエリディメンションを指定すると失敗します。誤った理解：メジャーの dimensions: でデータセットの行の識別方法やクエリのグループ化を指定できる。正しい理解：メジャーの dimensions: には使用可能なディメンションを指定します。内側のリストはそれぞれ 1 つのディメンションを表し、外側のリストは選択肢を列挙します。行の識別方法はデータセットの dimension: で指定します。グループ化はクエリの GROUP BY または columns.dimension: で指定します。対処：その指標で使用可能なディメンションを実際に限定する必要がある場合を除き、メジャーの dimensions: を削除します。結果のグループ化はクエリで指定します（GROUP BY / columns.dimension:）。

# Wrong: expecting dimensions: to produce GROUP BY region
売上高:
    type: measure
    dataset: 取引明細
    formula: SUM({売上金額})
    dimensions:
        - [地域]

# Right: no dimensions: lock; grouping lives in the query
売上高:
    type: measure
    dataset: 取引明細
    formula: SUM({売上金額})
# SELECT region, AGG(sales) FROM MODEL GROUP BY region

各役割の仕様については、ディメンションの役割を参照してください。

P64. メジャーに materialize: true を指定する #

症状：コンパイル時に ERROR error during processing [ref null]: undefined modifier 'materialize' が表示され、メジャーは暗黙のうちに除外されます（0 measure(s) processed）。誤り：コンパイラーが事前集計すると考えて、メジャーの定義に materialize: true を追加すること。メジャーレベルのマテリアライズ用フラグはありません（dmlc 0.3.16 で dmlc -c を実行して確認済み）。対処：マテリアライズは、トップレベルの type: materialize オブジェクト（parameters: + dimension: + measures:）、またはデータセットレベルの materialize: <name> で宣言します。メジャーには指定しないでください。マテリアライズの定義（type: materialize）とマテリアライズの例を参照してください。

# Wrong
売上高:
    type: measure
    dataset: 取引明細
    formula: SUM({売上金額})
    materialize: true   # ← undefined modifier 'materialize'

# Right
DWS_SALES:
    type: materialize
    parameters:
        dt_date: date
    dimension: [dt_date, 商品]
    measures: [売上高]

P66. 明示的なエンティティキーなしでメジャーをディメンションとして使う #

症状：コンパイルには、+d または dimension: でエンティティキーを明示する必要があります。通常は +d を使い、ディメンションを置き換える形式を使う前に、そのリリースの制限事項を確認してください。誤り：キーを指定せずにメジャーを使い、そのメジャーをどの単位のエンティティで評価するかが、出力される別のメジャーから明示的または暗黙的に決まると考えること。対処：メジャーをディメンションとして使う箇所で、完全なエンティティキーを宣言します。入力となるメジャーにキーが明示されていれば、インラインのスカラー関数で囲むこともできます。メジャーをディメンションとして使うを参照してください。

# Wrong
dimension:
    - payment_day

# Right, inline scalar
dimension:
    - payment_day: 'cast({承認日時: {+d: payment_id}} as date)'

P67. 指標から派生したディメンションの非互換性や依存関係 #

症状: コンパイル時に、分類キーに互換性がないか、ラベル間に依存関係があると報告されます。誤り: あるラベルが {+d: 店舗番号} を使い、別のラベルが {+d: 顧客番号} を使っています。または、あるラベルが同じクエリで宣言された別のラベルを参照しています。修正: 独立したラベルには、同じ完全なエンティティキーを使います。キー項目の順序は異なっていてもかまいません。ラベルが実際に異なる粒度で定義される場合は、別のリレーションまたは再利用可能な業務指標としてモデル化します。

P68. 出力指標を分類の粒度から上位の粒度に集計できない #

症状: コンパイル時に、集計が指定されていないか、再集計できないと報告されます。誤り: {売上高: {+d: 店舗番号}} をそのまま出力する、計算済みの重複を除いた件数を合計する、または意図した重み付けを定義せずに比率の平均を取ることです。修正: SUM({売上高: {+d: 店舗番号}}) のように、細かい粒度の参照を目的の集計関数で囲みます。比率の場合は、構成要素を上位の粒度に集計してから比率を再計算します。重複を除いた件数、中央値、パーセンタイルなどの指標では、適切な入力や集計状態を保持するか、サポートされる別の指標を定義します。いずれも行わない場合は、コンパイルエラーを許容します。

P69. 細かい粒度の WHERE を粗い粒度のクエリの filters: に指定 #

症状: CTE は粒度 (G)（例: 商品×地域）で集計し、絞り込み（売上件数 > 3）を行ってから、SUM で粒度 (Q)（例: 商品）まで集計します。ドラフトまたは --to-dml は、filters: "売上件数 > 3" と SUM({合計: {+d: 地域}}) を含むものの、クエリのディメンションとしては (Q) だけを出力します。コンパイルやクエリの統合により、これが商品レベルの HAVING COUNT(1) > 3 に変わり、集計対象が意図と異なることがあります。

誤り:

filters:
  "売上件数 > 3":                 # cnt is not defined at product-only grain
columns:
  dimension: [商品]
  総計: 'SUM({合計: {+d: 地域}})'

これも誤り: SUM({合計: {+d: 地域, +f: '{売上件数} > 3'}}) は入力の述語で集計指標を使っています。診断メッセージが指しているのはこの述語です。指標参照への +f の適用全般を禁止するものではありません。対応機能一覧を参照してください。

修正: 上位の粒度への集計の中で、共通の細かい粒度で絞り込みます。

総計: |-
  SUMIF({合計: {+d: 地域}}, {売上件数: {+d: 地域}} > 3)
# No accepted fine rows -> NULL; ELSE 0 would change that result.

クエリの filters: は、レポートまたは HAVING の範囲に限って使います。+d を使った多段集計a を参照してください。

P70. アトミック指標での OVER #

症状: window functions are not allowed in atomic measures が表示されます。古いバイナリでは、パーティション列が欠けた無効な SUM(…) OVER (…) … GROUP BY を生成し、終了コード 0 で終了する場合があります。

誤り:

measures:
  純仕入数量: 'SUM({数量}) over (partition by {店舗番号}, {商品番号})'

修正: ウィンドウ関数の配置では、明細行に対する OVER を columns: の下に置き、その後でアトミック集計を行います。

columns:
  純数量: 'SUM({数量}) over (partition by {店舗番号}, {商品番号})'
measures:
  純数量合計: 'SUM({純数量})'

GROUP-BY 後の順位や構成比は、{-d:} または {-df:} を使う複合指標のままです（dataset: は指定しません）。仕様はウィンドウ関数の配置を参照してください。

P71. 指標の PARTITION BY での {col} の直接参照 #

症状: … reference is not allowed in PARTITION BY が表示されるか、{dimension:} または {-d:} に関するヒントが表示されます。

誤り（指標での指定）: SUM({合計}) over (partition by {商品})。修正:

  • 明細行に対するウィンドウ関数は columns: に移し、そこで引き続き {商品} を直接参照します。
  • 集計後に適用するウィンドウ関数では、複合指標で partition by {-d: 地域} または {dimension: 商品} を使います。

明細行に対するウィンドウ関数では、データセットの columns: の下に {-d:} を置かないでください。ここでは列を直接参照します。

dmlc 0.3.16 で確認済みです（商品に 2 つの役割がある買い物かご併売分析の移行）。これらのケースでは、コンパイルはエラーなく通りますが、通知なしに意味が変わります。生成された ON 句を必ず確認してください。

P72. 粒度を定義する 2 つのフィールドが同じ列を参照すると、データセット間の上位集計で誤ったキーが結合に使われる #

症状: 厳格モードでコンパイルに成功し、診断メッセージも出ませんが、比率が誤っています。たとえば、リフトの分母が本来の left_count * right_count ではなく left_count * left_count になります。

誤り: データセットは、1 つの物理列に基づく 2 つのフィールド（left_product_id: '{商品番号}'、right_product_id: '{商品番号}'）を公開しています。2 番目の役割の上位集計 {sold_baskets: {-df: [left_product_id]}}（または {dimension: [month, store, right_product_id]}）は、right_product_id で結合される想定です。コンパイラは、粒度を粗くした一時結果のキーに別名を付け直し、最初の役割のキーで結合します（support.商品 = pair.left_product_id）。

修正: 各役割を pk() で sql: データセットから参照します。このデータセットでは、ソースを (shared dims, 商品番号) の粒度でグループ化し、dimension: を宣言します（P77）。pk() のキーは明示的に指定され、位置で対応付けられるため、左右のキーが同一のキーとして扱われることはありません。または、-df による上位集計を、別名の衝突が起きない粒度に限定します。生成された SQL に、… 商品番号 = t.left_product_id と … 商品番号 = t.right_product_id の 2 つの結合が個別にあることを確認してください。

P73. -df で上位集計する複合指標は、結合相手にしかない行を出力し、欠けているキーに値を補って出力することがある #

症状: 別のデータセットから上位の粒度に集計した指標は、コンパイル時に FULL OUTER JOIN を使う複合指標になります。集計された結合相手にしか存在しない行も出力されます。結合相手の一時結果では、粒度を定義するフィールドのうち、持っていないものを max(<col>) で補う場合があります。その結果、対応する行がない (month, store, 商品) 行が left = right = 商品 として現れることがあります。単に NULL が出るだけでなく、同じ商品同士のペアが作られます。

修正: 結合相手にしか存在しない行で NULL になる主指標を出力項目に残し、式をキーにしたフィルターでクエリを絞り込みます。

filters:
    '{同時購入注文数} is not null':      # formula as key, empty value

コンパイルすると、結合し直す箇所に WHERE <primary> IS NOT NULL が生成されます。主指標に値があると確認できるため、生成される FULL OUTER JOIN も LEFT JOIN に簡略化されます。最終的な結合タイプは、複合指標のテンプレートではなく、生成された SQL で確認してください。まず前提を確認してください。有効な主グループでは、主指標が NULL になることはありません。このフィルターが有効なのは、結合相手にしか存在しない行に主指標の値がない場合に限ります。（ディメンション修飾子b の補足です。）

P74. 1 つの物理テーブルを使う 2 つの table: データセット：マージ時の挙動と、警告なしに失われる -df の粒度 #

症状：warn during processing [dataset B]: similar dataset(s) [A] exist, consolidate?。続いて、2 つのデータセットの列構成が異なる場合は skip dimension column <f> for measure <m> which does not exist in dataset <A> が出力され、ロールアップは追加の通知なしにより粗い粒度で集計します（例：pk(店舗番号, left_id) ではなく pk(店舗番号)）。

確認済み（dmlc 0.3.16）：同じテーブルに 2 つの table: データセットがあるだけでは、クラッシュしません。最小の対称構成はコンパイルでき、2 つ目のデータセットを別の役割で使う場合も、-df の参照先は正しく決まります（right_id = t1.right_id）。データセットは主キーで自己結合され、1 つの #TEMP にマージされます。ただし、片方にだけ列を追加すると、マージ後の -df の名前解決では、もう片方のデータセットの別名フィールドが対象から外れます。（以前の「table: の重複 → NPE」という報告は原因の特定を誤っていました。クラッシュの原因は P75 のフィルターの記述形式でした。）

対処：原則として、物理テーブルごとに 1 つの table: データセットを使い、列に別名を付けます。複数の役割で使う必要がある場合は、列構成を同一にし、出力された SQL でロールアップ用の一時テーブルすべての pk(...) を確認します。ここでの警告は意味上の誤りを示します。

P75. クエリの filters: に記述する指標のガードフィルター：記述形式とエラー時の挙動 #

正しい書き方：'{measure} is not null':。式全体をキーにし、値は空にします。この方法で、FOJ の結果に含まれる結合相手のない行を、クエリの粒度で除外できます。

誤った書き方：my_measure: {condition: '...'} → スキーマエラー（condition はフィルターのプロパティではありません）。my_measure: '<expr>' ではキーが列名として扱われます。キーが指標に解決されると、Query.treat_filters は診断メッセージを出す代わりに NPE を発生させる場合があります。

対処：式そのものをキーにし、参照先の指標をクエリの粒度で解決できることを確認します。指標の参照を解決できない場合は、分かりやすいエラーメッセージの代わりに NPE が発生します。

P76. -df / -d の引数には、ソース列名ではなく、粒度を定義する宣言済みフィールド名を指定する #

症状：バインディング（columns.dimension: [..., new_name: '{col}']）でクエリのディメンション名を変更すると、column(s) [x] has been specified as -d/-df, but not in dimension [...] が表示されます。

原因：バインディングによって内部フィールド（new_name__<query>）が生成されます。修飾子は、粒度を定義するフィールド名を使ってフィールドを除外します。元の列名は粒度の定義に含まれなくなります。

対処：-df / -d / dimension: には、粒度を定義する宣言済みフィールド名を渡します。引き続き名前で除外する必要があるフィールドは、データセット内にその名前で残します。

P77. pk() で集計済みリレーションを参照する：参照先の sql: と外側の指標の dataset: #

症状：MAX(pk(...).{Support}.col) に対して dataset must be specified when aggregate non-measure column, did you mean <SupportDataset>? が表示されます。

ルール:

  • pk() の参照先には、データセットまたは直接指定する TABLE(pk_cols) 形式を使います。指標を pk() の参照先にすることはできません。そのため、集計済みの参照値（例：より粗い粒度での count(distinct …)）には、dimension: を宣言した sql: データセットが必要です。コンパイルすると、ほかのディメンションと同じように結合できる、インデックス付きの一時テーブルになります。
  • 外側の集計指標は、参照値を利用する側のデータセットの行を順に処理します。dataset: には、補助データセットではなく利用側のデータセットを指定します（dataset: BasketProductPair）。
  • 参照クエリの INNER JOIN は、補助データセットに必ず一致する行がある場合、コンパイル時に LEFT JOIN になります。この変換が許されるのは、検索キーが同じ母集団から生成される場合に限ります。判断の根拠は例外の記録に残してください。

P79. 同じディメンションに対する +d と -d / -df の併用 #

誤った挙動：{销量: {+d: 门店, -d: 门店}} または {销量: {+d: 门店, -df: 门店}} が受理され、それぞれ単純な {销量} または {-f: 门店} に書き換えられます。

理由：暗黙の解釈は一意に定まりません。修飾子を相殺すると入力ミスが隠れます。AVG では、細かい粒度での評価と単純な参照では評価段階が異なります。出力の粒度にそのフィールドがすでに含まれる場合、-df ≠ -f です。

対処：意図する評価段階を 1 つ指定します。単純な参照、細かい粒度を明示した参照とその外側での集計、または除外用の修飾子を使います。対象フィールドが異なる場合は、引き続き修飾子を併用できます。今回確認したビルドは、検証した競合を診断メッセージなしで受理し、外側で合計する前に地域別の合計値を繰り返し出力します。これは、競合を拒否するという要件に違反します。修飾子の組み合わせを参照してください。

P80. -f / -df により、出力の粒度に含まれないフィールドのクエリフィルターがレポート行に適用されなくなる #

誤った挙動：クエリフィルターが {店舗番号}=1 で、指標が {-f: 店舗番号} を使い、店舗番号 が出力の粒度に含まれない場合、フィルターが通知なしに省略され、フィルターが適用されていない側の FOJ の対応行が出力されます。

対処：-f がフィルターを外すのは指標の評価からだけです。クエリフィルターは引き続き対象となる行の集合を定義します。適用が抑止されたフィルターが出力列を参照できない場合は、相関 EXISTS またはセミジョインで行を絞り込みます。-f だけでグループ化を変更しないでください。

P81. カレンダーを介した展開なしで dimension: により異なる粒度の時間ディメンションに置き換える場合 #

誤った挙動：dt_month のクエリで {销量: {dimension: [dt_quarter]}} を指定すると、単一のスカラー値が付加されるか、月単位の CTE から dt_quarter を解決できません。

対処：カレンダーを介して月または日付を四半期に対応付け、四半期の粒度で評価します。次に、その四半期の合計を同じ四半期内の各月の行に展開します（nullpk(pk(dt_month).CAL.dt_quarter) のパターン）。加法性のある SUM では月別の値を再集計できます。非加法指標は、ファクトデータから粗い粒度で計算する必要があります。

P78. sql: エスケープには、集計対象と期間を絞り込む条件を組み込む必要がある #

症状：クエリの dt_* 範囲フィルターが sql: ブロックのテキスト内にプッシュダウンされることはありません。コンパイルで生成される一時的な派生テーブルの外側の WHERE 句に適用されます。エスケープ内の自己結合で片側に期間の制限がないと、集計対象が気づかないうちに広がります（たとえば、右側にあるレポート期間外の行もペアを形成します）。

対処方法：集計対象を常に限定する条件（line_status = 'SOLD'）と対称な期間の境界をエスケープの内部クエリに組み込み、結合の各側や各分岐に同じ採用条件を適用します。レポートの対象範囲は、クエリの filters: で外側のキーを使って指定します。また、エスケープが table: の管理する物理テーブルを参照する場合は、from {Dataset}（P22b）を使用し、物理テーブル名を直接指定しないでください。
