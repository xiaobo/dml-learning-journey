Diese Seite beschreibt die Eigenschaften und Formelvarianten von Kennzahlen. Kennzahlen entwerfen erläutert die Entscheidungen bei der Definition. Formelbeispiele zeigt typische fachliche Anwendungsfälle.

Grundsyntax #

measure_name:
    type: measure
    description: Business description
    dataset: dataset_name
    formula: aggregation_expression
    dimensions:                # optional allowed evaluation dimensions
        - [customer_id]
        - [customer_id, ...]   # listed fields remain required
    prerequisite: validity_expression

formula: ist erforderlich. dataset: bindet eine atomare Kennzahl auf oberster Ebene an ihre Datenquelle. Eine Kennzahl im Block measures: eines Datensatzes übernimmt diesen Datensatz. Zusammengesetzte Kennzahlen verweisen auf andere Kennzahlen und lassen dataset: weg.

dimensions: ist ein Array aus Arrays. Jede innere Liste definiert eine zulässige Alternative für die Dimensionen der Auswertung. Eine flache Liste führt zu string found, array expected. Auslassungspunkte erlauben zusätzliche Felder. Alle aufgeführten Felder bleiben erforderlich. Die Eigenschaft schränkt die Auswertung ein. Sie legt weder die Identität des Datensatzes noch die Gruppierung der Abfrage fest.

prerequisite: ergänzt einen Ausdruck, der prüft, ob die Ebene zulässig ist, auf der Zeilen oder Summen definiert sind. Die allgemeinen Metadatenfelder description, abbr und tags sind unter Metadatenfelder des Modells beschrieben. Wie Sie diese Einschränkungen auswählen, erfahren Sie unter Kennzahlen entwerfen.

Hinweise

  • Wenden Sie abfragespezifische Filter und Gruppierungen in der Modellabfrage an (SQL mit WHERE/GROUP BY oder im DML-Format mit filters: / columns: dimension:). Verwenden Sie dafür keine eigens für eine einzelne Abfrage definierten Kennzahlen. Die Regeln für Modellabfragen finden Sie unter Modellabfrage in SQL.
  • dataset: ist nur für atomare Kennzahlen vorgesehen. Ihre Formeln aggregieren direkt Zeilen oder Spaltenausdrücke des Datensatzes, ohne auf andere Kennzahlen zu verweisen. Zusammengesetzte Kennzahlen verweisen auf andere Kennzahlen und dürfen dataset: nicht deklarieren. Das gilt auch dann, wenn alle referenzierten Kennzahlen denselben Datensatz verwenden. Siehe Kennzahlreferenzen und die häufige Fehlerquelle P39.
  • Kennzahlen können numerische Werte, Datumswerte oder Klassifikationswerte zurückgeben. Formatieren Sie die Werte dort, wo sie angezeigt werden. Wählen Sie Aggregation und Datentyp passend zur fachlichen Definition.
  • Konvertieren Sie Rohfelder mit Geldbeträgen oder besonderen Genauigkeitsanforderungen möglichst einmal in einer atomaren Kennzahl (zum Beispiel SUM(CAST({amount} AS DECIMAL(38, 2)))). Verwenden Sie diese Kennzahl anschließend in weiteren Berechnungen.
  • Wenn fachliche Regeln auf Vergleichen mit > 0 / < 0 beruhen, stellen Sie sicher, dass die Basiskennzahl bereits den vorgesehenen Typ hat (zum Beispiel DECIMAL), bevor Sie sie in Bedingungen für MINIF/MAXIF/DISTINCTCOUNTIF wiederverwenden.

Einfache Aggregationen #

COUNT #

number_of_transactions:
    type: measure
    dataset: transactions
    formula: count(distinct transaction_id)

number_of_products:
    type: measure
    dataset: transactions
    formula: count(distinct product)

SUM #

amount:
    type: measure
    dataset: transactions
    formula: SUM(CAST({raw_amount} AS DECIMAL(38, 2)))

transaction_quantity:
    type: measure
    dataset: transactions
    formula: SUM(quantity)

MAX/MIN #

last_order_date:
    type: measure
    dataset: transactions
    formula: MAX(dt_date)

AVG #

avg_invoice_quantity:
    type: measure
    formula: 'AVG({invoice_quantity: {+d: transaction_id}})'

Gefilterte Kennzahlen #

Verwenden Sie {+f: condition} für Inline-Filter. Die Syntax finden Sie unter Funktionsmodifikatoren.

expense:
    type: measure
    dataset: transactions
    formula: |-
        {debit: {+f: {account_type: ['Expense', 'Other Expense']}}}

sales:
    type: measure
    description: Sales revenue from income accounts
    formula: |-
        {credit: {+f: {account_type: ['Income', 'Other Income']}}}

food_and_drink_expense:
    type: measure
    formula: |-
        {expense: {+f: "instr(account, 'Food & drink') > 0"}}

number_of_credit_card_transactions:
    type: measure
    formula: |-
        {number_of_transactions: {+f: {credit_card : 'yes'}}}

number_of_unpaid_invoices:
    type: measure
    formula: |-
        {number_of_invoices: {+f: 'open_balance > 0'}}

Kennzahlreferenzen #

So verweisen Sie in Formeln auf andere Kennzahlen:

Zusammengesetzte Kennzahlen dürfen dataset: nicht deklarieren. Wenn formula: auf eine andere Kennzahl verweist, lassen Sie dataset: weg. Atomare Kennzahlen binden mit dataset: die Quellzeilen oder Spaltenausdrücke, die sie aggregieren, ohne auf andere Kennzahlen zu verweisen. Die folgenden atomaren Beispiele (credit / debit) enthalten dataset:. Die zusammengesetzte Kennzahl profit lässt diese Eigenschaft weg. Siehe die häufige Fehlerquelle P39.

# Base measures
credit:
    type: measure
    dataset: transactions
    formula: SUM(credit)

debit:
    type: measure
    dataset: transactions
    formula: SUM(debit)

# Derived measure (composite — no dataset:)
profit:
    type: measure
    formula: |-
        {credit: {+f: {transaction_type: ['Income','Other Income','Expense','Other Expense']}}} -
        {debit: {+f: {transaction_type: ['Income','Other Income','Expense','Other Expense']}}}

Aliasse für Kennzahlen #

So erstellen Sie Aliasse für vorhandene Kennzahlen:

revenue: |-
    {sales}

income: |-
    {sales}

outgoing: |-
    {expense}

Komplexe Formeln #

Bedingte Aggregationen #

Kennzahlen mit SUMIF / DISTINCTCOUNTIF / MINIF / MAXIF, die auf andere Kennzahlen verweisen, sind zusammengesetzt. Deklarieren Sie dort kein dataset:, auch wenn eine Spalte in der Formel zu einem bekannten Datensatz „gehört“. Wenn Sie eine spaltenbezogene Aggregation benötigen, verwenden Sie dataset: nur in einer separaten atomaren Kennzahl. Siehe Kennzahlreferenzen und die häufige Fehlerquelle P39.

incoming_payment:
    type: measure
    formula: |-
        SUMIF({payment: {+d: customer}}, {customer} is not null)

outgoing_payment:
    type: measure
    formula: |-
        SUMIF({payment: {+d: vendor}}, {vendor} is not null)

Verschachtelte Aggregationen #

max_amount_per_invoice:
    type: measure
    formula: |-
        MAX({sales: {+d: transaction_id}})

daily_avg_sales:
    type: measure
    formula: |-
        divide(sum({sales: {+d: dt_date}}), distinctcount({dt_date}))

weekly_avg_sales:
    type: measure
    formula: |-
        divide(sum({sales: {+d: dt_week}}), distinctcount({dt_week}))

avg_sales_per_trx:
    type: measure
    formula: |-
        divide(sum({sales: {+d: transaction_id}}), distinctcount({transaction_id}))

Fensterfunktionen #

Platzierung von Fensterfunktionen. Die vollständigen Regeln finden Sie unter Platzierung von Fensterfunktionen. Die folgende Übersicht fasst sie zusammen.

Zweck Platzierung
OVER auf Detailebene (ohne GROUP BY, als Zeilenattribut für spätere Bedingungen mit DISTINCTCOUNTIF oder mit äußerem SUM / LAG) Berechnete Spalte unter columns:, anschließend atomare Aggregation
Rang / Anteil / laufende Summe nach GROUP-BY Als Übergangslösung atomare Aggregation plus zusammengesetzte Kennzahl mit Fensterfunktion / {-d:} / {-df:} / grand (ohne dataset:)

Atomare Kennzahlen lehnen OVER ab (window functions are not allowed in atomic measures). Häufige Fehlerquellen sind unter P70 und P71 beschrieben.

Detailebene (direkte Spaltenreferenzen für die Partitionierung unter columns:):

fact:
    type: dataset
    table: FACT_SALES
    columns:
        store_id:
        prod_id:
        qty:
        net_qty: 'SUM({qty}) over (partition by {store_id}, {prod_id})'
    measures:
        sum_net_qty: 'SUM({net_qty})'

Nach der Aggregation (Verweise auf die Aggregationsebene in der zusammengesetzten Kennzahl):

total_sales:
    type: measure
    dataset: fact
    formula: SUM({qty})

region_rank:
    type: measure
    formula: 'rank() over (partition by {-d: product} order by {total_sales} desc)'

In Modellabfragen mit SQL sollten Sie bevorzugt die Funktionsmakros aus system_macros.dml (rank, rank_asc, pot, grand) verwenden, wenn sie den Anwendungsfall abdecken.

SELECT product, AGG(sales, 'rank') AS sales_rank
FROM MODEL GROUP BY product

SELECT product, AGG({sales: pot}) AS share
FROM MODEL GROUP BY product

Die Kategorien und das Verhalten der Makros sind unter Funktionsmodifikatoren beschrieben.

ISNULL und IIF #

all_product_sales:
    type: measure
    description: Product sales including products with zero sales
    formula: |-
        SUM(isnull({sales: {+d: product}}, 0) * iif({DATASET_PRODUCT_SERVICE}.product is not null, 1, 0))

all_customer_sales:
    type: measure
    description: Customer sales including customers with zero sales
    formula: |-
        SUM(isnull({sales: {+d: customer}}, 0) * iif({DATASET_CUSTOMER}.customer is not null, 1, 0))

Standardwert bei fehlender Zeile einsetzen #

Funktion. Wenn eine Zeile aus einem Join, einem FOJ oder einer Materialisierung fehlt, setzt die Funktion einen Standardwert ein. So wird kein Nullwert in weitere Berechnungen übernommen.

Aktivieren Sie die Funktion, indem Sie die gesamte Kennzahlformel auf der äußersten Ebene mit isnull / ifnull / coalesce(公式, 字面量) umschließen.

Der Standardwert greift an Verwendungsstellen dieser Kennzahl (Abfragespalte, Umbenennung, {m: pp} / andere dt-Modifikatoren oder Einbettung in eine andere Formel), wenn an der jeweiligen Stelle Zeilen fehlen können (FOJ / nullpk / Umschließung bei der Materialisierung).

Beachten Sie den Unterschied zwischen diesen beiden Regeln.

  1. Keine automatische äußere Umschließung. Ein Verweis auf eine Kennzahl mit Standardwert in einer zusammengesetzten Kennzahl umschließt deren Ergebnisspalte allein noch nicht. Aktivieren Sie die Funktion für das Ergebnis selbst, wenn dessen Spalte bei einer fehlenden Zeile einen Wert ungleich NULL liefern muss.
  2. Bei der Einbettung wird die Standardwertlogik weiterhin expandiert. Wenn eine zusammengesetzte Kennzahl eine Abhängigkeit mit bereits aktiviertem Standardwert direkt oder über eine Kette von Formelreferenzen einbettet, wird die Standardwertlogik an FOJ-Verwendungsstellen, an denen Zeilen fehlen können, weiterhin dort expandiert, wo die Einbettung aufgerufen wird. Bei fehlenden Partnerzeilen ergibt zum Beispiel deep = {q2fp1} * 3 mit q2fp1 = {q2f} + 1 und q2f = isnull(SUM(...), 0) den Ausdruck (coalesce(dep, 0) + 1) * 3 statt NULL. Dabei greift der Standardwert der Abhängigkeit. Ein automatisches isnull(deep, …) findet nicht statt.
上期:
    type: measure
    formula: 'isnull({销售额: pp}, 0)'   # activate

上上期:
    type: measure
    formula: '{上期: pp}'                # use site → 0

本期减上期:
    type: measure
    formula: '{销售额} - {上期}'         # 上期 use site → 0 (no contagion)

本期减上期_fill:
    type: measure
    formula: 'isnull({销售额} - {上期}, 0)'  # activate on result

# Nested embed (activation on q2f; deep expands fill of q2f at FOJ)
q2f:   { dataset: secondary, formula: 'isnull(SUM({q2}), 0)' }
q2fp1: { formula: '{q2f} + 1' }
deep:  { formula: '{q2fp1} * 3' }

Keine Aktivierung (der Wert kann weiterhin null sein, wenn die Zeile fehlt):

Form Begründung
{销售额: pp} allein Nicht aktiviert
isnull({a}, {b}) / coalesce(a, b, 0) Ergänzung zur Kennzahl, kein (公式, 字面量)
isnull(…, 0) + 1 als aktivierte Kennzahl selbst Auswertung dieser Kennzahl bei null (häufig → 1). „Zeile fehlt → 0“ gilt für das neutrale Element dieser Kennzahl nicht.
Ergebnisspalte wird nie aktiviert Der Ersatzwert einer abhängigen Kennzahl kann innerhalb der Formel eingesetzt werden. An Stellen, an denen die Ergebnisspalte selbst weiterverwendet wird, wird sie nur dann automatisch mit einer Ersatzwertlogik umschlossen, wenn sie aktiviert ist.

Dasselbe Prinzip wie bei fill_nulls_with in MetricFlow oder COALESCE nach der Aggregation in Looker: Der Ersatzwert wird an einer Kennzahl deklariert und beim Verwenden dieser Kennzahl eingesetzt. DML erzeugt keine fehlenden Kalenderzeilen. Der Ersatzwert wird nur eingesetzt, wenn die Spalte nach dem Join null ist. Ergänzen Sie fehlende Datumswerte separat über einen Kalender oder auf der mit FOJ definierten Zeilenebene. Eine mögliche Fehlerquelle beschreibt der Index zur Fehlerbehebung unter P28b. Hinweise zum Compiler (dmlc): docs/fill-default-when-row-missing.md.

Wiederverwendbare Kennzahlen mit fortlaufender Kumulierung in zeitlicher Reihenfolge #

Eine benannte zusammengesetzte Kennzahl kann eine Fensterfunktion enthalten, die nach der Aggregation ausgewertet wird. Das Beispiel zum kumulierten Umsatz definiert SUM({sales}) OVER (ORDER BY {month} ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) auf der deklarierten Ebene [month]. Die Berechnung wird nicht nach Regionen partitioniert. Ein Filter auf Februar verschiebt den Startpunkt der Berechnung. Die laufende Summe additiver Beträge ist weder eine kumulierte Anzahl unterschiedlicher Werte noch ein kumuliertes Verhältnis. Das Beispiel enthält das vollständige Modell, die Abfragen und die erwarteten Ergebniszeilen. dimension: [] hebt für die Berechnung einer Gesamtsumme die Gruppierung auf. Es legt keine Reihenfolge fest und fordert keine kumulative Berechnung an. Legen Sie für den Saldo zum letzten Beobachtungszeitpunkt fest, ob das Datum je Entität oder global bestimmt wird und wie fehlende Beobachtungen und Gleichstände beim Datum behandelt werden. Eine Summe mit festgelegter Reihenfolge oder ein einzelnes Verfahren für den letzten Beobachtungstag deckt nicht alle semiadditiven Berechnungen ab.
