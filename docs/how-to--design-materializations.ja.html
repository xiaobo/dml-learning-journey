マテリアライズの粒度を選ぶ

このページの内容
  • クエリ性能と materialize の設計原則

繰り返し実行するクエリで、一定の粒度で保存された集計結果を再利用できる場合は、マテリアライズを使用します。宣言の構文と適用条件は、マテリアライズのリファレンスに記載されています。

クエリ性能と materialize の設計原則 #

クエリ性能を改善するためのチェックリスト：

  • 日付列が dt_date/dt_week/dt_month/dt_quarter/dt_year の規約（期間の初日）に従っていることを確認します。
  • 個別用途の指標を多数作るよりも、再利用できる少数の指標（例：sales、qty）を使います。
  • Model Query の SQL はシンプルに保ちます。FROM MODEL を指定し、クエリのディメンションフィールドと AGG(measure) を選択してから、GROUP BY でグループ化します。
  • 繰り返し集計することでクエリが遅くなる場合は、適切な粒度で materialize を追加します。

materialize を使用する条件：クエリが同じ基礎データを一定の粒度（例：商品別・店舗別・カテゴリ別の月次集計）で繰り返し集計し、かつデータが追記専用であるか、期間単位で更新できる場合に使用します。データ量がごく少ない場合、粒度をクエリごとに決める場合、またはモデルのセマンティクスをまだ検討している場合は、使用を避けます。

粒度の設計原則：

  1. 粒度は、行や集計値を定義する単位です。後続の処理で上位レベルに集計できる細かさを保ちつつ、行数が急増するほど細かくしないようにします。一般的な例は、DWD（日単位とキー）、DWS（月または四半期単位と分析ディメンション）、ADS（レポートでそのまま使える粒度）です。
  2. 後続の上位集計に備え、売上高や数量など、加算できる指標を保存します。グループ間で顧客の重複がない場合を除き、グループごとのユニーク顧客数を合算しないでください。エンティティキーを保持するか、目的の上位集計に使えるサポート対象の表現形式があることを確認します。
  3. 行を一意に識別するフィールドは dimension: に指定します。category_id から導出される category_name など、関数従属する属性は dimension_columns: に指定します。マテリアライズの宣言ルールを参照してください。
DWS_SALES_DATE_CATEGORY:
    type: materialize
    parameters:
        dt_date: date
    dimension:
        - dt_date
        - category_id
        - cust_id
    measures:
        - 销售额
        - 销售量

materialize は、モデリング時の最適化のための概念です。データセットを DuckDB に物理テーブルとして永続化することは、別の操作です。具体的な使い方は、マテリアライズの例も参照してください。

設定、クエリがマテリアライズを利用したかどうかの確認、更新、結果の確認は、マテリアライズのワークフローに従って行います。
