Einen expliziten Stichtag für eine kumulative KPI festlegen

Inhalt dieser Seite
  • Zwei Berechnungszeiträume in einem Ergebnis vergleichen
  • Das Verhalten bei fehlendem Zeitkontext prüfen
  • Die Gruppierung kann auch Monate ohne Verkäufe enthalten
  • Prüfung ausführen und Ergebnis lesen

Eine kumulative Kennzahl benötigt einen Zeitkontext. Ein Datumsfilter schränkt auch die übrigen, nicht kumulativen Kennzahlen derselben Abfrage ein. DML wählt weder das heutige Datum noch das jüngste Datum in den Faktendaten automatisch aus.

Zwei Berechnungszeiträume in einem Ergebnis vergleichen #

Im Januar beträgt der Umsatz 10 und der Gewinn 3. Im Februar beträgt der Umsatz 20 und der Gewinn 3. In der Februarabfrage beträgt die Marge für YTD genau (3+3)/(10+20)=20%. Der nicht kumulierte Umsatz beträgt 20; der kumulierte Umsatz von 30 wird dafür nicht ausgegeben.

Vollständige Datei: ytd/model.dml 
dialect: duckdb
F:
  type: dataset
  table: YTD_FACT
  dimension: [id]
  columns:
    id:
    dt_month:
    revenue_amount:
    profit_amount:
  measures:
    revenue: SUM({revenue_amount})
    profit: SUM({profit_amount})
margin:
  type: measure
  formula: 'DIVIDE({profit} * 1.0, {revenue})'
margin_ytd:
  type: measure
  formula: '{margin: ytd}'
Vollständige Datei: ytd/setup.sql 
CREATE TABLE YTD_FACT(id INTEGER, dt_month DATE,revenue_amount INTEGER,profit_amount INTEGER); INSERT INTO YTD_FACT VALUES (1,'2024-01-01',10,3),(2,'2024-02-01',20,3);
Vollständige Datei: ytd/february.sql 
SELECT AGG(margin_ytd), AGG(revenue) FROM MODEL WHERE dt_month='2024-02-01'

Das Modell definiert margin_ytd als '{margin: ytd}'. Zähler und Nenner werden jeweils über den gesamten kumulierten Zeitraum berechnet, bevor sie dividiert werden. Der Durchschnitt aus 30% und 15% beantwortet eine andere Frage.

Das Verhalten bei fehlendem Zeitkontext prüfen #

Vollständige Datei: ytd/missing_context.sql 
SELECT AGG(margin_ytd) FROM MODEL

Diese Abfrage lässt sich nicht kompilieren. Die Fehlermeldung weist darauf hin, dass dim_dt fehlt. Mit dem Filter für Februar liefert die Abfrage 20%. Der Filter ist kein unabhängiger Stichtagsparameter. Er beschränkt auch den nicht kumulierten Umsatz in derselben Abfrage auf Februar. Wenn ein Bericht Kennzahlen für unterschiedliche Zeiträume benötigt, legen Sie den Zeitraum für jede Kennzahl fest und prüfen Sie ihn.

Die Gruppierung kann auch Monate ohne Verkäufe enthalten #

Vollständige Datei: ytd/months.sql 
SELECT dt_month, AGG(margin_ytd), AGG(revenue) FROM MODEL GROUP BY dt_month ORDER BY dt_month

Dieses Testbeispiel liefert zwölf Monate. Im Januar beträgt die kumulierte Marge 30% und der Umsatz 10. Im Februar beträgt die kumulierte Marge 20% und der Umsatz 20. Von März bis Dezember beträgt die kumulierte Marge jeweils 20% und der nicht kumulierte Umsatz jeweils NULL. Der Abfragezweig für die kumulative Berechnung verwendet Monate, die aus dem Kalender erzeugt werden. Diese Zeilen stehen für keine neuen Transaktionen. NULL bedeutet nicht, dass der Wert 0 gemessen wurde.

Wenn der Bericht genau einen Monat als Ende des kumulierten Zeitraums benötigt, setzen Sie dafür einen expliziten Filter. Prüfen Sie nach einer Änderung des Zeitraums sowohl die ausgegebenen Monate als auch den Zeitraum der Eingangsdaten für jede Kennzahl.

Prüfung ausführen und Ergebnis lesen #

Laden Sie das vollständige Projekt herunter und führen Sie verify.ps1 wie in der Datei README beschrieben in PowerShell aus. dmlc muss über den Suchpfad erreichbar sein. Das Skript legt die Übungsdatenbank im neuen Ausgabeordner an und speichert dort die Ergebnisse und Diagnosemeldungen.

Dieses Beispiel wurde auf DuckDB mit dmlc 0.3.16 (Build 2026-11-13) geprüft. Den Fingerabdruck der ausführbaren Datei und den Status der einzelnen Prüffälle finden Sie in der Datei verification-summary.json im Download. Die Datenbankvalidierung und die anschließende Ausführung sind voneinander unabhängige Vorgänge. Es ist daher nicht gewährleistet, dass beide denselben Datenbank-Snapshot verwenden. Prüfen Sie das Beispiel für andere Datenbank-Engines separat.
