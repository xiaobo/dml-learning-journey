Diese Seite beschreibt type: query, Spalten, Filter, die Auswahl der Materialisierung und after:. Die Abfrage verwendet dieselben Modellkennzahlen wie die Modellabfrage in SQL.

Vorgabe für Dateinamen: Beim Kompilieren einer .dml-Datei mit dmlc -c muss der Name des type: query-Blocks mit dem Dateinamen ohne die Endung .dml übereinstimmen. Die Datei my_report.dml muss zum Beispiel my_report: type: query statt some_other_name: type: query enthalten. Bei abweichenden Namen bricht der Compiler mit folgender Meldung ab: query name should be <filename> (the same as filename) instead of <block_name>.

Grundstruktur #

my_report:
    type: query
    allows: ALL              # optional: consider compatible materializations

    columns:
        dimension:
            - dt_month
            - product
        sales:               # measure reference (no AGG needed)
        sales_yoy:
            formula: '{sales: yoy}'

columns: ist erforderlich. Die Schlüssel, die keine Dimension angeben, benennen die Ausgabespalten. Ihre Werte sind Formeln oder direkte Kennzahlreferenzen. Der optionale Schlüssel dataset: wählt die Dataset-Abfrageform und kann nicht mit columns.dimension kombiniert werden.

Abfragefilter haben die folgenden Formen. Jeder Schlüssel benennt einen Filter, den Modifikatoren in Kennzahlreferenzen ansprechen können.

Form des Werts Bedeutung
<column>: <value> Gleichheitsprüfung für die gleichnamige Spalte
<column>: [a, b] Prüfung, ob der Wert in der Liste enthalten ist
<name>: {column: <column>, value: <value>} Benannter Gleichheitsfilter für eine explizit angegebene Spalte
<name>: {column: <column>, range: [lo, hi]} Benannter Bereichsfilter für eine explizit angegebene Spalte, einschließlich beider Grenzen
<name>: {visibility: hidden, default: on} Ausgeblendeter Filter mit aktiviertem Standardwert

Die Regeln zur Filterplatzierung legen fest, welcher Verarbeitungsstufe die einzelnen Prädikate zugeordnet werden.

Detail und Aggregation #

Modus Angabe Einschränkungen
Aggregation Kein Schlüssel dataset: Kennzahlen sind zulässig. Der Compiler aggregiert sie.
Detail dataset: DATASET_NAME Keine Kennzahlen. Nur unverarbeitete Spalten sind zulässig. 
# Detail query
product_list:
    type: query
    dataset: DATASET_PRODUCTS
    columns:
        dimension:
            - product

Automatische Joins für Kennzahlen aus mehreren Datasets #

Wenn eine Aggregatabfrage Kennzahlen aus verschiedenen Datasets referenziert, werden diese nach den Regeln eines FULL OUTER JOIN über die gemeinsamen Dimensionsfelder zusammengeführt. Zeilen, die nur in einem Dataset vorkommen, erscheinen ebenfalls. Die Kennzahlen des jeweils anderen Datasets haben den Wert NULL.

Der generierte Join-Typ richtet sich danach, welche Zeilen nachweislich im Ergebnis bleiben müssen. Der Compiler geht von FULL OUTER JOIN aus und verwendet für jeden Join den restriktivsten Typ, der sich aus den Abfragefiltern ableiten lässt. "{primary_measure} is not null": unter filters: entfernt Zeilen, die nur auf der Sekundärseite vorkommen, und ändert den generierten Join-Typ zu LEFT JOIN. Wenn Filterbedingungen auf beiden Seiten einen vorhandenen Wert verlangen, ergibt sich INNER JOIN. Die Bedingung liefert nur dann dasselbe Ergebnis wie ein LEFT JOIN in der SQL-Referenzabfrage, wenn die primäre Kennzahl in gültigen Primärgruppen nie NULL sein kann. Weisen Sie diese Annahme für NULL und leere Gruppen nach und prüfen Sie die generierten Join-Typen und die Ausgabe. Andernfalls entfernt der Filter auch gültige Gruppen. Platzieren Sie die Bedingung außerhalb von after:, damit sie bei der Analyse der Datenherkunft, bei der Prüfung und bei der Wiederverwendung sichtbar bleibt.

Der Ausdruck muss als Schlüssel angegeben werden: "{expr}": mit leerem Wert. name: {condition: …} entspricht nicht dem Schema.

Spaltenreferenzen im DML-Format #

Spaltentyp Syntax Beispiel
Dimensionsfeld aus demselben Dataset Nur der Name product:
Dimensionsfeld aus einem anderen Dataset "{DATASET}.column" prod_id: "{DATASET_PRODUCTS}.prod_id"
Kennzahl Nur der Name sales:
Kennzahl mit Modifikator formula: sales_yoy: {sales: yoy}

Achtung: In einer Aggregatabfrage ohne dataset: führt ein unqualifizierter Spaltenname zu einem Fehler, wenn die Spalte zu einem bestimmten Dataset gehört. Verwenden Sie die Form "{DATASET}.column".

Automatische Aliaszuordnung und direkte Referenz #

Eine Abfragespalte ohne Formel kann anhand ihres Namens einer gleichnamigen Kennzahl oder Dataset-Spalte zugeordnet werden. Dies heißt automatische Aliaszuordnung. Es gibt drei Ebenen:

Ebene Mechanismus Beispiel Ergebnis
column (direkte Referenz) Eintrag ohne Formel unter columns: im Dataset. Der DML-Name entspricht dem Namen der Tabellenspalte. prod_amount: SUM(prod_amount) — der Name wird unverändert und ohne Alias übernommen
Abfragespalte → Kennzahl (automatische Aliaszuordnung) Abfragespalte ohne Formel. Der Spaltenname entspricht dem Namen der Kennzahl. revenue: (die Kennzahl revenue ist vorhanden) Der Compiler setzt den Ausdruck aus formula: der Kennzahl ein.
Abfragespalte → Dataset-Spalte (automatische Aliaszuordnung) Abfragespalte ohne Formel. Der Spaltenname entspricht dem Namen der Dataset-Spalte. Die Dataset-Spalte muss aus der Abfragedimension ableitbar sein. prod_name: (Dataset-Spalte über die Kette pk({prod_id})) Der Compiler löst die Spalte anhand der Dataset-Definition auf.

Verhalten im Detail:

  • dmlc -c prüft nicht anhand des Tabellenschemas, ob Dataset-Spalten vorhanden sind. Die Kompilierung gelingt auch bei einem abweichenden Namen, bei der Ausführung treten jedoch SQL-Fehler auf. Verwenden Sie validateOnly, um abweichende Namen zu erkennen. Dazu ist eine Datenbankverbindung erforderlich.
  • Wenn der Name einer Abfragespalte weder mit einer Kennzahl noch mit einer ableitbaren Dataset-Spalte übereinstimmt, wird der Fehler not defined, add formula? ausgegeben.
  • Wenn sich der Name der Abfragespalte vom Namen der Kennzahl unterscheidet, geben Sie eine explizite Formel an (display_name: '{measure_name}') oder benennen Sie die Kennzahl mit abbr: um.
  • Eine Dataset-Spalte, die sich nicht aus der Abfragedimension ableiten lässt, führt zum Fehler cannot be derived from dimension [store_id]. Dies betrifft beispielsweise eine unverarbeitete Faktenspalte ohne Abhängigkeit von einem Dimensionsfeld.
  • Eine unverändert übernommene Spalte (ohne formula:) kann in Objektform die Metadateneigenschaften description: und visibility: enthalten, ohne dass formula: erforderlich ist. Beispiel: revenue: { description: 'Total revenue' } ordnet die Spalte automatisch der Kennzahl revenue zu und fügt die Beschreibung hinzu.

visibility: hidden #

Blendet eine Spalte in der endgültigen Abfrageausgabe aus. In temporären Zwischentabellen bleibt sie verfügbar.

Aspekt Verhalten
Abschließendes SELECT Ausgeblendete Spalten fehlen normalerweise in der Ausgabe. Wenn ein Filter oder eine HAVING-Klausel eine ausgeblendete Spalte referenziert, kann sie in die endgültige Ausgabe übernommen werden. Prüfen Sie das generierte SQL, bevor Sie angeben, welche Spalten die Ausgabe genau enthält.
Temporäre Zwischentabellen Ausgeblendete Spalten bleiben für JOIN-Bedingungen und filters: verfügbar
filters: mit Referenzen auf ausgeblendete Dimensionsfelder Die Kompilierung gelingt, kann aber zu restriktiveren Join-Typen bei optionalen Joins führen und die Materialisierung von Hilfsergebnissen erzwingen. Prüfen Sie das generierte SQL.
SQL unter after: mit namentlichen Referenzen auf ausgeblendete Dimensionsfelder Schlägt fehl — query columns refer to nonexistence source column
PK-Kette Bleibt intakt — visibility: hidden allein löst keine PK-Warnung aus

Hinweis: Entfernen Sie visibility: hidden, wenn after: das Dimensionsfeld namentlich referenziert. Behalten Sie die Einstellung bei, wenn after: ausschließlich Kennzahlenspalten verwendet. Kompilieren Sie bei Ausgaben mit einem Ausgabevertrag die Abfrage und prüfen Sie, dass keine ausgeblendete Hilfsspalte im Endergebnis erscheint. Zusätzliche Spalten sind nur zulässig, wenn der Ausgabevertrag sie ausdrücklich erlaubt.

Gültige YAML-Schreibweisen: - dim: {visibility: hidden} oder eine verschachtelte Map, deren Schlüssel unter dem dim-Eintrag stehen. Steht visibility: auf derselben Einrückungsebene wie der dim-Schlüssel, meldet die Schemaprüfung einen Fehler wegen zu geringer Einrückung. Verwenden Sie die Inline-Form oder die verschachtelte Form. Prüfen Sie bei alleiniger Verwendung von dmlc -c immer das kompilierte SELECT (die Schemaprüfung läuft im Editor oder mit dmlc --lint).

Format für Abfragedimensionen #

columns:
    dimension:
        - dt_month
        - product
        # Correct: list dimension field names only

Falsch: Nehmen Sie datensatzübergreifende Spaltenzuordnungen nicht in die Dimensionsfelder der Abfrage auf. Definieren Sie diese Formeln als separate Abfragespalten:

# Wrong
columns:
    dimension:
        - f_tag_id: {DATASET_PT}.id

# Correct
columns:
    dimension:
        - f_tag_id
    f_tag_id: "{DATASET_PT}.id"

Ausnahme – Kennzahl als Dimension: Ein Eintrag für eine Abfragedimension kann eine Kennzahl binden (in der Regel mit +d). Die Abfrage gruppiert die Zeilen dann nach dem Wert dieser Kennzahl:

columns:
    dimension:
        - first_purchase_month: '{first_purchase_month: {+d: store_id}}'
    sales:

Deklarieren Sie den Schlüssel der Klassifizierungsentität explizit mit +d (bevorzugt) oder dimension:. Mehrere unabhängige Felder sind zulässig, wenn ihre vollständigen Schlüssel übereinstimmen. Reguläre Ausgabekennzahlen müssen sich ausgehend von Q ∪ K korrekt auf einer gröberen Ebene aggregieren lassen. Filter auf dem Label (filters: in der Formel oder HAVING in einer Model Query) greifen erst dann, wenn das Label vorliegt. Siehe Kennzahl als Dimension. Verwenden Sie diese Ausnahme nicht für physische Zuordnungen oder {DATASET}.col-Zuordnungen.

Ebenen für die Platzierung von Filtern #

Wo Sie einen Filter platzieren, hat semantische Auswirkungen und ist keine Frage des Syntaxstils:

Ebene Ort Was hier angegeben wird
filters: der Abfrage Abfrageblock Berichtsspezifische Datenausschnitte (Kanal, Marke, Datumsbereich)
Zwischenspalte oder Zwischenkennzahl .dml-Datensatz oder Kennzahl auf oberster Ebene Kennzahlspezifische Auswahlkriterien, wenn ausgeschlossene Zeilen in Gruppen mit NULL-Kennzahlwerten verbleiben dürfen
sql: im Dataset Dataset-Definition Dauerhafte Invarianten für die Menge der Quellzeilen oder Konstrukte, die sich in DML nicht deklarativ ausdrücken lassen

Wenn Sie eine WHERE-Bedingung auf Quelldaten als Auswahlbedingung für die Eingabe einer Kennzahl formulieren, ändert sich, welche Ergebniszeilen vorhanden sind. Ausgenommen sind Fälle, in denen Gruppen, die ausschließlich ausgeschlossene Zeilen enthalten, unmöglich sind oder laut Vertrag mit vorhandenen Gruppen mit NULL-Kennzahlwerten gleichwertig sind. Weisen Sie ausdrücklich nach, dass diese Ausnahme greift. Wenn sie nicht greift oder unklar ist, ob sie greift, behalten Sie eine Formulierung bei, die Zeilen entfernt.

Semantik strukturierter Bereiche: range: [start, end] in filters: der Abfrage schließt auf der mit dt_<grain> deklarierten Ebene beide Grenzwerte ein. Verwenden Sie für Tagesdaten aus 2025 den Bereich ['2025-01-01', '2025-12-31'] und für Monatsdaten den Bereich ['2025-01-01', '2025-12-01']. Ein SQL-Dialekt kann den Bereich mit einer exklusiven physischen Obergrenze wie < dateadd(day, 1, end) umsetzen. Der als Ende eingegebene DML-Wert bleibt der letzte eingeschlossene Wert.

Liste oder Bereich – ein häufiger Fehler: Ein einfacher Listenwert dim: ['a', 'b'] wird zu WHERE dim IN ('a', 'b') kompiliert (exakte Übereinstimmung mit einem der beiden Werte), nicht zu einem Bereich mit eingeschlossenen Grenzwerten. Bei Datumsdimensionen kann das unbemerkt Daten auslassen. dt_date: ['2024-01-01', '2025-12-31'] liefert nur Zeilen für diese beiden Tage und deckt nicht den gesamten Zeitraum von 2 Jahren ab. Verwenden Sie für Intervalle mit eingeschlossenen Grenzwerten immer range: [start, end]:

# Wrong — only 2 days of data
filters:
    dt_date: ['2024-01-01', '2025-12-31']

# Right — full inclusive range
filters:
    dt_date:
        range: ['2024-01-01', '2025-12-31']

Häufige Fehler bei Filtern:

Symptom Lösung
[dataset …] [filters]: not supported In filters: der Abfrage, in die Kennzahlenformel oder in die WHERE-Klausel unter sql: verschieben
referred column {DATASET}.col is undefined im Abfragefilter Zeichenfolgenform verwenden: "{DATASET}.col = value":
Eine Liste mit zwei Elementen für eine Datumsdimension liefert nur Daten für 2 Tage Verwenden Sie range: [start, end] anstelle einer einfachen Liste. dim: [a, b] wird zu IN (a, b) kompiliert, nicht zu BETWEEN.
Komplexe EXISTS-/PK-Kette in filters: der Abfrage Filtern Sie die Eingabe einer Kennzahl nur anhand kennzahlspezifischer Auswahlkriterien. Wenn die Bedingung Quellzeilen auswählt, lassen Sie sie auf der Verarbeitungsstufe für Quellzeilen. Wird sie in eine Kennzahl verschoben, kann sich die Grundgesamtheit des Berichts ändern. Prüfen Sie die erzeugten Prädikate und Joins.

Verkettung mit pk #

# Single PK lookup
formula: 'pk(customer_id).{DATASET_CUSTOMERS}.tier'

# Composite PK — all columns required
formula: 'pk(brand_id, tag_id).{DATASET_PRODUCTS}.state'

Regel für die Schlüsselanzahl: Die Anzahl der Schlüssel in pk(...) muss der Anzahl der Dimensionsfelder unter dimension: im Zieldatensatz entsprechen. Andernfalls erscheint expect N expr(s) to query dataset X using pk, but got M (siehe Index zur Fehlerbehebung, P65).

Verschachtelte Ketten: Eine aus einer pk()-Kette abgeleitete Spalte kann als Schlüssel in einer anderen pk()-Kette dienen. Der Compiler verfolgt die Ableitungskette und erzeugt die entsprechenden verschachtelten LEFT JOIN-Verknüpfungen. So können Sie direkt modellieren, dass ein Attribut nachgeschlagen und anschließend zum Nachschlagen eines weiteren Attributs verwendet wird, ohne sql: oder after: zu verwenden.

# fact dataset
columns:
    store_id:
    # First hop: store_id → Dim Customer → hq_id
    hq_id: pk({store_id}).{Dim Customer}.hq_id
    # Second hop: hq_id (itself a pk chain result) → Dim Customer → store_code
    hq_code: pk({hq_id}).{Dim Customer}.store_code
    # Third hop: hq_id → Dim Customer → org_id, then org_id → Dim Org → emp_name
    hq_org_id: pk({hq_id}).{Dim Customer}.org_id
    hq_emp_name: pk({hq_org_id}).{Dim Org}.emp_name

Im geprüften Build werden Vorwärtsreferenzen innerhalb derselben Datei unterstützt, auch für Spaltenabhängigkeiten und pk()-Ziele. Führen Sie Abhängigkeiten zur besseren Lesbarkeit zuerst auf. Für eingebundene Dateien gelten eigene Sichtbarkeitsgrenzen. Siehe Modellkomposition.

after:-Klausel #

after: ist optional. Ohne diese Klausel sortiert der Compiler aufsteigend nach den sichtbaren Ausgabespalten, die er den Dimensionsfeldern der Abfrage zuordnet. Dabei folgt er der aufgelösten Reihenfolge der Dimensionsfelder. Bei einem ausgeblendeten Dimensionsfeld kann für die Sortierung daher der Alias einer sichtbaren Abfragespalte anstelle des in der Definition angegebenen Feldnamens verwendet werden. Wenn in der Ausgabe keine Dimension wirksam ist, ist keine Zeilenreihenfolge garantiert. Fehlt die Sortierangabe für NULL, gilt der Standard des Zieldialekts.

Sobald ein after:-Block vorhanden ist, bestimmt er die Reihenfolge des Endergebnisses. Insbesondere hebt select * from {QUERY} ohne eigenes ORDER BY die Standardsortierung des Compilers auf. Verwenden Sie after: nur, wenn eine fachlich relevante Sortiervorgabe vom Standard abweicht: die Sortierrichtung, die Position von NULL, ein Kriterium bei gleichen Sortierwerten, die Sortierung nach einer Kennzahl oder einem Ausdruck oder die Verwendung von TOP oder LIMIT. Aggregieren Sie nicht erneut:

my_report:
    type: query
    columns:
        dimension: [product]
        sales:
    after: 'select * from {QUERY} ORDER BY sales DESC LIMIT 10'

Wenn after: vorhanden ist, ist {QUERY} erforderlich. Damit wird das Ergebnis der kompilierten Abfrage bezeichnet, das die nachgelagerte Anweisung verwendet. „Nur Sortierung“ bedeutet, dass der Block außer dieser Klammerung und ORDER BY/TOP/LIMIT keine fachliche Logik enthält. Der vorgelagerte Compiler gibt die Warnung redundant ORDER BY aus, wenn die angegebene Sortierung der Standardreihenfolge der Abfrageausgabe entspricht. Beachten Sie den Hinweis zur jeweiligen Stelle. Entfernen Sie nur die redundante ORDER BY-Klausel, wenn unter after: noch andere wichtige Verarbeitungsschritte stehen. Entfernen Sie den gesamten Block nur, wenn keine weiteren Verarbeitungsschritte übrig bleiben.

Falsch: Bei einer Standardabfrage für Kennzahlen unter after: mit group by erneut aggregieren. Lassen Sie die Kennzahlen im Abfrageblock aggregieren.

allows: ALL #

Damit der Compiler alle kompatiblen Materialisierungen berücksichtigen kann:

my_report:
    type: query
    allows: ALL
    columns:
        dimension:
            - dt_date
        sales:

allows: legt fest, welche Materialisierungen infrage kommen. ALL lässt Kandidaten zu, NONE deaktiviert die Verwendung von Materialisierungen. Explizit angegebene Namen schränken die Auswahl ein. Ob eine Materialisierung infrage kommt, hängt weiterhin davon ab, ob die Ebene, auf der Zeilen oder Summen definiert sind, und die Filter kompatibel sind. Die Einstellung lockert weder die Vorgaben unter dimensions: für Kennzahlen noch erlaubt sie eine beliebige Granularität der Abfrage. Siehe Materialisierungsdeklarationen.

Häufige Fehler in der YAML-Syntax #

  • Setzen Sie Formeln in Anführungszeichen, wenn sie :, { oder - enthalten: formula: 'SUMIF(...)'
  • Dimensionsfeld unter measures:: Falsch. Deklarieren Sie es ausschließlich unter dimension:.
  • dataset: bei zusammengesetzten Kennzahlen: Falsch. Lassen Sie dataset: weg, wenn die Formel auf andere Kennzahlen verweist.
  • Unterschiedliche Namen für ein Dimensionsfeld in verschiedenen Datensätzen: Verwenden Sie einen einheitlichen Namen (z. B. tag_id) und hinterlegen Sie die Zuordnung unter columns:.

Kurzreferenz für YAML-Abfragen #

Definieren Sie die Abfrage mit type: query. Geben Sie mit dimension: die Gruppierung des Ergebnisses und mit columns: die Ausgabe an. Wo eine Filterbedingung steht, bestimmt, ob sie auf Quellzeilen, eine einzelne Kennzahl oder das aggregierte Ergebnis angewendet wird. Prüfen Sie beim Kombinieren von Datensätzen zuerst die Verknüpfungsschlüssel, Schlüssel mit dem Wert NULL und Gruppen, die nur auf einer Seite vorkommen. Verwenden Sie after: für Abfrageoperationen wie die abschließende Sortierung.
