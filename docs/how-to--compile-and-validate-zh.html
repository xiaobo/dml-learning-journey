本指南覆盖：编译 Model Query、查看诊断与生成 SQL、校验源键、比较结果。可用旗标以你安装的可执行文件的 --help 与 --advanced-help 为准。

1. 确认可执行文件与模型 #

与文档记录的构建比对行为之前，先记录可执行文件路径、版本、构建时间和 SHA-256。

$dmlc = (Get-Command dmlc.exe).Source
& $dmlc --version
Get-FileHash -LiteralPath $dmlc -Algorithm SHA256
& $dmlc --advanced-help

安装 dmlc.exe 并将其目录加入 PATH。以下命令都在模型与查询所在目录运行。

模型文件名要与 SQL 的 FROM 名一致：model.dml 对应 FROM MODEL，acme.dml 对应 FROM acme。用 --model=model.dml 指定文件，或传所在目录按文件名发现。参见查询发现规则。

2. Lint 与严格编译 #

先 lint 模型，再严格编译消费查询。

& $dmlc --lint model.dml --json
& $dmlc --compile --strict query.sql --model=model.dml --json --artifacts=gen

每条命令后检查进程退出码，阅读 JSON 里的 status、diagnostics、notes、生成 SQL 与输出顺序，并按查询契约核对生成的分组、关联、谓词、别名和输出列。

严格编译返回 findings 时，保留警告与生成 SQL；先厘清目标数据范围与 NULL 行为，再改查询。去掉 --strict 不会让严格检查变成通过。

--artifacts 把编译产物存到目录；--output 把命令结果存到文件，两者不可混用。

3. 捕获 JSON 且不改变编码 #

用 --output 保存查询结果；加 --with-validation 在目标连接上先校验模型数据集键，通过后才执行。

& $dmlc --query query.sql --model=model.dml --connection=default --with-validation --output=result.json --replace

采集 lint / compile 证据时，stdout 与 stderr 分开捕获。用 Node.js 参数数组可避免 shell 引号问题并获得明确的 UTF-8 解码。把脚本存为模型与查询旁边的 compile.cjs。

const fs = require('node:fs');
const { spawnSync } = require('node:child_process');
const result = spawnSync(process.argv[2], [
	'--compile', '--strict', 'query.sql', '--model=model.dml',
	'--json', '--artifacts=gen'
], { encoding: 'utf8', cwd: __dirname });
if (result.error) throw result.error;
fs.writeFileSync('compile.stdout.json', result.stdout);
fs.writeFileSync('compile.stderr.txt', result.stderr);
const report = JSON.parse(result.stdout);
console.log(JSON.stringify({ processExit: result.status, report }, null, 2));
process.exitCode = result.status ?? 1;

用选定的可执行文件运行：

node compile.cjs $dmlc

JSON 解析失败时，保留原始输出流与进程退出码，先诊断该失败，不要把它当作语言错误。

Windows PowerShell 5.1 不支持 &&，请逐条运行命令；不要把 stderr 并入 JSON stdout。交互下需要屏蔽 stderr 时用 2>$null。

4. 校验源键与数据库可执行性 #

需要报告时用 --validate；当前证据缺失或过期、且需要结果时，用带校验的查询执行。

& $dmlc --validate query.sql --model=model.dml --connection=default --json

把 default 换成目标连接。检查退出码、校验结论、被检查的数据集与报告的问题；CLI JSON 报告把校验细节放在 data 下。

校验检查查询用到的每个数据集声明键是否最多标识一行源数据，并用 EXPLAIN 检查数据库能否规划该查询。业务合计要用独立 SQL 结果核对。

例如两笔不同的台账记录共享 (account, invoice, party) 键，金额分别为 10 和 20。若把该组合声明为数据集 dimension:，校验会报告该键及匹配的两行；用 --with-validation 时查询在执行前停止。应把台账记录 ID 声明为数据集键，再按 account、invoice、party 分组得到合计 30。若两行属于意外重复，修复源数据或产生它的关联。

模型、查询契约、连接或相关源数据变化后要重新校验。前置条件缺失时，把该项记录为 not run 并写明缺什么。

5. 执行并比较结果 #

当前校验证据缺失或过期时，在目标连接上带 --with-validation 运行查询。

& $dmlc --query query.sql --model=model.dml --connection=default --with-validation --json

校验通过后查询和导出才会执行。校验失败或未完成时，先阅读报告、解决问题再重跑。校验与执行是两次独立读取，其间源数据可能并发变化。

核对键、行重数、NULL 和全部度量。若存在独立结果，在同一源快照与口径下比较两条查询。

DuckDB 缓存被锁时，先找到持有它的进程与连接；仅当另一连接确实代表目标源时才可换用。不要为绕开锁而修改源数据。

具体失败场景见排错索引与错误码。

检查整个模型，不先写查询 #

运行 dmlc --validate path/to/model.dml --connection=default。需要结构化报告时加 --json，也可用 shell 重定向保存报告。

这会加载所选文件及其 includes，检查模型编译，并在线检查各数据集声明的完整 dimension 键或半开区间约束。冲突报告沿用原列名和少量示例。报告中的 checkedDatasets 是实际检查范围；没有声明维度的数据集不会自动产生键约束。它不会构造或执行一条业务查询，不执行物化准备/安装脚本，也不能据此保证任意指标查询都能在数据库执行。要检查特定查询的数据库规划，另行提供该查询。

练习发现并修复键声明问题 #

运行复合键和有效期查找案例，依次观察正常通过、重复键或区间重叠报错、修复后重新通过。再执行查询并核对结果。
