Filter auf der falschen Ebene #

Symptome: [filters]: not supported, cannot derive from dimension, referred column … is undefined

Ursache: Nach --to-dml stehen Prädikate noch auf der falschen Ebene. Typische Fälle sind filters: an einem Dataset (das Schema lässt filters: an Datasets grundsätzlich nicht zu), eine in sql: der Faktenquelle wiederholte Einschränkung der Dimension oder die Kurzform für Abfragefilter bei datasetübergreifenden Attributen.

Lösung: Ordnen Sie jedes Prädikat nach seinem semantischen Geltungsbereich ein (Hierarchie der Filterplatzierung):

Symptom Zielort
[dataset …] [filters]: not supported filters: der Abfrage, Formel der Messgröße oder sql: WHERE (Datasets unterstützen filters: grundsätzlich nicht)
In jedem Faktenzweig wiederholtes Prädikat zum Lebenszyklus oder zu einem Attribut Verwenden Sie filters: der Abfrage nur, wenn das Prädikat je nach Bericht variiert. Wenn es die dauerhaft einbezogene Grundgesamtheit definiert, behalten Sie eine Darstellung bei, die Zeilen ausschließt.
Numerisches Prädikat oder Verknüpfungsprädikat in sql: WHERE der Faktenquelle Verwenden Sie eine zwischengeschaltete Kennzahl als Filter erst, wenn Sie das Verhalten für Gruppen mit ausschließlich ausgeschlossenen Zeilen, für andere Kennzahlen derselben Ebene, für Joins und Fenster sowie den semantischen Unterschied zwischen einem fehlenden Wert und explizitem NULL überprüft haben.
referred column {DATASET}.col is undefined im Abfragefilter Schreibweise als Zeichenfolge: "{DATASET}.col = Wert":
Die Liste mit zwei Elementen dt_date: ['2024-01-01', '2025-12-31'] liefert nur 2 Tage Eine direkt angegebene Liste wird zur exakten Wertübereinstimmung mit IN (...) kompiliert, nicht zu einem Bereich. Verwenden Sie dt_date: { range: ['2024-01-01', '2025-12-31'] } für Intervalle, die beide Grenzen einschließen.
Datumsfenster für einen einzelnen Zweig Deklarieren Sie dt_date am betreffenden Dataset und verwenden Sie filters: dt_date: range: [...] in der Abfrage.

Eine Auswahlregel mit alternativem Lookup kann Joins restriktiver machen #

Eine Auswahlregel wie „Übereinstimmung mit der Zieldimension oder, falls es dort keine Entsprechung gibt, mit einer indirekten Dimension“ verwendet zwei optionale Beziehungen. Steht das abgeleitete Kennzeichen in filters: der Abfrage, kann das kompilierte SQL einen der Lookups zur Pflicht machen (INNER JOIN) oder den Ausdruck mit AND/OR so umsetzen, dass die Ausweichlogik verloren geht.

Verwenden Sie vorzugsweise diese Struktur:

Zielstatus: pk({dt_month}, {Kundennummer}).{TARGET_CUSTOMER}.state
KundeBerechtigt: |-
  iif({Zielstatus} = 1, 1,
    iif(pk({Kundennummer}).{INDIRECT_CUSTOMER}.Kundennummer is not null, 1, 0))
BerücksichtigterBetrag: iif({KundeBerechtigt} = 1, {Verkaufsbetrag}, null)

measures:
  Verkaufsbetrag: SUM({BerücksichtigterBetrag})

Prüfen Sie anschließend das erzeugte SQL. Beide Lookups müssen als LEFT JOIN erhalten bleiben und die Ausweichlogik muss innerhalb von CASE bleiben. Eine etwaige Bedingung für Ausgabegruppen sollte eine bereits ausgewählte primäre Messgröße wiederverwenden (HAVING AGG(Verkaufsbetrag) is not null), damit keine zusätzliche verborgene Spalte in das Ergebnis gelangt. Nutzen Sie nicht eindeutige Schlüssel und Überschneidungen zwischen Ziel- und indirekter Dimension als Diagnosehinweise. Beziehungen in DML sollten eine unbeabsichtigte Vervielfachung von Zeilen nicht stillschweigend reproduzieren.

P43. {dimension: [...]} und {-d: dim_dt} im Vergleich (unterschiedliche SQL-Struktur) #

Fehler: {-d: dim_dt} verwenden, obwohl das Referenz-SQL einen separaten GROUP BY-CTE auf einer gröberen Aggregationsebene verwendet. Lösung: Übernehmen Sie die Struktur der Referenz. {dimension: [cols]} erzwingt einen separaten CTE für die Aggregation. {-d: dim_dt} verwendet den Fensterausdruck OVER (PARTITION BY …). Siehe P44 und P45.

P44. Anteil am Fenstergesamtwert und {-d: dim} im Vergleich #

Fehler: Den mit --to-dml erzeugten Entwurf divide({m}, {m_minus_dim_X}) als endgültiges fachliches DML übernehmen. Lösung: Verwenden Sie divide({m}*1.0, {m: {-d: dim}}) in columns: der Abfrage oder in Messgrößen. Siehe Dimensions- und Filtermodifikatoren.

Entspricht Model Query SQL. Hier geht es um Fallstricke, die nur bei YAML auftreten. Die vollständigen Regeln stehen unter YAML-Abfragedeklarationen.

P62. dimensions: einer Messgröße als Zeilenschlüssel des Datasets oder zur Abfragegruppierung verwenden #

Symptom: An einer Messgröße steht dimensions: [[Region]] in der Erwartung, dass das Abfrageergebnis nach Region gruppiert wird, entsprechend dimension: am Dataset. Die Abfrage wird ohne diese Gruppierung kompiliert oder schlägt mit einer anderen Abfragedimension fehl. Falsche Annahme: dimensions: einer Messgröße legt fest, wie Zeilen im Dataset identifiziert werden, oder steuert die Gruppierung der Abfrage. Tatsächliches Verhalten: dimensions: einer Messgröße enthält die zulässigen Dimensionen. Jede innere Liste bildet eine Dimension. Die äußere Liste enthält Alternativen. Die Zeilenidentität wird in dimension: am Dataset festgelegt. Die Gruppierung wird mit GROUP BY oder columns.dimension: in der Abfrage festgelegt. Lösung: Entfernen Sie dimensions: von der Messgröße, sofern die Kennzahl diese zulässigen Dimensionen nicht tatsächlich benötigt. Legen Sie die Gruppierung des Ergebnisses in der Abfrage fest (GROUP BY / columns.dimension:).

# Wrong: expecting dimensions: to produce GROUP BY region
Umsatz:
    type: measure
    dataset: Transaktionen
    formula: SUM({Verkaufsbetrag})
    dimensions:
        - [Region]

# Right: no dimensions: lock; grouping lives in the query
Umsatz:
    type: measure
    dataset: Transaktionen
    formula: SUM({Verkaufsbetrag})
# SELECT region, AGG(sales) FROM MODEL GROUP BY region

Die verbindlichen Regeln finden Sie unter Dimensionsrollen.

P64. materialize: true an einer Messgröße #

Symptom: Beim Kompilieren erscheint ERROR error during processing [ref null]: undefined modifier 'materialize'. Die Messgröße wird stillschweigend verworfen (0 measure(s) processed). Fehler: materialize: true zur Definition einer Messgröße hinzufügen und erwarten, dass der Compiler sie vorab aggregiert. Für Messgrößen gibt es keine Materialisierungsoption (mit dmlc -c in dmlc 0.3.16 überprüft). Lösung: Deklarieren Sie die Materialisierung mit einem Objekt vom Typ type: materialize auf oberster Ebene (parameters: + dimension: + measures:) oder mit materialize: <name> am Dataset. Geben Sie sie niemals an einer Messgröße an. Siehe Materialisierungsdefinition (type: materialize) und Beispiele zur Materialisierung.

# Wrong
Umsatz:
    type: measure
    dataset: Transaktionen
    formula: SUM({Verkaufsbetrag})
    materialize: true   # ← undefined modifier 'materialize'

# Right
DWS_SALES:
    type: materialize
    parameters:
        dt_date: date
    dimension: [dt_date, Produkt]
    measures: [Umsatz]

P66. Messgröße als Dimension ohne expliziten Entitätsschlüssel #

Symptom: Für die Kompilierung muss der Entitätsschlüssel explizit mit +d oder dimension: angegeben werden. Verwenden Sie vorzugsweise +d und lesen Sie die Einschränkungen der jeweiligen Version, bevor Sie die Schreibweise zum Ersetzen von Dimensionen verwenden. Fehler: Eine Messgröße ohne Schlüssel verwenden und erwarten, dass eine andere ausgegebene Messgröße die Entitätsebene vorgibt oder impliziert. Lösung: Deklarieren Sie den vollständigen Entitätsschlüssel dort, wo Sie die Messgröße als Dimension verwenden. Direkt eingebettete Skalarfunktionen sind zulässig, wenn die als Eingabe verwendeten Messgrößen den Schlüssel explizit angeben. Siehe Messgröße als Dimension.

# Wrong
dimension:
    - payment_day

# Right, inline scalar
dimension:
    - payment_day: 'cast({Freigabezeit: {+d: payment_id}} as date)'

P67. Aus Kennzahlen abgeleitete Dimensionen mit Inkompatibilitäten oder Abhängigkeiten #

Symptom: Bei der Kompilierung werden inkompatible Klassifizierungsschlüssel oder eine Abhängigkeit zwischen Bezeichnungen gemeldet. Fehler: Eine Bezeichnung verwendet {+d: Filialnummer} und eine andere {+d: Kundennummer}, oder eine Bezeichnung verweist auf eine andere Bezeichnung, die in derselben Abfrage deklariert ist. Lösung: Verwenden Sie für unabhängige Bezeichnungen denselben vollständigen Entitätsschlüssel. Die Reihenfolge der Schlüsselfelder darf abweichen. Wenn die Bezeichnungen tatsächlich auf unterschiedlichen Granularitätsebenen definiert sind, modellieren Sie eine separate Relation oder eine wiederverwendbare fachliche Kennzahl.

P68. Ausgabekennzahl lässt sich von der Klassifizierungsebene aus nicht auf eine gröbere Ebene aggregieren #

Symptom: Bei der Kompilierung wird gemeldet, dass eine Aggregation fehlt oder dass eine erneute Aggregation nicht möglich ist. Fehler: {Umsatz: {+d: Filialnummer}} direkt ausgeben, bereits berechnete Anzahlen unterschiedlicher Werte summieren oder Mittelwerte von Quotienten bilden, ohne die gewünschte Gewichtung festzulegen. Lösung: Umschließen Sie die Referenz auf die feinere Ebene mit der gewünschten Aggregation, etwa SUM({Umsatz: {+d: Filialnummer}}). Aggregieren Sie bei Quotienten die Komponenten und berechnen Sie den Quotienten neu. Behalten Sie für Anzahlen unterschiedlicher Werte, Mediane, Perzentile und ähnliche Kennzahlen geeignete Eingabewerte oder Aggregationszustände bei oder definieren Sie eine separate unterstützte Kennzahl. Andernfalls müssen Sie den Kompilierungsfehler in Kauf nehmen.

P69. WHERE für eine feinere Granularität in filters: einer gröber aggregierten Abfrage #

Symptom: Der CTE aggregiert auf Ebene (G), etwa Produkt × Region, filtert (Verkaufsanzahl > 3) und summiert dann mit SUM auf Ebene (Q), etwa Produkt. Der Entwurf bzw. --to-dml gibt nur die Abfragedimension (Q) aus, zusammen mit filters: "Verkaufsanzahl > 3" und SUM({Summe: {+d: Region}}). Bei der Kompilierung oder Zusammenführung kann daraus HAVING COUNT(1) > 3 auf Produktebene werden. Dadurch gehen die falschen Zeilen in die Auswertung ein.

Fehler:

filters:
  "Verkaufsanzahl > 3":                 # cnt is not defined at product-only grain
columns:
  dimension: [Produkt]
  Gesamtsumme: 'SUM({Summe: {+d: Region}})'

Ebenfalls fehlerhaft: SUM({Summe: {+d: Region, +f: '{Verkaufsanzahl} > 3'}}) verwendet eine aggregierte Kennzahl in einem Eingabeprädikat. Die Diagnose bezieht sich auf dieses Prädikat und bedeutet kein generelles Verbot, +f auf Kennzahlreferenzen anzuwenden. Siehe die Tabelle der unterstützten Funktionen.

Lösung: Filtern Sie innerhalb der Aggregation auf der gemeinsamen feineren Ebene:

Gesamtsumme: |-
  SUMIF({Summe: {+d: Region}}, {Verkaufsanzahl: {+d: Region}} > 3)
# No accepted fine rows -> NULL; ELSE 0 would change that result.

Verwenden Sie filters: auf Abfrageebene nur für Filter im Berichts- bzw. HAVING-Kontext. Siehe Mehrstufige Aggregation mit +da.

P70. OVER bei einer atomaren Kennzahl #

Symptom: Die Meldung window functions are not allowed in atomic measures erscheint. Ältere Programmversionen können sich mit Exitcode 0 beenden und dabei ein ungültiges SUM(…) OVER (…) … GROUP BY mit fehlenden Partitionsspalten erzeugen.

Fehler:

measures:
  Nettoeinkaufsmenge: 'SUM({Menge}) over (partition by {Filialnummer}, {Artikelnummer})'

Lösung: Bei der Platzierung der Fensterfunktion gehört OVER für Detailzeilen unter columns:. Danach folgt die atomare Aggregation:

columns:
  Nettomenge: 'SUM({Menge}) over (partition by {Filialnummer}, {Artikelnummer})'
measures:
  Nettogesamtmenge: 'SUM({Nettomenge})'

Rang oder Anteil nach GROUP-BY bleibt eine zusammengesetzte Kennzahl (ohne dataset:) mit {-d:} bzw. {-df:}. Die Regeln stehen unter Platzierung von Fensterfunktionen.

P71. Direkte Referenz {col} in PARTITION BY einer Kennzahl #

Symptom: Die Meldung … reference is not allowed in PARTITION BY oder ein Hinweis auf {dimension:} oder {-d:} erscheint.

Fehler (bei einer Kennzahl): SUM({Summe}) over (partition by {Produkt}). Lösung:

  • Verschieben Sie eine Fensterfunktion für Detailzeilen nach columns: und referenzieren Sie {Produkt} dort weiterhin direkt.
  • Verwenden Sie für eine Fensterfunktion nach der Aggregation partition by {-d: Region} oder {dimension: Produkt} in einer zusammengesetzten Kennzahl.

Setzen Sie {-d:} für eine Fensterfunktion auf Detailzeilen nicht unter columns: des Datensatzes. Dort werden Spalten direkt referenziert.

Mit dmlc 0.3.16 überprüft (Migration der Warenkorbanalyse mit zwei Produktrollen). Diese Fälle lassen sich fehlerfrei kompilieren und ändern dabei unbemerkt die Semantik. Prüfen Sie stets die erzeugten ON-Klauseln.

P72. Zwei Granularitätsfelder für dieselbe Spalte führen bei datensatzübergreifender Aggregation zum falschen Join-Schlüssel #

Symptom: Die Kompilierung im strikten Modus ist erfolgreich und es gibt keine Diagnosemeldungen, aber ein Quotient ist falsch. Beispielsweise lautet der Nenner des Lift left_count * left_count statt left_count * right_count.

Fehler: Ein Datensatz stellt zwei Felder bereit, die auf derselben physischen Spalte basieren (left_product_id: '{Produktnummer}', right_product_id: '{Produktnummer}'). Für die Aggregation der zweiten Rolle mit {sold_baskets: {-df: [left_product_id]}} (oder {dimension: [month, store, right_product_id]}) wird erwartet, dass der Join über right_product_id erfolgt. Der Compiler weist dem Schlüssel des temporären Ergebnisses auf gröberer Ebene einen neuen Alias zu und erzeugt einen Join über den Schlüssel der ersten Rolle (support.Produkt = pair.left_product_id).

Lösung: Schlagen Sie jede Rolle mit pk() in einem sql:-Datensatz nach, der die Quelle auf der Ebene (shared dims, Produktnummer) gruppiert und dimension: deklariert (P77). Die Schlüssel für pk() werden explizit und anhand ihrer Position zugeordnet. Dadurch können linker und rechter Schlüssel nicht zusammenfallen. Alternativ können Sie -df-Aggregationen auf Ebenen beschränken, auf denen keine Aliaskollision auftritt. Prüfen Sie im generierten SQL, ob zwei getrennte Joins vorliegen, … Produktnummer = t.left_product_id und … Produktnummer = t.right_product_id.

P73. Zusammengesetzte Kennzahlen mit -df-Aggregation geben Zeilen aus, die nur im Partnerdatensatz vorkommen, und können Schlüsselwerte künstlich erzeugen #

Symptom: Bei der Kompilierung entsteht aus einer Kennzahl, die aus einem anderen Datensatz auf eine gröbere Ebene aggregiert wird, eine zusammengesetzte Kennzahl mit FULL OUTER JOIN. Zeilen, die nur im aggregierten Partnerdatensatz vorkommen, erscheinen in der Ausgabe. Das temporäre Ergebnis des Partnerdatensatzes kann fehlende Granularitätsfelder mit max(<col>) auffüllen. Dadurch kann eine Zeile (month, store, Produkt) ohne Entsprechung als left = right = Produkt erscheinen. Es entsteht also ein künstliches Paar eines Produkts mit sich selbst, anstatt dass lediglich NULL-Werte ausgegeben werden.

Lösung: Behalten Sie in der Ausgabe eine primäre Kennzahl bei, die für Zeilen, die nur im Partnerdatensatz vorkommen, den Wert NULL hat. Sichern Sie die Abfrage mit einem Filter ab, der die Formel als Schlüssel verwendet:

filters:
    '{GemeinsameWarenkörbe} is not null':      # formula as key, empty value

Bei der Kompilierung entsteht für den Rückjoin die Bedingung WHERE <primary> IS NOT NULL. Der damit nachgewiesene vorhandene Wert vereinfacht außerdem den erzeugten FULL OUTER JOIN zu LEFT JOIN. Maßgeblich für den endgültigen Join-Typ ist das erzeugte SQL, nicht die Vorlage für die zusammengesetzte Kennzahl. Weisen Sie zuerst die Voraussetzungen nach. In einer gültigen primären Gruppe darf die primäre Kennzahl niemals NULL sein. Der Filter funktioniert nur, wenn Zeilen, die ausschließlich im Partnerdatensatz vorkommen, keinen Wert für diese Kennzahl haben. (Ergänzt Dimensionsmodifikatorenb.)

P74. Zwei table:-Datasets auf derselben physischen Tabelle – Besonderheiten beim Zusammenführen und unbemerkter Verlust der -df-Granularität #

Symptom: warn during processing [dataset B]: similar dataset(s) [A] exist, consolidate?. Wenn die beiden Datasets unterschiedliche Spalten haben, folgt skip dimension column <f> for measure <m> which does not exist in dataset <A>. Der Rollup aggregiert ohne weiteren Hinweis auf einer gröberen Ebene (z. B. pk(Filialnummer) statt pk(Filialnummer, left_id)).

Überprüft mit dmlc 0.3.16: Zwei table:-Datasets auf derselben Tabelle führen für sich genommen nicht zu einem Absturz. Der minimale symmetrische Fall lässt sich kompilieren. Ein zweites Dataset in einer anderen Rolle bindet sogar -df korrekt (right_id = t1.right_id). Die Datasets werden per Self-Join über den Primärschlüssel zu einer einzigen #TEMP zusammengeführt. Wird nur auf einer Seite eine Spalte hinzugefügt, fallen beim Zusammenführen die Aliasfelder des anderen Datasets aus der Namensauflösung für -df heraus. (Die frühere Meldung „doppeltes table: → NPE“ nannte die falsche Ursache. Der Absturz ging auf die Filterstruktur in P75 zurück.)

Abhilfe: Verwenden Sie vorzugsweise pro physischer Tabelle ein einziges table:-Dataset mit Aliasspalten. Wenn mehrere Rollen nötig sind, halten Sie die Spaltenmengen identisch und prüfen Sie für jede temporäre Rollup-Tabelle pk(...) im generierten SQL. Eine Warnung an dieser Stelle weist auf einen semantischen Fehler hin.

P75. Schutzfilter für Kennzahlen in filters: der Abfrage – Syntax und Fehlerverhalten #

Richtig: '{measure} is not null':. Die gesamte Formel ist der Schlüssel, der Wert bleibt leer. So schließen Sie verwaiste FOJ-Zeilen auf der Ebene aus, auf der die Abfrage ihre Zeilen definiert.

Falsch: my_measure: {condition: '...'} → Schemafehler (condition ist keine Filtereigenschaft). Bei my_measure: '<expr>' wird der Schlüssel als Spaltenname interpretiert. Wird er als Kennzahl aufgelöst, kann Query.treat_filters eine NPE auslösen, statt eine Diagnose auszugeben.

Abhilfe: Verwenden Sie die Formel selbst als Schlüssel und stellen Sie sicher, dass die referenzierte Kennzahl auf der Granularität der Abfrage aufgelöst werden kann. Lässt sich der Verweis nicht auflösen, tritt eine NPE auf, statt dass eine verständliche Fehlermeldung ausgegeben wird.

P76. -df und -d erwarten deklarierte Feldnamen der Granularität statt Namen von Quellspalten #

Symptom: Nach dem Umbenennen einer Abfragedimension über eine Bindung (columns.dimension: [..., new_name: '{col}']) erscheint column(s) [x] has been specified as -d/-df, but not in dimension [...].

Ursache: Die Bindung erzeugt ein internes Feld (new_name__<query>). Modifikatoren entfernen Felder anhand der Namen, unter denen sie die Granularität definieren. Der zugrunde liegende Spaltenname gehört nicht mehr zu diesen Feldern.

Abhilfe: Übergeben Sie an -df, -d und dimension: die deklarierten Feldnamen der Granularität. Wenn ein Feld weiterhin über seinen Namen entfernbar sein muss, behalten Sie es unter diesem Namen im Dataset.

P77. Zugriff auf eine aggregierte Relation mit pk() – sql: als Ziel und dataset: an der umschließenden Kennzahl #

Symptom: Bei MAX(pk(...).{Support}.col) erscheint dataset must be specified when aggregate non-measure column, did you mean <SupportDataset>?.

Regeln:

  • pk() verweist auf Datasets oder verwendet direkt die Form TABLE(pk_cols). Eine Kennzahl kann kein Ziel von pk() sein. Ein aggregierter Nachschlagewert (z. B. count(distinct …) auf gröberer Ebene) braucht daher ein sql:-Dataset mit deklariertem dimension:-Eintrag. Der Compiler erzeugt daraus eine temporäre Tabelle mit Index, die sich wie eine Dimension verknüpfen lässt.
  • Die umschließende aggregierende Kennzahl durchläuft die Zeilen des nutzenden Datasets. Geben Sie dieses Dataset unter dataset: an (dataset: BasketProductPair, nicht das Hilfsdataset).
  • Ein INNER JOIN in der Referenzabfrage auf ein Hilfsdataset mit garantierten Treffern wird als LEFT JOIN kompiliert. Das ist nur zulässig, wenn die Nachschlageschlüssel aus derselben Grundgesamtheit stammen. Halten Sie die Begründung im Ausnahmeregister fest.

P79. +d zusammen mit -d oder -df für dieselbe Dimension #

Falsch: {销量: {+d: 门店, -d: 门店}} oder {销量: {+d: 门店, -df: 门店}} wird akzeptiert und zu {销量} bzw. {-f: 门店} vereinfacht.

Ursache: Es gibt keine eindeutige implizite Auslegung. Das gegenseitige Aufheben der Modifikatoren verdeckt Tippfehler. Bei AVG unterscheidet sich die Auswertung auf feiner Ebene von einem einfachen Verweis. Wenn das Feld bereits zur Ausgabegranularität gehört, gilt -df ≠ -f.

Abhilfe: Geben Sie genau die gewünschte Auswertungsstufe an. Verwenden Sie einen einfachen Verweis, einen expliziten Verweis auf feiner Ebene mit äußerer Aggregation oder einen Modifikator zum Entfernen. Für unterschiedliche Felder können Modifikatoren weiterhin kombiniert werden. Der aktuell geprüfte Build akzeptiert die untersuchten Konflikte ohne Diagnose und wiederholt die regionalen Summen vor einer äußeren Summierung. Damit verletzt er die Vorgabe, solche Konflikte zurückzuweisen. Siehe Kombination von Modifikatoren.

P80. -f / -df lässt bei den Berichtszeilen einen Abfragefilter auf einem Feld außerhalb der Ausgabegranularität weg #

Fehlerhaftes Verhalten: Die Abfrage filtert mit {Filialnummer}=1, während eine Kennzahl {-f: Filialnummer} verwendet und Filialnummer nicht zur Ausgabegranularität gehört. Dadurch entfällt der Filter ohne Hinweis, und FOJ-Partnerzeilen aus dem ungefilterten Zweig erscheinen.

Abhilfe: -f entfernt den Filter nur aus der Kennzahlauswertung. Abfragefilter bestimmen weiterhin die Grundgesamtheit. Wenn der blockierte Filter keine Ausgabespalte referenzieren kann, schränken Sie die Zeilen mit einem korrelierten EXISTS oder einem Semi-Join ein. Ändern Sie die Gruppierung nicht allein über -f.

P81. Wechsel der Granularität einer Zeitdimension mit dimension: ohne kalendergestützte Verteilung der Ergebnisse auf die Zeilen der feineren Ebene #

Fehlerhaftes Verhalten: {销量: {dimension: [dt_quarter]}} in einer Abfrage auf Ebene dt_month führt dazu, dass ein einzelner Skalarwert angefügt wird oder sich dt_quarter aus einer Monats-CTE nicht auflösen lässt.

Abhilfe: Werten Sie die Kennzahl auf Quartalsebene aus. Ordnen Sie dazu Monat oder Datum über den Kalender dem Quartal zu. Übertragen Sie dann die Quartalssumme auf jede Monatszeile des Quartals (Muster nullpk(pk(dt_month).CAL.dt_quarter)). Mit additivem SUM lassen sich Monatswerte erneut aggregieren. Nicht additive Kennzahlen müssen auf der gröberen Ebene aus den Faktendaten berechnet werden.

P78. Ein sql:-Escape muss die Filterbedingungen für die Grundgesamtheit und das Zeitfenster selbst enthalten #

Symptom: Die dt_*-Bereichsfilter der Abfrage werden nicht in den Text eines sql:-Blocks verschoben. Sie landen in der äußeren WHERE-Klausel der bei der Kompilierung erzeugten temporären abgeleiteten Tabelle. Bei einem Self-Join im Escape vergrößert eine Seite des Joins ohne Zeitgrenzen die Grundgesamtheit unbemerkt (z. B. bilden Zeilen auf der rechten Seite außerhalb des Berichtszeitraums Paare).

Lösung: Hinterlegen Sie die dauerhaft geltenden Filterbedingungen für die Grundgesamtheit (line_status = 'SOLD') und symmetrische Zeitfenstergrenzen in der inneren Abfrage des Escapes, damit für alle Join-Seiten und Zweige dieselben Auswahlkriterien gelten. Grenzen Sie den Berichtsumfang mit filters: der Abfrage anhand der äußeren Schlüssel ein. Wenn der Escape aus einer physischen Tabelle liest, die zu table: gehört, verwenden Sie from {Dataset} (P22b) und niemals den physischen Tabellennamen direkt.
