面向熟悉 SQL 的报表开发、应用开发和数据运维人员。

本练习使用月销售额与季度销售额两个 Maz。用生成的 setup_sql 安装运行时。执行 prepare_sql 后，根据返回的 data_ready=1 执行业务查询。等待期间可用 prepare_status_sql 查看本次请求，用 DML_MAZ_PROGRESS 查看全局进展。

先阅读prepare 与 refresh 的选择、参数和恢复规则。

用教程中的销售数据做季度报表 #

互动教程第 12 章的 FACT_SALES 数据集读取 TABLE_SALES，用 id 标识一笔销售，dt_month 记录月份，sales: SUM({amount}) 计算销售额。继续使用这份模型和 8 笔原始数据。1 月合计 70，2 月合计 100。

这个扩展新增两个物化结果和一张季度报表。

TABLE_SALES（销售明细） → SALES_MONTHLY（月销售额） → SALES_QUARTERLY（季度销售额） → quarterly_sales（报表）

查询准备先检查上游需要的月份，再构建下游季度。每个需要重建的分片单独提交。

准备第一季度 #

  1. 在空的 SQL Server 练习库运行互动教程的安装脚本。若已运行过该练习，继续使用同一个练习库。
  2. 运行下方的日历扩展。教程的练习日历只有日期和月份，范围截至 2025 年 2 月。这一步增加季度并补齐到 6 月底。
  3. 在教程的 model.dml 顶部加入 dialect: mssql，再追加下面的物化与报表定义。

回看互动教程第 12 章，下载原始 model.dml 和 SQL Server 安装脚本。

展开 SQL Server 日历扩展

SET dt_quarter = DATEFROMPARTS(YEAR(dt_date), 3 * (DATEPART(quarter, dt_date) - 1) + 1, 1);
ALTER TABLE dbo.DML_CALENDAR ALTER COLUMN dt_quarter date NOT NULL;

;WITH dates AS (

展开物化与报表定义 
SALES_MONTHLY:
  type: materialize
  parameters: {dt_month: range}
  dimension: [dt_month]
  measures: [sales]

SALES_QUARTERLY:
  type: materialize
  allows: [SALES_MONTHLY]
  parameters: {dt_quarter: range}
  dimension: [dt_quarter]
  measures: [sales]

quarterly_sales:
  type: query
  allows: [SALES_QUARTERLY]
  filters:
    dt_quarter:
      range: ['2025-01-01', '2025-01-01']
  columns:
    dimension: [dt_quarter]
    sales:

编译扩展后的模型，用生成的 setup_sql 安装物化和依赖。随后在自动提交连接上执行 quarterly_sales 的 prepare_sql；它完成准备和实际就绪检查后返回 data_ready=1，再执行同一请求的业务 sql。等待期间可从另一连接用 prepare_status_sql 观察状态。错误或等待超时后暂不查询，排除原因后重试普通准备。SQL Server 会话需要 IMPLICIT_TRANSACTIONS OFF 且 @@TRANCOUNT = 0。业务查询仍为 SELECT 或 CTE。

第一季度返回 170。1、2、3 月都已有月分片状态，3 月的分片当时为空。示例使用大写物化名，以避开当前 SQL Server 登记对混合大小写嵌套名称的问题。

新月份和历史更正怎样处理 #

按下方顺序在练习库运行三次数据变动。源事务提交后再执行 refresh。两次插入分别使用教程已有的地区和客户。

源表变化 要执行的操作 报表结果
向 TABLE_SALES 插入 3 月销售额 30。一季度已发布 refresh SALES_MONTHLY 的 3 月，默认刷新该月及已物化的一季度 一季度 170 → 200
向 TABLE_SALES 插入 4 月销售额 40。二季度及所需月分片尚未构建 将 quarterly_sales 的两个筛选边界都改为 2025-04-01。执行新的 prepare_sql，正常返回后再执行 sql 查询二季度 二季度首次返回 40
更正 2 月 id = 2 的销售额，20 改为 25 refresh SALES_MONTHLY 的 2 月，默认刷新该月及受影响一季度 一季度 200 → 205，二季度保持 40

回放使用 2025 年的历史分片。3 月补录和 2 月更正后，仅执行普通准备仍会复用旧结果。首次查询二季度时，正常准备能从源表读取 4 月的新数据，因为二季度和上游分片都是首次构建。如果上游已有缓存，包括曾构建为空的月份，提交后通知受影响月份可避免漏刷新。

展开三次写入及通知的 SQL 
-- 1. 3 月补录。源写入提交后登记刷新需求，并尝试调用 runner。
INSERT dbo.TABLE_SALES (id, region, customer, dt_month, status, amount)
VALUES (9, N'North', N'A', '20250301', N'completed', 30);

EXEC dbo.DML_REFRESH_MAZ
    @_materialize = N'SALES_MONTHLY',
    @_range_start = '20250301',
    @_range_end   = '20250331';

-- 2. 4 月首次入库。写入提交后首次准备二季度。
INSERT dbo.TABLE_SALES (id, region, customer, dt_month, status, amount)
VALUES (10, N'South', N'C', '20250401', N'completed', 40);

-- 3. 回到一季度。2 月更正提交后刷新月及季度。
UPDATE dbo.TABLE_SALES SET amount = 25 WHERE id = 2;

EXEC dbo.DML_REFRESH_MAZ
    @_materialize = N'SALES_MONTHLY',
    @_range_start = '20250201',
    @_range_end   = '20250228';

运行每个步骤后，先用表中列出的报表范围验证结果，再运行下一步。如果加载脚本显式打开事务，先提交该事务，再在自动提交连接上调用 refresh。

默认 refresh 先统一失效并登记选中月及受影响季度，再调用 runner；忙时可返回已受理。读取报表前执行 Query 的 prepare_sql，它会等待并检查本次就绪。若希望等查询使用时再重建，显式增加 @_invalidate_only=1；它提交标记后返回，不启动 runner，不取消既有待办。

需要核验整张报表时，对 SALES_QUARTERLY 使用 DML_PREPARE_MAZ、第一季度范围和 @_force_update = 1，强制重建本次必要月份和季度。只知道某个月源数据变化时，从 SALES_MONTHLY 调用 refresh；只刷新季度不会发现未通知的旧月缓存。

@_match 默认 exact；like 配合 SALES~_% 匹配字面前缀 SALES_，配合 % 匹配全部已登记 Maz。日期包含起止日；refresh 同时省略日期处理已有范围，不预建整个日历。跨月移动须覆盖旧月和新月。

中断后继续工作 #

每片独立提交。后片失败时，已完成片保留，当前片回滚。普通 prepare 可补齐已知目标和范围；重新执行带 force_update=1 的 prepare 是新强刷。

默认 refresh 中断后，已登记的剩余分片保存在 STATE。排除错误后，可调用无参 DML_REFRESH_MAZ，或通过后续 prepare、refresh 唤起 runner。再次发送默认 refresh 或 force_update=1 会重新声明需求，允许重做已完成片。无参 refresh 只继续待办，不重新失效已完成片。取消或超时后须先关闭该物理连接，再继续待办；仅 ROLLBACK 不会释放会话级 runner 锁。提交响应丢失时，先重新检查状态。

处理常见问题 #

现象 检查和处理
源数据已更正，报表仍显示旧值 核对源事务是否提交、失效是否覆盖全部入口和日期，以及报表随后是否执行了 prepare_sql。只通知下游时，检查它依赖的上游是否也需要失效。
找不到过程、目标或 @_match 参数 确认连接的是目标库，并由部署端执行模型生成的 setup_sql。精确名称用已登记的 Maz 名称。LIKE 无匹配时调用成功但无更新，先确认匹配集合。
提示需要自动提交 使用 autoCommit=true 的 JDBC 连接，确认没有显式或隐式事务。在源写入事务提交后再发出失效调用。
失效报日期缺失、反向或日历未覆盖 同时传入两个有序日期，确认 dbo.DML_CALENDAR 覆盖区间内每一天。明确需要全部已物化范围时，可以同时省略两个日期。
提示缺少 writer 权限 请数据库管理员核查调用账号对失效过程和每个受影响 Maz 写入过程的执行权限。失效前校验本次所有受影响目标，未授权则拒绝。
锁超时或调用时断连 客户端取消或超时后，关闭发生取消的物理连接。有连接池时丢弃该连接，以释放会话级 runner 锁。排除错误后，用无参 DML_REFRESH_MAZ 继续已登记的待办。如果查询准备失败，重新执行整段 prepare_sql，返回 data_ready=1 后再查询。

有状态表读取权限时，可以用下面的查询检查分片。

SELECT materialize, dim_dt, state, COALESCE(last_end_time, created_end_time) AS build_finished_at
FROM dbo.DML_MATERIALIZE_STATE
WHERE materialize IN (N'SALES_QUARTERLY', N'SALES_MONTHLY')
ORDER BY materialize, dim_dt;

state = 0 表示普通失效，state = 3 表示无效且待主动刷新，state = 1 表示已有完整结果发布。构建时间记录的是 Maz 写入完成时间。判断是否包含某次更正时，还要核对失效通知和随后的准备。

用下列源表查询核对练习最终结果。第一季度是 205，第二季度是 40。

WITH source_rows AS (
    SELECT DATEFROMPARTS(YEAR(dt_month), 3 * (DATEPART(quarter, dt_month) - 1) + 1, 1) AS dt_quarter,
           amount
    FROM dbo.TABLE_SALES
    WHERE dt_month >= '20250101' AND dt_month < '20250701'
)
SELECT dt_quarter, SUM(amount) AS sales
FROM source_rows
GROUP BY dt_quarter
ORDER BY dt_quarter;

参阅prepare 与 refresh 使用约定。

查看全局 runner 进展 #

用生成的 setup_sql 安装共享进展视图，然后查询：

SELECT pending_partitions, runner_running, estimated_seconds
FROM dbo.DML_MAZ_PROGRESS;

视图每次统计最近 60 秒，报告当前待办、不同分片的完成速度、新增速度和预计清空秒数。同一分片在窗口内完成多次只计一次。没有待办时预计秒数为 0；runner 已停止但仍有待办，或无法净消化时，预计秒数为 NULL。监控账号需有视图 SELECT 权限。

这是全局进展，不是本次报表的就绪证明。读取报表前使用该 Query 的 prepare_sql 等待并确认就绪。完整列说明、runtime 对象归属和恢复步骤见prepare 与 refresh 使用约定。
