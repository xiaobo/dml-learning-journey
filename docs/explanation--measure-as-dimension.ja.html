メジャーをディメンションとして使う

このパターンでは、エンティティごとにラベルを計算し、そのラベルで指標をグループ化します。ラベルはクエリのディメンションとして機能します。ソース行を識別するものではありません。

エンティティキーと評価段階 #

ラベルは特定の粒度のエンティティに属するため、分類には完全なエンティティキーが必要です。通常のレポート項目を Q、エンティティキーを K とします。+d: K を指定すると、分類器は Q ∪ K で定義される粒度で評価されます。コンパイラは完全なキーでラベルを対応付けてから、Q とラベルで通常の指標を集計します。

アトミックな定義 sales: SUM({amount}) を前提とすると、このクエリの断片は顧客を売上額でグループ化します。

report:
  type: query
  columns:
    dimension:
      - sales_bucket: '{sales: {+d: customer}}'
    total_sales: 'SUM({sales: {+d: customer}})'

外側に明示した SUM は、同じラベルを持つ顧客の売上額を合計します。この例では、売上額そのものをラベルとして使います。業務上の区分を使うには、その区分専用の分類器を定義し、検証する必要があります。

分類を使う箇所では、キーを明示する必要があります。{measure} だけを指定すると拒否されます。メジャー定義内のより細かい粒度の段階や、同じ階層にある別の指標で、不足しているキーを補うことはできません。

今回確認したビルドでは、検証対象の +d: customer と dimension: [customer] を使った件数ベースの分類器は、顧客単位で集計した後にラベルでグループ化する形にコンパイルされます。この検証で確認できるのは、テストした形式だけです。

母集団と再集計 #

分類の対象範囲、どのエンティティを母集団に含めるか、レポートの対象範囲は、それぞれ独立して決めます。-d は時間フィルターを保持するため、時間によるグループ化を外しただけでは、エンティティの全期間が分類対象になるとは限りません。ラベルの値が NULL でも、有効な区分になり得ます。その値だけでは、エンティティが母集団に含まれていないとは判断できません。また、分類によって非アクティブなエンティティが作られることもありません。

複数のラベルを使うには、互いに互換性のある完全なエンティティキーと、ラベルごとに独立した定義が必要です。加算可能な金額は、エンティティ単位の値を合計できます。比率、平均、重複を除いた件数には、再集計しても元の定義を保てる構成要素が必要です。

分類ラベルと指標に対するフィルター #

分類器が付けたラベルや、ラベル単位で評価される同階層のメジャーに対するフィルターは、分類の後に適用します。DML クエリでは、このような条件を filters: の下に記述できます。たとえば、"{首购月} is not null OR {销售额} > 0": と指定します。

Model Query では、メジャーに対する条件を HAVING として表せます。どのキーワードを使うかよりも、意味上どの段階で条件を適用するかが重要です。コンパイルで生成された SQL では、分類で得られたリレーションに WHERE を適用するのが一般的です。条件を分類より前に移すと、ラベルの計算に使う母集団が変わります。

制約 #

このパターンは、クエリの columns.dimension を対象とします。確認したマテリアライズでは、通常の属性 {region} はコンパイルできますが、{sales: {+d: id}} を materialize.dimension_columns に記述すると、使用できないメジャー参照として拒否されます。クエリの分類器をそのままマテリアライズの属性に移さないでください。生成された分類と再集計の段階を確認し、そのうえでご自身のデータを使ってキーを検証し、結果の値を比較してください。
