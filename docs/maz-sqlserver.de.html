Für Berichts- und Anwendungsentwickler sowie Mitarbeitende im Datenbetrieb mit SQL-Kenntnissen.

In dieser Übung verwenden Sie zwei Mazes für Monats- und Quartalsumsätze. Installieren Sie die Laufzeitumgebung mit dem generierten setup_sql. Führen Sie prepare_sql aus und starten Sie die fachliche Abfrage, sobald data_ready=1 zurückgegeben wird. Während der Wartezeit können Sie mit prepare_status_sql den Status dieser Anfrage und mit DML_MAZ_PROGRESS den Gesamtfortschritt verfolgen.

Lesen Sie zuerst „prepare und refresh auswählen: Parameter und Wiederherstellungsregeln“.

Ein Quartalsbericht auf Basis der Umsatzdaten aus dem Tutorial #

In Kapitel 12 des interaktiven Tutorials liest der Datensatz Verkaufspositionen aus TABLE_SALES, identifiziert jeden Verkauf anhand von VerkaufspositionID, erfasst den Monat in dt_month und berechnet den Umsatz als SUM({Verkaufsbetrag}). Verwenden Sie dieses Modell mit seinen 8 Quellzeilen weiter. Die Summe für Januar beträgt 70, die für Februar 100.

Diese Erweiterung fügt zwei materialisierte Ergebnisse und einen Quartalsbericht hinzu.

TABLE_SALES (Verkaufsdetails) → SALES_MONTHLY (Monatsumsatz) → SALES_QUARTERLY (Quartalsumsatz) → Quartalsumsatz (Bericht)

Bei der Abfragevorbereitung wird zuerst geprüft, welche Monate in der vorgelagerten Materialisierung benötigt werden. Anschließend wird das Quartal in der nachgelagerten Materialisierung aufgebaut. Für jede Partition, die neu aufgebaut werden muss, erfolgt ein eigener Commit.

Das erste Quartal vorbereiten #

  1. Führen Sie das Einrichtungsskript des interaktiven Tutorials in einer leeren Übungsdatenbank auf SQL Server aus. Wenn Sie diese Übung bereits durchgeführt haben, verwenden Sie dieselbe Datenbank weiter.
  2. Führen Sie die unten gezeigte Kalendererweiterung aus. Der Übungskalender aus dem Tutorial enthält nur Datum und Monat und endet im Februar 2025. Dieser Schritt ergänzt die Quartalsangaben und füllt den Kalender bis Ende Juni auf.
  3. Speichern Sie eine Kopie der Datei model.dml aus dem Tutorial als quarterly_sales.dml. Lassen Sie die vorhandene Zeile dialect: mssql stehen und fügen Sie die folgenden Definitionen für die Materialisierungen und den Bericht am Dateiende ein.

Schlagen Sie bei Bedarf in Kapitel 12 des interaktiven Tutorials nach und laden Sie die Originaldatei model.dml sowie das ursprüngliche Einrichtungsskript für SQL Server herunter.

Kompilieren Sie das erweiterte Modell und installieren Sie die Materialisierungen und Abhängigkeiten mit dem generierten setup_sql. Führen Sie anschließend für Quartalsumsatz das zugehörige prepare_sql über eine Verbindung mit Autocommit aus. Es schließt die Vorbereitung und die Prüfung der tatsächlichen Datenbereitschaft ab und gibt data_ready=1 zurück. Führen Sie dann die fachliche Abfrage aus sql für dieselbe Anfrage aus. Während der Wartezeit kann eine andere Verbindung den Status mit prepare_status_sql abfragen. Führen Sie die Abfrage bei einem Fehler oder bei Ablauf der Wartezeit noch nicht aus. Beheben Sie zuerst die Ursache und wiederholen Sie die reguläre Vorbereitung. Für die Sitzung auf SQL Server sind IMPLICIT_TRANSACTIONS OFF und @@TRANCOUNT = 0 erforderlich. Die fachliche Abfrage bleibt ein SELECT oder ein CTE.

Für das erste Quartal liefert die Abfrage 170. Für die Monate 1, 2 und 3 liegt jeweils ein Status für die Monatspartition vor. Die Partition für März war zu diesem Zeitpunkt leer. Das Beispiel schreibt die Namen der Materialisierungen vollständig in Großbuchstaben, um eine derzeitige Einschränkung bei der Registrierung verschachtelter Namen mit gemischter Groß- und Kleinschreibung auf SQL Server zu umgehen.

Wie neue Monate und Korrekturen an historischen Daten verarbeitet werden #

Führen Sie die drei unten aufgeführten Datenänderungen der Reihe nach in der Übungsdatenbank aus. Führen Sie refresh nach dem Commit der Quelltransaktion aus. Beide Einfügevorgänge verwenden Regionen und Kunden aus dem Tutorial.

Änderung an der Datenquelle Vorgang Berichtsergebnis
Märzumsatz von 30 in TABLE_SALES einfügen. Q1 ist bereits veröffentlicht. refresh für März auf SALES_MONTHLY ausführen. Standardmäßig werden dieser Monat und das materialisierte Q1 aktualisiert. Q1 170 → 200
Aprilumsatz von 40 einfügen. Q2 und die zugehörigen Monatspartitionen sind noch nicht aufgebaut. Bewahren Sie das Kompilierungsergebnis für das erste Quartal auf. Setzen Sie in quarterly_sales.dml beide Datumsgrenzen von dt_quarter auf 2025-04-01 und führen Sie den obigen Kompilierungsbefehl erneut aus. Führen Sie prepareSql aus dem neuen Ergebnis aus. Sobald data_ready=1 zurückgegeben wird, führen Sie sql aus demselben Ergebnis aus. Zum Prüfen der Februarkorrektur verwenden Sie das gespeicherte Ergebnis für das erste Quartal oder setzen beide Grenzen auf 2025-01-01 zurück und kompilieren erneut. Q2 liefert erstmals 40.
Den Februarumsatz für VerkaufspositionID = 2 von 20 auf 25 korrigieren. refresh für Februar auf SALES_MONTHLY ausführen. Standardmäßig werden dieser Monat und das betroffene Q1 aktualisiert. Q1 200 → 205, Q2 bleibt bei 40.

Beim Nachvollziehen der Änderungen werden historische Partitionen aus 2025 verwendet. Nach dem Nachtragen der Märzdaten und der Februarkorrektur verwendet die reguläre Vorbereitung allein weiterhin die alten Ergebnisse. Bei der ersten Abfrage von Q2 kann die reguläre Vorbereitung die neuen Aprildaten aus der Quelle lesen, weil Q2 und seine vorgelagerten Partitionen erstmals aufgebaut werden. Falls bereits vorgelagerte Zwischenergebnisse vorliegen, auch für Monate, deren Partitionen beim Aufbau leer waren, melden Sie nach dem Commit die betroffenen Monate, damit keine Aktualisierung ausbleibt.

SQL für die drei Schreibvorgänge und Änderungsmeldungen anzeigen 
-- 1. March backfill. After the source write commits, register the
--    refresh demand and attempt to call the runner.
INSERT dbo.TABLE_SALES (id, region, customer, dt_month, status, amount)
VALUES (9, N'North', N'A', '20250301', N'completed', 30);

EXEC dbo.DML_REFRESH_MAZ
    @_materialize = N'SALES_MONTHLY',
    @_range_start = '20250301',
    @_range_end   = '20250331';

-- 2. April arrives for the first time. After the write commits,
--    prepare Q2 for the first time.
INSERT dbo.TABLE_SALES (id, region, customer, dt_month, status, amount)
VALUES (10, N'South', N'C', '20250401', N'completed', 40);

-- 3. Back to Q1. After the February correction commits, refresh
--    the month and the quarter.
UPDATE dbo.TABLE_SALES SET amount = 25 WHERE id = 2;

EXEC dbo.DML_REFRESH_MAZ
    @_materialize = N'SALES_MONTHLY',
    @_range_start = '20250201',
    @_range_end   = '20250228';

Prüfen Sie nach jedem Schritt das Ergebnis für den in der Tabelle angegebenen Berichtszeitraum, bevor Sie fortfahren. Wenn Ihr Ladeskript eine explizite Transaktion öffnet, schließen Sie diese zuerst mit einem Commit ab und rufen Sie dann refresh über eine Verbindung mit Autocommit auf.

Standardmäßig werden bei refresh zunächst der ausgewählte Monat und die betroffenen Quartale gemeinsam invalidiert und registriert. Danach ruft refresh den Runner auf. Solange der Runner beschäftigt ist, kann refresh "accepted" zurückgeben. Führen Sie vor dem Lesen des Berichts das prepare_sql der Abfrage aus. Es wartet und prüft, ob die Daten für diese Abfrage bereitstehen. Um den Neuaufbau aufzuschieben, bis eine Abfrage ihn benötigt, geben Sie @_invalidate_only=1 ausdrücklich an. Damit werden die Invalidierungen registriert und der Aufruf kehrt zurück. Es wird kein Runner gestartet und bereits ausstehende Arbeit bleibt erhalten.

Um den gesamten Bericht zu prüfen, rufen Sie DML_PREPARE_MAZ für SALES_QUARTERLY mit dem Zeitraum Q1 und @_force_update = 1 auf. Dadurch werden die für diese Anfrage benötigten Monate und das Quartal neu aufgebaut. Wenn Sie nur wissen, dass sich die Quelldaten eines Monats geändert haben, setzen Sie mit refresh bei SALES_MONTHLY an. Eine Aktualisierung nur auf Quartalsebene erkennt keine veralteten Monatscaches, deren Änderungen noch nicht gemeldet wurden.

Für @_match ist exact die Standardeinstellung. Mit like und dem Muster SALES~_% werden Namen mit dem wörtlichen Präfix SALES_ ausgewählt. Das Muster % wählt in diesem Modus alle registrierten Mazes aus. Beide Datumsgrenzen sind eingeschlossen. Wenn beide Datumsangaben fehlen, verarbeitet refresh die vorhandenen Zeiträume und baut nicht den gesamten Kalender vorab auf. Bei einer Verschiebung in einen anderen Monat müssen der alte und der neue Monat abgedeckt sein.

Nach einer Unterbrechung fortfahren #

Für jede Partition wird ein eigener Commit ausgeführt. Schlägt die Verarbeitung einer späteren Partition fehl, bleiben die abgeschlossenen Partitionen erhalten, und die Änderungen an der aktuellen Partition werden zurückgerollt. Ein regulärer prepare-Aufruf kann die bekannten Ziele und Bereiche vervollständigen. Ein erneuter prepare-Aufruf mit force_update=1 startet eine neue erzwungene Aktualisierung.

Wird eine Standardaktualisierung unterbrochen, bleiben die registrierten ausstehenden Arbeiten in STATE gespeichert. Rufen Sie nach Behebung des Fehlers DML_REFRESH_MAZ ohne Parameter auf, oder aktivieren Sie den Runner durch einen späteren prepare- oder refresh-Aufruf. Ein erneuter Standardaktualisierungsaufruf oder ein erneuter Aufruf mit force_update=1 meldet den Aktualisierungsbedarf neu an und kann bereits abgeschlossene Partitionen erneut verarbeiten. Ein refresh-Aufruf ohne Parameter setzt nur ausstehende Arbeiten fort und invalidiert abgeschlossene Partitionen nicht erneut. Schließen Sie nach einem Abbruch oder einer Zeitüberschreitung die physische Verbindung, bevor Sie fortfahren. ROLLBACK allein gibt die Sitzungssperre des Runners nicht frei. Ist die Antwort auf einen Commit verloren gegangen, prüfen Sie zuerst erneut den Status.

Häufige Probleme #

Symptom Prüfung und Vorgehen
Die Quelldaten wurden korrigiert, aber der Bericht zeigt weiterhin alte Werte Prüfen Sie, ob die Quelltransaktion per Commit abgeschlossen wurde, ob die Invalidierung alle Einstiegspunkte und Datumswerte abgedeckt hat und ob für den Bericht anschließend prepare_sql ausgeführt wurde. Wenn Sie nur das nachgelagerte Objekt benachrichtigt haben, prüfen Sie, ob auch das ihm vorgelagerte Objekt invalidiert werden musste.
Prozedur, Ziel oder Parameter @_match wurde nicht gefunden Prüfen Sie, ob Sie mit der Zieldatenbank verbunden sind und ob das für das Modell generierte setup_sql bei der Bereitstellung ausgeführt wurde. Verwenden Sie für exakte Namensangaben die registrierten Maz-Namen. LIKE ist auch ohne Treffer erfolgreich, ändert dann aber nichts. Prüfen Sie vorher, welche Ziele dem Muster entsprechen.
Autocommit wird verlangt Verwenden Sie eine JDBC-Verbindung mit autoCommit=true und ohne explizite oder implizite Transaktion. Senden Sie Invalidierungsaufrufe erst, nachdem die Transaktion zum Schreiben der Quelldaten per Commit abgeschlossen wurde.
Die Invalidierung meldet fehlende, vertauschte oder nicht abgedeckte Datumswerte Geben Sie beide Datumswerte in der richtigen Reihenfolge an und prüfen Sie, ob dbo.DML_CALENDAR jeden Tag im Intervall abdeckt. Wenn ausdrücklich alle materialisierten Bereiche erfasst werden sollen, lassen Sie beide Datumswerte weg.
Berechtigung für den Writer verweigert Lassen Sie von einem Datenbankadministrator prüfen, ob das aufrufende Konto die Invalidierungsprozedur und den Writer jedes betroffenen Maz ausführen darf. Vor der Invalidierung werden alle betroffenen Ziele geprüft. Aufrufe ohne die erforderlichen Berechtigungen werden abgewiesen.
Zeitüberschreitung beim Warten auf eine Sperre oder Verbindungsabbruch während eines Aufrufs Schließen Sie nach einem clientseitigen Abbruch oder einer Zeitüberschreitung die betroffene physische Verbindung. Verwerfen Sie die Verbindung bei Verwendung eines Verbindungspools, damit die Sitzungssperre des Runners freigegeben wird. Rufen Sie nach Behebung des Fehlers DML_REFRESH_MAZ ohne Parameter auf, um die registrierten Arbeiten fortzusetzen. Wenn die Abfragevorbereitung fehlgeschlagen ist, führen Sie prepare_sql vollständig erneut aus. Führen Sie die Abfrage erst aus, wenn data_ready=1 gilt.

Wenn Sie Leseberechtigung für die Statustabelle haben, können Sie die Partitionen wie folgt prüfen:

SELECT materialize, dim_dt, state, COALESCE(last_end_time, created_end_time) AS build_finished_at
FROM dbo.DML_MATERIALIZE_STATE
WHERE materialize IN (N'SALES_QUARTERLY', N'SALES_MONTHLY')
ORDER BY materialize, dim_dt;

state = 0 steht für eine reguläre Invalidierung. state = 3 bedeutet, dass die Partition ungültig ist und eine aktive Aktualisierung aussteht. state = 1 bedeutet, dass ein vollständiges Ergebnis veröffentlicht wurde. Der Erstellungszeitpunkt gibt an, wann der Writer des Maz seine Arbeit abgeschlossen hat. Um festzustellen, ob eine bestimmte Korrektur enthalten ist, prüfen Sie auch die Invalidierungsbenachrichtigung und die anschließende Vorbereitung.

Prüfen Sie das Endergebnis der Übung mit dieser Abfrage der Quelldaten. Q1 ist 205 und Q2 ist 40.

WITH source_rows AS (
    SELECT DATEFROMPARTS(YEAR(dt_month), 3 * (DATEPART(quarter, dt_month) - 1) + 1, 1) AS dt_quarter,
           amount
    FROM dbo.TABLE_SALES
    WHERE dt_month >= '20250101' AND dt_month < '20250701'
)
SELECT dt_quarter, SUM(amount) AS sales
FROM source_rows
GROUP BY dt_quarter
ORDER BY dt_quarter;

Gesamtfortschritt des Runners überwachen #

Installieren Sie die gemeinsame Fortschrittsansicht mit dem generierten setup_sql und fragen Sie sie anschließend wie folgt ab:

SELECT pending_partitions, runner_running, estimated_seconds
FROM dbo.DML_MAZ_PROGRESS;

Die Statistiken der Ansicht beziehen sich bei jeder Abfrage auf die letzten 60 Sekunden. Sie zeigen die derzeit ausstehenden Arbeiten, die Raten, mit denen unterschiedliche Partitionen abgeschlossen beziehungsweise hinzugefügt werden, und die geschätzte Dauer in Sekunden bis zum Abbau der ausstehenden Arbeiten. Eine Partition, die im selben Zeitfenster mehrfach abgeschlossen wird, zählt einmal. Stehen keine Arbeiten aus, beträgt der Schätzwert 0. Er ist NULL, wenn der Runner bei noch ausstehenden Arbeiten zum Stillstand gekommen ist oder den Rückstand nicht abbauen kann, weil mehr Arbeit hinzukommt als abgeschlossen wird. Konten für die Überwachung benötigen die Berechtigung SELECT für die Ansicht.

Die Ansicht zeigt den Gesamtfortschritt. Daraus lässt sich die Bereitschaft dieses Berichts nicht ableiten. Verwenden Sie vor dem Lesen des Berichts das prepare_sql der Berichtsabfrage, um zu warten, bis die Daten bereit sind, und dies zu bestätigen. Die vollständigen Spaltenbeschreibungen, Angaben zu den Besitzern der Laufzeitobjekte und Schritte zur Wiederherstellung finden Sie in den Konventionen für prepare und refresh.
