Keep reusable definitions in the model and presentation choices in the query or reporting layer.

P1. Including presentation logic in DML #

Wrong: Putting FORMAT(...), CONCAT(...), CAST(... AS VARCHAR) in measure formulas. Fix: Remove formatting from .dml. Handle in dashboard/rendering layer.

P2. Including query-only derived columns in DML #

Wrong: Creating measures for calculations that only make sense in one specific query. Fix: Put query-specific expressions in Model Query SQL, not .dml.

P5. Not verifying compiled SQL matches golden SQL #

Wrong: Assuming -c output is correct just because it compiles. Fix: Run both the original SQL and compiled SQL; compare result sets.

P6. Creating one-off measures for filters or query-dimension combinations #

Wrong: sales_north, sales_south, sales_east — or sales_north when WHERE region = 'North' suffices. Fix: One generic measure sales; use WHERE region = 'North' in queries.

P7. Duplicating aggregation formulas #

Wrong: revenue: SUM({amount}) and total_revenue: SUM({amount}). Fix: One atomic measure; reference it everywhere.

SQL accepted by draft conversion #

In the November 2026 trial, --to-dml emitted drafts for standard CAST(... AS type), GROUP BY with CASE, ROW_NUMBER() in a CTE, LIMIT/OFFSET, EXTRACT, DATE_TRUNC, ILIKE, GENERATE_SERIES, NULLS LAST, and EXCEPT. A draft still needs compilation and a result comparison.

Input that failed in the trial Rewrite before conversion
sale_date::date AS d, DATE '2025-01-01' Use CAST(sale_date AS date) AS d or CAST('2025-01-01' AS date).
SUM(amount) FILTER (WHERE paid) Use SUM(CASE WHEN paid THEN amount END).
QUALIFY ROW_NUMBER() ... = 1 or DISTINCT ON Compute ROW_NUMBER() in a CTE with the same partition and ordering. Filter rn = 1 in the outer query.
$$hello$$ Use a single-quoted string, doubling embedded single quotes.
INTERVAL '1 day', LATERAL, STRING_AGG(... ORDER BY ...), or JSON ->> Normalize the expression for the intended parser and dialect or project it from a source view. Verify ordering, NULL behavior and row membership before converting.

After conversion:

  1. Add the entry dialect: for the target database if the draft omits it.
  2. Keep the filename stem and embedded query name the same. If two definitions use the same measure name, keep one definition or rename the query-local calculation and update its references.
  3. Place report period bounds on the query. Keep the source history required by pp, pop or ytd available to the measure.

Lint and strict-compile the edited draft, then compare it with the original SQL on the same data.
