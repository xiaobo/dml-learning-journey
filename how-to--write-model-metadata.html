Write model metadata

Use descriptions to help readers select the correct dataset, population, and measure before they query the model. For interpretation during analysis, see dataset semantics and metric definitions.

Describe each dataset

State what one source row represents and which fields identify it. Explain the business meaning of a headline total, required scope filters, and known time or geography limits.

description: |-
  一行代表一条管道交易明细，transaction_id 标识源记录。
  SUM(出厂价金额) 为管道净额，包含调拨和总仓流转，不代表终端 POS 销售。
  官方 UL 报告使用 是否统计UL = '是'。
  渠道表示购买方侧业务渠道，与卖出方渠道不同。

If two datasets expose seller and buyer perspectives over the same source, describe the different partner_id mappings. Do not imply that the datasets have different source grains unless they do.

Explain columns that affect decisions

Use object form when a column's name does not convey its meaning.

columns:
  Businesschannel:
    description: 购买方侧业务渠道。模型别名为渠道，与卖出方渠道不同。
  是否统计UL:
    description: 官方 UL 报告范围标志。报告和归因分析使用相同筛选。
  去年同期出厂价金额:
    description: 行级去年同期金额。计算同比前检查数据覆盖及缺失值。

Prioritize columns that affect population, grouping, joins, and comparisons. State known limitations as facts about the source. Do not turn a finding from one sample into a permanent property of the column.

Match measure names to their formulas

Use business terms as measure keys. Add a description that states the population, required evaluation dimension, and NULL or zero behavior when those affect interpretation.

If a legacy name misrepresents a formula, rename the canonical measure. Keep an alias only when existing consumers need compatibility. Preserve dataset ownership for atomic definitions.

# Fragment under a dataset's measures mapping.
管道净额:
  description: 管道净额包含调拨和总仓流转，不代表终端 POS 销售。
  formula: SUM({出厂价金额})

活跃购买方数:
  description: 有记录的不同购买方代码数量，包含全部购买方类型。
  formula: DISTINCTCOUNT({购买方代码})

活跃药店数:
  description: 有记录且类型为 Drugstore 的不同购买方代码数量。
  formula: 'DISTINCTCOUNTIF({购买方代码}, {购买方客户类型} = ''Drugstore'')'

Do not use a comment to compensate for a misleading canonical name. Put a durable limitation in description: so tools that read metadata can expose it.

Set internal SQL names when needed

Use abbr: for a stable SQL-compatible internal name. Keep the business key or explicit query alias as the consumer-facing name.

进货额(不含税):
  abbr: SaleAmountNoTax
  type: measure
  dataset: transactions
  description: 不含税的有效进货金额。
  formula: SUM({valid_sale_amount})

Before renaming a measure, inspect formula references, queries, and materialization consumers. An abbr does not by itself make every downstream dependency safe to rename.

Document derived labels and estimates

For a column macro, provide description: and formula: when its meaning requires explanation.

# Fragment under a dataset's column-macros mapping.
购买方渠道:
  description: 购买方侧业务渠道，来源为 Businesschannel。
  formula: '{Businesschannel}'

If a label comes from hardcoded rules, identify the rule and its limits. Distinguish a model-defined calendar label from an official business calendar. If a measure estimates terminal activity from pipeline transactions, state which transaction types it includes.

Verify the metadata with the model

  1. Check that each name, description, and formula describes the same metric.
  2. Check dataset descriptions against the declared source key and current scope.
  3. Inspect compatibility aliases and their consumers.
  4. Lint the changed model.
  5. Strict-compile a consumer query for each changed calculation.
  6. Inspect emitted aliases and output columns.
  7. Run applicable live checks using the CLI guide.

For measure syntax and evaluation dimensions, see Measures. For the full model-and-query workflow, follow Forward analysis.
