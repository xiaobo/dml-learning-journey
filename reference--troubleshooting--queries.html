Query syntax pitfalls

These entries cover SQL and YAML queries. Model Query SQL and YAML queries own the supported syntax.

P8. Forgetting AGG() in aggregation queries

Wrong: SELECT product, sales FROM MODEL GROUP BY product Fix: SELECT product, AGG(sales) FROM MODEL GROUP BY product

P9. Adding redundant alias on AGG()

Wrong: SELECT AGG(sales) as sales Fix: SELECT AGG(sales) — auto-aliases to sales

P10. Using subqueries

Wrong: SELECT * FROM MODEL WHERE sales > (SELECT AVG(sales) FROM MODEL) Fix: Use HAVING with a measure: HAVING AGG(sales) > AGG(avg_sales)

P11. Using JOINs

Wrong: SELECT a.*, b.* FROM MODEL a JOIN MODEL b ON a.id = b.id Fix: Use cross-dataset column-macros or pk(...) lookups in .dml

P12. Missing time context for time modifiers

Wrong: SELECT product, AGG({sales: yoy}) FROM MODEL GROUP BY product (neither a grouped time field nor a time filter)

Rule: Resolve the time context and satisfy macro prerequisites. An explicit grouped time field is clearest; a time filter can also supply the context. Prefer one time grain for readability.

Time-context reference: Time modifiers.

Correct (monthly YoY):

SELECT dt_month, AGG(sales), AGG({sales: yoy}) FROM MODEL GROUP BY dt_month

Correct (YTD at day grain):

SELECT dt_date, AGG(sales, 'ytd') FROM MODEL WHERE dt_date = date(current_date) GROUP BY dt_date

P13. Mixing time granularities

Guidance: Prefer one time grain. The checked build accepts dt_year, dt_month together; acceptance of multiple fields is not a guarantee that every macro combination has the intended context. Inspect the resolved time grain.

P14. Adding unnecessary null filters

Wrong: WHERE customer is not null when not explicitly requested. Fix: Only exclude nulls when the question specifically asks for it.

P15. Using BETWEEN for single periods

Guidance: dt_month = '2024-01-01' clearly selects January. A date interval is valid when that interval is intended; use explicit bounds and check timestamp/end-day semantics.

P16. Time-filter order is a style convention

Both predicate orders compile. Predicate order is a readability choice, not an engine requirement.

P17. Using ORDER BY without need

Wrong: Adding ORDER BY to every query. Fix: Only use ORDER BY for Top N or when the question explicitly asks for ranking.

P18. Manual growth rate calculation

Wrong: DIVIDE(AGG(sales), AGG(sales, 'ya')) - 1 Fix: AGG(sales, 'yoy') — built-in modifier.

P20. Using DISTINCT alone for existence checks

Wrong: SELECT DISTINCT customer FROM MODEL.transactions for "do we have any customers?" Fix: SELECT customer, dt_date, transaction_id FROM MODEL.transactions LIMIT 1 — return specific record.

Category: DML Model Design

P45. Measure in a detail query

Wrong: dataset: DATASET_PRODUCTS on a query that selects total_cost: (a measure). Fix: Remove dataset: for aggregate mode, or drop the measure from the detail query.

P46. Bare column name in aggregate query

Wrong: prod_id: with no dataset: when the column lives on DATASET_PRODUCTS. Fix: prod_id: "{DATASET_PRODUCTS}.prod_id".

P47. Mismatched dimension field names across datasets

Wrong: DATASET_PT uses dimension id; DATASET_MC uses tag_id. Fix: Align to one name (e.g. tag_id) and map warehouse columns in columns: (tag_id: id).

P48. Mapping used as a dimension field in dimension:

Wrong: - f_tag_id: {DATASET_PT}.id under columns: dimension:. Fix: List - f_tag_id only; define f_tag_id: |- … formula separately.

P49. Dimension field under measures:

Wrong: tag_id: with a formula under dataset measures:. Fix: Declare grain under dataset dimension:; use measures only for aggregations.

P50. Complex filter in query filters:

Wrong: EXISTS subquery or multi-field PK chain in query filters:. Fix: Move predicate into the fact dataset's sql: WHERE clause.

P51. PK chaining parameter count mismatch

Wrong: pk(1, tag_id).{DATASET_PRODUCTS}.state when DATASET_PRODUCTS has composite PK (brand_id, tag_id). Fix: pk(brand_id, tag_id).{DATASET_PRODUCTS}.state with all PK columns.

P52. Manual GROUP BY in after:

Wrong: Re-aggregating with group by in after: on a standard measure query. Fix: Let the query block aggregate measures. Omit after: for automatic dimension ordering. When custom ordering/limit requires it, reference {QUERY} and keep the block to presentation (select * from {QUERY} plus ORDER BY/TOP/LIMIT) unless unavoidable custom post-SQL is explicitly documented.

P60. Subquery for MAX date in aggregation query

Wrong: WHERE dt_month = (SELECT MAX(dt_month) FROM MODEL ...) Fix: Hardcode probe month or SELECT MAX(dt_month) FROM MODEL.<dataset> detail query.

P61. Aggregating directly on dataset with GROUP BY

Wrong: SELECT 购买方代码, 品牌, SUM(出厂价金额) FROM MODEL.DATASET_X GROUP BY 购买方代码, 品牌 Symptom: cannot aggregate directly on dataset MODEL.DATASET_X using GROUP BY Fix: Either (a) define measures in model.dml and use FROM MODEL with AGG(), or (b) use inline measures via /** dml ... **/ comment blocks for ad-hoc queries without editing .dml (see Inline measures (/** dml ... **/))
