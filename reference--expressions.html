This page owns reference forms and intrinsic functions. Measure modifiers owns modifier behavior. Model Query SQL owns query grammar and aliases. Functions in examples are expression syntax; emitted SQL depends on the selected dialect.

Reference syntax #

In .dml formulas #

Reference type Syntax Example
Column {column_name} SUM({amount})
Measure {measure_name} DIVIDE({sales}, {count})
Cross-dataset column {DATASET}.column {products}.price
Measure with modifier {measure: modifier} {sales: yoy}
Measure with nested modifiers {measure: {modifier: sub}} {sales: {+d: customer}}

In Model Query SQL #

Reference type Syntax Example
Column (dimension) bare name SELECT product, dt_month
Measure AGG(measure_name) AGG(sales)
Measure with modifier AGG({measure: modifier}) AGG({sales: yoy})
Measure with positional modifier AGG(measure, 'modifier') AGG(sales, 'yoy')

Key rule: {...} braces are for .dml only. In Model Query SQL, use bare names for dimensions and AGG(...) for measures. The only exception: AGG({measure: modifier}) for modifier form.

pk(...) lookups #

Cross-dataset column lookups in .dml formulas:

# Single PK
formula: 'SUM({amount} * pk(customer_id).{customers}.tier_discount)'

# Composite PK
formula: 'SUM(pk(brand_id, tag_id).{DATASET_PRODUCTS}.state)'

Supply one expression per target dimension field, in declaration order. pk(1, tag_id) has the correct arity for [brand_id, tag_id]; it deliberately fixes brand_id to 1. Whether that lookup is correct depends on the intended key and source uniqueness.

Functions #

Core aggregation functions #

Valid in both .dml and Model Query SQL. In .dml, they aggregate raw columns (SUM({amount})) or drill-down measures (SUM({sales: {+d: product}})). In Model Query SQL, they aggregate drill-down measures only (e.g. SUM(AGG({sales: {+d: product}})) sums per-product sales into a total). Use AGG(measure) alone for a plain measure reference.

Function Syntax Description
SUM SUM({column}) Sum
COUNT COUNT({column}) Count non-null
COUNT(DISTINCT ...) COUNT(DISTINCT {column}) Count distinct
MAX MAX({column}) Maximum
MIN MIN({column}) Minimum
AVG AVG({column}) Average

DML-specific functions #

The context column identifies where a function can appear within a valid measure expression. Model Query SQL still requires measure aggregation through AGG(...); these functions do not permit raw-column aggregation in SELECT.

Function Syntax Context Description
AGG() AGG(measure) Model Query SQL only References a measure in queries (not an aggregation function)
DIVIDE() DIVIDE({num}, {den}) Both Safe division (returns NULL on divide-by-zero)
DISTINCTCOUNT() DISTINCTCOUNT({column}) Both Count distinct values
SUMIF SUMIF({val}, {condition}) Both Conditional sum
COUNTIF COUNTIF({condition}) / COUNTIF({val}, {condition}) Both Matching rows / matching non-null values
AVGIF AVGIF({val}, {condition}) Both Conditional average
MAXIF MAXIF({val}, {condition}) Both Conditional maximum
MINIF MINIF({val}, {condition}) Both Conditional minimum
DISTINCTCOUNTIF DISTINCTCOUNTIF({val}, {condition}) Both Conditional distinct count

Conditional aggregation examples:

# In .dml
completed_sales:
    type: measure
    formula: SUMIF({amount}, {status} = 'completed')

high_value_customers:
    type: measure
    formula: 'DISTINCTCOUNTIF({customer_id}, {sales: {+d: customer_id}} > 1000)'

-- In Model Query SQL (modifier form)
SELECT AGG(sales, '+f', region = 'North') FROM MODEL

Conditional and utility functions #

Function Syntax Description
IIF IIF(condition, true_val, false_val) Inline conditional
ISNULL / IFNULL / COALESCE ISNULL({expr}, default) Null coalescing
NULLIF NULLIF({a}, {b}) Return NULL if a = b

Utility functions use the SQL expression layer. They are valid formula syntax, but they are not canonical DML intrinsic symbols. The DML function catalog reserves that identity for DML-owned functions such as AGG, DIVIDE, and SUMIF.

An outermost null-coalescing formula with a literal fallback activates missing-row fill at that measure's use sites.

daily_sales:
    type: measure
    formula: SUM(ISNULL({sales: {+d: dt_date}}, 0))

Date functions (SQLite dialect) #

Function Syntax Description
date() date(current_date) Current date
date(current_date, 'start of month') — First day of current month
date(current_date, 'start of month', '-1 month') — First day of last month
date(current_date, 'start of year') — First day of current year
date(current_date, '-N days') — N days ago

Dialect note: Match your date functions to the target dialect. DML supports a SQLite-style date expression language and lowers supported forms to the selected dialect. Inspect the emitted SQL; these expressions are not a promise that the target database accepts the same text natively.

Modifier syntax in Model Query SQL #

Two equivalent forms in Model Query SQL:

Form Syntax Example
Positional AGG(measure, 'mod1', 'mod2') AGG(sales, 'yoy')
Brace AGG({measure: mod}) AGG({sales: yoy})

Alias rules: See Model Query alias rules for the canonical alias rules table (AGG(sales) auto-aliases; AGG({sales: yoy}) requires AS).

Runtime variables #

Variable Context Meaning
{dim_dt} Time-aware expressions and modifiers Resolved standard time field for the current evaluation context
{measure} fn-macro formula The calling measure that the macro wraps
{dt_date}, {dt_week}, {dt_month}, {dt_quarter}, {dt_year} Standard time references The named standard time field

Time context defines resolution and period conventions. Define macros covers macro declarations and variable use.

Database-defined scalar functions #

Scalar calls can be retained in generated SQL, including inside an atomic measure and around an aggregated measure result. DML owns the measure context; the target database owns the function implementation and availability. See verified custom modifiers and database functions for a working example, evaluation-stage differences and validation requirements. This is not a blanket claim for aggregate or table-valued UDFs.
