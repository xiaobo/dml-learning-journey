This independent example models profitability. It complements the sales model in the interactive journey. Watch the overview animation to see how the definitions connect.

Agree the definition #

Business and data teams agree what net revenue and sales cost include. The model names these calculations, derives gross profit, and divides profit by revenue to obtain gross margin. DML and DMX capture the rules; the compiler generates SQL for the database. Together they can form the calculation core of an analytical semantic layer.

The model #

The logical dataset is FACT_PROFITABILITY; its physical source is TABLE_PROFITABILITY. Source field names differ from measure names so references are unambiguous. The complete source key is [id]. Use decimal types for revenue_amount and cost_amount in the physical table; CSV does not carry SQL column types, and integer division would lose the fractional margin.

FACT_PROFITABILITY:
  type: dataset
  table: TABLE_PROFITABILITY
  dimension: [id]
  columns:
    id:
    region:
    dt_month:
    revenue_amount:
    cost_amount:
  measures:
    net_revenue: SUM({revenue_amount})
    sales_cost: SUM({cost_amount})

gross_profit:
  type: measure
  formula: '{net_revenue} - {sales_cost}'

gross_margin:
  type: measure
  formula: 'DIVIDE({gross_profit}, {net_revenue})'

gross_margin_ytd:
  type: measure
  formula: '{gross_margin: ytd}'

gross_margin_prior_ytd:
  type: measure
  formula: '{gross_margin: {ytd, ya}}'

margin_change_pp:
  type: measure
  formula: '100 * ({gross_margin_ytd} - {gross_margin_prior_ytd})'

Change the context #

For North in February 2025, revenue is 300 and cost is 240, giving a 20% margin. January revenue is 100 and cost is 60, giving a 40% margin. Year-to-date revenue is 400 and cost is 300: the cumulative margin is 25%, not the 30% simple average of monthly margins.

Apply the time modifier directly to the named ratio: formula: '{gross_margin: ytd}'. This recalculates gross margin over the cumulative period from its revenue and cost dependencies; it does not sum or average monthly percentages. Prior-year YTD uses '{gross_margin: {ytd, ya}}'.

SELECT region, dt_month, AGG(gross_margin_ytd)
FROM MODEL
WHERE dt_month = '2025-02-01'
GROUP BY region, dt_month

Compare the same period #

North's January–February 2024 revenue is 200 and cost is 160, giving a 20% cumulative margin. The current cumulative margin of 25% is 5 percentage points higher. Relative growth would be 25%; it is a different calculation and is not the displayed difference.

SELECT region, dt_month, AGG(gross_margin_ytd), AGG(gross_margin_prior_ytd), AGG(margin_change_pp)
FROM MODEL
WHERE dt_month = '2025-02-01'
GROUP BY region, dt_month

Inspect the evidence #

The compiler record includes the executable identity, exact queries, process exits, statuses, diagnostics and generated SQL. The three checked queries pass strict compilation. Inspection confirms that the cumulative branches sum revenue and cost before division; the prior-year branch shifts the cumulative range by one year.

These observations cover this example and compiler build. A separate DuckDB execution check of these short formulas passed strict compilation and source-key validation. Independent SQL confirmed February YTD margins of 25% for North and 33⅓% for South, with prior-year YTD of 20% for both. This does not establish SQL Server execution parity. The browser independently calculates the invented rows; it does not execute DML. A zero revenue denominator produces NULL, and a missing prior period remains missing rather than becoming a fabricated zero.
