DML 理念与场景

DML的核心概念、设计哲学与适用场景。
用途：对外叙述、新人 onboarding、产品与工程对齐「DML 是什么 / 不是什么」。

1. 一句话定位

DML 把「指标是什么意思」和「查询在数仓里怎么正确执行」绑成一份可版本化的代码资产，供人、BI 和 Agent 统一消费。

问题域 Palantir Ontology DML
核心问句 组织如何在业务对象上决策并行动？ 组织如何稳定定义、计算、解释业务数字？
闭环类型 观察 → 决策 → 行动 → 写回源系统 定义 → 编译 → 查数 → 解释变化

DML 不是「小 Palantir」，而是语义执行基础设施（Semantic Execution Layer）：在客户已有数仓之上，承担指标语义 + 查询编译 + 多终端消费。

2. 核心概念

2.1 概念总览

概念 含义 与 Ontology 的近似关系
Dataset（数据集） 业务实体绑定物理表，声明一个 dimension 与若干列 Object 的分析切片（非可操作对象）
Measure（指标） 可复用度量，分 atomic（绑定 dataset）与 composite（引用其他 measure） 常对应属性聚合或 KPI 定义
Dimension field（维度字段） 一个有名称的 DML 字段 构成 dimension 的字段
Dimension（维度） 由一个或多个 dimension fields 组成的列表；按上下文承担 dataset、evaluation、query 或 materialization 角色；measure dimensions: 包含 allowed dimensions 声明身份、计算、分组或输出 key
Grain（行粒度） 一行代表什么；仅在比较粗细、兼容性或 fan-out 时需要 说明不同 dimension 上下文之间的行语义
DMX（指标表达式） 表达式语言：{ref}、修饰符、pk()、{Dataset}.col 等，支持跨数据集关联（凡 format: formula 处均可写） 指标计算与跨集引用子语言
Materialize（物化） 预聚合层 / 存储过程 语义模型与物理性能的桥梁
Query（模型查询） 两种等价语法：type: query（DML format）与 Model Query SQL（.sql） 消费层；语义相同
Compile & Execute dmlc 编译为方言 SQL，经 JDBC/MCP 执行 DML 的「运行时」是编译器 + 执行器

2.2 两层结构 + DMX

① 模型定义（.dml YAML）  →  datasets（含 columns）、measures、materialize、dt/fn-macros
② 模型查询（两种等价语法）  →  type: query（DML format）  ⇔  Model Query SQL（.sql）
   DMX 贯穿 ① 与 ② — 表达式语言：{ref}、修饰符、pk()、{Dataset}.col

分离原则： 测什么（建模）与 查什么（消费）分开；建模与查询均共享 DMX。
同一笔模型查询用 YAML 或 SQL 书写，编译语义等价（见 Model Query SQL）。

语言细节见 DML, DMX, and Model Query（含 DMX 概述、grain、system variables）。

2.3 Measure：atomic 与 composite

Measure 是单一领域类型（type: measure），按是否绑定 dataset 分为 atomic（绑定 dataset，使用列）与 composite（无 dataset:，引用其他 measure）两类。

建模纪律： 先 atomic 后 composite；不重复 SUM()；composite 不写 dataset:（pitfall P39）。

完整定义、示例与 dimensions: 约束见 Measure declarations。

2.3.1 Dataset 列：column 与 calculated column

类型 YAML 含义 IDE hover
column 产品名称:（无表达式） 直接引用底层表列；编译器称 direct reference column
calculated column 净额: amount - discount 或多行块 带公式/映射的派生列 calculated column

2.4 跨数据集引用（DMX 语法）

pk()、{Dataset}.column 是 DMX 公式语法，可用于一切 format: formula 处（dataset 列、measure 公式、column-macros、query 列/filter、materialize 列）。

# dataset 列 — DMX
brand_name: pk({brand_id}).BASE_DICT_ITEM(dict_item_id).item_name

# column-macros — 向 dataset 追加列，非独立领域对象
column-macros:
    DATASET_SALES:
        客户城市: '{DATASET_CUSTOMER}.city'

完整 DMX 语法（引用、修饰符、函数）见 Measure modifiers。

与 Palantir Link Type 的差异：DMX 链是可编译的 join 表达式；Palantir 是可浏览、可治理的图边 + 应用 API。pk() 解决键对齐后的关联，不替代跨系统实体解析（golden record）。

3. 设计哲学（五条信念）

3.1 语义必须可执行，不能只可描述

指标若不能编译为数仓 SQL、不能经 JDBC/MCP 消费，就只是文档。
反对「昂贵可视化」：高成本建模却没有信任、解释、测试（参见对比研究中 Palantir 社区 #6703「只读镜像」失败模式）。

3.2 像代码一样治理语义

Git、PR、LSP（lint / completion / rename）、dml_schema.yaml 校验。
按领域或可信状态拆分为多个 .dml，由入口文件 includes 组合——certified / preview 用不同根模型切换。
语义是工程资产，不是一次性 GUI 配置——相对 Palantir 用户苦求的 IaC，这是 DML 的刻意优势。

3.3 Dimension 在各执行阶段的作用

DML 在不同语法位置使用 dimension 表达不同契约：

术语 声明位置 含义
Dataset dimension dataset.dimension[] 声明源行身份；完整 dimension 的值组合必须在被消费的数据上标识一行
Evaluation dimension measure 公式 + 修饰符 一个 measure reference 在哪个 dimension 上计算
Query dimension GROUP BY / columns: dimension: 本次分析使用哪个 dimension 分组
Materialization dimension materialize dimension: 物化关系的输出分组 / key
Allowed dimensions measure dimensions: 多个可选的有效 dimension；每个内层列表是一个 dimension，不声明 dataset 身份或 query 分组

Dimension 决定所在上下文的 grain，也就是一行代表什么。例如，dataset dimension [ledger_entry_id] 声明 ledger-entry grain；query dimension [account, dt_month] 由两个 dimension fields 组成，产生更粗的月度账户 grain。

Measure 是聚合定义（如 SUM({amount})）。一个 measure reference 的 evaluation dimension 由 query dimension、公式和修饰符共同决定。Measure 可以用 dimensions: 限制 allowed dimensions；未设置时，可在 dataset 能力范围内的兼容 query dimension 上计算。

销售额:
    type: measure
    dataset: Sales
  # dimensions 未写 → 由 query dimension 和公式/修饰符决定 evaluation dimension
    formula: SUM({出厂价金额})

仅按产品可查的毛利:
    type: measure
    dataset: Sales
    formula: SUM({毛利})
    dimensions:
      - [product_id]   # one allowed dimension

DML 会根据 query dimension 先聚合各 dataset，避免典型的“先一对多 join，后聚合”fan-out。这一保证以模型契约成立为前提：编译器信任 dataset dimension: 和 pk(...) 匹配唯一性。用 validateOnly 在目标连接上检查完整 dataset dimension 的唯一性；失败时修正 dimension 声明、source key/ranges 或源数据，而不是在编译 SQL 外加 DISTINCT / GROUP BY。

3.4 复杂派生留在模型里

同比/环比、比率、多阶段聚合、快照 vs 流量、财务月——应留在 .dml，不散落到 BI calculated field、应用代码或临时 SQL。
模型是权威，不是遗留系统的只读镜像。

3.5 Agent 是平等消费者

MCP run_query、structuredContent、next.actions、explain_change，以及模型内 description / Agent playbook——Agent 与分析师走同一语义入口，不绕路裸 SQL。

3.6 边界信念（同样重要）

  • 不做写回、Action、现场运营 UI —— 属 Ontology kinetic 层。
  • 不替代数据集成、MDM、血缘平台 —— 但消费其产出（干净表、对齐的键）用于 pk() 与 datasets。
  • Context Layer（新鲜度、关账状态、实体解析、策略）与语义层分工：DML 负责算对；敢不敢用、该用哪口径，需元数据与治理外挂或演进。
  • 可信分层（现行）：按领域或可信状态（certified / preview / experimental）拆多个 .dml 文件，入口模型用 includes 组合可见指标集；生产与预览通过不同 --model / MCP model 切换。

DML 在栈中的角色： 介于物理数仓与各类分析消费者之间的语义 IR + 编译执行层。模型定义承载可复用指标语义（含物化策略）；模型查询表达「查什么」——可来自业务需求或遗留 SQL 改写；编译器融合二者、自动选路物化表，下推为数仓方言 SQL 后供人、BI 与 Agent 统一消费。

5. 适用场景

5.1 强匹配 ✅

场景 典型痛点 DML 提供什么 社区验证
统一指标平台 同一 KPI 在 SQL、BI、API、Agent 各写一遍 一份 .dml，多端编译 三社区共识：口径发散是头号痛点
复杂数仓 + 多层聚合 不知查日表还是月表 materialize + 自动选路 —
经营 / 财务分析 同比、财务月、期末/累计口径不一 DMX 修饰符与时间语义 日语社区：KPI 定義の未整理が精度低下原因
口径争议 / 定义可追溯 「这个数按什么定义算的？」「preview 还是正式？」 Git 模型、description、includes 分入口 + 编译 SQL（可审计公式与执行路径） 三社区共识：口径不透明导致不信任
变化归因 「为什么比上月多了/少了？」「哪个维度贡献最大？」 explain_change（方差分解、维度 driver、可选 PVM/LMDI） 三社区共识：「为什么变了」是 2026 前沿
Analytics Engineering 建仓后仍需语义层与 API 语义与执行一体（dmlc） —
AI 数据分析 Agent 幻觉列名、口径漂移 MCP + 模型 metadata 三社区共识：语义层是 Agent 必要条件
嵌入式 / 多租户分析 产品内嵌报表 jdbc:dmlc: + connections —
Agent 自助分析（指标定义 × 查询） ChatBI「单轮问答」；JOIN 曖昧さ；LLM 手写日期出错 公式自由 + 零 JOIN 查询 + 14+ 修饰符 + 编译校验 三社区验证：16.7%→83% 精度提升（经语义层）

5.2 可用但需补齐 ⚠️

场景 缺口 建议
多源实体未对齐 pk() 需键已对齐 先 MDM 或接 Context Layer
关账 / 新鲜度敏感 语义层不表达 pipeline 状态 metadata + catalog；Agent 先 probe
认证指标 / 运行时权限 字段级 publishStatus 在路线图 现行： 按 certified/preview 等拆 .dml 文件，入口模型用 includes 组合；MCP/CLI 指定不同 --model 切换可信边界

5.3 弱匹配 ❌

场景 原因
跨系统 写回（工单、调度、审批） 无 Action / kinetic 层
非技术用户的 对象探索 + 点选运营 无 Object Explorer 类 UI
实体解析为主（三系统同一客户） 非 golden record 平台
单表简单 BI 过重；直连即可
仅指标文档、不执行 用 glossary / catalog 即可

6. 与 Palantir Ontology 对照

维度 Palantir Ontology DML
隐喻 组织 API + 操作系统 分析 编译器 + 语义 IR
核心动词 create / update / act define / compile / query / explain
关系 Link Type（可浏览、可权限） pk() / {Dataset}.col（可编译）
治理 运行时 RBAC、Ontology 分支 Git + LSP +（演进）认证发布
典型用户 运营决策者、FDE、平台团队 数据平台、分析工程、Agent 集成
与遗留系统 渐进吸收 + Action 写回 语义权威 + 编译到现有数仓

叠用关系： 数仓 / Ontology 产出干净表与对齐键 → DML 在其上建可治理指标层与 Agent 查数面。二者互补，非替代。

7. 对外叙述模板

电梯稿（中文）

DML 是企业指标与查询的语义执行层。用开放 YAML 定义数据集、指标和物化策略，由 dmlc 编译到 Snowflake、Postgres、DuckDB 等，经 JDBC 与 MCP 为 BI 与 AI Agent 提供统一口径。它不在 ERP 里下单或改工单，但让「收入、同比、归因」在全公司只算一种、说得清、测得住。

与 Ontology 的一句话区分

Ontology 管名词怎么运营；DML 管数字怎么定义与执行。

英文（对外）

DML is a versioned semantic execution layer for metrics: define once in YAML, compile to your warehouse, consume via JDBC and MCP. It closes the read-analytics loop (define → query → explain), not the operational loop (observe → act → write back).
