Grain and join pitfalls

These entries cover evaluation grain, classifier attachment, windows, source membership, and join behavior. Join NULL equality owns equality rules.

Filter placement errors

Symptoms: [filters]: not supported, cannot derive from dimension, referred column … is undefined

Cause: Predicates left in the wrong layer after --to-dml — filters: on a dataset (the schema rejects filters: on datasets entirely), dim scoping duplicated in fact sql:, or query filter shorthand on cross-dataset attributes.

Fix: Classify each predicate by semantic scope (Filter placement hierarchy):

Symptom Move to
[dataset …] [filters]: not supported Query filters:, measure formula, or sql: WHERE (datasets don't support filters: at all)
Lifecycle/attribute predicate repeated in every fact branch Query filters: only when it is report-varying; keep a row-removing representation when it defines permanent population
Numeric/link predicate in fact sql: WHERE Use an intermediate metric gate only after proving rejected-only groups, sibling metrics, joins/windows, and absent-vs-present-NULL semantics
referred column {DATASET}.col is undefined in query filter String form: "{DATASET}.col = value":
Two-element list dt_date: ['2024-01-01', '2025-12-31'] returns only 2 days Bare list compiles to IN (...) exact match, not a range. Use dt_date: { range: ['2024-01-01', '2025-12-31'] } for inclusive intervals
Branch-specific date window Declare dt_date on that dataset; query filters: dt_date: range: [...]

Alternative lookup eligibility can strengthen joins

An eligibility rule such as “matches the target dimension or, failing that, an indirect dimension” uses two optional relationships. If the derived flag is placed in query filters:, compiled SQL may make one lookup required (INNER JOIN) or lower the AND/OR expression in a way that no longer preserves fallback semantics.

Prefer this shape:

target_state: pk({snapshot_month}, {customer_id}).{TARGET_CUSTOMER}.state
customer_is_eligible: |-
  iif({target_state} = 1, 1,
    iif(pk({customer_id}).{INDIRECT_CUSTOMER}.customer_id is not null, 1, 0))
included_amount: iif({customer_is_eligible} = 1, {amount}, null)

measures:
  amount: SUM({included_amount})

Then inspect the generated SQL: both lookups must remain LEFT JOIN, the fallback must remain inside CASE, and any output-group guard should reuse a selected primary measure (HAVING AGG(amount) is not null) so it does not leak an extra hidden column into the result. Treat non-unique keys and target/indirect overlap as diagnostics; DML relationships should not silently reproduce accidental fanout.

This section records compiler-facing behavior. SQL-migration acceptance, multiplicity classification, and evidence gates are owned by sql-to-dml's native-first contract; do not maintain a second policy here.

P43. {dimension: [...]} vs {-d: dim_dt} (different SQL shape)

Wrong: Using {-d: dim_dt} when golden SQL uses a separate GROUP BY CTE at reduced grain. Fix: Match structure: {dimension: [cols]} forces a separate aggregation CTE; {-d: dim_dt} uses window OVER (PARTITION BY …). See P44 and P45.

P44. Window share vs {-d: dim}

Wrong: Stocking draft divide({m}, {m_minus_dim_X}) from --to-dml as final business DML. Fix: Use divide({m}*1.0, {m: {-d: dim}}) in query columns: or measures. Migration detail: sql-to-dml curation {-df:} ratio pattern.

Equivalent to Model Query SQL; YAML-specific pitfalls. Full rules: YAML query declarations.

P62. Treating measure dimensions: as dataset identity or query grouping

Symptom: dimensions: [[region]] is written on a measure expecting the query output to be grouped by region (like dataset dimension:); the query instead compiles with no such grouping or fails with a different query dimension. Wrong mental model: measure dimensions: declares dataset row identity or drives query grouping. Correct mental model: measure dimensions: contains allowed dimensions. Each inner list is one dimension; the outer list contains alternatives. Dataset identity belongs to dataset dimension:; grouping belongs to query GROUP BY / columns.dimension:. Fix: Remove measure dimensions: unless the metric truly requires those allowed dimensions; put result grouping in the query (GROUP BY / columns.dimension:).

# Wrong: expecting dimensions: to produce GROUP BY region
sales:
    type: measure
    dataset: transactions
    formula: SUM({amount})
    dimensions:
        - [region]

# Right: no dimensions: lock; grouping lives in the query
sales:
    type: measure
    dataset: transactions
    formula: SUM({amount})
# SELECT region, AGG(sales) FROM MODEL GROUP BY region

See the dimension-role contract in dimension roles.

P64. materialize: true on a measure

Symptom: ERROR error during processing [ref null]: undefined modifier 'materialize' at compile time; the measure is silently dropped (0 measure(s) processed). Wrong: adding materialize: true to a measure definition, expecting the compiler to pre-aggregate it. There is no measure-level materialize flag (verified with dmlc -c, dmlc 0.3.16). Fix: declare materialization with a top-level type: materialize object (parameters: + dimension: + measures:), or dataset-level materialize: <name> — never on a measure. See Materialize definition (type: materialize) and materialization examples.

# Wrong
sales:
    type: measure
    dataset: transactions
    formula: SUM({amount})
    materialize: true   # ← undefined modifier 'materialize'

# Right
DWS_SALES:
    type: materialize
    parameters:
        dt_date: date
    dimension: [dt_date, product]
    measures: [sales]

P66. Measure-as-dimension without an explicit entity key

Symptom: compilation requires an explicit +d or dimension: entity key. Prefer +d and read the release limitations before using the replacement-dimension form. Wrong: using a bare measure and expecting another output measure to supply or imply its entity grain. Fix: declare the complete entity key at the dimension use site. Inline scalar wrappers are valid when their measure inputs carry the explicit key. See Measure-as-dimension.

# Wrong
dimension:
    - payment_day

# Right, inline scalar
dimension:
    - payment_day: 'cast({authorization_ts: {+d: payment_id}} as date)'

P67. Incompatible or dependent measure-derived dimensions

Symptom: compilation reports incompatible classification keys or a dependency between labels. Wrong: one label uses {+d: store_id} while another uses {+d: customer_id}, or one label refers to another label declared by the same query. Fix: make independent labels use the same complete entity key. Key order may differ. Model a separate relation or reusable business measure when labels truly live at different grains.

P68. Output measure cannot be rolled up from the classification grain

Symptom: compilation reports missing aggregation or that reaggregation is impossible. Wrong: expose {sales: {+d: store_id}} directly as an output, sum already-computed distinct counts, or average ratios without defining the intended weighting. Fix: surround a finer-grain reference with the intended aggregation, such as SUM({sales: {+d: store_id}}). For ratios, roll up components and recompute. For distinct, median, percentile, and similar measures, preserve suitable inputs/states or define a separate supported measure; otherwise accept the compile error.

P69. Fine-grain WHERE hung on coarse query filters:

Symptom: CTE aggregates at (G) (e.g. product×region), filters (cnt > 3), then SUMs to (Q) (e.g. product). Draft/--to-dml emits query dimension (Q) only with filters: "cnt > 3" and SUM({total: {+d: region}}). Compile/fusion may turn this into product-level HAVING COUNT(1) > 3 — wrong population.

Wrong:

filters:
  "cnt > 3":                 # cnt is not defined at product-only grain
columns:
  dimension: [product]
  grand_total: 'SUM({total: {+d: region}})'

Also wrong: SUM({total: {+d: region, +f: '{cnt} > 3'}}) uses an aggregate measure in an input predicate. The diagnostic refers to the predicate, not a general ban on applying +f to measure references. See the capability table.

Fix — filter inside the roll-up at the shared fine grain:

grand_total: |-
  SUMIF({total: {+d: region}}, {cnt: {+d: region}} > 3)
# No accepted fine rows -> NULL; ELSE 0 would change that result.

Keep query filters: for report/HAVING scope only. See Multi-level aggregation with +da.

P70. OVER on an atomic measure

Symptom: window functions are not allowed in atomic measures, or (older binaries) exit 0 with illegal SUM(…) OVER (…) … GROUP BY missing partition columns.

Wrong:

measures:
  净购进量: 'SUM({qty}) over (partition by {store_id}, {prod_id})'

Fix: window placement — detail OVER under columns:, then atomic agg:

columns:
  net_qty: 'SUM({qty}) over (partition by {store_id}, {prod_id})'
measures:
  sum_net_qty: 'SUM({net_qty})'

Post-GROUP-BY rank/share stays a composite (no dataset:) with {-d:} / {-df:}. Contract: Window placement.

P71. Bare {col} in measure PARTITION BY

Symptom: … reference is not allowed in PARTITION BY / Hint about {dimension:} or {-d:}.

Wrong (on a measure): SUM({total}) over (partition by {product}). Fix:

  • Detail row window → move to columns: and keep bare {product} there.
  • Post-aggregation window → partition by {-d: region} or {dimension: product} on a composite measure.

Do not put {-d:} under dataset columns: for a detail window — that branch uses bare column refs.

Verified on dmlc 0.3.16 (basket-affinity migration, dual product roles). These compile clean and silently change semantics — always inspect the emitted ON clauses.

P72. Two grain fields aliasing one column mis-anchor cross-dataset rollups

Symptom: strict compile passes, diagnostics empty, but a ratio is wrong — e.g. lift denominator is left_count * left_count instead of left_count * right_count.

Wrong: a dataset exposes two fields backed by one physical column (left_product_id: '{product_id}', right_product_id: '{product_id}'), and a second-role rollup {sold_baskets: {-df: [left_product_id]}} (or {dimension: [month, store, right_product_id]}) is expected to join on right_product_id. The compiler re-aliases the reduced temp's key and joins it on the first role's key (support.product = pair.left_product_id).

Fix: look up each role with pk() into a sql: dataset that groups the source at (shared dims, product_id) with a declared dimension: (P77); pk() keys are positional and explicit, so left and right cannot collapse. Or keep -df rollups only at grains with no alias collision. Verify in compiled SQL: two separate joins, … product_id = t.left_product_id and … product_id = t.right_product_id.

P73. -df rollup composites emit partner-only rows — and can fabricate key values

Symptom: a measure rolled up from another dataset compiles to a FULL OUTER JOIN composite; rows that exist only in the rolled-up partner emit output rows. The partner temp may project max(<col>) fillers for grain fields it lacks, so an orphan (month, store, product) row can surface as left = right = product — a fabricated self-pair, not just NULLs.

Fix: keep a selected primary measure that is NULL on partner-only rows and guard the query with a formula-keyed filter:

filters:
    '{pair_basket_count} is not null':      # formula as key, empty value

This compiles to a join-back WHERE <primary> IS NOT NULL — and the proven presence also reduces the emitted FULL OUTER JOIN to LEFT JOIN. Judge the final join type in emitted SQL, not the composition template. Prove the contract first: a valid primary group must never have a NULL primary measure, and the guard only holds when partner-only rows lack it. (Complements Dimension modifiersb.)

P74. Two table: datasets on one physical table — merge quirks and silent -df grain loss

Symptom: warn during processing [dataset B]: similar dataset(s) [A] exist, consolidate? — then, if the two datasets' column sets differ, skip dimension column <f> for measure <m> which does not exist in dataset <A> and the rollup silently aggregates at a coarser grain (e.g. pk(store_id) instead of pk(store_id, left_id)).

Verified (dmlc 0.3.16): two table: datasets on one table do not crash per se — the minimal symmetric case compiles, and a role-playing second dataset even anchors -df correctly (right_id = t1.right_id). The datasets are merged into one #TEMP via self-join on the pk. But adding a column to only one side makes the merge drop the other dataset's alias fields from -df resolution. (An earlier "duplicate table: → NPE" report was mis-attributed; the crash was P75's filter shape.)

Fix: prefer one table: dataset per physical table with alias columns. If you must role-play, keep the column sets identical and verify every rollup temp's pk(...) in emitted SQL — a warning here is a semantic error, not a nit.

P75. Measure guard filters in query filters: — shape and failure mode

Right: '{measure} is not null': — the entire formula is the key, value empty. This is the way to prune FOJ orphan rows at the query grain.

Wrong: my_measure: {condition: '...'} → schema error (condition is not a filter property). my_measure: '<expr>' treats the key as a column name; when it resolves to a measure, Query.treat_filters can NPE instead of emitting a diagnostic.

Fix: use the bare-formula key and make sure the referenced measure resolves at the query grain; an unresolvable measure reference fails with NPE, not a readable error.

P76. -df / -d arguments are declared grain field names, not source columns

Symptom: column(s) [x] has been specified as -d/-df, but not in dimension [...] after renaming a query dimension through a binding (columns.dimension: [..., new_name: '{col}']).

Cause: the binding synthesizes an internal field (new_name__<query>); modifiers remove fields by their grain names, and the underlying column name no longer exists in the grain.

Fix: pass the declared grain field names to -df / -d / dimension:. If a field must stay removable by name, keep it on the dataset under that name.

P77. pk() into an aggregate relation: sql: target + dataset: on the wrapper

Symptom: dataset must be specified when aggregate non-measure column, did you mean <SupportDataset>? on MAX(pk(...).{Support}.col).

Rules:

  • pk() targets datasets (or the raw TABLE(pk_cols) form) — a measure cannot be a pk() target. An aggregate lookup value (e.g. count(distinct …) at a coarser grain) therefore needs a sql: dataset with a declared dimension:; it compiles to an indexed temp that joins like any dimension.
  • The wrapping aggregate measure iterates rows of the consuming dataset — set dataset: to it (dataset: BasketProductPair, not the support dataset).
  • A golden INNER JOIN on a guaranteed-match support lowers to LEFT JOIN; acceptable only when the lookup keys are produced by the same population — note the reasoning in the escape ledger.

P79. Same-dimension +d with -d / -df

Wrong: {销量: {+d: 门店, -d: 门店}} or {销量: {+d: 门店, -df: 门店}} accepted and rewritten to bare {销量} or {-f: 门店}.

Why: no unique silent reading; canceling hides typos; for AVG the fine stage differs from a bare reference; when the output grain already contains the field, -df ≠ -f.

Fix: express one intended evaluation stage. Use a bare reference, an explicit fine-grain reference with an outer aggregate, or a removal modifier. Different fields can still coexist. The 2026-10-16 build accepts the checked conflicts without diagnostics and repeats regional totals before an outer sum. This violates the required rejection contract. See modifier composition and release evidence.

P80. -f / -df drops a non-grain query filter from the report row set

Wrong: query filter {store_id}=1 while a measure uses {-f: store_id} and store_id is not in the output grain → filter silently omitted → FOJ partner rows from the unfiltered arm appear.

Fix: -f only removes the filter from measure evaluation; query filters still define population. When the blocked filter cannot reference an output column, constrain rows with a correlated EXISTS / semi-join. Do not change grouping via -f alone.

P81. Cross-grain dimension: time replacement without calendar broadcast

Wrong: {销量: {dimension: [dt_quarter]}} on a dt_month query becomes a single scalar attach or fails to resolve dt_quarter from a month CTE.

Fix: evaluate at quarter grain (calendar bridge from month/date), then broadcast the quarter total onto each month row in that quarter (nullpk(pk(dt_month).CAL.dt_quarter) pattern). Additive SUM may re-aggregate months; non-additive measures need fact-level coarse grain.

P78. A sql: escape must bake its own population/window predicates

Symptom: query dt_* range filters do not push inside a sql: block's text — they land on the outer WHERE of the compiled derived temp. Inside a self-join escape an unbounded inner leg silently widens the population (e.g. right-leg rows outside the report window form pairs).

Fix: bake permanent population predicates (line_status = 'SOLD') and symmetric window bounds into the escape's inner query so every leg/branch sees identical eligibility; let query filters: handle report scope on the outer keys. And when the escape reads a table:-owned physical table, reference from {Dataset} (P22b) — never the raw table name.
