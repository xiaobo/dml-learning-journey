Window placement

A window calculation depends on the rows available at its evaluation stage. Detail windows operate before a later measure aggregate. Composite windows operate on aggregated measure results.

Supported placements

Calculation Placement Input rows
Attribute of each source row Calculated column under dataset columns: Detail rows
Rank or share of grouped measures Composite formula with no dataset: Aggregated rows
Atomic measure containing OVER Rejected in the checked build No supported placement

The release evidence records strict compilation of these shapes. Database execution and result parity are separate checks.

Detail window

fact:
  type: dataset
  table: FACT_SALES
  dimension: [id]
  columns:
    id:
    customer:
    region:
    amount:
    customer_amount: 'SUM({amount}) OVER (PARTITION BY {customer})'
  measures:
    repeated_customer_amount: 'SUM({customer_amount})'

The window repeats a customer's total on every detail row for that customer. Summing the calculated column counts the repeated total once per source row. The result is not a deduplicated customer total, so this example illustrates placement rather than a recommended sales metric.

A row-order-sensitive window also depends on its ordering, frame, tie-break key, and source population. Changing a filter's stage can change every window result in a partition.

Post-aggregation window

Given atomic sales: SUM({amount}), this composite formula ranks aggregated sales.

customer_rank:
  type: measure
  formula: 'rank() over (partition by {-d: customer} order by {sales} desc)'

At query grain [region, customer], the partition expression retains the other query fields, here region. The checked SQL groups by region and customer, then ranks SUM(amount) within each region. Physical fact rows are not the ranking input.

+d establishes a finer aggregation stage. It does not turn a grouped value into a detail-window attribute. Source filters, filters on window results, and final report filters can select different populations.

Model Query also accepts checked raw window forms. The query reference describes the query surfaces. Acceptance of one form does not establish support for arbitrary frames or dialects.
