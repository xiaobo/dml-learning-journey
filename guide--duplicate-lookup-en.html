Why duplicate dimension keys can double sales after a lookup

On this page
  • One region, two matches
  • Inspect the rows
  • Validate the real connection

When one fact row matches two dimension rows, a join can return that fact row twice. Summing the joined amounts then counts both matches. A lookup is safe only when the declared target key matches the actual data's uniqueness.

One region, two matches #

The lesson has two North sales: 10 and 20. With one North directory entry, the matched sales total is 30. Add a second North entry and each sale matches twice:

Source sale Matches Contribution after join
North, amount 10 2 20
North, amount 20 2 40
Total 4 joined rows 60

The source sales have not changed. The join result has more rows. A later aggregation can hide the extra rows while retaining the inflated amount.

Inspect the rows #

Open the lookup exercise and enable the invalid duplicate North entry. Compare the directory, matched rows and North total. The logical dataset DIM_REGION declares dimension: [region]; its physical source is TABLE_REGION. Repeated North values violate that source-key declaration.

Validate the real connection #

Before executing the report, run dmlc --validate-only on the intended connection. It checks whether the full declared dimensions of datasets reached by the query agree with the actual data. In this example, two North entries cause DIM_REGION to report DIMENSION_NOT_UNIQUE. Use the exercise's exact command and query, correct the declaration or source data, and validate again before execution to avoid duplicated lookup results.

Revalidate after relevant changes to the model, query, connection or source data. A legitimate one-to-many relationship needs an explicitly designed calculation.

The browser toggle affects only invented browser data. Validation probes source keys and query planning; it is not a comparison of executed report results. See grain and joins.
