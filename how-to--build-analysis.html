Build an analysis

Use this workflow to add reusable measures and a query that consumes them. For a first compilation, follow Compile your first model query. For syntax lookup, use Model Query.

Phase 1: Define the required answer

Record the report contract before writing SQL.

  1. Decide whether the answer needs source rows or grouped measures.
  2. List the fields that identify one result row.
  3. State the time range, comparison period, and report filters.
  4. Separate report filters from conditions that define a business measure.
  5. Record the source population, NULL behavior, and required output columns.
  6. List assumptions that could change the conclusion.

For business analysis, apply the assumption checks in data-analysis at this stage and after execution.

Phase 2: Draft the consumer query

Write the intended SELECT, WHERE, and GROUP BY before adding measures. Use existing business names wherever possible.

SELECT
	dt_month,
	渠道,
	AGG(销售额),
	AGG({销售额: yoy}) AS 销售额_yoy,
	AGG(同店销售额)
FROM MODEL
WHERE dt_month = '2025-03-01'
GROUP BY dt_month, 渠道

Keep report grouping, time windows, and channel slices in the query. Put reusable definitions, such as same-store eligibility, in the model. Add sorting or a row limit when the requested result depends on it. Predicate order does not change grammar acceptance.

Use a distinct alias for each modified measure reference. Check emitted output columns because the compiler can change their order or omit a requested time field on a known defective shape. See release evidence.

Phase 3: Find missing measure definitions

For each AGG(...) in the draft, inspect the target model.

  1. Reuse a measure when its definition matches the requested metric.
  2. If a similar measure has different semantics, preserve the distinction in its name and description.
  3. Add a measure when the draft needs a reusable business definition.
  4. Keep a report-only slice in the query unless the slice defines the metric itself.

Trace dependencies to atomic measures. For a same-store metric, the dependencies can include a customer-month amount, a customer-month eligibility calculation, and an outer rollup.

Phase 4: Extend the model

Define dependencies before their consumers where that order helps readers. Same-file forward references are supported in the checked cases.

  1. Declare the complete source-row identity on each dataset.
  2. Define atomic measures from dataset columns.
  3. Add measure dimensions: when a business calculation requires a particular evaluation dimension.
  4. Add +d at the reference that needs a finer evaluation dimension.
  5. Use an explicit outer aggregate to combine intermediate values.
  6. Define composite ratios from the required components.
  7. Add descriptions that state population, grain, and NULL behavior.

Test dimension-constrained measures with queries that include the required fields. A filter on dt_month does not by itself satisfy a closed [customer, dt_month] evaluation dimension.

For model patterns, see Measures. For descriptions and names, follow Write model metadata.

Phase 5: Validate the model and query

Use the selected dmlc.exe as the source of truth for uncertain behavior. Record its path, version, build timestamp, and dialect.

  1. Lint the changed model.
  2. Strict-compile a minimal query for each new calculation.
  3. Strict-compile the complete consumer query.
  4. Inspect diagnostics, notes, SQL, grouping, joins, filters, aliases, and output order.
  5. If a relevant connection is available, run validate-only before trusted execution.
  6. Execute a representative slice and compare results with the report contract.
  7. If an independent SQL or report result exists, compare row multiplicities, keys, NULLs, and all measures on the same source snapshot.
dmlc --lint model.dml --output-format=json
dmlc --compile --strict query.sql --model=model.dml --output-format=json --output-dir=gen
dmlc --validate-only query.sql --model=model.dml --connection=default --output-format=json

Run the final command only when default is the intended configured connection. Use the dmlc CLI covers output capture and validation failures.

Check each semantic rule against the actual formula. A same-store count cannot exceed a comparable total count when both use the same population. A subset amount can exceed the total when excluded rows contain negative values. Missing prior-year input can produce NULL, zero, or another declared fallback. Do not assume every YoY metric returns zero.

If a strict warning remains, retain the finding and its SQL. An emitted query is not a passed strict compile. If live checks are unavailable, record not run and the missing prerequisite.

For analytical conclusions, run queries that could disprove each headline claim. Keep that evidence with the report.

Phase 6: Review the final artifacts

Follow Phase 6 technical review after the applicable Phase 5 checks pass. Supply the model, consumer query, original report contract, compiler identity, and validation evidence.

Re-run affected checks after fixes. Keep business-definition changes visible and return to Phase 4 when a proposed optimization changes the metric.

Deliver the model and query

Save the reusable model, consumer SQL, and validation evidence together. Record remaining findings and checks that were not run. Use data-analysis for exports, dashboards, and the analytical narrative.
