Reproduce compiler observations

Use these probes to compare the selected executable with the documented build. Install Node.js and use a dmlc.exe with its required runtime available.

Run the probes

From the dml-dmx directory, run the following command.

node scripts/verify-reference.cjs scripts/dmlc-mcp/dmlc.exe

An absolute executable path also works. The runner copies inputs to a new OS temporary directory, strict-compiles each case, and saves stdout, stderr, generated artifacts, and command arguments. It prints the evidence path. No database connection is required.

Open report.json in that directory. Compare the fingerprint and version with release evidence.

Interpret the observations

Read each result according to its recorded case type.

Result Meaning
MATCH, accepted case Strict compilation and checked SQL patterns match. Live correctness is unverified.
MATCH, rejected case The invalid input produces the expected failure diagnostic.
EXPECTED FINDINGS Strict compilation returns the recorded warning status and diagnostics. The strict check has not passed.
KNOWN DEFECT REPRODUCED The recorded defective output remains. This is not a passing feature.
DRIFT The exit, status, diagnostic, or checked SQL shape changed.

Exit 0 means the observations match, including expected findings and known defects. Exit 1 means an unexpected change occurred. Review a fingerprint mismatch even when all patterns match.

Inspect the raw streams when a process fails or stdout is not JSON. A runtime or environment failure does not establish a language regression.

Review a build upgrade

  1. Retain the old manifest and evidence.
  2. Run the probes against the new executable.
  3. Inspect each changed diagnostic and SQL artifact.
  4. Check grouping, source membership, NULL behavior, and the final projection.
  5. Run applicable database validation and result comparisons.
  6. Update the manifest and affected documentation with the scope of the new evidence.

Keep a fixed defect separate from an accepted result until the required stages and output are verified. Pattern matches inspect selected SQL properties. They do not validate SQL semantics or result values.

Add a documented example

Give each case complete model inputs. Use query.sql and model.dml for SQL cases, or report.dml with a matching query key for direct DML compilation. Keep negative fixtures focused on one error.

Add expected status, exit, SQL patterns, absent SQL patterns, and diagnostic patterns to manifest.json as needed. Use kind: warning for expected strict findings and kind: known-defect for a reproduced compiler defect. The first_query case also lints the tutorial model before compilation.

Keep tutorial source blocks identical to their fixture files. Examples elsewhere can remain fragments with named dependencies, but do not describe them as executable acceptance cases.

The September manifest is retained as historical evidence. The runner uses manifest.json for the current build.
