Measure declarations

This page owns measure properties and formula forms. Design measures covers authoring decisions. Formula examples contains business patterns.

Basic syntax

measure_name:
    type: measure
    description: Business description
    dataset: dataset_name
    formula: aggregation_expression
    dimensions:                # optional allowed evaluation dimensions
        - [customer_id]
        - [customer_id, ...]   # listed fields remain required
    prerequisite: validity_expression

formula: is required. dataset: binds a top-level atomic measure to its source. A measure under a dataset's measures: block inherits that dataset. Composite measures reference other measures and omit dataset:.

dimensions: is an array of arrays. Each inner list is one alternative allowed evaluation dimension. A flat list fails with string found, array expected. An ellipsis permits additional fields, while every listed field remains required. The property constrains evaluation; it does not declare dataset identity or the query's grouping.

prerequisite: adds a grain-validity expression. The common metadata fields description, abbr, and tags are described in model metadata fields. Design measures covers how to choose these constraints.

Notes:

  • Apply query-specific filtering and grouping in the model query (SQL WHERE/GROUP BY, or DML format filters: / columns: dimension:) — not in one-off measures. Model Query rules: Model Query SQL.
  • dataset: is only for atomic measures. Their formulas directly aggregate that dataset's rows or column expressions without referencing other measures. Composite measures reference other measures and must not declare dataset:. This remains true when all referenced measures use the same dataset. See Measure References and pitfalls P39.
  • Measures may return numeric, date or classifier values. Keep display formatting in the consumer; choose aggregation and type to match the business definition.
  • For monetary or precision-sensitive raw fields, prefer casting once in an atomic measure (for example SUM(CAST({amount} AS DECIMAL(38, 2)))) and reusing that measure downstream.
  • When business rules rely on > 0 / < 0 comparisons, ensure the base measure is already typed as intended (e.g. DECIMAL) before reusing it in MINIF/MAXIF/DISTINCTCOUNTIF conditions.

Simple aggregations

COUNT

number_of_transactions:
    type: measure
    dataset: transactions
    formula: count(distinct transaction_id)

number_of_products:
    type: measure
    dataset: transactions
    formula: count(distinct product)

SUM

amount:
    type: measure
    dataset: transactions
    formula: SUM(CAST({raw_amount} AS DECIMAL(38, 2)))

transaction_quantity:
    type: measure
    dataset: transactions
    formula: SUM(quantity)

MAX/MIN

last_order_date:
    type: measure
    dataset: transactions
    formula: MAX(dt_date)

AVG

avg_invoice_quantity:
    type: measure
    formula: 'AVG({invoice_quantity: {+d: transaction_id}})'

Filtered measures

Use inline filters with {+f: condition}. Modifier syntax reference: Function modifiers.

expense:
    type: measure
    dataset: transactions
    formula: |-
        {debit: {+f: {account_type: ['Expense', 'Other Expense']}}}

sales:
    type: measure
    description: Sales revenue from income accounts
    formula: |-
        {credit: {+f: {account_type: ['Income', 'Other Income']}}}

food_and_drink_expense:
    type: measure
    formula: |-
        {expense: {+f: "instr(account, 'Food & drink') > 0"}}

number_of_credit_card_transactions:
    type: measure
    formula: |-
        {number_of_transactions: {+f: {credit_card : 'yes'}}}

number_of_unpaid_invoices:
    type: measure
    formula: |-
        {number_of_invoices: {+f: 'open_balance > 0'}}

Measure references

Reference other measures in formulas:

Composite measures must not declare dataset:. If formula: references another measure, omit dataset:. Atomic measures use dataset: to bind the source rows or column expressions they aggregate without referencing other measures. Atomic examples below (credit / debit) keep dataset:; the composite profit omits it. See pitfalls P39.

# Base measures
credit:
    type: measure
    dataset: transactions
    formula: SUM(credit)

debit:
    type: measure
    dataset: transactions
    formula: SUM(debit)

# Derived measure (composite — no dataset:)
profit:
    type: measure
    formula: |-
        {credit: {+f: {transaction_type: ['Income','Other Income','Expense','Other Expense']}}} -
        {debit: {+f: {transaction_type: ['Income','Other Income','Expense','Other Expense']}}}

Measure aliases

Create aliases for existing measures:

revenue: |-
    {sales}

income: |-
    {sales}

outgoing: |-
    {expense}

Complex formulas

Conditional aggregations

SUMIF / DISTINCTCOUNTIF / MINIF / MAXIF that reference other measures are composite: do not declare dataset: (even when a column in the formula “belongs” to a known dataset). Use dataset: only on a separate atomic measure if you need column-scoped aggregation. See Measure References and pitfalls P39.

incoming_payment:
    type: measure
    formula: |-
        SUMIF({payment: {+d: customer}}, {customer} is not null)

outgoing_payment:
    type: measure
    formula: |-
        SUMIF({payment: {+d: vendor}}, {vendor} is not null)

avg_sales_per_trx:

Window functions

Window placement — full contract: Window placement. Summary:

Intent Placement
Detail OVER (no GROUP BY; row attribute for later DISTINCTCOUNTIF / outer SUM / LAG gates) Calculated column under columns:, then atomic agg
Post-GROUP-BY rank / share / running total Transitional atomic agg + composite window / {-d:} / {-df:} / grand (no dataset:)

Atomic measures reject OVER (window functions are not allowed in atomic measures). Pitfalls: P70, P71.

Detail (bare partition cols under columns:):

fact:
    type: dataset
    table: FACT_SALES
    columns:
        store_id:
        prod_id:
        qty:
        net_qty: 'SUM({qty}) over (partition by {store_id}, {prod_id})'
    measures:
        sum_net_qty: 'SUM({net_qty})'

Post-aggregation (grain refs on the composite):

total_sales:
    type: measure
    dataset: fact
    formula: SUM({qty})

region_rank:
    type: measure
    formula: 'rank() over (partition by {-d: product} order by {total_sales} desc)'

In Model Query SQL — prefer fn-macros from system_macros.dml (rank, rank_asc, pot, grand) when they cover the pattern:

SELECT product, AGG(sales, 'rank') AS sales_rank
FROM MODEL GROUP BY product

SELECT product, AGG({sales: pot}) AS share
FROM MODEL GROUP BY product

See function modifiers for macro categories and behavior.

ISNULL and IIF

all_product_sales:
    type: measure
    description: Product sales including products with zero sales
    formula: |-
        SUM(isnull({sales: {+d: product}}, 0) * iif({DATASET_PRODUCT_SERVICE}.product is not null, 1, 0))

all_customer_sales:
    type: measure
    description: Customer sales including customers with zero sales
    formula: |-
        SUM(isnull({sales: {+d: customer}}, 0) * iif({DATASET_CUSTOMER}.customer is not null, 1, 0))

Fill default when row missing

Feature: fill default when a joined / FOJ / materialize row is missing (blocks null contagion into further math).

Activate by wrapping the measure formula outermost with isnull / ifnull / coalesce(公式, 字面量).

The default applies at use sites of that measure (query column, rename, {m: pp} / other dt modifiers, or embedded in another formula) when the site can be sparse (FOJ / nullpk / materialize wrap).

Two distinct rules (do not conflate):

  1. No invented outer wrap: mentioning a filled measure inside a composite does not by itself wrap that composite’s result column. Activate on the result if its column must be non-null when missing.
  2. Embedding still expands: when a composite embeds an already-activated dependency (or a chain of formula refs into one), sparse FOJ use sites still expand fill at the caller of that embedding — e.g. deep = {q2fp1} * 3 with q2fp1 = {q2f} + 1 and q2f = isnull(SUM(...), 0) yields (coalesce(dep, 0) + 1) * 3 on missing partner rows, not NULL. That is fill of the activated dep, not an automatic isnull(deep, …).
上期:
    type: measure
    formula: 'isnull({销售额: pp}, 0)'   # activate

上上期:
    type: measure
    formula: '{上期: pp}'                # use site → 0

本期减上期:
    type: measure
    formula: '{销售额} - {上期}'         # 上期 use site → 0 (no contagion)

本期减上期_fill:
    type: measure
    formula: 'isnull({销售额} - {上期}, 0)'  # activate on result

# Nested embed (activation on q2f; deep expands fill of q2f at FOJ)
q2f:   { dataset: secondary, formula: 'isnull(SUM({q2}), 0)' }
q2fp1: { formula: '{q2f} + 1' }
deep:  { formula: '{q2fp1} * 3' }

Not activation (still may be null when the row is missing):

Shape Why
Bare {销售额: pp} Not activated
isnull({a}, {b}) / coalesce(a, b, 0) Measure complement, not (公式, 字面量)
isnull(…, 0) + 1 as the activated measure itself Eval-at-null on that measure (often → 1), not “row missing → 0” for this measure’s identity
Result column never activated Dep may fill inside the formula body; the result column is not auto-wrapped at its further use sites unless activated

Same idea as MetricFlow fill_nulls_with / Looker post-agg COALESCE: declare on a measure; fill when that measure is used. DML does not create missing calendar rows — only fills when the joined column is null. Densify dates separately (calendar / FOJ grain). Pitfall: Troubleshooting index P28b.
