Choose a materialization grain

Use a materialization when repeated queries can reuse stored aggregates at a stable grain. Materialization reference owns declaration syntax and eligibility.

Performance & materialize design principles

Quick checklist for improving query performance:

  • Ensure time columns follow dt_date/dt_week/dt_month/dt_quarter/dt_year convention (first day of period).
  • Prefer a small set of reusable measures (e.g. sales, qty) rather than many one-off measures.
  • Keep Model Query SQL simple: FROM MODEL, select query dimension fields + AGG(measure), then GROUP BY.
  • When queries are slow due to repeated aggregation, add materialize at the right grain.

When to use materialize: queries repeatedly aggregate the same base data at a stable grain (e.g. monthly by product/store/category) and data is append-only or refreshable by period. Avoid when data is very small, the grain is ad-hoc, or model semantics are still being explored.

Grain design principles:

  1. Grain — fine enough for downstream rollups, not so fine it explodes row count. Common: DWD (daily + keys), DWS (month/quarter + analysis dims), ADS (report-ready).
  2. Store additive measures such as sales and quantity for downstream rollups. Do not sum distinct-customer counts across groups unless the customer sets are disjoint. Keep the entity key or verify a supported representation for the intended rollup.
  3. Put row-identity fields in dimension:. Put functionally dependent attributes, such as category_name derived from category_id, in dimension_columns:. See the materialization declaration rules.
DWS_SALES_DATE_CATEGORY:
    type: materialize
    parameters:
        dt_date: date
    dimension:
        - dt_date
        - category_id
        - cust_id
    measures:
        - 销售额
        - 销售量

materialize is a modeling-time optimization concept. Persisting a dataset into DuckDB as a physical table is a separate operation. See also: materialization examples for worked examples.
