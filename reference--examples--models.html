These fragments cover query dimensions, fill, materializations, and multi-dataset grain. They require the model objects named in each example.

Dimension modifiers #

Business question: What is the share of each product within its category?

Product share within category #

SELECT category, product,
       AGG(sales) as product_sales,
       AGG({sales: {dimension: [category]}}) as category_total
FROM MODEL
GROUP BY category, product

Here {sales: {dimension: [category]}} drops product and region, so sales is evaluated at category-only grain.

Using pot (percentage of total) #

pot drops all dimensions, giving each row's share of the grand total:

SELECT category, product,
       AGG(sales) as product_sales,
       AGG({sales: pot}) as share_of_grand_total
FROM MODEL
GROUP BY category, product

For share within a parent dimension (e.g. product / category total), use the dimension modifier instead:

-- Share of category (product / category total)
SELECT category, product,
       AGG(sales) as product_sales,
       DIVIDE(AGG(sales), AGG({sales: {dimension: [category]}})) as category_share
FROM MODEL
GROUP BY category, product

Hidden dimension fields #

Sometimes a dataset has dimensions that should not be exposed to end users but are needed for internal calculations.

transactions:
    type: dataset
    dimension:
        - dt_date
        - product
        - region
    columns:
        dt_date:
        product:
        region:
        transaction_id:          # internal dimension, not for analysis
        amount:

transaction_id can still be used in +d modifiers but won't clutter the MODEL table.

Moving annual total (MAT) #

SELECT dt_month, AGG(sales), AGG({sales: mat})
FROM MODEL
WHERE dt_month BETWEEN date(current_date, 'start of month', '-12 months')
                   AND date(current_date, 'start of month', '-1 month')
GROUP BY dt_month

mat computes a rolling 12-month total ending at each dt_month.

Key points: +d drills down — appends a dimension field to the evaluation dimension, aggregates at that finer grain, then rolls back up. -d removes dimension fields (roll up). dimension: [list] replaces the entire evaluation dimension. Use these to create share calculations, parent/child ratios, and grain-shifted comparisons.

Combo columns #

Business question: For each product, show the minimum invoice quantity where the invoice was paid.

Conditional aggregation #

min_paid_qty:
    type: measure
    dataset: transactions
    formula: MINIF({quantity}, {is_paid} = 1)

SELECT product, AGG(min_paid_qty)
FROM MODEL
GROUP BY product

Calendar densification vs fill default #

Densify (every date appears): ensure a calendar / spine grain exists, e.g. flag on Dim Calendar, then query at that grain.

Dim Calendar:
    type: dataset
    table: DML_CALENDAR
    dimension:
        - dt_date
    columns:
        dt_date:
        has_data:
            source: '1'

Fill default when row missing (block null contagion after join / FOJ): activate with outermost isnull / ifnull / coalesce(公式, 字面量). Applies at use sites of that measure only — see missing-row fill.

daily_sales:
    type: measure
    formula: 'isnull(SUM({sales: {+d: dt_date}}), 0)'   # activate

Do not rely on SUM(isnull({sales: {+d: dt_date}}, 0)) alone to fix missing join rows for later composites — activate the measure you will reference, or activate the composite result.

Key points: MINIF / MAXIF / AVGIF for conditional single-value aggregations. Sparse dates → densify; sparse measure rows after join → fill default at use sites (P28b).

allows: ALL for materialization selection #

See allows: ALL for syntax and example. allows: ALL permits compatible materialization candidates; it does not relax measure grain constraints.

Materialize #

Business question: A dashboard queries monthly sales, yoy growth, and MAT for the past 24 months every hour. The underlying dataset is very large.

Solution: Materialize #

Define the measures, then a materialization object that pre-aggregates them at a fixed grain:

sales:
    type: measure
    dataset: transactions
    formula: SUM({amount})

sales_yoy:
    type: measure
    formula: '{sales: yoy}'

sales_mat:
    type: measure
    formula: '{sales: mat}'

DWS_SALES_DATE_PRODUCT:
    type: materialize
    parameters:
        dt_date: date
    dimension:
        - dt_date
        - product
    measures:
        - sales
        - sales_yoy
        - sales_mat

A dataset can also declare its own materialization inline (materialize: <name> on the dataset) — see Dataset definition (type: dataset); the standalone object form is documented in materialization declarations.

⚠️ There is no measure-level materialize: true flag. The compiler rejects it with undefined modifier 'materialize' (verified with dmlc -c). Materialization is declared via type: materialize or dataset-level materialize: <name> — never on a measure.

How it works #

  1. The compiler registers the materialization and pre-aggregates the listed measures at the declared dimension: grain
  2. Queries referencing those measures at a compatible grain become candidates to be served from the materialized table instead of scanning raw data (subject to allows: — see Query definition (type: query))
  3. The materialization is refreshed through its stored procedure (parameters:), not in real time

Query with non-materialized filter #

SELECT dt_month, product, region, AGG(sales)
FROM MODEL
WHERE region = 'North'
GROUP BY dt_month, product, region

If the materialization grain is dt_date + product (no region), this query cannot be served from it. Consider materializing at multiple grains if needed.

When to materialize #

Scenario Materialize?
Measure scanned frequently, raw data very large Yes
Measure used in dashboards with strict SLA Yes
Measure queried ad-hoc, rarely No (overhead not worth it)
Measure grain = raw data grain No (no aggregation benefit)
Measure involves complex window functions Yes

Key points: materialization is declared with a type: materialize object (grain via dimension:, measures via measures:), not on the measure itself. Materialized measures are still referenced normally in queries (AGG(sales)). See Materialize definition (type: materialize) and materialization design.

Materialize as ETL replacement #

Business question: A stored procedure builds a fact table (INSERT INTO RPT_X SELECT ... FROM raw LEFT JOIN dim1 LEFT JOIN dim2 ...) and a report then consumes RPT_X. Can the stored procedure be replaced by DML?

Solution: Model the ETL pipeline as a materialize object #

Instead of treating RPT_X as an externally built table: dataset, model the entire pipeline: raw source as a table: dataset, enrichment via pk() chains, and RPT_X as a type: materialize that pre-aggregates from the enriched source.

# 1. Dimension datasets (the stored procedure's #temp tables)
Dim Customer:
    type: dataset
    table: MDM_STORE
    dimension: [store_id]
    columns:
        store_id:
        store_name:
        hq_id:

Dim Org:
    type: dataset
    table: MDM_ORG
    dimension: [org_id]
    columns:
        org_id:
        emp_name:

# 2. Source fact dataset with pk() chain enrichment
#    (replaces the stored procedure's SELECT ... LEFT JOIN ...)
raw_sales:
    type: dataset
    table: RAW_SALES
    dimension: [dt_month, store_id, prod_id]
    columns:
        dt_month:
        store_id:
        prod_id:
        amt:
        # pk() chain enrichment replaces LEFT JOINs
        store_name: pk({store_id}).{Dim Customer}.store_name
        hq_id: pk({store_id}).{Dim Customer}.hq_id
        # nested pk() chain: hq_id → Dim Customer → ... (hq_id is itself a pk result)
        hq_name: pk({hq_id}).{Dim Customer}.store_name
        # three-hop chain: store → hq_id → org_id → emp_name
        hq_org_id: pk({hq_id}).{Dim Customer}.org_id
        hq_emp: pk({hq_org_id}).{Dim Org}.emp_name
    measures:
        sales: SUM({amt})

# 3. Materialize replaces INSERT INTO RPT_X
#    Grain keys (dt_month, store_id, prod_id) go in dimension:.
#    Functionally dependent attributes (store_name, hq_name, hq_emp) go in
#    dimension_columns: — the compiler rejects derivable attributes in dimension:.
RPT_X:
    type: materialize
    parameters:
        dt_month: range
    dimension:
        - dt_month
        - store_id
        - prod_id
    dimension_columns:
        store_name:
        hq_name:
        hq_emp:
    measures:
        - sales

# 4. Report query consumes the materialize
report:
    type: query
    allows:
        - RPT_X
    filters:
        dt_month: { range: ['2024-01-01', '2024-03-01'] }
    columns:
        dimension: [dt_month, store_name]
        sales: '{sales}'

When to use this pattern:

  • The golden SQL is a stored procedure with INSERT INTO ... SELECT ... FROM raw JOIN dims.
  • The stored procedure's temp tables map cleanly to dimension datasets with pk() chain lookups.
  • The stored procedure's INNER JOIN population restrictions become measure gates; preserve the original population and inspect the emitted predicates.

Caveats:

  • Stored procedures that use @month (last balance month) to refresh all historical months' master data cannot be exactly reproduced with pk() chains that join on archive_month (per-month master data). Document this as a known limitation that needs result comparison on the same source snapshot.
  • CROSS APPLY table-valued functions and CASE WHEN key remapping require sql: escapes on dimension datasets; declare the resulting keys and validate their uniqueness.

Uneven dimensions #

Business question: Compare sales by region with inventory by warehouse. They share dt_date and product but not region or warehouse.

The challenge #

You cannot directly compare measures from datasets with completely different dimensions unless you align them.

sales:
    type: dataset
    table: fact_sales
    dimension:
        - dt_date
        - product
        - region
        - customer
    columns:
        dt_date:
        product:
        region:
        customer:
        amount:

inventory:
    type: dataset
    table: fact_inventory
    dimension:
        - dt_date
        - product
        - warehouse
    columns:
        dt_date:
        product:
        warehouse:
        units:

total_sales:
    type: measure
    dataset: sales
    formula: SUM({amount})

total_inventory:
    type: measure
    dataset: inventory
    formula: SUM({units})

Common grain: by product and date #

SELECT dt_date, product, AGG(total_sales), AGG(total_inventory)
FROM MODEL
WHERE dt_date = date(current_date)
GROUP BY dt_date, product

This works because both measures share dt_date and product. The model implicitly handles the missing dimensions.

If you need region + warehouse in the same query #

You generally cannot group by both region and warehouse because total_inventory has no region and total_sales has no warehouse.

Option 1: Two separate queries

-- Sales by region
SELECT dt_date, region, AGG(total_sales) FROM MODEL GROUP BY dt_date, region

-- Inventory by warehouse
SELECT dt_date, warehouse, AGG(total_inventory) FROM MODEL GROUP BY dt_date, warehouse

Option 2: Use modifiers to drop incompatible dimensions

SELECT dt_date, region,
       AGG(total_sales) as sales,
       AGG({total_inventory: {-d: warehouse}}) as inventory_dropped_warehouse
FROM MODEL
GROUP BY dt_date, region

{-d: warehouse} removes warehouse from inventory's grain, so inventory is evaluated at dt_date + product grain and can be joined with sales at dt_date + region + product grain. But this is usually semantically questionable — be careful.

Selected period and all-history totals #

-d removes grouping; it does not mean all history when a month filter remains. For these model fragments, use separate explicit query scopes:

-- Selected month
SELECT product, region, AGG(total_sales) AS period_sales
FROM MODEL
WHERE dt_month = date(current_date, 'start of month')
GROUP BY product, region

-- All history
SELECT product, region, AGG(total_sales) AS all_time_sales
FROM MODEL
GROUP BY product, region

Run the statements separately with the model definitions required by this page. For a complete executed comparison within one report, see fixed-axis denominators (中文). Its ordinary month grouping field is distinct from dim_dt time context.

Key points: Measures from different datasets can be queried together if they share enough dimensions. If dimensions don't align, use separate queries or carefully apply -d modifiers. Dropping dimensions to force compatibility can produce misleading results — document your intent.
