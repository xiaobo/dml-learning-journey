DML, DMX, and Model Query

A report combines business definitions with choices about grouping, filters, and presentation. DML keeps reusable definitions in a model, so reports can consume the same measures at compatible grains.

Metrics can reference other metrics, while analytical context determines how each reference is evaluated. A margin definition can therefore serve a regional report and a year-to-date KPI: the time transformation recalculates profit and revenue before division rather than averaging monthly margins. Measures from separate datasets can also compose at compatible grains; their output keys and missing sides must still match the intended report population. The profitability example follows this through composition, accumulation and comparison. DML models, DMX expressions and the compiler can provide the calculation core of an analytical semantic layer; agreeing business definitions remains a human responsibility.

The illustrated small journey through DML introduces these ideas with four example sales and a grouping explorer.

For a complete executable example, see Compile your first model query. The DML core specification defines the language contracts.

1. The model, query, and expression layers #

Layer Language Content Location
Model DML, Dato Measure Language Datasets, measures, and column macros .dml YAML
Query Model Query Measure selection, grouping, and report filters .sql or DML type: query
Expression DMX, Dato Measure eXpression Formulas, references, and modifiers Model formulas and query expressions

DML is a standalone semantic-layer compiler that works with model files and generates SQL for a database to execute. Database permissions and application authorization control access; dashboards and scheduling belong to the surrounding system. A model filter alone is not an access-control policy.

DML checks declaration structure and analytical compatibility, such as grain and time context. It does not provide complete static SQL expression type checking. Physical value types belong to the database, and the checked model schema rejects column type: declarations. A bad conversion or function argument can therefore survive compilation and fail at the database. See column metadata and value types.

A dataset binds columns to a physical table or SQL relation. Its dimension: declares the complete source-row key.

transactions:
  type: dataset
  table: fact_transactions
  dimension: [transaction_id]
  columns:
    transaction_id:
    amount:
    discount:
    net_amount: amount - discount
  measures:
    sales: SUM({net_amount})
    number_of_transactions: COUNT(1)

avg_transaction_value:
  type: measure
  formula: 'DIVIDE({sales}, {number_of_transactions})'

sales and number_of_transactions are atomic measures. They inherit the enclosing dataset and directly aggregate its rows or column expressions without referencing other measures. avg_transaction_value is composite because its formula references other measures, even though both use transactions. A composite measure has no dataset: property.

In a model formula, bare amount names a physical SQL column. {net_amount} expands the model's calculated column. Braces retain that distinction even when logical and physical names happen to match.

Column macros define reusable column expressions or cross-dataset lookups. They can expose attributes to measures without putting a join in each consumer query. The target dataset's complete key determines the lookup arguments; see source relations and lookups.

Model Query references measures through AGG(...). Model formulas use aggregation functions such as SUM and COUNT directly. AGG is the query interface to a measure, not a replacement for SUM inside a model formula.

A one-off measure can start in an inline DML block in the query file. Exploration does not require changing the shared model first. Review useful definitions before promoting them to shared measures.

2. Source relations, lookups and metric composition #

DML combines data at different stages. Choosing the stage determines which keys, filters and row populations you must check.

Task Mechanism Result contract
Reuse an attribute by its complete key pk(...) lookup in a model formula One target row per lookup key. Single and compound keys are supported.
Find the attribute valid at an event date pk(id, event_date) against [id, 'range(valid_from, valid_to)'] The checked finite intervals match [start,end). Intervals for the same id must not overlap.
Compare independent facts such as sales and budget Measures evaluated on aligned dimensions The normal key-union composition preserves groups present on either side, including missing values on the other.
Prepare a bridge, join, union or subquery relation Dataset sql: or a database view The prepared relation needs its own complete key. Define allocation weights and verify totals when one source row can match several rows.

Consumer Model Query SQL does not directly accept JOIN, UNION or subqueries. That restriction does not prohibit preparing supported relations in dataset SQL. Filters built into source SQL remain part of its population; they do not automatically become rules that respond to every consumer context.

Compound and effective-date lookups do not imply a general relationship graph with arbitrary path selection or automatic many-to-many allocation. Independent measure aggregation also does not repair duplicate lookup keys or a wrong alignment contract. Follow the compound-key and effective-date examples for complete models, deliberate key failures and repair. See composition semantics for unmatched groups and NULL keys, and dataset SQL for source ownership and the disclosed derived-relation validation-probe limitation.

3. Dimension roles and grain #

A dimension field is one named DML field. A dimension is a list of fields. The declaration site determines its role.

Declaration Meaning
Dataset dimension: Complete source-row identity
Formula dimension modifiers Evaluation dimension of one measure reference
Query GROUP BY or columns.dimension Result grouping
Materialize dimension: Stored grouping and key
Measure dimensions: Alternative allowed evaluation dimensions, one per inner list

Grain describes what one row represents in a particular context. For example, [transaction_id] identifies a transaction, while [region, dt_month] groups a report by region and month. A reporting group can contain many source rows, so it cannot replace the source key.

The modifier dimension: [] clears the evaluation dimension for a grand total. It does not declare dataset identity. +d adds fields for an intermediate calculation. An explicit outer aggregate combines those intermediate values when a formula needs a coarser result.

The compiler trusts the declared source key. Duplicate pk(...) targets can multiply rows even when compilation succeeds. Live validation checks observed key uniqueness. Result comparisons establish a different claim: whether the query returns the intended answer.

Dimension semantics explains these roles and their consequences in more detail.

4. Time context and dim_dt #

dim_dt represents the active time field of a measure's query context. It lets a formula refer to the current time grain without naming dt_date, dt_month, or dt_quarter directly. Macro prerequisites still limit which grains a macro accepts.

A grouped time field or a time filter can supply the context. Read strict diagnostics and inspect generated joins separately from syntax acceptance. The presence of a time comparison or key-union join does not itself imply a strict warning.

Declaring a standard fine time field such as dt_date makes supported coarser fields available through the system calendar. These virtual fields do not require duplicate physical declarations. Editor go-to-definition for a derived dt_month resolves to the explicit source time column.

A single KPI still needs an explicit cutoff. In the runnable example, a February filter gives YTD margin 20% over January and February, while ordinary sibling revenue is February-only. Without time context the query fails. Grouped calendar queries can also return months with cumulative values but NULL current revenue, so select output periods deliberately. The calendar must cover the intended dates on the executing connection.

The time context specification defines dim_dt and standard time fields. System macros provides a reference copy of time and formula macro definitions.

5. Reuse and integration #

Custom fn-macro definitions wrap a caller's measure formula, while dt-macro definitions change its time context. Both compose through the modifier syntax without changing the compiler. Database scalar calls reuse functions installed on the executing connection. The extension guide shows executed examples and a missing-function failure. These mechanisms do not establish a general module system or portable support for every UDF kind.

Set the model's SQL dialect explicitly. A recognized dialect is not evidence that every feature has executed successfully on that engine. Generated SQL can contain multiple statements, intermediate relations and calendar dependencies, so verify the execution environment too.

For an application that needs caller-bound filters, check the JDBC parameter boundary before adopting the query interface. The checked physical SQL parameters work, while semantic Model Query placeholders fail. Materialization parameters and internal literal parameterization do not supply the missing caller-visible binding API.

Compilation, validation and execution establish different facts. Live key validation can catch duplicates before a lookup multiplies rows, but it does not share a guaranteed snapshot with subsequent execution. Database EXPLAIN acceptance does not prove the returned numbers. Compare complete keys, row multiplicity, NULLs and unrounded values against an independent answer on the intended scope.
