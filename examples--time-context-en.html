Give a cumulative KPI an explicit cutoff

On this page

A cumulative measure needs a time context. A date filter in the same query also scopes ordinary sibling measures. DML does not silently choose today or the latest fact date.

Compare two scopes in one result #

January has revenue 10 and profit 3; February has revenue 20 and profit 3. In the February query, YTD margin is (3+3)/(10+20)=20%. Ordinary revenue is 20, not cumulative revenue 30.

完整文件 / Complete file: ytd/model.dml 
dialect: duckdb
F:
  type: dataset
  table: YTD_FACT
  dimension: [id]
  columns:
    id:
    dt_month:
    revenue_amount:
    profit_amount:
  measures:
    revenue: SUM({revenue_amount})
    profit: SUM({profit_amount})
margin:
  type: measure
  formula: 'DIVIDE({profit} * 1.0, {revenue})'
margin_ytd:
  type: measure
  formula: '{margin: ytd}'
完整文件 / Complete file: ytd/setup.sql 
CREATE TABLE YTD_FACT(id INTEGER, dt_month DATE,revenue_amount INTEGER,profit_amount INTEGER); INSERT INTO YTD_FACT VALUES (1,'2024-01-01',10,3),(2,'2024-02-01',20,3);
完整文件 / Complete file: ytd/february.sql 
SELECT AGG(margin_ytd), AGG(revenue) FROM MODEL WHERE dt_month='2024-02-01'

The model defines margin_ytd as '{margin: ytd}'. Components are calculated over the cumulative period before division. Averaging 30% and 15% answers a different question.

Observe missing context #

完整文件 / Complete file: ytd/missing_context.sql 
SELECT AGG(margin_ytd) FROM MODEL

This query fails compilation with a missing dim_dt diagnostic. Adding the February filter returns 20%. That filter is not an independent cutoff parameter: ordinary revenue in the same query also becomes February-only. Define and verify each scope if a report needs metrics over different periods.

Grouped months can exist without sales #

完整文件 / Complete file: ytd/months.sql 
SELECT dt_month, AGG(margin_ytd), AGG(revenue) FROM MODEL GROUP BY dt_month ORDER BY dt_month

This fixture returns twelve months. January has cumulative margin 30% and revenue 10; February has 20% and revenue 20. March through December have cumulative margin 20% and ordinary revenue NULL. The cumulative branch uses calendar-generated months. These rows are not new transactions, and NULL is not a measured zero.

Filter explicitly if the report needs one cutoff month. After changing the range, check both output months and every metric's input scope.

Run and interpret the checks #

Download the complete project and run verify.py as described in its README. It needs your existing dmlc, Python and DuckDB. The script creates a practice database only in the new output directory you specify. The shared verifier records results and diagnostics there.

This example was checked on DuckDB with dmlc 0.3.16, build 2026-11-13. The executable fingerprint and case statuses are in verification-summary.json in the download. Database validation and subsequent execution are independent operations; they do not guarantee a shared snapshot. Verify other engines separately.
