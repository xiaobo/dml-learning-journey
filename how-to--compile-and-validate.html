Use the dmlc CLI to check and run queries

Use this guide to compile a Model Query, inspect diagnostics and generated SQL, validate source keys, and compare results. Read available flags from your installed executable with --help and --advanced-help.

1. Identify the executable and model #

Record the executable path, version, build timestamp, and SHA-256 before comparing behavior with a documented build. Keep the model, included definitions and relevant configuration with the query: the same query text can produce different SQL after those inputs change.

$dmlc = (Get-Command dmlc.exe).Source
& $dmlc --version
Get-FileHash -LiteralPath $dmlc -Algorithm SHA256
& $dmlc --advanced-help

Install dmlc.exe and add its directory to PATH. Run these commands in the directory containing your model and query.

Match the model filename with the SQL FROM name. For model.dml, use FROM MODEL. For acme.dml, use FROM acme. Pass --model=model.dml to select a file, or pass its containing directory for filename discovery. See query discovery.

2. Lint and strict-compile #

Lint the model, then strict-compile the consumer query.

& $dmlc --lint model.dml --output-format=json
& $dmlc --compile --strict query.sql --model=model.dml --output-format=json --output-dir=gen

Inspect the process exit code after each command. Read the JSON status, diagnostics, notes, emitted SQL, and output order. Check the generated grouping, joins, predicates, aliases, and projected columns against the query contract.

If strict compilation returns findings, preserve the warning and emitted SQL. Resolve the intended population and NULL behavior before changing the query. Removing --strict does not make the strict check pass.

Use --output-dir for compile artifacts. Use --output for commands whose help documents a named output file. These flags are not interchangeable.

3. Capture JSON without changing its encoding #

For query result files, use the product output flag.

& $dmlc --model=model.dml query.sql -o outputs/result.json --overwrite

For lint or compile evidence, capture stdout separately from stderr. A Node.js argument array avoids shell quoting and gives explicit UTF-8 decoding. Save this script as compile.cjs beside the model and query.

const fs = require('node:fs');
const { spawnSync } = require('node:child_process');
const result = spawnSync(process.argv[2], [
	'--compile', '--strict', 'query.sql', '--model=model.dml',
	'--output-format=json', '--output-dir=gen'
], { encoding: 'utf8', cwd: __dirname });
if (result.error) throw result.error;
fs.writeFileSync('compile.stdout.json', result.stdout);
fs.writeFileSync('compile.stderr.txt', result.stderr);
const report = JSON.parse(result.stdout);
console.log(JSON.stringify({ processExit: result.status, report }, null, 2));
process.exitCode = result.status ?? 1;

Run it with the selected executable.

node compile.cjs $dmlc

If JSON parsing fails, retain the raw streams and process exit. Diagnose that failure before interpreting it as a language error.

In Windows PowerShell 5.1, run commands separately because && is unsupported. Avoid merging stderr into JSON stdout. If you need to suppress stderr interactively, use 2>$null in PowerShell.

4. Validate source keys and database acceptance #

If the target connection is configured, run validate-only before trusted execution or when relevant validation evidence becomes stale.

& $dmlc --validate-only query.sql --model=model.dml --connection=default --output-format=json

Replace default with the intended connection. Inspect status, summary, checks, generatedSql, diagnostics, next, and error.

Confirm that compilation, reached-dataset key checks, and the generated SQL's EXPLAIN probe pass. Validate-only does not execute the main result rows or establish business correctness.

If DIMENSION_NOT_UNIQUE appears, fix the complete dataset key, source ranges, or source data. Do not patch generated SQL with DISTINCT to conceal duplicate keys. If a validation query fails to execute, handle VALIDATION_QUERY_FAILED separately.

Re-run validation after a relevant model, query contract, connection, or source-state change. If a prerequisite is missing, record the check as not run and name the missing prerequisite.

5. Execute and compare results #

Run the consumer query on the validated connection.

& $dmlc --model=model.dml query.sql --connection=default -o outputs/result.json --overwrite

Check keys, row multiplicity, NULLs, and all measures. If an independent result exists, compare both queries on the same source snapshot and scope.

If a DuckDB cache is locked, identify the process and connection that owns it. Use another configured connection only when it represents the intended source. Do not change source data merely to avoid a lock.

For specific failures, use the troubleshooting index and error codes.

Practice a model/data contract repair #

Run the compound-key and effective-range examples to observe normal validation, a deliberate duplicate or overlap failure, and repaired validation followed by result comparison. This catches inconsistencies between the declared key and observed data before trusting a lookup result. Validation and query execution are separate operations; a successful check is not a same-snapshot or future-uniqueness guarantee.

Inspect a change or recover an existing query #

For a supported variance analysis, use --explain-change with a named measure, baseline and explicit time scope. Read the required inputs from dmlc --advanced-help. For a model containing net_revenue, dt_month and region, the checked invocation is:

dmlc --explain-change --measure=net_revenue --dim_dt=dt_month --current=2025-02-01 --baseline-modifier=pp --dimensions=region --model=model.dml

The comparison fixture gives baseline 300, current 400, and region contributions +200 and -100. These are fixture values, not the amounts in every example on this site. Check the baseline and current values before interpreting ranked dimensions. Contributions and surprise scores help select an investigation; they do not establish causes or eliminate confounding factors.

For an existing SQL query, --to-dml can generate a draft model and query.

dmlc --to-dml raw.sql --output=recovered.dml

Use a new output path and keep the generated draft warning. These commands were checked with dmlc 0.3.16; the available options vary by operation, so do not copy compile-only flags onto recovery commands. Review inferred keys, formulas, populations and warnings, then compile, validate and compare the recovered query's results against the original on the same source snapshot. Draft generation does not certify a production semantic model.

When integrating these tools, keep database and application responsibilities explicit. Database permissions and application authorization control access; a model filter alone is not an access-control guarantee. Generated SQL may have multiple statements, temporary relations and calendar dependencies. Verify execution on your target engine and measure representative workloads before making performance claims. The compiler does not supply dashboards or scheduling.
