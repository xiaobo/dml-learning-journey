Look up an attribute valid at an event date

On this page
  • Check the boundary date
  • Put the lookup rule in the model
  • Detect an overlap and repair it
  • Run and interpret the checks

Match the event date to a non-overlapping validity interval for the same object. This example uses [valid_from, valid_to): the start is included and the end is excluded.

Check the boundary date #

Label Validity Event date Amount
Jan [2024-01-01, 2024-02-01) 2024-01-01 10
Feb [2024-02-01, 2024-03-01) 2024-02-01 20

February 1 belongs to Feb, not Jan. The query returns Feb 20 and Jan 10, with one match per event.

Put the lookup rule in the model #

The target declares dimension: [id, 'range(valid_from, valid_to)']. Keep the range expression quoted: its comma belongs inside one YAML list item. The fact's pk({id}, {event_date}).{D}.label supplies the object id and event date in that order.

完整文件 / Complete file: range/model.dml 
dialect: duckdb
D:
  type: dataset
  table: DIM
  dimension: [id, 'range(valid_from, valid_to)']
  columns:
    id:
    valid_from:
    valid_to:
    label:
F:
  type: dataset
  table: FACT
  dimension: [fid]
  columns:
    fid:
    id:
    event_date:
    amount:
    label: 'pk({id}, {event_date}).{D}.label'
  measures:
    sales: SUM({amount})
完整文件 / Complete file: range/setup.sql 
CREATE TABLE DIM(id INTEGER, valid_from DATE,valid_to DATE,label VARCHAR); INSERT INTO DIM VALUES (1,'2024-01-01','2024-02-01','Jan'),(1,'2024-02-01','2024-03-01','Feb'); CREATE TABLE FACT(fid INTEGER,id INTEGER,event_date DATE,amount INTEGER); INSERT INTO FACT VALUES (1,1,'2024-01-01',10),(2,1,'2024-02-01',20);
完整文件 / Complete file: range/normal.sql 
SELECT label, AGG(sales) FROM MODEL GROUP BY label ORDER BY label

When replacing the label with a price or tier, define what the effective date and event date mean. This example demonstrates adjacent finite intervals, not open-ended validity, arbitrary many-to-many relationships or allocation rules.

Detect an overlap and repair it #

The verifier moves Jan's end to February 2, so February 1 matches both intervals. --validate-only reports DIMENSION_NOT_UNIQUE. Restoring the end to February 1 makes validation and the two-row result pass again.

Repair the business validity rule. Arbitrarily retaining one matching record conceals the conflict.

Run and interpret the checks #

Download the complete project and run verify.py as described in its README. It needs your existing dmlc, Python and DuckDB. The script creates a practice database only in the new output directory you specify. The shared verifier records results and diagnostics there.

This example was checked on DuckDB with dmlc 0.3.16, build 2026-11-13. The executable fingerprint and case statuses are in verification-summary.json in the download. Database validation and subsequent execution are independent operations; they do not guarantee a shared snapshot. Verify other engines separately.
