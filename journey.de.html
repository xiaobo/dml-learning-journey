01 / Die Zeilen

Verstehe zuerst,
was eine Zeile bedeutet.

Der Reisende zählte vier Verkäufe.
Jeder brauchte einen eigenen Namen.

Ein Dataset bildet eine Quelltabelle im Modell ab. dimension: [id] deklariert den vollständigen Quellschlüssel: Hier identifiziert id jede Verkaufszeile.

Zwei Verkäufe können dieselbe Region haben. region eignet sich zum Gruppieren, reicht aber als Quellschlüssel nicht aus.

Finde die beiden North-Verkäufe: gleiche Region, verschiedene IDs. Ein Quellschlüssel muss jede Zeile identifizieren.

Vier erfundene Verkäufe · TABLE_SALES

id = Verkaufs-ID, region = Verkaufsregion, amount = Verkaufsbetrag.

02 / DML

Bewahre die Definitionen
in einem Notizbuch auf.

„Wie nennen wir die Summe?“
Der Reisende schrieb: sales.

DML definiert das Modell in YAML. FACT_SALES benennt unser Dataset; TABLE_SALES ist seine physische Quelltabelle. Kennzahlen benennen wiederverwendbare Geschäftsberechnungen.

Atomare Kennzahlen sind an ein Dataset gebunden. Sie aggregieren dessen Zeilen oder Spaltenausdrücke, ohne andere Kennzahlen zu verwenden. Hier summiert sales die Beträge; cnt zählt die Zeilen.

Die Namen im Modell verstehen

In diesem Kurs bezeichnet FACT_ Datasets mit Geschäftsvorgängen, DIM_ Datasets zum Nachschlagen von Attributen und TABLE_ physische Tabellen. Feld- und Kennzahlnamen folgen lower_snake_case.

Wiederverwendbare Berechnungen gehören ins Modell, Berichtsgruppen und Filter in die Abfrage. Siehe DML, DMX und Model Query.

model.dml · das wiederverwendbare Modell

FACT_SALES:
  type: dataset
  table: TABLE_SALES
  dimension: [id]
  columns:
    id:
    region:
    amount:
  measures:
    sales: SUM({amount})
    cnt: COUNT(1)

{amount} referenziert die Modellspalte amount. Ein leerer Spalteneintrag verweist auf die gleichnamige physische Spalte.

03 / DMX

Eine Berechnung kann
Bekanntes wiederverwenden.

Der Reisende suchte den durchschnittlichen Verkaufsbetrag. Summe und Anzahl waren schon im Modell vorhanden.

DMX ist die Ausdruckssyntax innerhalb einer Formel. Die geschweiften Klammern in {sales} verweisen auf die Kennzahldefinition im Modell. Der Wert ergibt sich aus der Gruppierung und den Filtern dieser Referenz.

average_sale ist zusammengesetzt, weil es andere Kennzahlen verwendet. Bei einem Nenner von 0 liefert DIVIDE NULL, also keinen verfügbaren Wert.

Dieselbe Formel ergibt für North 30 ÷ 2 = 15, für alle vier Verkäufe 100 ÷ 4 = 25.

Die Formel in DMX
DIVIDE({sales}, {cnt})

salesBeträge summieren.

cntQuellzeilen zählen.

Vollständige Kennzahldefinition ansehen
average_sale:
  type: measure
  formula: 'DIVIDE({sales}, {cnt})'

Diese zusammengesetzte Kennzahl lässt dataset: weg. Ihre atomaren Abhängigkeiten bestimmen das Quelldataset. DMX kommt auch in Abfrageausdrücken vor.

04 / Model Query

Dieselben Kennzahlen.
Eine andere Sicht.

Der Reisende richtete das Fernrohr auf die Regionen.

Die Abfragedimension ist die Berichtsgruppierung: Sie bestimmt die Bedeutung einer Ergebniszeile. AGG(sales) fordert eine benannte Kennzahl an; SUM({amount}) bleibt im Modell. Die Definitionen bleiben unverändert.

Bei PivotTables entspricht GROUP BY region etwa dem Einfügen von region unter „Zeilen“. AGG gehört zu Model Query und ist keine Standard-SQL-Funktion.

Berichtsgruppierung wählen

Probiere Alle Verkäufe, dann Nach Verkauf: zuerst eine Summenzeile, dann vier Einzelzeilen. Kehre zu Nach Region zurück.

query.sql · Model Query

SELECT region, AGG(sales), AGG(average_sale)
FROM MODEL
GROUP BY region

FROM MODEL wählt model.dml mit dem Dataset und den drei Kennzahlen von oben.

Beispielergebnis

4 source rows → 2 result rows

regionsalesaverage_sale
North3015
South7035

Each result row represents one region. The source dataset still has dimension: [id].

North: 30 ÷ 2 = 15. South: 70 ÷ 2 = 35. The formula is evaluated for each result group.

The regional query for this four-row model passes strict compilation on the checked dmlc build.

06 / Bericht und Kennzahl filtern

Welche Verkäufe beantworten
welche Frage?

Zwischen den Belegen fand der Reisende einen zurückgegebenen Verkauf.

Unsere vier Verkäufe haben nun Monat, Kunde und Status. Vier Januarverkäufe dienen dem Vergleich. Wähle North: Umsatz 30, davon 10 aus abgeschlossenen Verkäufen.

Alle acht Verkäufe ansehen
Vollständiges Modell für Kapitel 6–12 ansehen

model.dml · eine wiederverwendbare Kennzahl

completed_sales:
  type: measure
  formula: '{sales: {+f: {status: completed}}}'

Ein Modifikator legt fest, wie diese Referenz berechnet wird. In {sales: ...} steht vor dem Doppelpunkt die Kennzahl, dahinter die Modifikatoreinstellung. Hier ergänzt +f den Filter status = completed; die Definition von sales bleibt unverändert.

f = filter, + = hinzufügen. Die Formel bedeutet: sales mit einem zusätzlichen Filter auf abgeschlossene Verkäufe.

Zwei Schreibweisen für Modifikatoren

{sales: pp} verwendet einen benannten Modifikator: sales für die Vorperiode. Das folgt in Kapitel 9.

{sales: {+f: {status: completed}}} verwendet Einstellungen mit einem Wert: die Bedingung status = completed hinzufügen. Die Klammern nach dem Doppelpunkt enthalten diese Einstellungen.

Weitere Formen stehen unter Modifikatorregeln und Beispiele.

Report WHERE selects the report's rows. +f restricts the inputs to completed_sales. The other measure still includes returned sales.

07 / Den Nenner klar benennen

Dreißig von wie viel?

Ein Anteil braucht einen Teil und ein Ganzes.

d = dimension, f = filter. -d entfernt das genannte Feld aus der Auswertungsgruppierung; -df entfernt zusätzlich die zugehörigen Filter. Das gilt nur für diese Referenz.

Wähle hier North und wechsle von -d zu -df. Der Nenner wechselt von 30 zu 100, der Anteil von 100 % zu 30 %.

model.dml · Kennzahldefinition

Der Nenner

Februar bleibt in beiden Kontexten fest.

Model Query ansehen

Nur die Auswertung des Nenners ändert sich. Februarfilter, Quellschlüssel und Bericht-GROUP BY bleiben gleich. Ohne zugehörigen Regionsfilter liefern beide hier denselben Nenner. Die Anteile sind Dezimalwerte und werden hier als Prozent angezeigt.

08 / Auf einer Zwischenebene rechnen

Umsatz je Kunde summieren.
Dann den Durchschnitt bilden.

Beide Februarverkäufe von South gehören Kunde C. Der Durchschnitt je Verkauf ist 35, die Summe dieses einen Kunden 70. Probiere SUM und MAX: North wird 30 bzw. 20, South bleibt 70. Kehre vor der Antwort zu AVG zurück.

model.dml · Kennzahldefinition

Stufe 1 · region + customer

Stufe 2 · region

d = dimension; +d: customer ergänzt customer zur Auswertungsdimension dieser Referenz. Das äußere AVG, SUM oder MAX fasst die Kundensummen wieder zur Abfragedimension zusammen. Quellschlüssel und Bericht-GROUP BY bleiben unverändert.

09 / Zeiträume vergleichen

Einen Monat zurückblicken.

Der Reisende legte die Januarseiten neben den Februar.

model.dml · Vergleichskennzahlen

previous_sales:
  type: measure
  formula: '{sales: pp}'
sales_change:
  type: measure
  formula: '{sales: pop}'

In {sales: pp} ist sales die Kennzahl und pp der Modifikator für den Vorperiodenwert. Bei Monatsvergleichen ist das der Vormonat. pop liefert aktueller Wert / Vorperiodenwert − 1 als Dezimalzahl. Siehe Zeitkontext.

Im Februar hat North Umsatz 30 und Vorperiodenumsatz 20. Das Wachstum ist 30 ÷ 20 − 1 = 50%. Wechsle zu Januar: Ohne Dezemberdaten sind die Vergleichswerte NULL. Kehre vor der Antwort zu Februar zurück.

query.sql · Berichtsfrage

Der Abfragefilter bleibt auf dem Zielmonat. Die Kennzahlen im Modell berechnen den Vorperiodenwert und die Wachstumsrate.

10 / Ein Attribut zuordnen

Ein Lookup braucht
einen eindeutigen Treffer.

Im Regionsverzeichnis ist Ada für North und Lin für South zuständig. Das Modell sucht über den vollständigen Schlüssel [region]. Füge einen ungültigen zweiten North-Eintrag hinzu und prüfe die verbundenen Zeilen.

DIM_REGION:
  type: dataset
  table: TABLE_REGION
  dimension: [region]
  columns:
    region:
    manager:

# Inside FACT_SALES.columns:
manager: 'pk(region).{DIM_REGION}.manager'

Regionsverzeichnis

Februarzeilen nach dem Lookup

Der Schalter verletzt absichtlich den deklarierten Schlüssel. Normales Kompilieren liest keine Quellzeilen. Mit einer Datenbankverbindung prüft dmlc --validate-only die vollständigen Dimensionen der erreichten Datasets und meldet bei nicht eindeutigen Schlüsseln DIMENSION_NOT_UNIQUE.

Doppelte Schlüssel mit dmlc erkennen

Speichere die Abfrage für die Datenbankübung als lookup.sql neben model.dml im heruntergeladenen Projekt. Die Auswahl von manager führt zum Dataset DIM_REGION.

SELECT manager, AGG(sales)
FROM MODEL
WHERE dt_month = '2025-02-01'
GROUP BY manager

Führe die Validierung mit der Verbindung aus, die deine Beispieltabellen enthält. Ersetze default durch deren Verbindungs-ID.

dmlc.exe --validate-only lookup.sql --model=model.dml --connection=default --output-format=json

Enthält TABLE_REGION dort beide North-Einträge, erwarte DIMENSION_NOT_UNIQUE für DIM_REGION. Korrigiere die Dimensionsdeklaration oder Quelldaten und validiere erneut.

Die Validierung prüft beobachtete Schlüssel und die Hauptabfrage mit EXPLAIN; sie führt den Bericht nicht zur Ergebnisgewinnung aus. Der Browserschalter ändert nur die erfundenen Daten dieser Seite, nicht deine Datenbank.

11 / Fehlende Werte verstehen

Ein fehlender Wert
ist nicht automatisch 0.

Wähle Durch den festen Wert 0 ersetzen. Beide Januarzeilen bleiben erhalten; die Vorperiodenwerte wechseln von NULL auf 0. NULL bedeutet hier, dass kein Vorperiodenwert vorliegt. Das Ersetzen belegt keinen tatsächlichen Dezemberumsatz von 0.

model.dml · Kennzahldefinition

Das äußerste ISNULL(..., 0) liefert überall, wo die Kennzahl verwendet wird, einen festen Ersatzwert. Es erzeugt keine neuen Monate oder Kunden.
