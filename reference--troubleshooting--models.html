These entries cover definitions, names, lookups, and metadata. Model structure and measure declarations own declaration syntax.

P21. AGG() in measure formulas #

Wrong: sales: AGG({amount}) in .dml Fix: sales: SUM({amount}) — use SQL aggregation functions in .dml

P22. Cross-dataset references without lookup #

Wrong: profit: SUM({sales.amount} - {costs.amount}) across datasets. Fix: Use column-macros with {DATASET}.column or pk(...) lookups.

P22b. Joining a table:-owned physical table in another dataset's sql: #

Wrong: Policy has table: policy, and another dataset's sql: does from policy / join policy. Fix: Use the dataset, not the physical table: from {Policy} / join {Policy}. For attributes without a SQL join, use pk(...).{Policy}.Col. {Policy} in sql: is a table-source substitution (compiler rewrites it to the dataset query name); it is not a column expression. See Dataset definition (type: dataset).

P23. Missing dataset: on atomic measures #

Wrong: sales: type: measure, formula: SUM({amount}) — no dataset. Fix: sales: type: measure, dataset: transactions, formula: SUM({amount})

P24. Overly specific measure names #

Wrong: sales_q1_2024_north, sales_john_doe. Fix: Generic measures + query filters.

P25. Not documenting edge cases #

Wrong: Measure without description that "excludes returns" or "includes zeros". Fix: Always add description: for non-obvious behavior. Document the dataset dimension and row meaning, scope flags, and misleading names—Write model metadata.

P27. Mixing dimension-constrained measures with incompatible queries #

Wrong: Selecting sales_by_product (allowed dimension [product]) and total_sales in a query whose query dimension is [dt_month]. Fix: Ensure every measure permits the query dimension and that their row meanings are grain-compatible, or use separate queries.

P28. Using +d when GROUP BY suffices #

Wrong: Creating sales_by_region: SUM({sales: {+d: region}}). Fix: sales: SUM({amount}) + query: SELECT region, AGG(sales) FROM MODEL GROUP BY region

P28b. Null contagion when a joined row is missing #

Wrong: profit: '{revenue} - {costs}' — if either side has no row for the slice (FOJ / sparse dt), that input is null and the difference becomes null.

Fix — fill default when row missing (missing-row fill):

  1. Activate sparse inputs with outermost isnull / ifnull / coalesce(公式, 字面量):
revenue: 'isnull(SUM({amount}), 0)'   # or wrap the existing measure formula outermost
costs: 'isnull(SUM({cost}), 0)'
profit: '{revenue} - {costs}'         # use sites of revenue/costs → 0
  1. If the result column itself must be non-null when its grain row is missing, activate on the result:
profit: 'isnull({revenue} - {costs}, 0)'

Not enough / not activation: isnull({a}, {b}), coalesce(a, b, 0), bare {m: pp}, or expecting an unrelated outer composite to gain an automatic isnull wrap. Embedding an already-activated dependency in a composite still expands that dep’s fill at sparse FOJ use sites (see measures.md Fill default).

P28c. Null-safe ON on composition FOJ (key-union) #

Wrong: Expecting multi-arm FOJ / densify to treat NULL dimension keys as one shared “unknown” entity (Power Query–style null-safe merge), or rewriting composition ON to null-safe so both arms’ empty keys collapse into one row with both measures filled.

Fix: Composition uses bare = (join NULL equality). Empty keys stay unmatched per arm. For a single unknown bucket, author an explicit sentinel (coalesce(dim, '…')) into the grain. Keep null-safe for row-preserving LEFT / nullpk only. Population ≠ ON: use presence / {primary} is not null when the report should drop secondary-only keys.

Category: Time Handling #

P37. Modifiers on columns #

Wrong: {customer_id: {+d: customer_id}} in a formula. Fix: Put drill-down on the measure being evaluated: {sales: {+d: customer_id}}. Other modifiers such as input +f also have column forms; this is not a ban on all column modifiers.

P38. Unquoted YAML formulas #

Wrong: formula: SUMIF({sales: {+d: dt_month}}, {dt_month} = {first_month}) without quotes when the value contains :, {, or -. Fix: formula: 'SUMIF(...)'

P39. dataset: on composite measures #

Wrong: Composite measure that references other measures still has dataset:. Fix: Omit dataset: when the formula references other measures; keep dataset: on atomic measures only.

P40. Measure cannot be redefined / duplicate formula #

Wrong: SELECT AGG(sales) AS sales or AGG(x) AS x when sales / x already exist as measures. Fix: Use SELECT AGG(sales) with no alias, or a neutral alias (AS sales_value). If the compiler says use existing measure "X", use AGG(X) instead of re-expressing the formula.

P41. DML {...} syntax in Model Query SQL #

Wrong: SELECT {dt_month}, AGG({sales}) FROM MODEL — braces are for .dml formulas only. Fix: SELECT dt_month, AGG(sales) FROM MODEL. Use AGG({sales: pop}) only for modifier form in queries.

P42. Bare name vs {col} inside .dml formulas #

Wrong (meaning): Treating formula: calc_amt * 2 as “forgot braces” / a compiler hole. Bare calc_amt binds as a physical table column (SQL pass-through). Fix: Brace when the intent is the calculated column’s definition: formula: '{calc_amt} * 2'. Leave physical columns bare: net: amount - discount. See Dataset definition (type: dataset).
