01 / データ行

まず、1 行が何を
表すかを知ろう。

旅人は 4 件の売上を数えました。
それぞれに、固有の名前が必要でした。

データセットはソーステーブルをモデルに対応付けます。dimension: [id] はソース行の完全なキーを宣言します。ここでは各行が1件の売上で、id が識別します。

02 / DML

定義は一冊の
ノートにまとめよう。

「合計に、どんな名前をつけよう？」
旅人は sales と書きました。

DML は YAML でモデルを定義します。FACT_SALES はデータセット名、TABLE_SALES は物理的な元テーブルです。メジャーは再利用できる業務計算に名前をつけます。

原子メジャーは1つのデータセットに結び付き、その行または列の式を集計します。他のメジャーは参照しません。ここでは sales が金額を合計し、cnt が行数を数えます。

モデル内の名前を確認する

この教材では、FACT_ はファクトデータセット、DIM_ は属性データセット、TABLE_ は物理テーブルを表します。フィールドとメジャーは lower_snake_case で命名します。

再利用する計算はモデルに、レポートのグループ化とフィルターはクエリに置きます。DML・DMX・Model Query を参照してください。

model.dml · 再利用するモデル

FACT_SALES:
  type: dataset
  table: TABLE_SALES
  dimension: [id]
  columns:
    id:
    region:
    amount:
  measures:
    sales: SUM({amount})
    cnt: COUNT(1)

{amount} はモデル列 amount を参照します。空の列定義は同名の物理列に対応します。

03 / DMX

すでにある定義を
計算に生かそう。

旅人は 1 件あたりの平均売上を知りたくなりました。モデルには、すでに合計と件数があります。

DMX は数式内の式の構文です。{sales} の波括弧はモデルのメジャー定義を参照し、その値はこの参照のグループ化とフィルターで計算されます。

average_sale は他のメジャーを再利用する複合メジャーです。分母がゼロの場合、DIVIDE は値がないことを示す NULL を返します。

同じ式でも、North では 30 ÷ 2 = 15、全 4 件では 100 ÷ 4 = 25 になります。

DMX で書いた式
DIVIDE({sales}, {cnt})

sales金額を合計します。

cnt元データの行数を数えます。

メジャーの完全な定義を見る
average_sale:
  type: measure
  formula: 'DIVIDE({sales}, {cnt})'

この複合メジャーでは dataset: を省略しています。依存する原子メジャーによって元データセットが決まります。DMX はクエリの式にも使われます。

04 / Model Query

同じメジャーを、
別の視点から。

旅人は望遠鏡を地域に向けました。

クエリ次元はレポートのグループ化で、結果の1行が何を表すかを決めます。AGG(sales) は名前付きメジャーを要求し、SUM({amount}) はモデルに置きます。モデル定義は変わりません。

ピボットテーブルなら、GROUP BY region は region を「行」に置く操作に似ています。AGG は Model Query 独自の関数で、標準 SQL の関数ではありません。

レポートのグループ化を選ぶ

全売上、次に売上明細別を試しましょう。合計 1 行から、明細 4 行に変わります。最後に地域別へ戻してください。

query.sql · Model Query

SELECT region, AGG(sales), AGG(average_sale)
FROM MODEL
GROUP BY region

FROM MODEL は、上のデータセットと 3 つのメジャーを含む model.dml を選びます。

結果の例

4 source rows → 2 result rows

regionsalesaverage_sale
North3015
South7035

Each result row represents one region. The source dataset still has dimension: [id].

North: 30 ÷ 2 = 15. South: 70 ÷ 2 = 35. The formula is evaluated for each result group.

The regional query for this four-row model passes strict compilation on the checked dmlc build.

コンパイルで確認用の SQL が生成されます。自分のデータでレポートを確かめるには、次の順に進めます。

  1. コンパイルし、診断と生成された SQL を確認する。
  2. 接続先で --validate-only を実行し、参照先データセットのキーと、EXPLAIN による SQL の検査を行う。
  3. レポートを実行し、行と値を独立した結果と比較する。

ブラウザーは計算例を表示します。実データの検証と結果比較にはデータベースが必要です。

06 / レポートとメジャーのフィルター

どの売上で、
どの問いに答えよう。

旅人は領収書の中に返品を見つけました。

4 件の売上に 2 月・顧客・ステータスを加えました。比較用に 1 月の 4 件も追加します。North を選ぶと、売上は 30、完了済み売上は 10 になります。

全 8 件の売上を見る
第 6〜12 章の完全なモデルを見る

model.dml · 再利用するメジャー

completed_sales:
  type: measure
  formula: '{sales: {+f: {status: completed}}}'

修飾子（modifier）は、この参照をどう計算するかを指定します。{sales: ...} のコロンの前はメジャー、後は修飾設定です。ここでは +f で完了状態のフィルターを加え、sales の定義は変えません。

f = filter（フィルター）、+ = 追加。「sales を計算し、今回は完了状態で絞る」と読みます。

修飾設定の2つの書き方

{sales: pp} は名前付き修飾子です。「sales の前期値」と読みます。第9章で使います。

{sales: {+f: {status: completed}}} は値付き設定です。status = completed の条件を加えます。コロンの後の波括弧に修飾設定を入れます。

他の形式は修飾子の規則と例を参照してください。

Report WHERE selects the report's rows. +f restricts the inputs to completed_sales. The other measure still includes returned sales.

07 / 分母を明確に

30 は、何に対する割合？

割合には、部分と全体の両方が必要です。

d = dimension（次元）、f = filter（フィルター）。-d はグループ化を除き、-df は関連フィルターも除きます。どちらもこの参照だけに適用します。

ここで North を選び、-d から -df に切り替えます。分母は30から100へ、割合は100%から30%へ変わります。

model.dml · メジャー定義

分母

どちらのコンテキストも 2 月のままです。

Model Query を見る

変わるのは分母の評価だけです。2月のフィルター、ソースキー、レポートの GROUP BY は変わりません。関連する地域フィルターがなければ、この例の分母は両者で同じです。比率は小数で返り、ここでは百分率で表示します。

08 / 中間の粒度で計算

顧客ごとに売上を合計し、
その平均を取る。

South の 2 月の 2 件は、どちらも顧客 C の売上です。明細平均は 35、顧客の合計は 70。SUM、MAX を試すと North は 30、20 に変わり、South は 70 のままです。回答前に AVG に戻しましょう。

model.dml · メジャー定義

段階 1 · region + customer

段階 2 · region

d = dimension（次元）。+d: customer はこの参照の評価次元に customer を追加します。外側の AVG・SUM・MAX で顧客別合計をクエリ次元に戻します。ソースキーと GROUP BY は変わりません。

Model Query を見る

ソース次元・クエリ次元・評価次元を比較します。それぞれ元の行の識別、結果のグループ化、中間計算を担います。

09 / 期間を比べる

ひと月前を振り返ろう。

旅人は 1 月のページを、2 月の隣に置きました。

model.dml · 比較メジャー

previous_sales:
  type: measure
  formula: '{sales: pp}'
sales_change:
  type: measure
  formula: '{sales: pop}'

{sales: pp} の sales はメジャー、pp は前期値を求める修飾子です。この例は月単位なので前月になります。pop は当期 ÷ 前期 − 1 の小数比率を返します。時間コンテキストも参照してください。

2 月の North の売上は 30、前期売上は 20。増加率は 30 ÷ 20 − 1 = 50% です。1 月に切り替えると、12 月の履歴がないため比較値は NULL になります。回答前に2 月へ戻しましょう。

query.sql · レポートの問い

クエリのフィルターは対象月のままにします。前月の値と成長率はモデル内のメジャーが計算します。

10 / 属性を関連づける

参照先には、
一意な一致が必要。

地域一覧では North の担当者が Ada、South が Lin です。モデルは一覧の完全なキー [region] で担当者を参照します。無効な North の重複行を加え、結合結果を確認しましょう。

DIM_REGION:
  type: dataset
  table: TABLE_REGION
  dimension: [region]
  columns:
    region:
    manager:

# Inside FACT_SALES.columns:
manager: 'pk(region).{DIM_REGION}.manager'

地域一覧

参照後の 2 月の行

この切り替えは意図的に宣言したキーに違反します。通常のコンパイルでは元データを読みません。接続先で dmlc --validate-only を実行すると、参照先データセットの完全な次元を検証し、一意でなければ DIMENSION_NOT_UNIQUE を報告します。

dmlc で重複キーを検出

データベースで試すときは、ダウンロードした model.dml と同じ場所に lookup.sql を保存します。manager を選ぶことで DIM_REGION データセットが参照されます。

SELECT manager, AGG(sales)
FROM MODEL
WHERE dt_month = '2025-02-01'
GROUP BY manager

サンプルテーブルがある接続先で検証します。default をその接続 ID に置き換えてください。

dmlc.exe --validate-only lookup.sql --model=model.dml --connection=default --output-format=json

接続先の TABLE_REGION に North が 2 件あれば、DIM_REGION に対する DIMENSION_NOT_UNIQUE が想定されます。次元の宣言か元データを修正し、再検証してください。

検証では実際のキーを調べ、EXPLAIN で主クエリを検査します。レポート結果の行は取得しません。この切り替えはページ内の架空データだけを変更し、データベースは変えません。

11 / 欠損の意味を考える

空白のページは、
ゼロとは限らない。

定数 0 で補うを選びましょう。1 月の地域 2 行はそのままで、前期売上が NULL から 0 に変わります。ここで NULL は前期の値がないことを示します。補完しても 12 月の売上がゼロだった証拠にはなりません。

model.dml · メジャー定義

最も外側の ISNULL(..., 0) は、このメジャーを使う場所で定数の代替値を返します。新しい月や顧客を作るものではありません。
