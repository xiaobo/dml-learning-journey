Measure modifiers

This page owns modifier payloads, filter effects, and composition. Expressions and functions owns references and intrinsic functions. Fine-grain aggregation examples shows complete stages.

Payload structure

In {measure: {modifier_a: value, modifier_b: value}}, the outer object has exactly one target-measure key. Its nested modifier map can contain several keys, subject to modifier constraints. The modifier schema defines the structure.

Key or form Payload
dim_dt Formula string or object with value and range fields
dim_dt as date, dim_dt as week, dim_dt as month, dim_dt as quarter, dim_dt as year, dim_dt as hour Period conversion variant; at most one time variant per modifier object
+f Filter-name string, list of filter names, or inline object such as {column: value}
-f Filter-name or column-name string, or a list of those names
Bare modifier name A dt-macro or fn-macro name

Time modifiers

The system macro reference copy contains time-shifting dt-macro definitions and formula-wrapping fn-macro definitions. Growth-rate macros return decimal rates. The selected executable's packaged resources govern available macros, formulas, and prerequisite constraints.

Two macro types:

Type Returns Examples
dt-macro Absolute value pp, ya, ytd, mat, p3m, ...
fn-macro (growth) Decimal rate pop, yoy, mom

Stacking: Modifiers can be stacked: AGG(sales, 'ytd', 'ya') = year-to-date one year ago. See modifier stacking for full stacking semantics.

Time context: time modifiers require a resolvable dim_dt and must satisfy their macro prerequisites. Grouping by a time field is the clearest form; a time filter can also supply the context. See Model Query time rules.

Period conversion with dim_dt:

SELECT dt_year, dt_quarter,
       AGG({sales: {dim_dt as quarter: pp}}) as last_quarter
FROM MODEL GROUP BY dt_year, dt_quarter

dim_dt as quarter makes pp operate at quarter grain even if the query groups by year + quarter.

Function modifiers

The system macro reference copy defines macros such as rank, pot, grand, firstday, and lastday. The selected executable's packaged resources determine the available names, formulas, and prerequisites. An unknown modifier diagnostic lists available names on the checked build.

Filter modifier +f is not a system macro — it is a schema-level modifier:

Modifier Syntax Returns Description
+f: condition {measure: {+f: {col: val}}} Filtered value Filter the measure while aggregating

+f filters atomic input rows; it is not a post-aggregation predicate.:

Target / predicate Behavior
Column inside an atomic aggregate Filters the input to that aggregate
Atomic measure + source-column predicate Supported; e.g. {sales: {+f: "status = 1"}} emits a conditional SUM
Simple composite + source-column predicate Propagates to its atomic dependencies; verified for divide({sales}, {cnt}). Use only when every dependency should receive the filter
Atomic measure with +d and source-column +f Supported in the checked AVG rollup; inspect that filtering precedes the fine-grain aggregation
Predicate referencing an aggregate measure, e.g. "{cnt} > 3" Rejected with cannot use +f modifier with measure(s); use fine-grain filter examples

A bare filtered atomic reference evaluates at the current query grain. Preserve +d and an explicit outer aggregate when the question concerns per-entity values (especially AVG, MIN, MAX, COUNT). Conditional SUM with no accepted input returns NULL; an explicit ELSE 0 is a different contract. Input gating can retain groups containing only rejected rows.

Window function fn-macros generate rank() over (...) in compiled SQL. Use them in Model Query SQL as AGG(measure, 'rank') or AGG({measure: rank}). See system_macros.dml for the full list and formulas.

Filter modifier in .dml (column target):

completed_sales:
    type: measure
    formula: "{amount: {+f: {status: 'completed'}}}"

Filter modifier in Model Query SQL:

SELECT AGG(sales, '+f', region = 'North') FROM MODEL

Dimension modifiers

Modifier Syntax Effect
+d: dim {measure: {+d: dim}} Drill down: append dimension field dim to the target evaluation dimension and evaluate there. Does not automatically roll up to the query grain — that requires an explicit outer aggregate (SUM/AVG/…). The target dimension comes from query GROUP BY plus the measure's dimensions: constraint (required fields must appear; ... allows additional query fields). Without a dimension modifier, a measure reference is already at its target evaluation dimension; wrapping it in SUM() fails with "cannot aggregate a measure w/o +d modifier". +d is required for any SUM({measure}), not just measures with dimensions: declarations.
-d: dim {measure: {-d: dim}} Remove dimension field dim from the measure's evaluation dimension, producing a coarser grain. Use list form {-d: [dim1, dim2]} to remove multiple fields—repeating {-d: dim1, -d: dim2} causes YAML duplicate-key errors. If the measure declares closed allowed dimensions, one must permit the resulting evaluation/query dimension; omitting measure dimensions: permits any compatible dimension. Query filters: on the removed field are still pushed down to the dataset WHERE—this can corrupt ratio denominators (see dimension and filter removal below).
-df: dim {measure: {-df: dim}} Combined -d + -f: removes a dimension field from the evaluation dimension (-d) and removes filters on that field from the measure's evaluation (-f). Query filters: that reference the removed field (or columns that depend on it including via pk() chains) are not pushed to the coarser-grain query's WHERE. Use list form {-df: [dim1, dim2]}. Equivalent to DAX CALCULATE(expr, REMOVEFILTERS(dim)).
-f: name {measure: {-f: name}} Remove filters referencing name from measure evaluation only. name can be a filter name (defined in query filters:) or a column name (including via pk() chain dependencies). Use list form {-f: [name1, name2]}. Does not change grouping. Query filters still define the report row set — when a blocked filter is not an output grain column, constrain population (e.g. EXISTS) rather than dropping the filter silently.
dimension: [dims] {measure: {dimension: [dim1, dim2]}} Replace the entire evaluation dimension with the listed dimension fields. It shares the dimension: token with dataset/query/materialize properties, but here it modifies one measure reference rather than declaring dataset identity, query grouping, or a materialization key. Semantically close to -d, but generates different SQL: a separate aggregation CTE instead of a window OVER (PARTITION BY …)—see pitfalls P43. Across time grains (e.g. {m:{dimension:[dt_quarter]}} on a dt_month query), bridge via the calendar and broadcast the coarse total onto fine rows — not a grand-total scalar.

Quick glossary (avoid ambiguity)

Writing Meaning
{销量: {+d: 门店}} Evaluate at query grain ∪ {门店}; stop there — no automatic roll-back
SUM({销量: {+d: 门店}}) (or AVG/MAX/…) Fine-grain values, then outer aggregate rolls back to the current query grain
{销量: {-d: 门店}} Drop 门店 from evaluation grain; filters on 门店 may still push down
{销量: {-df: 门店}} Drop 门店 from grain and block 门店-related filters on that measure
{销量: {-f: 门店}} Block 门店-related filters only; grouping unchanged

Same-dimension modifier conflicts

The language contract prohibits intersecting field sets in +d and either -d or -df within one modifier object. Different fields can coexist, as in SUM({销量: {+d: 门店, -d: 品牌}}). The 2026-10-16 build still accepts the checked same-field conflicts and emits repeated regional totals followed by an outer sum. This is an implementation gap. See modifier composition and release evidence.

-df — combined -d and -f

-df combines the semantics of two modifiers:

  • -d (don't group by): removes a dimension field from the measure's evaluation dimension, producing a coarser-grain aggregation.
  • -f (remove filter): removes filters on that dimension from the measure's evaluation — query filters: that reference the dimension (or columns that depend on it via pk() chains) are not pushed to the coarser-grain query's WHERE.

-df is shorthand for {-d: dim, -f: dim} — both forms produce identical compiled SQL. Use -df for brevity.

Use -df in ratio measures where the denominator must ignore both the grouping and the filtering of a dimension.

Problem it solves: Without -df, query filters: are pushed to dataset WHERE before aggregation. When -d generates a coarser-grain temp table (ratio denominator), it computes from the filtered base — shrinking the denominator. -df blocks this pushdown for the specified dimension: the filter is applied only to temp tables whose grain includes that dimension, and omitted from temp tables where the dimension was removed.

When to use -df vs -d:

Scenario Modifier Why
Ratio denominator must include all values of a dimension (e.g. brand share = brand sales / total sales across all brands) -df Filter on brand_id would shrink the denominator if pushed down
Ratio denominator should reflect the filtered subset (e.g. share within selected brands only) -d Filter on brand_id should apply to both numerator and denominator
No filter on the removed dimension field -d (or -df, equivalent) No filter to block

Example: brand share within each store, retaining selected brands in the numerator but including all brands in the denominator:

brand_share:
    type: measure
    formula: 'divide({sales} * 100.0, {sales: {-df: brand_id}})'

At query grain [store_id, brand_id], a query filter on brand_id applies to the numerator. The denominator removes that field and its filter, retaining the store context.

Dependency tracing: The compiler traces pk() chain dependencies. A filter on 客户标准名称 (pk({store_id}).MDM_STORE(store_id).store_name) is blocked when store_id is -df'd, because the column depends on store_id.

Equivalence with other systems:

System Equivalent Syntax
DAX (Power BI) CALCULATE(expr, REMOVEFILTERS(dim)) Removes grouping + filter context in one operation
Tableau No direct equivalent Use FIXED LOD + Context Filter, or Table Calculation Filter
Malloy No direct equivalent Use stage-level where: (post-aggregation) instead of source where:
LookML No direct equivalent Use filtered measure (filters: on measure) 
-- Product share within category
SELECT category, product,
       AGG(sales) as product_sales,
       AGG({sales: {dimension: [category]}}) as category_total
FROM MODEL GROUP BY category, product

-- Remove time grouping while retaining the selected time filter
SELECT region, AGG({sales: {-d: dim_dt}}) as selected_period_sales
FROM MODEL WHERE dt_month = date(current_date, 'start of month')
GROUP BY region

{-d:} on composite measures with FULL OUTER JOIN

Independent measure datasets normally compose through FULL OUTER JOIN at aligned evaluation grains (key-union). Alignment ON uses plain = (not null-safe). Row-preserving LEFT / nullpk stay null-safe. Population, equality, uniqueness, and fill are separate contracts; see cross-dataset composition and join NULL equality.

For primary-side population, use an unfilled presence measure guaranteed non-null for each real primary group and NULL for absent groups. For INNER population, require presence on both sides. An arbitrary business measure can be NULL on a valid group, and a filled measure can be non-null on an absent group. Neither is a reliable existence test. NULL arithmetic does not by itself remove secondary-only output rows.

Combining modifiers

Modifiers can be combined in a single reference, subject to same-dimension conflicts and modifier constraints:

# Filter + dimension (outer SUM rolls +d back to query grain)
formula: 'SUM({sales: {+d: customer, +f: {region: "North"}}})'

# Legal: +d and -d on DIFFERENT fields
formula: 'SUM({sales: {+d: customer, -d: brand}})'

# Prohibited by the language contract, but accepted by the checked build:
# formula: 'SUM({sales: {+d: store_id, -d: store_id}})'
# formula: '{sales: {+d: store_id, -df: store_id}}'

# Time + dimension
formula: '{sales: {+d: customer}, yoy}'

# Dimension + rank
formula: '{sales: {-d: dim_dt, rank}}'

# Dimension + filter removal (ratio with deferred filters)
formula: 'divide({sales: {-df: brand_id}} * 100.0, {sales: {-df: [store_id, brand_id]}})'

# Filter + absolute grain (e.g., ratio numerator/denominator at different grains)
formula: 'DIVIDE({sales: {+f: "status = 1", dimension: [prod_id]}}, {sales: {+f: "status = 1", dimension: [prod_id, store_id]}})'

In Model Query SQL:

SELECT product,
       AGG({sales: {-d: dt_date, rank}}) as all_time_rank
FROM MODEL
WHERE dt_month = date(current_date, 'start of month')
GROUP BY product

Modifier stacking

Multiple macros can be stacked in one expression. The compiler creates intermediate measures automatically, mirroring what a user would write manually.

Syntax: {measure: {macro1, macro2, macro3}} or AGG(measure, 'macro1', 'macro2', 'macro3')

For an ordinary sequential stack, the first macro transforms the original measure and the next macro applies to that intermediate. Time modifiers combined with multi-branch functions also transform their branches, as described below. A sequential example is:

# Stacking: yoy creates intermediate "sales_yoy", then rank applies to it
# Equivalent to:
#   sales_yoy:
#     type: measure
#     formula: '{sales: yoy}'
#   ...then: {sales_yoy: rank}
q_col: '{sales: {yoy, rank}}'

Time modifiers and multi-path functions: the verified build pushes ytd into the current and comparison branches of yoy. Both {sales: {yoy, ytd}} and {sales: {ytd, yoy}} emitted identical SQL for the recorded monthly probe: YTD sales divided by prior-year YTD sales, minus one. This is not a sum of monthly growth rates. Do not sort modifiers by category or infer a different meaning solely from generated intermediate names.

Grain-changing macros such as firstday have additional multi-path constraints. Verify the exact combination; an intended equivalence in a design proposal is not a release guarantee. Quote authored +f expressions containing YAML indicators, for example {sales: {+f: "amount > 5", yoy}}.

Intermediate measure reuse. Before creating a new intermediate, the compiler searches existing measures for one with the same formula (by expanded formula, shorthand, or map form). If a user-defined or previously generated measure matches, it is reused. This avoids redundant intermediates and lets users name their intermediates deliberately.

Name collision handling. If the auto-generated intermediate name (e.g. sales_yoy) collides with an existing measure that has a different formula, the compiler appends a numeric suffix: sales_yoy__2, sales_yoy__3, etc.

Compatibility: macro prerequisites, time context, allowed dimensions, duplicate keys, and reaggregation determine whether a stack is valid. Compile the exact stack on the target build. Two range macros and repeated macro keys are not general composition mechanisms. If an error remains after expressing the stages explicitly, keep the diagnostic and reproducer; a manually named intermediate does not establish equivalence by itself.
