DML evaluation semantics

This page owns evaluation context, grain compatibility, and composition contracts. Declaration syntax lives in model structure, measures, queries, and materialization. Compiler evidence records observed implementation gaps.

Scope and position

What this spec covers

This document specifies DML evaluation context, grain compatibility, and modifier constraints. Rules below describe language contracts. Error codes, MCP protocol, and structured error response format are documented in DMLC Error Codes Reference and MCP Contract (CLI + MCP).

Current product capability status and evidence boundaries are maintained separately in DML 产品事实源. This spec defines language meaning; examples here do not by themselves upgrade a product capability to tested.

What this spec does not cover

  • Compile and validate a query covers CLI commands and evidence collection.
  • MCP contract covers tool requests and responses.
  • Build an analysis covers business analysis procedures.
  • Core concepts explains the model, query, and expression layers.

Three-layer architecture

Layer Language What you write File
Modeling DML Datasets, measures, column-macros, materialize, dt/fn-macros .dml (YAML)
Querying Model Query (SQL or DML format) AGG(measure), GROUP BY, modifiers .sql or .dml type: query
Expressions DMX (Dato Measure eXpression) Formulas, references, modifiers, pk() Inside both layers

DMX is the shared expression language. In .dml formulas: {column}, {measure: modifier}, pk(...). In Model Query SQL: AGG(measure), AGG({measure: modifier}).

Core building blocks

Dataset — a table with a declared dimension and columns. Its dataset declared grain is determined by the declared dimension: list.

Measure — a named business metric. Two types:

  • Atomic: bound to a dataset (dataset: field), uses SQL aggregation on columns.
  • Composite: references other measures (no dataset: field).

Dimension field — one named DML field.

Dimension — a list containing one or more dimension fields. A dataset dimension: declares source-row identity; a query dimension declares grouping; an evaluation dimension controls a measure reference; and a materialization dimension declares an output key. Each inner list in measure dimensions: is one allowed dimension. A measure-as-dimension field is a query-dimension field whose value is produced by evaluating a measure (see Measure-as-dimension).

The modifier form {dimension: []} clears the evaluation dimension to request a grand-total context. The empty list is an operation, not a zero-field dimension.

Column-macro — a derived column or cross-dataset lookup defined in .dml. Brings fields from other datasets into measure formulas without JOIN.

Design principles

  1. Semantics must be executable. Measures compile to warehouse SQL — not just documentation.
  2. Govern semantics like code. Git, PR, LSP, dml_schema.yaml validation.
  3. Measures are not bound to a fixed result grain. A measure has a derived, optionally constrained measure valid/native context and is evaluated at an effective grain chosen by the query and modifiers; the compiler enforces compatibility.
  4. Complex derivations belong in the model. Time comparisons, ratios, multi-level aggregation — kept in .dml, not scattered to BI calculated fields or ad-hoc SQL.
  5. Agents are equal consumers. MCP run_query, structuredContent, next.actions — agents and analysts share the same semantic entry point.

Evaluation context model

Definition

The evaluation context is the complete set of information the compiler uses to resolve a measure reference into executable SQL.

The canonical product shorthand is Context = {grain, filters, time}. In the language model below, the time role is represented by the resolved dim_dt field.

Context = {
    grain: [dim₁, dim₂, ...],   // active grouping dimension fields
    filters: [predicate₁, ...],  // active filter predicates
    dim_dt: TimeDim | null       // resolved time dimension
}

Canonical grain roles

Role Source Description
Dataset declared grain Dataset dimension: What one dataset row represents
Measure valid/native context Dataset source, referenced measures, formula/modifiers, and optional measure dimensions: constraint Contexts in which the measure definition is valid; not a fixed output grain
Effective evaluation grain Query grain after applying +d, -d, dimension, and related modifiers Grain at which a particular measure reference is evaluated
Query result grain GROUP BY or query columns.dimension What one output row represents. May include measure-as-dimension fields (Measure-as-dimension) alongside physical or mapped dimension fields.

The broader query context combines query result grain with WHERE / filters: and resolved time information. “Measure native grain” and “target grain” in older material are aliases for measure valid/native context and effective evaluation grain respectively; new normative text should use the canonical terms above.

Context transition

Modifiers transform the evaluation context. The compiler applies modifiers to derive a new context for measure evaluation:

apply_modifier(Context, Modifier) -> Context'
Modifier Effect on grain Effect on filters
+d: dim Append dim to grain (drill down) No change
-d: dim Remove dim from grain (roll up) No change — filters on dim still pushed to dataset WHERE
-df: dim Remove dim from grain Remove filters on dim (and derived columns) from measure evaluation
dimension: [dims] Replace entire grain with dims No change
+f: condition No change Add condition to filters
-f: dim No change Remove filters referencing dim
dt-macro (e.g. ya, pp, ytd) No change Replace time range in dim_dt
fn-macro (e.g. yoy, rank) May change grain (e.g. grand → dimension: []) Depends on macro formula

dim_dt — the time dimension

dim_dt is the system variable representing the time dimension of the current query.

Resolution priority: query dimension → query filter → null.

Properties:

  • {dim_dt} — resolves to the query's current time field (e.g. dt_month, dt_quarter)
  • {dim_dt.datetype} — type string: 'day', 'week', 'month', 'quarter', 'year'
  • {dim_dt.periods_per_year} — periods per year: 52 for weeks, 12 for months, 4 for quarters
  • {dim_dt.datepart} — SQL datepart string

Design goal: use dim_dt instead of concrete dt_date/dt_month/dt_quarter in measure formulas, so a measure works at any time grain without rewriting.

Period conversion: dim_dt as quarter makes pp operate at quarter grain even if the query groups by year + quarter:

SELECT dt_year, dt_quarter,
       AGG({sales: {dim_dt as quarter: pp}}) as last_quarter
FROM MODEL GROUP BY dt_year, dt_quarter

Standard time dimension fields

Field Grain Example value
dt_date Day 2024-03-15
dt_week Week (starting Monday) 2024-03-11
dt_month Month 2024-03-01
dt_quarter Quarter 2024-01-01
dt_year Year 2024-01-01

All time fields use first-day format: the first day of the period.

Automatic coarser-grain derivation

A dataset that explicitly declares a standard time field also exposes the supported coarser members of the dt_<grain> series through the system calendar. For example, an explicit dt_date column makes dt_week, dt_month, dt_quarter, and dt_year valid dataset-scoped column references; model authors do not need to repeat those names under columns: merely to query or filter at a coarser time grain. The generated values follow the calendar and first-day rules above.

An auto-derived time field is a virtual column identity, not a second explicit source definition. Language tooling must therefore:

  • include supported derived fields in dataset-scoped resolution and completion;
  • accept them anywhere the corresponding dataset column is legal, including as query dimension fields, filters, formulas, and modifier payloads;
  • navigate a derived reference to the explicit source time column that supplies it (dt_month derived from dt_date navigates to dt_date);
  • keep the virtual field name read-only for rename purposes unless an explicit definition with that name exists.

If the same derived field can be reached from more than one explicit time source and no unique source can be selected, tooling must fail closed rather than choose an arbitrary definition.

Filter context and pushdown

Filter placement depends on semantic scope:

Layer Where What goes here
Query filters: / WHERE Query block Report-specific slices (channel, brand, date range)
Measure formula .dml measure Metric-specific eligibility when rejected rows may remain in output groups
Dataset sql: Dataset definition Permanent source-population restrictions that current declarative DML cannot express

A source WHERE and a NULL-producing measure gate are not generally interchangeable: rejected-only groups disappear in the former and may remain in the latter. Prove group existence, sibling metrics, distinct/join/window behavior, and NULL semantics before moving between these layers.

Pushdown rule: query filters: are pushed to the dataset WHERE before aggregation. When -d generates a coarser-grain temp table, the filter is still applied — this can shrink ratio denominators. Use -df to block filter pushdown for a specific dimension field.

Dependency tracing: the compiler traces column derive chain. A filter on store_name (pk({store_id}).MDM_STORE(store_id).store_name) is blocked when store_id is -df'd, because the column purily derived from store_id.

Grain system

The dimension in each evaluation context determines its grain and compatibility with other contexts. The DML roles of each dimension declaration are summarized in dimension roles.

Three grain types

Grain type Declared by Meaning
Dataset grain Dataset dimension: One row of the underlying table represents one value combination of the dimension fields in this dimension
Measure grain Formula + modifiers + optional dimensions: constraint The grain at which the measure's formula is valid
Query grain Query GROUP BY / columns.dimension: One query-result row represents one value combination of the dimension fields in this dimension

Grain compatibility rule

The query grain must be compatible with every measure's grain.

For an atomic measure without dimensions: constraint:

  • The measure can be evaluated at any compatible dimension composed from its dataset's dimension fields.
  • The compiler chooses aggregation from the declared grain and requested context; at the declared unique row grain it may project raw values.

For an atomic measure with dimensions: [[dims]] constraint:

  • The measure can only be evaluated at the specified grain.
  • Other formulas wanting to use it must explicitly {measure: {+d: dim}} to drill to that grain.
  • The compiler rejects incompatible grains with: cannot set dimension [...] since only [...] are allowed.

Dataset/materialize dimension: contains one dimension, while measure dimensions: contains alternative allowed dimensions—each inner list is one dimension. The latter is a constraint, not a declaration of dataset identity or query grouping. See the dimension-role contract in dimension roles.

For a composite measure:

  • The grain is the union of referenced measures' grains (after modifier resolution).
  • All referenced measures must be grain-compatible with each other.

Multi-level aggregation via +d

+d establishes a finer evaluation stage. It does not by itself roll the value back to the query grain.

Writing Meaning
{m: {+d: x}} Evaluate at query grain ∪ {x}; stop there
SUM / AVG / MAX / …({m: {+d: x}}) Fine-grain value, then an explicit outer aggregate rolls back to the current query grain
Query dim binding - lab: '{m: {+d: K}}' Measure-as-dimension (Measure-as-dimension): the result is a grouping key, not an ordinary rolled-up measure column

The outer aggregation function (SUM, AVG, MAX, etc.) is chosen by the author. The compiler does not invent it. With an outer aggregate, the compiler typically emits a CTE (WITH ... AS (SELECT ... GROUP BY ...) SELECT ...).

Pattern: atomic measure → +d drill-down inside a composite that supplies the outer aggregate → query at any grain

# Atomic measure (dataset grain: dt_date × store_id × prod_id)
销售量:
    type: measure
    dataset: o2o_pos
    formula: SUM(count_qty)

# Distribution SKU count: how many products have sales > 0?
# {销售量: {+d: prod_id}} drills down to per-product grain,
# then DISTINCTCOUNTIF counts products with positive sales.
分销SKU数:
    type: measure
    formula: |-
        DISTINCTCOUNTIF({prod_id}, {销售量: {+d: prod_id}} > 0)

# Distribution store count: how many stores have sales > 0?
分销客户数:
    type: measure
    formula: |-
        DISTINCTCOUNTIF({store_id}, {销售量: {+d: store_id}} > 0)

# Average sales per store (selling power)
卖力:
    type: measure
    formula: |-
        divide({销售额}, {分销客户数})

-- Query at brand × quarter grain — the +d inside each measure
-- generates intermediate CTEs at prod_id / store_id grain, then rolls up.
SELECT dt_quarter, brand,
       AGG(销售额),
       AGG(分销SKU数),
       AGG(分销客户数),
       AGG(卖力)
FROM MODEL
GROUP BY dt_quarter, brand

When +d appears on a query dimension binding rather than inside a measure formula with an explicit outer aggregate, that is measure-as-dimension (Measure-as-dimension), not the two-step pattern above.

Cross-dataset auto-join

Independent measure datasets normally aggregate separately and compose with FULL OUTER JOIN on aligned dimensions (key-union). Composition / densify FOJ ON uses plain = (SQL NULL≠NULL); row-preserving LEFT and nullpk invent stay null-safe. Do not assume the same NULL equality for composition and for pk() / detail spines. Authoring detail: join NULL equality.

Emitted join type. FULL OUTER JOIN is the composition semantics, not the emitted form. The intermediate template emits FULL OUTER JOIN (or densify UNION+LEFT with the same bare-= contract); the SQL compiler may then reduce each join to the strongest type proven by query predicates: a filter that proves the primary side present (e.g. {primary_presence_measure} is not null) lowers the emitted join to LEFT JOIN; filters proving both sides required lower it to INNER JOIN. Inspect the emitted SQL for the final join type — a LEFT/INNER result means the presence contract was proven by authored filters, not that composition semantics or ON equality changed.

For a LEFT population, filter on a dedicated primary presence measure that is non-null on every valid primary group and NULL on absent groups. For an INNER population, require presence from both sides. Use unfilled source counts or another proven presence signal; a nullable business value can discard valid groups, while missing-row fill can retain absent groups.

Validate shared key meaning, complete-key uniqueness, nullable-key acceptance (bare = vs null-safe site), unmatched rows, and missing-row fill separately. Independent preaggregation does not repair duplicate lookup keys or a wrong alignment contract. Executable probes establish SQL shape, not database result parity.

Grain safety enforcement (existing compiler behavior)

The compiler enforces grain safety at compile time:

  1. Measure dimension-constraint violation: if a measure with allowed dimension dimensions: [[customer_id]] is referenced at a query dimension that also includes dt_date, the compiler rejects with:

    cannot set dimension [dt_date, customer_id]+d: customer_id since only [[customer_id]] are allowed

    The compiler now includes a Hint explaining that ... allows additional dimension fields but listed fields remain required, and suggests using +d to add missing required fields. Use ... to permit additional dimension fields; the listed fields remain required.

  2. Measure aggregation requires +d: SUM({measure}) fails with "cannot aggregate a measure w/o +d modifier"—the compiler includes a Hint explaining that without +d the measure is already at its target evaluation dimension with nothing finer to aggregate. This applies to any measure reference wrapped in an aggregation function, regardless of dimensions: declarations. The target evaluation dimension comes from query GROUP BY plus the measure's allowed-dimension constraint. +d: dim appends a dimension field and evaluates at the resulting finer grain; the outer SUM/AVG/… rolls back to the target dimension. Use SUM({measure: {+d: dim}}) (not bare {measure: {+d: dim}} as a rolled-up column) when that two-step contract is intended.

  3. Missing time context: time modifiers require a resolvable dim_dt and their macro prerequisites. A grouped time field or a time filter can supply the context.

  4. Incompatible cross-dataset grains: if two measures from different datasets don't share enough dimensions for the query grain, the compiler reports an error.

  5. Measure-as-dimension rules: see Measure-as-dimension and the release caveats. Missing entity keys are rejected, but static checks do not catch every invalid lowering.

Evidence boundary: compile success is not a proof of valid SQL or correct numbers. The distributed build has a strict-success classifier probe that emits GROUP BY COUNT(1). Check SQL shape, live uniqueness and result parity as separate gates; see release evidence.

Time grain rules

  • Prefer one explicit time grain for a clear reporting contract. The checked build accepts dt_year, dt_month together; this does not establish every multi-time modifier combination.
  • Use period-start values for coarser time fields. Equality selects one period; structured range: [start, end] includes both endpoints at that grain.
  • WHERE predicate order is an authoring convention, not a grammar restriction.
  • Use the macro's actual prerequisites and resolved dim_dt; a time filter can supply the context without a visible time grouping field.

Measure-as-dimension

A measure-as-dimension field is a member of the query dimension whose value is the result of evaluating a measure (or a scalar expression over such a measure), not a physical dataset column. It remains a query-dimension role (dimension roles): it contributes to the query result grain. It does not declare dataset identity.

Explanation: Measure-as-dimension. This section states the intended multi-pass contract. The explanation separates working shapes from shipped lowering defects. The compiler models these query columns separately from physical dimension columns and ordinary output measures while reusing normal measure calculation behavior.

Syntax on columns.dimension

Authoring forms and capability boundaries (DML-format query):

Form Example Meaning
Named measure + explicit +d - first_purchase_month: '{first_purchase_month: {+d: store_id}}' Evaluate the measure with store_id appended to its evaluation dimension; use the result as the query-dimension field
Bare measure name - first_purchase_month Invalid for a measure-derived dimension. The use site must declare an explicit complete +d key.
Scalar wrap over {m: {+d: dim}} - payment_day: 'cast({authorization_ts: {+d: payment_id}} as date)' Evaluate the scalar once per complete key and use the result as a query-dimension field.
Named scalar measure + +d on the query measure formula: 'cast({authorization_ts} as date)', then - payment_day: '{dt_payment_day: {+d: payment_id}}' Equivalent preferred authoring shape when the scalar is reusable
dimension: / rank label (no +d) - brand_bucket: 'iif({sales: {dimension: [brand], rank}} < 5, {brand}, ''others'')' Query-dimension formula that replaces evaluation dimension via dimension: / uses rank; not the +d multi-pass attachment pattern

Prefer type: query for authoring and validating these bindings. SQL shown in generated fixture headers is not proof that the corresponding Model Query SQL round trip is supported.

Evaluation semantics (multi-pass)

Let M be the measure-as-dimension expression, K its explicitly authored +d fields, and Q the ordinary query-dimension fields. Its evaluation and attachment grain is G = Q ∪ K, excluding measure-derived labels. Internal aggregation stages do not redefine K.

  1. Fine-grain evaluation. Evaluate every measure-as-dimension at G. Evaluate ordinary output measures at G as well, preserving the states or component measures required for later rollup.
  2. Attach on the complete classification key G. The classification relation must have one scalar value per complete key. If it is not co-located with consuming measures, attach it before grouping those measures by its value. Store-month classification requires store and month in the join, not just +d: store_id. Coarser attachment requires its complete key to be available or provably derivable in the consumer; a finer attachment requires an explicit drill-down and rollup. Preserve NULL-key and query-population semantics.
  3. Roll up to query result grain. Aggregate ordinary measures to { measure-as-dimension fields } ∪ Q. Fields in K are dropped unless also present in Q. If an ordinary measure cannot be safely rewritten to evaluation at G followed by this rollup, compilation fails.

This is the same executable idea as multi-level aggregation via +d (multi-level aggregation), specialized so the drilled measure result becomes a query-dimension field rather than only an intermediate input to a composite formula.

source
  → evaluate measure-as-dimension + other measures at finer evaluation dimension (+d)
  → attach on the complete classification key
  → roll up to query result grain (GROUP BY measure-as-dimension field[, ordinary query-dimension fields])

+d compatibility

Use explicit entity keys on the classification and participating sibling drill-down references. Compatibility is determined by resolved evaluation dimensions and scope, not only the spelling of +d payloads.

Shared +d. Every measure-as-dimension requires an explicit complete key. Several independent labels are allowed only when their keys are equal as sets; declaration order within the key is irrelevant.

Bare references. Do not infer entity grain from sibling measures. Use an explicit +d or dimension: entity key; a bare measure binding is rejected. dimension: is recognized but not reliable for all shapes in the checked build. Adding or removing an output metric must not change classification membership.

Different keys. Independent labels with unequal keys are rejected. A label may not depend on another label in the same query. General bridging between different entity grains requires a separate modeled relation.

Constraints

  1. Classification requires explicit entity keys (+d preferred; dimension: is also recognized). Multiple-label compatibility and safe rollup are contract requirements, not blanket release guarantees; validate the exact query.

  2. General period-modifier combinations are unverified. test_82d exercises a mat rolling-year classifier; this does not establish yoy/pop correctness. Use only combinations with explicit classification/report time scope and result evidence.

  3. Scalar transformations may be inline or named. They must yield one determined value per complete classification key.

  4. Measure dimensions: allowlists and grain-safety rules (grain safety) apply to every measure reference inside the measure-as-dimension expression at its effective evaluation grain.

  5. Cross-dataset auto-join (cross-dataset composition) still aggregates each dataset’s measures to a common query grain; a measure-as-dimension field is part of that query grain after attachment and roll-up.

  6. Group by the same completed classification value that is displayed. One row per complete query key is required, including NULL keys. A classifier does not authorize summing nonadditive measures or inventing inactive entities. Ratios retain their component semantics; an explicit outer aggregate over entity values remains the author's choice.

  7. Source filters apply through existing modifier rules. -d changes grain without removing filters; -f and -df provide the existing scope controls. A label predicate belongs after classification, and a report aggregate threshold after aggregation; neither may alter the inputs of its own classification. History-to-cutoff, rolling-window and current-selection classifiers are distinct business definitions.

Example

first_purchase_month below specifically means the first positive monthly net-sales month within the evaluation scope. purchase_span explicitly evaluates both endpoints at the entity grain and surrounds the finer result with the final aggregation.

first_purchase_month:
    type: measure
    formula: 'MINIF({dt_month}, {sales: {+d: dt_month}} > 0)'

report:
    type: query
    allows: ALL
    columns:
        dimension:
            - first_purchase_month: '{first_purchase_month: {+d: store_id}}'
        sales:
        purchase_span: 'SUM(datediff(day, {first_buy: {+d: store_id}}, {last_buy: {+d: store_id}}))'
  • Query result grain: [first_purchase_month].
  • Fine-grain evaluation via {+d: store_id} on the measure-as-dimension and on purchase_span.
  • Final GROUP BY uses first_purchase_month and drops store_id.

Modifier schema constraints

From dmx_variable_schema.yaml, the modifier object has these structural constraints:

  • dim_dt variants: at most one dim_dt / dim_dt as date / dim_dt as month / etc. per modifier object.
  • +d and dimension: at most one per modifier object (mutually exclusive).
  • -d and dimension: at most one per modifier object (mutually exclusive).
  • +d and -d / -df: may coexist only when their dimension-name sets are disjoint (drill one field, remove another). Same-name intersection is illegal — see modifier composition.
  • Multiple modifiers can coexist in a single modifier object (see combining modifiers for composition examples), subject to the intersection rule above.

Modifier composition

Preserve authored modifier order. Several macros may create intermediate measures; time macros on multi-path functions may instead propagate into each branch. See stacking semantics and its release probes.

Write one YAML key per modifier: {+f: {a: 1, b: 2}}, not repeated +f keys. -df combines dimension removal with filter removal.

Same-dimension modifier conflicts:

The language contract requires a compile error when the field set of +d intersects the field set of either -d or -df within one modifier object. The current build does not enforce this requirement in the checked cases. Do not algebraically cancel to bare {m}, and do not silently rewrite {+d: x, -df: x} into {-f: x} (when the output grain already contains x, -df and -f differ).

Illegal Why
{销量: {+d: 门店, -d: 门店}} Add and remove the same field — no unique silent reading; canceling to {销量} hides typos and diverges from AVG({销量: {+d: 门店}}) (equal weight per store)
{销量: {+d: 门店, -df: 门店}} Must not become {-f: 门店}; grain vs filter-only semantics diverge

Authors who intend a clear reading must write one of: {销量} / SUM({销量: {+d: 门店}}) / {销量: {-d:…\|-df:…\|-f:…}}.
Different dimensions may still coexist, e.g. SUM({销量: {+d: 门店, -d: 品牌}}).

The 2026-10-16 dimension_conflict and dimension_filter_conflict probes both exit 0. They emit a regional window total at customer grain and then sum the repeated totals. The manifest records this behavior as a known compiler gap. It is not an accepted authoring pattern. See release evidence.
