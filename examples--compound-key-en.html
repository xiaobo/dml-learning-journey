Look up an id that repeats across regions

On this page
  • Inspect the input and result
  • Define the lookup once
  • Check the key after a source change
  • Run and interpret the checks

Declare the complete business key and supply lookup arguments in declaration order. id=1 can exist in both east and west; the (id, region) combination must be unique.

Inspect the input and result #

The target maps (1,east) to East and (1,west) to West. Sales are 10 and 20 respectively. The query returns:

Label Sales
East 10
West 20

Joining on id alone cannot distinguish these target rows. This small fixture isolates that boundary; the unit of currency does not change the result.

Define the lookup once #

The target declares dimension: [id, region]. The fact's label is pk({id}, {region}).{D}.label, with arguments in the same order as the target dimension.

完整文件 / Complete file: compound/model.dml 
dialect: duckdb
D:
  type: dataset
  table: DIM
  dimension: [id, region]
  columns:
    id:
    region:
    label:
F:
  type: dataset
  table: FACT
  dimension: [fid]
  columns:
    fid:
    id:
    region:
    amount:
    label: 'pk({id}, {region}).{D}.label'
  measures:
    sales: SUM({amount})
完整文件 / Complete file: compound/setup.sql 
CREATE TABLE DIM(id INTEGER, region VARCHAR, label VARCHAR); INSERT INTO DIM VALUES (1,'east','East'),(1,'west','West'); CREATE TABLE FACT(fid INTEGER,id INTEGER,region VARCHAR,amount INTEGER); INSERT INTO FACT VALUES (1,1,'east',10),(2,1,'west',20);
完整文件 / Complete file: compound/normal.sql 
SELECT label, AGG(sales) FROM MODEL GROUP BY label ORDER BY label

The query reuses this modeled lookup when grouping by label. You do not repeat the join condition in every consumer. Identify your actual complete business key before adapting id, region.

Check the key after a source change #

The verifier compiles, validates and executes the normal data. It then inserts a duplicate (1,east) and expects --validate-only to report DIMENSION_NOT_UNIQUE. After removing the duplicate, validation and complete result comparison pass again.

Validation detects a mismatch between the declared key and current data before you trust lookup results. It does not guarantee uniqueness of future writes. Repair the source, complete key or data; adding DISTINCT to the final output cannot reliably undo an inflated aggregate.

Run and interpret the checks #

Download the complete project and run verify.py as described in its README. It needs your existing dmlc, Python and DuckDB. The script creates a practice database only in the new output directory you specify. The shared verifier records results and diagnostics there.

This example was checked on DuckDB with dmlc 0.3.16, build 2026-11-13. The executable fingerprint and case statuses are in verification-summary.json in the download. Database validation and subsequent execution are independent operations; they do not guarantee a shared snapshot. Verify other engines separately.
