Design a reusable measure

Use this guide after the analysis workflow identifies a missing business calculation. Define its population and intermediate grain before choosing a formula.

Metric-eligibility predicates in intermediate columns

Use an intermediate column when a predicate defines which rows contribute to one metric while the dataset population remains meaningful. Do not classify predicates from names such as state or delete_time; the same-looking condition may instead define the permanent source population.

columns:
    valid_amount:
        description: Row-level amount gated by validity checks
        formula: 'iif(state = 1 and delete_time is null, prod_amount, null)'
measures:
    total: SUM({valid_amount})

SUM ignores NULL, so the aggregate value matches a filtered sum for groups that contain at least one accepted row. It is not generally equivalent to a source WHERE: a group containing only rejected rows disappears under WHERE but can remain as a row with total = NULL under the gate. Sibling counts, joins, windows, and downstream filters can also change.

Use this rewrite only after proving rejected-only group behavior, sibling-metric gates, distinct/join/window population, and absent-vs-present-NULL equivalence. Otherwise retain a row-removing predicate at query/relationship scope or use a minimal documented dataset sql: escape for a permanent source invariant.

Decomposition chain example: tax_rate_effective (rate resolution) → amount_excl_tax (tax conversion) → eligible_amount (metric-specific gate) → SUM({eligible_amount}) (measure). The compiler inlines these intermediate expressions; inspect generated SQL to verify lowering and population behavior.

Derivative measures

Apply report-specific modifiers at the consumption site. Define a derivative measure in .dml only when the modified value must be reused everywhere (e.g. listed in a type: materialize object) or encoded as a named business metric. Use DMX references — never AGG() in measure formulas:

sales_last_month:
    type: measure
    formula: '{sales: pp}'

sales_yoy_growth:
    type: measure
    formula: '{sales: yoy}'

sales_by_product:
    type: measure
    formula: SUM({sales: {+d: product}})

These measures preserve their named transformation; evaluation still depends on the query context and modifier/filter rules.

CTEs and multi-step logic

If your SQL uses CTEs, translate them into one of:

  1. Measures with modifiers (preferred) — if the CTE just adds a filter or dimension field
  2. Column-macros — if the CTE computes a derived column
  3. Separate queries — if the CTE genuinely produces an intermediate result set

Example: SQL with CTE that filters to "completed orders"

-- Original SQL
WITH completed AS (
    SELECT * FROM orders WHERE status = 'completed'
)
SELECT product, SUM(amount) FROM completed GROUP BY product

# DML approach
completed_sales:
    type: measure
    formula: SUM({amount: {+f: {status: 'completed'}}})

-- Model Query SQL: retain the row-removing population restriction
SELECT product, AGG(completed_sales) FROM MODEL
WHERE status = 'completed'
GROUP BY product

Dimension-constrained measures

⚠️ Measure dimensions: contains allowed dimensions. Each inner list is one allowed dimension; the outer list contains alternatives. It does not define dataset row identity or query grouping; those belong to dataset dimension: and query GROUP BY / columns.dimension: respectively. See dimension roles.

Add this constraint only when the metric must be evaluated with a specific dimension:

# "Average order value per customer" — customer_id is required during evaluation
aov_per_customer:
    type: measure
    formula: DIVIDE({sales}, {number_of_transactions})
    dimensions:
        - [customer_id]    # ← the only allowed dimension

Other formulas wanting to use it must explicitly {aov_per_customer: {+d: customer_id}} to evaluate it with customer_id, then roll it up. Document the constraint clearly—it is powerful but can produce surprising results.

Translate SQL into measures

Checklist to turn a metric spec or existing SQL (CTEs, JOINs) into DML measures and boring Model Query SQL (FROM MODEL + AGG(...)).

Start from dimensions, not SQL text:

  • Final query dimension? (e.g. [customer] or [customer, dt_month])
  • Intermediate evaluation dimension? (e.g. [customer] for first purchase)
  • Map: evaluate directly on the dataset dimension → atomic measure; change an evaluation dimension → +d / dimension; constrain allowed dimensions → dimension-constrained measure. Confirm that intermediate and result grains are compatible. If logic truly needs JOIN/subquery and cannot be expressed in DML, stop and reassess—do not bypass Model Query SQL rules.

Dimension-constrained measures (encode CTE-like intermediate rows):

  • Define a measure with one allowed dimension: dimensions: [[customer_id]]
  • Roll up with SUM({that_measure: {+d: customer_id}}) (or AVG, etc.)
  • dimensions: restricts validity; +d on that measure in another formula adds the required dimension field to its evaluation dimension
first_month:
    type: measure
    description: first month with sales > 0 (customer grain only)
    formula: 'MINIF({dt_month}, {sales: {+d: dt_month}} > 0)'
    dimensions:
        - [customer_id]

first_month_sales_by_customer:
    type: measure
    description: sales in customer's first month (customer grain only)
    formula: 'SUMIF({sales: {+d: dt_month}}, {dt_month} = {first_month})'
    dimensions:
        - [customer_id]

first_month_sales_total:
    type: measure
    formula: 'SUM({first_month_sales_by_customer: {+d: customer_id}})'

Inside a customer-restricted measure, {sales: {+d: dt_month}} is that customer's sales in that month.

To group a report by first_month (query dimension = measure result) while aligning sibling measures with +d: customer_id, see measure-as-dimension: Measure-as-dimension.

"Exists / ever" logic (retention, repeat):

  • Customer-level flag: ISNULL(MAXIF(1, <condition>), 0) with dimensions: [[customer_id]]
  • Total with flag: SUM({flag: {+d: customer_id}})
  • Rate: DIVIDE(total_flag, total_customers)

Turn CTEs into measure(s):

CTE pattern DML approach
customer×month aggregation {sales: {+d: [customer, dt_month]}}
first purchase month MINIF({dt_month}, …) at customer grain
per-customer flags customer-grain MAXIF
final KPI SUM({customer_measure: {+d: customer_id}}) and ratios

Target query shape: SELECT AGG(kpi_1), AGG(kpi_2), ... FROM MODEL.

+d in DISTINCTCOUNTIF / SUMIF conditions (cross-grain filtering)

When counting entities at one grain while filtering at another, put {+d: dimension_field} on the measure in the condition — not on the column.

  • Wrong: DISTINCTCOUNTIF({entity: {+d: entity}}, …) — invalid; modifiers only on measures
  • Correct: DISTINCTCOUNTIF({entity}, {sales: {+d: entity}} > 0 AND …)

Cohort scope: define first purchase at an explicit entity grain and history/as-of scope, then compare it with the observation period. Reuse a named classifier only after its allowed dimensions and attachment grain are validated. Inlining a failing expression does not prove the semantics or bypass an incompatible grain. See measure-as-dimension for checked shapes and release defects.

Backward-looking repurchase metrics

Define the business sentence first (who, observation month, window). Build customer-grain flags, then aggregate: SUM({flag: {+d: customer_id}}) or DISTINCTCOUNTIF(...). Review with the business owner before changing semantics.
