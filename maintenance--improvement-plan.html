DML and DMX improvement plan

This plan records proposed compiler and validation work from SQL-to-DML curation. Requirements below are goals. They do not establish released behavior. Release evidence records observations from the selected executable.

Current decisions and evidence

Cross-dataset composition uses FULL OUTER JOIN semantics. Proven presence filters can restrict the population, and the compiler can reduce the emitted join type. Join equality, membership, and missing-row fill remain separate contracts.

The earlier plan permitted NULL-safe composition. The current join NULL equality contract supersedes that policy: key-union composition uses ordinary =, while designated row-preserving attachment uses NULL-safe equality. The 2026-10-16 cross_dataset probe emits ordinary equality.

Query measure-as-dimension has checked +d and dimension: classifier forms on the 2026-10-16 build. Classifiers in materialize.dimension_columns remain deferred. The concept pages and the atomic-versus-composite +f corrections already exist.

The 2026-10-16 audit also records strict join warnings, an omitted output field in two_times, and accepted same-field modifier conflicts that require a rejection diagnostic. These observations replace stale claims that the current classifier probes reproduce the September defects.

Relationship validation requirements

For every migrated join, the validation evidence must identify the following facts.

  • Source join type and equality operator.
  • DML alignment fields and their complete evaluation grain.
  • Observed nullable-key behavior.
  • Presence measures that establish required source membership.
  • Complete dataset-key uniqueness.
  • Output multiplicity and missing-row fill.
  • Parity with an independent result when one is available.

A LEFT population requires a primary presence signal that is non-NULL for every valid primary group. An INNER population requires sound membership signals for both sides. An arbitrary nullable business value is insufficient.

Validation cases must include matched keys, unmatched keys on each side, NULL keys, and duplicate keys. Nullable source equality must be compared with emitted equality at each join site. No blanket acceptance of NULL-to-NULL matching applies to ordinary composition.

The proposed evidence manifest contains these fields.

relationship:
  source_join: left
  source_equality: ordinary
  dml_composition: full_outer
  alignment_keys: []
  primary_presence_measure:
  secondary_presence_measure:
  nullable_key_status: unknown
  uniqueness_status: not_run
  null_semantics_acceptance: missing
  multiplicity_status: not_run

The migration workflow must reject missing or contradictory required evidence. Missing live prerequisites remain not_run.

Filter and aggregation requirements

Atomic-measure +f is supported in checked cases. Composite propagation is valid only when the predicate is intended for every atomic dependency. +f combined with +d must retain all filtered components at the requested fine grain.

The validation suite must distinguish no-match NULL from an explicit ELSE 0. Non-distributive outer calculations must retain the required intermediate grain. A fine-grain aggregate predicate must remain at its declared stage.

The language contract requires rejection when +d intersects either -d or -df in the same modifier object. Query filters must still constrain the report population when a reference blocks their propagation. Missing-row fill at a dependency use site must not create an unrelated outer fill.

Generated SQL requirements

Strict compilation must diagnose invalid or incomplete SQL, including these cases.

  • SQL that does not parse in the selected dialect.
  • Unresolved DML tokens outside comments and string literals.
  • Invalid mixtures of aggregate and non-aggregate projections.
  • Missing or incorrectly bound columns.
  • Logical dataset names emitted as physical relations.
  • Missing, renamed, or reordered output columns that violate the declared contract.
  • Abnormal termination instead of a structured diagnostic.

The current two_times case needs explicit output-contract coverage. Success with one requested time field omitted is not an accepted query result.

Grain, classifier, and ownership requirements

A grouped-row window count must preserve both stages: group source rows at the fine grain, then count those groups at the requested partition. A coarse constant one does not preserve that meaning.

Classifier validation must distinguish the label value, complete entity key, membership population, and report grouping. NULL can be a valid classifier value. A NULL label alone does not prove absence.

Name resolution must retain source ownership. Ambiguous-reference diagnostics must identify the reference site, selected owner, competing candidates, and final name. A logical CTE name must not silently bind to a physical table.

Deferred materialization and SQL alternatives

Measure classifiers in materialize.dimension_columns require a separate design for entity keys, functional dependencies, inherited names, and downstream relationships. Curated fixtures must not depend on this capability before it is verified.

When a supported native form cannot preserve a required contract, the proposed alternative may use a focused SQL dataset for source restrictions, physical windows, explicit joins, aggregate support, deduplication, or a keyless row bag. Each exception needs its invariant, rejected native attempts, reproducer, compiler evidence, owner, and review date.

Delivery and acceptance

Prioritize structured diagnostics and output-contract checks, then relationship evidence, grouped windows, classifier membership, and ownership defects. Update --simplify, --to-dml, and migration evidence after the relevant contracts pass.

Completion requires executable regression evidence for the intended build, explicit live-validation status, and parity evidence where an independent result exists. Documentation updates alone do not complete compiler work. Materialize classifiers remain outside acceptance until a separate design is approved.
