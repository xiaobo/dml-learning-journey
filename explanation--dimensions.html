Dimension semantics and derived grain

Use this guide to reason about dimension behavior when modeling datasets, writing measures, compiling queries, or diagnosing row multiplication. It explains the language model; the normative reference remains DML evaluation semantics.

1. The object model

A dimension field is one named DML field.

A dimension is a list containing one or more dimension fields.

Examples:

[order_id]
[order_id, line_id]
[product_id, dt_month]

Each line above is one dimension. [product_id, dt_month] is one dimension containing two fields.

Measure dimensions: has one additional list level because it can contain alternative allowed dimensions:

dimensions:
  - [customer_id]
  - [account_id, dt_month]

The outer list contains two allowed dimensions. Each inner list is one dimension.

A grand total has no dimension. In measure-modifier syntax, {dimension: []} clears the evaluation dimension to request that context; the empty list is an operation, not a zero-field dimension.

2. The five dimension roles

The list structure is the same, but its DML location determines its behavior:

DML location Role Behavior
Dataset dimension: Dataset dimension Declares the dimension fields whose complete value combination identifies one source row.
Formula plus dimension modifiers Evaluation dimension Determines the dimension at which one measure reference is evaluated.
Query GROUP BY or columns.dimension Query dimension Groups the returned rows and determines what one result row represents.
Materialize dimension: Materialization dimension Defines the grouping and key of the materialized relation.
Measure dimensions: Allowed dimensions Constrains the alternative dimensions at which the measure may be evaluated. It does not declare source identity or query grouping.

These roles are not interchangeable. For example, adding [region] to a measure's dimensions: does not add region to a query result. The query still needs GROUP BY region or columns.dimension: [region].

3. Grain is derived from a dimension

Grain describes what one row represents after a dimension is applied in a specific context.

Context Dimension Derived grain
Order-line dataset [order_id, line_id] One source row per order line
Monthly product query [product_id, dt_month] One result row per product and month
Customer evaluation [customer_id] One intermediate value per customer
Monthly account materialization [account_id, dt_month] One materialized row per account and month

Dimension is the language contract; grain is the row meaning produced by that contract. Use grain to compare row meanings, reason about fan-out, or explain why two dimensions are incompatible. Do not use a desired reporting grain as a substitute for source-row identity.

Adding a dimension field usually produces a finer grain, and removing one usually produces a coarser grain. That intuition is not sufficient proof of compatibility: field derivation, time relationships, measure constraints, and dataset boundaries still matter. Let the compiler validate the declared relationship.

4. Dataset dimension: source-row identity

The dataset dimension contains the fields that identify one physical source row:

Order Line:
    type: dataset
    table: tabOrderLine
    dimension: [order_id, line_id]
    columns:
        order_id:
        line_id:
        product_id:
        net_amount:

Uniqueness applies to the complete [order_id, line_id] value combination. order_id may repeat across lines, and line_id may repeat across orders, while the complete dataset dimension remains unique.

Do not replace the physical identity with a repeatable business grouping. If the source contains several ledger entries for the same [account_id, invoice_id], that list is not a valid dataset dimension even when reports commonly group by it. Use the physical entry key as the dataset dimension and [account_id, invoice_id] as a query or materialization dimension.

pk(...) relies on the target dataset dimension:

  • the lookup arguments correspond to the target dimension fields;
  • their arity and meaning must match that dimension;
  • one lookup must match at most one target row.

The compiler trusts this contract and may lower a lookup to a LEFT JOIN. Duplicate target keys can therefore multiply rows and measures. Adding DISTINCT or GROUP BY to compiled SQL does not repair the model contract.

5. Query dimension: result grouping

In Model Query SQL:

SELECT dt_month, product_id, AGG(net_sales)
FROM MODEL
GROUP BY dt_month, product_id

The query dimension is [dt_month, product_id]. Each result row represents one month and product value combination.

In DML-format Query, the equivalent role is explicit:

Monthly Product Sales:
    type: query
    columns:
        dimension: [dt_month, product_id]
        net_sales: "{net_sales}"

A query without grouping has no query dimension and returns a grand-total context when its measures permit one.

When compatible measures come from different datasets, the compiler aggregates each measure independently to the query grain and then combines the results using shared dimension fields. This avoids the usual aggregate fan-out caused by joining detail rows first. It does not remove the need for valid dataset dimensions or unique pk(...) lookups.

A query-dimension field may also be a measure-as-dimension: a measure result used as a query-dimension field (often bound with {name: {+d: dim}}). That is still a query-dimension role, not dataset dimension: identity. Authoring contract: Measure-as-dimension.

6. Evaluation dimension: one measure reference

The query dimension supplies the starting context for a measure reference. Formula structure, allowed dimensions, and modifiers determine its effective evaluation dimension.

Given query dimension [dt_month, region, brand]:

Measure reference Dimension operation Resulting evaluation dimension
{sales} No dimension modifier Resolved target dimension
{sales: {+d: customer_id}} Add dimension field customer_id [dt_month, region, brand, customer_id]
{sales: {-d: brand}} Remove dimension field brand [dt_month, region]
{sales: {dimension: [region]}} Replace the complete dimension [region]
{sales: {dimension: []}} Clear the dimension Grand-total context

These operations affect only that measure reference; they do not change the query GROUP BY.

-d removes a dimension field but retains a query filter on that field when the compiler pushes filters to the dataset. -df removes the field and blocks its related filter propagation for that reference. Use the latter when a denominator must include values excluded by the query filter. See Measure modifiers for syntax and filter behavior.

7. Allowed dimensions: measure validity

Measure dimensions: restricts valid evaluation dimensions when the business definition requires it:

Revenue per Customer:
    type: measure
    formula: DIVIDE({net_sales}, {active_customers})
    dimensions:
      - [customer_id]

[customer_id] is one closed allowed dimension. It constrains evaluation; it does not identify dataset rows and does not group query output.

An ellipsis permits additional dimension fields while keeping the listed fields required:

dimensions:
  - [customer_id, ...]

This accepts compatible evaluation dimensions that contain customer_id. Omitting measure dimensions: permits any dimension compatible with the measure and its dataset dependencies.

If a formula needs a required dimension field that the query does not provide, add it to the relevant measure reference with +d and perform the required outer aggregation. Do not add a query grouping merely to satisfy an intermediate calculation.

8. Materialization dimension: stored output identity

A materialization dimension declares the grouping and key of stored results:

Monthly Account Balance:
    type: materialize
    dimension: [account_id, dt_month]
    measures: [closing_balance]

dimension_columns: are functionally dependent attributes carried with those keys. They are not additional fields in the materialization dimension. If an attribute is derivable from the materialization dimension, keep it in dimension_columns: rather than changing the stored row identity.

9. Compatibility and validation

Compilation checks the declared model contract:

  • dimension fields resolve through the relevant datasets and column macros;
  • evaluation dimensions satisfy measure dimensions: constraints;
  • modifiers can produce a valid evaluation dimension;
  • measures from different datasets support the query dimension;
  • time modifiers have the required active time field.

Compilation does not connect to live data and cannot prove dataset dimension uniqueness.

Run validateOnly when current evidence is missing or stale. For the compiled query, it runs the generated dataset-key checks on the selected connection and checks database acceptance and planning of the main query through EXPLAIN; it does not execute the main result rows.

Validation evidence covers the model and query contract, connection, and source state observed at validation time. A relevant model change, source refresh, key-policy change, or connection change makes that evidence stale.

If validation reports DIMENSION_NOT_UNIQUE, fix the source key, dataset dimension, overlapping ranges, or source data. If a validation query cannot execute or returns a malformed result, handle VALIDATION_QUERY_FAILED separately; it is not evidence of duplicate keys.

Validation proves neither business correctness nor parity with a trusted report. When migrating an existing query, compare both results on the same filters, time window, and query dimension.
