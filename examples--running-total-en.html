Reuse an ordered running sales measure

On this page

  • Filtering before the window changes its starting point
  • Run and interpret the checks

Define the ordered accumulation as a named measure and declare its allowed grain. This example accumulates sales, not gross margins or monthly distinct customer counts.

Inspect the definition and result #

Monthly sales are January 40 and February 20. running_sales returns January 40 and February 60.

running_sales:
  type: measure
  formula: 'SUM({sales}) OVER (ORDER BY {month} ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)'
  dimensions:
    - [month]

ORDER BY month chooses time order; ROWS accumulates from the first row through the current row. There is no partition, so regions are first combined into monthly sales. dimensions: [[month]] restricts the use grain to month. The ISO-formatted month strings sort chronologically.

完整文件 / Complete file: fixed/model.dml 
dialect: duckdb
F:
  type: dataset
  table: FACT
  dimension: [id]
  columns:
    id:
    region:
    month:
    amount:
  measures:
    sales: SUM({amount})
region_selected:
  type: measure
  formula: '{sales: {-d: month}}'
region_all_months:
  type: measure
  formula: '{sales: {-df: month}}'
running_sales:
  type: measure
  formula: 'SUM({sales}) OVER (ORDER BY {month} ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)'
  dimensions:
    - [month]
完整文件 / Complete file: fixed/running.sql 
SELECT month, AGG(sales), AGG(running_sales) FROM MODEL GROUP BY month ORDER BY month

Other queries can reference the same running_sales. To accumulate separately per region, define the partition and allowed grain, then verify its results. Adding region to a query alone does not establish that behavior.

Filtering before the window changes its starting point #

完整文件 / Complete file: fixed/running_february.sql 
SELECT month, AGG(sales), AGG(running_sales) FROM MODEL WHERE month='2024-02-01' GROUP BY month ORDER BY month

With February alone selected, sales and running sales are both 20. January's 40 is not retained automatically. This is accumulation over the selected result population. For year-to-date through February, use an explicit YTD scope and inspect its inputs; see the cumulative KPI.

A cumulative rank ordered by metric value is not a chronological running total. Ordering is part of the definition. An empty evaluation grain such as {sales: {dimension: []}} requests a total, not an ordered accumulation.

Run and interpret the checks #

Download the complete project and run verify.py as described in its README. It needs your existing dmlc, Python and DuckDB. The script creates a practice database only in the new output directory you specify. The shared verifier records results and diagnostics there.

This example was checked on DuckDB with dmlc 0.3.16, build 2026-11-13. The executable fingerprint and case statuses are in verification-summary.json in the download. Database validation and subsequent execution are independent operations; they do not guarantee a shared snapshot. Verify other engines separately.
